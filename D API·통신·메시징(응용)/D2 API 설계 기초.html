D2 API 설계 기초

0. 한눈에 보는 결론

  • API는 프론트와 백엔드 사이의 계약(contract)이다. 좋은 API 설계란 "문서를 안 봐도 예측 가능한 계약"을 만드는 일이다.
  • REST의 핵심은 자원(명사)은 URI에, 행위(동사)는 HTTP 메서드에 담는 역할 분담이다. /deleteUser?id=3이 아니라 DELETE /users/3.
  • 멱등성(idempotency)은 "같은 요청을 여러 번 보내도 결과(서버 상태)가 한 번 보낸 것과 같다"는 성질이다. 네트워크는 반드시 끊기므로, 재시도해도 되는 요청과 안 되는 요청의 구분이 멱등성에서 나온다.
  • 상태 코드는 클래스(2xx/3xx/4xx/5xx)부터 정확히 고른다. 클라이언트·프록시·모니터링이 모두 코드를 보고 자동으로 행동하기 때문에, "200에 에러 메시지 담기"는 계약 위반이다.
  • 301 vs 302 선택의 실체는 캐시 가능성이다. 301(영구)은 브라우저가 기억해 다음부터 원래 주소를 묻지도 않고 건너뛰고, 302(임시)는 매번 다시 물어본다. 돌이킬 수 없는 쪽이 301이다.
  • 버저닝(versioning)은 깨지는 변경(breaking change)이 생겼을 때만 올린다. 필드 추가는 대개 안 깨지고, 필드 삭제·의미 변경·타입 변경은 깨진다.

1. API 설계는 계약 설계다

프론트엔드(예: Vue 컴포넌트의 Axios 호출)와 백엔드(예: Java 컨트롤러)는 서로의 코드를 보지 못한 채 HTTP 요청·응답의 형태만으로 협업한다. URL이 무엇이고, 어떤 메서드를 쓰고, 성공·실패 시 상태 코드와 본문이 어떻게 생겼는가 — 이 약속의 집합이 API 계약이다.

계약이 좋으면 상대방은 문서를 최소한만 보고도 동작을 예측한다. GET /orders/42가 주문 조회라는 것, 없는 주문이면 404가 온다는 것, 조회를 두 번 해도 아무 일도 일어나지 않는다는 것 — 이 예측 가능성이 REST가 주는 실질적 가치다. 반대로 계약이 자의적이면(모든 요청이 POST, 모든 응답이 200) 매 엔드포인트마다 문서와 소스를 확인해야 하고, 중간 장비(캐시·프록시)와 도구(모니터링·재시도 로직)의 자동화가 전부 무력화된다. 그렇다면 예측 가능성은 어디서 만들어지는가 — 첫 번째 지렛대는 "의미를 어디에 두는가"이고, 그 답이 REST다.

2. REST — 자원은 URI에, 행위는 메서드에

REST(Representational State Transfer)는 프로토콜이 아니라 HTTP를 설계 의도대로 쓰는 스타일이다. 실무에서 지켜야 할 골자는 두 가지다.

  • URI는 자원(resource)을 가리키는 명사로 만든다. 컬렉션은 복수형(/users), 개별 자원은 식별자를 붙여(/users/3), 소속 관계는 계층으로(/users/3/orders) 표현한다.
  • 행위는 HTTP 메서드로 표현한다. URI에 get, create, delete 같은 동사가 들어가기 시작하면 메서드와 역할이 중복되고 있다는 신호다.
동사 URI 방식 (안티패턴) 자원 중심 방식 (REST) ────────────────────────── ───────────────────── POST /getUserList GET /users POST /createUser POST /users POST /updateUser?id=3 PUT /users/3 POST /deleteUser?id=3 DELETE /users/3

오른쪽 방식의 이득은 미학이 아니다. GET은 캐시가 가능해지고, DELETE는 실패 시 재시도해도 안전하다는 판단이 가능해지며(아래 멱등성), 로그와 모니터링에서 "어떤 자원에 어떤 종류의 작업이 몰리는가"가 메서드×경로만으로 집계된다. 의미를 표준 위치에 두면 표준 도구가 전부 공짜로 따라온다.

현실적인 선: 모든 행위가 자원으로 깔끔하게 환원되지는 않는다. "주문 취소" 같은 도메인 동작은 POST /orders/42/cancel처럼 동사를 허용하는 절충이 널리 쓰인다. 원칙은 "기본은 자원 중심, 예외는 의도적으로"다.

3. HTTP 메서드의 성질 — 안전성과 멱등성

2절은 "행위는 메서드에"라고 했지만, 어떤 행위에 어떤 메서드를 쓸지는 아직 정하지 않았다. 그 선택 기준은 "느낌"이 아니라 표준이 정의한 두 가지 성질이다. 안전(safe)은 서버 상태를 바꾸지 않는다는 뜻이고, 멱등(idempotent)은 같은 요청을 1번 보내든 N번 보내든 서버 상태가 같아진다는 뜻이다.

메서드용도안전멱등비고
GET조회OO본문 없이, 캐시 가능
PUT전체 교체(해당 위치에 이 내용을 두라)XO같은 본문으로 반복해도 결과 동일
DELETE삭제XO두 번째부터는 404여도 상태는 동일
POST생성·비멱등 처리XX반복하면 자원이 N개 생길 수 있음
PATCH부분 수정X보장 없음내용에 따라 다름("+1 하라"는 비멱등)

멱등성이 왜 계약의 핵심인가? 네트워크 실패는 "요청이 안 갔는지, 응답만 못 받았는지" 구분해 주지 않기 때문이다. 타임아웃이 났을 때, 멱등한 요청(PUT /users/3)은 그냥 다시 보내면 된다 — 서버에 이미 반영됐어도 같은 결과이므로. 비멱등한 요청(POST /orders)은 다시 보내면 주문이 두 건 생길 수 있다. 그래서 HTTP 클라이언트·프록시의 자동 재시도는 관례상 멱등 메서드에만 적용되고, POST의 안전한 재시도가 필요하면 멱등 키(idempotency key — 클라이언트가 요청마다 고유 ID를 부여하고 서버가 중복을 흡수) 같은 별도 장치를 계약에 추가해야 한다.

흔한 오해: "멱등 = 응답이 항상 같다"가 아니다. DELETE를 두 번 보내면 첫 번째는 204, 두 번째는 404로 응답은 다를 수 있다. 같아야 하는 것은 서버의 상태다(그 자원이 없는 상태).

4. 상태 코드 — 클래스부터 정확히

URI와 메서드가 요청 쪽 계약이었다면, 상태 코드는 응답 쪽 계약이다. 그리고 요청 쪽과 마찬가지로, 상태 코드도 사람이 아니라 기계가 먼저 읽는다. 브라우저는 3xx를 보고 자동 이동하고, 캐시는 200/301을 보고 저장 여부를 정하고, 모니터링은 5xx 비율로 알림을 울리고, 재시도 로직은 4xx(내 잘못 — 다시 보내도 똑같이 실패)와 5xx(서버 사정 — 잠시 후 재시도 가치 있음)를 다르게 다룬다.

클래스의미실무 대표
2xx성공200 OK(본문 있음) · 201 Created(생성, Location 헤더로 새 자원 위치) · 204 No Content(성공, 본문 없음 — 삭제·수정 후)
3xx다른 곳으로 — 리다이렉트301 · 302 · 304 Not Modified(캐시 유효, 본문 생략)
4xx클라이언트 잘못 — 고쳐서 보내라400(요청 형식 오류) · 401(인증 안 됨 — 누구인지 모름) · 403(인가 안 됨 — 누군지 알지만 권한 없음) · 404(자원 없음) · 409(상태 충돌) · 422(형식은 맞으나 의미상 검증 실패)
5xx서버 잘못 — 클라이언트는 죄 없음500(내부 오류) · 502/504(뒤 서버 연결 실패/시간 초과) · 503(과부하·점검)

"200 + 본문에 {"success": false}" 안티패턴 — 상태 코드로는 성공이라 캐시·모니터링·재시도가 모두 속는다. 5xx가 나야 할 장애가 대시보드에서 전부 정상으로 보이고, 실패 응답이 캐시에 저장되는 사고까지 이어진다. 에러의 분류는 상태 코드로, 상세(에러 코드·메시지)는 본문으로 — 역할을 나눠야 한다.

5. 301 vs 302 — 멱등성·캐시 관점의 선택 근거

4절의 표에서 유일하게 "성공도 실패도 아닌" 클래스가 3xx였다. 리다이렉트를 따로 한 절로 다루는 이유는, 여기가 캐시(응답 계약의 관심사)와 멱등성(요청 계약의 관심사)이 정확히 교차하는 지점이라 앞 두 절의 개념 없이는 올바른 선택이 불가능하기 때문이다. 리다이렉트 응답은 "네가 찾는 것은 여기가 아니라 저기"라는 안내이고, Location 헤더가 목적지를 담는다. 301과 302의 차이는 안내문의 뉘앙스 차이가 아니라 클라이언트(특히 브라우저와 캐시)가 그 안내를 얼마나 오래 기억하는가의 차이다.

301 Moved Permanently302 Found (임시 이동)
의미영구 이사 — 앞으로도 계속 저기임시 안내 — 지금만 저기, 다음엔 다시 물어보라
캐시기본적으로 캐시됨. 브라우저가 기억해 두고, 다음부터는 원 주소에 요청조차 안 보내고 바로 새 주소로 감기본적으로 캐시 안 됨. 매번 원 주소에 접속해 안내를 다시 받음
되돌리기서버가 마음을 바꿔도 이미 캐시한 브라우저에게 알릴 방법이 없음서버가 언제든 안내를 바꾸거나 없앨 수 있음
전형적 용도도메인 이전, http→https, URL 구조 개편로그인 후 원래 페이지로, 점검 페이지, A/B 분기

선택 기준을 한 문장으로: "이 안내를 클라이언트가 영원히 기억해도 괜찮은가?" 괜찮으면 301, 조금이라도 바뀔 수 있으면 302다. 301을 잘못 쓰면 사용자의 브라우저 캐시라는, 서버가 손댈 수 없는 곳에 잘못된 안내가 박제된다. 로그인 페이지로의 이동을 301로 보냈다가 로그인 이후에도 계속 로그인 페이지로 끌려가는 사고가 전형적인 예다.

5.1 멱등성 관점 — 307/308이 존재하는 이유

원래 규격상 301/302는 리다이렉트 시 요청 메서드를 유지해야 하지만, 역사적으로 대부분의 브라우저가 POST를 GET으로 바꿔서 따라간다. 이것이 위험한 이유가 정확히 멱등성이다 — 비멱등한 POST(주문 제출)가 안전한 GET(조회)으로 둔갑하면서 본문이 유실되고, 서버는 처리 요청을 받지 못한다. 이 모호함을 없애려고 메서드 변경을 금지한 짝이 추가됐다: 307 Temporary Redirect(302의 엄격판), 308 Permanent Redirect(301의 엄격판). POST 요청을 본문 그대로 다른 곳에서 다시 처리하게 하려면 307/308을 써야 한다.

기억할 2×2: 임시(캐시 안 됨) 영구(캐시됨) 메서드 GET화 허용 302 301 메서드 그대로 유지 307 308

연결: "리다이렉트를 서버가 보낼지, 프론트 JS가 이동할지"의 구분은 C3 클라이언트 vs 서버사이드 리다이렉트.html 참조. 여기서는 서버가 보낼 때 몇 번을 고를지를 다뤘다.

6. 버저닝 — 깨지는 변경을 관리하는 기술

여기까지가 계약을 처음 맺는 기술이었다면, 버저닝은 이미 맺은 계약을 바꾸는 기술이다. API는 배포 후에도 진화한다. 문제는 이미 배포된 클라이언트(사용자 브라우저의 옛 프론트 번들, 외부 연동사)가 옛 계약을 계속 사용한다는 점이다. 그래서 변경을 두 부류로 나누는 감각이 먼저다.

  • 호환 변경(non-breaking) — 응답에 필드 추가, 새 엔드포인트 추가, 선택 파라미터 추가. 옛 클라이언트는 모르는 필드를 무시하면 되므로 버전을 올릴 필요가 없다. (단, 이는 "모르는 필드를 무시한다"가 역직렬화 설정에 반영돼 있을 때 이야기다 — C10 직렬화와 역직렬화.html의 스키마 진화와 같은 문제.)
  • 깨지는 변경(breaking) — 필드 삭제·이름 변경·타입 변경·의미 변경, 필수 파라미터 추가, 상태 코드 의미 변경. 옛 클라이언트가 오동작하므로 새 버전을 열고 옛 버전을 유예 기간 동안 병행 운영해야 한다.
방식모양장점단점
URI 버전/v1/users → /v2/users명시적, 브라우저로 확인 가능, 라우팅 단순"같은 자원인데 URI가 둘"이라는 이론적 어색함
헤더/미디어 타입Accept: application/vnd.api.v2+jsonURI 불변, 협상 유연눈에 안 보이고 도구·캐시 설정이 번거로움
쿼리 파라미터/users?version=2도입 간단빠뜨리기 쉽고 캐시 키 관리가 지저분함

실무 다수파는 URI 버전이다. 어떤 방식이든 요점은 방식 선택보다 운영 규율이다: 버전은 자주 올리는 것이 아니라 최대한 안 올리는 것(호환 변경으로 흡수), 올렸다면 구버전 폐기(deprecation) 일정과 공지까지가 버저닝이다.

7. 흔히 헷갈리는 지점

① "PUT vs PATCH는 취향이다"? — 계약이 다르다. PUT은 "이 내용으로 전체 교체"라서 빠뜨린 필드는 지워지는 것이 원칙적 의미이고, PATCH는 "보낸 필드만 수정"이다. 부분 수정 의도로 PUT을 쓰면 클라이언트마다 해석이 갈려 데이터가 소리 없이 지워진다.

② "401과 403은 비슷하다"? — 401은 "누구인지 모르겠다(인증 실패 — 로그인 창으로)", 403은 "누군지 알지만 안 된다(인가 실패 — 권한 안내로)". 프론트의 후속 동작이 완전히 달라지므로 섞으면 UX가 망가진다.

③ "GET에 본문을 담으면 편한데"? — 규격상 정의되지 않은 영역이라 프록시·캐시·서버 구현이 본문을 버리거나 거부할 수 있다. 복잡한 조회 조건은 쿼리 파라미터로, 정 안 되면 POST /users/search 같은 검색 전용 엔드포인트로 절충한다.

④ "일단 302 대신 301을 쓰면 요청이 줄어 성능에 좋다"? — 맞는 말이지만 그 성능은 되돌릴 수 없음과의 거래다. 확신이 없으면 302(또는 307)로 시작하고, 영구임이 확정된 뒤 301로 승격하는 순서가 안전하다.

★ 8. 언어별 대조

7절까지 다룬 계약의 성질 — 메서드 선택, 상태 코드 분류, 리다이렉트의 캐시 가능성 — 은 언어마다 다른 도구·관용구로 번역된다. 서버가 계약을 선언하는 방식과 클라이언트가 계약을 해석하는 방식이 언어마다 어디까지 강제되고 어디부터 개발자 재량인지를 보면, "계약"이라는 개념 자체가 더 뚜렷해진다.

언어서버 쪽 표현클라이언트 쪽 표현비고
Java Spring @GetMapping/@PostMapping·ResponseEntity.status(...) HttpClient·RestTemplate — 재시도 라이브러리가 멱등 메서드 기본 대상 아래 8.1
JS·TS Express app.get/post(...)·res.status(...) fetch(4xx/5xx도 정상 resolve)·Axios(비2xx를 자동으로 예외 승격) 아래 8.2
Python FastAPI 데코레이터가 메서드·상태 코드·본문 형태를 타입 힌트로 선언 requests — resp.history로 리다이렉트 추적 확인, raise_for_status() 아래 8.3
C++ 표준 웹 프레임워크 없음(Crow·Drogon 등 서드파티) libcurl — CURLOPT_FOLLOWLOCATION으로 리다이렉트 추적을 직접 제어 아래 8.4

8.1 Java — 관례가 계약을 제도화하는 언어

Java 쪽 생태계에서는 개별 개발자의 선택이 아니라 프레임워크 관례가 계약을 강제한다. Spring MVC의 @GetMapping·@PostMapping 같은 어노테이션(annotation — 코드에 붙이는 메타데이터 주석. 컴파일 후에도 남아 있다가 프레임워크가 실행 시점에 읽어 동작을 결정한다)은 "이 메서드는 이 URI와 이 HTTP 메서드에 응답한다"는 2절의 REST 매핑을 선언부 한 줄로 못박는다. 애플리케이션이 기동될 때 스프링 컨테이너는 이 어노테이션들을 읽어 라우팅 표(HandlerMapping)를 만드는데, 이 과정에서 같은 URI·메서드 조합이 중복 선언되면 기동 자체가 실패한다 — 계약 위반이 요청이 들어온 뒤 조용히 드러나는 대신, 배포 이전 단계에서 걸러지는 구조다.

상태 코드도 같은 방식으로 코드에 새겨진다. ResponseEntity는 4절의 상태 코드 클래스를 반환 타입 수준에서 명시하도록 강제하고, PUT·PATCH를 어노테이션으로 구분해 두면 3절의 멱등성 구분이 라우팅 표에 그대로 드러난다. 

@RestController
@RequestMapping("/orders")
class OrderController {

    @GetMapping("/{id}")
    ResponseEntity<Order> get(@PathVariable Long id) {
        return orderService.find(id)
            .map(ResponseEntity::ok)                 // 200
            .orElseGet(() -> ResponseEntity.notFound().build()); // 404
    }

    @PostMapping
    ResponseEntity<Order> create(@RequestBody OrderRequest req) {
        Order created = orderService.create(req);    // 비멱등 — 반복 호출 시 여러 건 생성
        return ResponseEntity
            .created(URI.create("/orders/" + created.getId())) // 201 + Location
            .body(created);
    }

    @PutMapping("/{id}")
    ResponseEntity<Void> replace(@PathVariable Long id, @RequestBody OrderRequest req) {
        orderService.replace(id, req);                // 멱등 — 여러 번 보내도 결과 동일
        return ResponseEntity.noContent().build();     // 204
    }
}

클라이언트 쪽에서도 같은 원칙이 확인된다. Spring Retry 같은 재시도 도구는 예외 없이 "멱등한 연산에만 적용하라"고 안내하는데, 이는 프레임워크가 POST 안에 담긴 업무 의미까지는 알 수 없기 때문이다 — 어떤 POST가 안전하게 재시도해도 되는지는 계약을 설계한 사람만 아는 정보다.

Java 관점의 통찰: 어노테이션 기반 라우팅의 진짜 이점은 코드가 짧아지는 것이 아니라, 계약 위반의 발견 시점을 앞당긴다는 데 있다. URI·메서드 중복은 런타임 첫 요청이 아니라 애플리케이션 기동 시점에 예외로 터진다. 다만 이 안전망은 "선언부에 적을 수 있는 것"에만 적용된다 — 어떤 POST가 멱등하게 설계됐는지 같은 업무 의미는 어노테이션이 대신 검증해 주지 않으므로, 관례가 계약의 형식은 강제해도 계약의 의도까지 강제하지는 못한다.

8.2 JS·TS — 계약 해석이 라이브러리 옵션으로 갈리는 언어

JS·TS 진영은 정반대의 그림을 보여준다. 같은 HTTP 요청을 다루는 브라우저 내장 fetch와 서드파티 라이브러리 Axios가 "무엇을 실패로 볼 것인가"를 서로 다르게 정의한다는 사실 자체가, 4절에서 말한 "상태 코드는 계약이다"를 소비자 쪽에서 뒤집어 보여주는 사례다.

fetch가 반환하는 프로미스(Promise — 비동기 작업의 결과를 나중에 담을 상자 역할을 하는 객체)는 네트워크 자체가 실패했을 때만 reject된다. 서버가 404나 500을 응답해도 그것은 "정상적으로 도착한 응답"이므로 프로미스는 resolve되고, 실패 여부는 response.ok(상태 코드가 200~299인지)를 개발자가 직접 확인해야 한다. Axios는 이 판정을 라이브러리가 대신 맡아, 2xx 밖의 응답을 자동으로 예외로 승격시켜 catch로 보낸다. 

// fetch: 4xx/5xx도 정상 resolve — "실패"의 판정을 소비자가 직접 내려야 한다
const res = await fetch('/orders/42');
if (!res.ok) {                                    // res.ok === (200 <= status < 300)
  throw new Error(`요청 실패: ${res.status}`);      // 404여도 여기서 명시적으로 예외가 된다
}
const order = await res.json();

// axios: 2xx 밖이면 라이브러리가 알아서 reject — try/catch로 실패가 자동 분리된다
try {
  const { data } = await axios.get('/orders/42');
} catch (err) {
  if (err.response) console.log(err.response.status); // 404 등 — 여기 도달했다는 것 자체가 판정 결과
}

TS를 얹어도 이 간극은 메워지지 않는다. TS의 구조적 타이핑(structural typing — 타입 이름이 아니라 멤버 구성이 같으면 호환으로 판정하는 방식)은 컴파일 시점에만 존재하고 컴파일 결과물에서는 완전히 사라진다(타입 소거). 즉 await res.json()의 반환값에 Order 타입을 붙여도, 그것은 "실제로 그런 모양이라는 보장"이 아니라 개발자의 선언일 뿐이다 — 상태 코드를 검사하지 않고 지나간 404 응답의 본문(에러 메시지 JSON)도 컴파일러는 Order로 믿고 통과시킨다.

JS·TS 관점의 통찰: "상태 코드로 성공·실패를 가른다"는 4절의 원칙이 실제로 지켜지는지는 프로토콜이 아니라 클라이언트 라이브러리의 기본 옵션에 달려 있다(Axios에도 이 판정 기준을 바꾸는 validateStatus 옵션이 있다). TS 타입은 이 판정을 대신해 주지 않는다 — 컴파일 타임에 사라지는 주석이므로, 상태 코드 검사를 생략하면 "타입은 맞는데 실제로는 에러 응답"인 값이 아무 경고 없이 흘러간다. 계약 검증은 결국 런타임 코드로 명시해야 한다.

8.3 Python — 타입 힌트가 계약이 되고, 흔적이 눈에 남는 언어

Python은 서버·클라이언트 양쪽에서 대조적인 모습을 보인다. 서버 쪽 FastAPI는 원래 정적 타입이 없는 언어에 타입 힌트(type hint — 변수·매개변수의 예상 타입을 주석처럼 표시하는 문법으로, 그 자체로는 강제력이 없다)를 붙여 이를 런타임 검증 규칙으로 승격시킨다. 클라이언트 쪽 requests는 반대로, 5절·5.1절에서 다룬 리다이렉트·멱등성 문제를 코드로 직접 확인해 볼 수 있게 흔적을 남겨 준다. 

from fastapi import FastAPI, status
from pydantic import BaseModel

class OrderIn(BaseModel):
    item: str
    quantity: int

class OrderOut(OrderIn):
    id: int

app = FastAPI()

@app.post("/orders", response_model=OrderOut, status_code=status.HTTP_201_CREATED)
def create_order(order: OrderIn):
    # 타입 힌트가 곧 계약 — 요청 본문이 이 모양과 안 맞으면
    # 함수가 실행되기도 전에 422로 자동 응답된다
    ...

response_model은 반환값을 인터프리터가 실행 중에 다시 한 번 검사하게 만든다 — 함수가 실수로 계약에 없는 필드를 내보내면, 컴파일 언어라면 타입 오류로 잡힐 일이 Python에서는 응답을 내보내는 순간의 검증 실패(서버 오류)로 나타난다. 정적 타입 검사가 없는 대신 인터프리터가 매 요청마다 이 검사를 대신 치르는 셈이다. 

import requests

r = requests.get("https://example.com/old-path")
print(r.status_code)          # 200  ← 최종 목적지의 코드
print(r.url)                  # https://example.com/new-path  ← 실제로 도착한 곳
print(r.history)              # [<Response [301]>]  ← 거쳐 온 리다이렉트의 흔적

r2 = requests.get("https://example.com/old-path", allow_redirects=False)
print(r2.status_code, r2.headers["Location"])   # 301 /new-path  ← 서버가 실제로 보낸 원본

r2.raise_for_status()         # 4xx/5xx일 때만 HTTPError — 예외 승격은 "요청할 때만" 일어난다

Python 관점의 통찰: FastAPI의 타입 힌트는 컴파일 타임 보장이 아니라 매 요청마다 반복되는 런타임 검사다 — Java의 제네릭처럼 한 번 컴파일하면 끝나는 것이 아니라, 인터프리터가 요청을 받을 때마다 값을 다시 들여다본다. 그 대신 정적 타입이 못 잡는 것(예: 응답 본문이 실제로 계약과 다른데도 타입만 붙여 놓은 경우)까지 걸러낸다는 이점이 있다. 클라이언트 쪽에서는 allow_redirects=False로 리다이렉트 추적을 끄면 5.1절에서 말한 "POST가 리다이렉트를 타면서 GET으로 둔갑해 본문이 사라지는" 문제를 history에서 눈으로 재현해 볼 수 있다 — 문서로 읽는 것과 직접 확인하는 것은 이해의 깊이가 다르다.

8.4 C++ — 계약이 곧 이진 호환성 경계이기도 한 언어

C++에는 표준 웹 프레임워크가 없어, 고수준 클라이언트가 "알아서" 해 주던 일들 — 리다이렉트 따라가기, 상태 코드 분류, 재시도 — 이 전부 계약 해석 코드로 눈앞에 드러난다. 게다가 C++은 계약을 동적 링크로 배포하는 경우가 많아, API 설계가 또 하나의 층 — ABI(application binary interface — 소스 코드가 아니라 컴파일된 바이너리끼리 호환되기 위한 저수준 약속. 함수 호출 규약·구조체의 메모리 배치 등을 포함한다) — 와 맞물린다.

libcurl의 CURL* 핸들이 그 예다. 내부 필드가 헤더에 전혀 노출되지 않는 불투명 포인터(opaque pointer — 가리키는 대상의 내부 구조를 호출자에게 감추고 포인터만 넘겨주는 방식)라서, libcurl 개발자가 내부 구조체의 레이아웃을 바꿔도 이미 컴파일된 클라이언트 바이너리는 재컴파일 없이 새 버전 라이브러리와 다시 링크만 하면 그대로 동작한다. 소스 코드 재컴파일이 항상 전제되는 고수준 언어에서는 잘 드러나지 않는 구분이지만, C++에서 라이브러리를 동적 링크로 배포하는 순간 API(무엇을 호출할 수 있는가)와 ABI(그 호출이 바이너리 수준에서 어떻게 맞물리는가)를 따로 관리해야 한다. 

CURL* curl = curl_easy_init();   // 불투명 포인터 — 내부 구조체 크기·배치는 알 필요도, 알 수도 없다
curl_easy_setopt(curl, CURLOPT_URL, "https://example.com/orders");

// ① 리다이렉트를 따라갈지 자체가 옵트인 — 기본값은 "따라가지 않음"
curl_easy_setopt(curl, CURLOPT_FOLLOWLOCATION, 1L);
curl_easy_setopt(curl, CURLOPT_MAXREDIRS, 5L);        // 무한 리다이렉트 방어도 직접

// ② 301/302에서 POST를 GET으로 바꿀지도 직접 선택 (5.1절의 그 문제)
curl_easy_setopt(curl, CURLOPT_POSTREDIR, CURL_REDIR_POST_301 | CURL_REDIR_POST_302);
//    이 옵션이 없으면 libcurl은 관행대로 GET으로 바꿔 따라간다

curl_easy_perform(curl);

long code = 0;
curl_easy_getinfo(curl, CURLINFO_RESPONSE_CODE, &code);   // ③ 상태 코드는 그냥 숫자
if (code >= 500) { /* 재시도 가치 있음 */ }               //    분류·분기도 내 몫
curl_easy_cleanup(curl);                                   // ④ 수명 관리도 내 몫

C++ 관점의 통찰(메모리·수명·ABI): 응답 본문은 콜백으로 조각조각 전달되므로, 받아 담을 버퍼의 수명이 요청 수행 시간 전체보다 길어야 한다 — 지역 std::string에 담고 스코프를 벗어나면 그 뒤에 도착한 조각이 이미 해제된 메모리를 건드린다. 고수준 언어에서는 GC가 감춰 주던 문제다. 여기에 더해, CURL*처럼 API 경계를 불투명 포인터로 설계하는 것은 단순한 캡슐화 취향이 아니라 ABI 안정성 전략이다 — 이 설계 덕분에 라이브러리 내부 구현이 바뀌어도 배포된 바이너리는 재컴파일 없이 계속 호환된다. 정리하면: "리다이렉트를 따라간다", "4xx면 예외를 던진다"는 프로토콜의 성질이 아니라 클라이언트 라이브러리의 정책이며, C++에서는 그 정책을 담은 API 자체가 바이너리 호환성 경계이기도 하다. 계약(D2의 주제)을 설계할 때 "클라이언트가 알아서 하겠지"를 전제로 삼으면 안 되는 이유가 여기서도 확인된다.

9. 함께 알면 좋은 것

  • API 문서화와 스키마 우선 설계 — 계약을 코드보다 먼저 문서(OpenAPI)로 확정하는 흐름. D11 API 문서화와 스키마.html에서 다룬다.
  • REST 너머의 스타일 — 오버페칭·스트리밍 등 REST의 한계와 GraphQL·gRPC의 답은 D3 REST vs GraphQL vs gRPC.html 참조.
  • 페이지네이션(pagination) — 컬렉션 조회 계약의 필수 요소. offset 방식과 커서(cursor) 방식의 트레이드오프.
  • 멱등 키(idempotency key) — 결제처럼 POST인데 중복이 치명적인 곳에서, 클라이언트 생성 고유 키로 서버가 중복 요청을 흡수하는 패턴.
  • HATEOAS — 응답에 다음 행동 링크를 담는 REST의 원전적 이상. 실무 채택은 드물지만 "계약의 자기 서술"이라는 문제의식은 유효하다.

10. 한 장 요약

  • API 설계 = 예측 가능한 계약 설계. 자원은 URI(명사), 행위는 메서드(동사)에.
  • 멱등성 = N번 보내도 상태가 1번과 동일. 재시도 가능 여부의 근거이며 GET·PUT·DELETE는 멱등, POST는 아니다.
  • 상태 코드는 기계가 읽는다 — 클래스(2/3/4/5xx)부터 정확히. 200에 에러 담기 금지.
  • 301은 캐시되어 되돌릴 수 없고 302는 매번 다시 묻는다 — "영원히 기억돼도 되는가"로 고른다. 메서드 보존이 필요하면 307/308.
  • 버저닝은 깨지는 변경에만. 호환 변경으로 흡수하는 것이 상책, 올렸으면 구버전 폐기 계획까지.

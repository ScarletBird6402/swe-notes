M3 빌드 번들 검사 방법론

0. 한눈에 보는 결론

  • 빌드를 거친 순간 소스와 산출물은 다른 물건이다 — 제거(트리셰이킹)·변형(미니파이)·주입(환경값)·치환이 일어난 뒤이므로, 소스를 읽고 산출물을 추측하는 것은 검사가 아니라 예측이다.
  • 그래서 원칙은 하나: 산출물에 대한 질문("들어갔는가/빠졌는가/몇 번 들어갔는가")은 산출물에서 답한다.
  • 기본 검사 도구는 소박하다 — 문자열 탐색(grep·strings). 요령은 변환을 살아남는 마커(문자열 리터럴·에러 메시지·API 경로)를 찾는 것이다. 함수·변수 이름은 미니파이가 지우므로 마커가 못 된다.
  • 미니파이 ≠ 난독화: 전자는 크기 축소(이름 단축·공백 제거), 후자는 의도적 읽기 방해다. 그리고 둘 다 보안 수단이 아니다 — 번들에 넣은 것은 형태만 바뀔 뿐 전부 사용자 손에 있다.
  • 소스맵은 산출물↔소스의 대응표다 — 에러 좌표 복원뿐 아니라 "번들 안에 무엇이 얼마나 들어갔는가"를 역산하는 검사 도구이며, 동시에 공개 배포하면 소스가 노출되는 양날의 검이다.

1. 소스 ≠ 산출물 — 추측과 검사의 차이

M2 빌드 방식 vs dev 서버.html의 결론에서 이어받자: 빌드는 소스를 그대로 포장하는 것이 아니라 제거하고, 바꾸고, 끼워 넣는다. 트리셰이킹은 "안 쓴다고 증명된" 코드를 들어내고, 미니파이는 이름과 구조를 다시 쓰고, 환경값은 리터럴로 구워지며, 헬퍼·폴리필·런타임 코드는 소스에 없던 것이 들어온다. 그 결과, 다음 질문들에 소스 코드는 답을 줄 수 없다:

  • 들어갔는가 — "내가 고친 코드가 지금 배포된 번들에 반영돼 있나?" "이 기능 플래그 분기가 산출물에 남아 있나?"
  • 빠졌는가 — "디버그 로그·테스트 훅이 배포물에서 제거됐나?" "서버 전용 모듈·비밀 값이 클라이언트 번들에 새어 들어가지 않았나?"
  • 몇 번 들어갔는가 — "같은 라이브러리가 버전 둘로 중복 포함되지 않았나?"(번들 비대·미묘한 버그의 단골 원인)

전부 산출물의 사실 확인 문제인데, 흔한 실무 습관은 소스에서 답을 찾는 것이다 — "소스에 있으니 들어갔겠지", "import를 지웠으니 빠졌겠지". 이 추측이 배신당하는 경로는 M2가 보여 줬다(트리셰이킹의 오판, 캐시된 옛 산출물, 환경 분기). 방법론의 전환은 단순하다: 산출물 파일을 열어 직접 확인한다. 그러려면 산출물이 어떻게 생겼는지부터 알아야 한다 — 열어 봤을 때 읽을 수 있어야 검사가 되기 때문이다.

2. 산출물 읽기의 최소 지식 — 미니파이 vs 난독화, 그리고 번들의 생김새

빌드된 JS 번들을 처음 열면 한 줄짜리 알파벳 죽이 나온다. 이것을 읽으려면 두 변환을 구분해야 한다.

미니파이(minification)난독화(obfuscation)
목적크기 축소 — 전송량·파싱 시간 절감읽기 방해 — 역공학 비용 올리기
수단공백·주석 제거, 지역 이름 단축(userCount→n), 동등 문법 축약제어 흐름 뒤틀기, 문자열 인코딩, 더미 코드 삽입
기본 적용표준 빌드에 기본 포함별도 도구로 선택 적용(성능 비용 있음)
검사에 주는 영향이름은 사라지되 문자열 리터럴은 남는다문자열까지 인코딩될 수 있음 — 마커 탐색 무력화

검사 관점의 핵심은 표의 마지막 행이다. 미니파이는 의미를 보존하는 압축이라 동작에 필요한 것 — 문자열 리터럴, 프로퍼티 이름(외부 계약이라 못 줄이는 것), API 경로 — 은 남긴다. 반면 난독화는 그것마저 감추려 든다(대신 실행 시 복원 비용을 치른다). 일반 웹 앱의 번들은 미니파이까지만 적용된 경우가 대부분이므로, "살아남는 문자열"이 존재한다는 사실이 3절 방법론의 발판이 된다. 번들의 구조도 알아 두면 읽기가 쉬워진다: 번들러는 모듈들을 함수 단위로 접어 배열·맵으로 담고 자체 로더로 잇거나, 스코프를 통합(scope hoisting)해 하나로 편다 — 어느 쪽이든 청크 파일 여러 개 + 진입점이라는 겉모양이고, 빌드 설정에 따라 모듈 경계 주석이나 라이선스 주석이 남아 "어느 라이브러리가 이 구간인가"의 단서가 된다.

개념 함정 — 미니파이·난독화는 보안 수단이 아니다: 둘 다 가역이다. 미니파이는 포매터 한 번이면 구조가 복원되고, 난독화도 실행 가능한 코드인 이상 결국 분석된다(실행기가 해독할 수 있으면 사람도 할 수 있다). 따라서 "난독화했으니 API 키를 넣어도 된다"는 성립하지 않는다 — 클라이언트 산출물에 들어간 것은 전부 공개된 것이며, 비밀은 애초에 번들에 넣지 않는 것 외의 답이 없다. 이 확인("비밀이 번들에 없는가") 역시 3절 절차의 단골 질문이다.

3. 검사 절차 — 살아남는 마커를 문자열로 찾는다

2절의 지식을 절차로 조립하면 네 단계다. 도구는 어느 환경에나 있는 문자열 탐색이면 충분하다.

① 검사 대상 산출물을 특정한다. "지금 배포된 그 파일"이어야 한다 — 로컬 dist/가 아니라, 배포 서버·CDN에서 실제로 내려받은 파일이 정본이다(로컬 빌드와 배포물이 같다는 보장은 없다 — 그게 바로 검사하려는 명제일 수 있다). 브라우저 개발자 도구의 네트워크 탭에서 받은 파일을 저장하는 것이 가장 확실하다.

② 변환을 살아남을 마커를 고른다. 함수명·변수명은 미니파이가 지우니 부적격. 좋은 마커는 문자열 리터럴이다 — 사용자에게 보이는 문구, 에러 메시지, API 경로("/api/orders"), 로그 태그. 수정 반영 여부를 확인하려면 이번 수정에만 있는 문자열을 고른다. 마땅한 게 없으면 검사용 마커를 소스에 심고 빌드하는 것도 정당한 기법이다(확인 후 제거). 

# ③ 산출물에서 마커를 탐색한다
grep -c "주문번호가 중복되었습니다" dist/assets/index-a1b2c3.js   # 있는가 + 몇 번인가
grep -o "api/v[0-9]*/orders" dist/assets/*.js | sort | uniq -c    # API 경로 버전 혼재 검사

# "빠졌는가" 검사 — 나오면 안 되는 것들
grep -n "console.debug\|TEST_HOOK" dist/assets/*.js
grep -rn "sk_live_\|BEGIN RSA" dist/          # 비밀 값 유출 검사(패턴은 조직 규약대로)

④ 판정한다 — 단, "안 나옴"의 해석은 신중하게. 마커가 나오면 "들어갔다"는 확정이다(문자열 우연 일치만 배제하면). 반대로 안 나온다고 "없다"가 확정되지는 않는다 — 문자열이 조각나 연결되거나(템플릿 결합), 유니코드 이스케이프로 인코딩되거나, 압축 서빙된 파일을 풀지 않고 검사했을 수 있다. "없음"을 판정할 때는 반드시 살아 있어야 할 대조군 마커 (예: 앱 이름, 항상 있는 에러 문구)가 나오는지 먼저 확인해 검사 자체의 유효성을 세운다 — 대조군도 안 나오면 없는 게 아니라 검사 방법이 틀린 것이다.

중복 검사의 요령: 같은 라이브러리의 이중 포함은 크기 이상 신호로 먼저 오는 경우가 많다. 라이선스 주석·패키지 고유 문자열을 grep -c로 세어 2 이상이면 의심 — 확정과 원인 추적(어느 두 경로로 들어왔나)은 4절의 소스맵 분석이 맡는다.

4. 소스맵 — 대응표로 하는 정밀 검사

문자열 탐색은 "있다/없다"에 강하지만 "무엇이 얼마나, 왜 들어갔는가"에는 약하다. 그 정밀도를 주는 것이 소스맵(source map)이다 — 산출물의 각 위치가 원본 소스의 어느 파일·행·열에서 왔는지를 기록한 대응표로, 빌드 시 .map 파일로 함께 생성된다(산출물 말미의 //# sourceMappingURL=… 주석이 연결 고리).

원래 용도는 에러 좌표 복원이다 — 배포 번들의 index-a1b2c3.js:1:48213을 OrderList.vue:87로 되돌리는 것. 그런데 대응표를 반대로 집계하면 검사 도구가 된다: 산출물의 바이트를 원본 파일별로 귀속시키면 "이 번들 몇 KB가 어느 모듈에서 왔는가"의 지도가 나온다. 번들 분석기(트리맵 시각화 도구들, source-map-explorer류)가 하는 일이 정확히 이것이고, 1절의 세 질문이 여기서 한꺼번에 풀린다 — 무엇이 들어갔는지(목록), 무엇이 무거운지(면적), 무엇이 중복인지(같은 패키지가 두 영역). 

# 소스맵 기반 구성 분석 — "이 번들은 무엇으로 이루어졌는가"
npx source-map-explorer dist/assets/index-*.js
# → 모듈별 바이트 귀속 트리맵: 중복 포함·의외의 대형 의존성이 면적으로 보인다

단, 소스맵은 공개 여부를 설계해야 하는 산출물이다. 대응표에는 원본 소스 전체가 사실상 담기므로(sourcesContent 필드), 공개 서버에 .map을 올리는 것은 소스 저장소를 여는 것과 크게 다르지 않다. 표준 절충은 "생성은 하되 공개 서빙하지 않고, 에러 수집기에만 업로드"다 — 진단 능력은 유지하면서 노출은 막는 배치. 반대로 소스가 이미 공개된 오픈소스 프로젝트라면 공개가 무해하다 — 어느 쪽이든 기본값에 맡기지 말고 결정해야 할 항목이다.

흔히 헷갈리는 지점

  • "소스를 확인했으니 산출물도 그럴 것이다?" — 이 문서 전체의 반례가 답이다. 소스는 산출물의 입력이지 내용이 아니다. 배포 사고 조사에서 "소스 봤어요"는 "산출물은 안 봤어요"와 같은 말이다.
  • "grep에 안 나오니 번들에 없다?" — 3절 ④의 함정. 문자열 분해·인코딩·압축(gzip/브로틀리 상태로 저장된 파일)· 난독화가 탐색을 무력화할 수 있다. "없음" 판정에는 대조군 마커 확인이 선행 조건이다.
  • "미니파이됐으니 아무도 못 읽는다?" — 포매터 한 번이면 구조가 돌아오고, 프로퍼티명·문자열은 애초에 남아 있다. 읽기 어려움과 읽기 불가능은 다르며, 보안 경계는 산출물 안이 아니라 산출물에 무엇을 넣는가에 있다.
  • "node_modules에 있으니 번들에 들어갔다?" — 실물 층(M1)과 산출물은 다른 층이다. 트리셰이킹이 대부분을 들어냈을 수도, 반대로 설치 안 된 것이 CDN 외부 참조로 실행될 수도 있다. 번들 포함 여부는 번들에서만 확정된다.
  • "소스맵은 디버깅 편의 기능일 뿐이다?" — 검사 도구이자 노출면이기도 하다(4절). "공개 서버에 .map이 올라가 있는가"는 배포 점검 목록에 들어갈 항목이다.

★ 언어별 대조 — 산출물 직접 검사의 언어별 도구함

"산출물에서 답한다"는 원칙은 범언어적이고, 역사적으로는 오히려 컴파일 언어 쪽이 원조다 — 언어별로 산출물의 형태와 여는 도구가 다를 뿐이다.

단골 질문수정 반영·중복·비밀 유출리소스 포함·상수 인라이닝·클래스 충돌데이터 파일 포함·로드 경로심벌 존재·버전 문자열·스트립 여부

JS·TS — 문자열 탐색 + 소스맵 분석, 그리고 "타입은 산출물에 없다"

3·4절이 이미 JS 도구함이므로 여기서는 TS 특이점을 짚는다. TS의 타입은 컴파일 시 소거된다 — 즉 타입만 바꾼 수정은 산출물 diff가 0이다. 이는 검사에 두 방향으로 작용한다: "타입 리팩터링이 배포물에 영향 없음"을 확인하고 싶을 때는 산출물 비교 (빌드 두 번 후 diff)가 그것을 증명해 주는 반가운 성질이고, 반대로 "수정이 반영됐는지 번들에서 확인하자"는 3절 절차에 타입 수정은 원리적으로 걸리지 않는다는 한계이기도 하다. 또 하나의 TS 함정은 enum·데코레이터처럼 런타임 코드를 생성하는 타입 기능이다 — "타입은 소거된다"의 예외들이라, 이들의 수정은 산출물에 나타난다. 소거 규칙의 경계를 아는 것 자체가 번들 검사의 전제 지식인 셈이다: 

// 빌드 재현성 확인 관용구 — 같은 소스에서 두 번 빌드해 산출물을 비교
npm run build && mv dist dist-a
npm run build && diff -r dist-a dist    # 해시 파일명 때문에 내용 기준 비교 도구를 쓰기도

Java — jar는 zip이다: 목록·클래스·상수까지 열어 본다

Java 산출물 검사의 출발점은 "jar/war는 그냥 zip"이라는 사실이다. 목록 조회로 리소스 포함 여부(M2의 jar 리소스 함정을 검사하는 법이 바로 이것)를, 클래스 역어셈블로 컴파일 결과를 확인한다: 

jar tf app.jar | grep "config/rules.json"     # 리소스가 실제로 패키징됐는가
unzip -p app.jar META-INF/MANIFEST.MF          # 매니페스트(버전·메인클래스) 확인

# 상수 인라이닝 검사 — 이 클래스가 들고 있는 값은 무엇인가
javap -c -p -classpath app.jar com.example.OrderService | grep -A2 "TIMEOUT"

javap가 특히 값진 지점이 컴파일 타임 상수 인라이닝 검사다 — static final 상수는 사용처 바이트코드에 리터럴로 복사되므로(M1 Java 절), "상수를 고쳐 배포했는데 옛 값으로 동작"하는 사고의 확정 진단은 사용처 클래스를 역어셈블해 리터럴을 직접 보는 것뿐이다. fat jar(의존성을 모두 풀어 한 jar에 담는 패키징)에서는 같은 FQCN(완전 수식 클래스명)의 클래스가 서로 다른 라이브러리에서 두 번 들어오는 충돌이 단골 질문이다 — 클래스패스에서는 먼저 발견된 쪽이 조용히 이기므로, jar tf 목록에서 중복 FQCN을 세는 것이 JS의 중복 번들 검사와 정확히 평행한 절차다. JVM 기제 덤: "지금 로드된 클래스가 어느 jar에서 왔는가"는 실행 중 getProtectionDomain().getCodeSource()로 물을 수 있다 — 산출물 검사의 런타임 버전이다.

Python — wheel도 zip이고, 진짜 질문은 "지금 로드된 게 어느 파일인가"다

Python의 배포 산출물(wheel)도 zip이라 목록 검사는 같은 문법이다 — M2에서 본 "패키징 시 데이터 파일 누락"의 확정 진단이 이것이다: 

zipinfo dist/myapp-1.2.0-py3-none-any.whl | grep "templates/"   # 데이터 파일 포함 확인
pip show -f myapp | head -30                                     # 설치된 실물의 파일 목록

# 가장 자주 필요한 검사 — "지금 import된 코드는 어느 파일인가"
python -c "import myapp; print(myapp.__file__)"

마지막 한 줄이 Python 검사의 정수다. 인터프리터 언어라 "번들"이 없는 대신, 어느 실물이 로드되는가가 같은 자리의 질문이 된다 — 개발 중 소스 트리와 설치된 패키지가 공존하면(editable 설치·중복 설치·sys.path 순서) "고친 파일과 실행되는 파일이 다른" 사고가 나고, __file__ 확인이 그 확정 진단이다. 바이트코드 캐시(__pycache__의 pyc)는 소스 타임스탬프로 무효화되지만, 배포 방식에 따라(소스 없이 pyc만 배포, 타임스탬프 리셋) 옛 바이트코드가 도는 변종도 있다 — dis 모듈로 로드된 함수를 역어셈블하면 "메모리에 있는 코드"를 직접 볼 수 있다. 인터프리터 관점 통찰: Python의 검사 도구가 유난히 런타임 쪽(__file__·dis·introspection)에 발달한 것은, 산출물 층이 얇은 대신 로드 경로가 동적이라 사고가 "패키징"보다 "어느 것이 로드됐나"에서 나기 때문이다.

C++ — strings의 원조: 심벌과 문자열로 바이너리를 읽는다

"산출물에서 문자열을 찾는다"는 방법론의 원조가 유닉스 strings다 — 바이너리에서 출력 가능한 문자열만 추려 주는 이 도구는 C·C++ 바이너리 검사의 기본기였고, JS 번들 grep은 그 후예다: 

strings app | grep "build_config"        # 구워진 버전·설정 문자열 확인 (O8 연계)
nm -C app | grep "OrderService"          # 심벌 존재 확인 (-C: 이름 장식 복원)
objdump -d app | less                    # 역어셈블 — 최후의 정밀 검사
file app                                  # 스트립 여부·아키텍처 식별

C++ 특유의 주의점은 심벌의 부재가 코드의 부재를 뜻하지 않는다는 것이다 — 인라인 확장된 함수는 호출부에 녹아 심벌이 없고, 링크 타임 최적화(LTO)와 스트립(디버그·심벌 정보 제거)은 지도를 통째로 지운다. 스트립된 release 바이너리에서는 문자열 리터럴이 사실상 유일한 마커라, 빌드 시점에 버전·설정 문자열을 의도적으로 굽는 규율(빌드 ID, --version 출력)이 검사 가능성을 만드는 투자가 된다. 미니파이·난독화의 대응물도 짚을 만하다: 컴파일 자체가 이름을 기계어로 바꾸는 가장 강한 "난독화"지만, 이름 장식(name mangling)된 심벌·RTTI 문자열·예외 메시지는 남는다 — nm -C가 장식을 복원해 주는 것은 소스맵의 원시적 조상인 셈이다. ABI 관점 덤: 공유 라이브러리의 중복·버전 혼재 검사는 ldd(어느 .so가 실제로 로드되는가)로 한다 — JS의 중복 번들, Java의 중복 FQCN과 같은 질문의 네이티브판이다.

함께 알면 좋은 것

  • 번들 분석기(트리맵) — 소스맵·모듈 그래프에서 "무엇이 몇 KB인가"를 시각화(rollup-plugin-visualizer, webpack-bundle-analyzer, source-map-explorer류). 중복 포함·비대 의존성 발견의 표준 도구.
  • 크기 예산(size budget) 게이트 — 산출물 크기 상한을 파이프라인 검사로 두고 초과 시 실패시키는 관행. "검사를 매 빌드 자동으로"의 가장 싼 형태로, 의도치 않은 대형 의존성 유입을 즉시 드러낸다.
  • 산출물 diff — 이전 배포물과 새 산출물의 차이를 보는 검사. "이번 배포에서 번들에 무엇이 달라졌는가"를 리뷰 대상으로 만들며, 수정 반영 확인(3절)의 체계화판이다.
  • 비밀 스캐너 — 키·토큰 패턴을 저장소뿐 아니라 빌드 산출물에도 돌리는 검사. "소스엔 없는데 빌드가 주입"하는 경로(환경값 구워짐 — O8)가 있으므로 산출물 스캔이 별도로 필요하다.
  • 재현 가능한 빌드(reproducible build) — 같은 소스·같은 도구에서 비트 단위 동일 산출물이 나오게 하는 목표. 달성되면 "이 산출물이 이 소스에서 나왔는가"를 해시 비교 하나로 검증할 수 있다 — 검사 방법론의 종착지이며, 상세는 M12 빌드 재현성과 환경 독립성.html 소관.

한 장 요약

  • 빌드는 제거·변형·주입을 수행하므로 소스는 산출물의 증거가 아니다 — "들어갔나/빠졌나/몇 번인가"는 산출물에서 확인한다.
  • 미니파이(크기 축소, 문자열은 생존) vs 난독화(읽기 방해, 문자열도 감춤)를 구분하되, 둘 다 보안이 아니다 — 번들에 넣은 것은 공개된 것.
  • 검사 절차: ① 배포된 실물 확보 → ② 변환을 살아남는 마커(문자열 리터럴) 선정 → ③ grep → ④ 판정 — 단 "안 나옴"은 대조군 마커 확인 후에만 "없음"으로 해석.
  • 소스맵 = 산출물↔소스 대응표: 에러 좌표 복원 + 바이트 귀속 분석(무엇이 얼마나 들어갔나)의 검사 도구이자, 공개 시 소스 노출이라는 관리 대상.
  • 언어별 도구함: JS는 grep+분석기(타입은 산출물에 없음), Java는 jar tf·javap(리소스·인라인 상수·중복 FQCN), Python은 zipinfo·__file__(포함 여부·로드 경로), C++은 strings·nm·ldd(심벌·구운 문자열·중복 so) — 형태는 달라도 질문은 같다.

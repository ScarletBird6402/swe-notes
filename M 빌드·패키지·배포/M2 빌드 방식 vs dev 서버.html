M2 빌드 방식 vs dev 서버

0. 한눈에 보는 결론

  • dev 서버와 빌드는 "같은 앱을 띄우는 두 방법"이 아니라, 같은 소스에서 출발해 서로 다른 산출물을 만드는 두 개의 생산 라인이다.
  • dev 서버의 목적은 반복 개발 속도 — 요청 시점 변환·메모리 서빙·최적화 생략·HMR로 "수정 → 확인" 주기를 초 단위로 줄인다.
  • 빌드의 목적은 배포 품질 — 전체를 미리 변환·번들·최적화(트리셰이킹·미니파이)해 사용자가 받을 최종 산출물을 만든다.
  • HMR(hot module replacement)의 원리는 모듈 그래프의 국소 교체다: 변경된 모듈만 다시 변환해 실행 중인 페이지에 밀어 넣고, 나머지 상태는 유지한다.
  • "dev 서버에선 되는데 빌드에선 깨진다"(또는 그 역)는 미스터리가 아니라 두 라인의 구조적 차이의 귀결 — 변환 도구·최적화 유무·환경 분기·파일 처리 규칙이 다르다.
  • 따라서 최종 확인은 반드시 빌드 산출물로 한다 — dev 서버에서의 확인은 "개발이 편했다"이지 "배포물이 검증됐다"가 아니다.

1. 두 개의 생산 라인 — 왜 실행 경로가 둘인가

프론트엔드 프로젝트의 명령 두 개 — dev와 build — 를 나란히 놓고, 각각이 소스에 무슨 일을 하는지부터 보자.

dev 서버: 소스 ──(요청 올 때, 그 파일만 변환)──▶ 메모리에서 즉시 응답 변환 최소·최적화 없음·모듈을 낱개로 서빙 빌드: 소스 ──(미리, 전체를 변환·연결·최적화)──▶ dist/ 디스크 산출물 번들링·트리셰이킹·미니파이·해시 파일명

왜 하나로 안 되는가. 두 국면의 요구가 정반대이기 때문이다. 반복 개발 국면의 지표는 "저장 후 화면 반영까지 몇 초인가"다 — 하루에 수백 번 도는 주기라 1초와 10초의 차이가 생산성을 지배한다. 그래서 dev 서버는 미리 다 만들지 않는다: 브라우저가 요청한 모듈만 그때그때 변환하고, 결과를 디스크에 쓰지 않고 메모리에서 응답하며, 비싼 최적화는 전부 생략한다. 최종 확인·배포 국면의 지표는 반대로 "사용자가 받는 산출물이 얼마나 작고 빠르고 자기완결적인가"다. 그래서 빌드는 시간이 걸리더라도 전체 모듈 그래프를 분석해 하나로 연결(번들링)하고, 안 쓰는 코드를 제거(트리셰이킹)하고, 이름을 줄이고 공백을 없애며(미니파이), 캐싱을 위해 파일명에 내용 해시를 박는다.

결과적으로 브라우저가 실행하는 코드가 두 경로에서 물리적으로 다르다 — dev에서는 변환만 거친 낱개 모듈 수백 개, 빌드에서는 최적화로 재조립된 소수의 번들. "같은 소스니까 같은 동작"이라는 직관이 왜 배신당하는지의 뿌리가 여기다(3절). 만들어진 산출물이 서버에서 어떻게 서빙되는가 — 정적 파일 서버·경로 해석 — 는 O2 정적 파일 서빙 모델.html의 소관이고, 이 문서는 "무엇이 만들어지는가"까지를 다룬다.

2. HMR 원리 — 새로고침 없이 모듈만 갈아 끼우기

dev 서버의 속도를 완성하는 마지막 조각이 HMR이다. 파일 저장 후 전체 새로고침을 하면 앱 상태(입력 중인 폼, 열어 둔 모달, 스토어 값)가 전멸한다 — "로그인하고 3단계 들어가서 확인"을 매 수정마다 반복하게 만드는 비용이다. HMR은 이것을 모듈 그래프의 국소 교체로 해결한다:

파일 저장 → dev 서버가 감시(watch)로 감지, 그 모듈만 재변환 → WebSocket으로 브라우저에 "모듈 X가 바뀌었다" 통지 → 클라이언트 런타임이 새 모듈을 받아 그래프에서 옛 모듈과 교체 → 교체를 받아들일(accept) 경계에서 갱신 처리 — 나머지 앱 상태는 그대로

핵심 개념은 수용 경계(accept boundary)다. 모듈 하나가 바뀌면 그것을 import하는 모듈들도 영향을 받는데, 그래프를 거슬러 올라가다 "이 갱신은 내가 처리할 수 있다"고 선언한 모듈(예: 프레임워크 플러그인이 컴포넌트 파일마다 자동으로 심는 HMR 핸들러)을 만나면 전파가 거기서 멈추고 그 서브트리만 교체된다. Vue·React의 단일 파일 컴포넌트가 저장 즉시 상태 유지 교체되는 것은 프레임워크 통합이 이 경계를 컴포넌트 단위로 만들어 주기 때문이다. 경계를 끝까지 못 찾으면(예: 진입점이나 전역 부수효과 모듈 수정) HMR은 포기하고 전체 새로고침으로 폴백한다 — HMR이 "가끔 전체 리로드가 되는" 것은 버그가 아니라 설계된 안전판이다.

짚을 점: HMR은 dev 서버 산출물에만 존재하는 메커니즘이다 — 감시자도, WebSocket 채널도, 클라이언트 런타임도 빌드 산출물에는 없다. 즉 HMR이 매끄럽게 도는 화면은 정의상 "빌드와 다른 코드"가 도는 화면이며, 이 사실이 다음 절의 어긋남 목록으로 직결된다. 또 하나 — HMR의 상태 유지는 양날이다: 모듈은 새것인데 살아남은 상태는 옛 코드가 만든 것이라, 오래 켜 둔 dev 세션은 어떤 새로고침으로도 재현 안 되는 혼합 상태에 빠질 수 있다. "이상하면 일단 수동 새로고침"이 HMR 시대의 1차 처방인 이유다.

3. 어긋남의 해부 — dev에서 되는데 빌드에서 깨지는 이유

1·2절의 구조 차이를 사고 유형으로 번역하면, "dev에서 되는데 빌드에서 깨진다"의 원인은 대부분 다음 넷 중 하나다.

① 변환 파이프라인 자체가 다르다. 속도를 위해 dev 서버는 빠른 변환기를, 빌드는 분석력 좋은 번들러를 쓰는 구성이 흔하다(대표적으로 Vite: dev는 esbuild 변환 + 네이티브 ESM 서빙, 빌드는 Rollup 번들 — 공식 문서가 두 경로의 차이를 명시한다). 두 도구의 문법 지원·플러그인 처리·모듈 해석 규칙의 미세한 차이가 그대로 "한쪽에서만 나는 에러"가 된다.

② 최적화는 빌드에만 있다. 트리셰이킹은 "정적 분석상 안 쓰는" 코드를 제거하는데, 부수효과로만 동작하는 import(전역 등록, 폴리필, CSS 주입 — import "./register-widgets"처럼 값을 안 쓰는 import)를 "안 쓰는 코드"로 오판해 제거할 수 있다 — dev에는 트리셰이킹이 없으므로 dev에서만 동작한다. 미니파이는 함수·클래스 이름을 줄이므로, 이름에 의존하는 코드(fn.name으로 분기, 클래스명 기반 직렬화)가 빌드에서만 깨진다.

③ 파일·경로 처리 규칙이 다르다. 고전은 파일명 대소문자다 — 대소문자 무시 파일 시스템(Windows·기본 macOS)의 dev 서버는 import "./Header"가 header.vue를 찾아 주지만, 빌드나 대소문자 구분 환경(리눅스 기반이 대부분인 빌드·배포 머신)에서는 못 찾는다. 동적 import의 경로가 변수일 때(빌드 도구가 정적으로 추적 못 하는 형태), 공개 자산 디렉터리와 모듈 자산의 처리 차이도 이 부류다.

④ 환경 분기가 다른 가지를 탄다. process.env.NODE_ENV류 분기는 dev와 빌드에서 다른 코드를 실행하도록 설계된 것이다 — 프레임워크의 개발 모드 경고·상세 에러·검증 코드는 빌드에서 통째로 제거된다. 개발 모드의 관대한 동작(경고만 하고 진행)에 기대던 코드가 빌드에서 조용히 다르게 동작하는 원인이다. 역방향 어긋남 — 빌드에선 되는데 dev에서 깨진다 — 도 같은 구조에서 나온다: HMR이 만든 혼합 상태(2절), dev 전용 프록시·오버레이와의 간섭, 모듈을 낱개로 서빙할 때만 드러나는 순환 참조의 평가 순서 문제가 대표다.

개념 함정 — "확인했다"의 대상 착오: dev 서버에서 본 화면은 빌드 산출물의 미리보기가 아니다. 다른 도구가 다른 변환을 거쳐 만든 다른 코드다. 그러므로 "dev에서 확인했으니 배포해도 된다"는 문장은 성립하지 않는다 — 배포 전 최종 확인은 build 산출물을 로컬에서 서빙해(preview류 명령) 하는 것이며, 자동화 파이프라인이 빌드를 매번 도는 것도 이 어긋남을 조기에 드러내는 장치다. 산출물에 무엇이 들어갔는지 직접 검사하는 절차는 M3 빌드 번들 검사 방법론.html이 이어받는다.

흔히 헷갈리는 지점

  • "dev 서버가 느려졌다 = 빌드도 느려진다?" — 별개다. dev의 병목은 요청 시점 변환·감시자·HMR 전파이고 빌드의 병목은 전체 분석·최적화다. 한쪽 튜닝이 다른 쪽에 안 통하는 이유이며, 성능 이슈는 어느 라인의 문제인지부터 특정해야 한다.
  • "HMR로 반영 안 되는 수정은 버그다?" — 설정 파일·환경 변수·전역 초기화 코드처럼 수용 경계 밖의 변경은 전체 리로드나 서버 재시작이 정상 동작이다. "저장했는데 안 바뀐다"의 절반은 HMR 한계가 아니라 재시작이 필요한 변경을 HMR로 기대한 것이다.
  • "트리셰이킹이 제거했다면 원래 안 쓰는 코드다?" — 트리셰이킹의 기준은 "정적 분석으로 사용이 증명되는가"다. 부수효과 import·동적 접근처럼 분석 밖의 사용은 "안 씀"으로 오판될 수 있고, 그래서 라이브러리들은 부수효과 없음을 선언 (sideEffects 필드)해 제거 가능 범위를 명시한다 — 제거는 증명의 결과이지 사실의 보증이 아니다.
  • "소스에 있으니 산출물에도 있다 / 소스에 없으니 산출물에도 없다?" — 양방향 모두 틀릴 수 있다(제거·주입·치환). 산출물에 대한 질문은 소스가 아니라 산출물에서 답한다 — M3의 주제.
  • "빌드는 프론트엔드 얘기다?" — 두-라인 구조는 범언어적이다. 백엔드도 "IDE에서 실행"과 "패키징 산출물 실행"이 같은 어긋남 축을 갖는다(5절 Java·Python 항목이 정확히 이것이다).

★ 언어별 대조 — 각 언어의 "dev 경로 vs 최종 산출물" 어긋남

"빠른 반복 경로"와 "최종 산출물 경로"의 분리는 프론트엔드 용어를 벗기면 모든 언어에 있다 — 언어마다 그 틈이 어디에 생기는지가 다를 뿐이다.

JS·TS — 두 라인이 명시적으로 다른 도구인 생태계, 그리고 타입 검사의 부재

이 문서의 본산이다. 현행 표준 도구 Vite는 두 라인의 분리를 설계 원칙으로 명시한다 — dev는 브라우저의 네이티브 ESM 로딩에 기대 모듈을 낱개로 서빙하며 esbuild로 요청 시점 변환하고, 빌드는 Rollup으로 전체를 번들·최적화한다. HMR 수용 경계는 API로 노출된다: 

// HMR 수용 경계 — 이 코드는 dev 산출물에만 존재하고 빌드에서는 제거된다
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    rerender(newModule.render);   // 새 모듈로 국소 갱신, 앱 상태는 유지
  });
}

TS 사용자에게는 전용 함정이 하나 더 있다. 속도를 위해 dev 서버(와 esbuild류 변환기)는 타입 검사를 하지 않는다 — 타입을 벗겨내기만 하는 transpile 모드다. 즉 "dev 서버가 잘 돈다"는 타입 에러가 없다는 뜻이 아니며, 타입 검사는 별도 프로세스 (tsc --noEmit·IDE·빌드 단계 플러그인)가 담당한다. 반대로 빌드에 타입 검사를 물려 두면 "dev는 돌던 코드가 빌드에서 타입 에러로 실패"가 되는데, 이는 어긋남이 아니라 검사 시점의 설계다. 런타임 기제 관점 특기점: dev의 낱개 모듈 서빙에서는 모듈 평가 순서가 import 그래프를 충실히 따르지만, 번들은 모듈들을 하나의 스코프로 접으며 순서를 재배열한다 — 순환 참조·최상위 부수효과의 타이밍이 두 경로에서 달라지는 근본 이유다.

Java — "IDE에서 실행"과 "jar로 실행"이라는 두 라인

Java의 빠른 반복 경로는 IDE의 증분 컴파일 위에 있다 — 저장 시 바뀐 파일만 재컴파일되고, 디버그 세션 중에는 JVM의 핫스왑이 메서드 본문 변경에 한해 실행 중 클래스를 교체한다(시그니처·필드 추가는 불가 — HMR보다 훨씬 좁은 교체 능력). Spring DevTools는 2-클래스로더 구조(라이브러리는 유지, 앱 클래스만 새 로더로)로 "빠른 재시작"을 제공한다 — 상태를 유지하는 HMR이라기보다 싼 전체 리로드에 가깝다. 어긋남의 고전은 실행 형태 차이에서 온다: 

// IDE 실행(클래스패스 = 디렉터리)에서는 되고, jar 패키징 후 깨지는 고전
File f = new File(getClass().getResource("/config/rules.json").toURI());
// jar 안에서 리소스는 "파일"이 아니라 압축 엔트리 — toURI()→File 변환이 실패한다

// 두 환경 모두에서 동작하는 형태: 스트림으로 읽는다
try (InputStream in = getClass().getResourceAsStream("/config/rules.json")) { … }

IDE의 클래스패스는 풀린 디렉터리라 리소스가 진짜 파일이지만, 패키징 산출물(jar) 안에서는 압축 스트림이다 — "개발 환경에선 되는데 배포 jar에서 깨진다"의 Java 대표 사례이며, 구조적으로는 3절 ③(경로·파일 처리 규칙 차이)과 같은 자리다. JVM 기제 덤: 개발 중 자주 재시작되는 JVM은 JIT 워밍업이 리셋되므로 dev에서의 체감 성능은 배포 성능의 근거가 못 된다 — 성능 확인 역시 "최종 산출물로, 데워진 상태에서"가 원칙이다.

Python — 리로드는 "교체"가 아니라 "재시작"이고, 빌드의 함정은 패키징에 있다

인터프리터 언어라 변환 단계가 없으니 두-라인 문제가 없을 것 같지만, 두 자리에서 되살아난다. 첫째, dev 서버의 auto-reload는 HMR과 원리가 다르다 — 파일 변경을 감지하면 프로세스를 통째로 재시작한다(uvicorn --reload, Flask 디버그 모드). 모듈 교체가 아니라 전멸 후 재기동이라 상태는 전부 사라지며, 이것이 안전한 이유는 Python의 모듈 캐시(sys.modules) 때문이다 — 부분 교체(importlib.reload)는 옛 객체를 참조하는 곳을 다 갱신하지 못해 "반은 새 코드, 반은 옛 코드"를 만들기 쉬워, 도구들이 재시작을 택한 것이다: 

# uvicorn --reload 의 동작: HMR이 아니라 감시 + 전체 재시작
# (상태 유지 없음 — 대신 혼합 상태 위험도 없음)
uvicorn app:api --reload

# importlib.reload가 위험한 이유의 축약형
import handlers
h = handlers.Handler()      # 옛 클래스의 인스턴스
importlib.reload(handlers)  # 모듈 객체는 갱신되지만
isinstance(h, handlers.Handler)  # → False. 옛 클래스와 새 클래스는 다른 객체다

둘째, "빌드에서 깨진다"의 Python형은 패키징이다. 소스 트리에서는 옆에 있던 데이터 파일(템플릿·정적 파일·모델 파일)이 wheel·컨테이너 이미지에는 선언(package-data 설정) 없이는 포함되지 않는다 — "저장소 체크아웃에선 되는데 설치된 패키지에선 FileNotFoundError"라는, Java의 jar 리소스 함정과 정확히 평행한 사고다. 객체 모델 관점 특기점: Python은 데코레이터·임포트 부수효과로 임포트 시점에 등록이 일어나는 코드가 많아, 리로드·패키징으로 임포트 순서·횟수가 달라지면 등록 상태가 달라진다 — "실행 경로가 바뀌면 부수효과 타이밍이 바뀐다"는 3절 ④의 인터프리터판이다.

C++ — debug/release가 곧 두 라인이고, 어긋남은 미정의 동작이 메운다

C++의 빠른 반복 경로는 증분 빌드다 — 바뀐 번역 단위만 재컴파일하고 다시 링크한다(빌드 시스템의 의존성 그래프가 dev 서버의 감시자 역할). 실행 중 코드 교체는 언어 표준에 없고, 핫 리로드가 꼭 필요한 도메인(게임 엔진 등)은 로직을 동적 라이브러리로 분리해 런타임에 다시 로드하는 구조를 직접 만든다 — ABI 안정성과 상태 이관을 전부 수동 관리해야 하는, HMR의 수제작 버전이다. 이 언어의 진짜 두-라인 어긋남은 debug 구성과 release 구성 사이에 있다: 

int sum(const std::vector<int>& v) {
    int s = 0;
    for (size_t i = 0; i <= v.size(); ++i)   // off-by-one: 마지막 반복이 범위 밖
        s += v[i];
    return s;
}
// debug 빌드: 검사 활성 STL이 범위 밖 접근을 즉시 잡아 준다 (표준 아닌 디버그 기능)
// release 빌드: 검사 없음 + 최적화 — 조용히 쓰레기 값을 더하거나,
//               UB를 전제로 한 최적화가 루프 자체를 다르게 변형할 수 있다

debug 빌드는 assert·반복자 검사·초기화 패턴 채움 같은 안전망을 켜고 최적화를 끈다. release는 그 반대다 — 그리고 미정의 동작(undefined behavior)이 있는 코드는 최적화 수준에 따라 증상이 달라진다: 컴파일러는 "UB는 없다"를 전제로 코드를 변형하므로, debug에서 우연히 멀쩡하던 코드가 release에서만 깨지는(또는 그 역) 일이 구조적으로 발생한다. "dev에서 되는데 빌드에서 깨진다"의 가장 오래된 원형이 여기 있는 셈이다. 컴파일 타임 관점 덤: NDEBUG로 assert가 통째로 소거되므로 부수효과 있는 식을 assert 안에 쓰면 release에서 그 코드가 사라진다 — JS의 "빌드가 개발 전용 분기를 제거"(3절 ④)와 같은 자리의, 더 오래된 함정이다.

함께 알면 좋은 것

  • 빌드 산출물 미리보기 — 빌드 결과를 로컬에서 서빙해 보는 명령(vite preview류). "최종 확인은 빌드 산출물로"를 가장 싸게 실천하는 도구로, 배포 전 마지막 관문으로 습관화할 가치가 있다.
  • 자동화 파이프라인의 빌드 게이트 — PR마다 빌드를 실제로 돌려 두-라인 어긋남을 병합 전에 드러내는 장치. "dev만 돌려 본 코드"가 본선에 못 들어오게 하는 구조적 방어다.
  • 소스 맵(source map) — 변환·최적화된 산출물과 원본 소스의 대응표. 빌드 산출물에서 난 에러를 소스 좌표로 되돌려 주는 다리로, 두 라인이 다르다는 사실을 "디버깅 가능한 다름"으로 만들어 준다.
  • 개발·운영 환경 일치 원칙(dev/prod parity) — 12-Factor의 원칙 중 하나. 두 라인의 차이를 0으로 만들 수는 없으므로, 차이를 알려진 목록으로 관리하고 그 밖의 축(런타임 버전·의존성·서비스)은 일치시키는 방향.
  • E2E 테스트의 대상 선택 — 종단 테스트를 dev 서버에 물리면 빠르지만 검증 대상이 배포물과 달라진다. 파이프라인의 E2E는 빌드 산출물(preview·스테이징)에 물리는 것이 원칙이고, dev 서버 E2E는 개발 중 빠른 피드백용으로 역할을 나눈다.

한 장 요약

  • dev 서버와 빌드는 같은 소스의 두 생산 라인 — 전자는 반복 속도(요청 시점 변환·메모리·무최적화·HMR), 후자는 배포 품질(전체 변환·번들·트리셰이킹·미니파이)에 최적화돼 있고, 산출물이 물리적으로 다르다.
  • HMR = 감시 → 변경 모듈 재변환 → WebSocket 통지 → 수용 경계에서 국소 교체(상태 유지). 경계 못 찾으면 전체 리로드 폴백이 정상이며, 오래된 HMR 세션은 재현 불가한 혼합 상태일 수 있다.
  • 어긋남의 4대 원인: ① 변환 도구가 다름 ② 최적화(트리셰이킹의 부수효과 import 제거·미니파이의 이름 파괴)는 빌드에만 ③ 파일·경로 규칙(대소문자!) ④ 환경 분기(NODE_ENV)가 다른 가지를 탐. 역방향(빌드는 되는데 dev가 깨짐)은 HMR 혼합 상태·평가 순서가 주범.
  • 최종 확인은 빌드 산출물로 — preview로 로컬 확인, 파이프라인에서 매번 빌드, E2E는 산출물에 물린다. dev 확인은 배포 검증이 아니다.
  • 범언어 평행: Java는 IDE 클래스패스 vs jar 리소스, Python은 리로드(재시작)와 패키징 누락, C++은 debug/release + UB — 이름만 다른 같은 구조다.

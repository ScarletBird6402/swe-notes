E18 ORM 삭제·벌크 DML과 세션 정합

0. 한눈에 보는 결론

  • ORM에는 삭제·수정의 두 경로가 있다: 객체를 하나씩 다루는 객체 경로(session.delete(obj) — unit of work를 통과)와, WHERE 조건으로 집합을 한 번에 다루는 벌크 경로(DELETE ... WHERE ... 직행).
  • 세션은 identity map(동일성 지도 — "한 PK에 한 객체"를 보장하는 세션 내부의 객체 캐시)으로 자기가 아는 세계를 관리한다. 객체 경로는 이 지도를 통과하고, 벌크 경로는 이 지도를 우회한다.
  • 대표 함정: 벌크 DML 직후 "DB에는 반영됐는데 세션 안 객체는 옛 상태" — 이미 로드해 둔 객체가 삭제·수정 사실을 모른 채 살아 있고, 그 낡은 객체로 이어지는 로직이 조용히 틀린다.
  • 우회를 보정하는 다이얼이 synchronize_session이다: 'evaluate'(WHERE를 파이썬에서 재평가해 지도 갱신) / 'fetch'(영향받은 PK를 조회·RETURNING으로 받아 갱신) / False(보정 안 함). 2020년대 중반 기준 기본값은 'auto' — RETURNING 지원 DB(PostgreSQL·Oracle 등)에선 fetch, 아니면 evaluate.
  • 단건 삭제 N번 반복 → 복합키 tuple_().in_() 벌크 1문장 전환의 대가: 왕복은 N→1로 줄지만, cascade·이벤트·identity map 정합 같은 객체 경로의 서비스가 전부 꺼진다. 전환은 성능 선택이 아니라 어느 세계의 규칙으로 지울 것인가의 선택이다.

1. 두 경로 — 같은 "삭제"라는 말, 다른 세계

ORM에서 "지운다"는 코드는 두 가지로 쓸 수 있고, 생성되는 SQL이 비슷해 보여서 같은 일로 오해하기 쉽다. (이하 SQLAlchemy를 대표 예시로 쓰지만, 두 경로의 구분은 ORM 일반의 구조다.) 

# 객체 경로: 객체를 먼저 손에 쥐고, 세션에게 "이 객체를 지워 달라"
user = session.get(User, 7)      # SELECT — 객체가 세션에 로드됨
session.delete(user)             # 삭제 '예약' (unit of work에 기록)
session.commit()                 # 이때 DELETE 실행 + 관련 정리 일괄 수행

# 벌크 경로: 객체 없이, 조건에 맞는 '집합'을 DB에서 직접 지워 달라
session.execute(
    delete(User).where(User.active == False)
)                                # DELETE ... WHERE ... 가 곧바로 나감
객체 경로 (unit of work)벌크 경로 (bulk DML)
단위객체 1개씩WHERE에 맞는 집합 전체
SQL 왕복로드 SELECT + 객체당 DELETE1문장
cascade·이벤트·연관 정리ORM이 수행수행 안 함(DB 제약의 ON DELETE만 동작)
세션(identity map)과의 관계지도를 통과 — 항상 정합지도를 우회 — 보정 없으면 어긋남

표의 마지막 행이 이 문서의 주제다. "우회"가 정확히 무엇을 우회한다는 것인지 알려면, 먼저 세션이 들고 있는 지도 — identity map — 가 무엇인지부터 보아야 한다.

2. identity map — 세션이 아는 세계의 지도

세션(persistence context라고도 부른다)은 자기가 로드한 객체를 PK를 키로 하는 딕셔너리에 보관한다. 이것이 identity map이고, 두 가지 일을 한다.

  • 동일성 보장 — 같은 세션에서 같은 PK를 두 번 조회하면 같은 객체(같은 참조)를 돌려준다. 한 트랜잭션 안에서 "user 7"이 두 개의 다른 객체로 존재하며 서로 다른 값을 들고 있는 혼돈을 원천 차단한다.
  • 변경 추적의 기반 — unit of work는 이 지도 위의 객체들을 관찰해 무엇이 바뀌었는지(dirty), 무엇이 삭제 예약됐는지 기록했다가, flush 시점에 SQL로 번역한다.
세션(identity map) DB ┌───────────────────────┐ ┌──────────────┐ │ (User, 7) → 객체 A │ ←로드→ │ users 테이블 │ │ (User, 9) → 객체 B │ │ │ └───────────────────────┘ └──────────────┘ 객체 경로의 모든 읽기·쓰기는 이 지도를 거친다 = 지도와 DB가 어긋날 틈이 (flush 시점 관리 하에) 없다

요점: 객체 경로의 세계에서 "진실"은 지도와 DB의 합의이고, ORM은 그 합의를 유지하는 기계다. 그런데 벌크 DML은 이 기계에 알리지 않고 DB에 직접 말을 건다 — 다음 절의 함정이 정확히 여기서 나온다.

3. 함정 해부 — 벌크 DML은 지도를 모른 채 DB만 바꾼다

u = session.get(User, 7)                 # 지도에 (User,7)→u 등록. u.active == False 라 하자
session.execute(
    delete(User).where(User.active == False),
    execution_options={"synchronize_session": False}   # 보정 없음(4절)일 때
)
# DB: user 7 행은 이미 사라졌다
print(u.active)          # 세션 안 u는 멀쩡히 살아서 옛 값을 답한다
session.add(u.audit())   # 죽은 행 기준의 후속 로직이 '성공적으로' 진행된다
벌크 DELETE의 여정: session.execute(delete(...)) │ ├──────────────▶ DB: 조건에 맞는 행 삭제 ✔ │ ✘ identity map: 아무 통지도 받지 못함 → (User,7)→u 가 그대로 남음 = "DB에는 없는데 세션에는 있는" 유령 객체

이 함정이 악질인 이유는 세 겹이다.

  • 에러가 없다. DELETE도 성공했고, u 접근도 성공한다 — 어긋남은 값의 형태로만 존재한다. "성공의 얼굴로 오는 손상"이라는 점에서 K5 계보다.
  • 같은 트랜잭션 안에서 일어난다. 격리 수준(E4)의 문제 — 남의 변경이 언제 보이는가 — 와 달리, 이것은 내가 만든 변경을 내가 못 보는 문제다. DB 격리를 아무리 높여도 해결되지 않는다.
  • 객체 경로의 서비스가 전부 빠진다. cascade 삭제, 삭제 전후 이벤트 훅, 연관 컬렉션 정리가 실행되지 않는다 — DB 스키마의 ON DELETE 제약만이 동작한다. "ORM이 해 주던 일"의 목록을 정확히 아는 사람만 벌크 경로를 안전하게 쓸 수 있다.

구조적으로 보면: 이것은 캐시 일관성 문제의 한 사례다 — identity map은 DB 위의 캐시이고, 캐시를 우회한 원본 변경은 캐시를 낡게 만든다. 같은 구도가 애플리케이션 캐시(E4 9절), CPU 캐시(★7절 C++)에서 반복된다. ORM이 특별히 못난 것이 아니라, 우회로가 있는 모든 캐시의 숙명이다.

4. synchronize_session — 우회를 보정하는 세 전략

ORM도 이 숙명을 알기에, 벌크 DML에 "실행 후 지도를 어떻게 맞출 것인가"를 지정하는 다이얼을 달아 두었다. SQLAlchemy의 synchronize_session이 대표 형태다.

전략동작비용한계
'evaluate' WHERE 조건을 파이썬 식으로 재평가해, 지도 안에서 조건에 맞는 객체를 찾아 제거(삭제)·갱신(수정) 추가 SQL 없음 — 가장 쌈 SQL로만 표현 가능한 조건(DB 함수, 복잡한 서브쿼리, 일부 복합 튜플 비교)은 평가 불가 → 에러로 거부
'fetch' 영향받은 행의 PK 목록을 확보(사전 SELECT 또는 RETURNING)해 그 PK들의 지도 항목을 제거·만료 SELECT 1회 또는 RETURNING 비용 비용이 있지만 조건 형태 무관 — 범용
False 보정하지 않음 — 3절의 어긋남을 그대로 둠 0 이후 세션의 해당 객체 접근이 전부 지뢰. "이 세션에서 그 객체들을 다시 안 본다"가 보장될 때만

최근에는(2020년대 중반 기준): 기본값이 'auto'로 정리되었다 — RETURNING을 지원하는 백엔드에서는 fetch, 아니면 evaluate를 자동 선택한다. 과거(1.x 계열) 기본값은 'evaluate'였고, 복합 조건에서 "Could not evaluate current criteria in Python" 에러를 만나 'fetch'나 False를 급히 지정하는 것이 통과의례였다 — 낡은 예제·답변에 남아 있는 이 관행을 현재 기본값과 혼동하지 말 것.

방언 차이(Oracle 병기): RETURNING 가용성이 auto의 분기점이므로 DB가 곧 전략이다 — PostgreSQL·Oracle은 RETURNING 지원(Oracle은 RETURNING ... INTO 구문 계열)으로 fetch가 RETURNING 한 방에 끝나고, MySQL은 DELETE/UPDATE의 RETURNING이 없어 fetch가 사전 SELECT로 수행된다. 같은 코드의 실제 SQL 왕복 수가 DB에 따라 달라지는 지점이다.

다이얼이 있으니 함정은 끝났는가? 아직 하나가 남았다 — 보정은 벌크를 이미 선택한 뒤의 이야기다. 애초에 언제 객체 경로를 버리고 벌크로 넘어가는 것이 옳은가가 실무의 진짜 판단이고, 그 전형적 장면이 다음 절이다.

5. 반복 단건 삭제 → 복합키 IN 벌크 — 전환의 판단

"조건에 맞는 대상 목록을 이미 알고 있고(예: 화면에서 선택된 항목들), 그것들을 지운다"는 흔한 요구를 두 경로로 쓰면: 

# 객체 경로: 대상이 N개면 왕복도 N번 (로드까지 하면 2N번)
for oid, rev in targets:                     # (order_id, revision) 복합키라 하자
    obj = session.get(OrderLine, (oid, rev))
    session.delete(obj)

# 벌크 경로: 복합키를 튜플 IN으로 — 1문장
from sqlalchemy import tuple_, delete
session.execute(
    delete(OrderLine).where(
        tuple_(OrderLine.order_id, OrderLine.revision).in_(targets)
    )
)
# 생성 SQL: DELETE FROM order_line WHERE (order_id, revision) IN ((1,3),(1,4),(2,1), ...)
  • 전환의 이득 — 왕복 N(또는 2N) → 1. 대상이 수백~수천이면 이 차이가 응답 시간을 지배한다. 유일성 제약(복합 PK·유니크 제약)이 있는 테이블이라면 튜플 IN이 정확히 그 제약의 키로 조준하므로 의미도 명확하다.
  • 전환의 대가 — 1절 표의 오른쪽 열 전부: cascade·이벤트 미발동, 지도 정합은 4절 다이얼로 직접 관리, 그리고 "몇 건이 지워졌는가"를 rowcount로 검증하는 책임(기대 N건 ≠ 실제 건수면 대상 목록이 낡았다는 신호)까지 코드의 몫이 된다.
  • 판단 기준을 한 문장으로 — 삭제가 "행 제거" 이상의 의미(연쇄 정리·후속 훅·감사 기록)를 갖는가? 갖는다면 객체 경로(또는 그 의미를 벌크 후 수동 재현), 순수한 행 제거라면 벌크가 정답에 가깝다.

튜플 IN의 방언 주의: 다중 컬럼 IN(WHERE (a,b) IN ((1,2),...))은 PostgreSQL·MySQL·Oracle 모두 지원하지만 세부가 갈린다 — MySQL은 과거 버전에서 이 형태의 인덱스 활용이 약해 실행 계획 확인(E5)이 특히 권장되고, Oracle은 IN 목록 크기 제한(전통적으로 1000개, 튜플 형태는 우회 가능하나 한계 존재) 때문에 대량 목록은 분할(chunking) 또는 임시 테이블 조인으로 설계한다. "된다/안 된다"가 아니라 "몇 건까지, 어떤 계획으로"를 방언별로 확인하는 습관이 필요하다.

6. 흔히 헷갈리는 지점

① "벌크 delete도 cascade가 되겠지"? — ORM 수준 cascade는 객체 경로의 서비스다(1절). 벌크에서는 DB 제약의 ON DELETE CASCADE/SET NULL만 동작한다. ORM cascade에만 의존하던 스키마라면 벌크 삭제가 고아 행 또는 FK 위반으로 나타난다.

② "commit 전이니까 아직 안 지워졌다"? — 벌크 DML은 execute 시점에 SQL이 나간다(확정은 물론 커밋 시 — E3). "flush를 안 했으니 DB에 안 갔다"는 감각은 객체 경로의 것이고, 벌크는 그 대기열을 쓰지 않는다. 반대로 객체 경로의 미flush 변경과 벌크가 섞이면 순서 문제가 생기므로, 벌크 전 flush가 안전 수칙이다.

③ "False가 제일 빠르니 항상 False"? — 속도의 대가가 3절의 유령 객체다. "이 세션이 그 객체들을 다시 보지 않는다"를 지금 보장할 수 있어도, 코드가 자라며 그 보장은 깨진다. 기본값(auto)에서 출발하고, False는 근거를 주석으로 남길 수 있을 때만.

④ "expire_all() 한 방이면 정합 문제 끝"? — 지도의 모든 객체를 만료시키면 어긋남은 사라지지만, 이후 각 객체 접근마다 재조회 SELECT가 나간다 — 보정 비용을 없앤 게 아니라 뒤로 미루고 잘게 쪼갠 것이다. evaluate/fetch가 겨냥 보정이라면 expire_all은 융단 폭격이다.

★ 7. 언어별 대조

"관리 계층을 우회한 변경이 계층의 캐시를 낡게 만든다"는 이 문서의 축은 ORM 밖에서도 반복된다. 각 언어에서 이 축이 어떤 얼굴로 나타나는지가 비교의 관점이다.

언어대응 장면어긋남의 형태비고
Java JPA 벌크 JPQL(DELETE FROM ...)과 영속성 컨텍스트 1차 캐시에 삭제된 엔티티가 잔존 — em.clear()·clearAutomatically로 보정 표 + 7.3 요약
JS·TS Prisma deleteMany 등 — identity map이 없는 무상태 모델 지도가 없어 이 함정 자체가 없음 — 대신 손에 든 결과 객체의 신선도는 전적으로 코드 책임 표 + 7.3 요약
Python SQLAlchemy identity map — 본문 함정의 원산지 3절 그대로 — 실험으로 재현 가능 아래 심화 참조
C++ 컨테이너의 반복자·참조 무효화, 캐시 일관성 낡은 포인터/반복자 접근 = 정의되지 않은 동작 아래 심화 참조

7.1 C++ — 우회 변경의 극한 형태: 무효화는 에러가 아니라 UB다

"관리 주체 몰래 원본을 바꾸면 손에 든 참조가 낡는다"를 C++은 언어 규칙 수준에서 겪는다. 컨테이너를 변형하면 기존 반복자·참조가 무효화(invalidation)될 수 있고, 무효화된 것을 쓰는 순간은 예외가 아니라 정의되지 않은 동작(undefined behavior, UB — 무슨 일이 일어나도 표준이 책임지지 않는 상태)이다. 

std::unordered_map<int, User> cache;          // identity map에 해당하는 자료구조
User* u = &cache.at(7);                        // 객체를 "손에 쥔" 상태 (3절의 u와 같은 처지)

cache.erase(7);                                // 관리 구조에 정식으로 알리고 제거 — 여기까진 명확
// *u 접근은 이제 UB: 크래시가 나면 오히려 운이 좋고, 대개는 쓰레기 값으로 '성공'한다

// ORM 함정과의 대응:
//   session.execute(delete(...))  ≒  다른 코드가 내 몰래 cache를 rehash/erase
//   synchronize_session           ≒  "변형 후 어떤 반복자·참조가 살아남는가" 규칙표
//   'fetch'/'evaluate'            ≒  변형 후 참조를 다시 얻는 규율 (find를 다시 한다)

C++ 관점의 통찰(메모리·수명): C++ 표준 라이브러리는 연산별로 "무엇이 무효화되는가"를 계약 문서로 못박아 두었고(예: vector 재할당은 전부 무효화, unordered_map의 rehash는 반복자만 무효화하고 참조는 유지), 숙련자는 변형 후 참조를 다시 얻는 것을 반사신경으로 갖고 있다. ORM의 synchronize_session이 하는 일이 정확히 이 계약의 자동화다 — "변형이 일어났으니 낡았을 수 있는 손잡이를 정리한다". 차이는 결과의 가혹함뿐이다: C++은 UB로 즉사 가능성이라도 있지만, ORM의 유령 객체는 멀쩡한 값을 돌려주며 계속 산다 — 어떤 의미에서 더 위험하다.

7.2 Python — 함정을 30초 만에 재현하고, 보정이 하는 일을 눈으로 보기

본문의 함정은 SQLAlchemy로 즉시 재현·관찰할 수 있다. 보정 전략을 바꿔 가며 지도(session.identity_map)를 직접 들여다보는 것이 가장 빠른 이해다. 

from sqlalchemy import delete, tuple_

u = session.get(User, 7)
print((User, (7,)) in session.identity_map)      # True — 지도에 등록됨
print(u in session)                              # True

# ① 보정 없음: 지도가 그대로 남는다
session.execute(delete(User).where(User.id == 7),
                execution_options={"synchronize_session": False})
print(u in session)                              # True ← 유령 (DB에는 이미 없음)

# ② fetch 보정: RETURNING/SELECT로 PK를 받아 지도에서 축출한다
session.rollback()                               # 실험 원상 복구
u = session.get(User, 7)
session.execute(delete(User).where(User.id == 7),
                execution_options={"synchronize_session": "fetch"})
print(u in session)                              # False ← 지도에서 제거됨 (deleted 상태)

# ③ 복합키 벌크의 evaluate 한계 재현
session.execute(
    delete(OrderLine).where(
        tuple_(OrderLine.order_id, OrderLine.revision).in_([(1, 3), (2, 1)])
    ),
    execution_options={"synchronize_session": "evaluate"},
)   # 튜플 IN은 파이썬 재평가가 어려운 대표 사례 — 평가 불가 시 에러로 거부되며,
    # 'auto'가 RETURNING 백엔드에서 fetch를 고르는 실용적 이유가 이것이다

Python 관점의 통찰: ②에서 fetch가 지도를 고치는 방식은 "u를 새 값으로 채움"이 아니라 "u를 삭제됨 상태로 표시하고 축출"이다 — 삭제에서 정합이란 갱신이 아니라 퇴거다. 그리고 ①과 ②의 차이가 순수하게 execution_options 한 줄이라는 점이 이 주제의 실무 감각을 결정한다: 벌크 DML의 안전성은 SQL이 아니라 실행 옵션에 있다. 코드 리뷰에서 delete().where()를 보면 WHERE보다 먼저 물어야 할 것이 "세션에 이 대상들이 로드되어 있을 수 있는가, 그렇다면 보정 전략은 무엇인가"다.

7.3 Java / JS·TS — 한 줄 요약

Java(JPA)의 벌크 JPQL도 영속성 컨텍스트(1차 캐시)를 동일하게 우회하며, 처방은 벌크 직후 em.clear()(또는 Spring Data의 @Modifying(clearAutomatically = true)) — SQLAlchemy의 fetch/evaluate 같은 겨냥 보정이 아니라 컨텍스트 전체를 비우는 쪽이 관례라는 차이가 있다(6절 ④의 트레이드오프를 기본값으로 받아들인 설계). JS·TS의 주류 ORM(Prisma 등)은 identity map 없는 무상태 모델이라 이 함정 자체가 성립하지 않는다 — 대신 "쿼리 결과는 그 시점의 스냅샷일 뿐"이라는 원칙이 전면에 오며, 손에 든 객체의 신선도를 언어·도구가 아니라 코드 규율로만 지킨다는 점에서 자유와 책임을 맞바꾼 설계다.

8. 함께 알면 좋은 것

  • 세션 수명주기와 확정 지점 — 이 문서가 "세션 안"에서 벌어지는 일을 다뤘다면, 세션 자체가 언제 열리고 커밋되고 닫히는가는 E19의 주제다(직접 후속).
  • 낙관적 락과 벌크 — 버전 컬럼(E4) 기반 낙관적 락은 객체 경로의 장치라, 벌크 UPDATE는 버전 검사·증가를 건너뛴다. 벌크와 낙관적 락을 함께 쓰는 테이블은 버전 컬럼 갱신을 벌크 문장에 직접 포함해야 한다.
  • soft delete와의 상호작용 — "삭제 = deleted_at UPDATE"인 스키마에서 벌크 삭제는 벌크 UPDATE가 되고, 본문의 모든 논의(우회·보정·이벤트 미발동)가 그대로 적용된다.
  • 대량 삭제의 운영 측면 — 수백만 행 삭제는 정합 이전에 락 범위·undo 급증·복제 지연의 문제다. 배치 분할과 비피크 시간대 실행이 통례.
  • ON DELETE 제약 설계 — 벌크 경로에서 유일하게 동작하는 연쇄 장치이므로, "ORM cascade와 DB 제약 중 어디에 진실을 둘 것인가"를 스키마 설계 시점에 정해 두는 것이 상책.

9. 한 장 요약

  • 삭제의 두 경로: 객체 경로(unit of work 통과 — cascade·이벤트·정합 제공)와 벌크 경로(DML 직행 — 전부 생략). 같은 "지운다"가 아니다.
  • identity map은 "한 PK 한 객체"의 지도이자 캐시 — 벌크 DML은 이 지도를 우회하므로 "DB에는 반영, 세션 객체는 옛 상태"의 유령이 생긴다. 에러 없이.
  • 보정 다이얼 synchronize_session: evaluate(파이썬 재평가)/fetch(PK 확보 후 축출)/False(방치). 현행 기본 auto = RETURNING 되는 DB(PostgreSQL·Oracle)는 fetch, MySQL은 사전 SELECT.
  • 단건 N회 → 복합키 tuple_().in_() 1문장 전환의 기준: 삭제가 "행 제거" 이상의 의미를 갖는가. 튜플 IN은 3방언 모두 지원하되 MySQL은 계획 확인, Oracle은 IN 목록 규모 설계.
  • 벌크 전 flush, rowcount 검증, False에는 근거 주석 — 벌크 DML의 안전성은 SQL이 아니라 실행 규율에 있다.

E1 인덱스 원리와 복합 인덱스

0. 한눈에 보는 결론

  • 인덱스(index)는 미리 정렬해 둔 별도의 자료구조다. "정렬돼 있으면 빨리 찾을 수 있다"는 단순한 원리를 디스크 환경에 맞게 구현한 것이 B-tree다.
  • 인덱스의 효용은 seek(원하는 지점으로 점프)이 scan(전부 훑기)을 대체할 때 나온다. 인덱스가 있어도 scan이 선택되면 효과가 없다.
  • 복합 인덱스(composite index)는 앞 컬럼부터 차례로 정렬된다. 따라서 선두 컬럼(leading column)을 조건에 쓰지 않으면 그 인덱스는 사실상 못 쓴다.
  • 컬럼 순서의 황금률: 등호(=) 조건 컬럼을 앞에, 범위(<, >, BETWEEN) 조건 컬럼을 뒤에. 범위 조건을 만나는 순간 그 뒤 컬럼들의 정렬은 활용이 끊긴다.
  • 선택도(selectivity)가 높은(값이 다양해서 조건으로 걸렀을 때 소수만 남는) 컬럼일수록 인덱스 가치가 크다. 성별 같은 저선택도 컬럼 단독 인덱스는 거의 무용하다.
  • 인덱스는 공짜가 아니다 — 쓰기(INSERT/UPDATE/DELETE)마다 인덱스도 갱신되므로, 읽기 속도를 쓰기 비용과 저장 공간으로 사는 거래다.

1. 인덱스가 없는 세계 — 전체 스캔

테이블은 기본적으로 "도착한 순서대로 쌓인 종이 더미"에 가깝다. 조건에 맞는 행을 찾으려면 처음부터 끝까지 모든 행을 확인하는 수밖에 없는데, 이것이 전체 테이블 스캔(full table scan)이다. 행이 100만 개면 100만 번 확인한다 — 데이터가 늘수록 비용이 정비례로 늘어난다.

책 뒤의 "찾아보기" 페이지가 해결책의 원형이다. 본문(테이블)은 그대로 두고, 키워드를 가나다순으로 정렬한 별도 목록에 "이 단어는 몇 쪽"이라는 위치 정보를 달아 둔다. 정렬돼 있으므로 이진 탐색이 가능해지고, 100만 항목도 약 20번의 비교로 찾는다. 데이터베이스 인덱스가 정확히 이 구조다: 정렬된 (키 값 → 행 위치) 목록.

2. 왜 하필 B-tree인가

정렬된 목록이면 배열 + 이진 탐색으로도 충분해 보이지만, 데이터베이스에는 두 가지 제약이 있다: 데이터가 디스크에 있고, 계속 삽입·삭제된다.

  • 디스크는 한 바이트씩이 아니라 페이지(page)라는 블록 단위(보통 수 KB)로 읽는다. 읽기 횟수 = 디스크 접근 횟수이므로, "몇 번 비교하나"보다 "페이지를 몇 번 읽나"가 진짜 비용이다.
  • 정렬된 배열은 중간 삽입 때 뒤 전체를 밀어야 해서 삽입이 계속되는 환경에 부적합하다.

B-tree는 이 두 제약에 맞춘 답이다. 노드 하나를 디스크 페이지 하나에 맞추고, 노드마다 자식을 수백 개씩 두는(높은 fan-out — 한 노드에서 갈라지는 가지 수) 넓고 낮은 트리를 만든다. 그러면 수천만 행도 트리 높이가 3~4 수준이라, 디스크 읽기 서너 번으로 어떤 키든 도달한다. 삽입·삭제 시에는 노드를 쪼개거나 합치며 항상 균형을 유지한다.

[루트 노드] ← 페이지 1회 읽기 / | \ [내부 노드] [내부 노드] ... ← 페이지 1회 읽기 / | \ [리프] [리프] [리프] ── 리프끼리 연결 ← 페이지 1회 읽기 │ └─ 리프에는 (키 값, 행 위치)가 정렬된 채 저장 → 리프 연결 덕분에 범위 검색은 "점프 후 옆으로 이동"

리프 노드들이 옆으로 연결돼 있다는 점이 중요하다. BETWEEN 같은 범위 검색은 시작점까지 트리를 타고 내려간 뒤, 리프를 따라 옆으로 읽기만 하면 된다. 값이 다르지만 같은 원리로, ORDER BY가 인덱스 정렬 순서와 일치하면 별도 정렬 작업 없이 리프를 순서대로 읽는 것으로 끝난다.

3. seek vs scan — 인덱스 효용의 실체

동작무엇을 하나비용의 성격
seek (탐색) 트리를 타고 조건에 맞는 지점으로 점프한 뒤 필요한 만큼만 읽음 결과 행 수에 비례 (전체 크기와 거의 무관)
scan (스캔) 테이블 또는 인덱스 전체를 처음부터 끝까지 읽으며 조건 확인 전체 행 수에 비례

핵심 오해 방지: 인덱스가 "있다"고 seek이 "된다"는 보장이 없다. 쿼리 최적화기(optimizer)는 조건의 형태와 통계를 보고 seek이 이득인지 판단하며, 다음 경우 인덱스를 두고도 scan을 택하거나 seek이 불가능해진다:

  • 인덱스 컬럼에 함수·연산을 씌운 경우 — WHERE YEAR(created_at) = 2026은 정렬된 원본 값이 아닌 계산 결과를 묻는 것이라 트리를 탈 수 없다. created_at >= '2026-01-01' AND created_at < '2027-01-01'처럼 범위로 바꾸면 seek이 된다.
  • 앞쪽이 와일드카드인 패턴 — LIKE '%김'은 "끝이 김"이라 정렬 순서를 이용할 수 없다(LIKE '김%'은 가능).
  • 조건이 걸러내는 비율이 낮아, 어차피 대부분의 행을 읽어야 하는 경우 — 이때는 scan이 오히려 빠르다(아래 선택도 참조).

4. 복합 인덱스 — 정렬의 사전 순서를 이해하면 전부 풀린다

복합 인덱스는 여러 컬럼을 묶어 하나의 인덱스로 만든 것이다. 핵심은 정렬 방식이다: 첫 컬럼으로 먼저 정렬하고, 첫 컬럼이 같은 것끼리 두 번째 컬럼으로 정렬한다 — 성(姓)으로 먼저, 같은 성 안에서 이름으로 정렬된 전화번호부와 같다(사전식 정렬).

INDEX (city, age) 의 리프 정렬 상태: (부산, 22) (부산, 31) (부산, 45) (서울, 19) (서울, 25) (서울, 25) (서울, 40) └────── city가 같은 구간 안에서만 age가 정렬돼 있음 ──────┘

4.1 선두 컬럼 원칙

전화번호부에서 "이름이 '민수'인 사람"을 찾을 수 있을까? 성을 모르면 결국 전체를 훑어야 한다. 마찬가지로 INDEX (city, age)에서 WHERE age = 25만 있는 쿼리는 이 인덱스로 seek할 수 없다 — age의 정렬은 city가 같은 구간 안에서만 유효하기 때문이다. 복합 인덱스는 선두 컬럼부터 연속으로 조건에 등장해야 힘을 쓴다.

4.2 등호 앞, 범위 뒤

컬럼 순서를 정할 때의 황금률이다. 이유를 위 그림으로 확인해 보자.

  • WHERE city = '서울' AND age > 20 + INDEX (city, age) → city를 등호로 고정하면 "서울 구간"이라는 연속된 한 덩어리가 잡히고, 그 안에서 age는 완전히 정렬돼 있으므로 age 범위도 seek으로 처리된다. ✅
  • 같은 쿼리 + INDEX (age, city) → age > 20이라는 범위를 먼저 잡으면, 그 넓은 구간 안에서 city는 정렬돼 있지 않다(각 age 값 구간마다 따로 정렬). city 조건은 잡은 구간을 일일이 훑으며 걸러내야 한다. ⚠️

일반화: 인덱스 탐색은 "등호로 고정 → 고정 → … → 마지막에 범위 하나"까지가 seek의 한계다. 범위 조건을 만나는 순간, 그 뒤 컬럼들의 정렬은 탐색에 쓰지 못한다(정렬·필터에 부분적으로 활용될 수는 있으나 점프는 불가). 그래서 자주 쓰는 쿼리 패턴을 보고 "등호 컬럼들 → 범위 컬럼" 순으로 배치한다.

5. 선택도 — 어떤 컬럼이 인덱스 가치가 있는가

선택도는 조건이 얼마나 소수의 행만 남기는가를 나타낸다. 값의 종류가 많은 컬럼(주민 ID, 이메일, 주문번호)은 등호 조건 하나로 한두 행만 남으므로 선택도가 높고, 값이 몇 가지뿐인 컬럼(성별, 활성 여부)은 절반씩만 걸러 선택도가 낮다.

선택도가 낮으면 인덱스가 있어도 최적화기가 scan을 택하는 경우가 많다. seek은 "인덱스에서 위치를 찾고 → 테이블 본체로 건너가 행을 가져오는" 두 단계라, 가져올 행이 너무 많으면 이 왕복 비용이 순차적으로 쭉 읽는 scan보다 비싸지기 때문이다. 대략 전체의 수 퍼센트를 넘게 읽는 조건이라면 인덱스 효용을 의심해야 한다.

복합 인덱스와의 연결: 저선택도 컬럼도 복합 인덱스의 등호 선두 컬럼으로는 가치가 있을 수 있다. (활성여부, 가입일)처럼 "활성 사용자 중 최근 가입자" 패턴이 잦다면, 활성여부가 구간을 반으로 줄이고 그 안에서 가입일 정렬을 쓰는 조합이 성립한다. 단독 인덱스의 가치와 복합 인덱스 내 역할은 별개로 판단한다.

6. 흔히 헷갈리는 지점

① "인덱스는 많을수록 좋다"? — 모든 쓰기 작업은 걸려 있는 인덱스 전부를 함께 갱신한다. 인덱스 10개가 걸린 테이블의 INSERT는 사실상 11곳에 쓰는 셈이다. 읽기 패턴이 확인된 곳에만 만든다.

② "(a, b) 인덱스가 있으면 (a) 인덱스도 따로 필요하다"? — 아니다. 선두 컬럼 원칙에 의해 (a, b)는 a 단독 조건도 지원한다. 반대로 b 단독 조건은 지원하지 못한다 — 방향이 있는 포함 관계다.

③ 조용한 실패에 주의 — 인덱스를 못 타는 쿼리는 오류를 내지 않는다. 데이터가 적을 때는 scan도 빨라서 문제가 숨어 있다가, 데이터가 쌓인 뒤에야 급격히 느려진다. "지금 빠르다"는 "인덱스를 탄다"의 증거가 아니며, 실행 계획으로 확인해야 한다.

④ 암묵적 형 변환의 함정 — 문자열 컬럼을 숫자와 비교(WHERE phone = 01012345678)하면 컬럼 쪽에 변환 함수가 씌워진 것과 같아져 seek이 무효화될 수 있다. 함수를 "직접 안 썼어도" 생길 수 있는 문제다.

★ 7. 언어별 대조

"정렬된 구조는 범위 탐색이 되고, 해시 구조는 등호만 된다"는 인덱스의 근본 원리는 각 언어의 내장 자료구조에 그대로 나타난다. DB의 B-tree 인덱스 vs 해시 인덱스 구분과 정확히 평행하다.

언어정렬 기반(≈ B-tree 인덱스)해시 기반(≈ 해시 인덱스)비고
Java TreeMap — 범위 검색(subMap), 정렬 순회 지원 HashMap — 등호 조회만, 순서 없음 정렬 트리 vs 해시의 교과서적 대비
JS·TS 내장 정렬 맵 없음 — 정렬 배열 + 직접 이진 탐색 Map, 객체 — 키 등호 조회 범위 검색이 필요하면 라이브러리나 수동 구현
Python 정렬 리스트 + bisect 모듈 dict, set 아래 심화 참조
C++ std::map(균형 이진 트리), lower_bound std::unordered_map 아래 심화 참조 — "왜 이진 트리가 아니라 B-tree인가"의 답이 여기 있다

7.1 C++ — std::map으로 seek을 손으로 재현하기

std::map은 균형 이진 탐색 트리(대개 red-black tree — 삽입·삭제 후에도 높이 균형을 자동 유지하는 이진 트리)로 구현되며, 키가 항상 정렬돼 있다. lower_bound는 "이 값 이상이 시작되는 지점"으로 점프하는 연산 — DB 인덱스 seek의 축소판이다. 

std::map<int, std::string> users;  // 키(나이) 기준 항상 정렬 유지

// seek: age >= 20 인 첫 지점으로 점프한 뒤, 옆으로 읽기 (범위 검색)
for (auto it = users.lower_bound(20); it != users.end() && it->first < 30; ++it) {
    // 20 <= age < 30 구간만 순회 — 전체를 훑지 않는다
}

// 대조: std::unordered_map(해시)은 == 조회만 가능, 범위·정렬 순회 불가

메모리 관점의 통찰: std::map은 노드 하나에 원소 하나를 담아 포인터로 흩어 놓기 때문에, 순회할 때마다 메모리 여기저기로 점프해 캐시 미스가 잦다. DB가 이진 트리 대신 B-tree를 쓰는 이유가 바로 이것의 확장판이다 — 노드 하나를 페이지 크기로 키워 수백 개의 키를 붙여 놓으면, 접근 1회(디스크 읽기/캐시 라인 로드)당 얻는 정보가 극대화된다. 같은 이유로 인메모리에서도 노드가 뚱뚱한 B-tree 계열이 이진 트리보다 빠른 경우가 많다.

7.2 Python — dict가 안 되는 것이 곧 해시 인덱스가 안 되는 것

dict는 해시 테이블이라 등호 조회는 평균 상수 시간이지만, "키가 20 이상인 항목"은 결국 전부 순회해야 한다 — 해시 인덱스가 범위 조건을 지원하지 못하는 것과 동일한 이유다(해시 함수가 정렬 순서를 파괴한다). 범위가 필요하면 정렬 리스트 + bisect(이진 탐색으로 삽입/탐색 지점을 찾아 주는 표준 모듈)를 쓴다. 

import bisect

ages = [19, 22, 25, 25, 31, 40, 45]          # 정렬 상태 유지가 전제 (인덱스의 유지 비용에 해당)

lo = bisect.bisect_left(ages, 20)              # seek: 20 이상 시작 지점으로 점프
hi = bisect.bisect_left(ages, 30)
result = ages[lo:hi]                           # 리프를 옆으로 읽듯 구간만 취함 → [22, 25, 25]

# 복합 인덱스의 사전식 정렬도 튜플 비교로 재현된다
rows = sorted(data)                            # [('부산',22), ('부산',31), ('서울',19), ...]
# ('서울', 20) <= x < ('서울', 999) 구간 탐색 = "city 등호 + age 범위"와 같은 구조

Python 관점의 통찰: 튜플 비교가 "첫 원소부터 차례로, 같으면 다음 원소로" 진행되는 사전식이라는 점은 복합 인덱스 정렬 규칙 그 자체다. ('서울', 25)를 찾을 수 있어도 "둘째 원소가 25인 것"은 이진 탐색으로 못 찾는다는 사실을 직접 확인해 보면, 선두 컬럼 원칙이 관례가 아니라 정렬의 수학적 성질임이 체감된다.

7.3 Java / JS·TS — 한 줄 요약

Java의 TreeMap.subMap(20, 30)은 위 C++ 예제와 동일한 범위 seek이며, JPA 등 ORM을 쓰더라도 생성되는 SQL이 인덱스를 탈 수 있는 형태인지는 개발자 책임이다. JS·TS(프론트엔드)에서는 대량 데이터를 클라이언트에서 필터링하기 전에, 서버/DB가 인덱스로 걸러 보내는 것이 옳은 경계 설정임을 기억하면 된다.

8. 함께 알면 좋은 것

  • 실행 계획(execution plan) — 쿼리가 실제로 seek을 탔는지 scan을 했는지 확인하는 유일한 방법. EXPLAIN으로 조회하며, 인덱스 학습의 다음 단계다.
  • 커버링 인덱스(covering index) — 쿼리가 요구하는 컬럼이 전부 인덱스 안에 있으면 테이블 본체를 아예 안 읽는다. "인덱스에서 위치만 찾고 본체로 건너가는" 2단계 비용을 없애는 기법.
  • 클러스터드 인덱스(clustered index) — 테이블 본체 자체를 특정 키 순서로 정렬해 저장하는 방식(테이블당 하나). 나머지 보조 인덱스와의 관계가 스토리지 엔진 이해의 핵심이다.
  • 통계와 카디널리티(cardinality) — 최적화기는 컬럼 값 분포 통계로 선택도를 추정한다. 통계가 낡으면 좋은 인덱스를 두고도 엉뚱한 계획을 세운다.
  • 해시 인덱스 · 전문(full-text) 인덱스 — B-tree가 만능이 아니다. 등호 전용 초고속(해시), 단어 검색(LIKE '%..%'의 올바른 대안, 전문 인덱스) 등 조건 형태별 전용 구조가 있다.

9. 한 장 요약

  • 인덱스 = 정렬된 (키 → 위치) 자료구조. B-tree는 이를 "페이지 단위 디스크 + 잦은 삽입" 환경에 맞게 넓고 낮게 만든 것.
  • 효용의 실체는 seek(점프 후 필요한 만큼만) vs scan(전부 훑기). 컬럼에 함수·연산·앞 와일드카드가 붙으면 seek 불가.
  • 복합 인덱스는 사전식 정렬 — 선두 컬럼 없이는 못 쓰고, (a,b)는 a 단독을 겸한다.
  • 컬럼 배치는 "등호 앞, 범위 뒤". 범위를 만나는 순간 뒤 컬럼의 정렬은 탐색에 못 쓴다.
  • 선택도 높은 조건일수록 인덱스 가치가 크고, 대량을 읽는 조건은 scan이 더 쌀 수 있다.
  • 인덱스는 쓰기 비용·공간과의 거래이며, 실제로 타는지는 실행 계획으로만 확인된다.

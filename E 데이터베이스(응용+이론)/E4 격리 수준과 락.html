E4 격리 수준과 락

0. 한눈에 보는 결론

  • 격리 수준(isolation level)은 E3에서 미룬 질문 — "동시에 도는 트랜잭션들이 서로를 얼마나 볼 수 있는가" — 에 대한 단계별 답이다. 완벽한 격리(직렬 실행)는 느리므로, DB는 정확성을 조금씩 팔아 동시성을 사는 다이얼을 제공한다.
  • 다이얼을 낮출 때 새어 나오는 것이 세 가지 이상현상(anomaly)이다: 더티 리드(커밋 안 된 값을 봄) · 반복 불가능 읽기(같은 행을 두 번 읽으니 값이 달라짐) · 팬텀 리드(같은 조건을 두 번 조회하니 행이 늘어남).
  • 표준 4단계: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE. 실무의 기본값은 가운데 둘 중 하나다(PostgreSQL·Oracle 계열은 READ COMMITTED, MySQL InnoDB는 REPEATABLE READ).
  • 격리의 구현 수단은 두 계열이다. 락(lock)은 "충돌할 것 같으면 기다리게 한다"(비관적), MVCC(multi-version concurrency control, 다중 버전 동시성 제어)는 "버전을 여러 개 유지해 읽기는 기다리지 않게 한다". 현대 주류 DB는 MVCC로 읽기를, 락으로 쓰기를 다룬다.
  • 실무에서 정말 자주 무는 함정은 이상현상 3종보다 갱신 유실(lost update) — "읽고-계산하고-쓰기" 사이에 남이 끼어들어 내 갱신이 남의 갱신을 덮는 것 — 이며, 기본 격리 수준은 이를 막아 주지 않는다. 해법은 SELECT ... FOR UPDATE(비관적 락) 또는 버전 컬럼(낙관적 락)이다.

1. 왜 다이얼인가 — 완벽한 격리는 공짜가 아니다

E3의 격리성(I)을 문자 그대로 지키는 가장 확실한 방법은 트랜잭션을 한 번에 하나씩 실행하는 것이다. 그러면 이상현상은 원천 봉쇄되지만, 동시 접속 1만의 서비스가 DB 작업을 한 줄로 세우게 된다 — 정확성 100%, 처리량 붕괴.

그래서 모든 DB는 반대 방향의 질문을 던진다: "어떤 종류의 '서로 보임'까지는 허용해도 되는가?" 허용할수록 동시성은 오르고, 대신 특정한 이상 결과가 나올 수 있게 된다. 격리 수준이란 이 거래의 표준화된 눈금이고, 눈금을 고르려면 먼저 무엇이 새는지 — 이상현상의 정체 — 를 알아야 한다.

2. 세 가지 이상현상 — 무엇이 새는가

모두 "트랜잭션 T1이 읽는 도중에 T2가 끼어드는" 구도다. 끼어드는 방식에 따라 세 종류로 나뉜다.

이상현상시나리오왜 위험한가
더티 리드
(dirty read)		 T2가 잔액을 100→50으로 바꾸고 아직 커밋 전. T1이 50을 읽음. 직후 T2가 롤백. T1은 세상에 존재한 적 없는 값으로 판단·계산을 했다. 제안 단계의 값(E3 2절)이 새어 나간 것.
반복 불가능 읽기
(non-repeatable read)		 T1이 같은 행을 두 번 읽는 사이에, T2가 그 행을 바꾸고 커밋. 두 읽기의 값이 다름. 커밋된 값이므로 "가짜"는 아니지만, 한 트랜잭션 안의 논리가 서로 다른 세계를 본다. 검증 시점과 사용 시점의 값이 달라지는 버그의 형태.
팬텀 리드
(phantom read)		 T1이 WHERE amount > 100으로 두 번 조회하는 사이에, T2가 조건에 맞는 새 행을 INSERT 후 커밋. 두 번째 조회에 유령 행이 등장. 반복 불가능 읽기의 집합 버전 — 행 값이 아니라 행의 존재가 달라진다. "조건에 맞는 행"은 잠글 대상이 아직 없어서 행 단위 락으로는 못 막는다는 점이 따로 분류되는 이유.

세 현상의 관계: 심각도 순서이자 포함 관계처럼 읽으면 된다 — "커밋 안 된 값이 보임" ⊃ "커밋된 변경이 중간에 보임(값)" ⊃ "커밋된 변경이 중간에 보임(집합)". 격리 수준의 눈금은 정확히 이 셋을 바깥쪽부터 하나씩 차단하는 구조다.

3. 격리 수준 4단계 — 눈금과 현실의 기본값

2절의 세 현상을 차단 목록으로 삼으면 표준(SQL) 4단계가 그대로 유도된다.

격리 수준더티 리드반복 불가능 읽기팬텀 리드메모
READ UNCOMMITTED발생발생발생사실상 사용 금지 구역. 일부 DB는 지원 자체를 안 함
READ COMMITTED차단발생발생"커밋된 것만 본다". PostgreSQL·Oracle 계열 기본값
REPEATABLE READ차단차단표준상 발생 가능"트랜잭션 시작 시점의 스냅샷을 본다". MySQL InnoDB 기본값 (Oracle에는 이 눈금이 없음 — 아래 참조)
SERIALIZABLE차단차단차단"직렬 실행과 동일한 결과 보장". 충돌 시 대기 또는 에러로 강제
  • 기본값이 곧 현실이다. 대부분의 서비스 코드는 DB 기본값 위에서 돈다. 즉 "우리 서비스에서 어떤 이상현상이 가능한가"는 코드가 아니라 사용 중인 DB의 기본 격리 수준이 정하고 있다 — 자기 DB의 기본값을 모르는 채 동시성 버그를 추적하는 것은 지도의 축척을 모른 채 길을 찾는 것과 같다.
  • 눈금의 지원 범위 자체도 DB마다 다르다. Oracle은 4단계 중 READ COMMITTED(기본)와 SERIALIZABLE 둘만 제공한다 — READ UNCOMMITTED는 MVCC(undo 기반 읽기 일관성) 구조상 더티 리드가 원천적으로 없어 존재 이유가 없고, REPEATABLE READ는 눈금 자체가 없다(트랜잭션 전체의 스냅샷 고정이 필요하면 SERIALIZABLE 또는 읽기 전용 트랜잭션 SET TRANSACTION READ ONLY로 올라간다). "격리 수준을 올리자"는 결정이 DB에 따라 선택지부터 다르다는 뜻이다.
  • 표는 표준, 구현은 각색이다. 예컨대 MySQL InnoDB의 REPEATABLE READ는 갭 락(gap lock — 행 사이의 "틈"까지 잠금)으로 팬텀을 상당 부분 막고, PostgreSQL의 REPEATABLE READ는 스냅샷 방식이라 표준의 표와 거동이 다르다. Oracle의 SERIALIZABLE 역시 엄밀히는 스냅샷 격리에 가까워 직렬화 충돌 시 ORA-08177(cannot serialize access) 에러로 실패시킨다 — 7절 ①의 "재시도 필수"가 에러 번호로 구체화되는 예. 표준 표는 어휘로, 정확한 거동은 사용 DB 문서로 확인하는 것이 옳은 습관이다.

그런데 "차단"이라는 말은 선언일 뿐, DB가 실제로 무엇을 해서 차단하는가는 별개의 질문이다. 그 구현 수단이 다음 두 절 — 락과 MVCC — 이다.

4. 락 — 기다리게 해서 지킨다

첫 번째 수단은 고전적이다: 충돌할 수 있는 접근을 줄 세운다.

  • 공유 락(shared, S) — "읽는 중". 여럿이 동시에 잡을 수 있다(읽기끼리는 충돌하지 않으므로).
  • 배타 락(exclusive, X) — "고치는 중". 오직 하나만, 그리고 공유 락과도 공존 불가. UPDATE·DELETE가 대상 행에 잡으며, 커밋/롤백까지 유지된다 — E3 4절의 "트랜잭션 길이 = 남이 기다리는 시간"의 정체가 바로 이것이다.
  • granularity(입자) — 행 단위가 기본이지만 상황에 따라 페이지·테이블 단위로 커진다. 입자가 클수록 관리 비용은 줄고 동시성은 죽는다.

4.1 데드락 — 줄 세우기의 필연적 부작용

T1: A행 락 확보 ──> B행 락 대기 ─┐ ├─ 서로가 서로를 기다림 = 영원히 진행 불가 T2: B행 락 확보 ──> A행 락 대기 ─┘ DB의 처리: 감지 후 한쪽을 강제 롤백(희생자 선정) + 데드락 에러 반환

두 트랜잭션이 서로 다른 순서로 같은 자원들을 잡으면 발생한다. 중요한 태도 전환: 데드락 에러는 DB의 오작동이 아니라 정상적인 충돌 해소 절차다. 예방은 "자원을 항상 같은 순서로 잡기"(예: 계좌 이체 시 항상 작은 id부터 잠금), 대응은 희생된 트랜잭션의 재시도다 — 재시도해도 안전하려면 트랜잭션이 멱등하게 설계되어야 한다는 점에서 D2의 멱등성 논의와 만난다.

5. MVCC — 버전을 여러 개 둬서 기다림을 없앤다

락만으로 격리를 구현하면 치명적 병목이 남는다: 읽기가 쓰기를 기다리고, 쓰기가 읽기를 기다린다. 조회가 대부분인 웹 서비스에서 이 대기는 견딜 수 없으므로, 현대 DB는 두 번째 수단을 발명했다 — 행을 고칠 때 덮어쓰지 않고 새 버전을 만들고 옛 버전을 남겨 두는 것이다.

잔액 행의 버전 사슬: [v1: 100, T5가 커밋] ← [v2: 50, T9가 커밋] ← [v3: 30, T12 진행 중·미커밋] T10(스냅샷 시점: T9 커밋 직후)이 읽으면 → v2(50)를 봄 · T12가 고치는 중이어도 기다리지 않는다 (읽기가 쓰기에 안 막힘) · T12의 미커밋 v3은 안 보인다 (더티 리드 원천 차단) · 트랜잭션 내내 같은 스냅샷을 보면 (반복 불가능 읽기·팬텀도 차단 — REPEATABLE READ의 구현)
  • 읽기는 스냅샷으로, 쓰기는 여전히 락으로. MVCC에서도 같은 행을 동시에 고치는 것까지 허용할 수는 없다 — UPDATE끼리는 4절의 배타 락으로 줄을 선다. "읽기 무대기 + 쓰기 직렬화"가 현대 DB의 표준 조합이다.
  • 스냅샷의 기준 시점이 격리 수준을 만든다. 문장마다 새 스냅샷이면 READ COMMITTED(문장 사이에 남의 커밋이 보임), 트랜잭션 시작 시 고정이면 REPEATABLE READ — 3절의 눈금이 MVCC에서는 스냅샷 갱신 주기로 구현되는 것이다.
  • 공짜는 아니다. 옛 버전들이 쌓이므로 청소(가비지 수거 — PostgreSQL의 VACUUM 등)가 필요하고, 장수 트랜잭션은 "아직 누가 보고 있을지 모르는" 옛 버전의 청소를 막아 저장 공간·성능을 갉아먹는다 — 트랜잭션을 짧게 하라는 E3의 원칙이 MVCC에서 한 번 더 강화된다.

6. 실무 선택 — 그리고 다이얼이 못 막아 주는 것

여기까지로 다이얼(3절)과 그 내부 장치(4·5절)를 확보했다. 실전의 선택은 의외로 단순한 기본형에서 출발한다: DB 기본 격리 수준을 그대로 쓰되, 정말 충돌이 문제 되는 지점만 국소적으로 보강한다. 보강이 필요한 대표 상황이 갱신 유실이다.

6.1 갱신 유실(lost update) — 표에 없는 네 번째 문제

-- 재고 차감을 "읽고-계산하고-쓰기"로 구현한 경우 (READ COMMITTED에서)
T1: SELECT stock FROM items WHERE id = 7;   -- 10을 읽음
T2: SELECT stock FROM items WHERE id = 7;   -- 역시 10을 읽음
T1: UPDATE items SET stock = 9 WHERE id = 7; COMMIT;   -- 10-1=9
T2: UPDATE items SET stock = 9 WHERE id = 7; COMMIT;   -- 자기가 읽은 10 기준 10-1=9
-- 두 건이 팔렸는데 재고는 1만 줄었다: T1의 갱신이 유실됨

어느 시점에도 더티 리드·반복 불가능 읽기는 없었다 — 모두가 커밋된 값만 읽었다. 문제는 읽기와 쓰기 사이의 시간이며, 기본 격리 수준은 이 틈을 지켜 주지 않는다. 표준적 보강책은 둘이다.

비관적 락 — SELECT ... FOR UPDATE낙관적 락 — 버전 컬럼
발상"충돌할 거야" — 읽는 시점부터 배타 락을 잡아 남을 대기시킴"충돌 잘 안 해" — 자유롭게 읽고, 쓸 때 WHERE version = 읽었던 값으로 검사. 0건 갱신이면 충돌 → 재시도
충돌이 잦으면유리(재시도 낭비 없음)불리(재시도 폭증)
충돌이 드물면불리(불필요한 대기·데드락 위험)유리(락 비용 0)
제일 단순한 대안가능하다면 읽지 말고 한 문장으로: UPDATE items SET stock = stock - 1 WHERE id = 7 AND stock > 0 — 읽기-쓰기 틈 자체를 없앤다

7. 흔히 헷갈리는 지점

① "격리 수준을 SERIALIZABLE로 올리면 동시성 문제 끝"? — 문제의 종류는 사라지지만 대가가 이동한다: 충돌 시 대기·강제 롤백(직렬화 에러)이 늘어나 재시도 로직이 필수가 되고 처리량이 떨어진다. 다이얼은 문제를 없애는 게 아니라 "이상 결과"와 "대기/재시도" 사이에서 형태를 바꾼다.

② "MVCC니까 락은 이제 없다"? — 읽기의 대기가 없어진 것이다. 쓰기끼리는 여전히 배타 락으로 줄을 서고(5절), 데드락도 그대로 존재한다. 그리고 6.1절의 갱신 유실은 MVCC가 있어도 발생한다.

③ "REPEATABLE READ면 팬텀까지 안전"? — DB에 따라 다르다(3절). MySQL InnoDB는 갭 락·스냅샷으로 대부분 막지만, 표준 정의상 REPEATABLE READ는 팬텀을 허용한다. "우리 DB에서는"이라는 한정어 없이 이 문장을 말하면 틀릴 수 있다.

④ "데드락 에러 = 코드 버그"? — 동시 실행의 정상 산출물일 수 있다(4.1절). 로그에서 박멸할 대상이 아니라 빈도를 관리하고 재시도로 흡수할 대상이다. 물론 같은 자원 다른 순서 획득처럼 예방 가능한 패턴은 고친다.

⑤ "이건 DB만의 문제다"? — 구도가 낯익지 않은가: "읽고-계산하고-쓰기" 사이에 남이 끼어드는 문제는 애플리케이션 메모리의 경쟁 조건(race condition)과 동형이다. 락·낙관적 검사라는 해법 계열까지 평행하다 — G1 스레드 안전성 기초.html과 겹쳐 읽으면 하나의 문제 계보임이 보인다.

★ 8. 언어별 대조

격리 수준과 락은 SQL의 세계지만, 그것을 지정하고 활용하는 문은 애플리케이션 코드에 있다. 각 언어 생태계가 이 문을 어떻게 노출하는지, 특히 낙관적 락(6.1절)을 어떤 관용구로 지원하는지가 비교의 축이다.

8.1 C++ — 같은 문제, 같은 해법: 락 순서와 데드락

4.1절의 데드락은 DB만의 현상이 아니다. 여러 자원을 서로 다른 순서로 잠그면 어떤 세계에서든 발생하며, C++의 std::mutex(상호 배제 장치)에서도 형태가 똑같다. 다만 여기서는 DB처럼 감지해 주는 심판이 없어 프로그램이 그냥 멈춘다. 

std::mutex mA, mB;

// 위험: 두 스레드가 반대 순서로 잠그면 서로를 영원히 기다린다
void thread1() { std::lock_guard<std::mutex> a(mA); std::lock_guard<std::mutex> b(mB); }
void thread2() { std::lock_guard<std::mutex> b(mB); std::lock_guard<std::mutex> a(mA); }

// 해법 ①: 항상 같은 순서로 잠근다  (DB에서 "작은 id부터 잠금"과 동일한 규율)
// 해법 ②: 여러 락을 한 번에 획득 — 교착 회피 알고리즘이 내장된 도구를 쓴다
void safe() {
    std::scoped_lock lock(mA, mB);   // 순서에 무관하게 안전하게 둘 다 확보
}

C++ 관점의 통찰(수명·소유권): lock_guard·scoped_lock은 락의 수명을 스코프에 묶는 장치다 — 예외가 나든 중간에 반환하든 소멸자가 반드시 잠금을 푼다. DB 트랜잭션의 락이 "커밋/롤백까지" 유지되는 것과 정확히 같은 발상으로, 해제 시점을 사람의 기억이 아니라 구조에 맡긴다는 원칙이다.
결정적 차이도 하나 있다: DB는 데드락을 감지해서 한쪽을 희생시키지만(4.1절), std::mutex에는 그런 심판이 없어 프로세스가 조용히 정지한다. "데드락 에러가 로그에 찍히는 것은 그나마 다행"이라는 4.1절의 태도 전환이 이 대조에서 설득력을 얻는다 — 감지 가능한 실패가 감지 불가능한 정지보다 낫다.

8.2 Python — GIL이 있어도 경쟁 조건은 사라지지 않는다

Python에는 GIL(global interpreter lock, 전역 인터프리터 락 — 한 번에 하나의 스레드만 바이트코드를 실행하게 하는 잠금)이 있어 "동시 실행이 없으니 안전하지 않나" 오해하기 쉽다. 그러나 GIL은 바이트코드 단위로만 배타적일 뿐, 6.1절의 갱신 유실 — 읽고-계산하고-쓰기 사이에 남이 끼어드는 문제 — 는 그대로 일어난다. 

import threading

counter = 0
def worker():
    global counter
    for _ in range(100_000):
        counter += 1      # 읽기 → +1 → 쓰기: 세 단계 사이에 다른 스레드가 끼어들 수 있다

threads = [threading.Thread(target=worker) for _ in range(4)]
[t.start() for t in threads]; [t.join() for t in threads]
print(counter)            # 400000이 아닌 값이 나온다 — DB의 갱신 유실과 정확히 동형

# 해법도 평행하다: 잠그거나(비관적), 원자적 연산 하나로 만들거나
lock = threading.Lock()
with lock:
    counter += 1          # ≒ SELECT ... FOR UPDATE

# DB 쪽 관용구 (SQLAlchemy)
item = session.query(Item).with_for_update().get(7)   # 비관적 락

Python 관점의 통찰: counter += 1이 한 줄인데도 안전하지 않다는 사실이 이 문서 전체의 요약이다 — 원자적으로 보이는 것과 원자적인 것은 다르다. 6.1절에서 "읽고-쓰기를 UPDATE items SET stock = stock - 1 한 문장으로 만들라"고 한 처방이, 여기서는 "락으로 감싸라" 또는 "원자적 연산을 쓰라"로 번역된다. 문제도 해법도 층위만 다를 뿐 같은 계보라는 것이 G1 스레드 안전성 기초.html과 이 문서를 겹쳐 읽는 이유다.
참고로 최근 Python에는 GIL을 제거한 실험적 빌드가 도입 단계에 있는데, 그 경우 위 코드의 결과는 더 어긋난다 — GIL이 우연히 제공하던 보호막마저 사라지기 때문이다. "언어가 보장해 주는 줄 알았던 것"에 기대는 코드가 왜 위험한지 보여 주는 사례다.

8.3 Java / JS·TS — 한 줄 요약

Java는 낙관적 락이 프레임워크 관용구로 정착한 대표 사례로, JPA의 @Version 필드 하나면 UPDATE에 WHERE version = ?가 자동으로 붙고 0건 갱신 시 예외가 발생한다 — 다만 재시도는 프레임워크 밖의 책임이라, 예외를 그대로 흘리면 낙관적 락은 "가끔 실패하는 기능"으로 보인다(충돌 감지는 프레임워크, 충돌 해소는 내 코드). JS·TS에서는 격리 수준이 커넥션·트랜잭션 단위 속성이라는 점이 관건으로, 풀에서 받은 임의의 커넥션에 SET TRANSACTION ...을 실행하면 엉뚱한 트랜잭션에 적용될 수 있어 트랜잭션 콜백의 옵션으로 지정하는 API가 안전하다.

9. 함께 알면 좋은 것

  • 갭 락과 넥스트 키 락 — MySQL InnoDB가 REPEATABLE READ에서 팬텀을 막는 장치(행 사이 "틈"의 잠금). 예상 밖의 락 대기·데드락의 원인이 되기도 하므로 MySQL 사용자라면 한 단계 깊이 볼 가치가 있다.
  • 스냅샷 격리와 쓰기 왜곡(write skew) — MVCC 기반 REPEATABLE READ가 SERIALIZABLE과 다른 미묘한 지점. "각자 다른 행을 고쳤는데 합쳐 보면 규칙 위반"인 패턴.
  • 락 대기 관찰 — 락 경합은 실행 계획에 나타나지 않는 성능 문제다(E5 실행 계획 읽기.html의 사각지대). DB별 락 대기 뷰·타임아웃 설정(lock timeout)이 관찰 도구다.
  • 분산 락 — 여러 애플리케이션 인스턴스에 걸친 상호 배제. DB 락의 바깥 확장판으로, 별도의 도구(예: 인메모리 저장소 기반)와 함정(만료·소유권)을 가진다.
  • 애플리케이션 캐시와의 정합성 — DB에서 아무리 격리해도 그 앞의 캐시가 낡은 값을 주면 무효다. 격리의 경계가 어디까지인지 인식할 것.

10. 한 장 요약

  • 격리 수준 = 정확성↔동시성 다이얼. 낮출수록 이상현상(더티 리드 → 반복 불가능 읽기 → 팬텀)이 바깥쪽부터 허용된다.
  • 실무 기본값은 READ COMMITTED(PostgreSQL·Oracle) 또는 REPEATABLE READ(MySQL InnoDB) — 자기 DB의 기본값 확인이 출발점. 지원 눈금 자체도 다르다(Oracle은 READ COMMITTED·SERIALIZABLE 2단만). 표준 표는 어휘, 정확한 거동은 DB 문서.
  • 구현은 락(쓰기 줄 세우기, 커밋까지 유지, 데드락은 정상 산출물 — 재시도로 흡수)과 MVCC(버전 사슬 + 스냅샷으로 읽기 무대기)의 조합.
  • 표 밖의 실전 함정은 갱신 유실 — 읽기와 쓰기 사이의 틈. 한 문장 UPDATE > 낙관적 락(버전 컬럼+재시도) / 비관적 락(FOR UPDATE)으로 보강.
  • 선택 전략: 기본값에서 시작해 충돌이 실증된 지점만 국소 보강. 전역 다이얼 상향은 문제의 형태를 대기·재시도로 바꿀 뿐임을 알고 쓸 것.

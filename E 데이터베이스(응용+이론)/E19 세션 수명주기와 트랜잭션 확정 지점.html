E19 세션 수명주기와 트랜잭션 확정 지점

0. 한눈에 보는 결론

  • 웹 애플리케이션에서 ORM 세션의 표준 수명은 요청 스코프 — 요청이 들어올 때 열리고, 응답이 나갈 때 닫힌다. 프레임워크의 의존성 주입(예: yield 기반 DI)이 이 열고-닫기를 대신해 준다.
  • 이 편의의 대가로 근본 질문이 흐려진다: "커밋은 누가, 언제 하는가?" 확정 지점의 주인은 셋일 수 있다 — 요청 끝의 프레임워크(암묵 커밋), 코드 중간의 명시 commit()/rollback(), 그리고 블록형 컨텍스트(with begin():).
  • 세 주인이 섞일 때 함정이 열린다: 중간 명시 커밋은 트랜잭션을 쪼개서 이후 실패에도 앞부분이 확정되고(부분 확정), 명시 롤백 뒤의 프레임워크 암묵 커밋은 빈 트랜잭션에 대한 no-op이 되어 "커밋 로그는 있는데 데이터는 없는" 혼란을 만든다.
  • 확정 지점 ≠ 세션 종료 지점. commit()은 세션을 닫지 않는다 — 세션은 계속 살아서 다음 작업 시 새 트랜잭션을 자동 개시하고, 커밋된 객체들은 만료(expire)되어 다음 접근 때 재조회된다. "커밋했으니 끝"이라는 감각이 요청 후반부의 미스터리한 SELECT와 두 번째 트랜잭션의 정체다.
  • 설계 원칙 한 줄: 확정 지점의 주인을 계층당 하나로 통일하라 — 프레임워크에 맡겼으면 코드 중간 커밋을 금지하고, 코드가 가지려면 프레임워크 암묵 커밋을 끄는 것이 정석이다.

1. 세션의 수명 — 왜 "요청 하나 = 세션 하나"인가

E18에서 세션은 identity map을 품은 "작업 공간"이었다. 그렇다면 이 작업 공간은 언제 만들어지고 언제 버려져야 하는가? 극단 둘을 보면 답이 좁혀진다.

  • 전역 세션 하나를 계속 쓰면 — identity map이 무한히 자라고(메모리), 여러 요청의 변경이 한 unit of work에 뒤섞이며, 한 요청의 실패 롤백이 남의 변경까지 지운다. 작업 공간의 공유는 곧 작업의 뒤섞임이다.
  • 쿼리마다 새 세션을 열면 — 한 요청 안에서 identity map의 이득(동일성·변경 추적)이 사라지고, 여러 쿼리를 한 트랜잭션으로 묶을 수 없다.

그 사이의 자연스러운 단위가 요청이다 — 하나의 요청은 대개 하나의 업무 단위이고, 업무 단위는 하나의 트랜잭션이길 원하기 때문이다. 그래서 웹 프레임워크들은 "요청 시작에 세션을 만들어 핸들러에 주입하고, 응답 후 닫는" 패턴을 표준화했다. FastAPI 계열의 yield DI가 대표 형태다: 

def get_session():
    with Session(engine) as session:   # 요청 시작: 세션 생성
        yield session                  # ← 핸들러가 이것을 주입받아 사용
    # 요청 종료: with 블록이 닫히며 세션 close (커밋/롤백 정책은 구성에 따라 — 3절)

@app.post("/orders")
def create_order(req: OrderReq, session = Depends(get_session)):
    session.add(Order(**req.dict()))
    # commit이 없다? — 그럼 누가 하는가. 이것이 이 문서의 질문이다

마지막 주석의 질문이 핵심이다. 수명(언제 열리고 닫히나)은 정해졌지만, 확정(언제 커밋되나)은 아직 정해지지 않았다. 둘을 구분하려면 먼저 세션이 변경을 어떻게 모으는지 — flush와 commit의 구분 — 를 봐야 한다.

2. unit of work — 모아서, 내보내고(flush), 확정한다(commit)

세션은 add·속성 변경·delete를 즉시 SQL로 보내지 않는다. unit of work(작업 단위) 패턴에 따라 변경을 장부에 모아 두었다가, 필요한 순간에 한꺼번에 SQL로 번역해 내보낸다. 여기서 두 동사를 구분해야 한다.

flushcommit
하는 일장부의 변경을 SQL로 번역해 전송flush 후, DB에 트랜잭션 확정을 지시
이후 상태변경이 DB 커넥션에 반영됐지만 아직 제안 상태(같은 트랜잭션에서만 보임 — E3 2절)변경이 세상에 공표됨 — 롤백 불가
일어나는 때명시 호출, commit 직전, 그리고 쿼리 직전 자동(autoflush) — 내 미확정 변경이 내 조회에 보이게 하려고명시 호출 또는 3절의 위임 주체가
session.add(A) ─┐ A.name = "x" ──┼──▶ [장부(unit of work)] ──flush──▶ [DB: 제안 상태] ──commit──▶ [확정] session.delete(B)┘ 모은다 내보낸다 공표한다

이 그림에서 "확정 지점"이란 마지막 화살표가 누구의 손으로 당겨지는가의 문제다. 후보가 셋이다.

3. 확정 지점의 세 주인

주인형태확정 시점장·단
① 프레임워크
(암묵 커밋)		 DI가 요청 종료 시 commit()(정상) / rollback()(예외)을 대신 수행하도록 구성 핸들러 반환 직후 핸들러가 깨끗해짐 / 확정이 코드에 안 보임 — 4절 함정의 토양
② 코드
(명시 커밋)		 핸들러·서비스가 직접 session.commit()/rollback() 호출한 그 줄 확정이 눈에 보임 / 모든 경로에서 호출을 보장할 규율 필요(누락=미확정, 예외 경로=롤백 책임)
③ 블록
(컨텍스트)		 with session.begin(): — 블록 이탈 방식으로 커밋/롤백 자동 분기(E3 6.2절) 블록의 끝 경계가 들여쓰기로 보임 + 예외 안전 / 블록 구조를 강제

셋 다 정당한 설계다. 문제는 선택이 아니라 혼합에서 생긴다 — 특히 ①을 깔아 둔 채 ②를 끼워 넣는, 가장 흔한 조합에서.

4. 함정 해부 — 암묵과 명시가 섞일 때

①(요청 끝 암묵 커밋)이 구성된 애플리케이션에서, 어떤 핸들러가 "확실히 저장하고 싶어서" 중간에 commit()을 직접 부른다고 하자. 

@app.post("/transfer")
def transfer(req, session = Depends(get_session)):   # 요청 끝에 암묵 commit 구성됨
    session.add(withdraw_record)
    session.commit()                  # (a) 중간 명시 커밋 — "여기까지는 확실히"
    session.add(deposit_record)
    risky_validation(req)             # (b) 여기서 예외가 나면?
    # 요청 끝: 예외 발생 시 프레임워크는 rollback을 수행
시간축: |── T1: withdraw 기록 ──commit(a)──|── T2: deposit 기록 ──✘예외(b)──rollback──| 결과: T1은 확정(출금 기록 있음) T2는 취소(입금 기록 없음) = 한 요청 = 한 업무 단위라는 전제가 (a)에서 소리 없이 깨졌다
  • 부분 확정 — (a)의 명시 커밋은 트랜잭션을 둘로 쪼갠다. 이후 실패의 롤백은 T2에만 미치므로, "전부 아니면 전무"(E3의 원자성)가 요청 단위가 아니라 조각 단위로 좁혀진다. 코드만 보면 (a)는 신중함처럼 보인다는 것이 이 함정의 위장술이다.
  • 롤백 후 no-op 커밋 — 반대 방향도 있다: 코드가 검증 실패로 session.rollback()을 명시 호출하고 정상 응답(예: 422)을 반환하면, 요청 끝의 암묵 commit()은 새로(비어) 시작된 트랜잭션에 대한 사실상의 no-op이 된다. 동작은 무해하지만 관측이 오염된다 — 로그·프록시 계층에는 COMMIT이 찍히므로 "커밋됐는데 데이터가 없다"는 헛수사를 부른다. (일부 구성은 변경이 없으면 커밋 자체를 생략하기도 한다 — "커밋 로그가 안 남는" 반대 방향의 혼란. 어느 쪽이든 원인은 같다: 확정의 주인이 둘이라는 것.)
  • 진단이 어긋나는 이유 — 장애 조사가 대개 핸들러 코드에서 시작되는데, 확정의 절반은 코드 밖(프레임워크 구성)에 있다. "commit이 코드에 없는데 데이터가 있다 / commit을 했는데 일부만 있다"는 증상 앞에서는 구성 파일의 세션 정책부터 확인하는 것이 지름길이다.

처방: 확정 지점의 주인을 계층당 하나로. ①을 쓰기로 했다면 핸들러·서비스에서 commit() 호출을 금지(중간 확정이 꼭 필요한 예외적 업무 — 예: 대량 배치의 구간 확정 — 는 ①의 스코프 밖으로 분리), ②를 쓰기로 했다면 DI의 암묵 커밋을 끄고 세션 종료는 close만 하게 구성한다. 규칙은 어느 쪽이든 좋다 — 두 규칙의 공존만이 나쁘다.

5. 확정 지점 ≠ 세션 종료 지점

4절까지는 "누가 커밋하나"였다. 남은 혼동 하나는 "커밋하면 끝나나"다 — 답은 아니오이며, 이 구분이 요청 후반부의 미스터리들을 푼다. 

u = session.get(User, 7)
u.name = "kim"
session.commit()            # 확정 지점 — 그러나 세션은 계속 살아 있다

print(u.name)               # ← 여기서 SELECT가 다시 나간다?! (기본 구성 기준)
session.add(other)          # ← 그리고 이 작업은 '두 번째' 트랜잭션에 속한다
  • 커밋 후 객체는 만료(expire)된다 — 기본 구성(expire_on_commit=True)에서 커밋은 identity map의 객체들을 "낡았을 수 있음"으로 표시한다. 커밋 순간 트랜잭션이 끝나므로, 그 이후의 세상(남의 커밋 포함)을 반영하려면 재조회가 필요하다는 논리다. 커밋 직후의 속성 접근마다 SELECT가 나가는 이유이고, 응답 직렬화가 커밋 뒤에 일어나는 구조에서 "저장 한 번에 SELECT 여러 방"이 관측되는 이유다.
  • 다음 작업은 새 트랜잭션을 자동 개시한다 — 세션은 "트랜잭션 공장"처럼 동작한다: 커밋으로 하나가 끝나면, 다음 SQL이 필요한 순간 조용히 다음 트랜잭션을 연다. 한 요청에서 커밋을 두 번 부르면 트랜잭션이 세 개(마지막은 암묵 정리 대상)까지 생길 수 있다 — 4절의 부분 확정이 시간축에서 어떤 모양인지의 다른 표현이다.
  • 종료는 close — 커넥션을 풀에 반납하고 identity map을 비우는 것은 close(요청 스코프에서는 DI의 with 종료)다. 수명(1절)·확정(3~4절)·만료(이 절)는 각각 다른 사건이며, 셋을 한 단어 "끝"으로 뭉뚱그리는 것이 이 주제의 혼동 전부라 해도 과언이 아니다.

층위 정리(중복 방지): Java 계열의 @Transactional이 다루는 선언적 트랜잭션 경계와 전파(propagation — 메서드 호출이 겹칠 때 트랜잭션을 이어받을지 새로 열지의 규칙)는 C15 트랜잭션 관리와 전파.html의 소관이다. 이 문서는 같은 현상을 세션(작업 공간)의 수명주기 각도에서 다뤘다 — C15가 "경계를 어떻게 선언하고 겹침을 어떻게 푸는가"라면, 여기는 "그 경계 아래에서 세션·트랜잭션 객체가 실제로 언제 생기고 확정되고 소멸하는가"다.

6. 흔히 헷갈리는 지점

① "flush했으니 저장됐다"? — flush는 제안 전송이지 확정이 아니다(2절). flush 후 롤백하면 사라진다. 반대로 "autoflush 때문에 내 쿼리에 미커밋 변경이 보인다"를 "이미 커밋됐다"로 오독하는 것도 같은 혼동의 거울상이다.

② "commit했으니 세션도 끝났다"? — 5절. 세션은 살아 있고, 만료된 객체와 함께 다음 트랜잭션을 열 준비가 되어 있다. 커밋 후 객체를 계속 쓰는 코드는 재조회 비용(또는 detached 상태 에러)을 계산에 넣어야 한다.

③ "예외가 나면 알아서 롤백되겠지"? — 주인이 누구냐에 달렸다(3절). ①·③은 예외 경로의 롤백이 구조에 내장돼 있지만, ②(명시)는 try/except로 직접 보장해야 하며, 롤백 없이 세션을 계속 쓰면 "이전 예외로 세션이 오염되어 롤백이 필요하다"는 유형의 에러가 후속 작업에서 터진다 — 증상이 원인에서 멀리 떨어져 나타나는 전형.

④ "DB가 알아서 커밋해 주는 경우도 있던데"? — 방언의 함정이다. Oracle은 DDL 실행 시 암묵 커밋을 수행하므로(E3 2절), 요청 스코프 트랜잭션 안에 DDL성 작업이 끼면 프레임워크·코드 누구도 부르지 않은 확정이 일어난다. PostgreSQL은 DDL도 트랜잭션에 포함되고 MySQL은 Oracle처럼 암묵 커밋 계열이다 — "확정 지점의 주인" 목록에 DB 방언이라는 네 번째 후보가 숨어 있는 셈이다.

★ 7. 언어별 대조

"확정의 주인이 누구인가"라는 질문은 언어마다 표준 답이 다르고, 그 답이 곧 각 생태계의 트랜잭션 사고방식이다.

언어표준적인 확정 주인혼합 함정의 형태비고
Java 프록시(@Transactional) — 메서드 정상 반환=커밋, 런타임 예외=롤백 선언 경계 안의 수동 커밋/롤백, self-invocation으로 경계 자체가 미적용 표 + 7.3 요약 (상세는 C15)
JS·TS 콜백 블록 — $transaction(async tx => ...) 반환=커밋, throw=롤백 콜백 밖 클라이언트로 쿼리(트랜잭션 밖 실행), 콜백 안 자체 커밋 시도 표 + 7.3 요약
Python 구성에 따라 ①②③ 모두 통용 — 그래서 혼합 함정의 원산지 본문 4절 그대로 아래 심화 참조
C++ RAII 가드 — 스코프 소유자가 곧 확정 주인 가드 객체를 복사·전달하면 "주인이 둘" 문제가 타입 수준에서 재현 아래 심화 참조

7.1 C++ — "확정의 주인은 하나"를 타입으로 강제하기

4절의 처방("주인을 하나로")을 C++은 소유권(ownership — 자원을 해제할 책임이 누구에게 있는가를 타입으로 표현하는 규율)으로 구현할 수 있다. E3에서 본 RAII 가드에 이동 전용(move-only) 성질을 더하면, "커밋 권한이 동시에 두 곳에 있는" 상태가 컴파일 에러가 된다. 

class TxOwner {
    Connection* conn_;                       // nullptr = 권한이 이양된 빈 껍데기
public:
    explicit TxOwner(Connection& c) : conn_(&c) { conn_->exec("BEGIN"); }

    TxOwner(const TxOwner&) = delete;              // 복사 금지: 주인은 둘일 수 없다
    TxOwner(TxOwner&& o) : conn_(o.conn_) { o.conn_ = nullptr; }   // 이동 = 권한 이양

    void commit() { conn_->exec("COMMIT"); conn_ = nullptr; }      // 확정 후 권한 소멸
    ~TxOwner() { if (conn_) conn_->exec("ROLLBACK"); }             // 주인이 확정 안 하면 롤백
};

void service(TxOwner tx) {          // 값으로 받음 = 확정 권한을 '넘겨받음'
    do_work();
    tx.commit();                    // 확정은 현재 주인의 전유물
}
// 호출부: service(std::move(tx));  — 이후 호출부의 tx는 빈 껍데기, 이중 커밋 원천 불가

C++ 관점의 통찰(소유권·수명): 4절의 함정은 결국 "커밋 권한의 공유"였다 — 프레임워크도 갖고, 코드도 갖는. 이동 전용 타입은 그 공유를 문법적으로 불가능하게 만든다: 권한은 언제나 정확히 한 곳에 있고, 이양은 std::move로 명시되며, 아무도 확정하지 않으면 소멸자가 안전한 쪽(롤백)으로 처리한다. GC 언어에는 이 강제 장치가 없으므로 같은 원칙을 관례(계층당 하나)와 리뷰로 지켜야 한다는 것 — 그것이 4절 처방의 정체다. 언어가 못 막아 주는 규칙일수록 문서화가 필요하다.

7.2 Python — 세 주인을 실험으로 구분하기

Python(SQLAlchemy)은 세 주인이 모두 관용구로 존재하는 생태계라, 각각의 확정 시점을 직접 관찰하는 것이 최선의 예방 접종이다. 

import logging
logging.basicConfig(); logging.getLogger("sqlalchemy.engine").setLevel(logging.INFO)
# → BEGIN / COMMIT / ROLLBACK 이 로그로 보인다: 아래 각 형태에서 '언제' 찍히는지 관찰

# 주인 ②: 명시 — COMMIT은 정확히 이 줄에서
with Session(engine) as s:
    s.add(a)
    s.commit()                       # ← COMMIT 로그
    s.add(b)                         # ← 다음 문장에서 새 BEGIN 로그 (5절: 세션은 공장)
                                     # b는? — close 시 롤백: 커밋 없는 변경의 최후

# 주인 ③: 블록 — COMMIT은 블록의 끝에서
with Session(engine) as s:
    with s.begin():
        s.add(a)                     # 블록 안: 아직 COMMIT 없음
    # ← 여기서 COMMIT 로그 (예외였다면 ROLLBACK)

# 주인 ①: 요청 스코프 DI에 위임 — 핸들러에는 commit이 등장하지 않는다
def get_session():
    with Session(engine) as s:
        try:
            yield s
            s.commit()               # 정상 경로: 요청 끝 암묵 커밋
        except Exception:
            s.rollback()             # 예외 경로
            raise

Python 관점의 통찰: 마지막 형태에서 yield가 경계선이다 — yield 위는 요청 전, 아래는 요청 후에 실행되므로, 커밋이 "핸들러가 반환한 뒤"에 일어난다는 시간 구조가 코드에 그대로 적혀 있다. 4절의 함정을 이 코드로 재현하면 정확히 보인다: 핸들러가 중간에 s.commit()을 부르면 로그에 COMMIT이 두 번 찍히고, 그 사이가 별개의 트랜잭션이다. 엔진 로그에서 BEGIN~COMMIT 쌍의 개수를 세는 것 — 그것이 "이 요청의 원자성 단위가 실제로 몇 조각인가"를 확인하는 가장 정직한 방법이다.

7.3 Java / JS·TS — 한 줄 요약

Java의 @Transactional은 주인 ①(프록시 위임)을 언어 표준으로 굳힌 형태로, "핸들러에 commit이 없다"가 기본 풍경이며 혼합 함정도 같은 자리(선언 경계 안의 수동 개입, self-invocation)에서 난다 — 경계 선언과 전파 규칙의 본론은 C15로. JS·TS(Prisma 등)는 주인 ③(콜백 블록)을 표준으로 택해 "콜백 반환 = 커밋, throw = 롤백"이 계약이고, 함정은 확정 시점보다 어느 클라이언트로 쿼리하는가(콜백에 주입된 tx 대신 바깥 클라이언트를 쓰면 트랜잭션 밖 실행)에 있다 — 확정의 주인 문제가 커넥션 귀속 문제로 번역된 형태다.

8. 함께 알면 좋은 것

  • ORM 삭제·벌크 DML과 세션 정합 — 세션 "안"에서 identity map이 겪는 일. 이 문서와 짝을 이루는 E18.
  • expire_on_commit 다이얼 — 5절의 커밋 후 재조회가 부담이면 끌 수 있다. 대가는 "커밋 후 객체가 낡았을 수 있음"을 코드가 감수하는 것 — 신선도와 왕복 수의 트레이드오프.
  • 배치 작업의 구간 확정 — 수백만 건 처리에서는 요청 스코프 원칙 밖에서 N건마다 커밋하는 설계가 정당하다. 단 "실패 시 어디부터 재개하는가"(체크포인트)와 멱등 재처리가 세트다.
  • 읽기 전용 트랜잭션 — 조회만 하는 요청에 쓰기 트랜잭션 비용을 물리지 않는 구성(SET TRANSACTION READ ONLY 계열). Oracle에서는 조회 일관성 확보 수단이기도 하다(E4 3절).
  • 커넥션 풀과 세션의 관계 — 세션 close가 커넥션 반납인 구조에서, 세션을 오래 여는 것은 풀 고갈로 직결된다. "세션 짧게"는 정합만이 아니라 자원의 문제이기도 하다.

9. 한 장 요약

  • 세션 수명은 요청 스코프가 표준(yield DI) — 수명은 정해져도 확정의 주인(프레임워크 암묵 / 코드 명시 / 블록)은 별도 결정 사항이다.
  • flush(제안 전송)와 commit(확정)을 구분 — unit of work는 모았다가 내보내고, 확정은 마지막 화살표다.
  • 암묵+명시 혼합이 함정: 중간 명시 커밋 = 트랜잭션 쪼개기(부분 확정), 명시 롤백 후 암묵 커밋 = 빈 트랜잭션 no-op(관측 오염). 처방은 계층당 주인 하나.
  • 확정 ≠ 종료: 커밋 후 세션은 살아서 객체를 만료시키고 다음 트랜잭션을 자동 개시한다. BEGIN~COMMIT 쌍 수를 로그로 세는 것이 원자성 단위의 실측.
  • 네 번째 숨은 주인 = DB 방언: Oracle·MySQL의 DDL 암묵 커밋은 누구도 부르지 않은 확정을 만든다(PostgreSQL은 DDL도 트랜잭션 내). 선언적 경계·전파의 본론은 C15에서.

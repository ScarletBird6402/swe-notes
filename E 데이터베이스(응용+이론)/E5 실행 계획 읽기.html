E5 실행 계획 읽기

0. 한눈에 보는 결론

  • SQL은 "무엇을"만 말하고 "어떻게"는 말하지 않는 선언형 언어다. "어떻게"를 정하는 것은 DB의 옵티마이저(optimizer)이고, 그 결정문을 사람이 읽을 수 있게 펼친 것이 실행 계획(execution plan)이다.
  • 여는 주문은 쿼리 앞에 EXPLAIN을 붙이는 것. EXPLAIN은 실행 없이 "예상"을, EXPLAIN ANALYZE는 실제로 실행한 "실측"을 보여 준다 — 느린 쿼리 수사의 시작과 끝이 이 두 명령이다.
  • 가장 먼저 볼 것은 접근 방식이다: 인덱스로 소수 행을 집는가(E1의 열매), 아니면 테이블 전체를 훑는가(풀스캔). 그리고 rows(예상 처리 행 수) — "1건 찾자고 100만 행을 읽는" 낭비가 숫자로 드러난다.
  • 인덱스가 있는데도 안 타는 데는 전형적 이유가 있다: 컬럼을 함수·연산으로 감쌈, 타입 불일치(암묵적 형변환), 복합 인덱스 선두 컬럼 누락, LIKE '%…', 그리고 "안 타는 게 실제로 더 빠른 경우"(낮은 선택도) — 마지막 것은 고칠 대상이 아니다.
  • 실행 계획의 rows·비용은 통계 기반 추정치다. 추정과 실측(ANALYZE)이 크게 어긋나면 쿼리가 아니라 통계가 낡은 것일 수 있다.
  • 단, 실행 계획은 만능 진단서가 아니다 — 락 대기(→ E4)는 계획에 나타나지 않는다. "계획은 완벽한데 느리다"면 다른 범인을 찾아야 한다.

1. 선언과 절차 사이 — 실행 계획이 존재하는 이유

SELECT * FROM orders WHERE user_id = 42라는 문장에는 "orders를 처음부터 훑어라"도 "인덱스를 타라"도 적혀 있지 않다. 같은 질문에 대한 실행 경로는 여러 개이고 — 전체 스캔, 이 인덱스, 저 인덱스, 조인이라면 순서와 방식까지 — 어느 경로가 싼지는 데이터의 분포와 양에 따라 다르다. 옵티마이저는 테이블 통계를 근거로 각 경로의 비용을 추정해 가장 싼 경로를 고르는 부품이다.

개발자 입장에서 이 구조가 뜻하는 바: 내가 쓴 SQL과 실제 실행되는 절차 사이에는 번역기가 하나 끼어 있다. 쿼리가 느릴 때 SQL 문장만 노려봐서는 답이 안 나오는 이유이고, 번역 결과를 직접 확인하는 창구가 필요한 이유다. 그 창구가 EXPLAIN이다.

2. EXPLAIN 여는 법 — 예상과 실측

사용법은 허무할 만큼 간단하다. 문법과 출력 형태는 DB마다 다르지만(이 문서는 널리 쓰이는 MySQL·PostgreSQL·Oracle을 대표 예시로 쓴다), 개념은 공통이다. 

-- 예상 계획: 실행하지 않고 옵티마이저의 선택만 확인 (안전, 운영에서도 부담 없음)
EXPLAIN SELECT * FROM orders WHERE user_id = 42;              -- MySQL·PostgreSQL

EXPLAIN PLAN FOR SELECT * FROM orders WHERE user_id = 42;     -- Oracle: 계획을 plan_table에 기록 후
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);                      --         꺼내서 보는 2단계

-- 실측 계획: 실제로 실행하고 단계별 실제 소요·실제 행 수까지 표시
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;      -- MySQL(8.0.18+)·PostgreSQL

SELECT /*+ GATHER_PLAN_STATISTICS */ * FROM orders WHERE user_id = 42;          -- Oracle: 실측 수집 힌트로 실행 후
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));    --         방금 실행의 실측 계획 조회
-- 주의: 실측 계열은 정말 실행된다. UPDATE/DELETE에 쓰면 데이터가 정말 바뀐다(트랜잭션으로 감싸고 롤백할 것)

출력에서 처음부터 다 읽으려 하지 말고, 세 가지만 찾는 습관으로 시작한다.

볼 것MySQL EXPLAIN에서PostgreSQL EXPLAIN에서Oracle DBMS_XPLAN에서답하는 질문
① 접근 방식type 컬럼 (const/ref/range/index/ALL)노드 이름 (Index Scan/Seq Scan 등)Operation 열 (INDEX UNIQUE SCAN/INDEX RANGE SCAN/TABLE ACCESS FULL 등)집어서 읽나, 훑어서 읽나
② 사용 인덱스key 컬럼 (NULL이면 미사용)Index Scan using 인덱스명INDEX 계열 연산 행의 Name 열에 인덱스명어떤 인덱스를(못) 탔나
③ 처리 행 수rows (추정)rows=추정 (actual rows=실측)Rows(추정) / A-Rows(실측 — DISPLAY_CURSOR 시)얼마나 읽어서 얼마를 건지나

3. 접근 방식 스펙트럼 — 풀스캔 진단의 기준선

2절의 ①을 읽으려면 눈금이 필요하다. 접근 방식은 "얼마나 정확히 집어 읽는가"의 스펙트럼으로 이해하면 된다(MySQL type 어휘 기준, 개념은 공통).

정확히 집음 ◀──────────────────────────────────────────▶ 전부 훑음 const/eq_ref ref range index ALL PK·유니크로 일반 인덱스로 인덱스로 구간을 인덱스를 테이블 최대 1행 같은 값 여러 행 (BETWEEN,>,<) 처음부터 끝까지 전체 스캔 (풀스캔의 인덱스판) (풀스캔)

어휘만 다를 뿐 스펙트럼은 DB 공통이다 — Oracle로 옮기면 대략 const/eq_ref ≒ INDEX UNIQUE SCAN, ref·range ≒ INDEX RANGE SCAN, index ≒ INDEX FULL SCAN, ALL ≒ TABLE ACCESS FULL에 대응하고, PostgreSQL의 Seq Scan이 곧 ALL/TABLE ACCESS FULL 자리다. 이하 본문은 MySQL 어휘로 쓰되, 판단 기준은 세 방언에 동일하게 적용된다.

  • ALL(풀스캔)이 뜨면 우선 용의자다 — 단, 유죄 확정은 아니다. 수백 행짜리 코드 테이블은 전체를 읽는 게 인덱스 왕복보다 싸고, 옵티마이저도 그래서 풀스캔을 선택한 것이다. 풀스캔이 문제인 것은 큰 테이블에서 소수 행을 찾을 때다.
  • index는 이름과 달리 좋은 신호가 아니다 — 인덱스를 "타는" 게 아니라 인덱스 전체를 훑는 것(풀 인덱스 스캔)으로, ALL보다 약간 나은 정도다.
  • 판단 공식: 테이블 크기 × 건질 비율. "orders 500만 행에서 user 하나의 주문 30건"에 ALL이 떴다면 명백한 수사 대상, "지역 코드 200행 전체 조회"에 ALL은 정상이다.

4. 인덱스가 있는데 안 탄다 — 전형적 이유 다섯

3절의 눈금으로 "타야 할 자리에서 안 탔다"가 확인됐다면, 다음 질문은 왜다. 원인의 대부분은 다음 다섯 패턴 안에 있다.

패턴예시원리처방
① 컬럼을 감쌈 WHERE YEAR(created_at) = 2026 인덱스는 원본 값으로 정렬돼 있다. 함수를 통과한 값의 정렬은 모른다 컬럼을 벗겨 구간 조건으로: created_at >= '2026-01-01' AND created_at < '2027-01-01'
② 타입 불일치 문자열 컬럼에 WHERE phone = 01012345678(숫자) DB가 컬럼 쪽을 암묵 형변환하면 ①과 동일해진다 리터럴·바인딩 타입을 컬럼과 일치('...'로). 애플리케이션 바인딩 타입도 점검
③ 복합 인덱스 선두 누락 인덱스 (user_id, status)인데 WHERE status = 'PAID'만 복합 인덱스는 선두 컬럼부터의 사전식 정렬 — 선두 없이는 진입 불가(E1의 핵심 규칙) 선두 컬럼 조건 추가, 또는 (status, ...) 인덱스 검토
④ 앞쪽 와일드카드 WHERE name LIKE '%철수' 정렬의 기준인 "첫 글자"가 미정이라 어디서 시작할지 알 수 없다 가능하면 전방 일치('김%')로 설계, 아니면 전문 검색(full-text) 계열 도구
⑤ 낮은 선택도(selectivity) WHERE deleted = false (전체의 95%) 어차피 대부분을 읽어야 하면 인덱스 왕복(찾고→본문 접근)이 풀스캔보다 비싸다 — 옵티마이저가 옳다 고치지 않는다. 진짜 필터는 다른 조건에 맡기고, 그 조건의 인덱스를 챙긴다

다섯 패턴의 공통 원리: ①~④는 전부 "인덱스는 정렬된 자료구조이고, 정렬 순서를 활용할 수 없는 조건은 못 탄다"의 변주다(원리는 E1). ⑤만 성격이 다르다 — 탈 수 있는데 안 타는 것이고, 그것이 합리적 선택이다. 즉 "인덱스를 안 탔다"는 관찰은 곧바로 "고쳐야 한다"로 번역되지 않는다.

5. rows와 비용 — 이 숫자들은 추정치다

4절까지는 계획을 믿고 읽었다. 그러나 계획의 숫자에는 태생적 한계가 있다: 옵티마이저는 실행 전에 비용을 계산해야 하므로, 실제 데이터가 아니라 표본으로 만든 통계(행 수, 값 분포 히스토그램 등)에 의존한다. 통계가 현실과 어긋나면 — 대량 적재 직후, 분포가 급변한 뒤 — 옵티마이저는 낡은 지도로 길을 고른다. 

-- PostgreSQL EXPLAIN ANALYZE 출력의 전형적 "통계 낡음" 신호
Index Scan using idx_orders_user on orders
  (cost=0.43..8.45 rows=3 ...)        ← 추정: 3행이라 판단해 이 계획을 선택
  (actual ... rows=182,400 ...)       ← 실측: 18만 행. 추정이 6만 배 어긋남
  • 추정 vs 실측의 큰 괴리 = 통계 문제의 신호. 이때의 처방은 쿼리 수정이 아니라 통계 갱신이다 — PostgreSQL ANALYZE 테이블, MySQL ANALYZE TABLE, Oracle DBMS_STATS.GATHER_TABLE_STATS('스키마','테이블'). (Oracle은 야간 자동 통계 수집 작업이 기본 구성되어 있어, "대량 적재 직후"처럼 자동 주기가 못 따라온 시점이 전형적 괴리 구간이다.)
  • 비용(cost) 숫자는 절대 시간(초)이 아니다. 같은 쿼리의 계획 후보끼리 비교하기 위한 상대 단위다. "cost 8.45니까 8.45ms"식 독해는 오독.
  • 같은 이유로, 개발 DB(1만 행)에서 본 계획은 운영 DB(1억 행)의 계획과 다를 수 있다 — 데이터가 다르면 통계가 다르고, 통계가 다르면 선택이 달라진다. 계획 확인은 실 분포에 가까운 데이터에서.

6. 진단 루틴 — 도구들을 절차로 묶기

이제 부품(EXPLAIN, 접근 방식 눈금, 미사용 원인 목록, 통계 감각)이 모였으니 절차로 조립한다. 느린 쿼리 앞에서의 표준 루틴:

① 범인 특정 슬로우 쿼리 로그·APM에서 "실제로 느린 그 쿼리"와 실제 바인딩 값 확보 ↓ (추측으로 고른 쿼리를 튜닝하는 것이 최대의 낭비) ② 예상 확인 EXPLAIN — 접근 방식(type/노드)·인덱스(key)·rows 세 가지 독해 (2·3절) ↓ ③ 가설 수립 풀스캔? → 4절 다섯 패턴 대조 / 계획 자체가 이상? → 5절 통계 의심 ↓ ④ 수정 쿼리 형태 수정(①②④) 또는 인덱스 추가·재설계(③) 또는 통계 갱신(5절) ↓ ⑤ 재검증 EXPLAIN ANALYZE로 실측 비교 — "빨라진 것 같다"가 아니라 숫자로 확인 ↓ ⑥ 원상 감시 배포 후 슬로우 로그 재확인. 인덱스 추가는 쓰기 비용 증가이기도 하다(E1)

루틴의 사각지대: 실행 계획은 "읽고 찾는 비용"의 지도이지 "기다림"의 지도가 아니다. 계획도 실측도 훌륭한데 특정 시간대만 느리다면 락 대기(E4)·커넥션 풀 고갈·리소스 경합 계열을 의심해야 한다. EXPLAIN 밖의 범인은 EXPLAIN으로 안 잡힌다.

7. 흔히 헷갈리는 지점

① "풀스캔 = 무조건 악"? — 3절·4절 ⑤에서 봤듯 소량 테이블·낮은 선택도에서는 풀스캔이 최적해다. 박멸 대상은 풀스캔이 아니라 "큰 테이블에서 소수를 찾는데 훑는" 조합이다.

② "인덱스를 만들었으니 쓰겠지"? — 옵티마이저는 인덱스의 존재가 아니라 비용으로 선택한다. 4절의 다섯 이유 중 하나로 외면당할 수 있고, 특히 ⑤라면 외면이 정답이다. 확인 수단은 언제나 EXPLAIN이지 인덱스 목록이 아니다.

③ "EXPLAIN이 좋게 나왔으니 끝"? — EXPLAIN은 추정이다(5절). 통계가 낡았다면 좋아 보이는 계획이 실행 시 배신한다. 최종 판정은 EXPLAIN ANALYZE의 실측으로.

④ "개발 환경에서 빨랐는데 운영에서 느리다"? — 5절의 마지막 항목. 데이터 규모·분포가 다르면 옵티마이저는 다른 계획을 고른다. 버그가 아니라 설계된 동작이다.

⑤ "ORM을 쓰니까 실행 계획은 DBA의 일"? — ORM은 SQL을 대신 써 줄 뿐 계획을 대신 읽어 주지 않는다. 오히려 ORM이 생성한 SQL은 눈에 안 보여서 4절 패턴(특히 타입 불일치·함수 감싸기)이 몰래 들어오기 쉽다 — ★8절의 주제.

★ 8. 언어별 대조

실행 계획 자체는 언어 중립(SQL의 세계)이므로, 언어별로 갈리는 지점은 하나다: 내 코드가 만들어 보내는 SQL을 어떻게 꺼내서 EXPLAIN 앞에 세우는가. ORM을 쓸수록 이 "꺼내는" 단계가 진단 루틴 ①의 관건이 되고, 그 방식이 언어·생태계마다 달라서 각자 다른 함정을 남긴다.

언어SQL을 꺼내는 방법확인 시점특유의 함정
Java Hibernate/JPA SQL 로깅 + 바인딩 파라미터 로깅 런타임(쿼리 실행 시 로그로 관찰) 지연 로딩·상속 매핑이 JPQL 한 줄을 여러 SQL로 부풀림
JS·TS 쿼리빌더의 .toSQL()/.getSql()류 메서드 실행 전(체인을 완성한 뒤 언제든 호출) 바인딩 값이 자리표시자로만 보여 별도 치환 필요
Python SQLAlchemy echo=True·compile() 런타임 로그 또는 실행 전 컴파일 개별 SQL은 보여도 반복 횟수(N+1)는 세어 주지 않음
C++ 없음 — SQL을 직접 작성하므로 이미 손에 있음 작성 시점 바인딩 함수 선택 자체가 타입 불일치를 유발

8.1 Java — 로그를 열어야 보이는 SQL

JPA(Java Persistence API)로 짠 코드에는 SQL 문자열이 아예 등장하지 않는다. 개발자는 엔티티(entity — 테이블에 대응하는 객체)와 JPQL(JPA 전용 객체 지향 쿼리 언어)만 다루고, 실제 SQL은 Hibernate 같은 구현체가 내부에서 조립한다. 문제는 이 조립 결과가 기본 설정으로는 어디에도 출력되지 않는다는 점이다 — 진단 루틴 ①("실제로 느린 그 쿼리와 실제 바인딩 값 확보")을 시작하려면 먼저 로그부터 열어야 한다. 

# application.properties — 생성 SQL과 바인딩 값을 함께 로그로 노출
spring.jpa.properties.hibernate.show_sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.orm.jdbc.bind=TRACE   # 바인딩 파라미터는 별도 로거(보안·성능상 기본 비공개)

# 로그 예시
# select o1_0.id, o1_0.user_id, o1_0.status from orders o1_0 where o1_0.user_id=?
# binding parameter [1] as [BIGINT] - [42]

SQL과 바인딩 값이 로그에 따로 찍히는 이유는 바인딩 로깅이 기본으로 꺼져 있기 때문이다 — 파라미터에는 개인정보가 실릴 수 있어서다. 두 줄을 손으로 합쳐야 EXPLAIN 앞에 세울 완성된 쿼리가 나온다.

로그를 확보했다고 끝이 아니다. JPQL 한 줄이 실행 시 여러 SQL로 갈라지는 대표 사례가 지연 로딩(lazy loading — 연관 데이터를 실제 접근하는 시점까지 조회를 미루는 방식)이다. 연관 엔티티를 반복문 안에서 접근하면, EXPLAIN으로는 완벽한 쿼리 하나가 N번 반복되는 형태로 로그에 찍힌다. 여기에 상속 매핑 전략(JOINED 등)까지 겹치면 반복되는 각 쿼리의 조인 개수까지 늘어나 로그가 한층 방대해진다.

Java 관점의 통찰: Hibernate SQL 로그를 켜는 것은 선택 사항이 아니라 습관이어야 한다. JPQL·Criteria API는 "무엇을 조회할지"의 계약일 뿐 "어떤 SQL이 되는지"를 보장하지 않으므로, 로그 없이는 EXPLAIN에 넣을 대상 자체가 없다. 로그에서 SQL 한 줄만 세지 말고 같은 모양의 SQL이 몇 번 반복되는지부터 세는 것이 순서다 — 개별 쿼리의 계획이 완벽해도 반복 횟수가 범인인 경우가 많기 때문이다.

8.2 JS·TS — 실행 전에 SQL을 확인하는 관용구

Java의 SQL 로깅이 "쿼리가 실행된 후 로그를 뒤지는" 수동적 확인이라면, JS·TS의 쿼리빌더(query builder)는 실행 없이 SQL 문자열만 미리 뽑아내는 메서드를 제공한다는 점이 다르다. Knex·TypeORM·Kysely 같은 라이브러리는 체인으로 조립한 쿼리 객체에 .toSQL()이나 .getSql()류의 메서드를 호출하면, DB에 보내지 않고도 완성된 SQL과 바인딩 배열을 즉시 돌려준다. 

// Knex 예시
const query = knex('orders').where('user_id', 42).select('*');

const { sql, bindings } = query.toSQL().toNative();
console.log(sql);       // select * from `orders` where `user_id` = ?
console.log(bindings);  // [42]

// TypeORM QueryBuilder 예시
const qb = dataSource.getRepository(Order)
  .createQueryBuilder('o')
  .where('o.userId = :uid', { uid: 42 });

console.log(qb.getSql());                 // 자리표시자(:uid)가 남은 SQL
console.log(qb.getQueryAndParameters());  // [sql, [42]] — EXPLAIN에 넣기 직전 형태

여기서 걸리는 함정은 자리표시자다. toSQL()이 돌려주는 문자열은 ?나 :uid 같은 자리표시자를 그대로 담고 있어서, EXPLAIN 앞에 세우려면 바인딩 배열의 값을 손으로 채워 넣어야 한다. 일부 라이브러리가 제공하는 "값을 문자열에 직접 끼워 넣는" 변형(값 인라인 옵션)은 진단용으로만 쓸 것 — 실제 실행 경로에 그대로 쓰면 SQL 문자열 조립이 되어 SQL 주입(injection) 위험을 그대로 되살린다.

JS·TS 관점의 통찰: 쿼리빌더가 감춘 것은 SQL 자체가 아니라 SQL이 조립되는 순간이다. 메서드 체인은 최종적으로 실행하기 전까지 SQL 문자열을 만들지 않으므로, "일단 실행해서 로그를 본다"는 Java식 습관 대신 "실행하기 전에 .toSQL()로 미리 들여다본다"는 습관이 자연스럽게 자리 잡는다. 이 차이 덕분에 JS·TS 쪽에서는 EXPLAIN 앞에 세울 SQL을 얻는 데 별도 로그 설정이나 실제 실행이 필요 없다는 점이 Java·Python과 갈리는 지점이다.

8.3 Python — ORM이 무엇을 만드는지 눈으로 보기

JS·TS의 쿼리빌더가 실행 전에 SQL을 미리 보여준다면, Python은 설정 한 줄로 실행되는 모든 SQL이 흘러가는 것을 지켜본다는 점에서 스타일이 다르다. 이 방식은 ORM이 생성하는 SQL의 감각을 기르는 데 좋다. 

from sqlalchemy import create_engine, text
engine = create_engine(url, echo=True)      # 실행되는 모든 SQL과 파라미터를 출력

# 컴파일된 SQL을 실행 없이 확인
print(query.statement.compile(engine, compile_kwargs={"literal_binds": True}))

# 실행 계획을 직접 조회 (PostgreSQL 예)
with engine.connect() as conn:
    for row in conn.execute(text("EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = :uid"),
                            {"uid": 42}):
        print(row[0])

Python 관점의 통찰: echo=True로 로그를 켜 보면 대개 두 가지를 동시에 발견한다 — 개별 쿼리가 느린 문제와, 빠른 쿼리가 수백 번 반복되는 문제(N+1). 실행 계획은 앞의 것만 진단하므로, ORM 스택에서는 "쿼리가 몇 번 나가는가"를 세는 일이 "각 쿼리의 계획을 읽는 일"보다 먼저다.
또 하나 유의할 점: 파라미터를 문자열로 이어 붙여 확인하는 literal_binds는 계획 확인용일 뿐, 실제 실행에 이 방식을 쓰면 SQL 주입(injection)에 노출된다. 진단 편의와 실행 안전성을 분리해 다뤄야 한다.

8.4 C++ — 바인딩 타입이 계획을 바꾼다

C++처럼 SQL을 직접 쓰는 환경에는 "생성된 SQL을 꺼내는" 단계가 없다. 대신 4절 ②(타입 불일치)가 가장 날것으로 드러나는 자리가 된다 — 준비된 문(prepared statement)에 값을 바인딩할 때 어떤 타입으로 넘기는지가 코드에 그대로 적혀 있기 때문이다. 

// 컬럼 phone이 VARCHAR인 테이블에 대해

// ① 숫자로 바인딩 — DB가 컬럼 쪽을 형변환하게 되어 인덱스를 못 탄다
sqlite3_bind_int64(stmt, 1, 1012345678);        // WHERE phone = 1012345678

// ② 문자열로 바인딩 — 컬럼 타입과 일치, 인덱스 정상 사용
sqlite3_bind_text(stmt, 1, "01012345678", -1, SQLITE_STATIC);
//                                            ↑ 문자열 수명 관리 방식을 명시해야 한다

C++ 관점의 통찰(메모리·수명): 마지막 인자에 주목할 만하다 — SQLITE_STATIC은 "이 문자열은 내가 살려 둘 테니 복사하지 말라"는 약속이고, SQLITE_TRANSIENT는 "복사해 두라"는 뜻이다. 지역 버퍼를 넘기면서 전자를 쓰면 실행 시점에 이미 해제된 메모리를 읽는다 — 고수준 언어에서는 존재하지 않는 종류의 버그다.
개념적 소득은 이것이다: 바인딩은 "값을 전달하는 일"이 아니라 "값과 타입과 수명을 함께 전달하는 일"이다. Java·JS·TS·Python 스택에서 ? 자리에 변수를 넣는 순간 라이브러리가 대신 결정해 주던 타입이, 여기서는 함수 이름 (bind_int64 vs bind_text)으로 노출된다. 8.1~8.3절에서 본 "SQL은 같은데 앱에서만 느리다"는 미스터리가 어디서 결정되는지, C++에서는 그 결정 지점이 코드 한 줄로 숨김없이 드러난다.

9. 함께 알면 좋은 것

  • 커버링 인덱스(covering index) — SELECT 대상 컬럼까지 인덱스에 다 있어 본문 접근 없이 인덱스만으로 끝내는 형태. 계획에 별도 표시(MySQL Using index 등)가 뜨는, 3절 스펙트럼 바깥의 보너스 단계.
  • 조인 계획 읽기 — 다중 테이블 쿼리에서는 조인 순서·방식(중첩 루프/해시/정렬 병합)이 계획의 몸통이 된다. 이 문서의 단일 테이블 독해가 그 선수 과목.
  • 옵티마이저 힌트 — 계획을 강제하는 최후 수단. 데이터가 변해도 강제가 남는 부작용 때문에 "통계·쿼리·인덱스로 해결 불가일 때만"이 통례.
  • 슬로우 쿼리 로그와 APM — 진단 루틴 ①의 도구. 임계 시간 설정과 로그 주기 검토가 운영 습관이다.
  • 실행 계획 캐시와 파라미터 민감성 — 바인딩 값에 따라 최적 계획이 다른 쿼리에서, 캐시된 계획이 특정 값에만 유리한 문제(일부 DB). "가끔만 느린 쿼리"의 원인 후보.

10. 한 장 요약

  • SQL은 선언, 실행 절차는 옵티마이저의 선택 — 그 선택문이 실행 계획이고 EXPLAIN(예상)/EXPLAIN ANALYZE(실측)로 읽는다.
  • 독해는 세 가지부터: 접근 방식(집나/훑나), 사용 인덱스, rows. 풀스캔은 "큰 테이블 × 소수 행"일 때만 용의자.
  • 인덱스 외면의 5대 원인 — 함수 감싸기·타입 불일치·선두 컬럼 누락·앞쪽 와일드카드는 "정렬을 못 쓰게 한 것"(수정 대상), 낮은 선택도는 옵티마이저가 옳은 것(수정 비대상).
  • 계획의 숫자는 통계 기반 추정 — 실측과의 큰 괴리는 통계 갱신 신호. 개발↔운영 계획 상이도 같은 원리.
  • 루틴: 실제 느린 쿼리 특정 → EXPLAIN 독해 → 패턴 대조 → 수정 → ANALYZE 재검증. 단 락 대기 등 "기다림"은 이 지도 밖(→ E4).

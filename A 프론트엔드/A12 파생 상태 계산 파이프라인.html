A12 파생 상태 계산 파이프라인

0. 한눈에 보는 결론

  • 화면이 요구하는 모양이 늘 때마다 원본 데이터를 고치면, 곧 "무엇이 진짜인가"를 아무도 모르게 된다. 원본은 하나, 나머지는 전부 계산이 기본 원칙이다.
  • 파생 상태(derived state)는 저장하는 값이 아니라 원본에서 계산되는 값이다. 저장하는 순간 원본과의 동기화 책임이 생기고, 그 책임은 반드시 언젠가 어긴다.
  • 여러 가공이 필요하면 한 함수에 뭉치지 말고 filter → sort → group처럼 단계별 순차 파생 체인으로 쪼갠다. 각 단계는 앞 단계의 출력만 입력으로 받는 순수 계산이다.
  • 체인으로 쪼개는 실질적 이득은 두 가지 — 단계 사이에 검증을 끼울 수 있고, 단계 하나(예: 그룹 키)만 바꿔 전체를 재사용할 수 있다.
  • 최대 함정은 파생 단계 안에서 원본을 건드리는 것이다. 정렬처럼 제자리(in-place)에서 동작하는 연산이 대표적 범인이다.

1. 문제 제기 — 화면은 여러 모양을 원하고, 원본은 하나다

주문 목록을 보여주는 화면을 생각해 보자. 서버에서 받은 원본은 단순한 배열 하나다. 그런데 화면의 요구는 하나가 아니다. 취소 건은 빼고 보여달라(필터), 최신순으로 보여달라(정렬), 날짜별로 묶어 보여달라(그룹), 요약 카드에는 건수와 합계도 보여달라(집계). 같은 원본에서 나온 네 가지 다른 모양이다.

여기서 가장 유혹적인 잘못은 원본을 직접 그 모양으로 고치는 것이다. "정렬해서 보여줘야 하니까 받아온 배열을 정렬해 두자", "취소 건은 안 쓰니까 지워 두자". 처음엔 동작한다. 그런데 다음 요구가 오면 문제가 드러난다 — 취소 건을 지워버린 배열로는 "취소 포함 전체 건수"를 계산할 수 없다. 원본이 이미 특정 화면의 사정에 맞춰 훼손됐기 때문이다.

흔히 헷갈리는 지점: "받아온 데이터를 컴포넌트에서 쓰기 좋게 미리 가공해 두는 것"은 좋은 습관처럼 보인다. 하지만 가공 결과로 원본을 대체하면, 그 시점 이후로는 다른 가공을 시작할 출발점이 사라진다. 가공은 언제나 원본의 사본 위에서, 원본을 남겨둔 채 일어나야 한다.

그렇다면 원본을 남겨둔다 치고, 가공된 결과들은 어디에 두어야 하는가? 이 질문이 다음 절의 주제다.

2. 파생 상태 — 저장하지 말고 계산하라

상태(state)를 설계할 때의 오래된 원칙이 있다: 저장할 최소한만 저장하고, 나머지는 계산하라. 원본 배열은 저장할 가치가 있는 상태다. 하지만 "필터된 배열", "정렬된 배열", "그룹핑된 맵"은 전부 원본에서 계산으로 얻을 수 있는 값이다. 이런 값을 파생 상태(derived state)라고 부른다.

파생 상태를 별도 변수에 저장하면 어떤 일이 생기는가. 원본이 바뀔 때마다 저장해 둔 파생값도 함께 갱신해야 한다. 갱신 코드를 한 군데라도 빠뜨리면, 원본과 파생값이 서로 다른 이야기를 하는 상태가 된다 — 화면 한쪽은 새 데이터, 다른 쪽은 옛 데이터를 보여주는 종류의 버그가 이렇게 태어난다. 동기화 책임은 코드가 커질수록 어기기 쉬워지므로, 애초에 책임 자체가 생기지 않게 하는 것이 정답이다: 파생값은 저장하지 않고, 읽을 때마다 계산되도록 선언한다.

"읽을 때마다 계산하면 느리지 않은가?"라는 걱정이 자연스럽게 따라온다. 그래서 대부분의 프레임워크는 캐시가 붙은 계산 선언을 제공한다. Vue의 computed, React의 useMemo, 상태 라이브러리들의 selector가 모두 같은 물건이다. 본질은 하나로 요약된다:

computed/selector의 본질 = 순수 함수 + 의존성 추적 + 캐시. 의존하는 원본이 안 바뀌었으면 저장해 둔 결과를 그대로 돌려주고, 바뀌었을 때만 다시 계산한다. 즉 "저장의 성능"과 "계산의 정합성"을 동시에 얻는 장치다. 이 캐시가 성립하려면 계산 함수가 순수(pure)해야 한다 — 같은 입력이면 같은 출력, 그리고 입력을 변형하지 않을 것.

여기까지가 파생 하나의 이야기다. 그런데 처음 문제로 돌아가면, 화면은 필터·정렬·그룹을 연달아 요구했다. 파생 하나가 아니라 파생의 연쇄가 필요하다. 이것을 어떻게 조직하는가가 이 문서의 핵심이다.

3. 파이프라인 설계 — 단계별 순차 파생

3.1 한 덩어리 vs 체인

필터·정렬·그룹을 전부 수행하는 computed 하나를 만들 수도 있다. 동작은 한다. 하지만 그 함수는 곧 화면 요구가 추가될 때마다 자라나고, 중간 결과를 확인할 수 없는 블랙박스가 된다. 대안은 각 가공을 독립된 파생 단계로 선언하고, 뒤 단계가 앞 단계의 출력을 입력으로 받게 연결하는 것이다:

원본 orders (불변) │ ▼ [filter] ──▶ visibleOrders "취소 제외" │ ▼ [sort] ──▶ sortedOrders "최신순" │ ▼ [group] ──▶ ordersByDate "날짜별 묶음" │ ▼ 화면 렌더

Vue로 쓰면 이렇게 된다. 각 단계가 짧고, 이름이 붙고, 앞 단계만 바라본다:

const orders = ref([])   // 원본 — 이후 어떤 단계도 이것을 변형하지 않는다

const visibleOrders = computed(() =>
  orders.value.filter(o => o.status !== 'CANCELLED'))

const sortedOrders = computed(() =>
  [...visibleOrders.value].sort((a, b) => b.date - a.date))  // 사본 정렬!

const ordersByDate = computed(() =>
  groupBy(sortedOrders.value, o => o.date))

3.2 체인이 주는 첫 번째 이득 — 단계 사이의 검증 지점

가공이 한 덩어리면, 최종 결과가 이상할 때 "필터가 잘못됐나, 정렬이 잘못됐나, 그룹핑이 잘못됐나"를 안에서 뜯어봐야 한다. 체인이면 각 단계의 출력이 이름 붙은 값으로 존재하므로, 단계 사이에 검증을 끼울 수 있다. 개발 중에는 로그나 assertion으로 "필터 후 건수가 원본 이하인가", "정렬 후 첫 원소가 정말 최신인가"를 확인하고, 문제가 생기면 어느 관문에서 데이터가 틀어졌는지 단계 단위로 좁힐 수 있다. 관측 지점이 구조에 내장되는 셈이다.

3.3 두 번째 이득 — 단계 교체 재사용

"날짜별 말고 고객별로도 묶어 보여달라"는 요구가 오면, 한 덩어리 구현은 함수 전체를 복사해 한 줄을 고치게 된다. 체인 구현은 filter·sort 단계를 그대로 공유하고 group 단계의 키 함수만 다른 파생을 하나 더 선언하면 끝난다:

const ordersByDate     = computed(() => groupBy(sortedOrders.value, o => o.date))
const ordersByCustomer = computed(() => groupBy(sortedOrders.value, o => o.customerId))

체인의 각 마디가 재사용 단위가 되는 것 — 이것이 파이프라인 설계의 실용적 핵심이다. 그런데 이 모든 이득은 한 가지 전제 위에 서 있다: 각 단계가 정말로 입력을 건드리지 않는 순수 파생이어야 한다는 것. 이 전제가 깨지는 대표적 사고들을 다음 절에서 본다.

4. 흔히 헷갈리는 지점 — 체인을 무너뜨리는 세 가지 함정

4.1 제자리 연산이 원본을 오염시킨다

많은 언어의 정렬은 새 배열을 만드는 게 아니라 주어진 배열을 제자리에서 재배열한다. JS의 Array.prototype.sort가 그렇다. 파생 단계 안에서 무심코 visibleOrders.value.sort(...)를 호출하면, "파생값을 계산하는 척하면서 앞 단계의 출력(나아가 원본)을 변형"하게 된다. 증상은 교묘하다 — 화면은 대체로 맞게 보이는데, 정렬 기준을 바꿀 때마다 원본의 순서가 누적 변형되어 다른 파생(예: "원래 수신 순서" 표시)이 조용히 틀어진다.

규율: 파생 단계 안에서 변형 연산을 쓰려면 반드시 사본을 먼저 만든다 — [...arr].sort(...). 언어가 비파괴 버전을 제공하면 그쪽을 기본으로 쓴다(JS의 toSorted·toReversed처럼 사본을 돌려주는 API — 2020년대 중반 기준 주요 런타임에서 사용 가능).

4.2 파생값을 다시 상태로 저장한다

"computed로 두면 매번 계산이 도니까, 계산 결과를 ref에 저장해 두고 watch로 갱신하자"는 발상은 파생을 다시 저장으로 되돌리는 퇴행이다. 2절에서 본 동기화 책임이 그대로 부활하고, 여기에 갱신 타이밍 문제(원본은 바뀌었는데 watch가 아직 안 돈 순간의 불일치)까지 추가된다. 캐시는 프레임워크의 computed가 이미 해 준다 — 성능이 걱정되면 저장이 아니라 계산 비용 자체를 측정하고 줄이는 것이 순서다.

4.3 단계 순서에는 의미가 있다

filter → sort → group 순서는 임의가 아니다. 필터를 먼저 하면 정렬할 원소 수가 줄어 계산이 싸지고, 그룹은 정렬보다 뒤에 와야 각 그룹 내부의 순서가 보존된다. 순서를 바꿔 group → sort로 짜면 "그룹핑된 객체를 어떻게 정렬하지?"라는 어색한 문제를 스스로 만들게 된다. 파이프라인을 설계할 때는 각 단계의 출력 형태(배열인가, 맵인가)가 다음 단계의 입력 요구와 맞는지를 먼저 그려보라. 형태가 안 맞는 연결은 대개 순서가 잘못됐다는 신호다.

메모이제이션과 참조 동일성: computed 캐시는 보통 의존값의 참조 변화로 재계산을 판단한다. 파생 단계가 매번 새 배열을 돌려주는 것은 정합성 관점에선 올바르지만, 그 출력을 의존하는 하위 단계는 "내용이 같아도 참조가 바뀌었으니" 다시 계산한다. 체인이 길고 데이터가 클 때 이것이 비용이 되면, 내용 비교 기반 캐시나 세분화된 의존 선언으로 조정한다 — 다만 이것은 측정 후의 최적화이지 기본 설계가 아니다.

★ 5. 언어별 대조 — "캐시된 순수 파생"은 어디에나 있다

파생 파이프라인은 프론트엔드 고유 개념이 아니다. "원본을 두고, 순수 계산의 연쇄로 원하는 모양을 얻는다"는 발상이 각 언어에서 어떤 얼굴로 나타나는지 보자.

언어파이프라인의 얼굴캐시특징
JavaStream API — stream().filter().sorted().collect(groupingBy(...))없음(일회성)체인 문법은 동일하나 스트림은 소비되면 끝 — 파생 "상태"가 아니라 파생 "계산 1회"
JS·TSVue computed·React useMemo·selector 라이브러리의존성 추적 캐시UI 반응성과 결합된 파생 — 이 문서의 본론
Python컴프리헨션·제너레이터·itertools.groupby·functools 캐시선택적(데코레이터)지연 평가와 캐시를 명시적으로 조립
C++ranges 라이브러리의 view 체인(C++20)없음(지연 평가)사본 없이 "보는 방법"만 합성 — 불변 원본이 문법으로 강제 가능

Java의 Stream은 파이프라인 사고를 익히기에 가장 좋은 문법이지만 매 호출이 전체 재계산이라는 점에서 computed와 다르고, JS·TS 생태계는 캐시를 프레임워크가 대신 들어주는 형태다. 타깃 언어 둘은 더 깊이 본다.

5.1 Python — 지연 평가 조립과 groupby의 함정

Python은 파생 체인을 제너레이터(generator — 값을 미리 다 만들지 않고 요청될 때 하나씩 내놓는 반복 가능 객체)로 조립할 수 있다. 각 단계가 순수하고, 원본 리스트는 건드리지 않는다:

from itertools import groupby

orders = load_orders()          # 원본 — 이후 변형하지 않는다

visible = (o for o in orders if o.status != "CANCELLED")   # filter
ordered = sorted(visible, key=lambda o: o.date, reverse=True)  # sort (새 리스트)
by_date = {d: list(g) for d, g in groupby(ordered, key=lambda o: o.date)}  # group

여기에 개념 함정이 하나 숨어 있다. itertools.groupby는 SQL의 GROUP BY와 달리 인접한 같은 키끼리만 묶는다. 정렬되지 않은 입력을 주면 같은 날짜가 여러 그룹으로 쪼개져 나온다. 즉 Python에서는 "group은 sort 뒤"라는 파이프라인 순서 규칙이 관례가 아니라 정합성 요건이다 — 4.3절의 순서 논의가 언어 명세로 강제되는 사례다.

캐시가 필요하면 명시적으로 붙인다. 클래스 속성 파생이라면 functools.cached_property가 "처음 읽을 때 계산, 이후 저장값"을 제공한다. 다만 Vue computed와 달리 의존성 추적이 없어서 원본이 바뀌어도 스스로 무효화되지 않는다 — 원본 변경 시 캐시를 직접 지워야 하며, 이 차이를 모르면 "원본은 바꿨는데 파생값이 옛날 것"이라는, 저장 파생의 동기화 버그를 그대로 재현하게 된다.

Python 통찰: 제너레이터 체인은 "소비되면 끝"(Java Stream과 같음)이고, 리스트로 굳히면 그 시점의 스냅샷이다. Python의 파생 설계는 어느 단계에서 지연을 굳혀 스냅샷으로 만들 것인가를 선택하는 문제이며, 프레임워크가 이 선택을 대신해 주지 않는다.

5.2 C++ — 불변을 타입으로 강제하는 view 합성

C++20 ranges의 view는 "데이터를 가공한 결과"가 아니라 데이터를 그렇게 보는 방법을 값으로 만든 것이다. 사본을 만들지 않고 체인을 합성하며, 실제 계산은 순회할 때 일어난다(지연 평가):

#include <ranges>
#include <algorithm>
#include <vector>

const std::vector<Order> orders = load_orders();  // const = 원본 불변을 컴파일러가 보증

auto visible = orders
             | std::views::filter([](const Order& o) {
                   return o.status != Status::Cancelled; });

// 정렬은 view로 할 수 없다 — 재배열은 본질적으로 사본이 필요하다
std::vector<Order> sorted_orders(visible.begin(), visible.end());  // 여기서 실체화
std::ranges::sort(sorted_orders, std::ranges::greater{}, &Order::date);

주목할 지점이 둘이다. 첫째, 원본을 const로 선언하면 파생 단계가 원본을 변형하는 실수(4.1절)가 컴파일 오류가 된다 — 다른 언어에서 규율로 지키는 것을 타입 시스템이 대신 지켜준다. 둘째, filter는 "보는 방법"으로 표현되지만 sort는 view로 표현할 수 없다. 재배열은 원소들의 위치라는 실체를 요구하므로, 이 지점에서 사본을 만들어 실체화(materialize)해야 한다. 파이프라인의 어떤 단계가 값싼 "관점"이고 어떤 단계가 비용을 치르는 "실체화"인지가 C++에서는 코드 구조로 드러난다.

C++ 통찰: view 체인은 원본의 수명에 기생한다 — 원본 벡터가 소멸한 뒤 view를 순회하면 미정의 동작이다. 프레임워크의 computed는 의존 원본의 수명을 런타임이 관리해 주지만, C++에서는 파생이 원본보다 오래 살지 않는다는 수명 규칙을 프로그래머가 직접 보증해야 한다. 파생 설계가 곧 수명 설계가 되는 것이 C++의 고유한 각도다.

함께 알면 좋은 것

  • 단일 진실 원천(single source of truth, SSOT) — "원본은 하나, 나머지는 파생"의 일반화. 상태 설계 전반(전역 store 설계 포함)의 지도 원리다.
  • 시그널(signal) — 최근에는 파생 상태의 의존성 추적을 프레임워크 내부 구현이 아니라 언어 수준 원시 타입으로 표준화하려는 흐름이 뚜렷하다. 쓰기 가능한 상태와 읽기 전용 파생을 구분한 TC39 시그널 제안이 진행 중이고(2024년 Stage 1 진입), Angular·Solid·Preact 등 다수 프레임워크가 이미 시그널 기반 반응성을 채택했다. 개념은 이 문서의 computed와 동일하다 — 이름과 소속만 이동 중이다.
  • 구체화 뷰(materialized view) — 데이터베이스의 같은 문제. 일반 뷰는 "읽을 때 계산"(computed), 구체화 뷰는 "저장해 두고 갱신"(4.2절의 저장 파생)이며, DB 세계는 후자의 동기화 비용을 리프레시 전략이라는 이름으로 정면 관리한다. 파생을 저장으로 되돌리는 게 언제 정당한지에 대한 좋은 대조 사례.
  • 셀렉터 합성 라이브러리 — 파생 체인 + 메모이제이션을 전담하는 도구들(React 생태계의 Reselect가 고전). 4.3절의 참조 동일성 문제를 라이브러리 차원에서 다루는 방식을 보여준다.
  • 속성 기반 검증과 파이프라인 — 3.2절의 단계 사이 검증을 체계화하면 "필터 출력은 항상 원본의 부분집합", "정렬 출력은 순서만 다른 같은 집합" 같은 단계별 불변식(invariant)이 된다. 테스트로 굳혀두면 단계 교체 시의 안전망이 된다.

한 장 요약

  • 원본은 불변으로 하나만 두고, 화면이 원하는 모양은 전부 파생으로 계산한다 — 파생을 저장하면 동기화 책임이 생기고, 그 책임은 언젠가 어긴다.
  • computed/selector의 본질은 순수 함수 + 의존성 추적 + 캐시다. 캐시가 성립하려면 계산이 입력을 변형하지 않아야 한다.
  • 여러 가공은 filter → sort → group의 단계별 체인으로 — 단계 사이에 검증을 끼울 수 있고, 그룹 키 하나만 바꿔 재사용할 수 있다.
  • 제자리 정렬이 원본을 오염시키는 것이 최대 함정 — 사본 정렬([...arr].sort·toSorted)을 습관으로, C++이라면 const로 강제.
  • 순서에는 의미가 있다: 필터는 앞(비용 절감), 그룹은 정렬 뒤(그룹 내 순서 보존 — Python groupby에선 정합성 요건).

S1 프론트엔드 보안 기초

0. 한눈에 보는 결론

  • 프론트엔드 보안 사고의 뿌리는 하나다: 데이터로 취급해야 할 문자열이 코드로 승격되어 실행되는 것. 교차 사이트 스크립팅(cross-site scripting, XSS)은 이 문제의 브라우저판이다.
  • 브라우저는 HTML 문자열 안의 <script>와 이벤트 속성을 구분 없이 해석한다 — 사용자 입력이 그대로 마크업에 섞이면, 입력이 곧 코드가 된다.
  • 1차 방어는 출력 이스케이프(output escaping): 값을 화면에 넣는 순간, 넣는 맥락에 맞게 특수문자를 무력화한다. 현대 프레임워크는 이것을 기본으로 해 준다.
  • v-html·innerHTML류는 그 기본 방어를 의도적으로 끄는 스위치다 — 여기에 사용자 유래 데이터를 넣는 순간 XSS의 문이 열린다.
  • 콘텐츠 보안 정책(Content Security Policy, CSP)은 2차 방어다: 뚫린 뒤에도 "어디서 온 스크립트만 실행 가능"을 브라우저 수준에서 강제해 피해를 차단한다.
  • 입력 필터링만으로는 부족하다 — 같은 값도 어느 맥락에 출력되느냐에 따라 위험이 달라지기 때문이다.

1. 문제의 뿌리 — 데이터가 코드로 승격될 때

모든 인젝션 계열 공격(XSS, SQL 인젝션, 명령 인젝션…)은 같은 구조를 가진다. 프로그램이 "명령"과 "데이터"를 같은 문자열 안에 섞어서 해석기(브라우저·DB·셸)에 넘기면, 해석기는 어디까지가 명령이고 어디부터가 데이터인지 알 길이 없다. 공격자는 데이터 자리에 명령의 문법을 밀어 넣어 그 경계를 무너뜨린다.

개발자 의도: <p>안녕하세요, [사용자이름]님</p> ← 이름은 "데이터" 공격자 입력: <script>steal(document.cookie)</script> 브라우저가 본 것: <p>안녕하세요, <script>…</script>님</p> ← 데이터가 "코드"로 승격

프론트엔드에서 이 해석기는 브라우저이고, 브라우저의 언어는 HTML·JS다. 따라서 프론트엔드 보안 기초의 핵심 질문은 이것이다: 사용자 유래 문자열이 브라우저에게 코드로 읽힐 수 있는 경로가 어디인가, 그 경로마다 승격을 어떻게 차단하는가.

2. XSS의 세 형태 — 주입 경로로 구분한다

형태악성 스크립트가 오는 경로특징
반사형(reflected)요청(URL 파라미터 등)에 실려 와서 응답에 즉시 되돌아 나옴피해자가 조작된 링크를 클릭해야 성립
저장형(stored)게시글·댓글·프로필 등으로 서버에 저장되었다가, 열람하는 모든 사용자에게 실행가장 위험 — 한 번 심으면 다수가 자동 피격
DOM 기반서버를 거치지 않고, 프론트 JS가 URL 조각 등을 읽어 직접 DOM에 꽂으면서 발생서버 로그에 안 남아 탐지 어려움. SPA에서 비중 증가

실행된 스크립트는 그 페이지의 사용자 권한으로 움직인다 — 세션 쿠키·토큰 탈취, 사용자인 척 API 호출, 화면 위조(가짜 로그인 폼)까지. "우리 서비스엔 훔칠 게 없다"는 판단은 대개 틀린다: 로그인 상태 자체가 훔칠 물건이다.

3. 방어 1 — 출력 이스케이프: 맥락이 전부다

이스케이프는 특수문자를 "문법 기호"가 아니라 "그냥 글자"로 바꾸는 변환이다: < → &lt;, " → &quot;. 중요한 것은 출력되는 맥락마다 위험한 문자가 다르다는 사실이다.

출력 맥락예승격 문자
HTML 본문<p>{값}</p>< > &
HTML 속성<img alt="{값}">따옴표 — 속성을 닫고 onerror= 같은 이벤트 속성 주입
JS 문자열 안var name = "{값}";따옴표·역슬래시·</script>
URL<a href="{값}">javascript: 스킴 자체

그래서 "입구에서 한 번 필터링"은 원리적으로 불완전하다 — 입구에서는 이 값이 나중에 어느 맥락에 출력될지 모른다. 올바른 위치는 출력 지점이고, 현대 프레임워크의 템플릿 바인딩(Vue의 {{ }}, React의 JSX 등)이 HTML 맥락 이스케이프를 기본으로 수행하는 이유가 이것이다.

v-html은 "이 값은 이스케이프하지 말고 HTML로 해석하라"는 명시적 선언이다. 즉 프레임워크의 기본 방어를 끄는 스위치. 서버가 만든 신뢰된 마크업을 넣는 정당한 용도가 있지만, 사용자 유래 데이터가 한 방울이라도 섞인 값을 넣으면 그 지점이 곧 XSS다. innerHTML 직접 대입, document.write도 같은 부류다. 텍스트를 넣을 곳엔 textContent·일반 바인딩을 쓴다.

4. 방어 2 — CSP: 뚫린 다음을 대비하는 층

이스케이프가 완벽해도 사람은 실수한다. CSP는 서버가 응답 헤더로 "이 페이지에서 실행 가능한 스크립트의 출처"를 선언하면, 브라우저가 그 외의 실행을 거부하는 2차 방어선이다. 

Content-Security-Policy: script-src 'self' https://cdn.example.com

이 선언 하나로 인라인 <script>와 이벤트 속성(onclick="…") 실행이 기본 차단된다 — 주입에 성공한 공격 코드 대부분이 바로 이 형태라, 이스케이프가 뚫려도 실행 단계에서 막힌다. 핵심 태도는 심층 방어(defense in depth)다: 한 겹이 완벽하다고 가정하지 않고 겹을 쌓는다. 도입 시에는 보고 전용 모드(Content-Security-Policy-Report-Only)로 무엇이 막힐지 관찰한 뒤 강제로 전환하는 것이 정석이다.

5. 흔히 헷갈리는 지점

  • "입력 검증을 하니까 안전하다" — 검증과 이스케이프는 역할이 다르다. 검증은 "이 값이 형식에 맞는가"(이메일·길이 등), 이스케이프는 "이 값이 출력 맥락에서 코드로 승격되지 않는가"다. 이름에 <가 들어간 정당한 입력도 있고, 검증을 통과한 값도 맥락이 바뀌면 위험해진다. 둘 다 한다.
  • 이스케이프 vs 새니타이즈(sanitize). 이스케이프는 전부 글자로 만들기, 새니타이즈는 "허용한 태그만 남기고 위험 요소를 제거"하기다. 사용자에게 서식(굵게·링크)을 허용해야 해서 v-html이 불가피하다면, 검증된 새니타이저 라이브러리로 정화한 결과만 넣는다 — 직접 정규식으로 만드는 새니타이저는 우회 사례가 축적된 실패 장르다.
  • "프론트에서 막았으니 됐다" — 프론트 검증은 UX, 보안은 서버의 몫. 공격자는 브라우저를 거치지 않고 API를 직접 호출한다. 저장형 XSS의 정화·검증은 서버에서도 반드시 수행돼야 한다.
  • 조용한 확산 — 저장형 XSS는 터진 시점과 심은 시점이 다르다. 취약점을 고쳐도 이미 DB에 저장된 악성 콘텐츠는 남아 있다. 패치 후 기존 데이터 정화까지가 대응이다.

★ 6. 언어별 대조

"데이터의 코드 승격"은 브라우저만의 문제가 아니다. 각 언어 생태계에는 저마다의 승격 표면과, 그것을 막는 표준 관용구가 있다 — XSS 방어에서 배운 원리(맥락별 무력화, 코드와 데이터의 분리)가 그대로 반복된다.

언어/환경대표 승격 표면표준 방어
Java(서버 템플릿)JSP에 값 직접 출력JSTL <c:out>·템플릿 엔진의 자동 이스케이프
JS·TS(브라우저)innerHTML·v-html·evaltextContent·기본 바인딩·CSP
Python템플릿 수동 조립·eval류Jinja2 자동 이스케이프·리터럴 파서(아래 심화)
C++포맷 문자열·셸 명령 조립포맷 인자 분리·exec류 인자 배열(아래 심화)

6.1 Python — eval의 유혹과 "코드가 아닌 파서"

Python에서 흔한 승격 사고는 "문자열을 파이썬답게 해석하고 싶을 때" 일어난다. 사용자가 보낸 "[1, 2, 3]"을 리스트로 만들려고 eval을 쓰는 순간, 그 입력칸은 파이썬 인터프리터의 입력창이 된다. 

import ast

user_input = "[1, 2, 3]"
data = eval(user_input)              # 승격: "__import__('os').system('…')"도 실행됨
data = ast.literal_eval(user_input)  # 안전: 리터럴(숫자·문자열·리스트…)만 파싱, 코드는 거부

Python 관점의 통찰: literal_eval은 "표현력을 깎아서 안전을 사는" 설계다 — 리터럴 문법만 받는 파서라 애초에 실행할 코드 개념이 없다. 웹 템플릿의 Jinja2가 자동 이스케이프를 기본값으로 켜 두는 것과 같은 철학이다: 안전이 기본, 위험(|safe 필터)이 명시적 선언. Vue의 {{ }} 기본 / v-html 명시 구도와 정확히 평행하다.

6.2 C++ — 포맷 문자열과 셸: 가장 오래된 승격들

C 계열의 고전 승격이 포맷 문자열 취약점이다. printf(user_input)처럼 사용자 문자열을 포맷 자리에 직접 넣으면, 입력 속 %s·%n 같은 지시자가 코드로 해석되어 스택 읽기·메모리 쓰기까지 이어진다. 셸 명령 조립(system("cmd " + input))도 같은 구조 — 입력 속 ;가 명령 구분자로 승격된다. 

// 취약: 입력이 "포맷 언어"로 해석됨
printf(user_input);                    // 입력에 %n이 있으면 메모리 쓰기
// 안전: 포맷(코드)과 값(데이터)을 분리
printf("%s", user_input);

// 취약: 입력이 "셸 언어"로 해석됨
system(("ping " + host).c_str());      // host = "8.8.8.8; rm -rf /"
// 안전: 인자 배열로 넘겨 셸 해석 자체를 생략 (execvp 계열)

C++ 관점의 통찰: 안전한 API의 공통 형태는 "코드 채널과 데이터 채널의 분리"다 — printf의 포맷/인자 분리, execvp의 명령/인자 배열, DB의 파라미터 바인딩, 그리고 프론트의 템플릿/바인딩 분리까지 전부 같은 해법의 변주다. 인젝션 방어를 개별 암기가 아니라 이 한 문장으로 기억하는 편이 오래간다.

6.3 Java / JS·TS — 한 줄 요약

Java 서버 렌더링에서는 "표현식으로 값 직접 출력"이 위험 표면이고 <c:out>·현대 템플릿 엔진의 자동 이스케이프가 답이다. JS·TS는 이 문서의 본문 그 자체 — 덧붙이면, 프레임워크 없는 바닐라 DOM 조작에서 textContent vs innerHTML의 선택이 곧 이스케이프 여부의 선택이다.

7. 함께 알면 좋은 것

  • 인젝션의 형제들 — SQL 인젝션·명령 인젝션은 해석기만 다른 같은 병. 파라미터 바인딩이 그쪽의 "이스케이프"다.
  • HttpOnly·Secure 쿠키 — 스크립트에서 쿠키 접근을 차단해, XSS가 성공해도 세션 탈취를 어렵게 하는 완화층.
  • Trusted Types — innerHTML류 싱크에 검증된 타입만 들어가도록 브라우저가 강제하는 최신 방어(DOM XSS 겨냥).
  • 새니타이저 라이브러리 — 서식 허용이 필요할 때의 표준 답. 직접 구현 대신 검증된 것을 쓴다.
  • CSP 보고 모드 운영 — 차단 전 관찰 기간을 두는 도입 전략과 위반 리포트 수집.

8. 한 장 요약

  • XSS = 사용자 유래 문자열이 브라우저에게 코드로 승격되는 것. 반사형·저장형·DOM 기반은 주입 경로의 차이다.
  • 1차 방어는 출력 지점의 맥락별 이스케이프 — 프레임워크 기본 바인딩이 해 주며, v-html·innerHTML은 그 방어를 끄는 명시적 스위치다.
  • 2차 방어는 CSP — 실행 가능한 스크립트 출처를 브라우저 수준에서 제한하는 심층 방어.
  • 검증≠이스케이프≠새니타이즈: 역할이 다르며, 서식 허용이 필요하면 검증된 새니타이저만.
  • 보안 판단의 최종 책임은 서버 — 프론트 검증은 우회 가능하다.
  • 모든 인젝션의 공통 해법: 코드 채널과 데이터 채널의 분리.

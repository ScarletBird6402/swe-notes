S1 프론트엔드 보안 기초

0. 한눈에 보는 결론

  • 프론트엔드 보안 사고의 뿌리는 하나다: 데이터로 취급해야 할 문자열이 코드로 승격되어 실행되는 것. 교차 사이트 스크립팅(cross-site scripting, XSS)은 이 문제의 브라우저판이다.
  • 브라우저는 HTML 문자열 안의 <script>와 이벤트 속성을 구분 없이 해석한다 — 사용자 입력이 그대로 마크업에 섞이면, 입력이 곧 코드가 된다.
  • 1차 방어는 출력 이스케이프(output escaping): 값을 화면에 넣는 순간, 넣는 맥락에 맞게 특수문자를 무력화한다. 현대 프레임워크는 이것을 기본으로 해 준다.
  • v-html·innerHTML류는 그 기본 방어를 의도적으로 끄는 스위치다 — 여기에 사용자 유래 데이터를 넣는 순간 XSS의 문이 열린다.
  • 콘텐츠 보안 정책(Content Security Policy, CSP)은 2차 방어다: 뚫린 뒤에도 "어디서 온 스크립트만 실행 가능"을 브라우저 수준에서 강제해 피해를 차단한다.
  • 입력 필터링만으로는 부족하다 — 같은 값도 어느 맥락에 출력되느냐에 따라 위험이 달라지기 때문이다.

1. 문제의 뿌리 — 데이터가 코드로 승격될 때

모든 인젝션 계열 공격(XSS, SQL 인젝션, 명령 인젝션…)은 같은 구조를 가진다. 프로그램이 "명령"과 "데이터"를 같은 문자열 안에 섞어서 해석기(브라우저·DB·셸)에 넘기면, 해석기는 어디까지가 명령이고 어디부터가 데이터인지 알 길이 없다. 공격자는 데이터 자리에 명령의 문법을 밀어 넣어 그 경계를 무너뜨린다.

개발자 의도: <p>안녕하세요, [사용자이름]님</p> ← 이름은 "데이터" 공격자 입력: <script>steal(document.cookie)</script> 브라우저가 본 것: <p>안녕하세요, <script>…</script>님</p> ← 데이터가 "코드"로 승격

프론트엔드에서 이 해석기는 브라우저이고, 브라우저의 언어는 HTML·JS다. 따라서 프론트엔드 보안 기초의 핵심 질문은 이것이다: 사용자 유래 문자열이 브라우저에게 코드로 읽힐 수 있는 경로가 어디인가, 그 경로마다 승격을 어떻게 차단하는가. 해석기가 DB·셸로 바뀌었을 때의 같은 병은 S3·S10이 이어받는다.

2. XSS의 세 형태 — 주입 경로로 구분한다

그 경로를 먼저 분류해야 방어 지점이 보인다 — 악성 스크립트가 어디서 와서 어디로 들어가는지에 따라 세 형태로 나눈다.

형태악성 스크립트가 오는 경로특징
반사형(reflected)요청(URL 파라미터 등)에 실려 와서 응답에 즉시 되돌아 나옴피해자가 조작된 링크를 클릭해야 성립
저장형(stored)게시글·댓글·프로필 등으로 서버에 저장되었다가, 열람하는 모든 사용자에게 실행가장 위험 — 한 번 심으면 다수가 자동 피격
DOM 기반서버를 거치지 않고, 프론트 JS가 URL 조각 등을 읽어 직접 DOM에 꽂으면서 발생서버 로그에 안 남아 탐지 어려움. SPA에서 비중 증가

실행된 스크립트는 그 페이지의 사용자 권한으로 움직인다 — 세션 쿠키·토큰 탈취, 사용자인 척 API 호출, 화면 위조(가짜 로그인 폼)까지. "우리 서비스엔 훔칠 게 없다"는 판단은 대개 틀린다: 로그인 상태 자체가 훔칠 물건이다.

3. 방어 1 — 출력 이스케이프: 맥락이 전부다

세 형태 모두 마지막 순간은 같다 — 문자열이 마크업 자리에 놓이는 순간이다. 그래서 1차 방어도 그 순간을 겨냥한다. 이스케이프는 특수문자를 "문법 기호"가 아니라 "그냥 글자"로 바꾸는 변환이다: < → &lt;, " → &quot;. 중요한 것은 출력되는 맥락마다 위험한 문자가 다르다는 사실이다.

출력 맥락예승격 문자
HTML 본문<p>{값}</p>< > &
HTML 속성<img alt="{값}">따옴표 — 속성을 닫고 onerror= 같은 이벤트 속성 주입
JS 문자열 안var name = "{값}";따옴표·역슬래시·</script>
URL<a href="{값}">javascript: 스킴 자체

그래서 "입구에서 한 번 필터링"은 원리적으로 불완전하다 — 입구에서는 이 값이 나중에 어느 맥락에 출력될지 모른다. 올바른 위치는 출력 지점이고, 현대 프레임워크의 템플릿 바인딩(Vue의 {{ }}, React의 JSX 등)이 HTML 맥락 이스케이프를 기본으로 수행하는 이유가 이것이다.

v-html은 "이 값은 이스케이프하지 말고 HTML로 해석하라"는 명시적 선언이다. 즉 프레임워크의 기본 방어를 끄는 스위치. 서버가 만든 신뢰된 마크업을 넣는 정당한 용도가 있지만, 사용자 유래 데이터가 한 방울이라도 섞인 값을 넣으면 그 지점이 곧 XSS다. innerHTML 직접 대입, document.write도 같은 부류다. 텍스트를 넣을 곳엔 textContent·일반 바인딩을 쓴다.

4. 방어 2 — CSP: 뚫린 다음을 대비하는 층

이스케이프가 완벽해도 사람은 실수한다. CSP는 서버가 응답 헤더로 "이 페이지에서 실행 가능한 스크립트의 출처"를 선언하면, 브라우저가 그 외의 실행을 거부하는 2차 방어선이다. 

Content-Security-Policy: script-src 'self' https://cdn.example.com

이 선언 하나로 인라인 <script>와 이벤트 속성(onclick="…") 실행이 기본 차단된다 — 주입에 성공한 공격 코드 대부분이 바로 이 형태라, 이스케이프가 뚫려도 실행 단계에서 막힌다. 핵심 태도는 심층 방어(defense in depth)다: 한 겹이 완벽하다고 가정하지 않고 겹을 쌓는다.

위 형태는 개념을 보여 주기엔 충분하지만, 허용한 출처 안에 스크립트를 되돌려 주는 엔드포인트(JSONP 등)나 구식 라이브러리가 하나라도 있으면 우회된다 — 호스트 허용 목록은 "그 출처에서 오는 것은 전부 신뢰한다"는 선언이라, 출처가 늘수록 목록을 안전하게 유지하기 어려워진다.

최근에는(2020년대 중반 기준) 출처 대신 요청마다 서버가 만든 무작위 값(nonce)을 <script nonce="…">에 붙이고 정책에 같은 값을 선언하는 방식이 권장된다 — 주입된 스크립트는 그 값을 알 수 없으므로 실행되지 않는다. 함께 쓰는 'strict-dynamic'은 "nonce를 받은 스크립트가 동적으로 로드한 스크립트도 신뢰"라는 뜻으로, 허용 목록을 유지하는 부담을 없앤다. 

Content-Security-Policy: script-src 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'

'unsafe-inline'을 script-src에 넣는 순간 CSP가 막으려던 문(인라인 실행)이 도로 열린다. 구식 브라우저 호환용 대체값으로만, 그것도 nonce와 함께 둘 때만 무해하다 — nonce를 이해하는 브라우저는 'unsafe-inline'을 무시하기 때문이다.

어느 형태든 도입 시에는 보고 전용 모드(Content-Security-Policy-Report-Only)로 무엇이 막힐지 관찰한 뒤 강제로 전환하는 것이 정석이다.

5. 흔히 헷갈리는 지점

  • "입력 검증을 하니까 안전하다" — 검증과 이스케이프는 역할이 다르다. 검증은 "이 값이 형식에 맞는가"(이메일·길이 등), 이스케이프는 "이 값이 출력 맥락에서 코드로 승격되지 않는가"다. 이름에 <가 들어간 정당한 입력도 있고, 검증을 통과한 값도 맥락이 바뀌면 위험해진다. 둘 다 한다.
  • 이스케이프 vs 새니타이즈(sanitize). 이스케이프는 전부 글자로 만들기, 새니타이즈는 "허용한 태그만 남기고 위험 요소를 제거"하기다. 사용자에게 서식(굵게·링크)을 허용해야 해서 v-html이 불가피하다면, 검증된 새니타이저 라이브러리로 정화한 결과만 넣는다 — 직접 정규식으로 만드는 새니타이저는 우회 사례가 축적된 실패 장르다.
  • "프론트에서 막았으니 됐다" — 프론트 검증은 UX, 보안은 서버의 몫. 공격자는 브라우저를 거치지 않고 API를 직접 호출한다. 저장형 XSS의 정화·검증은 서버에서도 반드시 수행돼야 한다.
  • 조용한 확산 — 저장형 XSS는 터진 시점과 심은 시점이 다르다. 취약점을 고쳐도 이미 DB에 저장된 악성 콘텐츠는 남아 있다. 패치 후 기존 데이터 정화까지가 대응이다.

★ 6. 언어별 대조

"데이터의 코드 승격"은 브라우저만의 문제가 아니다. 각 언어 생태계에는 저마다의 승격 표면과, 그것을 막는 표준 관용구가 있다 — XSS 방어에서 배운 원리(맥락별 무력화, 코드와 데이터의 분리)가 그대로 반복된다. 다만 언어마다 "기본 방어가 어디에 놓여 있고, 그것을 끄는 스위치가 무엇인가"가 다르다. 본문이 브라우저를 축으로 봤다면, 여기서는 그 축을 네 언어의 런타임 위로 옮겨 본다.

언어/환경대표 승격 표면(싱크)기본 방어가 놓인 곳방어를 끄는 스위치

6.1 Java — 서버가 HTML을 만드는 순간의 출력 인코딩

Java 서버 렌더링에서 승격 표면은 "템플릿이 값을 문자열로 이어 붙이는 지점"이다. JVM 자체는 String을 단 한 종류만 안다 — 이스케이프된 문자열과 사용자 원문은 런타임에서 구분되지 않으므로, 방어의 규율은 전적으로 템플릿 엔진이 출력 시점에 무엇을 기본으로 하느냐에 달려 있다. 이 기본값이 엔진마다 다르다는 것이 Java 특유의 함정이다. 

<%-- JSP: 표현 언어(EL — ${…}로 값을 꺼내 쓰는 템플릿 문법)는 기본적으로 이스케이프하지 않는다 --%>
<p>안녕하세요, ${param.name}님</p>                 <%-- 승격: 원문 그대로 출력 --%>
<p>안녕하세요, <c:out value="${param.name}"/>님</p>   <%-- 안전: escapeXml 기본 true --%>

<!-- Thymeleaf: 기본이 이스케이프, 끄는 쪽이 명시적 -->
<p th:text="${user.name}">…</p>     <!-- 안전: HTML 맥락 이스케이프 -->
<p th:utext="${post.body}">…</p>    <!-- 스위치: u = unescaped, v-html과 같은 선언 -->
<a th:href="@{/u/{id}(id=${uid})}">  <!-- 링크 식은 파라미터를 URL 인코딩하지만 스킴은 검사하지 않는다 -->

JSP는 역사적 이유로 ${…}가 원문을 내보내고 <c:out>이 이스케이프를 추가하는 구조라 "안전이 옵션"이다. 반면 Thymeleaf처럼 현대 엔진은 th:text가 기본 이스케이프이고 th:utext가 끄는 스위치라 "위험이 옵션"이다. 같은 언어 안에서도 기본값의 방향이 반대이므로, 팀이 어느 엔진을 쓰든 "이 엔진의 기본은 어느 쪽인가"를 먼저 확인하는 것이 Java 서버 XSS 방어의 첫 단계다. 또 하나, 속성 맥락은 별개다 — th:href의 링크 식은 파라미터를 URL 인코딩해 주지만, 사용자가 통째로 넘긴 URL의 javascript: 스킴까지 걸러 주지는 않으므로 스킴 허용 목록은 애플리케이션 코드의 몫이다.

2차 방어인 CSP는 Java에서 "헤더를 누가 붙이느냐"의 문제가 된다. Spring Security는 기본으로 여러 보안 헤더를 붙이지만 CSP는 기본 포함이 아니다 — 명시적으로 선언해야 하며, 헤더 DSL이 보고 전용 모드까지 같이 제공한다. 

// Spring Security 헤더 DSL — CSP는 직접 켜야 한다
http.headers(headers -> headers
    .contentSecurityPolicy(csp -> csp
        .policyDirectives("script-src 'self'; object-src 'none'; base-uri 'self'")
        // 'self' 대신 nonce 기반이 권장 — nonce는 요청마다 생성해 템플릿과 헤더에 같이 넣어야 하므로 필터/인터셉터가 필요(4절)
        .reportOnly()      // 도입기: 관찰만, 강제 전환 시 이 줄 제거
    )
);

Java 관점의 통찰: JVM에는 "안전한 문자열"이라는 타입이 없지만 명목적 타입 시스템(이름이 다르면 다른 타입)이 있어, SafeHtml 같은 래퍼 클래스를 만들면 "이스케이프를 거친 값만 이 타입이 된다"는 규율을 컴파일러가 강제할 수 있다. 출력 인코더 라이브러리들이 반환 타입을 이렇게 구분하는 이유이며, 아래 JS·TS 절의 브랜드 타입과 같은 발상이다.

6.2 JS·TS — 싱크가 곧 파서: DOM API 두 갈래와 그 위의 방어층

JS·TS는 이 문서의 본진이다. 브라우저 안에서 "데이터가 코드로 승격되는 지점"에는 이름이 있다 — 싱크(sink — 문자열을 받아 HTML·URL·스크립트로 해석하는 API). 반대편에 사용자 유래 문자열이 들어오는 소스(source — location.hash·location.search·document.referrer·postMessage 데이터 등)가 있고, 소스에서 싱크까지 이스케이프 없이 흐르면 본문 2절의 DOM 기반 XSS가 된다.

소스 경로 싱크(해석기 호출) location.hash ─────────┐ ┌─ innerHTML / outerHTML / insertAdjacentHTML → HTML 파서 location.search ───────┼─ 문자열 그대로 ─────────┼─ a.href = "javascript:…" → URL 스킴 해석 postMessage 데이터 ────┘ └─ eval / new Function / setTimeout("…") → JS 파서 ┌───────────────────────────────────────────────────────────────┐ │ textContent / createElement + append / setAttribute("alt", …) │ → 이스케이프 없이 안전한 갈래: 트리에 직접 삽입, 파서 미호출 └───────────────────────────────────────────────────────────────┘

핵심은 DOM API가 두 갈래라는 점이다. innerHTML 대입은 그 자리에서 HTML 파서를 동기적으로 호출한다 — 문자열은 마크업으로 해석된다. 반면 textContent·createElement·append는 파서를 거치지 않고 트리 노드를 직접 만든다. 이 갈래에서는 이스케이프가 "안 필요한" 것이 아니라 개념 자체가 없다 — 애초에 해석기를 부르지 않기 때문이다. 

const q = new URLSearchParams(location.search).get("q") ?? "";

el.innerHTML = `검색어: ${q}`;             // 승격: HTML 파서 호출 — q = '<img src=x onerror="…">'
el.textContent = `검색어: ${q}`;           // 안전: 텍스트 노드 — 파서 미호출

link.href = q;                             // 승격: "javascript:" 스킴이면 클릭 시 실행
link.href = /^https?:\/\//.test(q) ? q : "#";  // 안전: 스킴 허용 목록

el.innerHTML = "<script>alert(1)</script>";   // 실행 안 됨(HTML 명세) — 그러나
el.innerHTML = "<img src=x onerror=…>";        // 이벤트 속성은 실행됨: "script 태그는 안 도니 안전"은 오해

런타임의 함정 하나를 짚자. HTML 명세상 innerHTML로 삽입된 <script>는 실행되지 않는다 — 여기서 "그러니 안전하다"는 오해가 나오지만, onerror 같은 이벤트 속성과 <svg onload>류는 그대로 실행된다. 파서를 부르는 순간 어떤 문법이 코드가 될지는 브라우저가 결정하며, 개발자가 그 목록을 외워서 막는 방식은 실패한다.

프레임워크는 이 두 갈래를 기본값으로 정리해 준다. Vue의 {{ }}·v-bind, React의 JSX 자식과 속성은 이스케이프된 텍스트/속성으로 삽입되고, v-html·dangerouslySetInnerHTML이 파서 갈래로 넘어가는 명시적 스위치다. 다만 프레임워크의 경계는 HTML 맥락까지다 — :href·href={url}에 바인딩된 값의 javascript: 스킴은 두 프레임워크 모두 자동으로 걸러 주지 않는다(경고를 내는 버전은 있으나 차단에 의존하지 말 것). 본문 3절의 "URL 맥락은 스킴 자체가 승격 문자"가 프레임워크 안에서도 그대로 남는 지점이다.

그 위에 브라우저 수준의 방어층이 있다. Trusted Types는 CSP 지시어 하나로 "문자열은 싱크에 못 들어간다"를 강제한다 — 등록된 정책이 만든 TrustedHTML 객체만 innerHTML류가 받고, 평범한 문자열 대입은 예외를 던진다. 즉 "어딘가에서 이스케이프를 잊었다"는 사고를 싱크에서 런타임 오류로 바꾸는 장치이며, 새니타이저는 이 정책 안에 자리 잡는다. 2020년대 중반 기준 Chromium 계열에 이어 Firefox도 지원하고(2026년 초), 미지원 브라우저는 지시어를 무시하므로 점진 도입이 가능하다. 서식 허용이 필요한 경우의 새니타이저는 DOMPurify류 라이브러리가 표준 답이고, 브라우저 내장 Element.setHTML()(Sanitizer API)이 2026년 초부터 일부 브라우저에 실리기 시작했으나 아직 전 브라우저 기본이 아니므로 기능 감지 후 라이브러리로 대체하는 구성이 관례다. 주의할 점은 짝이 되는 setHTMLUnsafe()다 — 이름대로 새니타이즈를 하지 않는 갈래이며 더 일찍 널리 실렸으므로, 자동 완성에서 고른 메서드가 어느 쪽인지 확인해야 한다(라이브러리의 "검증 없는 decode" 함정과 같은 구조). 

// CSP: Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app
const policy = trustedTypes.createPolicy("app", {
  createHTML: (dirty) => DOMPurify.sanitize(dirty)   // 새니타이저는 정책 안에서만
});
el.innerHTML = policy.createHTML(userHtml);   // OK: TrustedHTML
el.innerHTML = userHtml;                      // TypeError — 문자열은 싱크에 못 들어감

TS는 여기서 아무것도 보태지 못한다는 사실이 중요하다. 타입은 컴파일 시 지워지고(타입 소거 — 타입 정보가 실행 코드에 남지 않는 것), 무엇보다 소스에서 온 문자열과 이스케이프된 문자열이 둘 다 string이라 구조적 타이핑상 구분이 없다. 브랜드 타입(branded type — 실제 값은 같지만 이름표 필드를 덧붙여 컴파일러가 다른 타입으로 보게 하는 기법)으로 "안전한 문자열"을 흉내 낼 수는 있다. 

type SafeHtml = string & { readonly __brand: "SafeHtml" };
const sanitize = (dirty: string): SafeHtml => DOMPurify.sanitize(dirty) as SafeHtml;
function setHtml(el: Element, html: SafeHtml) { el.innerHTML = html; }

setHtml(el, sanitize(userInput));   // OK
setHtml(el, userInput);             // 컴파일 에러 — string은 SafeHtml이 아니다
// 단, as 캐스트 한 줄이면 뚫리고 런타임엔 아무 검사도 남지 않는다

JS·TS 관점의 통찰: 브랜드 타입은 컴파일 타임의 Trusted Types이고, Trusted Types는 런타임의 브랜드 타입이다. 전자는 as 한 줄로 우회되고 후자는 정책이 없으면 앱이 멈춘다 — 그래서 둘을 겹쳐 쓴다. "이스케이프를 어디서 했는가"를 코드 리뷰로 추적하는 대신, 싱크에 들어갈 수 있는 값의 종류를 타입으로 좁히는 것이 JS·TS에서 XSS 방어를 구조화하는 방법이다.

6.3 Python — eval의 유혹, 그리고 "안전"을 값에 실어 나르는 객체 모델

Python에서 흔한 승격 사고는 "문자열을 파이썬답게 해석하고 싶을 때" 일어난다. 사용자가 보낸 "[1, 2, 3]"을 리스트로 만들려고 eval을 쓰는 순간, 그 입력칸은 파이썬 인터프리터의 입력창이 된다. 

import ast

user_input = "[1, 2, 3]"
data = eval(user_input)              # 승격: 임의 식이 인터프리터에서 실행됨
data = ast.literal_eval(user_input)  # 안전: 리터럴(숫자·문자열·리스트…)만 파싱, 코드는 거부

웹 템플릿 쪽의 함정은 더 조용하다. Jinja2는 흔히 "자동 이스케이프가 기본"으로 알려져 있지만, 정확히는 Environment()를 직접 만들면 기본이 꺼져 있다. 켜는 표준 방법인 select_autoescape()는 템플릿 파일 확장자(.html·.htm·.xml)를 보고 결정하므로, .txt나 .j2 같은 이름의 템플릿이나 문자열에서 바로 만든 Template("…")은 이스케이프 없이 렌더링된다. Flask가 render_template에서 HTML 계열 확장자만 자동으로 켜 주는 것도 같은 규칙의 결과다 — "프레임워크가 해 준다"는 믿음이 확장자 하나에 걸려 있다. 

from jinja2 import Environment, FileSystemLoader, select_autoescape
from markupsafe import Markup, escape

env = Environment(loader=FileSystemLoader("templates"))            # autoescape 기본 False
env = Environment(loader=FileSystemLoader("templates"),
                  autoescape=select_autoescape())                  # .html/.htm/.xml만 켜짐
env = Environment(loader=FileSystemLoader("templates"), autoescape=True)  # 확장자 무관 항상

# Markup: "이미 안전한 HTML"임을 값 자체에 표식
Markup("<b>{}</b>").format(user_name)   # 안전: 인자는 이스케이프되어 들어감
Markup(f"<b>{user_name}</b>")           # 스위치: 완성된 문자열에 표식만 붙임 — |safe와 동일한 위험

여기서 Python 객체 모델이 드러난다. Markup은 str의 서브클래스로, "이 값은 이스케이프를 마쳤다"는 사실을 런타임 값의 타입에 실어 나른다. 템플릿 엔진은 출력 시점에 __html__() 메서드가 있는 객체를 신뢰된 마크업으로 취급하는데, 이것은 덕 타이핑 — 클래스 이름이 아니라 "그 메서드를 갖고 있는가"로 판단 — 이 보안 규약으로 쓰인 사례다. 그래서 Markup + 일반 str은 일반 쪽을 자동 이스케이프해 합치고, 템플릿의 |safe 필터와 Markup() 생성자는 같은 스위치의 두 얼굴이 된다.

Python 관점의 통찰: literal_eval은 "표현력을 깎아서 안전을 사는" 설계다 — 리터럴 문법만 받는 파서라 애초에 실행할 코드 개념이 없다. 템플릿 쪽도 같은 철학이지만 방향이 하나 더 있다: TS가 컴파일 후 잃어버리는 "안전한 문자열" 구분을 Python은 Markup이라는 런타임 타입으로 끝까지 들고 간다. 대신 그 표식은 Markup()에 무엇을 넣느냐에 전적으로 의존하므로, 안전이 기본·위험이 명시라는 구도(Vue의 {{ }} / v-html)는 유지되되 "명시적 위험"의 자리가 |safe 하나가 아니라 Markup 생성자와 autoescape 설정까지 셋이다.

6.4 C++ — 포맷 문자열과 셸: 가장 오래된 승격, 그리고 컴파일 타임 봉쇄

C 계열의 고전 승격이 포맷 문자열 취약점이다. printf(user_input)처럼 사용자 문자열을 포맷 자리에 직접 넣으면, 입력 속 %s·%n 같은 지시자가 코드로 해석되어 스택 읽기·메모리 쓰기까지 이어진다 — %n은 "지금까지 출력한 글자 수를 다음 인자가 가리키는 주소에 써라"는 지시자라, 인자가 없으면 스택에 우연히 놓인 값을 주소로 삼는다. 메모리 안전이 언어에 없기에 문자열 해석 오류가 곧 메모리 훼손이 되는 것이 C++ 특유의 증폭이다. 셸 명령 조립(system("cmd " + input))도 같은 구조 — 입력 속 ;가 명령 구분자로 승격된다(인자 배열로 나누는 예제는 S3 6.4). 

// 취약: 입력이 "포맷 언어"로 해석됨
printf(user_input);                    // 입력에 %n이 있으면 메모리 쓰기 (-Wformat-security가 경고)
// 안전: 포맷(코드)과 값(데이터)을 분리
printf("%s", user_input);

// 셸 명령 조립(system)도 같은 구조 — 인자 배열(execvp)로 나누는 예제는 S3 6.4 참조

현대 C++는 이 문제를 컴파일 타임으로 끌어올렸다. C++20 std::format의 포맷 문자열 매개변수는 컴파일 시점에 평가되어야 하는 타입(format_string)이라, 런타임 문자열을 포맷 자리에 넣으면 아예 컴파일되지 않는다. 포맷 "언어"는 리터럴에만 존재할 수 있고, 정말 런타임 포맷이 필요하면 std::vformat이라는 별도 이름을 써야 한다 — 위험한 경로에 다른 이름을 붙여 명시적 스위치로 만든 셈이다. 

#include <format>

std::string s1 = std::format("{}", user_input);   // 안전: 포맷은 리터럴, 값은 인자
std::string s2 = std::format(user_input);         // 컴파일 에러 — 런타임 문자열은 포맷이 될 수 없다
std::string s3 = std::vformat(user_input, std::make_format_args());  // 명시적 스위치 (2020년대 중반 기준 C++20 DR 반영 컴파일러)

// "안전한 문자열" 타입: 암시 변환을 막은 래퍼 — 런타임 비용 0
struct SafeHtml { std::string v; explicit SafeHtml(std::string s) : v(std::move(s)) {} };
SafeHtml escape_html(std::string_view raw);      // 유일한 생산 경로
void write_body(SafeHtml html);                  // std::string을 넘기면 컴파일 에러

HTML 출력 자체에 관해서는 C++가 특이한 위치에 있다. 표준 라이브러리에 HTML 이스케이프 함수가 없어 서버·임베디드 코드가 직접 짜거나 라이브러리를 들이는데, 직접 짤 때 흔한 실수가 본문 3절의 "맥락별 승격 문자" 목록을 HTML 본문 기준으로만 만드는 것이다(속성 맥락의 따옴표 누락). 대신 명목적 타입과 explicit 생성자로 위 SafeHtml처럼 "생산 경로가 하나뿐인 타입"을 만들면, TS의 브랜드 타입과 달리 캐스트 없이는 우회할 수 없고 Python의 Markup과 달리 런타임 객체 비용도 없다 — 타입 소거가 아니라 타입은 컴파일러가, 값은 그냥 문자열이 맡는 분업이다.

C++ 관점의 통찰: 안전한 API의 공통 형태는 "코드 채널과 데이터 채널의 분리"다 — printf의 포맷/인자 분리, execvp의 명령/인자 배열, DB의 파라미터 바인딩, 그리고 프론트의 템플릿/바인딩 분리까지 전부 같은 해법의 변주다. C++20 std::format은 여기서 한 걸음 더 나가 그 분리를 컴파일러가 강제한다: 코드 채널(포맷)은 상수여야 하고 데이터 채널(인자)만 런타임 값을 받는다. 인젝션 방어를 개별 암기가 아니라 이 한 문장으로 기억하는 편이 오래간다 — 그리고 가능하다면 그 문장을 타입으로 적어 컴파일러에게 넘긴다.

7. 함께 알면 좋은 것

  • 인젝션의 형제들 — SQL 인젝션·명령 인젝션은 해석기만 다른 같은 병. 파라미터 바인딩이 그쪽의 "이스케이프"다.
  • HttpOnly·Secure·SameSite 쿠키와 __Host- 접두 — 스크립트의 쿠키 접근 차단(XSS 완화), 교차 사이트 자동 전송 제한(CSRF 완화), 접두로 Secure·Path=/·Domain 없음을 브라우저가 강제. 보관 위치 판단은 S2 6절.
  • 하위 리소스 무결성(Subresource Integrity, SRI) — CDN에서 받는 스크립트 태그에 해시(integrity=)를 붙여, 허용한 출처가 변조돼도 실행을 거부한다. CSP의 출처 허용 목록이 못 막는 "허용된 출처의 내용 변조"를 막는 층.
  • 새니타이저 라이브러리 — 서식 허용이 필요할 때의 표준 답. 직접 구현 대신 검증된 것을 쓴다.
  • CSP 보고 모드 운영 — 차단 전 관찰 기간을 두는 도입 전략과 위반 리포트 수집.

8. 한 장 요약

  • XSS = 사용자 유래 문자열이 브라우저에게 코드로 승격되는 것. 반사형·저장형·DOM 기반은 주입 경로의 차이다.
  • 1차 방어는 출력 지점의 맥락별 이스케이프 — 프레임워크 기본 바인딩이 해 주며, v-html·innerHTML은 그 방어를 끄는 명시적 스위치다.
  • 2차 방어는 CSP — 실행 가능한 스크립트 출처를 브라우저 수준에서 제한하는 심층 방어.
  • 검증≠이스케이프≠새니타이즈: 역할이 다르며, 서식 허용이 필요하면 검증된 새니타이저만.
  • 보안 판단의 최종 책임은 서버 — 프론트 검증은 우회 가능하다.
  • 모든 인젝션의 공통 해법: 코드 채널과 데이터 채널의 분리.

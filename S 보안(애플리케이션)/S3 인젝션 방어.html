S3 인젝션 방어

0. 한눈에 보는 결론

  • 인젝션은 S1에서 본 XSS와 같은 병이다: 데이터로 취급해야 할 문자열이 해석기에게 코드로 승격되어 실행된다. 브라우저 대신 데이터베이스가 해석기면 그것이 SQL 인젝션(SQL injection)이다.
  • 근본 원인은 하나 — 프로그램이 명령(SQL 문법)과 데이터(사용자 값)를 같은 문자열로 조립해 DB에 넘기는 것. 문자열 이어붙이기(string concatenation)가 사고의 진원지다.
  • 1차 방어는 파라미터 바인딩(parameterized query): 쿼리의 골격(코드)을 먼저 DB에 보내 확정하고, 값(데이터)은 별도 채널로 나중에 전달한다. 값이 아무리 SQL처럼 생겨도 문법으로 해석될 통로가 없다.
  • 2차 방어는 입력 검증(input validation): 값이 형식·정책에 맞는지 확인한다. 바인딩과 역할이 다르다 — 바인딩은 "값이 코드로 새지 않게", 검증은 "이 값이 애초에 받아도 되는 값인가".
  • 바인딩이 통하지 않는 자리가 있다 — 예: 어느 페이지로 보낼지 결정하는 URL 값. 여기엔 해석기의 코드/데이터 경계가 없어서, 검증(특히 허용 목록, allowlist)이 유일한 방어다. 오픈 리다이렉트(open redirect)가 대표 사례다.
  • 모든 인젝션 방어의 한 문장: 코드 채널과 데이터 채널을 분리하라. 분리가 불가능한 자리에서만 검증으로 값을 통제하라.

1. 같은 병, 다른 해석기 — S1의 명제를 서버로 옮기면

S1의 명제 하나로 시작한다 — 명령과 데이터를 같은 문자열에 섞어 해석기에 넘기면, 해석기는 경계를 모르고 공격자는 데이터 자리에 명령 문법을 밀어 넣는다.

XSS에서 해석기는 브라우저였다. 백엔드로 내려오면 해석기가 바뀐다 — 가장 흔한 것이 데이터베이스이고, 그때 이 문제를 SQL 인젝션이라 부른다. 셸이면 명령 인젝션, LDAP이면 LDAP 인젝션 — 이름만 다를 뿐 구조는 동일하다.

개발자 의도: SELECT * FROM users WHERE name = '[입력]' ← 입력은 "데이터" 공격자 입력: ' OR '1'='1 DB가 본 것: SELECT * FROM users WHERE name = '' OR '1'='1' ← 데이터가 "코드"로 승격

따라서 이 문서의 질문은 S1과 같은 형태다: 사용자 유래 문자열이 해석기에게 코드로 읽힐 수 있는 경로가 어디인가, 그 경로마다 승격을 어떻게 차단하는가. 이 문서는 그 해석기가 DB일 때(2~3절)와, 해석기가 아예 없이 값 자체가 결정이 될 때(4절)를 차례로 본다.

2. SQL 인젝션 해부 — 이어붙이기가 문을 연다

문제는 거의 항상 이 한 줄에서 시작한다 — 사용자 값을 SQL 문자열에 직접 이어붙이는 코드다. 

// 취약: name이 SQL 문법으로 해석될 수 있다
String sql = "SELECT * FROM users WHERE name = '" + input + "'";

input이 평범한 이름이면 문제없어 보인다. 하지만 input에 따옴표가 들어오면, 그 따옴표는 개발자가 열어 둔 문자열 리터럴을 닫아 버리고, 뒤에 붙은 문자열은 SQL 문법으로 읽힌다. 데이터 자리에서 시작한 값이 명령의 일부로 승격되는 순간이다.

공격 입력완성된 쿼리(개념)결과
' OR '1'='1… WHERE name = '' OR '1'='1'조건이 항상 참 → 전체 행 노출(인증 우회)
'; DROP TABLE users;--… name = ''; DROP TABLE users;--'다중 문장 실행(허용 시) → 데이터 파괴
' UNION SELECT ...원 쿼리에 다른 조회 결과를 이어 붙임다른 테이블 데이터 탈취

피해는 조회에 그치지 않는다 — 인증 우회, 데이터 탈취·변조·삭제, 때로는 DB 계정 권한을 통한 서버 장악까지 이어진다. 핵심은 "우리 입력칸은 짧으니 괜찮다"는 판단이 대개 틀린다는 것: 취약한 것은 입력의 길이가 아니라 조립 방식이다.

최근 동향을 하나만 덧붙이면(2020년대 중반 기준), OWASP Top 10 2025년판에서 인젝션은 A05다 — 2021년판의 A03에서 두 계단 내려왔지만 여전히 상위이고, 가장 많은 취약점 유형(CWE)이 묶이는 범주로 남아 있다.

3. 방어 1 — 파라미터 바인딩: 채널을 나눈다

근본 해법은 이스케이프가 아니라 구조를 바꾸는 것이다. 파라미터 바인딩(=prepared statement)은 쿼리를 두 단계로 나눈다.

  1. 골격(코드) 먼저. 값이 들어갈 자리를 ?·$1 같은 자리표시자(placeholder)로 비운 채, 쿼리 구조를 DB에 먼저 보내 파싱·확정한다.
  2. 값(데이터) 나중에. 실제 값은 별도 채널로 전달한다. 이 시점엔 쿼리 구조가 이미 굳어 있어, 값이 무엇이든 새 문법으로 해석될 통로가 없다.
// 안전: 코드 채널(쿼리)과 데이터 채널(값)을 분리
String sql = "SELECT * FROM users WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, input);   // input = "' OR '1'='1" 여도 그냥 '이름 문자열'일 뿐

이제 input에 ' OR '1'='1이 들어와도, DB는 그것을 "name이라는 이름을 가진 사용자를 찾아라"로 읽는다 — 그런 이름이 없을 뿐, 문법으로 해석되지 않는다. 이것이 S1 마지막에 요약했던 "코드 채널과 데이터 채널의 분리"의 DB 판이다. XSS의 출력 이스케이프가 출력 지점에서 무력화하는 방식이라면, 바인딩은 애초에 값이 코드 문맥에 닿지 못하게 통로 자체를 나눈다.

"따옴표를 직접 이스케이프하면 되지 않나?" — 손으로 '를 ''로 바꾸는 방식은 우회 사례가 축적된 실패 장르다. 문자셋 차이, 유니코드 변형, 숫자 컨텍스트(따옴표 없는 자리)에서 줄줄이 뚫린다. 바인딩이 존재하는데 수동 이스케이프를 택할 이유는 없다.

바인딩이 안 되는 자리: 식별자. 자리표시자는 값(WHERE의 비교 대상, INSERT의 데이터)만 바인딩한다. 테이블·컬럼 이름, 정렬 방향(ASC/DESC) 같은 식별자는 쿼리 구조의 일부라 바인딩할 수 없다. 정렬 컬럼을 사용자가 고르게 하는 화면이라면, 그 값은 반드시 허용 목록으로 검증한다(예: {"name","created_at"}에 있는 값만 통과). 여기서 4절의 검증과 만난다.

4. 방어 2 — 입력 검증: 값 자체가 결정일 때

바인딩은 "값이 코드로 새지 않게" 하는 방어다. 그런데 값이 해석기로 들어가지 않고, 그 값 자체가 프로그램의 결정이 되는 자리가 있다. 이런 곳엔 분리할 코드/데이터 경계가 없어서 바인딩이라는 개념이 성립하지 않는다 — 값이 정책에 맞는지 검증하는 것이 유일한 방어다.

입력 검증은 두 원칙이 핵심이다. 첫째, 허용 목록 우선 — "위험한 것을 막는다"(차단 목록)가 아니라 "허용한 것만 통과시킨다". 위험의 목록은 끝이 없지만 허용의 목록은 유한하다. 둘째, 검증은 이스케이프·바인딩을 대체하지 않는다 — 역할이 다르다(5절).

4.1 사례 — 오픈 리다이렉트: URL을 신뢰하면 벌어지는 일

로그인 후 원래 보던 페이지로 돌려보내려고, 앱은 흔히 URL 파라미터에 목적지를 실어 나른다: /login?next=/dashboard. 로그인이 끝나면 서버는 next 값으로 리다이렉트한다. 문제는 이 값을 검증 없이 그대로 믿을 때 생긴다.

정상: /login?next=/dashboard → 로그인 후 우리 사이트 /dashboard로 공격: /login?next=https://evil.example → 로그인 후 공격자 사이트로 튕겨 나감

공격자는 우리 도메인에서 시작하는 링크를 미끼로 뿌린다. 사용자는 신뢰하는 주소라 여겨 클릭하지만, 로그인 직후 감쪽같이 공격자의 가짜 로그인 화면으로 넘어간다 — 진짜 사이트를 거쳐 왔기에 의심이 무뎌진다(피싱 신뢰 세탁). 여기에 javascript: 스킴까지 허용되면 리다이렉트 순간 스크립트가 실행되어 S1의 DOM 기반 XSS로 번진다.

이 값에는 "바인딩"할 대상이 없다. 목적지 URL 자체가 결정이므로, 방어는 오직 검증이다:

  • 스킴 허용 목록. http·https만 허용하고 javascript:·data:·기타 스킴은 거부한다. 상대 경로만 받는다면 스킴이 아예 없어야 한다.
  • 자기 참조(self-reference)만 허용. 목적지 호스트가 우리 도메인일 때만 통과시킨다. 외부로 나가는 리다이렉트가 업무상 필요하면, 임의 URL 대신 신뢰 목적지 허용 목록에 있는 것만 허용한다.
  • 가장 안전한 형태: 값을 URL로 받지 않기. 목적지를 next=profile 같은 불투명 키로 받고, 서버가 그 키를 {"profile" → "/user/profile"} 사전에서 실제 경로로 번역한다. 사용자 입력이 목적지 문자열에 직접 닿지 않으니 우회 여지가 사라진다.

순진한 문자열 검사는 뚫린다. "https://mysite.com으로 시작하면 통과"는 https://mysite.com.evil.example(하위처럼 보이는 다른 도메인)이나 https://evil.example/https://mysite.com(경로에 심기)로 우회된다. //evil.example(스킴 생략, 브라우저가 프로토콜 상대 URL로 해석), \ 대 / 혼동, URL 파서 간 해석 차이도 고전적 우회 표면이다. 그래서 "시작 문자열 비교"가 아니라 URL을 정식으로 파싱해 호스트를 꺼내 허용 목록과 정확히 대조하고, 되도록 위의 불투명 키 방식으로 문제를 아예 없앤다.

오픈 리다이렉트는 SQL 인젝션과 표면이 전혀 다르지만 배우는 교훈은 이어진다 — 채널을 나눌 수 있으면 나누고(바인딩), 나눌 수 없으면 허용 목록으로 값을 좁힌다(검증). 3절 끝의 "정렬 컬럼은 허용 목록으로"가 바로 이 검증이 SQL 세계에서 필요한 지점이었다.

5. 흔히 헷갈리는 지점

  • "입력 검증을 하니까 SQL 인젝션은 안전하다" — 검증과 바인딩은 역할이 다르다. 검증은 "이 값이 받아도 되는 형식인가"(이메일·길이·허용 목록), 바인딩은 "이 값이 SQL 문법으로 승격되지 않는가"다. 이름에 따옴표가 들어간 정당한 입력(O'Brien)도 있다 — 검증으로 막을 값이 아니라 바인딩으로 안전하게 넘길 값이다. 둘 다 한다. S1의 "검증 ≠ 이스케이프"와 정확히 같은 구도.
  • "ORM을 쓰니까 자동으로 안전하다" — 대체로 맞지만 예외가 있다. ORM의 일반 조회는 내부적으로 바인딩한다. 그러나 raw 쿼리·문자열 조립 API에 값을 이어붙이면 바인딩이 사라진다. "ORM 사용"이 아니라 "값이 바인딩 채널로 가는가"가 판단 기준이다.
  • 차단 목록(blocklist) vs 허용 목록. "위험 키워드(DROP, -- 등)를 걸러낸다"는 접근은 우회의 무한 게임이다(대소문자·주석·인코딩 변형). 허용 목록이 원칙인 이유: 안전의 정의는 유한하지만 위험의 정의는 그렇지 않다.
  • "프론트에서 검증했으니 됐다" — S1과 같은 이유로 서버가 다시 한다. 공격자는 브라우저를 거치지 않는다.

★ 6. 언어별 대조

5절의 판단 기준 — "값이 바인딩 채널로 가는가" — 는 네 언어에서 그대로 통하지만, 채널이 조용히 닫히는 자리는 언어마다 다르다. Java는 바인딩을 누가(서버냐 드라이버냐) 수행하는지와 ORM이 걸러 주지 못하는 식별자 자리가, JS·TS는 드라이버마다 다른 자리표시자와 겉모습이 같은 두 종류의 템플릿 리터럴이, Python은 문자열 포맷과 똑같이 생긴 자리표시자가, C++은 해석기가 DB를 넘어 셸까지 확장되는 지점이 각각의 함정이다. 원리(코드/데이터 채널 분리, 못 나누면 허용 목록)는 반복되고, 그 원리가 어떤 API 형태로 드러나는가가 다르다.

언어바인딩 API(자리표시자)채널이 조용히 닫히는 자리그 언어만의 특이점
Java PreparedStatement의 ?, JPA의 명명 파라미터 :name Statement 문자열 조립, JPQL·네이티브 쿼리에 문자열 결합 데이터베이스 드라이버에 따라 "서버 측 prepare"가 아니라 "클라이언트 측 이스케이프 에뮬레이션"일 수 있다
JS·TS 드라이버별 $1(위치 지정)·?(순서), 태그드 템플릿 리터럴 일반 템플릿 리터럴로 값 삽입, JSON 객체가 그대로 쿼리 구조로 흘러감 타입 선언은 컴파일 시 지워져 문자열의 출처를 구분하지 못한다
Python DB-API 자리표시자 — 드라이버마다 5종 중 하나(%s/?/:name …) % 연산자·f-string으로 쿼리를 먼저 완성 %s가 문자열 포맷과 똑같이 생겼다 — 콤마 하나가 채널의 경계
C++ PQexecParams·mysql_stmt_bind_param, execvp의 인자 배열 +·snprintf로 쿼리·셸 명령 조립, system() 채널 분리가 함수 시그니처(텍스트 + 값 배열)로 드러나며, 값 버퍼의 수명이 개발자 책임

6.1 Java — 바인딩은 "누가 prepare하는가"까지 봐야 한다

3절의 PreparedStatement가 안전한 이유를 프로토콜 수준에서 다시 보면, 두 단계가 서로 다른 패킷으로 오간다. 먼저 자리표시자만 있는 SQL 텍스트가 DB 서버로 가고, 서버가 그것을 파싱해 문장 핸들(statement handle — 서버가 확정한 쿼리 골격을 가리키는 번호표)을 돌려준다. 실행 시점에는 이 핸들과 함께 값이 타입·길이 정보를 붙인 바이너리 파라미터로 전송된다. 값이 SQL 텍스트와 합쳐지는 순간이 프로토콜 어디에도 없으므로, 값이 따옴표를 품고 있든 세미콜론을 품고 있든 문법으로 읽힐 통로가 원천적으로 없다.

그런데 이 그림이 항상 성립하지는 않는다. 일부 데이터베이스 드라이버는 PreparedStatement라는 같은 API를 제공하면서도 내부에서는 클라이언트 측 에뮬레이션을 한다 — 드라이버가 값을 직접 이스케이프해 한 문장으로 합친 뒤 일반 쿼리로 보내는 방식이다. 대표적으로 MySQL용 드라이버는 2020년대 중반 기준으로도 서버 측 prepare가 기본 꺼짐이고 연결 옵션으로 켜야 한다. 에뮬레이션도 드라이버가 연결 문자셋을 알고 이스케이프하므로 손 이스케이프와는 달리 실용적으로 안전하지만, "바인딩 = 프로토콜 분리"라는 명제가 API 이름만으로 보장되지는 않는다는 점은 알아 둘 가치가 있다.

서버 측 prepare (프로토콜 분리) [1] "SELECT … WHERE name = ?" ──텍스트 패킷──▶ 서버 파싱·확정 → 문장 핸들 [2] 값 "O'Brien" ──바이너리 파라미터 패킷──▶ 핸들 실행 → 값이 SQL 텍스트와 합쳐지는 순간이 없다 드라이버 측 에뮬레이션 (클라이언트 이스케이프) [1] 드라이버가 값을 이스케이프해 한 문장으로 합침 "… name = 'O\'Brien'" [2] 완성된 문장을 일반 쿼리로 전송 → 안전이 드라이버의 이스케이프 정확성(문자셋 인지)에 의존

생태계 관행에서 더 흔한 함정은 ORM이다. JPA의 JPQL은 SQL이 아니지만 여전히 문자열이고, JPQL 파서라는 또 하나의 해석기가 있다. createQuery에 값을 이어붙이면 승격 통로가 그대로 다시 열리고, 네이티브 쿼리(createNativeQuery)로 내려가면 3절의 문제로 정확히 되돌아간다. ORM이 막아 주는 것은 값 바인딩이지 문자열 결합이 아니다 — 5절의 "ORM 사용이 아니라 값이 바인딩 채널로 가는가"가 여기서 코드로 보인다. 

// 취약: JPQL도 문자열이다 — 이어붙이면 승격 통로가 다시 열린다
List<User> r = em.createQuery(
    "SELECT u FROM User u WHERE u.name = '" + name + "'", User.class).getResultList();

// 안전: 명명 파라미터 — 골격은 상수, 값은 setParameter로 별도 전달
List<User> r = em.createQuery(
    "SELECT u FROM User u WHERE u.name = :name", User.class)
    .setParameter("name", name).getResultList();

// 바인딩이 안 되는 자리: 정렬 컬럼(식별자) → 허용 목록을 통과한 값만 조립
static final Set<String> SORTABLE = Set.of("name", "created_at");
if (!SORTABLE.contains(sortBy)) throw new IllegalArgumentException("sort");
String jpql = "SELECT u FROM User u ORDER BY u." + sortBy;   // 통과한 값은 사실상 상수

ORM이 못 막는 것도 분명하다. 정렬 컬럼, 동적 테이블명, 조건에 넣을 컬럼 선택은 모두 식별자라 어떤 ORM에서도 바인딩 대상이 아니다. 화면에서 정렬 기준을 고르게 하는 흔한 요구에서 "ORDER BY " + sortBy가 나오는 이유이고, 이 자리의 유일한 방어는 4절의 허용 목록이다. Criteria API처럼 쿼리를 객체로 조립하는 API를 쓰면 식별자조차 메타모델 속성으로 고르게 되어 사용자 문자열이 쿼리 텍스트에 닿는 지점 자체가 사라진다 — 4.1의 "불투명 키로 받고 서버가 번역한다"와 같은 발상이다.

Java 관점의 통찰: JVM의 타입 시스템은 String과 "SQL 골격"을 구분하지 않는다. 그래서 PreparedStatement의 API 형태 자체 — SQL은 생성 시 한 번 넘기고 값은 setString 같은 별도 메서드로만 넣는다 — 가 채널 분리를 강제하는 장치다. 정적 분석 도구가 "상수가 아닌 문자열이 쿼리 API로 들어간다"를 경고하는 것도 같은 이유이며, 쿼리 문자열이 리터럴이 아닌 순간이 곧 점검이 필요한 순간이다.

6.2 JS·TS — 자리표시자는 드라이버마다 다르고, 타입은 출처를 모른다

JS 생태계에는 표준 DB 인터페이스가 없어서 자리표시자 표기가 드라이버마다 다르다. PostgreSQL용 드라이버는 $1·$2처럼 위치를 지정하는 표기(같은 값을 두 번 쓰면 $1을 두 번 적는다)이고, MySQL용 드라이버는 ?를 등장 순서대로 값 배열에 대응시킨다. 후자에서는 같은 이름의 두 메서드가 다른 일을 하기도 한다 — 2020년대 중반 기준 대표 드라이버에서 execute()는 서버 측 prepare를, query()는 클라이언트 측 이스케이프 에뮬레이션을 수행한다(6.1의 구분이 메서드 이름에 나타난 셈이다).

더 자주 벌어지는 사고는 템플릿 리터럴 오용이다. 백틱 문자열 안의 ${name}은 JS 엔진이 먼저 평가해 완성된 문자열 하나를 만든다 — 드라이버는 이미 합쳐진 문자열을 받을 뿐이라 바인딩할 것이 남아 있지 않다. 반면 태그드 템플릿 리터럴(tagged template literal — 백틱 문자열 앞에 함수를 붙여, 엔진이 문자열을 합치는 대신 그 함수를 호출하게 하는 문법)은 태그 함수가 고정 문자열 조각 배열과 값 배열을 따로 받는다. 안전한 쿼리 라이브러리가 이 문법을 쓰는 이유는 바로 그 "따로"에 있다 — 조각은 골격이 되고 값은 자리표시자로 바뀐다. 겉모습은 한 글자(태그 유무)만 다르다. 

// 취약: 일반 템플릿 리터럴 — JS 엔진이 먼저 문자열을 완성해 드라이버에 넘긴다
await client.query(`SELECT * FROM users WHERE name = '${name}'`);

// 안전: 드라이버 자리표시자 — 골격과 값 배열을 따로 넘긴다
await client.query('SELECT * FROM users WHERE name = $1', [name]);   // 위치 지정($1)
await conn.execute('SELECT * FROM users WHERE name = ?', [name]);    // 순서 기반(?), 서버 측 prepare

// 안전: 태그드 템플릿 — 겉모습은 위의 취약 코드와 거의 같지만 동작이 다르다
await sql`SELECT * FROM users WHERE name = ${name}`;
// 엔진은 sql(["SELECT * FROM users WHERE name = ", ""], name) 으로 호출한다
// → 태그 함수가 조각을 골격으로, 값을 $1로 바꿔 바인딩

JS·TS만의 또 다른 표면은 문자열이 아니라 객체다. 요청 본문은 JSON을 파싱한 객체이고, 문서형 DB의 쿼리 역시 객체다. 값 자리에 문자열이 올 거라 가정하고 req.body.name을 그대로 넣으면, 공격자는 문자열 대신 {"$ne": ""} 같은 조건 객체를 보낼 수 있고 그것이 쿼리 구조로 그대로 앉는다. 따옴표도 이스케이프도 등장하지 않는 구조 주입이며, 바인딩할 문자열 경계가 애초에 없다는 점에서 4절의 검증 영역이다 — 상세는 S10 2절에서 다루므로 여기서는 방어의 방향만 적는다: 값 자리에는 문자열만 오도록 타입을 못 박거나 경계에서 런타임 스키마 검증으로 구조 전체를 거른다. 

// 구조 주입: req.body는 JSON을 파싱한 "객체"다 — 문자열이라 가정하면 뚫린다
//   보낸 본문 { "name": { "$ne": "" } }  → 조건 객체가 값 자리에 그대로 앉는다
users.findOne({ name: req.body.name });

// 방어: 값 자리에는 문자열만 — 런타임에서 타입을 못 박는다(TS 타입은 여기서 아무 일도 하지 않는다)
if (typeof req.body.name !== 'string') throw new Error('invalid input');
users.findOne({ name: req.body.name });

마지막 줄의 괄호가 TS의 핵심 함정이다. TS의 타입은 컴파일 시 지워지는 타입 소거(type erasure — 타입 검사 뒤 타입 정보를 결과 JS에서 모두 제거하는 방식) 대상이라, name: string이라고 선언해도 런타임의 req.body.name이 객체인 것을 막지 못한다. 마찬가지로 string 타입은 그 문자열이 상수 리터럴인지 사용자 입력인지를 구분하지 못한다. 구분하고 싶다면 브랜드 타입(branded type — 구조가 같은 값을 구별하려고 이름표 속성을 덧붙인 타입)으로 "검증을 통과한 문자열"을 별도 타입으로 만들어 쿼리 함수가 그 타입만 받게 하는 식으로, 출처를 타입 체계에 직접 새겨 넣어야 한다.

JS·TS 관점의 통찰: 이 언어에서 인젝션 방어는 "문자열을 어떻게 다루나"보다 "값이 어느 시점에 합쳐지나"의 문제다. 일반 템플릿 리터럴은 엔진 평가 시점에, 태그드 템플릿은 태그 함수 호출 시점에, 드라이버 자리표시자는 전송 시점에 합쳐진다 — 합치는 주체가 엔진이면 취약, 드라이버·라이브러리면 안전이다. 그리고 JSON과 객체의 경계가 없다는 편의성이 곧 구조 주입의 표면이므로, 경계에서의 런타임 검증은 선택이 아니라 타입 소거의 대가다.

6.3 Python — %s는 문자열 포맷이 아니다

Python에서 가장 흔한 승격 사고는 "자리표시자를 문자열 포맷으로 착각"하는 데서 온다. DB-API의 자리표시자는 우연히 %s로 생겼지만, 이것은 파이썬의 % 포맷과 전혀 다른 것이다 — 드라이버에게 "값을 별도 채널로 바인딩하라"는 지시다. 착각이 쉬운 데는 구조적 이유가 있다. DB-API는 라이브러리가 아니라 명세라서 자리표시자 표기가 드라이버마다 다르고(paramstyle 5종: qmark의 ?, numeric의 :1, named의 :name, format의 %s, pyformat의 %(name)s), 그중 두 종류가 하필 파이썬 포맷 문법과 같은 모양을 골랐다. 각 드라이버 모듈의 paramstyle 속성이 어느 표기를 쓰는지 알려 준다. 

name = request.args["name"]

# 취약: 파이썬이 먼저 문자열을 완성해 버림 → 값이 SQL 문법으로 승격
cur.execute("SELECT * FROM users WHERE name = '%s'" % name)
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")

# 안전: 드라이버에게 골격과 값을 따로 넘김 (따옴표도 드라이버가 처리)
cur.execute("SELECT * FROM users WHERE name = %s", (name,))              # format  (PostgreSQL·MySQL용 드라이버)
cur.execute("SELECT * FROM users WHERE name = ?", (name,))               # qmark   (sqlite3)
cur.execute("SELECT * FROM users WHERE name = :name", {"name": name})    # named
cur.execute("SELECT * FROM users WHERE name = %(name)s", {"name": name}) # pyformat
print(db_module.paramstyle)   # 이 드라이버가 쓰는 표기를 알려 주는 DB-API 속성

# 함정: 값을 튜플이 아닌 문자열로 넘기면, 문자열은 "문자들의 시퀀스"로 풀린다
cur.execute("SELECT * FROM users WHERE name = ?", name)   # 글자 수만큼 바인딩 시도 → 개수 불일치 오류

f-string은 이 착각을 한 단계 더 감춘다. f"… {name}"은 execute가 호출되기도 전에 인터프리터가 평가를 끝낸 보통 문자열이라, execute 입장에서는 값이 있었다는 사실조차 남지 않는다. 마지막 줄의 함정도 파이썬 객체 모델에서 온다 — 문자열은 시퀀스이므로 (name,) 대신 name을 넘기면 드라이버는 글자 하나하나를 파라미터로 세려 든다. 다행히 이 실수는 조용히 뚫리는 대신 개수 불일치 오류로 드러난다. 드라이버가 서버 측 prepare를 하는지 클라이언트 측 이스케이프를 하는지도 드라이버마다 다르다(2020년대 중반 기준 PostgreSQL용 최신 세대 드라이버는 서버 측 바인딩이 기본이고, 이전 세대는 클라이언트 측 치환이었다) — 어느 쪽이든 execute의 두 번째 인자로 넘기는 한 개발자 코드에서는 채널이 분리돼 있다.

Python 관점의 통찰: 두 줄은 겉보기에 %s로 똑같지만 의미가 정반대다. % 연산자·f-string은 "인터프리터가 지금 문자열을 합쳐라"이고, execute의 두 번째 인자로 넘기는 %s는 "드라이버가 나중에 바인딩하라"다. 콤마 하나(값을 두 번째 인자로 분리)가 코드 채널과 데이터 채널을 가르는 경계다 — 동적 언어라 타입이 이 경계를 대신 지켜 주지 않으므로, "쿼리 문자열에 사용자 값이 들어간 채 execute에 도달하는가"를 눈으로 보는 이 경계 감각이 곧 바인딩의 본질이다.

6.4 C++ — 채널 분리가 함수 시그니처로 드러나는 언어, 그리고 "나눌 수 없는" 자리들

C 계열에서도 답은 prepared statement다. 다만 이 언어에서는 채널 분리가 추상적 개념이 아니라 함수 시그니처에 그대로 보인다. libpq의 PQexecParams는 골격 텍스트와 값 포인터 배열(길이·형식 배열까지)을 별도 인자로 받고, MySQL C API의 mysql_stmt_bind_param은 값마다 버퍼 주소·타입·길이를 담은 구조체 배열을 받아 바이너리 프로토콜로 보낸다. 이 형태는 반대로 함정도 드러낸다 — 값을 snprintf로 골격에 찍어 넣는 것은 Python의 %s와 달리 진짜 문자열 포맷이므로 바인딩이 아니다. 시그니처가 "텍스트 하나"인 함수(PQexec, mysql_query)에 조립된 문자열을 넘기는 순간 채널은 닫힌다. 

// 취약: 진짜 포맷이다 — snprintf가 값을 골격에 찍어 넣어 문자열 하나로 만든다
snprintf(buf, sizeof buf, "SELECT * FROM users WHERE name = '%s'", name.c_str());
PQexec(conn, buf);

// 안전: 함수 시그니처 자체가 골격(텍스트)과 값(배열)을 분리한다
const char* params[] = { name.c_str() };
PGresult* r = PQexecParams(conn,
    "SELECT * FROM users WHERE name = $1",     // 골격: 상수 텍스트
    1, nullptr, params, nullptr, nullptr, 0);  // 값: 별도 배열(길이·형식은 뒤의 인자로)

메모리·수명 관점의 함정이 여기 덧붙는다. mysql_stmt_bind_param류 API는 값을 복사하지 않고 버퍼의 주소를 기억했다가 실행 시점에 읽는다. 바인딩 뒤 원본 std::string이 소멸하거나 재할당되면 실행 시점에 댕글링 포인터를 읽게 되고, 이는 인젝션이 아니라 정의되지 않은 동작으로 나타난다. 위 코드의 name.c_str()도 name이 호출이 끝날 때까지 살아 있어야 유효하다 — 임시 객체의 c_str()을 배열에 담아 두면 같은 문제가 생긴다. 채널을 나누는 것은 API가 해 주지만, 나뉜 데이터 채널의 수명은 개발자 몫이다.

그런데 인젝션 원리가 가장 선명하게 드러나는 곳은 셸 명령 조립이다 — 해석기만 DB에서 셸로 바뀔 뿐 구조가 같고, C++에서는 프로세스 실행 API가 손에 직접 잡히기 때문이다. 

// 취약: 입력이 "셸 언어"로 해석됨 — ;가 명령 구분자로 승격
std::string cmd = "ping -c 1 " + host;
system(cmd.c_str());                           // host = "8.8.8.8; <임의 명령>" 이면 두 번째 명령이 실행된다

// 안전: 인자 배열로 넘겨 셸 해석 자체를 생략 (execvp 계열)
//        명령(코드)과 인자(데이터)가 배열 원소로 분리 → 문법 해석 통로가 없다
const char* argv[] = { "ping", "-c", "1", host.c_str(), nullptr };
execvp(argv[0], const_cast<char* const*>(argv));   // 같은 host 값은 그저 '이상한 호스트명' 하나

컴파일 타임 관점에서 C++이 줄 수 있는 것도 있다. 쿼리 골격을 받는 함수의 매개변수를 문자열 리터럴 참조(const char (&)[N])나 C++20의 consteval 검사로 제한하면, 런타임에 조립된 std::string은 컴파일 단계에서 거부된다 — 6.1에서 정적 분석 도구가 경고하던 "상수가 아닌 쿼리 문자열"을 타입 시스템이 직접 막는 셈이다. 물론 이것은 골격 자리에만 통하며, 정렬 컬럼처럼 사용자가 골라야 하는 식별자는 여전히 허용 목록으로 좁혀야 한다.

C++ 관점의 통찰: S1 6.4가 포맷 문자열에서 보인 "코드 채널/데이터 채널 분리"가 여기서는 DB 바인딩과 execvp 인자 배열로 나타난다. 단, 분리의 결과가 다시 문자열 하나로 합쳐져 해석기에 들어가면(snprintf로 만든 쿼리, 조립된 셸 명령) 그 분리는 무효다 — 합쳐지는 시점이 해석기 앞이냐 뒤냐가 전부다. 반대로, 나눌 채널이 없는 자리 — 정렬 컬럼 이름, 리다이렉트 목적지 URL — 에서는 분리가 불가능하므로 허용 목록으로 값을 좁힌다. "나눌 수 있으면 바인딩, 없으면 allowlist"가 인젝션 방어 전체를 관통하는 판단 규칙이다.

7. 함께 알면 좋은 것

  • 인젝션의 형제들 — 명령 인젝션·LDAP·XPath·NoSQL 인젝션은 해석기만 다른 같은 병. 각 해석기의 "바인딩"에 해당하는 안전 API를 찾는 것이 방어의 출발점이다. → S10에서 정면으로 다룬다.
  • 안전한 역직렬화 — 신뢰할 수 없는 바이트를 객체로 되살리면 "데이터가 객체·코드로 승격"되는 또 다른 인젝션이 된다. C10에서 다루는 스키마·포맷 통제가 이 방어의 토대다.
  • 최소 권한 원칙 — DB 계정이 애초에 DROP·다른 스키마 접근 권한이 없다면, 바인딩이 뚫려도 피해 범위가 줄어든다(심층 방어).
  • 저장 프로시저의 오해 — 프로시저를 쓴다고 자동으로 안전하지 않다. 프로시저 내부에서 동적 SQL을 조립하면 같은 취약점이 그대로 재현된다.
  • 오류 메시지 노출 관리 — DB 오류를 그대로 화면에 내보내면 공격자에게 스키마 힌트를 준다. 사용자에겐 일반화된 메시지, 상세는 서버 로그로.

8. 한 장 요약

  • 인젝션 = 사용자 유래 문자열이 해석기에게 코드로 승격되는 것. SQL 인젝션은 그 해석기가 DB인 경우 — XSS(S1)와 같은 병이다. 진원지는 문자열 이어붙이기 — 취약한 것은 입력 길이가 아니라 조립 방식이다.
  • 1차 방어는 파라미터 바인딩 — 쿼리 골격(코드)과 값(데이터)을 별도 채널로 분리한다. 수동 이스케이프는 실패 장르.
  • 2차 방어는 입력 검증 — 바인딩과 역할이 다르다. 값 자체가 결정인 자리(정렬 컬럼, 오픈 리다이렉트 목적지)에선 검증, 특히 허용 목록이 유일한 방어다.
  • 오픈 리다이렉트 방어: 스킴 허용 목록 + 자기 참조만 허용 + 가급적 불투명 키→서버 번역. 순진한 시작 문자열 비교는 우회된다.
  • ORM·저장 프로시저도 값이 바인딩 채널로 가는지가 기준. 최종 책임은 서버.
  • 관통하는 규칙: 나눌 수 있으면 바인딩, 나눌 수 없으면 허용 목록 — 코드 채널과 데이터 채널의 분리.

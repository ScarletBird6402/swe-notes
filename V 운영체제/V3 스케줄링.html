V3 스케줄링

0. 한눈에 보는 결론

  • V1이 컨텍스트 스위치의 "어떻게"와 "비용"을 다뤘다면, 스케줄링은 "언제, 누구로 갈아탈 것인가"의 결정 규칙이다.
  • 스케줄러의 목표 — 처리량·응답성·공정성 — 는 서로 당긴다. 모든 스케줄링 설계는 이 삼각형 안 어딘가에 점을 찍는 일이다.
  • 선점(preemption)은 "실행 중인 흐름의 CPU를 강제로 회수할 수 있는가"다. 현대 범용 OS는 타이머 인터럽트 기반 선점형 — 폭주한 코드 한 줄이 시스템을 인질로 잡지 못하는 이유다.
  • 우선순위는 "회수한 CPU를 누구에게 줄 것인가"의 답이지만, 응용 코드가 지정하는 우선순위는 대부분 명령이 아니라 힌트다.
  • 우선순위의 그림자가 기아(starvation) — 뒷줄이 영원히 차례를 못 받는 상태다. 오래 기다린 흐름의 순위를 올려 주는 에이징(aging)이 표준 처방이다.
  • 스케줄러는 대기가 많은 흐름을 우대한다 — "I/O 중심 작업은 스레드를 늘려도 된다"(V1)는 관용구가 성립하는 또 하나의 이유다.

1. 스케줄러의 문제 — 코어보다 흐름이 많다

V1은 "코어 수보다 많은 스레드가 동시에 도는 것처럼 보이는 이유는 운영체제가 짧은 간격으로 흐름을 갈아태우기 때문"이라고 했고, 갈아타는 행위(컨텍스트 스위치)의 비용을 계산했다. 남겨 둔 질문이 이 문서의 전부다: 그 갈아타기를 언제 하고, 다음 주자를 누구로 뽑는가.

결정의 대상부터 정리하자. 스레드는 세 상태를 오간다 — CPU에서 도는 실행, CPU만 나면 당장 뛸 수 있는 준비(ready), I/O 완료·락 해제 등 사건을 기다리느라 CPU를 줘도 못 뛰는 대기(blocked). 스케줄러가 고르는 것은 준비 큐에 서 있는 흐름들이다 — 대기 중인 흐름은 후보조차 아니라는 것, 이것이 이 문서 전체에서 반복될 사실이다.

디스패치(선발) ──▶ [ 준비 ] ◀────────────── [ 실행 ] ▲ 선점·시간 소진 │ │ │ I/O 요청·락 대기 └────── [ 대기 ] ◀─────────┘ 사건 발생(I/O 완료 등)

그렇다면 "잘 고른다"는 것은 무엇인가. 좋은 스케줄링의 기준이 하나가 아니라는 데서 모든 복잡성이 나온다.

  • 처리량: 단위 시간에 끝내는 일의 총량. 스위치를 줄이고 각 흐름을 오래 돌릴수록 유리하다(스위치는 순수 오버헤드이므로 — V1).
  • 응답성: 사건이 난 뒤 반응까지의 지연. 스위치를 자주 해서 모두에게 빨리 차례를 돌릴수록 유리하다.
  • 공정성: 어떤 흐름도 부당하게 굶지 않을 것.

처리량과 응답성이 정면으로 충돌함을 주목하라 — 하나는 "덜 갈아타라", 하나는 "자주 갈아타라"고 말한다. 따라서 스케줄러는 절충의 기계이고, 절충의 첫 번째 손잡이는 갈아타는 시점을 누가 정하는가이다.

2. 선점 — 언제 빼앗는가

실행 중인 흐름이 스스로 CPU를 내놓을 때까지 기다리는 방식이 비선점(협력형)이고, 운영체제가 강제로 회수할 수 있는 방식이 선점형이다. 협력형은 스위치 시점을 흐름 자신이 알므로 단순하고 오버헤드가 적지만, 치명적 약점이 있다 — 양보하지 않는 흐름 하나가 시스템 전체를 인질로 잡는다. 무한 루프 한 줄이면 끝이다. 그래서 현대 범용 OS는 모두 선점형이다.

선점의 구현이 타이머 인터럽트다. 하드웨어 타이머가 주기적으로 CPU를 커널로 강제 진입시키고, 커널은 그때마다 "지금 흐름을 계속 돌릴 것인가"를 판단한다. 각 흐름에게 연속으로 허용되는 실행 시간이 타임 슬라이스(time slice)이며, 이 길이가 §1 삼각형의 다이얼이다: 짧게 잡으면 응답성이 좋아지는 대신 스위치 비용(캐시·TLB 식힘 포함 — V1)의 비중이 커지고, 길게 잡으면 그 반대다.

선점은 흐름 입장에서 아무 두 명령 사이에서나 일어날 수 있다. V1에서 "++count 한 줄도 기계 수준에서는 세 단계"라며 경쟁 조건을 경고했는데, 그 겹침을 실제로 만들어 내는 장본인이 바로 선점이다 — 스레드 안전성(G1)이 "언젠가"가 아니라 "언제든"의 문제인 이유가 스케줄러에 있다.

타이머가 울렸고 커널이 "바꾸자"고 결정했다고 하자. 준비 큐에 후보가 여럿이라면 — 다음 질문은 자연히 누구를 뽑는가가 된다.

3. 우선순위 — 누구에게 주는가

가장 단순한 답은 도착 순서대로(FIFO)지만, 이는 삼각형의 응답성 꼭짓점을 포기하는 답이다 — 긴 계산 작업 하나가 앞에 서면 0.1초짜리 응답 작업이 그 전체를 기다린다. 그래서 실용 스케줄러는 흐름마다 우선순위를 매기고 높은 쪽을 먼저 뽑는다. 문제는 순위를 무엇으로 매기느냐다.

사용자가 지정하는 정적 순위(유닉스 계열의 nice 값 등)도 있지만, 현대 스케줄러의 핵심은 행동 관찰에 기반한 동적 조정이다. 대표 규칙 하나가 스케줄링의 절반을 설명한다: 자주 대기에 들어가는(I/O 중심) 흐름을 우대하고, 슬라이스를 꽉 채워 쓰는(CPU 중심) 흐름은 뒤로 보낸다.

왜 이것이 합리적인가. I/O 중심 흐름은 CPU를 줘도 금방 다시 대기로 빠진다 — 잠깐 쓰고 비켜 주므로 우대해도 처리량 손해가 거의 없고, 그 짧은 실행이 사용자 응답이나 다음 I/O의 발주로 이어지므로 응답성 이득은 크다. 대기하는 동안 코어는 어차피 CPU 중심 흐름들이 쓴다. V1의 "스레드 증설이 유효한 것은 대기 중심 작업"이라는 결론이 여기서 한 번 더 보강된다: 대기 중심 흐름은 코어를 오래 점유하지 않을 뿐 아니라, 스케줄러가 구조적으로 편애하는 대상이다.

이 규칙은 자동 분류기이기도 하다 — 개발자가 "이건 I/O 작업"이라고 신고하지 않아도, 스케줄러는 슬라이스 소진 이력만 보고 흐름의 성격을 추정해 낸다. "관찰된 행동이 선언보다 정직하다"는 설계 원칙의 고전적 사례다.

그러나 우선순위는 본질적으로 누군가를 뒤로 미루는 장치다. 미룸이 반복되면 어떻게 되는가 — 우선순위의 그림자가 다음 절이다.

4. 기아와 역전 — 우선순위의 그림자

높은 순위의 흐름이 끊이지 않으면 낮은 순위의 흐름은 준비 큐에서 영원히 뽑히지 않을 수 있다 — 기아다. 드물게만 도는 낮은 순위 작업(통계 집계, 정리 배치 등)이 부하가 높은 날에만 조용히 밀려 안 돈다면, 그것은 버그처럼 보이지 않는 기아다. 표준 처방은 에이징: 기다린 시간에 비례해 순위를 점진적으로 올려, 어떤 흐름이든 언젠가는 최상위에 도달해 반드시 실행되게 한다. 공정성 꼭짓점을 규칙으로 보증하는 장치다.

더 교묘한 그림자가 우선순위 역전(priority inversion)이다 — 낮은 순위 흐름이 락을 쥔 채 밀려나 있으면, 그 락을 기다리는 높은 순위 흐름도 함께 멈춘다. 사실상 높은 순위가 낮은 순위 아래로 뒤집힌 것이다. 심지어 중간 순위의 무관한 흐름들이 낮은 순위 흐름을 계속 밀어내면, 최고 순위 흐름이 무기한 굶는다. 처방은 우선순위 상속: 락 보유자를 대기자 중 최고 순위로 임시 승격시켜 빨리 일을 끝내고 락을 놓게 한다.

역전이 주는 교훈은 우선순위보다 크다 — 스케줄러가 보는 의존성(준비 큐의 순위)과 실제 의존성(누가 누구의 락을 기다리는가)이 서로 다른 그래프라는 것. 동기화가 끼는 순간 "순위를 높였으니 먼저 돌겠지"는 보장이 아니라 희망이 된다. 우선순위로 동기화 문제를 풀려는 시도(순위를 올려 경쟁을 "이기게" 하기)가 안티패턴인 이유다.

이제 규칙의 전모가 보인다 — 선점이 "언제"를, 우선순위가 "누구"를 정하고, 에이징·상속이 그 부작용을 상쇄한다. 이 구조를 코드 쪽에서 바라보면, 널리 퍼진 관용구 몇 개가 사실과 다르게 이해되고 있음이 드러난다.

5. 흔히 헷갈리는 지점

  • 우선순위 ≠ 속도. 우선순위는 경합이 있을 때 뽑히는 순서일 뿐, 실행 자체를 빠르게 하지 않는다. 코어가 남는 시스템에서는 순위를 아무리 올려도 아무것도 달라지지 않는다.
  • 양보(yield)는 계약이 아니다. "CPU를 양보한다"는 호출은 스케줄러에 대한 제안일 뿐이며, 준비 큐에 더 높은(또는 동순위) 후보가 없으면 즉시 자신이 다시 뽑힌다. 양보를 동기화 수단(상대가 먼저 돌기를 기대)으로 쓰는 코드는 타이밍 운에 기대는 코드다.
  • 잠들기(sleep)와 대기의 구분. 잠들기·I/O 대기 중인 흐름은 준비 큐에 없다 — CPU를 "적게 쓰는" 게 아니라 후보에서 빠져 있는 것이다. 반대로 락을 스핀(반복 확인)으로 기다리는 흐름은 대기처럼 보여도 스케줄러에게는 왕성한 CPU 중심 흐름이다 — 우대는커녕 감점된다(§3).
  • CPU 100%가 곧 과부하는 아니다. 계산 작업이 코어를 꽉 채워 쓰는 것은 정상이다. 위험 신호는 사용률이 아니라 준비 큐의 길이(뛸 수 있는데 못 뛰는 흐름 수 — 부하 평균이 대변)가 코어 수를 지속적으로 크게 넘는 상태다.
  • 단일 스레드 환경에도 스케줄링 문제는 있다. 이벤트 루프는 협력형 스케줄러와 구조가 같다 — 콜백 하나가 오래 돌면 §2의 "인질" 문제가 그대로 재현된다(뒤에서 다시 본다).

6.1 Python — 스케줄러가 둘인 언어

Python 스레드는 OS 스레드이므로 일차로 OS 스케줄러의 지배를 받는다. 그런데 실행되려면 GIL(V1 — 바이트코드를 실행하는 스레드는 한 순간에 하나라는 인터프리터 수준의 락)까지 쥐어야 하므로, 사실상 두 번째 스케줄링이 인터프리터 층에서 벌어진다: 실행 중인 스레드는 일정 간격마다 GIL을 내려놓아 다른 스레드에게 기회를 주고, 누가 다음에 GIL을 쥐는가는 OS가 누구를 깨우느냐에 달린다. 

import sys

print(sys.getswitchinterval())   # 기본 0.005 — GIL 자발 반납 간격(초)

# 간격을 늘리면: 스위치 오버헤드 감소, 스레드 간 응답성 저하
# 간격을 줄이면: 반대 — 이 다이얼이 §2 타임 슬라이스와 같은 트레이드오프다
sys.setswitchinterval(0.01)

Python 관점의 통찰: OS 스케줄러가 스레드 A를 코어에 올려도 GIL을 B가 쥐고 있으면 A는 곧장 다시 잔다 — OS의 결정이 인터프리터 층에서 거부권을 맞는 구조다. 이 이중 구조 때문에 Python 멀티스레드의 성능 직관은 OS 지식만으로도, Python 지식만으로도 완성되지 않는다. 계산 스레드가 하나라도 섞이면 I/O 스레드들의 응답까지 출렁이는 현상(계산 스레드가 GIL을 오래, 자주 재획득)이 대표적인 이중 구조의 증상이다.

6.2 C++ — 다이얼이 전부 노출된 언어

std::thread는 표준 API로는 양보와 잠들기 정도만 주지만, 네이티브 핸들을 통해 OS의 다이얼 전부 — 스케줄링 정책, 실시간 순위, 특정 코어 고정(친화도) — 에 손이 닿는다. 지연 요동을 통제해야 하는 도메인이 C++에 머무는 이유 중 하나다. 

#include <thread>
#include <atomic>
using namespace std::chrono_literals;

std::atomic<bool> ready{false};

void spin_wait()  { while (!ready) { }                          }  // 준비 큐 상주 — CPU 중심으로 '감점'(§3·§5)
void yield_wait() { while (!ready) std::this_thread::yield();   }  // 제안일 뿐 — 경합 없으면 스핀과 대동소이
void sleep_wait() { while (!ready) std::this_thread::sleep_for(1ms); }  // 대기로 이탈 — 지연 1ms를 내고 CPU를 산다

C++ 관점의 통찰: 세 대기법의 차이는 문법이 아니라 스케줄러 관점의 신분이다 — 스핀은 실행/준비를 오가는 왕성한 후보, 잠들기는 후보 명단에서의 이탈. 스핀이 정당한 경우는 "기다림이 스위치 비용(마이크로초)보다 짧다고 확신할 때"뿐이고, 그 확신이 틀리면 코어 하나를 통째로 태우며 동료 스레드의 순위까지 깎는다(슬라이스를 꽉 쓰는 흐름으로 분류되므로). 제어권이 전부 노출된 언어에서는 "무엇을 할 수 있는가"보다 "스케줄러에게 어떻게 보이는가"를 아는 것이 실력이다.

6.3 Java / JS·TS — 한 줄 요약

Java는 순위 힌트가 플랫폼마다 다르게(또는 무시되어) 번역되는 경험을 거치며 "스케줄링은 OS에 맡기고 애플리케이션은 스레드 풀·큐로 제어한다"는 문화로 수렴했고, 최근의 가상 스레드는 그 위에 JVM 자체 스케줄러를 얹어 Python과는 다른 이유로 "스케줄러 두 층" 구조가 됐다. JS·TS의 이벤트 루프는 §2의 협력형 그 자체라서 — 선점이 없으므로 — 긴 계산 하나가 모든 콜백의 응답성을 인질로 잡으며, "작업을 잘게 쪼개 루프에 자주 돌려준다"는 규율이 이 언어의 타임 슬라이스 역할을 한다.

7. 함께 알면 좋은 것

  • 부하 평균(load average) — 준비 큐 길이의 시간 평균(리눅스는 특정 대기 상태 포함). "코어 수 대비 몇 배인가"로 읽는 §5의 실전 지표.
  • 코어 친화도(CPU affinity) — 흐름을 특정 코어에 고정해 캐시가 식는 것(V1)을 막는 기법. 스케줄러의 이주 자유와 캐시 온기의 맞바꿈.
  • 컨테이너 CPU 제한과 스로틀링 — cgroup은 컨테이너의 CPU 시간을 주기당 할당량으로 제한하며, 소진 시 다음 주기까지 전 스레드가 강제 정지된다. "코어가 놀아도 내 서비스 지연이 튀는" 현상의 흔한 원인.
  • 사용자 수준 스케줄링 — 고루틴·가상 스레드·코루틴 등 런타임이 소수의 OS 스레드 위에 다수의 경량 흐름을 직접 배치하는 구조. "OS 스레드는 비싸다"(V1)에 대한 응답이자, 이 문서의 규칙이 런타임 안에서 한 번 더 반복되는 재귀.
  • 실시간 스케줄링 — "평균이 아니라 마감(deadline)을 보증하라"는 다른 목표 함수의 세계. 범용 OS의 공정성 장치를 우회하므로 오용 시 시스템 전체를 굶길 수 있다.

8. 한 장 요약

  • 스케줄링 = 준비 큐에서 다음 실행 흐름을 고르는 규칙. 처리량(덜 갈아타기)과 응답성(자주 갈아타기)의 절충이 모든 설계의 축이다.
  • 선점은 타이머 인터럽트로 CPU를 강제 회수하는 것 — 폭주 코드로부터 시스템을 지키고, 동시에 경쟁 조건이 "언제든" 터질 수 있게 만드는 장본인이다.
  • 우선순위의 핵심은 동적 조정: 대기 많은 흐름 우대, 슬라이스 소진 흐름 감점 — 선언이 아니라 행동을 본다.
  • 기아는 에이징으로, 우선순위 역전은 상속으로 상쇄한다 — 우선순위로 동기화를 이기려는 설계는 안티패턴이다.
  • 응용에서 순위·양보는 힌트일 뿐이다. 실전 제어 수단은 풀 크기·큐·작업 쪼개기 쪽에 있다.
  • 언어별 관전 포인트: Java(위임+풀 문화), JS(협력형 루프 — 쪼개기가 슬라이스), Python(OS+GIL 이중 스케줄), C++(다이얼 전부 노출 — 스핀의 유혹과 대가).

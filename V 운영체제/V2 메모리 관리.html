V2 메모리 관리

0. 한눈에 보는 결론

  • 가상 메모리(virtual memory)는 "각 프로세스가 0번지부터 시작하는 자기만의 연속 메모리를 본다"는 환상이다 — V1의 격리는 이 환상 위에 서 있다.
  • 환상의 구현은 쪼개기다: 주소 공간을 고정 크기 페이지로 나누고, 페이지마다 "실제로는 어디"를 페이지 테이블에 적는다. 연속으로 보이는 것과 연속으로 있는 것은 별개다.
  • 매 접근마다 테이블을 뒤지면 메모리가 배로 느려진다 — 변환 결과를 담아 두는 캐시 TLB가 이 비용을 감춘다. V1에서 "컨텍스트 스위치 때 TLB가 식는다"고 한 그 TLB다.
  • 페이지 폴트(page fault)는 에러가 아니라 정상 동작 기제다 — "아직 안 올라온 페이지"를 그때 가져오는 요구 페이징이 이 폴트 위에 구현된다.
  • 물리 메모리가 부족하면 덜 쓰는 페이지를 디스크로 내리는 것이 스와핑(swapping) — 환상은 유지되지만 속도가 새기 시작하고, 심하면 스래싱으로 무너진다.
  • 도구가 보여주는 메모리 수치(가상 크기 vs 상주 크기)는 이 구조를 알아야 읽힌다 — "메모리를 잡았다"와 "메모리를 쓰고 있다"는 다른 말이다.

1. 왜 물리 주소를 직접 쓰지 않는가

V1은 "프로세스마다 자기만의 주소 공간이 있고, 가상→물리 변환은 운영체제와 하드웨어가 한다"는 결과만 두고 넘어왔다. 이 문서는 그 유보를 회수한다 — 왜 이런 우회가 필요하고, 어떻게 구현되며, 어디서 비용이 새는가.

프로그램이 물리 주소를 직접 쓴다고 가정해 보면 세 가지가 즉시 무너진다.

  • 배치: 컴파일 시점엔 프로그램이 물리 메모리 어디에 올라갈지 모른다. 두 프로그램이 같은 번지를 쓰도록 컴파일되어 있으면 동시에 못 띄운다.
  • 보호: 어떤 프로세스든 아무 물리 번지나 만질 수 있다면, V1의 격리 — "잘못된 포인터의 피해는 자기 세계 안에서 끝난다" — 는 성립할 수 없다.
  • 용량: 물리 메모리보다 큰 프로그램은 아예 실행할 수 없고, 프로세스 여럿의 합이 물리 메모리를 넘어도 안 된다.

가상 메모리는 세 문제를 한 번에 푸는 답이다: 모든 프로세스에게 "너는 0번지부터 시작하는 넉넉한 연속 공간을 혼자 쓴다"는 환상을 주고, 실제 물리 배치는 운영체제가 뒤에서 관리한다. 그렇다면 다음 질문은 구현이다 — 이 환상을 무슨 수로 만드는가? 프로세스의 공간 전체를 물리 메모리의 연속 구간에 통째로 대응시키는 방법은 금방 막힌다(빈 구간 크기가 제각각이라 틈이 남는 외부 단편화, 공간 확장의 어려움). 현대 운영체제의 답은 연속이라는 가정 자체를 버리고 잘게 쪼개는 것이다.

2. 페이징 — 쪼개서 흩어 놓고, 표로 잇는다

페이징(paging)은 가상 주소 공간을 고정 크기 조각(페이지, 통상 4KB)으로, 물리 메모리를 같은 크기 조각(프레임)으로 나눈다. 가상 페이지는 물리 프레임 어디에든 들어갈 수 있고, "가상 페이지 몇 번 → 물리 프레임 몇 번"의 대응을 프로세스마다 페이지 테이블에 기록한다.

가상 주소 = [ 페이지 번호 | 페이지 안 오프셋 ] │ ▼ 페이지 테이블 (프로세스마다 하나) 페이지 번호 → 프레임 번호 (+ 권한 비트 R/W/X, 존재 비트) │ ▼ 물리 주소 = [ 프레임 번호 | 오프셋 그대로 ]

이 한 장의 표가 앞 절의 세 문제를 모두 해소한다. 배치 — 어느 프레임이 비었든 거기 넣고 표만 고치면 되니 연속 구간을 찾을 필요가 없다. 보호 — 변환은 반드시 자기 테이블을 거치므로, 테이블에 없는 메모리는 주소를 만들어 낼 방법 자체가 없다. V1의 격리가 바로 이 문장의 귀결이다. 표 항목마다 붙는 권한 비트는 "읽기 전용 페이지에 쓰기", "데이터 페이지를 실행" 같은 시도를 하드웨어 수준에서 차단한다. 용량 — 표의 항목이 반드시 물리 프레임을 가리킬 필요가 없다는 점에서 풀리는데, 이것이 §4의 주제다.

페이지 테이블 자체도 메모리를 먹는다. 64비트의 광대한 주소 공간을 한 장의 평면 표로 만들면 표가 기가바이트급이 되므로, 실제로는 표를 다단계 트리로 만들어 "실제로 쓰는 구간"의 표만 존재하게 한다. 구조는 달라져도 원리는 같다 — 번호를 키로 프레임을 찾는 사전.

그런데 이 설계에는 치명적으로 보이는 비용이 숨어 있다. 모든 메모리 접근이 "테이블을 읽고(메모리 접근) → 진짜 데이터를 읽는(또 메모리 접근)" 두 번 일이 된다 — 다단계 표라면 단계 수만큼 더. 환상을 유지하는 대가로 메모리가 몇 배 느려진다면 아무도 쓰지 않았을 것이다. 이 비용을 감추는 장치가 다음 절이다.

3. TLB — 변환 비용을 감추는 캐시

TLB(translation lookaside buffer)는 최근에 수행한 "페이지 번호 → 프레임 번호" 변환 결과를 담아 두는 하드웨어 캐시다 — 한 줄로: 주소 번역 결과의 캐시. 프로그램의 메모리 접근은 좁은 구간에 몰리는 경향(지역성)이 있어, 수십~수천 항목의 작은 TLB로도 대부분의 접근이 표를 거치지 않고 즉시 변환된다. TLB에 있으면 변환 비용은 사실상 0, 없으면(TLB 미스) 그때만 테이블을 걷는다.

여기서 V1의 문장 하나가 완성된다. "프로세스 간 스위치는 스레드 간 스위치보다 무겁다 — 주소 공간이 바뀌므로 TLB가 통째로 무효화되기 때문"이라고 했다. 이제 이유가 보인다: TLB의 항목은 지금 테이블 기준의 변환 결과인데, 프로세스가 바뀌면 테이블이 바뀌므로 모든 항목이 무효가 된다. 새 프로세스는 접근마다 TLB 미스를 내며 식은 상태로 출발한다. 같은 프로세스의 스레드끼리는 테이블이 같으니 이 비용이 없다 — "스레드는 갈아타기도 가볍다"의 하드웨어적 근거다.

TLB까지 놓으면 변환은 빠르다. 그런데 지금까지는 표 항목이 항상 유효한 프레임을 가리킨다고 가정했다. 표에 "이 페이지는 지금 물리 메모리에 없음"이라고 적혀 있다면 무슨 일이 벌어지는가 — 여기서 이 구조의 가장 흥미로운 반전이 나온다.

4. 페이지 폴트와 요구 페이징 — "없음"이 기능이 되는 곳

존재 비트가 꺼진 페이지에 접근하면 하드웨어는 실행을 중단하고 운영체제를 호출한다. 이것이 페이지 폴트다. 이름에 fault가 들어 있지만 대부분의 페이지 폴트는 에러가 아니라 정상 절차다 — 운영체제가 "그 페이지를 이제 준비하겠다"고 개입하는 훅(hook)이며, 준비가 끝나면 중단됐던 명령이 아무 일 없었다는 듯 재실행된다. 응용 프로그램은 폴트가 났는지조차 모른다.

이 기제 위에 요구 페이징(demand paging)이 선다: 프로그램을 실행할 때 전체를 미리 올리지 않고, 페이지를 실제로 건드리는 순간에 올린다. 실행 파일의 코드도, malloc으로 잡은 큰 버퍼도 처음에는 표에 "아직 없음"으로만 기록되고, 첫 접근의 폴트가 실제 적재를 일으킨다. 거대한 프로그램이 순식간에 뜨는 이유, "메모리를 할당받았다"와 "물리 메모리를 점유한다"가 다른 말인 이유가 여기 있다.

같은 기제의 응용이 쓰기 시 복사(copy-on-write)다. 프로세스를 복제할 때 메모리를 실제로 복사하지 않고 두 프로세스의 표가 같은 프레임을 읽기 전용으로 가리키게 한 뒤, 어느 쪽이든 쓰려는 순간의 폴트에서만 그 페이지를 복사한다. "일단 없다고/안 된다고 해 두고, 폴트가 나면 그때 진짜 일을 한다"는 패턴 — 가상 메모리의 여러 최적화가 이 한 패턴의 변주다.

요구 페이징의 전제는 "필요하면 그때 가져올 수 있다"는 것이다. 그런데 가져오려는 순간 빈 프레임이 하나도 없다면? 누군가를 내보내야 자리가 난다 — 환상이 물리 메모리의 크기와 정면으로 부딪히는 지점이다.

5. 스와핑 — 환상이 새는 곳

물리 메모리가 부족하면 운영체제는 덜 쓰이는 페이지를 골라 디스크의 스왑 영역으로 내리고(존재 비트를 끄고), 그 프레임을 새 페이지에 준다. 내려간 페이지를 다시 건드리면 페이지 폴트 → 디스크에서 다시 올라온다. 표 덕분에 환상은 완벽히 유지된다 — 프로그램은 자기 페이지가 디스크를 다녀왔는지 알 수 없다. 다만 하나만 샌다: 시간. 메모리 접근이 나노초에서 디스크 왕복의 밀리초로, 자릿수 여러 개가 튄다.

어느 페이지를 내보낼 것인가가 교체 정책이다. 이상적 답 "앞으로 가장 오래 안 쓸 페이지"는 미래를 알아야 하므로, 실제로는 "최근에 안 쓴 페이지는 앞으로도 안 쓸 것"이라는 근사(LRU 계열)를 쓴다 — 지역성이라는 같은 가정이 TLB에서는 적중률을, 여기서는 교체 정책을 떠받친다.

스래싱(thrashing) — 환상이 무너지는 임계점. 활발히 쓰는 페이지들의 합이 물리 메모리를 넘어서면, 페이지를 올리기 위해 방금 쓰던 페이지를 내리고, 그 페이지가 곧바로 다시 폴트를 낸다. 시스템은 디스크 왕복만 반복하며 실제 일은 거의 못 한다. CPU 사용률은 낮은데 시스템이 마비되어 있다면 스래싱을 의심하라 — CPU가 노는 이유가 "일이 없어서"가 아니라 "모두가 디스크를 기다려서"다. 점진적으로 느려지는 게 아니라 임계점을 넘는 순간 절벽처럼 무너진다는 것이 이 현상의 특징이다.

스왑을 어떤 저장 매체에 두는가, 매체별 특성이 이 비용을 얼마나 바꾸는가는 저장 계층 설계의 주제이므로 여기서는 넘어간다 — 계층 배치 판단은 W4에서 다룬다. 개념 수준에서 기억할 것은 하나다: 스와핑은 "메모리가 모자라도 죽지 않게" 해 주는 완충이지 성능 장치가 아니며, 완충마저 소진되면 운영체제는 프로세스를 강제 종료하는 최후 수단(리눅스의 OOM killer가 대표 예)까지 간다.

여기까지가 기제의 전부다 — 쪼개고(페이징), 캐시하고(TLB), 미루고(요구 페이징), 넘치면 내린다(스와핑). 이제 이 구조를 알아야만 바르게 읽히는 숫자와 관용구들을 점검하자.

6. 흔히 헷갈리는 지점

  • 가상 크기(VSZ) vs 상주 집합 크기(resident set size, RSS). 가상 크기는 표에 등록된 공간의 총합(약속), 상주 크기는 지금 물리 프레임을 점유한 양(현실)이다. 요구 페이징 때문에 가상 크기는 상주 크기보다 훨씬 클 수 있고, 그 자체는 전혀 문제가 아니다. "프로세스가 메모리를 얼마나 쓰나"의 답에 가까운 것은 상주 크기 쪽이다.
  • "할당 성공 = 메모리 확보"가 아니다. 요구 페이징 하에서 할당은 표에 약속을 적는 일이고, 물리 프레임은 첫 접근 때 확보된다. 약속의 합이 물리 용량을 넘도록 허용하는 시스템(과약정, overcommit)에서는 할당이 성공하고도 한참 뒤 접근 시점에 메모리 부족이 터질 수 있다.
  • "메모리가 꽉 찼다"는 착시. 운영체제는 남는 메모리를 파일 캐시로 채워 둔다(안 쓰는 메모리는 낭비이므로). 전체 사용량이 높아 보여도 캐시 몫은 압박이 오면 즉시 회수되는 여유분이다 — "사용 중"과 "회수 불가"를 구분해서 읽어야 한다.
  • 페이지 폴트 카운트가 높다 ≠ 장애. 폴트에는 디스크를 안 가는 가벼운 폴트(minor — 이미 메모리에 있는 프레임을 표에 잇기만)와 디스크를 다녀오는 무거운 폴트(major)가 있다. 성능 신호로 봐야 할 것은 major 쪽이며, minor는 정상 동작의 소음에 가깝다.
  • "스왑을 쓰고 있다 = 위험"이 아니다. 오래 안 쓴 페이지가 스왑에 내려가 있는 것은 건강한 상태일 수 있다. 위험 신호는 스왑의 존재량이 아니라 스왑 입출력이 지속적으로 발생하는 것(스래싱의 전조)이다.

★ 7. 언어별 대조

지금까지는 운영체제의 층이었다. 그런데 응용 코드와 운영체제 사이에는 한 층이 더 있다 — 언어 런타임은 운영체제에서 큰 구간을 받아 두고 그 안에서 자기 방식으로 힙을 관리한다. "내 코드의 메모리"가 실제로 어떻게 잡히고 언제 반납되는지가 언어마다 다른 이유다.

언어힙 관리 주체반납의 실제이 문서와의 접점
JavaJVM — 시작 시 힙 구간 예약(-Xmx 상한), GC가 내부 관리객체 해제 ≠ OS 반납. JVM이 힙을 쥐고 재사용가상 크기는 예약분, 상주는 실사용분 — 둘의 괴리가 표준 상태
JS·TSV8 등 엔진 — 자체 힙 + GC, 기본 힙 상한 존재엔진 내부 재사용 중심힙 상한 초과는 OS가 아니라 엔진이 먼저 끊는다
Python인터프리터 — 참조 카운팅 + 순환 수거기, 소형 객체 전용 할당기객체 소멸 후에도 메모리를 풀(pool)로 보유하는 경향"객체 지웠는데 상주 크기가 안 준다"의 원인
C++개발자 — new/delete, 할당자가 OS와 직거래해제 시점·방식 전부 코드 책임가상 메모리의 보호가 최후 안전망(그마저 뚫리면 미정의 동작)

7.1 Python — 지웠는데 왜 메모리가 안 줄어드는가

Python은 참조 카운팅(객체를 가리키는 참조 수가 0이 되는 즉시 소멸)을 기본으로 하고, 참조가 서로를 물고 도는 순환만 별도 수거기가 끊는다. 소멸 자체는 즉각적이다 — 그런데 상주 크기는 따라 줄지 않는 경우가 많다. 인터프리터가 소형 객체용 메모리를 블록 단위로 받아 두고, 객체가 죽어도 그 블록을 운영체제에 돌려주는 대신 다음 할당을 위해 보유하기 때문이다. 같은 크기 객체가 다시 태어나면 재사용되므로 이는 최적화지 누수가 아니다. 

import sys

a = []
b = a                          # 같은 리스트를 가리키는 참조 둘
print(sys.getrefcount(a))      # 3 (a, b, + getrefcount 호출 인자 자신)

big = [0] * 10_000_000         # 상주 크기 수십 MB 증가
del big                        # 객체는 즉시 소멸하지만,
                               # 상주 크기는 그만큼 줄지 않을 수 있다
                               # (인터프리터가 풀을 보유 — 추적은 tracemalloc으로)

Python 관점의 통찰: "메모리 사용량"이라는 한 단어 뒤에 세 개의 층이 겹쳐 있다 — 살아 있는 객체의 합(참조 카운팅의 세계), 인터프리터가 보유한 풀(런타임의 세계), 운영체제가 보는 상주 집합(이 문서의 세계). 누수를 의심할 때 어느 층의 숫자를 보고 있는지부터 확인하는 습관이 진단 시간의 대부분을 절약한다. 층을 혼동하면 "del 했는데 안 줄어든다"는 가짜 누수를 쫓게 된다.

7.2 C++ — 환상의 보호를 최후 안전망으로 쓰는 언어

C++에서 힙 수명은 전적으로 코드 책임이다. 해제한 메모리를 다시 쓰는 것(use-after-free), 두 번 해제, 배열 경계 밖 쓰기 — 전부 미정의 동작(undefined behavior, 표준이 결과를 정의하지 않아 무엇이 일어나도 이상하지 않은 상태)이다. 흥미로운 것은 이런 버그가 탐지되는 방식이다: 운이 좋으면 표에 없는 페이지를 건드려 즉시 죽지만(segmentation fault — §2의 보호가 잡아 준 것), 운이 나쁘면 자기 주소 공간 안의 유효한 다른 데이터를 조용히 밟는다. 가상 메모리의 보호는 프로세스 간 격리이지 프로세스 안의 안전이 아니기 때문이다. 

#include <memory>

void manual() {
    int* p = new int[1000];
    // ... 예외가 나면 delete[]에 도달하지 못한다 → 누수
    delete[] p;
    // *p = 1;   // 해제 후 사용 — UB. 크래시가 '나면' 오히려 다행
}

void raii() {
    auto p = std::make_unique<int[]>(1000);
}   // 스코프를 벗어나는 순간 소멸자가 해제 — 경로가 몇 갈래든 보장

C++ 관점의 통찰: segfault가 "나 준다"는 것은 사실 행운이다 — 페이지 단위 보호는 페이지 경계를 넘는 접근만 잡을 수 있고, 같은 페이지 안의 오염은 통과시킨다. 그래서 C++ 진영의 실전 답은 하드웨어 보호에 기대지 않는 것이다: 소유권을 타입에 박는 RAII(자원 획득이 곧 초기화 — 소멸자가 해제를 보장하는 관용구)와 스마트 포인터로 해제 경로 자체를 코드에서 소거한다. 언어가 안전망을 안 주므로 관용구가 안전망이 된 사례다.

7.3 Java / JS·TS — 한 줄 요약

Java는 힙 상한(-Xmx)까지를 JVM이 통치하는 나라로 만들어 개발자를 물리 메모리에서 가장 멀리 떼어 놓았다 — 대신 컨테이너 메모리 제한과 JVM 힙 설정이 어긋나면 "힙은 여유인데 컨테이너가 죽는" 식의 층간 충돌이 난다. JS·TS는 엔진 기본 힙 상한이 물리 메모리보다 먼저 오는 천장이라, 대용량 처리에서 만나는 메모리 부족은 대개 OS가 아니라 엔진의 것이다. 두 언어 모두 교훈은 같다: GC가 있어도 이 문서가 무관해지는 게 아니라, 런타임 힙과 OS 메모리라는 두 층의 관계로 문제가 옮겨 갈 뿐이다.

8. 함께 알면 좋은 것

  • 메모리 매핑 파일(memory-mapped file) — 파일을 주소 공간에 매핑해 읽기/쓰기를 메모리 접근으로 바꾸는 기법. 페이지 폴트 기제의 또 다른 응용이며, 파일 I/O와의 관계는 V4에서.
  • 대형 페이지(huge page) — 페이지를 2MB 등으로 키워 TLB 한 항목이 덮는 범위를 넓히는 기법. TLB 미스가 병목인 대용량 메모리 워크로드(DB 등)의 표준 처방.
  • 컨테이너 메모리 제한 — cgroup은 컨테이너별 상주 메모리 상한을 강제하고, 초과 시 그 컨테이너만 OOM 처리한다. "머신 전체는 여유인데 내 컨테이너가 죽는" 구조의 근원.
  • 과약정(overcommit) 정책 — 약속의 합이 물리+스왑을 넘도록 허용할지의 운영체제 설정. 요구 페이징의 통계적 베팅이며, 실패 시점이 할당에서 접근으로 이동하는 원인.
  • 주소 공간 배치 무작위화(ASLR) — 스택·힙·라이브러리의 가상 주소를 실행마다 무작위로 배치해 공격자가 주소를 예측하기 어렵게 하는 보안 기법. "주소는 어차피 가상"이라는 이 문서의 전제가 보안 도구가 된 사례.

9. 한 장 요약

  • 가상 메모리 = 배치·보호·용량 문제를 "프로세스마다 사적인 연속 공간"이라는 환상으로 푸는 구조. V1의 격리는 이 표(페이지 테이블) 밖의 주소를 만들 수 없다는 사실의 귀결이다.
  • 구현은 쪼개기: 페이지↔프레임 대응을 표에 적고, 변환 비용은 TLB로 감춘다 — 프로세스 스위치가 무거운 이유(TLB 무효화)가 여기서 나온다.
  • 페이지 폴트는 에러가 아니라 훅이다: 요구 페이징·쓰기 시 복사가 "폴트 나면 그때 일한다" 패턴 위에 선다.
  • 메모리가 넘치면 스와핑으로 버티되 시간이 새고, 활발한 페이지 합이 물리 용량을 넘으면 스래싱으로 절벽처럼 무너진다.
  • 수치 읽기: 가상 크기는 약속, 상주 크기는 현실. major 폴트와 지속적 스왑 I/O가 진짜 경고 신호다.
  • 언어 런타임은 OS 위에 자기 힙 층을 얹는다 — "지웠는데 안 줄어든다"류의 미스터리는 대부분 층의 혼동이다.

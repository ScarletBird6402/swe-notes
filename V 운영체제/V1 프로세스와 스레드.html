V1 프로세스와 스레드

0. 한눈에 보는 결론

  • 프로세스는 격리의 단위, 스레드는 실행의 단위다. 프로세스는 자기만의 주소 공간(address space)을 갖고, 스레드는 한 프로세스 안에서 그 공간을 공유하는 실행 흐름이다.
  • 격리와 공유는 맞바꿈이다: 프로세스끼리는 서로를 망가뜨릴 수 없지만 대화가 비싸고, 스레드끼리는 대화가 공짜지만 서로를 망가뜨릴 수 있다.
  • 컨텍스트 스위치는 CPU가 실행 흐름을 갈아타는 비용이다 — 레지스터 저장·복원이라는 명시적 비용보다, 캐시·TLB가 식는 간접 비용이 대개 더 크다.
  • 프로세스 간 통신(inter-process communication, IPC)은 격리를 유지한 채 대화하는 통로들이다 — 파이프·소켓·공유 메모리, 각각 편의성과 성능을 다르게 판다.
  • "스레드를 늘리면 빨라진다"는 조건부로만 참이다: CPU 코어 수, 작업의 성격(계산 vs 대기), 공유 상태의 경합이 상한을 정한다.
  • 웹 개발자의 매일에 이 개념이 숨어 있다: 요청당 스레드 서버, 커넥션 풀 크기, Node의 단일 스레드, Python 워커 프로세스 수 — 전부 이 문서의 응용이다.

1. 프로그램, 프로세스, 스레드 — 세 개의 층

디스크에 있는 실행 파일은 프로그램(정적인 코드와 데이터)이다. 운영체제가 그것을 메모리에 올리고 실행 자원을 붙이면 프로세스(살아있는 인스턴스)가 된다. 같은 프로그램을 두 번 실행하면 프로세스 두 개 — 같은 악보로 연주되는 별개의 공연이다.

프로세스 안에서 실제로 명령을 한 줄씩 실행해 나가는 흐름이 스레드다. 모든 프로세스는 최소 한 개의 스레드를 가지며(main), 여러 개를 만들면 한 프로세스 안에서 여러 흐름이 동시에 진행된다.

프로그램(디스크의 파일) └─ 실행 → 프로세스 (주소 공간 + 자원 + 스레드들) ├─ 스레드 1 (자기 스택·레지스터) ┐ ├─ 스레드 2 (자기 스택·레지스터) ├─ 코드·힙·전역은 공유 └─ 스레드 3 (자기 스택·레지스터) ┘

2. 주소 공간 — 격리의 실체

각 프로세스는 "0번지부터 시작하는 나만의 메모리 세계"를 본다. 이것이 주소 공간이다. 프로세스 A의 1000번지와 B의 1000번지는 이름만 같을 뿐 물리적으로 다른 곳이며, 이 변환(가상→물리)은 운영체제와 하드웨어가 수행한다 — 그 기제(가상 메모리·페이징)는 V2에서 다룬다.

여기서 중요한 것은 결과다: 프로세스는 다른 프로세스의 메모리를 우연히라도 읽거나 쓸 수 없다. 한 프로세스가 잘못된 포인터로 폭주해도 피해는 자기 세계 안에서 끝난다. 브라우저가 탭마다 프로세스를 쓰는 이유, 워커를 프로세스로 띄운 서버에서 워커 하나가 죽어도 나머지가 사는 이유가 이 격리다.

격리는 안전인 동시에 벽이다. 두 프로세스가 협력하려면 벽에 뚫린 공식 통로(IPC, §5)를 써야 하고, 그 통로는 같은 주소 공간 안의 대화보다 항상 비싸다. "격리를 살 것인가, 공유를 살 것인가"가 멀티프로세스 vs 멀티스레드 선택의 본질이다.

3. 스레드 — 같은 세계를 공유하는 흐름들

한 프로세스의 스레드들은 코드·힙·전역 변수를 공유하고, 스택과 레지스터만 각자 갖는다. 공유 덕에 스레드 간 데이터 전달은 "그냥 같은 변수를 읽으면" 된다 — 복사도, 직렬화도, 커널 개입도 없다. 이것이 스레드의 강점이자 함정의 근원이다.

두 스레드가 같은 변수에 동시에 쓰면 결과는 실행 타이밍에 따라 달라진다 — 경쟁 조건(race condition)이다. 격리가 없으므로 보호는 전적으로 개발자의 규율(락·불변성·동기화)에 달리며, 이 주제는 동시성 카테고리(G1)에서 본격적으로 다룬다. 여기서 기억할 것은 구조적 사실 하나다: 스레드의 위험은 버그가 아니라 설계의 대가다. 공유를 공짜로 얻는 대신 안전을 수동으로 구축해야 한다.

4. 컨텍스트 스위치 — 갈아타기의 비용

CPU 코어는 한 순간에 하나의 흐름만 실행한다. 코어 수보다 많은 스레드가 "동시에" 도는 것처럼 보이는 이유는, 운영체제가 짧은 간격으로 흐름을 갈아태우기 때문이다. 이 갈아타기가 컨텍스트 스위치이며, 비용은 두 겹이다.

  • 직접 비용: 현재 흐름의 레지스터·상태를 저장하고 다음 흐름 것을 복원하는 커널 작업. 마이크로초 단위.
  • 간접 비용: 새 흐름이 시작되면 CPU 캐시와 TLB(가상→물리 주소 변환 결과를 담아 두는 캐시 — 한 줄로: "주소 번역 결과의 캐시")에 이전 흐름의 데이터만 남아 있다. 새 흐름은 한동안 캐시 미스를 연발하며 식은 상태로 달린다. 대개 직접 비용보다 크다.

프로세스 간 스위치는 스레드 간 스위치보다 무겁다 — 주소 공간 자체가 바뀌므로 TLB가 통째로 무효화되기 때문이다. "스레드는 가볍다"는 관용구의 실제 의미가 이것이다: 생성도 가볍지만, 갈아타기도 가볍다.

흔한 함정 — 스레드 수 ∝ 처리량이라는 착각. 코어가 8개인데 계산 중심 스레드를 800개 만들면, 일은 늘지 않고 컨텍스트 스위치와 캐시 오염만 는다. 스레드 증설이 유효한 것은 흐름 대부분이 대기(I/O·네트워크)하는 작업일 때다 — 기다리는 동안 코어를 다른 흐름에 넘길 수 있기 때문. "이 작업은 CPU를 쓰는가, 기다리는가"가 스레드 설계의 첫 질문이다.

6. 흔히 헷갈리는 지점

  • 동시성(concurrency) vs 병렬성(parallelism). 동시성은 여러 흐름을 다루는 구조(한 코어에서 번갈아도 성립), 병렬성은 물리적으로 같은 순간에 실행(코어 여러 개 필요). 단일 코어에서도 동시성은 있고 병렬성은 없다.
  • 멀티프로세스 vs 멀티스레드는 우열이 아니라 배치다. 장애 격리·독립 배포가 중요하면 프로세스, 데이터 공유가 잦고 통신 비용이 아까우면 스레드. 실무 서버는 흔히 "프로세스 여러 개 × 각자 스레드 여러 개"로 둘을 섞는다.
  • "메인 스레드가 죽으면?"의 답은 런타임마다 다르다. 많은 환경에서 프로세스 종료는 그 안의 모든 스레드를 함께 끝낸다 — 스레드는 프로세스라는 세계 안의 존재라서다. 백그라운드 작업을 스레드에 맡겼다면 프로세스 수명 관리가 곧 그 작업의 수명 관리다.
  • 조용한 실패 — 다른 스레드의 예외. 여러 런타임에서 작업 스레드의 처리되지 않은 예외는 메인 흐름에 전파되지 않고 그 스레드만 조용히 끝낸다. "돌고 있는 줄 알았던 스레드가 없다"는 장애의 고전이다.

★ 7. 언어별 대조

"스레드"라는 단어는 언어마다 가리키는 실체가 다르다 — OS 스레드에 직결된 언어부터, 스레드를 하나로 제한한 언어, 스레드는 있으되 병렬 계산을 막아 둔 언어까지. 차이의 핵심은 두 가지다: 누가 스케줄링하는가(OS인가, 언어 런타임인가), 그리고 메모리를 공유하는가(이 장의 격리 ↔ 공유 축). 이 두 답이 각 생태계의 서버 아키텍처를 결정했다.

7.1 Java — 스케줄러가 둘이 되다: 플랫폼 스레드와 가상 스레드

Java의 전통적 스레드(플랫폼 스레드)는 new Thread() 한 줄이 곧 커널에 스레드 생성을 요청하는 OS 스레드 1:1 매핑이다. 스레드마다 커널 자원과 넉넉한 스택 영역이 예약되므로 수천 개는 되지만 수십만 개는 어렵고, 소켓을 기다리는 동안에도 그 OS 스레드는 점유된 채 잠든다. "대기 작업에 스레드 하나씩"이 아까워지는 지점이 여기이며, 요청당 스레드 서버가 스레드 풀 크기·커넥션 풀 크기를 신중히 맞추는 문화는 이 비용에 대한 대응이다.

가상 스레드(virtual thread — Java 21에서 정식 도입된, JVM이 직접 관리하는 경량 스레드)는 이 매핑을 다대일로 바꾼다. JVM은 코어 수 정도의 플랫폼 스레드를 캐리어 스레드(carrier — 가상 스레드를 실제로 태워 실행하는 플랫폼 스레드)로 두고, 그 위에 가상 스레드를 번갈아 얹는다. 가상 스레드가 소켓 읽기·sleep·락 대기로 블로킹되는 순간 JVM은 그 스레드의 스택 프레임을 힙 객체로 옮겨 캐리어에서 내려놓고(unmount), 캐리어는 곧바로 다른 가상 스레드를 태운다(mount). 즉 스케줄러가 두 층이 된다 — OS는 캐리어를 스케줄하고, JVM은 가상 스레드를 캐리어에 스케줄한다. 이 장 §4의 원리("대기가 많은 작업만 스레드 증설이 유효하다")를 런타임이 자동화한 셈이다.

OS 스케줄러 ── 캐리어 스레드(플랫폼 스레드, ≈ 코어 수) ├─ [가상 스레드 A 실행 중] │ └─ 소켓 대기 발생 → A 언마운트 (스택을 힙에 보관, 캐리어 반납) └─ [가상 스레드 B 마운트] ← JVM 스케줄러가 큐에서 꺼냄 (A는 I/O 완료 시 다시 큐에 들어가 아무 캐리어에나 마운트)
// 플랫폼 스레드: OS 스레드 1:1 — 대기 중에도 커널 스레드를 점유한다
Thread t = Thread.ofPlatform().start(() -> fetch(url));

// 가상 스레드: 작업마다 하나씩 만들어도 된다 (Java 21+)
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (String url : urls) {
        ex.submit(() -> fetch(url));   // 10만 개여도 OS 스레드는 캐리어(≈코어 수)뿐
    }
}   // close()가 모든 작업 완료를 기다린다
// fetch()가 소켓을 기다리는 순간 JVM이 이 가상 스레드를 캐리어에서 내려놓는다 —
// 코드 모양은 동기식 그대로인데, 아래에서는 이벤트 루프와 같은 일이 벌어진다

함정은 고정(pinning — 가상 스레드가 블로킹되는데도 캐리어에서 내려올 수 없어 캐리어까지 함께 잠드는 상태)이다. 고정이 잦으면 캐리어가 소진되어 "가상 스레드를 썼는데 요청당 스레드보다 느린" 결과가 난다. 초기(Java 21)에는 synchronized 블록 안에서의 블로킹이 대표적 고정 원인이었으나, 2020년대 중반 기준 Java 24에서 이 제약이 제거되어 현재 남은 고정 원인은 네이티브 코드(JNI·외부 함수) 호출 중의 블로킹 정도다. 또 하나 — 가상 스레드는 계산 작업을 빠르게 하지 않는다. 캐리어 수가 곧 병렬 상한이므로 CPU 작업은 여전히 코어 수가 상한이며, 가상 스레드는 오직 대기를 싸게 만든다.

Java 관점의 통찰: 가상 스레드는 "풀에 넣어 재사용"하면 안 된다 — 풀은 스레드가 비쌀 때의 처방이고, 가상 스레드는 생성이 싸도록 설계된 것이라 풀에 넣는 순간 그 이점이 사라진다. 대신 신경 쓸 곳은 가상 스레드가 무제한으로 늘어 뒤에 있는 자원(데이터베이스 커넥션 등)을 압도하는 일이며, 그때 필요한 것은 스레드 풀이 아니라 세마포어 같은 동시 진입 수 제한이다.

7.2 JS·TS — 스레드 없이 동시성: 이벤트 루프와 Worker의 격리

JS는 반대 극단에서 출발한다. 자바스크립트 코드를 실행하는 스레드는 하나이며, 동시성은 스레드가 아니라 이벤트 루프가 만든다. 원리는 "기다리지 않는다"이다 — fetch()나 파일 읽기를 호출하면 JS 스레드는 요청만 런타임에 넘기고 즉시 다음 일로 넘어간다. 실제 대기는 OS(커널의 비동기 I/O 알림)나 런타임의 보조 스레드 풀이 맡고, 완료되면 콜백이 큐에 들어가며, 이벤트 루프는 큐에서 하나를 꺼내 끝까지 실행한 뒤 다음 것을 꺼낸다. 이 장 §4에서 "대기 작업은 코어를 다른 흐름에 넘기면 된다"고 했는데, JS는 넘길 다른 스레드를 만드는 대신 대기 자체를 스레드 밖으로 밀어낸 것이다.

콜 스택 (JS 실행 — 단일 스레드, 콜백 하나를 끝까지 실행) │ fetch(url) 호출 → 요청을 런타임에 위임하고 즉시 반환 ▼ 이벤트 루프 ── 태스크 큐 [ 완료된 콜백 … ] ──► 하나 꺼내 실행 → 반복 ▲ I/O 완료 알림 (커널 비동기 I/O / 런타임 보조 스레드 풀)

얻는 것은 구조적 안전이다: JS 힙을 만지는 스레드가 하나뿐이므로 메모리 수준의 경쟁 조건이 성립할 수 없다. 락도, 원자 연산도 필요 없다. 잃는 것은 정반대의 함정이다 — 콜백 하나가 끝날 때까지 아무도 끼어들지 못하므로, 큰 계산 하나가 루프를 잡으면 모든 요청·모든 타이머·모든 화면 갱신이 함께 멈춘다. "싱글 스레드라 안전하다"는 말은 계산 작업 앞에서는 "싱글 스레드라 전부 멈춘다"로 뒤집힌다.

그래서 진짜 병렬이 필요할 때 쓰는 Worker(worker_threads·Web Worker)는 기술적으로는 같은 프로세스의 OS 스레드지만 철학은 프로세스다. Worker마다 별도의 JS 힙과 별도의 이벤트 루프를 가지며, 메인과 Worker는 postMessage로만 대화한다. 이때 값은 구조적 복제(structured clone — 객체 그래프를 통째로 복사하는 알고리즘)로 복사되어 건너간다. 격리를 유지한 채 대화하는 통로 — 이 장 §5의 IPC 원리가 스레드 위에 재현된 것이다. 예외가 하나 있다: SharedArrayBuffer는 두 Worker가 같은 메모리를 매핑하는 공유 메모리이며, 그 순간 §5의 결론대로 동기화 책임(Atomics)이 부활한다. 

// 메인: 스레드 없이 두 대기를 "동시에" 진행
const a = fetch(url1);                 // 요청만 걸어 두고 바로 반환
const b = fetch(url2);
const [ra, rb] = await Promise.all([a, b]);

// 계산은 루프를 막는다 → Worker(별도 힙·별도 이벤트 루프)로
import { Worker } from 'node:worker_threads';
const w = new Worker('./heavy.js', { workerData: { n: 1e9 } }); // 값은 복사되어 전달
w.on('message', (result) => console.log(result));              // 돌아올 때도 복사

// 예외 — SharedArrayBuffer: 진짜 공유 메모리, 경쟁 조건이 돌아온다
const shared = new SharedArrayBuffer(4);
const counter = new Int32Array(shared);   // 여러 Worker에 postMessage로 넘겨도 복사되지 않음
Atomics.add(counter, 0, 1);               // counter[0]++ 은 안전하지 않다 — C++의 ++naive와 같은 이유

TS는 이 그림에 아무것도 더하지 못한다 — 타입은 컴파일 시 지워지므로 "이 값이 어느 스레드에 있는가"를 타입으로 표현할 수 없고, postMessage로 받은 값은 any다. 더 미묘한 함정은 구조적 복제가 프로토타입을 버린다는 점이다: 클래스 인스턴스를 Worker로 보내면 필드만 복사된 평범한 객체가 도착하고 메서드는 사라진다. TS 타입은 Order라고 말하지만 런타임의 실체는 Order가 아니다.

JS·TS 관점의 통찰: JS가 회피한 것은 "메모리 수준"의 경쟁 조건뿐이다. await 한 번은 이벤트 루프에 제어를 돌려주는 양보 지점이라, "확인하고(if) → await → 행동한다"는 코드는 그 사이에 다른 콜백이 상태를 바꿔 놓을 수 있다 — 락 없이도 논리적 경쟁 조건은 성립한다. 그리고 "싱글 스레드"는 JS 실행 스레드 이야기일 뿐, Node 프로세스 자체는 런타임 보조 스레드 풀과 GC 스레드를 거느린 어엿한 멀티스레드 프로세스다.

7.3 Python — GIL: 스레드가 있는데 병렬이 안 되는 이유

Python의 threading.Thread는 Java의 플랫폼 스레드처럼 진짜 OS 스레드다. 그런데도 병렬 계산이 안 되는 이유는 인터프리터 안에 있다. 전역 인터프리터 락(global interpreter lock, GIL)은 "파이썬 바이트코드를 실행하는 스레드는 한 순간에 하나"라는 인터프리터 수준의 락이다. 스레드가 여럿이어도 GIL을 쥔 하나만 달리고, 나머지는 OS 스케줄러가 코어를 배정해 줘도 락 앞에서 다시 잠든다 — OS 스케줄링 위에 인터프리터의 락 양도가 한 층 더 얹힌 구조다.

그래서 Python 스레드는 대기가 많은 작업(I/O)에는 유효하다 — 소켓·파일을 기다리는 C 코드는 GIL을 내려놓으므로, 그동안 다른 스레드가 바이트코드를 실행한다. 반면 계산 작업은 스레드를 늘려도 한 코어만큼만 나온다. 더 나쁜 것은, 계산 스레드들이 일정 간격(스위치 인터벌 — 기본 5ms)마다 GIL을 강제로 주고받으므로 한 코어어치 일에 컨텍스트 스위치 비용(§4)까지 얹힌다는 점이다. 계산을 병렬화하려면 프로세스를 늘려야 하며, 이는 이 문서의 원리 그대로다: 프로세스마다 인터프리터와 GIL이 따로 있으므로 격리 비용(직렬화해서 주고받기)을 내고 병렬성을 산다. 

import sys
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def cpu_heavy(n): ...        # 계산 작업
def fetch(url): ...          # 대기(I/O) 작업

sys.getswitchinterval()      # 0.005 — 계산 스레드끼리 GIL을 강제로 넘기는 간격

# I/O 대기 → 스레드로 충분 (기다리는 동안 GIL 반납)
with ThreadPoolExecutor(max_workers=20) as ex:
    pages = list(ex.map(fetch, urls))

# CPU 계산 → 프로세스로 (격리 비용을 내고 진짜 병렬을 산다)
with ProcessPoolExecutor(max_workers=8) as ex:
    results = list(ex.map(cpu_heavy, jobs))   # 인자·결과는 pickle로 직렬화되어 오간다

예외와 동향 두 가지. 첫째, 수치 라이브러리의 C 확장처럼 무거운 계산을 C 수준에서 수행하는 코드는 그동안 GIL을 놓는 경우가 많아, "스레드로 계산 병렬화"가 부분적으로 성립한다 — 병목이 바이트코드인지 C 코드인지를 먼저 봐야 하는 이유다. 둘째, 2020년대 중반 기준 GIL 없는 프리스레디드(free-threaded) 빌드가 Python 3.13에서 실험적으로 등장해 3.14에서 정식 지원으로 승격됐다. 다만 기본 빌드가 아닌 별도 배포본(python3.14t)이며, 이를 쓰면 스레드 병렬 계산이 가능해지는 대신 C++·Java와 같은 "공유 메모리의 경쟁 조건"이 Python 코드에도 온전히 돌아온다.

Python 관점의 통찰: 두 풀의 API가 똑같다는 점이 교과서적이다 — 코드 모양은 같지만 아래에서는 "공유 메모리의 스레드"와 "직렬화로 대화하는 프로세스"라는 정반대의 배치가 돈다. 인자와 반환값이 pickle로 오간다는 것(= 프로세스 풀에는 직렬화 불가능한 객체를 못 넘긴다), 그리고 워커 프로세스를 만드는 방식(부모 주소 공간을 복제하는 fork / 새 인터프리터를 띄우는 spawn)이 곧 격리 비용의 정체라는 것까지 보이면 이 장의 격리 개념을 체득한 것이다.

7.4 C++ — 공유 주소 공간을 맨손으로 만지기

std::thread는 OS 스레드에 직결되고(생성자 호출 = 커널 스레드 생성), 그 위에 JVM의 캐리어도, 이벤트 루프도, GIL도 없다. 스케줄링은 전적으로 OS가 하고 언어는 어떤 보호도 끼워 넣지 않는다. 같은 변수를 두 스레드가 동기화 없이 쓰면 미정의 동작(undefined behavior — 표준이 결과를 정의하지 않아 무엇이 일어나도 이상하지 않은 상태)이다. 

#include <thread>
#include <atomic>

int naive = 0;
std::atomic<int> safe{0};

void work() {
    for (int i = 0; i < 100000; ++i) {
        ++naive;   // 두 스레드가 겹치면 증가 유실 — 경쟁 조건(UB)
        ++safe;    // 원자적 증가 — 항상 정확
    }
}
int main() {
    std::thread a(work), b(work);
    a.join(); b.join();
    // naive: 200000보다 작을 수 있음 / safe: 정확히 200000
}

C++에서만 추가로 성립하는 문제는 수명이다. 이 장 §1에서 스레드는 자기 스택만 따로 갖는다고 했는데, C++는 그 스택 위의 지역 변수를 다른 스레드에 참조로 넘기는 것을 막지 않는다. 넘긴 쪽 함수가 먼저 반환하면 그 스택 프레임은 사라지고, 받은 스레드는 이미 없는 메모리를 가리키게 된다. 또 std::thread 객체는 소멸 전에 반드시 join(끝날 때까지 기다림) 또는 detach(연을 끊고 방치) 되어야 하며, 둘 다 하지 않으면 프로그램이 즉시 종료된다. 

void spawn_bad() {
    int local = 42;
    std::thread t([&local] { use(local); });   // 지역 변수를 참조로 캡처
    t.detach();
}   // spawn_bad 반환 → local의 스택 프레임 소멸 → t는 사라진 메모리를 읽는다

void spawn_ok() {
    int local = 42;
    std::jthread t([local] { use(local); });   // 값으로 복사 — 스택 수명과 분리
}   // C++20 jthread: 소멸자가 자동 join — 잊어도 종료되지 않고, 수명이 스코프에 묶인다

C++ 관점의 통찰: ++naive가 깨지는 이유는 그것이 기계 수준에서 "읽기→증가→쓰기" 세 단계이기 때문이다 — 고수준 문법 한 토큰이 원자적이리라는 직관은 하드웨어 앞에서 무너진다. 스레드 생성이 곧 커널 자원 할당이므로 C++ 서버가 스레드 풀을 미리 만들어 재사용하는 것은 취향이 아니라 생성·컨텍스트 스위치 비용에 대한 직접적 대응이며(가상 스레드 덕에 풀이 불필요해진 Java와 정반대 방향의 처방), detach한 스레드가 §6의 "프로세스가 죽으면 스레드도 죽는다"에 그대로 노출된다는 것 — 스레드 수명 관리를 런타임이 아니라 소유권으로 해결해야 한다는 것이 C++만의 조건이다.

8. 함께 알면 좋은 것

  • 스케줄링 — 누가 다음에 CPU를 받는가: 선점·우선순위·기아. 컨텍스트 스위치의 "언제"를 정하는 규칙(V3).
  • 가상 메모리 — 주소 공간이라는 환상을 만드는 기제: 페이징·스와핑(V2).
  • 스레드 안전성 — 공유의 대가를 지불하는 기술: 락·불변성·원자성(G1).
  • 코루틴·그린 스레드 — OS 스레드 하나 위에 얹는 경량 흐름들. "스레드는 비싸다"에 대한 언어 런타임들의 답.
  • 컨테이너와 프로세스 — 컨테이너는 가상 머신이 아니라 격리를 강화한 프로세스다. 이 장의 격리 개념이 곧 컨테이너 이해의 바탕.

9. 한 장 요약

  • 프로세스 = 주소 공간을 가진 격리 단위, 스레드 = 그 안에서 스택만 따로 갖는 실행 흐름. 격리 ↔ 공유의 맞바꿈이 모든 선택의 축이다.
  • 컨텍스트 스위치 비용의 본체는 레지스터 저장이 아니라 캐시·TLB가 식는 것 — 프로세스 간 전환이 더 무거운 이유도 TLB 무효화다.
  • 스레드 증설이 유효한 것은 대기 중심 작업뿐. 계산 작업은 코어 수가 상한이다.
  • IPC(파이프·소켓·공유 메모리)는 격리를 되파는 눈금 조절 — 빠를수록 동기화 책임이 부활한다.
  • 언어별 "스레드"는 실체가 다르다: Java(OS 1:1), JS(단일+이벤트 루프), Python(GIL — 계산은 프로세스로), C++(맨손의 OS 스레드).
  • 작업 스레드의 예외는 조용히 사라질 수 있다 — 스레드의 생사 관찰은 설계 사항이다.

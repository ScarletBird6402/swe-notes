C10 직렬화와 역직렬화

0. 한눈에 보는 결론

  • 직렬화(serialization)는 메모리 속 객체를 저장·전송 가능한 바이트 나열로 바꾸는 것, 역직렬화(deserialization)는 그 바이트에서 객체를 다시 조립하는 것이다.
  • 필요한 이유: 객체는 포인터·참조로 얽힌 메모리 내부 구조라서, 프로세스 밖(네트워크, 파일, DB)으로는 그 모습 그대로 나갈 수 없다.
  • 포맷 선택은 트레이드오프다 — 텍스트(JSON 등)는 사람이 읽고 디버깅하기 좋고, 바이너리(Protobuf 등)는 작고 빠르며 스키마로 계약을 강제한다.
  • 직렬화된 데이터는 코드보다 오래 산다. 쓰는 쪽과 읽는 쪽의 코드 버전이 달라지는 순간은 반드시 오며, 이때를 대비하는 것이 스키마 진화(schema evolution)다.
  • 버전 호환의 기본기: 필드는 추가는 안전하게(기본값·생략 허용), 삭제·의미 변경은 위험하게 취급하고, 모르는 필드는 버리지 말고 관용적으로 지나친다.
  • 역직렬화는 외부 입력이 객체가 되는 지점, 즉 신뢰 경계다. 언어 네이티브 직렬화(예: pickle)로 신뢰할 수 없는 데이터를 역직렬화하는 것은 코드 실행을 허용하는 것과 같다.

1. 왜 객체는 그대로 내보낼 수 없는가 — 객체 ↔ 바이트

메모리 안의 객체는 사진처럼 한 덩어리가 아니다. 주문 객체가 회원 객체를 참조하고, 회원 객체가 주소 리스트를 참조하는 식으로, 메모리 주소(포인터·참조)로 연결된 그래프다. 이 주소들은 지금 이 프로세스의, 지금 이 순간의 메모리에서만 의미가 있다. 다른 컴퓨터는 물론이고, 같은 컴퓨터에서 프로그램을 재시작하기만 해도 무효가 된다.

그래서 객체를 프로세스 밖으로 보내려면, 주소로 연결된 그래프를 주소 없이 값만으로 표현한 1차원 바이트 나열로 평탄화해야 한다. 이것이 직렬화이고, 받는 쪽에서 그 바이트를 해석해 자기 메모리에 새 객체 그래프를 지어 올리는 것이 역직렬화다.

[프로세스 A 메모리] [프로세스 B 메모리] 객체 그래프(주소로 연결) 새 객체 그래프(새 주소) │ ▲ │ 직렬화: 값만 뽑아 평탄화 │ 역직렬화: 해석해 재조립 ▼ │ 바이트 나열 ──── 네트워크 전송 / 파일·DB 저장 ────────┘ {"orderId":7,"user":{"name":"Kim"}} ← 주소가 아니라 "값"만 남는다

핵심 관찰: 역직렬화로 만들어진 객체는 원본과 값이 같은 새 객체이지, 원본 그 자체가 아니다. 같은 객체를 두 번 참조하던 구조·객체의 동일성(identity)·연결된 자원(열린 파일, 소켓)은 기본적으로 살아남지 않는다. 직렬화는 "상태의 복사"이지 "객체의 이동"이 아니다.

2. 포맷 — 무엇을 기준으로 고르는가

같은 객체라도 바이트로 표현하는 방법은 여러 가지이며, 각 포맷은 서로 다른 것을 우선한다.

계열대표강점약점
텍스트 · 자기 기술
(필드 이름이 데이터에 포함)		 JSON, XML, YAML 사람이 읽고 고칠 수 있음, 언어 중립, 스키마 없이도 해석 가능 → 웹 API의 기본값 용량 큼(이름 반복), 파싱 느림, 타입 표현력 빈약(날짜·이진 데이터 없음)
바이너리 · 스키마 기반
(구조 정의를 코드 밖 스키마로 관리)		 Protocol Buffers, Avro, Thrift 작고 빠름, 스키마가 곧 계약 문서, 버전 호환 규칙 내장 사람이 못 읽음, 스키마 관리 체계 필요
바이너리 · 자기 기술 MessagePack, BSON, CBOR JSON과 구조 호환이면서 더 작고 빠름 스키마 계약은 없음 (JSON의 단점 일부 공유)
언어 네이티브 Java 직렬화, Python pickle 객체 그래프를 코드 몇 줄로 통째로 보존 타 언어와 교환 불가, 클래스 구조에 강결합, 보안 위험 — 아래 상세

선택 기준은 결국 세 질문이다: 누가 읽는가(사람 디버깅이 중요하면 텍스트), 누구와 교환하는가(이종 언어·외부 공개면 언어 중립 필수, 네이티브 배제), 얼마나 오래·많이 흐르는가(대용량·고빈도·장기 보존이면 스키마 기반 바이너리의 비용 절감과 계약 강제가 값을 한다).

3. 스키마 진화 — 직렬화의 진짜 어려운 문제

직렬화 자체는 라이브러리가 해 준다. 어려움은 시간이 흐르면서 시작된다: 데이터를 쓴 코드와 읽는 코드의 버전이 달라지는 상황은 예외가 아니라 정상 운영이다.

  • 서버는 배포로 새 버전이 됐는데, 사용자 브라우저에는 어제 로드된 구버전 프론트가 떠 있다.
  • 여러 서버 인스턴스를 순차 배포하는 동안, 신·구 버전이 동시에 메시지를 주고받는다.
  • 작년에 파일·DB·메시지 큐에 저장된 데이터를 올해의 코드가 읽는다.

이때 성립해야 하는 두 방향의 호환이 있다:

방향정의전형적 상황
후방 호환(backward compatibility) 새 코드가 옛 데이터를 읽을 수 있다 새 서버가 작년에 저장된 레코드, 구버전 클라이언트의 요청을 처리
전방 호환(forward compatibility) 옛 코드가 새 데이터를 읽을 수 있다 아직 배포 안 된 구버전 서버·구버전 앱이 새 서버의 응답을 처리

3.1 버전 호환을 지키는 변경 규칙

  • 필드 추가는 "선택적 + 기본값"으로 — 새 필드가 없어도(옛 데이터) 기본값으로 채워 읽고(후방), 옛 코드는 모르는 필드를 무시하면 된다(전방). 추가하자마자 필수로 요구하면 두 방향 모두 깨진다.
  • 모르는 필드는 관용적으로 — 읽는 쪽은 처음 보는 필드를 만나도 실패하지 않고 지나쳐야 전방 호환이 성립한다. 다만 읽고-수정하고-다시 쓰는 중계 코드라면, 모르는 필드를 버리지 말고 보존해 되써야 남의 새 필드를 조용히 증발시키지 않는다.
  • 삭제는 "쓰기 중단 → 유예 → 제거"의 단계로 — 어딘가에 그 필드를 읽는 코드·저장된 데이터가 남아 있는 한 즉시 삭제는 파손이다. 우선 선택적으로 바꾸고, 쓰기를 멈추고, 충분한 유예 후 제거한다.
  • 이름·타입·의미 변경은 사실상 "삭제 + 추가" — 같은 필드의 타입을 바꾸거나(문자열→숫자), 단위 의미를 바꾸는(원→달러) 변경은 가장 위험하다. 새 필드를 추가하고 옛 필드를 단계적으로 은퇴시키는 쪽이 안전하다.

스키마 기반 포맷이 강한 이유: Protocol Buffers는 필드를 이름이 아니라 번호로 식별하고, 번호 재사용을 금지하는 규칙으로 위 원칙들을 체계화했다. 모르는 번호의 필드는 자동으로 건너뛰고 보존한다. JSON에는 이런 내장 규칙이 없으므로, 같은 규율을 팀의 관례와 검증 코드로 직접 지켜야 한다 — 원리는 포맷과 무관하게 동일하다.

4. 역직렬화는 신뢰 경계다

역직렬화는 "외부에서 온 바이트가 내 프로세스 안의 객체가 되는" 지점이다. 두 층위의 위험을 구분해야 한다.

  • 데이터 검증의 문제(모든 포맷 공통) — 파싱이 성공했다는 것은 문법이 맞다는 뜻일 뿐이다. 나이가 -3이거나, 필수 값이 빠졌거나, 문자열이 1GB일 수 있다. 역직렬화 직후의 검증은 생략할 수 없는 단계다.
  • 코드 실행의 문제(네이티브 직렬화 특유) — Java 직렬화나 pickle 같은 포맷은 바이트 안에 "어떤 클래스를 어떻게 복원할지"에 대한 지시가 들어 있고, 복원 과정에서 그 클래스의 코드가 실행된다. 공격자가 바이트를 조작하면 역직렬화하는 행위 자체가 임의 코드 실행이 될 수 있다. 그래서 원칙은 단순하다: 신뢰할 수 없는 입력에는 네이티브 직렬화를 쓰지 않는다 — 데이터만 담는 포맷(JSON, Protobuf 등)을 쓴다.

5. 흔히 헷갈리는 지점

① "직렬화하면 안전하게 보호된다"? — 직렬화는 표현 형식의 변환일 뿐, 암호화도 압축도 아니다. 바이너리 포맷이 "사람 눈에 안 읽힌다"는 것과 "기밀이 보호된다"는 것은 전혀 다르다. 보호가 필요하면 직렬화 이후에 암호화를 별도로 적용한다.

② JSON 숫자의 조용한 정밀도 손실 — JSON 자체는 숫자 크기를 제한하지 않지만, 많은 파서가 숫자를 배정밀도 부동소수점으로 읽는다. 253을 넘는 정수 ID가 오류 없이 끝자리만 바뀐 채 도착하는 조용한 실패가 생긴다. 큰 ID·금액은 문자열로 나르는 관례가 이 때문이다.

③ 순환 참조 — A가 B를, B가 다시 A를 참조하는 그래프를 값 평탄화 방식으로 직렬화하면 무한 재귀에 빠진다. 참조를 ID로 치환하거나, 직렬화 대상 모델에서는 순환을 애초에 끊는 것이 정석이다. "도메인 객체를 그대로 직렬화하지 말고 전송용 객체(DTO)를 따로 두라"는 조언의 근거 중 하나다.

④ 필드 이름 바꾸기는 리팩터링이 아니다 — 코드 안에서의 이름 변경은 도구가 안전하게 해 주지만, 직렬화 필드 이름은 이미 저장·배포된 데이터와의 계약이다. IDE가 초록불을 켜도, 어제 저장된 데이터는 옛 이름으로 남아 있다.

★ 6. 언어별 대조

지금까지 본 원리 — 값만 남기는 평탄화, 스키마 진화, 신뢰 경계로서의 역직렬화 — 는 언어와 무관하게 성립한다. 다만 "그 값을 어떻게 찾아내는가"와 "그 과정에서 무엇이 조용히 새는가"는 언어마다 전혀 다른 얼굴을 하고 있다.

언어대표 수단값을 찾아내는 방식특유의 함정
Java Jackson 등 JSON 매핑 라이브러리, 네이티브 직렬화(Serializable) 리플렉션(reflection — 실행 중에 클래스의 필드·메서드 구조를 코드로 조회·호출하는 기능)으로 접근자·필드를 런타임에 훑어 매핑 계약(어노테이션·명명 규칙)을 벗어난 필드는 조용히 누락, 네이티브 직렬화의 버전 식별자 불일치
JS·TS JSON.parse / JSON.stringify 내장 언어의 값 모델 자체가 JSON과 거의 동형이라 매핑 코드가 거의 필요 없음 Date·undefined는 왕복에서 조용히 변형·탈락, BigInt는 예외 발생(시끄러운 실패), TS 타입은 런타임을 보증하지 않음
Python json 모듈(교환용), pickle(내부 한정) 인스턴스 속성을 담은 내부 딕셔너리(__dict__)에서 값만 뽑거나, pickle은 복원 절차까지 함께 기록 pickle 역직렬화는 임의 코드 실행 통로, json은 dict를 돌려줄 뿐 클래스 인스턴스가 아님
C++ 표준 직렬화 없음 — 라이브러리 또는 직접 구현 런타임 리플렉션이 없어, 값을 뽑는 코드를 사람이 직접 작성해야 함(컴파일 타임에 구조가 고정) 구조체를 그대로 복사(memcpy)하려는 유혹, 컴파일러·플랫폼마다 다른 메모리 표현(ABI)

6.1 Java — 리플렉션이 대신 훑어주는 매핑, 그리고 그 대가

Java에는 객체를 값으로 평탄화해 주는 언어 내장 기능이 없다. 대신 Jackson 같은 라이브러리가 리플렉션으로 클래스의 접근자(getter)나 필드를 런타임에 훑어 이름을 맞춰 준다. 편리함의 대가는 계약이 암묵적이라는 것이다 — 접근자가 없거나 이름 규칙을 벗어난 필드는 예외 없이 조용히 매핑에서 빠진다. 

public class User {
    private final long id;
    private final String name;

    @JsonCreator
    public User(@JsonProperty("id") long id, @JsonProperty("name") String name) {
        this.id = id;
        this.name = name;
    }
    // getter도, @JsonProperty도 없는 필드는 리플렉션이 "찾지 못한다" —
    // 계약을 대신 찾아주는 것이지, 계약을 만들어 주는 것이 아니다
}

네이티브 직렬화(Serializable)를 쓰면 이 문제가 한 단계 더 깊어진다. 클래스에는 serialVersionUID라는 버전 식별자 필드를 둘 수 있는데, 이 값을 명시하지 않으면 컴파일러가 클래스의 필드 구성으로부터 자동 계산해 채운다. 즉 기능과 무관한 필드 하나만 추가·삭제해도 이 식별자가 달라지고, 역직렬화하는 쪽의 클래스와 값이 다르면 JVM은 호환 여부를 판단할 수 없다며 복원을 거부한다. 

class LegacySession implements Serializable {
    // 생략하면 컴파일러가 클래스 구조로 자동 계산 — 겉보기엔 사소한 리팩터링도
    // 이 값을 바꿔 버려, 이미 저장된 옛 데이터의 복원을 깨뜨릴 수 있다
    private static final long serialVersionUID = 1L;
}

Java 관점의 통찰: 리플렉션 기반 매핑은 "코드를 안 짜도 되게" 해 주지만, 계약을 코드 밖(명명 규칙·어노테이션)으로 옮겼을 뿐 계약 자체를 없애지는 못한다. 어노테이션이 스키마 진화 원칙(추가는 선택적으로, 삭제는 단계적으로)을 어기면 컴파일은 성공해도 매핑은 조용히 어긋난다 — 리플렉션이 실패를 컴파일 타임에서 런타임으로 옮겨 놓았을 뿐이다.

6.2 JS·TS — JSON이 모어(母語)인 언어가 만드는 착시

JS의 값 모델은 JSON과 구조가 거의 같아서, JSON.stringify/JSON.parse를 쓰면 직렬화가 "그냥 되는 것"처럼 느껴진다. 바로 이 익숙함이 함정이다 — JSON이 표현하지 못하는 값이 왕복하는 순간 변환 규칙이 개입하는데, 어떤 값은 조용히 변형·탈락하고(조용한 실패) 어떤 값은 예외를 던진다(시끄러운 실패). 

const payload = {
  when: new Date(),   // Date 객체
  note: undefined,    // 정의되지 않음
  big: 10n             // BigInt
};

JSON.stringify(payload);
// '{"when":"2026-08-05T00:00:00.000Z"}'
// - when: Date는 ISO 문자열로 바뀐다. 다시 JSON.parse해도 Date가 아니라 문자열이다.
// - note: undefined인 속성은 키째로 사라진다(배열 안이면 null로 바뀜).
// - big: BigInt는 stringify 시점에 즉시 TypeError를 던진다.

TS 타입은 이 간극을 메워 주지 않는다. 타입은 컴파일이 끝나면 사라지는 컴파일 타임 개념이라, JSON.parse가 실제로 무엇을 돌려주는지는 검사하지 못한다. 타입 선언은 "이 값이 이런 모양이길 바란다"는 약속일 뿐, 파싱 결과가 그 약속을 지켰는지 런타임에 확인해 주는 장치가 아니다. 

interface User { id: number; createdAt: Date; }

const user: User = JSON.parse(text);   // 컴파일은 통과한다
user.createdAt.getFullYear();          // 런타임 오류 — createdAt은 실제로는 string이다

JS·TS 관점의 통찰: "JSON이 언어의 일부처럼 느껴진다"는 사실 자체가 역설적으로 위험을 가린다. 직렬화 경계를 넘는 값 중 JSON이 표현할 수 없는 것(날짜·정의되지 않은 값·큰 정수)은 항상 별도로 인코딩·디코딩 규칙을 정해야 하며, 그 규칙을 지켰는지는 타입이 아니라 런타임 검증(스키마 검증기 등)이 확인해야 한다.

6.3 Python — 인터프리터가 객체를 값으로 보는 두 가지 방식

Python 객체의 인스턴스 속성은 대체로 __dict__라는 딕셔너리 하나에 담겨 있다. json 모듈은 기본적으로 dict·list·기본 타입만 알기 때문에, 커스텀 객체를 직렬화하려면 이 __dict__에서 값만 뽑아내는 변환 함수를 직접 넘겨야 한다 — 이것이 "값만 남기는 평탄화"가 Python 인터프리터 수준에서 드러나는 모습이다. 

class User:
    def __init__(self, id, name):
        self.id = id
        self.name = name

u = User(7, "Kim")
u.__dict__   # {'id': 7, 'name': 'Kim'} — 인스턴스 속성은 결국 딕셔너리다

import json
json.dumps(u)                                  # TypeError: User는 json이 모르는 타입
json.dumps(u, default=lambda o: o.__dict__)    # 값만 명시적으로 뽑아 줘야 함

pickle은 다른 층위에서 동작한다. __dict__의 값뿐 아니라 "어느 모듈의 어느 클래스인지, 복원 시 어떤 절차(__reduce__ 등)를 거칠지"까지 바이트 안에 함께 기록한다. 편리함의 원천 — 객체 그래프를 통째로 복원할 수 있다는 것 — 이 그대로 위험의 원천이다. 이 복원 절차 지시를 조작하면 임의의 호출을 유발할 수 있기 때문이다. 

import pickle
pickle.dumps(u)
# 바이트 안에는 __dict__ 값뿐 아니라 "복원 시 무엇을 호출할지"에 대한 지시까지 들어 있다
# pickle.loads(신뢰할 수 없는_바이트)  # 이 지시를 그대로 실행하는 행위 — 절대 금지

Python 관점의 통찰: json.loads가 돌려주는 것은 dict·list뿐이다 — 내 클래스의 인스턴스가 아니다. 반대로 pickle은 "값 + 복원 절차"까지 돌려주기에 인스턴스가 그대로 나온다. 이 둘의 차이는 결국 "인터프리터가 클래스를 어떻게 다시 만드는가"에 대한 정보를 바이트에 얼마나 담느냐의 문제이며, 그 정보가 많을수록 편리함과 위험이 함께 커진다.

6.4 C++ — 값을 뽑는 코드를 사람이 직접 써야 하는 언어

C++에는 런타임에 클래스 구조를 훑어 주는 리플렉션이 없다. 그래서 "값만 남기는 평탄화"를 대신해 줄 존재가 없고, 직접 접근할 수 있는 객체의 메모리 표현을 그대로 파일에 쓰는 것이 직렬화처럼 보이는 유혹이 생긴다. 

struct User {
    int         id;      // 4바이트라고 단정할 수 없음 (플랫폼별 상이)
    std::string name;    // 실제 문자들은 힙에 있고, 여기엔 그 주소(포인터)가 있을 뿐
};

User u{7, "Kim"};
write(fd, &u, sizeof(u));   // ❌ 직렬화가 아니다:
// 1) name의 "포인터 값"이 저장됨 — 읽는 쪽 메모리에선 무의미한 주소
// 2) 컴파일러가 정렬을 위해 끼운 패딩 바이트(쓰레기 값)까지 딸려 감
// 3) 바이트 순서(엔디언)·타입 크기가 기계·컴파일러마다 다름
// 4) 가상 함수가 있다면 vtable 포인터(가상 함수 테이블 주소)까지 오염

// ✅ 올바른 방향: "값"을 명시적으로 뽑아 정의된 포맷으로 기록
void serialize(const User& u, std::ostream& out) {
    write_i32_le(out, u.id);                    // 크기·바이트 순서를 포맷이 고정
    write_i32_le(out, u.name.size());
    out.write(u.name.data(), u.name.size());    // 포인터가 아니라 내용물을 기록
}

이 문제는 한 프로그램의 실행 사이에서도 생기지만, 서로 다른 컴파일러·버전으로 빌드된 두 프로그램 사이에서는 더 근본적이다. 클래스의 메모리 레이아웃(필드 순서, 패딩, vtable 배치)을 정확히 어떻게 배치할지는 표준이 강제하지 않는 ABI(응용 이진 인터페이스, application binary interface — 컴파일된 바이너리끼리 서로 호출·전달할 때 지키는 저수준 약속)의 영역이라, 컴파일러나 버전이 바뀌면 같은 소스 코드도 다른 메모리 표현을 만들어 낼 수 있다. memcpy로 만든 바이트는 이식 가능한 직렬화 포맷이 아니라, "이 컴파일러가 지금 이 순간 만든 ABI"에 종속된 바이트일 뿐이다.

C++ 관점의 통찰: 이 예제는 직렬화의 정의를 역으로 증명한다 — 직렬화란 "메모리 표현(주소·패딩·정렬·엔디언·ABI가 얽힌, 이 컴파일러·이 기계만의 사정)"을 "플랫폼 중립적인 값의 표현"으로 옮기는 번역이다. 리플렉션이 없는 C++에서는 이 번역을 컴파일 타임에 사람이 직접 코드로 새겨 넣어야 하지만, 다른 언어에서는 런타임이 메모리 표현을 감춰 주기에 번역이 항상 일어나고 있다는 사실 자체를 잊기 쉽다.

7. 함께 알면 좋은 것

  • DTO(전송용 객체) 분리 — 도메인 객체와 직렬화 대상 객체를 분리하면, 내부 리팩터링이 외부 계약(필드 이름·구조)을 건드리지 않게 격리된다. 순환 참조·과다 노출 문제의 예방책이기도 하다.
  • IDL(interface definition language) — Protobuf의 .proto처럼 스키마를 언어 중립 파일로 정의하고 각 언어 코드를 생성하는 방식. "계약을 코드보다 앞에 두는" 사고방식의 도구다.
  • 문자 인코딩 — 텍스트 포맷도 결국 바이트가 되려면 인코딩(사실상 UTF-8)을 거친다. "문자열 ↔ 바이트"는 직렬화의 최하층이며, 인코딩 불일치는 한글 깨짐의 고전적 원인이다.
  • API 버저닝 전략 — 스키마 진화 원칙의 API 차원 확장. 호환 규칙으로 버티는 범위와, 버전을 갈라야 하는 파괴적 변경의 경계를 다룬다.
  • 스키마 레지스트리(schema registry) — 메시지 큐 환경에서 스키마 버전들을 중앙 관리하고 호환성 규칙 위반을 등록 시점에 차단하는 장치. 스키마 진화를 "관례"에서 "시스템"으로 격상시킨다.

8. 한 장 요약

  • 직렬화 = 주소로 얽힌 객체 그래프를 값만의 바이트 나열로 평탄화, 역직렬화 = 그 바이트로 새 객체를 재조립. 복원물은 "같은 값의 새 객체"다.
  • 포맷은 트레이드오프: 텍스트·자기 기술(가독성·범용) vs 바이너리·스키마 기반(효율·계약) vs 네이티브(편리하나 폐쇄적·위험).
  • 쓴 코드와 읽는 코드의 버전은 반드시 어긋난다 — 후방(새 코드↔옛 데이터)·전방(옛 코드↔새 데이터) 호환을 함께 챙기는 것이 스키마 진화.
  • 변경 규칙: 추가는 선택적+기본값, 모르는 필드는 관용(중계 시 보존), 삭제는 단계적, 타입·의미 변경은 사실상 삭제+추가.
  • 역직렬화는 신뢰 경계 — 파싱 성공 ≠ 유효한 데이터이며, 신뢰할 수 없는 입력에 네이티브 직렬화는 금지.
  • 직렬화는 암호화가 아니고, JSON 큰 정수는 조용히 깨질 수 있으며, 직렬화 필드 이름 변경은 리팩터링이 아니라 계약 파기다.

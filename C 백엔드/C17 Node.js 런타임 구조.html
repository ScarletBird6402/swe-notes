C17 Node.js 런타임 구조

0. 한눈에 보는 결론

  • Node.js = V8(자바스크립트 엔진) + libuv(이벤트 루프·비동기 I/O 라이브러리) + 표준 라이브러리. "브라우저 밖에서 JS를 돌리는 서버 런타임"의 실체가 이 조합이다.
  • "싱글 스레드"의 정확한 뜻: 내 자바스크립트 코드를 실행하는 스레드가 하나라는 것이지, Node 프로세스에 스레드가 하나라는 뜻이 아니다. 뒤에는 libuv의 워커 스레드 풀과 V8 내부 스레드들이 있다.
  • 적은 스레드로 많은 동시 접속을 처리하는 비결은 논블로킹 I/O — "기다리지 말고 다른 일을 하다가, 준비되면 통지받는다". 네트워크 I/O는 OS의 이벤트 통지 기능(epoll 등)으로, 파일 I/O 등은 스레드 풀로 처리된다.
  • 이벤트 루프는 단계(phase)를 도는 반복문이다: 타이머 → 폴링(I/O 대기·콜백 실행) → setImmediate → … 이 한 바퀴가 계속 돈다. 각 콜백 사이마다 마이크로태스크(Promise·process.nextTick)가 끼어들어 먼저 소진된다.
  • 치명적 약점은 대칭적이다: JS 스레드가 하나이므로, 콜백 하나가 오래 계산하면(CPU 바운드) 서버 전체가 멈춘다. I/O 대기는 공짜지만 계산은 공짜가 아니다.
  • CPU 바운드 작업의 탈출구는 worker_threads(스레드), cluster/멀티 프로세스(코어 수만큼 복제)다.

1. Node.js의 3층 구조 — V8, libuv, 그리고 그 사이

자바스크립트 언어 자체에는 파일을 읽거나 소켓을 여는 기능이 없다. 브라우저에서 그 일을 브라우저(웹 API)가 해 주듯, 서버에서는 Node.js 런타임이 해 준다. 구조는 세 층이다.

┌────────────────────────────────────────────┐ │ 내 JS 코드 + Node 표준 라이브러리(fs, http, …) │ ← 개발자가 보는 층 ├────────────────────────────────────────────┤ │ V8: JS 해석·JIT 컴파일·메모리(힙) 관리 │ ← "JS를 실행"하는 층 ├────────────────────────────────────────────┤ │ libuv: 이벤트 루프·논블로킹 I/O·스레드 풀 (C 라이브러리) │ ← "기다림을 관리"하는 층 └────────────────────────────────────────────┘ ↕ OS (epoll / kqueue / IOCP, 파일시스템, 소켓)

역할 분담이 요점이다. V8은 계산을, libuv는 기다림을 담당한다. fs.readFile()을 호출하면 JS에서는 함수 호출 한 번이지만, 실제로는 "libuv에 작업을 접수하고 즉시 반환 → libuv가 OS와 협업해 완료 → 완료 통지가 이벤트 루프를 통해 콜백으로 돌아옴"이라는 왕복이 일어난다. 비동기 프로그래밍의 개념 원론(콜백·Promise·async/await·이벤트 루프 일반론)은 G3 비동기 프로그래밍 모델.html에서 다루며, 이 문서는 그것의 Node 구현을 다룬다.

2. "싱글 스레드"의 실체

1절 그림의 세 층 가운데 먼저 V8 층 — "JS를 실행한다"는 부분 — 을 확대해 보자. Node가 싱글 스레드라는 말은 이 층에 대해서만, 그것도 절반만 맞다. 정확히는 다음과 같다.

  • JS 실행 스레드(메인 스레드)는 하나 — 내 코드의 어떤 두 줄도 동시에 실행되지 않는다. 콜백은 항상 하나씩, 끝까지(run-to-completion) 실행된다.
  • 그 뒤에 libuv 워커 스레드 풀(기본 4개, UV_THREADPOOL_SIZE 환경변수로 조절)이 파일 I/O·DNS 조회·암호화 같은 "논블로킹 API가 없는 작업"을 대신 수행한다.
  • V8도 가비지 컬렉션·JIT 최적화용 보조 스레드를 따로 굴린다.

이 구조의 실용적 의미: 공유 상태에 락이 필요 없다. 두 요청의 핸들러가 같은 변수를 건드려도 동시에 실행되지 않으므로 경쟁 조건(race condition)의 상당 부분이 원천 차단된다 (멀티스레드 언어에서 이것이 왜 큰 문제인지는 G1 스레드 안전성 기초.html 참조). 대신 대가로, 메인 스레드의 1초는 서버 전체의 1초가 된다 — 아래 6절.

Java 개발자를 위한 대응 관계: 전통적 Java 서블릿 컨테이너는 "요청 1개 = 스레드 1개"로, 스레드가 DB 응답을 블로킹 대기한다. 동시 접속 1만이면 스레드 1만 개가 필요해 메모리·컨텍스트 스위치 비용이 폭발한다. Node는 "요청 1만 개 = JS 스레드 1개 + 대기 중인 소켓 1만 개"로, 기다림을 스레드가 아닌 이벤트 목록으로 관리한다. (프로세스·스레드·컨텍스트 스위치의 기초는 V1 프로세스와 스레드.html.)

3. 논블로킹 I/O — "기다리지 않는다"의 두 가지 구현

"기다림을 스레드가 아닌 이벤트 목록으로 관리한다"(2절)가 성립하려면, 애초에 스레드가 기다리며 멈추는 일이 없어야 한다. 이제 libuv 층으로 내려가 그 구현을 보자. 블로킹 I/O는 "다 될 때까지 이 스레드는 여기서 멈춤"이고, 논블로킹 I/O는 "접수만 하고 즉시 반환, 완료는 나중에 통지"다. libuv는 작업 종류에 따라 두 가지 방법으로 이를 구현한다.

작업 종류구현 방법동작
네트워크 I/O (소켓 — HTTP, DB 연결 등) OS의 이벤트 통지 기능
(Linux epoll / macOS kqueue / Windows IOCP)		 수천 개 소켓을 OS에 등록해 두고 "준비된 것 있으면 알려 달라"고 한 번에 묻는다. 스레드 소비 0 — 진짜 논블로킹
파일 I/O·DNS·CPU성 내장 작업 (fs, dns.lookup, crypto의 일부, zlib) libuv 워커 스레드 풀(기본 4개) OS 파일 API는 통지형 인터페이스가 마땅치 않아, 워커 스레드가 대신 블로킹하고 끝나면 메인에 통지 — "블로킹의 외주화"

스레드 풀 4개의 함정: 파일 읽기나 crypto.pbkdf2(비밀번호 해싱) 같은 작업을 동시에 5개 이상 던지면 5번째부터는 풀이 빌 때까지 큐에서 대기한다. "논블로킹인데 왜 느리지?"의 흔한 정체다. 네트워크 I/O는 이 제한과 무관하다는 점이 핵심 구분이다.

4. 이벤트 루프 — libuv의 단계(phase) 순환

3절에서 "접수만 하고 즉시 반환"한 작업들의 완료 통지는, 그럼 어떻게 내 콜백 호출로 되돌아오는가? 그 배달을 맡는 장치가 이벤트 루프다 — 신비한 무언가가 아니라 C로 짠 while 루프다. 한 바퀴(tick)마다 정해진 단계를 순서대로 방문하며, 각 단계의 큐에 쌓인 콜백을 실행한다.

┌─> ① timers : 시간이 된 setTimeout / setInterval 콜백 │ ② pending : 일부 지연된 시스템 콜백 │ ③ poll : ★ I/O 완료 통지 수거·콜백 실행. 할 일 없으면 여기서 대기 │ ④ check : setImmediate 콜백 └── ⑤ close : 소켓 close 등 정리 콜백 ※ 각 콜백이 끝날 때마다: process.nextTick 큐 → Promise(마이크로태스크) 큐를 전부 비운 뒤에야 다음 콜백으로 진행

기억할 것은 세 가지다.

  • poll 단계가 심장이다. 대부분의 시간을 여기서 보내며, OS에 "준비된 I/O 있나"를 묻고(epoll 대기) 도착한 완료 통지의 콜백을 실행한다. 다음 타이머 만기가 가까우면 그만큼만 기다렸다가 ①로 돌아간다.
  • 마이크로태스크는 새치기 줄이다. await 다음 줄, .then() 콜백은 이벤트 루프 단계 사이가 아니라 지금 실행 중인 콜백이 끝나는 즉시 처리된다. process.nextTick은 그보다도 먼저다.
  • setTimeout(fn, 0)도 최소 한 바퀴 뒤다. "0ms"는 "즉시"가 아니라 "다음 timers 단계에"라는 뜻이다.
console.log('A');                          // 1: 동기
setTimeout(() => console.log('B'), 0);     // 4: 다음 바퀴 timers 단계
Promise.resolve().then(() => console.log('C')); // 3: 현재 콜백 직후 마이크로태스크
console.log('D');                          // 2: 동기
// 출력: A D C B — "Promise가 setTimeout보다 항상 먼저"의 이유

브라우저와의 관계: 이벤트 루프라는 개념은 브라우저에도 있지만(B2 브라우저 이벤트 루프.html), 구현이 다르다. 브라우저는 렌더링(화면 갱신)과의 조율이 중심이고 Node(libuv)는 I/O 단계 순환이 중심이다. "마이크로태스크가 태스크 사이에 끼어든다"는 규칙은 양쪽 공통이다.

5. 하나로 모자랄 때 — worker_threads와 cluster

여기까지의 구조는 전부 "JS 스레드 하나 + 루프 하나" 위의 이야기였다. 이 구도가 감당 못 하는 두 상황 — 계산이 무겁거나, 코어가 남아돌거나 — 을 위해 Node는 공식 탈출구를 제공한다.

도구무엇언제
worker_threads JS 실행 스레드를 추가로 띄움. 메모리는 기본 격리, 메시지로 통신 이미지 처리·대형 JSON 파싱·암호화 등 CPU 바운드 작업을 메인에서 격리할 때
cluster / 멀티 프로세스 Node 프로세스를 CPU 코어 수만큼 복제, 같은 포트를 나눠 받음 멀티코어 서버에서 처리량을 코어만큼 확장할 때(프로세스 매니저·컨테이너 오케스트레이션으로 대체되기도)
child_process 외부 프로그램 실행(쉘 명령 등) Node 밖의 도구를 부릴 때

구분 감각: I/O가 많다 → 기본 구조로 충분(이벤트 루프가 설계상 그 용도), 계산이 많다 → worker_threads, 코어를 다 쓰고 싶다 → 프로세스 복제. 프로세스 복제 시에는 프로세스 간 메모리가 격리되므로 인메모리 세션 같은 공유 상태가 깨진다는 점을 함께 설계해야 한다.

6. CPU 바운드가 루프를 막는다 — 진단과 방어

탈출구가 마련되어 있다는 것은 뒤집으면, 탈출시키지 않은 무거운 계산이 메인에 남아 있으면 안 된다는 뜻이다. Node의 모든 강점은 "메인 스레드가 항상 빨리 루프로 복귀한다"는 전제 위에 서 있다. 콜백 하나가 3초짜리 반복문을 돌면, 그 3초 동안 타이머도, 새 요청 수락도, 진행 중이던 다른 응답도 전부 정지한다. 동시 접속 1만의 서버라면 1만 명이 함께 멈춘다. 

app.get('/report', (req, res) => {
  const result = heavyAggregation(bigData);  // 3초 동안 동기 계산
  res.json(result);
});
// 이 3초 동안 /health 조차 응답 불가 → 로드밸런서가 인스턴스를 죽었다고 판단할 수도
  • 진단: 이벤트 루프 지연(event loop lag — "1ms 뒤에 실행해 달라"고 한 타이머가 실제로 얼마나 늦게 실행되는지) 지표를 모니터링한다. 지연이 수백 ms면 어딘가에서 동기 작업이 루프를 잡고 있다는 뜻이다.
  • 방어: 큰 계산은 worker_threads로 격리, 큰 배열 처리는 청크로 쪼개 사이사이 루프에 양보, JSON.parse할 대상의 크기 상한 설정, fs.readFileSync 등 *Sync API를 요청 처리 경로에서 금지.

7. 흔히 헷갈리는 지점

① "async를 붙이면 병렬로 실행된다"? — 아니다. async/await는 기다림을 양보하게 할 뿐, JS 코드 실행은 여전히 한 번에 하나다. 동시에 진행되는 것은 I/O 대기이지 계산이 아니다. CPU 작업에 async를 붙여도 루프는 똑같이 막힌다.

② "논블로킹이니까 뭘 해도 안 막힌다"? — 논블로킹은 I/O의 성질이다. 동기 계산, *Sync API, 거대한 JSON.stringify는 그대로 막는다.

③ process.nextTick 남용 — nextTick 큐는 이벤트 루프 진행보다 항상 먼저 완전히 비워진다. nextTick 안에서 다시 nextTick을 예약하는 재귀는 I/O를 영원히 굶긴다(starvation). 지연 실행 의도라면 setImmediate가 안전한 선택이다.

④ "스레드가 없으니 동시성 버그도 없다"? — 락 경쟁은 없지만, await 지점마다 다른 콜백이 끼어들 수 있다. "읽고-await-쓰기" 사이에 다른 요청이 같은 값을 바꾸는 논리적 경쟁은 여전히 존재한다. 스레드 안전성과는 다른 층위의, 그러나 실재하는 문제다.

★ 8. 언어별 대조

"동시 접속을 무엇으로 감당하는가"라는 질문에 각 언어 생태계가 내놓은 답을 나란히 놓으면, Node의 선택이 여러 답 중 하나임이 보인다. 축은 두 개다 — 대기를 스레드로 감당하는가, 이벤트로 감당하는가. 그리고 그 답이 "왜 그 언어에서는 그렇게 나왔는가"는 언어의 내부 기제(스레드 모델·인터프리터 락·메모리 관리)로 설명된다.

언어전통적 모델이벤트/비동기 모델그 답이 나온 내부 이유
Java 요청당 스레드(서블릿) — 블로킹 I/O를 스레드 수로 감당 Netty·리액티브 스택(이벤트 루프), 가상 스레드(스레드 자체를 싸게) OS 스레드가 진짜 병렬이라 "스레드를 더 싸게"가 가능한 선택지였다
JS·TS — (처음부터 단일 스레드) 이벤트 루프가 유일한 모델. 브라우저와 Node가 구현만 다름 언어에 스레드·락이 없다. 런타임이 루프를 돌리고 코드는 콜백·await로 양보
Python 스레드는 있으나 GIL로 CPU 병렬 불가 — 사실상 I/O용 asyncio — 이벤트 루프 + async/await, Node와 가장 유사 어차피 계산 병렬이 안 되니 I/O 동시성만 루프로 얻는 것이 합리적
C++ 스레드·프로세스 직접 관리 epoll/io_uring 직접 사용, Boost.Asio, C++20 코루틴 런타임이 없다 — libuv가 감춘 층(OS 통지·객체 수명)을 직접 다룬다

8.1 Java — "스레드를 안 쓴다"의 반대편, "스레드를 싸게 만든다"

2절의 정보 상자에서 본 대응 관계를 구조로 펼쳐 보자. 전통적 Java 서버는 요청마다 스레드 풀에서 스레드 하나를 꺼내 주고, 그 스레드가 데이터베이스 응답을 블로킹 대기한다. 대기 중인 스레드는 CPU를 쓰지 않지만 스택 메모리(스레드당 보통 수백 KB~1MB)와 OS 스케줄러의 자리를 점유하므로, 동시 처리량은 "스레드 풀 크기"라는 숫자로 못 박힌다.

요청당 스레드(Java 전통) 이벤트 루프(Node) ────────────────────── ────────────────────── 스레드1 ──[DB 대기…]── 응답 JS 스레드 1개 ──┐ 스레드2 ──[DB 대기…]── 응답 ├─ 소켓 1만 개를 epoll에 등록 스레드3 ──[DB 대기…]── 응답 │ 준비된 것만 콜백으로 …(풀 크기만큼) ┘ 대기 = 스레드가 잠듦(자리 점유) 대기 = 이벤트 목록의 항목 하나(자리 없음)

Java 생태계는 이 한계에 두 번 답했다. 첫 번째 답은 Node와 같은 방향이다 — NIO(java.nio의 셀렉터, Linux에서는 결국 epoll)를 바탕으로 한 Netty나 리액티브 스택이 이벤트 루프 스레드 몇 개로 소켓 수만 개를 다룬다. 대가도 Node와 같다: 루프 스레드에서 블로킹하면 안 되므로 코드 전체가 콜백·리액티브 연산자 체인으로 바뀌어야 하고, 블로킹 라이브러리(전통적인 데이터베이스 드라이버 등) 하나가 섞이면 루프가 막힌다.

두 번째 답은 반대 방향이다. 가상 스레드(virtual thread — JVM이 스택을 힙에 두고 직접 스케줄링하는 경량 스레드. 블로킹 호출을 만나면 그 스택을 떼어 보관하고, 실제로 실행을 담당하던 OS 스레드(캐리어)를 다른 가상 스레드에게 넘긴다)는 "스레드는 비싸다"는 전제 자체를 무너뜨린다. 코드는 요청당 스레드 모양 그대로 블로킹 호출을 쓰는데, JVM이 뒤에서 "대기 중인 것을 스레드에서 떼어 내고 준비되면 다시 붙이는" 일 — 즉 libuv가 하는 일 — 을 대신한다. 

// 전통: 고정 스레드 풀 — 동시 처리량 ≒ 200. 대기 중에도 스레드가 자리를 점유
ExecutorService pool = Executors.newFixedThreadPool(200);
pool.submit(() -> {
    String body = db.query(sql);     // 블로킹: 이 OS 스레드는 응답이 올 때까지 잠든다
    respond(body);
});

// 가상 스레드(Java 21 이후): 코드는 블로킹 그대로, 스레드만 싸졌다
ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor();
vt.submit(() -> {
    String body = db.query(sql);     // 블로킹처럼 보이지만 캐리어 스레드를 반납하고 대기
    respond(body);                   // 준비되면 아무 캐리어에서나 이어서 실행
});

Node와 견주면 위치가 선명하다. Node의 await는 "여기서 루프에 양보한다"를 개발자가 코드에 표시하는 방식이고, 가상 스레드는 그 양보 지점을 JVM이 블로킹 호출 안에서 알아서 처리하는 방식이다. 결과적으로 얻는 것은 같다 — 대기 하나가 스레드 하나를 소비하지 않는다. 다만 6절의 약점은 Java에 없다: 캐리어가 코어 수만큼 있어 CPU 계산 하나가 서버 전체를 세우지 않는다. 대신 2절에서 Node가 공짜로 얻은 "락 불필요"는 사라져, 공유 상태에는 여전히 동기화가 필요하다.

Java 관점의 통찰(JVM 기제와 시점): 가상 스레드는 2020년대 중반 기준으로 Java 21(2023)에서 정식 기능이 되었고, 초기에는 synchronized 블록 안에서 블로킹하면 캐리어를 반납하지 못하는 고정(pinning) 문제가 있었으나 Java 24(2025)에서 JVM의 모니터 구현이 바뀌어 해소되었다. 요점은 "스레드가 싸졌다"가 스레드 풀 크기 튜닝을 없앨 뿐, 루프 자체가 있는 Node와 달리 구조가 바뀌지는 않는다는 것 — 블로킹 코드를 그대로 두고 처리량만 얻는 선택이다.

8.2 JS·TS — 단계 순서를 코드로 확인하기, 그리고 TS가 관여하지 않는 이유

JS에는 스레드도 락도 언어 차원에 없으므로 이벤트 루프가 유일한 모델이고, 이 문서 전체가 그 설명이었다. 여기서는 4절의 단계 그림이 정말 그 순서로 도는지를 코드로 확인한다. 핵심은 "지금 내가 어느 단계의 콜백 안에 있는가"가 다음에 무엇이 실행될지를 결정한다는 점이다. 

const fs = require('fs');

fs.readFile(__filename, () => {                    // ③ poll 단계에서 실행되는 I/O 콜백
  setTimeout(() => console.log('timeout'), 0);     // → 다음 바퀴 ① timers 에 예약
  setImmediate(() => console.log('immediate'));    // → 이번 바퀴 ④ check 에 예약
  process.nextTick(() => console.log('nextTick')); // → 이 콜백이 끝나는 즉시 (1순위)
  Promise.resolve().then(() => console.log('promise')); // → 그 다음 (마이크로태스크)
  console.log('sync');
});
// 출력: sync → nextTick → promise → immediate → timeout
// poll(③) 안에서 예약했으므로 check(④)가 timers(①)보다 먼저 온다 — 항상 결정적

같은 두 줄(setTimeout(…, 0)과 setImmediate)을 I/O 콜백 밖, 즉 스크립트 최상위에 쓰면 순서가 실행마다 달라진다. 최상위 코드가 끝나고 루프가 ①로 들어갈 때 1ms 타이머가 이미 만기됐는지가 그 순간의 시스템 시각에 달려 있기 때문이다. "I/O 콜백 안에서는 setImmediate가 항상 먼저"라는 규칙이 지연 실행을 예약할 때 setImmediate를 고르는 이유다. 마이크로태스크 두 줄의 순서(nextTick → Promise)는 Node가 두 개의 큐를 별도로 두고 nextTick 큐를 먼저 완전히 비운 뒤 Promise 큐로 넘어가기 때문이며, 7절 ③의 굶김 문제도 여기서 나온다. 2020년대 중반의 Node는 타이머·setImmediate 콜백 하나하나 사이마다 이 두 큐를 비운다(브라우저와 같은 규칙 — 초기 Node는 단계 전체가 끝난 뒤 비웠다).

엔진 쪽 기제 하나만 더 보자. 콜백이 나중에 불릴 때 참조하는 변수(요청 객체, 응답 객체)는 클로저가 붙잡고 있고, V8의 가비지 컬렉터가 그 참조를 보고 살려 둔다. 그래서 "비동기 작업의 완료 시점까지 객체를 살려 두기"라는 문제가 JS에서는 아예 등장하지 않는다 — 8.4의 C++이 이 문제를 어떻게 손으로 푸는지와 대조된다.

TS는 이 절의 어느 것도 바꾸지 않는다. TS의 타입은 컴파일 시 지워지며(타입 소거 — 출력된 JS에는 타입 정보가 한 글자도 남지 않는다), 이벤트 루프·마이크로태스크 큐·스레드 풀은 전부 런타임(Node)의 것이다. async function f(): Promise<Data>라는 서명은 "f는 호출 즉시 Promise를 돌려주고 본문의 await 지점에서 루프에 양보한다"는 사실을 타입으로 적어 둔 것일 뿐, 양보의 시점과 순서는 JS와 완전히 같다. 컴파일 대상(target)을 낮추면 async/await가 제너레이터 기반 코드로 변환되기도 하지만 실행 순서는 보존된다.

JS·TS 관점의 통찰: 타입이 잡아 주지 못하는 것이 정확히 이 문서의 주제다. 6절의 3초짜리 동기 계산도, 7절 ④의 "읽고-await-쓰기" 사이 끼어들기도 타입 검사는 통과한다. TS가 보장하는 것은 값의 모양이고, 루프를 막지 않는 것과 양보 지점의 안전은 여전히 개발자의 몫이다.

8.3 Python — asyncio는 Node의 평행 세계, 그리고 GIL이라는 이유

Python에도 진짜 OS 스레드가 있는데 왜 이벤트 루프를 따로 만들었을까? 답은 GIL(global interpreter lock, 전역 인터프리터 락 — 인터프리터가 한 번에 하나의 스레드만 바이트코드를 실행하도록 붙잡는 잠금 장치)이다. 스레드를 여럿 띄워도 CPU 계산은 병렬이 되지 않으므로, "그럴 바에는 I/O 동시성만 깔끔하게 얻자"는 결론이 asyncio이고 이는 Node의 설계 논리와 정확히 같다. 다만 도달 경로가 다르다 — Node는 "스레드가 하나라서", Python은 "스레드는 있지만 락이 병렬을 막아서"다. 

import asyncio

async def handler(n):
    print(f"{n} 시작")
    await asyncio.sleep(1)        # ← Node의 await와 동일: 여기서 루프에 양보
    print(f"{n} 끝")

async def main():
    # 셋이 "동시에" 진행된다 — 스레드가 아니라 대기가 겹치는 것
    await asyncio.gather(handler(1), handler(2), handler(3))

    # Node의 libuv 스레드 풀에 해당: 블로킹 함수를 워커 스레드로 외주
    loop = asyncio.get_running_loop()
    data = await loop.run_in_executor(None, blocking_read, "big.bin")

asyncio.run(main())               # Node와 다른 점: 루프를 명시적으로 기동한다
# 전체 소요 약 1초. 단, time.sleep(1)(동기 대기)로 바꾸면 3초 — 루프가 막힌다

구조 대응이 거의 1:1이다. asyncio.run이 루프를 만들고(Node는 프로세스가 곧 루프), await가 양보 지점이며, run_in_executor가 3절의 "블로킹의 외주화"에 해당한다. 차이는 인터프리터가 코루틴을 제너레이터의 확장으로 구현한다는 점이다 — async def 함수는 호출해도 실행되지 않고 코루틴 객체를 돌려주며, 루프가 send()로 한 단계씩 진행시킨다. Node에서 "async 함수는 첫 await까지 동기로 실행된다"와 달리, Python의 코루틴은 await나 gather로 루프에 넘기기 전에는 한 줄도 실행되지 않는다 — 호출만 하고 await를 잊으면 아무 일도 없이 경고만 남는 이유다.

Python 관점의 통찰: 코드의 마지막 주석이 6절(CPU 바운드가 루프를 막는다)의 재현 실험이다. time.sleep은 스레드를 통째로 재우므로 루프가 정지하고, asyncio.sleep은 루프에 제어를 돌려준다 — Node에서 *Sync API를 요청 경로에서 금지하는 이유와 같은 구조다.
탈출구도 평행하다: CPU 병렬이 필요하면 Python은 multiprocessing(GIL이 프로세스마다 따로 있으므로), Node는 worker_threads·프로세스 복제로 간다. 다만 이 전제는 움직이고 있다 — 2020년대 중반 기준으로 GIL을 제거한 자유 스레드 빌드(free-threaded build)가 Python 3.13(2024)에서 실험 도입, 3.14(2025)에서 정식 지원 단계에 들어섰으나 아직 기본 빌드는 아니다. GIL이 사라지면 "스레드가 있는데도 루프를 쓴 이유"의 절반이 약해지지만, I/O 동시성을 스레드보다 싸게 얻는다는 나머지 절반은 그대로 남는다.

8.4 C++ — libuv가 감춘 층을 맨손으로 보기

이벤트 루프의 poll 단계(4절)가 실제로 무엇을 하는지는, libuv가 내부에서 호출하는 OS 기능을 직접 써 보면 원형 그대로 드러난다. libuv 자체가 C로 짜인 라이브러리이므로 아래 코드는 비유가 아니라 Node가 실제로 하는 일의 축약본이다. Linux의 epoll은 "관심 있는 소켓들을 커널에 등록해 두고, 준비된 것들의 목록을 한 번에 받아 오는" 장치다. 

int ep = epoll_create1(0);

struct epoll_event ev{};
ev.events = EPOLLIN;              // "읽을 데이터가 생기면 알려 달라"
ev.data.fd = client_fd;
epoll_ctl(ep, EPOLL_CTL_ADD, client_fd, &ev);   // 소켓 수천 개를 이렇게 등록

struct epoll_event events[64];
while (true) {                                   // ← 이것이 "이벤트 루프"의 정체
    int n = epoll_wait(ep, events, 64, timeout_ms);  // 준비된 것 없으면 여기서 잠듦
    for (int i = 0; i < n; ++i) {                    // 준비된 것만 골라서
        handle(events[i].data.fd);                   // 콜백에 해당하는 처리
    }
}

4절 그림과 대응시키면 epoll_wait의 timeout_ms가 "다음 타이머 만기까지만 기다린다"이고, for 루프가 poll 단계의 콜백 실행이다. timers·check 같은 다른 단계는 이 while 앞뒤에 "만기된 타이머 목록 처리"·"immediate 목록 처리"를 끼워 넣은 것에 지나지 않는다. Node가 C++ 개발자에게 낯설지 않은 이유이자, 반대로 C++에는 이 루프를 대신 돌려 주는 런타임이 없다는 사실이 드러나는 지점이다 — Boost.Asio 같은 라이브러리를 쓰거나, C++20 코루틴(co_await — 컴파일러가 함수를 중단·재개 가능한 상태 기계로 변환해 주는 문법. 단, 그 재개를 언제 누가 할지는 여전히 라이브러리 몫)으로 await와 닮은 문법을 얻더라도, 스케줄러와 루프는 직접 고르고 조립해야 한다.

C++ 관점의 통찰(메모리·수명): 위 코드에서 ev.data에는 보통 fd 대신 연결 상태 객체의 포인터를 실어 둔다. 그러면 곧바로 수명 문제가 생긴다 — 연결이 끊겨 객체를 해제했는데 이미 커널에 등록된 이벤트가 나중에 도착하면, 해제된 메모리를 가리키는 포인터로 콜백이 불린다. 그래서 C++ 비동기 서버는 shared_ptr로 콜백 실행 동안 객체를 살려 두는 식의 수명 연장 장치를 반드시 갖춘다.
8.2에서 본 대로 Node에서 이 고민이 전혀 없는 이유가 여기서 선명해진다: 콜백이 참조하는 객체는 클로저가 붙잡고 있고 GC가 그 참조를 보고 살려 두므로, "콜백이 나중에 불린다"는 비동기의 본질적 위험을 런타임이 대신 감당해 주는 것이다. 편의의 정체가 곧 비용(GC 일시 정지, 그리고 6절과 같은 층위에서 루프를 잠깐 세우는 원인)의 정체이기도 하다.

  • 스트림(stream)과 백프레셔(backpressure) — 큰 데이터를 메모리에 다 올리지 않고 흘려보내는 Node의 핵심 추상화. 생산 속도 > 소비 속도일 때의 제어가 백프레셔다.
  • 이벤트 루프 지연 모니터링 — perf_hooks.monitorEventLoopDelay(). 운영에서 CPU 바운드 침입을 조기 발견하는 표준 지표.
  • V8 메모리 구조와 GC — 힙 상한, old/new space. "이벤트 루프는 한가한데 프로세스가 죽는" 유형의 문제는 이쪽이다.
  • libuv 문서의 단계 설명 — 본 문서의 단계 그림은 단순화본이다. pending/prepare 등 세부 단계는 공식 문서 기준으로 확인.

10. 한 장 요약

  • Node = V8(계산) + libuv(기다림). JS 실행 스레드는 하나, 뒤에 워커 풀(기본 4)이 있다.
  • 네트워크 I/O는 OS 이벤트 통지(epoll 등)로 스레드 소비 없이, 파일 I/O 등은 워커 풀이 대신 블로킹.
  • 이벤트 루프 = timers → poll(심장) → check(setImmediate)… 의 단계 순환. 마이크로태스크(Promise·nextTick)는 콜백 사이마다 새치기로 전부 소진.
  • 강점(락 없는 동시성, 접속 수만을 스레드 1개로)과 약점(콜백 하나의 긴 계산 = 서버 전체 정지)은 같은 설계의 양면.
  • CPU 바운드는 worker_threads로 격리, 코어 확장은 프로세스 복제로. *Sync API는 요청 경로에서 금지.

C11 마샬링과 타입 시그니처 매핑

0. 한눈에 보는 결론

  • 마샬링(marshalling)은 데이터를 경계(언어↔언어, 프로세스↔프로세스, 앱↔네트워크) 너머로 보낼 수 있는 형태로 꾸리는 일이다. 직렬화(C10)가 "바이트로 만드는 기술"이라면, 이 문서의 주제는 그 앞뒤 단계 — 서로 다른 타입 체계 사이의 대응(mapping) — 다.
  • 근본 문제: 언어들의 타입 체계는 1:1로 포개지지 않는다. Java의 long/int/BigDecimal 구분은 JSON에 오면 전부 number 하나로 뭉개지고, 받은 쪽은 자기 언어의 기본 타입으로 다시 추측한다.
  • 대표 함정(일반화 형태): JSON 역직렬화의 숫자 정규화로 인한 타입 정보 소실. ① 64비트 정수가 JS number(53비트 정밀도)를 넘어 끝자리가 조용히 바뀌고, ② 1.0이 파서를 거치며 1이 되어 정수/실수 경계가 사라지며, ③ 라운드트립(직렬화→역직렬화) 후 원래 타입으로 돌아오지 않는다. 셋 다 에러 없이 일어난다.
  • 컬렉션도 같은 운명이다: Set·Date·Enum은 JSON에 대응물이 없어 배열·문자열로 강등되고, 맵의 키는 문자열만 허용되며, null/부재/JS의 undefined 3형제는 언어마다 다르게 해석된다.
  • 처방의 원칙: 경계의 타입 대응을 우연에 맡기지 말고 명시적으로 고정한다 — DTO/스키마로 필드별 타입 선언, 정밀도가 중요한 큰 정수·금액은 문자열 또는 최소 단위 정수로, 날짜는 표준 문자열 형식으로 계약에 못박는다.

1. 마샬링 — 직렬화와 무엇이 다른가

C10은 "객체를 바이트열로, 바이트열을 객체로" 바꾸는 기술을 다뤘다. 그런데 실무 장애의 상당수는 바이트 변환 자체가 아니라 그 앞뒤에서 난다: 내 언어의 타입을 전송 형식의 타입으로 대응시키는 순간(보낼 때), 그리고 전송 형식의 타입을 상대 언어의 타입으로 복원 추측하는 순간(받을 때). 이 대응 작업 전체를 마샬링이라 부른다 (용어 관행은 6절에서 정리한다 — 문맥에 따라 직렬화와 섞여 쓰인다).

2. 근본 문제 — 타입 체계는 1:1로 포개지지 않는다

각 언어는 저마다의 역사와 목적으로 타입 체계를 설계했고, 전송 형식(특히 JSON)은 그중 최소 공통분모만 남겼다. 숫자 하나만 나란히 놓아도 격차가 보인다.

왼쪽의 풍부한 구분(크기·정수/실수·십진 정밀)이 가운데 기둥에서 number 하나로 합쳐진다. 합쳐진 것은 되돌릴 수 없다 — 받은 쪽은 "이 number가 원래 long이었는지 BigDecimal이었는지" 알 방법이 없고, 자기 언어의 관습대로 추측할 뿐이다. 이 비가역성이 다음 절의 함정을 만든다.

3. 함정 해부 — 숫자 정규화와 타입 소실

2절의 "합쳐지면 못 되돌린다"가 실제 사고로 나타나는 세 형태다. 공통점은 예외도 경고도 없이, 값이 그럴듯한 채로 틀린다는 것 — "동작은 하는데 결과가 이상한" 문제의 전형이라 K5의 계보에 속한다.

3.1 형태 ① — 큰 정수의 끝자리가 조용히 바뀐다

// 서버(Java): long id = 9007199254740993  (2^53 + 1, 64비트 정수로는 평범한 값)
// 응답 JSON:  {"id": 9007199254740993}

// 프론트(JS):
const obj = JSON.parse(response);
console.log(obj.id);          // 9007199254740992  ← 끝자리가 3에서 2로. 에러 없음.

JS의 number는 64비트 부동소수점이라 정수를 253(약 9천조)까지만 정확히 표현한다. 그 너머의 정수는 파싱 순간 가장 가까운 표현 가능한 값으로 반올림된다. DB 시퀀스·스노플레이크형 ID처럼 64비트를 꽉 채우는 값에서 "특정 데이터만 조회가 안 된다"(반올림된 ID로 재요청하므로) 같은 괴담형 버그가 여기서 나온다.

3.2 형태 ② — 정수/실수 경계가 사라진다

// 보낼 때: 1.0 (실수라는 의도)
JSON.stringify({ rate: 1.0 })   // '{"rate":1}'  ← 직렬화가 이미 .0을 지움

// 받은 쪽(언어별로 다른 추측):
// JS     : 1      (어차피 number 하나라 구분 개념 자체가 없음)
// Python : 1 (int) ← 원래 float였다는 정보는 소실
// Java   : 필드 타입이 double이면 1.0으로 복원되지만, Object/Map으로 받으면 Integer로

"1.0을 보냈는데 1이 왔다"는 값의 문제가 아니라(수학적으로 같다) 타입의 문제다. 받은 쪽이 Map<String, Object>·dict·동적 처리로 다루는 순간 "정수면 A 로직, 실수면 B 로직" 같은 분기, 타입 검사, 재직렬화 결과가 원본과 달라진다. 파서는 값을 자기 언어의 기본 타입으로 정규화할 뿐, 원래의 타입 의도를 운반해 주지 않는다.

3.3 형태 ③ — 라운드트립이 원형을 보존하지 않는다

Java 객체 ──직렬화──▶ JSON ──역직렬화──▶ JS 객체 ──직렬화──▶ JSON' ──역직렬화──▶ Java 객체' 기대: 객체' == 객체 현실: long은 반올림(①), 1.0은 1(②), BigDecimal 정밀도는 double로 절삭, Date는 문자열, Enum은 문자열, Set은 배열...

①②의 귀결이다. 경계를 왕복하는 데이터 — 프론트에서 받아 저장했다가 다시 보내는 폼, 시스템 간 중계 — 는 손상이 단계마다 누적된다. "원본과 재직렬화 결과의 diff가 0이어야 한다"는 라운드트립 테스트가 이 계열 함정의 유효한 검출기인 이유다.

세 형태의 공통 교훈: 손상은 역직렬화 "실패"가 아니라 역직렬화 "성공"의 얼굴로 온다. 그래서 이 함정은 예외 로그가 아니라 계약 설계(5절)로 막아야 한다.

4. 컬렉션·복합 타입 — 강등과 3형제

숫자에서 본 "최소 공통분모로의 강등"은 복합 타입에서 더 광범위하게 일어난다. JSON의 그릇은 배열과 객체 둘뿐이기 때문이다.

관찰: 표의 모든 행이 같은 문장으로 요약된다 — "전송 형식에 없는 개념은 표현과 함께 성질도 잃는다." 잃은 성질을 복원하는 책임은 자동으로 생기지 않으므로, 누군가(5절의 변환 계층)에게 명시적으로 배정되어야 한다.

5. 처방 — 경계의 타입을 우연에 맡기지 않는다

3·4절의 함정은 전부 "타입 대응을 파서의 기본 동작에 맡긴" 결과였다. 처방은 그 반대 방향 — 대응을 명시적 계약과 변환 계층으로 고정하는 것 — 이며, 구체적으로 네 가지다.

  • ① 경계 전용 DTO/스키마를 둔다. 내부 도메인 객체를 그대로 직렬화하지 않고, 경계용 타입(DTO, TS 인터페이스, 스키마 정의)을 따로 두어 필드마다 전송 표현을 선언한다. "이 필드는 문자열로 나간다"가 코드에 적혀 있으면 파서의 추측이 끼어들 자리가 없다. 스키마를 문서·검증과 연결하는 방법은 D11.
  • ② 정밀도가 중요한 수는 문자열로 보낸다. 64비트 ID·정밀 금액은 "9007199254740993"처럼 문자열로 — 3.1의 반올림이 원천 차단된다. 금액은 대안으로 최소 단위 정수(원·센트 단위 int)도 널리 쓰인다(53비트 안이면 안전). 어느 쪽이든 계약에 명시가 핵심.
  • ③ 날짜·시각은 표준 형식 문자열로 못박는다. 관례상 ISO 8601(예: 2026-07-16T09:00:00+09:00) + 타임존 포함. "epoch 숫자, 단 밀리초" 같은 선택도 가능하나 무엇이든 한 형식으로 통일하고 문서화한다.
  • ④ 변환은 경계 한 곳에서만 한다. 문자열↔BigDecimal, ISO 문자열↔Date 변환 코드가 비즈니스 로직 곳곳에 흩어지면 한 곳의 누락이 곧 버그다. 경계 계층(컨트롤러/클라이언트 어댑터)에서 변환을 끝내고, 내부에서는 내부 타입만 흐르게 한다.

6. 흔히 헷갈리는 지점

① "마샬링 = 직렬화 아닌가?" — 겹치는 용어가 맞고, 생태계마다 관행이 다르다(Go는 JSON 변환 함수 이름 자체가 Marshal이고, Java 전통에서는 원격 호출·XML 바인딩 문맥에서 마샬링을 썼다). 실무 요령은 용어 논쟁이 아니라 두 관심사의 구분이다 — 바이트로 만드는 기술(C10)과 타입을 대응시키는 규칙(이 문서). 어느 쪽 단어를 쓰든 후자를 잊는 것이 사고의 원인.

② "JSON은 타입이 있으니 타입이 보존된다"? — JSON의 타입은 6종(문자열·숫자·불리언·null·배열·객체)뿐이고 숫자에 정밀도 규정이 없다. "타입이 있다"와 "내 언어의 타입이 보존된다"는 전혀 다른 명제다(2절).

③ "TS 인터페이스로 받으니 안전하다"? — TS 타입은 컴파일 시점 표기일 뿐, JSON.parse 결과를 런타임에 검증하지 않는다. as UserDto는 확신의 표현이지 검사가 아니다. 런타임 검증은 스키마 검증 라이브러리 등 별도 장치의 몫.

④ "null이나 undefined나 없는 거나 그게 그거"? — 부분 수정 API에서 "null = 이 필드를 비워라, 부재 = 건드리지 마라"로 의미가 갈리는 순간 3형제 구분은 데이터 삭제 사고의 경계선이 된다(4절 표). JS의 undefined가 직렬화에서 필드째 사라진다는 사실은 이 구분을 프론트가 의도치 않게 조작할 수 있다는 뜻이다.

★ 7. 언어별 대조

같은 문서, 네 가지 결과 — 특히 첫 표 둘째 행에서 정확/부정확이 언어에 따라 갈린다는 점이 3.1 함정의 요약이고, 둘째 표는 그 갈림의 원인을 "선언을 읽는 시점"으로 정리한 것이다. 이제 언어별로 그 시점이 만드는 고유한 함정을 본다.

7.1 Java — 리플렉션이 선언을 읽는다, 선언이 없는 곳에서 추측이 되살아난다

Java의 JSON 바인딩 라이브러리(Jackson 계열이 대표)는 리플렉션 — 실행 중에 클래스의 필드·메서드·생성자 정보를 읽어 내는 기능 — 으로 대상 클래스를 훑는다. 필드명·getter·생성자 매개변수 이름을 JSON 키와 맞추고, 각 필드에 선언된 타입으로 토큰 원문을 직접 변환한다. long id면 숫자 토큰을 double을 거치지 않고 바로 long으로, BigDecimal price면 십진 표기 그대로 만든다. 그래서 Java끼리는 3절의 함정이 드러나지 않는다 — 선언이 있는 한, 파서는 추측하지 않는다.

문제는 선언이 없는 지점이다. 대상이 Object나 Map<String, Object>이면 파서는 값의 크기를 보고 Integer/Long/Double을 고른다 — 3.2절의 세계로 되돌아간다. 그리고 그보다 교묘한 지점이 제네릭 소거(type erasure — 컴파일러가 타입 검사를 마친 뒤 타입 인자를 바이트코드에서 지워, List<Long>이 런타임에는 그냥 List가 되는 것)다. 

// 대표 JSON 라이브러리(Jackson 계열)의 전형적 사용 — 대표 예시
record UserDto(long id, BigDecimal price, List<Long> ids) {}
String s = "{\"id\": 9007199254740993, \"price\": 19.99, \"ids\": [1, 2]}";
ObjectMapper mapper = new ObjectMapper();

// ① 선언이 있는 곳: 리플렉션이 필드 타입을 읽어 토큰 원문에서 바로 만든다
UserDto dto = mapper.readValue(s, UserDto.class);
dto.id();      // 9007199254740993  (정확 — double을 거치지 않음)
dto.price();   // 19.99 (BigDecimal — 원문 표기 보존)
dto.ids();     // [1, 2] — 필드 선언 List<Long>을 읽어 원소를 Long으로

// ② 선언이 없는 곳: 값의 크기로 추측한다
Map<String, Object> m = mapper.readValue(s, Map.class);
m.get("id");     // Long   (int 범위를 넘었으므로)
m.get("price");  // Double (십진 정밀도 소실 — 3.2절)
((List<?>) m.get("ids")).get(0);   // Integer — Long이 아니다

// ③ 소거의 함정: 로컬 변수의 제네릭은 런타임에 List일 뿐
List<Long> ids = mapper.readValue("[1, 2]", List.class);   // 경고만 뜨고 컴파일된다
long first = ids.get(0);   // ClassCastException: Integer cannot be cast to Long — 여기서 터진다

// 복원: 익명 하위 클래스를 만들어 타입 인자를 클래스 메타데이터에 남긴다
List<Long> ok = mapper.readValue("[1, 2]", new TypeReference<List<Long>>() {});

③이 작동하는 원리가 이 절의 핵심이다. 소거가 지우는 것은 객체의 타입 인자이지 선언의 타입 인자가 아니다 — 필드·메서드·상위 클래스 선언에 적힌 List<Long>은 클래스 메타데이터에 남고, 리플렉션으로 읽을 수 있다. 그래서 ①의 DTO 필드는 원소 타입을 정확히 복원하지만, 로컬 변수 ids의 타입 인자는 어디에도 남지 않아 파서는 List.class만 받는다. TypeReference는 상위 클래스 선언에 타입 인자를 적어 두기 위해 익명 하위 클래스를 만드는 트릭이다 — 지워지지 않는 자리에 선언을 옮겨 놓는 것이다.

Java 관점의 통찰(타입 시스템·생태계 관행): 리플렉션 바인딩은 "선언이 진실"인 방식이고, 3절의 함정은 선언이 없는 지점 — Object, 원시 컬렉션, 로컬 제네릭 — 에서만 되살아난다. 5절 ①(경계 DTO)은 Java에서 "선언 없는 지점을 없애라"로 번역되며, 웹 프레임워크(Spring MVC 계열)가 @RequestBody UserDto 같은 컨트롤러 매개변수 선언에 같은 바인딩을 적용하므로 메서드 시그니처가 곧 경계 계약이 된다. 동적 바인딩을 피할 수 없는 자리(범용 중계·로그)에서는 파서 설정 — 실수를 BigDecimal로, 정수를 Long으로 고정하는 옵션 — 이 Python의 parse_float에 해당하는 개입 지점이다. 마지막으로 Java 서버가 정확히 만든 long이 JS 프론트에서 반올림되는 3.1은 보내는 쪽 문제다 — 방어는 받는 쪽 코드가 아니라 @JsonSerialize(using = ToStringSerializer.class) 류로 문자열화하는 보내는 쪽 계약에 둔다.

7.2 JS·TS — 타입은 컴파일러 안에만 있다

JS에는 런타임 타입 선언이 없고, TS의 타입은 컴파일 시 소거된다 — 타입 검사를 마친 뒤 인터페이스·타입 주석·as를 모두 지운 순수 JS만 출력되는 것이다. 따라서 7.1의 "리플렉션이 선언을 읽는다"에 해당하는 단계가 존재하지 않는다. JSON.parse의 반환 타입은 any이고, any는 구조적 타이핑(structural typing — 이름이 아니라 멤버 구성으로 호환을 판정하는 방식)의 검사조차 건너뛰는 구멍이라 어떤 타입으로든 단언할 수 있다.

user.ts (작성) user.js (컴파일 출력 — 실제로 실행되는 것) interface UserDto { id: bigint; price: string } (인터페이스 — 사라짐) const u = JSON.parse(t) as UserDto; const u = JSON.parse(t); ▲ ▲ 컴파일러 안에서만 의미 런타임에 남는 것은 이것뿐 — 검사 0회

여기에 JSON 숫자가 number(64비트 부동소수점) 하나로 읽힌다는 3.1의 사실이 겹친다. BigInt가 있어도 JSON.parse는 쓰지 않고, JSON.stringify는 BigInt를 만나면 예외를 던진다. 종래의 reviver(파싱 후 값을 가공하는 콜백)로도 못 살린다 — 콜백이 호출될 때 값은 이미 반올림된 number이기 때문이다. 

interface UserDto { id: bigint; price: string }

// 이 단언은 런타임에 아무것도 검사하지 않는다 — as는 컴파일러에게 하는 약속일 뿐
const u = JSON.parse('{"id": 9007199254740993, "price": 19.99}') as UserDto;
typeof u.id;      // "number" — 선언은 bigint지만 실제는 반올림된 number
typeof u.price;   // "number" — 선언은 string. 아무도 막지 않았다

JSON.stringify({ id: 1n });   // TypeError: Do not know how to serialize a BigInt

// 자리 ①: 경계에서 런타임 스키마 검증 (zod 계열 라이브러리의 API 형태 — 대표 예시)
const User = z.object({
  id: z.string().transform(BigInt),   // 계약(5절 ②): 문자열로 받아 BigInt로
  price: z.string(),
});
type User = z.infer<typeof User>;     // 타입을 스키마에서 "도출" — 선언과 검사가 한 곳
const user = User.parse(JSON.parse(text));   // 어긋나면 여기서 예외 — 조용히 통과하지 않는다

// 자리 ②: 파서 훅의 원문 접근 (ECMAScript 2026 편입 — 지원 런타임에서만)
JSON.parse('{"id": 9007199254740993}', (key, value, ctx) =>
  key === 'id' ? BigInt(ctx.source) : value);   // 반올림 전 토큰 원문으로 복원

자리 ①이 6절 ③("TS 인터페이스로 받으니 안전하다"의 반박)의 실천형이다. 스키마 검증 라이브러리는 런타임 검사와 컴파일 타임 타입을 한 선언에서 함께 얻는 장치로, TS 생태계에서 5절 ①의 DTO 역할을 맡는다 — 인터페이스만 따로 두면 선언과 검사가 갈라져 한쪽만 고치는 사고가 난다. 자리 ②는 2020년대 중반 기준 최신 런타임(V8·WebKit 계열)에서만 쓸 수 있으므로 계약(문자열화)을 대체하지는 못하고, 계약을 바꿀 수 없는 상대와 마주쳤을 때의 탈출구다.

JS·TS 관점의 통찰(런타임·타입 소거): TS의 타입은 경계 안쪽에서만 참이다. as UserDto는 "여기부터 이 모양이라고 믿겠다"는 선언이며, 그 믿음은 JSON.parse가 돌려준 값과 무관하게 성립한다. 따라서 마샬링 경계에서 TS가 보증하는 것은 0이고, 믿음을 검사로 바꾸는 유일한 방법은 런타임에 실행되는 코드(스키마 검증)를 그 경계에 두는 것이다. 같은 이유로 JS가 3.1에서 유일하게 "부정확" 칸을 차지하는 것은 언어의 결함이 아니라 선언을 읽는 단계가 없는 언어에서 파서가 기본값(double)을 고를 수밖에 없기 때문이다 — 해결의 자리가 코드가 아니라 계약이라는 5절의 결론이 언어 차원에서 재확인된다.

7.3 Python — 정규화 규칙에 직접 개입하기

Python은 3절의 함정을 가장 잘 보여 주면서 동시에 가장 깔끔한 탈출구를 가진 언어다. int가 임의 정밀도 객체라 3.1(큰 정수 반올림)은 겪지 않지만, float는 C의 double을 감싼 객체라 십진 정밀도 문제는 그대로이고, 기본 바인딩 대상이 dict — 즉 7.1의 "선언 없는 지점"이 기본값 — 이라 3.2(정수/실수 경계)에도 그대로 노출된다. 대신 표준 라이브러리가 파서의 숫자 변환 규칙을 교체할 수 있는 훅을 제공한다. 

import json
from decimal import Decimal

s = '{"id": 9007199254740993, "price": 19.99, "rate": 1.0}'

# 기본 동작: price는 float가 되어 십진 정밀도가 사라진다
d1 = json.loads(s)
print(type(d1["id"]), d1["id"])        # <class 'int'> 9007199254740993  ← 정확(무제한 정수)
print(repr(d1["price"]))               # 19.99 → 내부적으로는 이진 부동소수점 근사값
print(type(d1["rate"]))                # <class 'float'> — 토큰에 '.'이 있어서. "1"로 왔다면 int

# 훅으로 정규화 규칙을 바꾼다: 실수를 Decimal로 받아 십진 정밀도 보존
d2 = json.loads(s, parse_float=Decimal)
print(repr(d2["price"]))               # Decimal('19.99')  ← 원문 표기 그대로 보존

# 내보낼 때도 대칭이 필요하다 (Decimal은 기본 인코더가 모른다)
json.dumps({"price": Decimal("19.99")}, default=str)   # {"price": "19.99"}

# 반대 방향의 함정: Python은 정확히 내보내지만 받는 쪽(JS)이 반올림한다
json.dumps({"id": 9007199254740993})   # {"id": 9007199254740993} — 계약(문자열화)은 여전히 필요

파서가 정수와 실수를 가르는 기준은 토큰 원문에 .이나 지수 표기가 있는가뿐이다. 그래서 보내는 쪽이 1.0을 1로 지워 보냈다면(3.2) Python 쪽에서는 어떤 훅으로도 되살릴 수 없다 — 훅은 "토큰을 무엇으로 만들 것인가"에 개입하는 것이지 잃어버린 토큰을 복원하지는 못한다. 선언을 두고 싶다면 데이터클래스 기반 검증 라이브러리(대표 예시: pydantic 계열)가 7.1의 DTO 역할을 하는데, 이때도 필드 타입 힌트는 런타임 검사 코드가 읽어야만 의미를 갖는다 — 타입 힌트 자체는 인터프리터가 강제하지 않는다는 점에서 JS·TS와 같은 편에 있고, 다만 힌트가 런타임 객체(__annotations__)로 남아 읽을 수는 있다는 점에서 Java와 같은 편에 있다.

Python 관점의 통찰(객체 모델): parse_float=Decimal 한 줄이 이 문서의 처방을 요약한다 — 파서의 기본 정규화는 "선택"이지 "사실"이 아니다. 금액을 float로 받으면 0.1 + 0.2가 정확히 0.3이 아닌 세계로 들어가고, 그 오차는 합산·비교를 거치며 누적된다. 정밀도가 중요한 값에 대해 "십진 표기를 그대로 들고 다니는 타입"으로 받는 것은, 5절 ②의 문자열 계약과 동일한 목적(원문 보존)을 언어 도구로 달성하는 방법이다.
대칭성에도 주의할 만하다: 들어올 때 Decimal로 받아도 나갈 때 규칙을 맞추지 않으면 인코더가 처리하지 못하거나 다시 float로 떨어진다. 3.3절의 라운드트립 문제는 입력·출력 양쪽의 규칙이 짝을 이룰 때만 해결된다. 그리고 Python이 큰 정수를 정확히 다룬다는 사실이 계약을 안전하게 만들지는 않는다 — 정확한 값을 내보내도 상대 언어가 반올림하면 사고는 상대 쪽에서 난다. 자기 언어의 정확성은 경계의 정확성이 아니다.

7.4 C++ — 복원은 추측이 아니라 선언이다

2절에서 본 "받은 쪽이 자기 언어의 관습대로 추측한다"는 문제를, C++ JSON 라이브러리들은 구조적으로 회피한다 — 꺼낼 때 타입을 개발자가 지정하게 만들기 때문이다. 추측할 여지 자체가 없어지는 대신, 지정을 틀리면 그 자리에서 드러난다. 7.1의 리플렉션이 런타임에 선언을 읽었다면, C++은 선언을 컴파일 타임에 읽는다 — 리플렉션이 없는 대신 템플릿이 그 역할을 한다. 

// nlohmann/json 계열의 전형적 사용 (대표 예시)
auto j = json::parse(R"({"id": 9007199254740993, "rate": 1.0, "price": "19.99"})");

auto id   = j["id"].get<int64_t>();     // ← "이것을 64비트 정수로 읽겠다"고 선언
auto rate = j["rate"].get<double>();    // ← "이것을 실수로 읽겠다"

// 선언을 틀리면 조용히 넘어가지 않는다
auto bad  = j["id"].get<int32_t>();     // 범위 초과 — 라이브러리에 따라 예외 또는 정의되지 않은 절삭

// 문자열 계약(5절 ②)을 쓰는 경우: 파싱도 명시적으로
int64_t id2 = std::stoll(j["id"].get<std::string>());   // 실패 시 예외 — 조용한 손상이 없다

// 경계 DTO(5절 ①)의 C++ 판: 구조체 + 변환 훅. 라이브러리가 인수 타입의 네임스페이스에서 from_json을 찾는다
struct UserDto { int64_t id; std::string price; };      // long이 아니라 int64_t — 아래 ABI 참조
void from_json(const json& j, UserDto& u) {
    j.at("id").get_to(u.id);                            // 필드마다 타입이 코드에 적혀 있다
    j.at("price").get_to(u.price);                      // at()은 키 부재 시 예외 — 4절 "부재"가 조용히 지나가지 않음
}
auto dto = j.get<UserDto>();

from_json이 별도 등록 없이 호출되는 것은 인수 의존 탐색(argument-dependent lookup, ADL — 함수 인수의 타입이 선언된 네임스페이스에서도 함수를 찾아 주는 규칙) 덕분이며, 이것이 Java의 리플렉션 스캔에 대응하는 C++의 "선언 발견" 기제다. 발견도 검사도 컴파일 타임에 끝나므로, 선언이 빠진 필드는 실행 전에 컴파일 에러로 드러난다.

C++ 관점의 통찰(메모리·수명·ABI·컴파일 타임): get<T>()는 템플릿이라 어떤 타입으로 읽을지가 컴파일 시점에 확정된다 — 3.2절의 "받은 쪽이 정수인지 실수인지 판정한다"는 상황 자체가 성립하지 않는다. 타입 정보를 데이터에서 복원하는 대신 코드에 적어 두는 방식이며, 이것이 5절 ①의 처방과 정확히 같은 발상임에 주목할 만하다. C++은 언어가 그 규율을 강제할 뿐이다.
ABI(application binary interface — 컴파일된 코드끼리 타입 크기·정렬·호출 규약을 맞추는 약속) 관점의 함정이 하나 더 있다: long의 크기가 플랫폼마다 다르다(64비트 리눅스 계열은 8바이트, 64비트 Windows는 4바이트). 경계 구조체에 long id라고 적으면 한 플랫폼에서는 64비트 ID를 정확히 받고 다른 플랫폼에서는 절삭된다 — 2절의 "타입 체계는 1:1로 포개지지 않는다"가 같은 언어 안에서도 성립하는 사례라, 경계 타입은 int64_t 같은 고정 폭 정수형으로 적는다. 같은 이유로 구조체 메모리를 그대로 소켓에 흘려보내는 것은 마샬링이 아니다 — 패딩·엔디언·크기가 컴파일러와 플랫폼의 선택이지 계약이 아니기 때문이다.
수명 쪽 함정도 있다: 파싱 결과에서 문자열을 참조로 꺼내 두고 원본 json 객체가 먼저 소멸하면 허상 참조가 된다. "경계를 건너온 데이터의 소유권을 누가 갖는가"라는 질문이 여기서는 명시적 선택이 되는데, GC 언어에서는 이 질문이 감춰져 있을 뿐 사라진 것은 아니다 — 캐시에 넣어 둔 역직렬화 결과를 다른 곳에서 변형해 오염시키는 문제가 같은 질문의 다른 얼굴이다.

8. 함께 알면 좋은 것

  • 스키마 우선 전송 형식 — 필드 타입을 스키마 파일(IDL)로 먼저 선언하고 각 언어 코드를 생성하는 계열(gRPC의 proto 등). 타입 대응을 사람의 규율이 아니라 도구가 보장하게 하는 접근으로, JSON 대비 트레이드오프는 D3 참조.
  • JSON Schema와 런타임 검증 — JSON을 유지하면서 계약을 기계 검증 가능하게 만드는 중간 지대. 문서화와의 연결은 D11.
  • 문자 인코딩 — 이 문서가 다룬 "타입의 대응" 아래층에는 "바이트와 문자의 대응"이 또 있다. 경계에서 깨지는 방식이 유사하다.
  • 라운드트립 테스트 — 대표 페이로드에 대해 직렬화→역직렬화→재직렬화 결과의 동일성을 검사하는 테스트. 3.3 계열 회귀의 저비용 검출기.
  • DB 드라이버의 타입 매핑 — 같은 문제의 또 다른 경계: DECIMAL·BIGINT·타임스탬프가 언어 타입으로 올 때도 동일한 대응 규칙 문제가 있다. "경계마다 매핑 표를 확인한다"는 습관은 전송 형식에 국한되지 않는다.

9. 한 장 요약

  • 마샬링 = 경계를 건너기 위한 타입 대응. C10(바이트 변환 기술)의 앞뒤 단계이며, 사고는 주로 이 대응에서 난다.
  • 타입 체계는 1:1이 아니다 — JSON number 하나로 뭉개진 정보(크기·정수/실수·정밀도)는 받은 쪽에서 복원 불가, 파서는 자기 언어 기본 타입으로 추측할 뿐.
  • 3대 함정: 253 초과 정수의 조용한 반올림 / 1.0→1 정수·실수 경계 소실 / 라운드트립 비보존 — 모두 에러 없이 성공의 얼굴로 온다.
  • 컬렉션은 성질째 강등된다(Set→배열, 맵 키→문자열, Date·Enum→문자열) — null/부재/undefined 3형제 구분까지 계약에서 정의할 것.
  • 처방: 경계 DTO/스키마로 필드별 표현 고정, 큰 정수·금액은 문자열(또는 최소 단위 정수), 날짜는 표준 형식 통일, 변환은 경계 한 곳에서만.

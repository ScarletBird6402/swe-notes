C11 마샬링과 타입 시그니처 매핑

0. 한눈에 보는 결론

  • 마샬링(marshalling)은 데이터를 경계(언어↔언어, 프로세스↔프로세스, 앱↔네트워크) 너머로 보낼 수 있는 형태로 꾸리는 일이다. 직렬화(C10)가 "바이트로 만드는 기술"이라면, 이 문서의 주제는 그 앞뒤 단계 — 서로 다른 타입 체계 사이의 대응(mapping) — 다.
  • 근본 문제: 언어들의 타입 체계는 1:1로 포개지지 않는다. Java의 long/int/BigDecimal 구분은 JSON에 오면 전부 number 하나로 뭉개지고, 받은 쪽은 자기 언어의 기본 타입으로 다시 추측한다.
  • 대표 함정(일반화 형태): JSON 역직렬화의 숫자 정규화로 인한 타입 정보 소실. ① 64비트 정수가 JS number(53비트 정밀도)를 넘어 끝자리가 조용히 바뀌고, ② 1.0이 파서를 거치며 1이 되어 정수/실수 경계가 사라지며, ③ 라운드트립(직렬화→역직렬화) 후 원래 타입으로 돌아오지 않는다. 셋 다 에러 없이 일어난다.
  • 컬렉션도 같은 운명이다: Set·Date·Enum은 JSON에 대응물이 없어 배열·문자열로 강등되고, 맵의 키는 문자열만 허용되며, null/부재/JS의 undefined 3형제는 언어마다 다르게 해석된다.
  • 처방의 원칙: 경계의 타입 대응을 우연에 맡기지 말고 명시적으로 고정한다 — DTO/스키마로 필드별 타입 선언, 정밀도가 중요한 큰 정수·금액은 문자열 또는 최소 단위 정수로, 날짜는 표준 문자열 형식으로 계약에 못박는다.

1. 마샬링 — 직렬화와 무엇이 다른가

C10은 "객체를 바이트열로, 바이트열을 객체로" 바꾸는 기술을 다뤘다. 그런데 실무 장애의 상당수는 바이트 변환 자체가 아니라 그 앞뒤에서 난다: 내 언어의 타입을 전송 형식의 타입으로 대응시키는 순간(보낼 때), 그리고 전송 형식의 타입을 상대 언어의 타입으로 복원 추측하는 순간(받을 때). 이 대응 작업 전체를 마샬링이라 부른다 (용어 관행은 6절에서 정리한다 — 문맥에 따라 직렬화와 섞여 쓰인다).

2. 근본 문제 — 타입 체계는 1:1로 포개지지 않는다

각 언어는 저마다의 역사와 목적으로 타입 체계를 설계했고, 전송 형식(특히 JSON)은 그중 최소 공통분모만 남겼다. 숫자 하나만 나란히 놓아도 격차가 보인다.

3. 함정 해부 — 숫자 정규화와 타입 소실

2절의 "합쳐지면 못 되돌린다"가 실제 사고로 나타나는 세 형태다. 공통점은 예외도 경고도 없이, 값이 그럴듯한 채로 틀린다는 것 — "동작은 하는데 결과가 이상한" 문제의 전형이라 K5의 계보에 속한다.

3.1 형태 ① — 큰 정수의 끝자리가 조용히 바뀐다

// 서버(Java): long id = 9007199254740993  (2^53 + 1, 64비트 정수로는 평범한 값)
// 응답 JSON:  {"id": 9007199254740993}

// 프론트(JS):
const obj = JSON.parse(response);
console.log(obj.id);          // 9007199254740992  ← 끝자리가 3에서 2로. 에러 없음.

JS의 number는 64비트 부동소수점이라 정수를 253(약 9천조)까지만 정확히 표현한다. 그 너머의 정수는 파싱 순간 가장 가까운 표현 가능한 값으로 반올림된다. DB 시퀀스·스노플레이크형 ID처럼 64비트를 꽉 채우는 값에서 "특정 데이터만 조회가 안 된다"(반올림된 ID로 재요청하므로) 같은 괴담형 버그가 여기서 나온다.

3.2 형태 ② — 정수/실수 경계가 사라진다

// 보낼 때: 1.0 (실수라는 의도)
JSON.stringify({ rate: 1.0 })   // '{"rate":1}'  ← 직렬화가 이미 .0을 지움

// 받은 쪽(언어별로 다른 추측):
// JS     : 1      (어차피 number 하나라 구분 개념 자체가 없음)
// Python : 1 (int) ← 원래 float였다는 정보는 소실
// Java   : 필드 타입이 double이면 1.0으로 복원되지만, Object/Map으로 받으면 Integer로

"1.0을 보냈는데 1이 왔다"는 값의 문제가 아니라(수학적으로 같다) 타입의 문제다. 받은 쪽이 Map<String, Object>·dict·동적 처리로 다루는 순간 "정수면 A 로직, 실수면 B 로직" 같은 분기, 타입 검사, 재직렬화 결과가 원본과 달라진다. 파서는 값을 자기 언어의 기본 타입으로 정규화할 뿐, 원래의 타입 의도를 운반해 주지 않는다.

3.3 형태 ③ — 라운드트립이 원형을 보존하지 않는다

Java 객체 ──직렬화──▶ JSON ──역직렬화──▶ JS 객체 ──직렬화──▶ JSON' ──역직렬화──▶ Java 객체' 기대: 객체' == 객체 현실: long은 반올림(①), 1.0은 1(②), BigDecimal 정밀도는 double로 절삭, Date는 문자열, Enum은 문자열, Set은 배열...

①②의 귀결이다. 경계를 왕복하는 데이터 — 프론트에서 받아 저장했다가 다시 보내는 폼, 시스템 간 중계 — 는 손상이 단계마다 누적된다. "원본과 재직렬화 결과의 diff가 0이어야 한다"는 라운드트립 테스트가 이 계열 함정의 유효한 검출기인 이유다.

세 형태의 공통 교훈: 손상은 역직렬화 "실패"가 아니라 역직렬화 "성공"의 얼굴로 온다. 그래서 이 함정은 예외 로그가 아니라 계약 설계(5절)로 막아야 한다.

4. 컬렉션·복합 타입 — 강등과 3형제

숫자에서 본 "최소 공통분모로의 강등"은 복합 타입에서 더 광범위하게 일어난다. JSON의 그릇은 배열과 객체 둘뿐이기 때문이다.

원 타입JSON에서받은 쪽에서 벌어지는 일

관찰: 표의 모든 행이 같은 문장으로 요약된다 — "전송 형식에 없는 개념은 표현과 함께 성질도 잃는다." 잃은 성질을 복원하는 책임은 자동으로 생기지 않으므로, 누군가(5절의 변환 계층)에게 명시적으로 배정되어야 한다.

5. 처방 — 경계의 타입을 우연에 맡기지 않는다

3·4절의 함정은 전부 "타입 대응을 파서의 기본 동작에 맡긴" 결과였다. 처방은 그 반대 방향 — 대응을 명시적 계약과 변환 계층으로 고정하는 것 — 이며, 구체적으로 네 가지다.

  • ① 경계 전용 DTO/스키마를 둔다. 내부 도메인 객체를 그대로 직렬화하지 않고, 경계용 타입(DTO, TS 인터페이스, 스키마 정의)을 따로 두어 필드마다 전송 표현을 선언한다. "이 필드는 문자열로 나간다"가 코드에 적혀 있으면 파서의 추측이 끼어들 자리가 없다. 스키마를 문서·검증과 연결하는 방법은 D11.
  • ② 정밀도가 중요한 수는 문자열로 보낸다. 64비트 ID·정밀 금액은 "9007199254740993"처럼 문자열로 — 3.1의 반올림이 원천 차단된다. 금액은 대안으로 최소 단위 정수(원·센트 단위 int)도 널리 쓰인다(53비트 안이면 안전). 어느 쪽이든 계약에 명시가 핵심.
  • ③ 날짜·시각은 표준 형식 문자열로 못박는다. 관례상 ISO 8601(예: 2026-07-16T09:00:00+09:00) + 타임존 포함. "epoch 숫자, 단 밀리초" 같은 선택도 가능하나 무엇이든 한 형식으로 통일하고 문서화한다.
  • ④ 변환은 경계 한 곳에서만 한다. 문자열↔BigDecimal, ISO 문자열↔Date 변환 코드가 비즈니스 로직 곳곳에 흩어지면 한 곳의 누락이 곧 버그다. 경계 계층(컨트롤러/클라이언트 어댑터)에서 변환을 끝내고, 내부에서는 내부 타입만 흐르게 한다.

6. 흔히 헷갈리는 지점

① "마샬링 = 직렬화 아닌가?" — 겹치는 용어가 맞고, 생태계마다 관행이 다르다(Go는 JSON 변환 함수 이름 자체가 Marshal이고, Java 전통에서는 원격 호출·XML 바인딩 문맥에서 마샬링을 썼다). 실무 요령은 용어 논쟁이 아니라 두 관심사의 구분이다 — 바이트로 만드는 기술(C10)과 타입을 대응시키는 규칙(이 문서). 어느 쪽 단어를 쓰든 후자를 잊는 것이 사고의 원인.

② "JSON은 타입이 있으니 타입이 보존된다"? — JSON의 타입은 6종(문자열·숫자·불리언·null·배열·객체)뿐이고 숫자에 정밀도 규정이 없다. "타입이 있다"와 "내 언어의 타입이 보존된다"는 전혀 다른 명제다(2절).

③ "TS 인터페이스로 받으니 안전하다"? — TS 타입은 컴파일 시점 표기일 뿐, JSON.parse 결과를 런타임에 검증하지 않는다. as UserDto는 확신의 표현이지 검사가 아니다. 런타임 검증은 스키마 검증 라이브러리 등 별도 장치의 몫.

④ "null이나 undefined나 없는 거나 그게 그거"? — 부분 수정 API에서 "null = 이 필드를 비워라, 부재 = 건드리지 마라"로 의미가 갈리는 순간 3형제 구분은 데이터 삭제 사고의 경계선이 된다(4절 표). JS의 undefined가 직렬화에서 필드째 사라진다는 사실은 이 구분을 프론트가 의도치 않게 조작할 수 있다는 뜻이다.

7.1 C++ — 복원은 추측이 아니라 선언이다

2절에서 본 "받은 쪽이 자기 언어의 관습대로 추측한다"는 문제를, C++ JSON 라이브러리들은 구조적으로 회피한다 — 꺼낼 때 타입을 개발자가 지정하게 만들기 때문이다. 추측할 여지 자체가 없어지는 대신, 지정을 틀리면 그 자리에서 드러난다. 

// nlohmann/json 계열의 전형적 사용 (대표 예시)
auto j = json::parse(R"({"id": 9007199254740993, "rate": 1.0})");

auto id   = j["id"].get<int64_t>();     // ← "이것을 64비트 정수로 읽겠다"고 선언
auto rate = j["rate"].get<double>();    // ← "이것을 실수로 읽겠다"

// 선언을 틀리면 조용히 넘어가지 않는다
auto bad  = j["id"].get<int32_t>();     // 범위 초과 — 라이브러리에 따라 예외 또는 정의되지 않은 절삭

// 문자열 계약(5절 ②)을 쓰는 경우: 파싱도 명시적으로
auto id_str = j["id"].get<std::string>();
int64_t id2 = std::stoll(id_str);       // 실패 시 예외 — 조용한 손상이 없다

C++ 관점의 통찰(메모리·수명·컴파일 타임): get<T>()는 템플릿이라 어떤 타입으로 읽을지가 컴파일 시점에 확정된다 — 3.2절의 "받은 쪽이 정수인지 실수인지 판정한다"는 상황 자체가 성립하지 않는다. 타입 정보를 데이터에서 복원하는 대신 코드에 적어 두는 방식이며, 이것이 5절 ①(경계 DTO로 필드별 표현을 선언)의 처방과 정확히 같은 발상임에 주목할 만하다. C++은 언어가 그 규율을 강제할 뿐이다.
수명 쪽 함정도 하나 있다: 파싱 결과에서 문자열을 참조로 꺼내 두고 원본 json 객체가 먼저 소멸하면 허상 참조가 된다. "경계를 건너온 데이터의 소유권을 누가 갖는가"라는 질문이 여기서는 명시적 선택이 되는데, GC 언어에서는 이 질문이 감춰져 있을 뿐 사라진 것은 아니다 — 캐시에 넣어 둔 역직렬화 결과를 다른 곳에서 변형해 오염시키는 문제가 같은 질문의 다른 얼굴이다.

7.2 Python — 정규화 규칙에 직접 개입하기

Python은 3절의 함정을 가장 잘 보여 주면서 동시에 가장 깔끔한 탈출구를 가진 언어다. 무제한 정수 덕에 3.1(큰 정수 반올림)은 겪지 않지만 3.2(정수/실수 경계)에는 그대로 노출되며, 표준 라이브러리가 파서의 숫자 변환 규칙을 교체할 수 있는 훅을 제공한다. 

import json
from decimal import Decimal

s = '{"id": 9007199254740993, "price": 19.99}'

# 기본 동작: price는 float가 되어 십진 정밀도가 사라진다
d1 = json.loads(s)
print(type(d1["id"]), d1["id"])        # <class 'int'> 9007199254740993  ← 정확(무제한 정수)
print(repr(d1["price"]))               # 19.99 → 내부적으로는 이진 부동소수점 근사값

# 훅으로 정규화 규칙을 바꾼다: 실수를 Decimal로 받아 십진 정밀도 보존
d2 = json.loads(s, parse_float=Decimal)
print(repr(d2["price"]))               # Decimal('19.99')  ← 원문 표기 그대로 보존

# 내보낼 때도 대칭이 필요하다 (Decimal은 기본 인코더가 모른다)
json.dumps({"price": Decimal("19.99")}, default=str)   # {"price": "19.99"}

Python 관점의 통찰: parse_float=Decimal 한 줄이 이 문서의 처방을 요약한다 — 파서의 기본 정규화는 "선택"이지 "사실"이 아니다. 금액을 float로 받으면 0.1 + 0.2가 정확히 0.3이 아닌 세계로 들어가고, 그 오차는 합산·비교를 거치며 누적된다. 정밀도가 중요한 값에 대해 "십진 표기를 그대로 들고 다니는 타입"으로 받는 것은, 5절 ②의 문자열 계약과 동일한 목적(원문 보존)을 언어 도구로 달성하는 방법이다.
대칭성에도 주의할 만하다: 들어올 때 Decimal로 받아도 나갈 때 규칙을 맞추지 않으면 인코더가 처리하지 못하거나 다시 float로 떨어진다. 3.3절의 라운드트립 문제는 입력·출력 양쪽의 규칙이 짝을 이룰 때만 해결된다.

7.3 Java / JS·TS — 한 줄 요약

Java는 대상 필드 타입(long, BigDecimal)에 맞춰 복원되므로 Java끼리는 문제가 드러나지 않는다 — 함정은 상대가 Java가 아닐 때 터지며, 서버가 정확히 만든 숫자가 프론트에서 반올림되는 3.1이 전형이다(방어는 받는 쪽이 아니라 보내는 쪽 계약에서 문자열화로). JS·TS에는 BigInt가 있지만 JSON.parse의 기본 동작은 여전히 반올림이고 JSON.stringify는 BigInt를 직렬화하지 못한다 — 즉 해결의 자리는 코드가 아니라 계약이라는 5절의 결론이 언어 차원에서 재확인된다.

8. 함께 알면 좋은 것

  • 스키마 우선 전송 형식 — 필드 타입을 스키마 파일(IDL)로 먼저 선언하고 각 언어 코드를 생성하는 계열(gRPC의 proto 등). 타입 대응을 사람의 규율이 아니라 도구가 보장하게 하는 접근으로, JSON 대비 트레이드오프는 D3 참조.
  • JSON Schema와 런타임 검증 — JSON을 유지하면서 계약을 기계 검증 가능하게 만드는 중간 지대. 문서화와의 연결은 D11.
  • 문자 인코딩 — 이 문서가 다룬 "타입의 대응" 아래층에는 "바이트와 문자의 대응"이 또 있다. 경계에서 깨지는 방식이 유사하다.
  • 라운드트립 테스트 — 대표 페이로드에 대해 직렬화→역직렬화→재직렬화 결과의 동일성을 검사하는 테스트. 3.3 계열 회귀의 저비용 검출기.
  • DB 드라이버의 타입 매핑 — 같은 문제의 또 다른 경계: DECIMAL·BIGINT·타임스탬프가 언어 타입으로 올 때도 동일한 대응 규칙 문제가 있다. "경계마다 매핑 표를 확인한다"는 습관은 전송 형식에 국한되지 않는다.

9. 한 장 요약

  • 마샬링 = 경계를 건너기 위한 타입 대응. C10(바이트 변환 기술)의 앞뒤 단계이며, 사고는 주로 이 대응에서 난다.
  • 타입 체계는 1:1이 아니다 — JSON number 하나로 뭉개진 정보(크기·정수/실수·정밀도)는 받은 쪽에서 복원 불가, 파서는 자기 언어 기본 타입으로 추측할 뿐.
  • 3대 함정: 253 초과 정수의 조용한 반올림 / 1.0→1 정수·실수 경계 소실 / 라운드트립 비보존 — 모두 에러 없이 성공의 얼굴로 온다.
  • 컬렉션은 성질째 강등된다(Set→배열, 맵 키→문자열, Date·Enum→문자열) — null/부재/undefined 3형제 구분까지 계약에서 정의할 것.
  • 처방: 경계 DTO/스키마로 필드별 표현 고정, 큰 정수·금액은 문자열(또는 최소 단위 정수), 날짜는 표준 형식 통일, 변환은 경계 한 곳에서만.

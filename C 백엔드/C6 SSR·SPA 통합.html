C6 SSR·SPA 통합

0. 한눈에 보는 결론

  • 서버 렌더링 페이지 안에 SPA를 얹는 통합은 과도기 편법이 아니라 점진 도입의 표준 경로다 — 기존 시스템을 유지한 채 화면 단위로 SPA를 심는다.
  • 통합의 본질적 난점: 한 페이지 안에 두 종류의 요청이 공존하게 된다 — 브라우저 내비게이션이 만드는 문서 요청(HTML·리다이렉트의 세계)과 SPA가 만드는 데이터 요청(JSON·상태 코드의 세계).
  • 두 세계는 에러·인증 규약이 다르다. 특히 세션 만료 시 리다이렉트는 문서 세계에서만 통한다 — 데이터 요청이 로그인 페이지로 리다이렉트되면 "JSON 기대 자리에 HTML 200"이라는 엉뚱한 실패로 나타난다.
  • 해법은 규약의 이원화: 서버는 요청 종류를 판별해 문서에는 리다이렉트, API에는 401/403 JSON으로 응답하고, 클라이언트는 인터셉터 한 곳에서 401을 받아 로그인 흐름을 처리한다.
  • Axios 인터셉터류는 이 이원화를 SPA 쪽에서 받아내는 표준 장치다 — 인증 헤더 부착·401 공통 처리·에러 정규화를 산재시키지 않고 한 관문에 모은다.

1. 한 페이지 안의 두 세계 — 이 통합은 왜 생기는가

C1 서버사이드 렌더링 vs 클라이언트 렌더링.html은 렌더링 위치를 "선택"의 문제로 다뤘다. 그런데 실무에는 선택이 아니라 공존이 강제되는 상황이 흔하다 — 이미 서버 템플릿으로 돌아가는 시스템이 있고, 그 위에 새 화면만 SPA로 얹고 싶은 경우다. 전면 재작성은 위험과 비용이 크므로, 서버 렌더 페이지의 한 구획에 SPA를 임베드하는 절충이 표준 경로가 된다.

임베드 자체는 간단하다. 서버 템플릿이 마운트 지점과 번들을 내주면 된다: 

<!-- 서버가 렌더링한 페이지의 일부 (템플릿) -->
<nav>…서버가 그린 공통 내비게이션…</nav>

<div id="order-app"></div>          <!-- SPA 마운트 지점 -->
<script>
  window.__INITIAL__ = { userId: 42, role: "manager" };  /* 초기 데이터 주입 */
</script>
<script src="/static/order-app.bundle.js"></script>      <!-- SPA 번들 -->

서버는 첫 화면 골격·공통 영역을 렌더링하고, SPA는 자기 구획(#order-app) 안에서 데이터 요청으로 살아 움직인다. 초기 데이터 주입(전역 변수·데이터 속성으로 서버 값을 넘기는 것)은 SPA가 뜨자마자 필요한 값의 API 왕복을 아끼는 관행이다. 여기까지는 순조롭다 — 문제는 이 페이지가 이제 두 가지 언어로 서버와 대화한다는 데서 시작한다. 링크 클릭·폼 제출은 예전처럼 브라우저 내비게이션(문서 요청)을 만들고, SPA 구획 안의 조작은 fetch·XHR(데이터 요청)을 만든다. 한 화면, 두 세계다.

2. 문서 요청과 데이터 요청 — 같은 서버, 다른 규약

두 요청은 같은 HTTP로 날아가지만, 응답을 소비하는 주체와 그 주체가 이해하는 규약이 다르다. 이 차이가 이 문서의 모든 문제의 뿌리이므로 정확히 갈라 두자.

문서 요청 (내비게이션)데이터 요청 (fetch·XHR)
만드는 주체브라우저 자체(주소창·링크·폼)페이지 안의 JS 코드
기대 응답HTML 문서JSON(구조화 데이터)
응답 소비자브라우저 — 화면을 통째로 교체JS 코드 — 파싱해 상태 갱신
302 리다이렉트화면 전환으로 동작(주소창 변경)fetch가 조용히 따라가서 최종 응답만 JS에 전달 — 화면은 그대로
에러 전달에러 페이지를 그려서상태 코드 + JSON 본문으로

표의 마지막 두 행이 핵심이다. 리다이렉트는 문서 세계의 화면 전환 수단이다 — 브라우저가 302를 받으면 새 주소로 이동해 그 페이지를 그린다. 그런데 데이터 요청의 302는 전혀 다르게 동작한다: fetch·XHR은 리다이렉트를 투명하게 따라가 최종 목적지의 응답만 JS에 돌려준다. JS 입장에서는 리다이렉트가 있었는지조차 보이지 않고, 화면 전환은 당연히 일어나지 않는다. "서버가 리다이렉트를 보냈으니 사용자가 그 페이지로 가겠지"라는 가정은 요청을 브라우저가 만들었을 때만 성립하는 것이다.

프레임: 서버 입장에서 이제 클라이언트는 하나가 아니다. "브라우저"라는 문서 소비자와 "페이지 속 JS"라는 데이터 소비자, 두 부류의 클라이언트가 같은 서버를 본다. 서로 다른 클라이언트에게 같은 응답 규약을 쓰면 어느 한쪽에서 반드시 어긋난다 — 다음 절의 인증 만료가 그 어긋남의 대표 사례다.

3. 인증 만료의 두 얼굴 — 권한 흐름이 두 세계에 걸칠 때

이 시스템의 인증이 세션 기반이라 하자 — 여기서 세션은 "로그인 상태를 서버가 기억하고, 브라우저는 쿠키에 담긴 식별자로 자신을 증명하는 방식" 정도로만 정의한다(저장·수명·확장 문제는 C4 서버 세션 관리.html 소관이며, 토큰 방식과의 비교는 S2 토큰 기반 인증 — JWT vs 세션.html). 쿠키는 문서 요청이든 데이터 요청이든 같은 오리진이면 자동으로 실려 가므로, 로그인 상태는 두 세계가 공유한다. 여기까지는 통합의 좋은 소식이다.

나쁜 소식은 만료 순간에 온다. 사용자가 페이지를 열어 둔 채 자리를 비웠고 세션이 만료됐다. 전통 서버 앱의 표준 동작은 "미인증 요청 → 로그인 페이지로 302"다. 문서 세계에서 이것은 완벽하게 동작한다 — 사용자는 다음 클릭에서 로그인 화면을 만난다. 그런데 SPA 구획이 데이터 요청을 보내면 2절의 규약 충돌이 정확히 발화한다:

SPA: GET /api/orders (만료된 쿠키) → 서버: 302 Location: /login ← 문서 세계의 반사적 응답 → fetch가 조용히 /login을 따라감 → 응답: 200 OK, 본문 = 로그인 페이지 HTML → SPA: JSON.parse("<!DOCTYPE html…") → SyntaxError 증상: "주문 목록을 불러오지 못했습니다" + 콘솔의 JSON 파싱 에러 실체: 단순 세션 만료. 에러의 표면과 원인이 완전히 다른 계층에 있다

사용자는 로그인 화면을 보지 못하고, 개발자는 "API가 이상한 응답을 준다"는 방향으로 조사를 시작한다 — 만료라는 평범한 사건이 가장 미궁 같은 증상으로 번역된 것이다. 권한 부족(로그인은 됐지만 자격 없음)도 같은 구조로 어긋난다: 문서 세계의 "권한 없음 안내 페이지로 리다이렉트"가 데이터 요청에는 같은 "HTML 200" 사고를 만든다.

해법은 서버가 두 부류의 클라이언트에게 다른 규약으로 응답하는 것이다. 미인증·무권한 상황에서 — 문서 요청에는 기존대로 리다이렉트, 데이터 요청에는 401(미인증)/403(권한 없음) 상태 코드 + JSON 본문. 요청 종류의 판별 기준은 관례로 정한다: API 경로 접두(/api/), Accept: application/json 헤더, 또는 클라이언트가 붙이는 식별 헤더 (X-Requested-With)가 통용된다. 그리고 클라이언트 쪽에는 이 401/403을 받아 로그인 유도·안내를 수행할 자리가 필요하다 — 그 자리가 다음 절의 인터셉터다.

4. 인터셉터 — 흩어질 규약 처리를 한 관문에 모으기

3절의 규약("데이터 요청의 인증 실패는 401 JSON")이 정해져도, 그 처리를 모든 API 호출부마다 쓰게 할 수는 없다 — 호출부가 수십 곳이면 누락·불일치가 필연이다. HTTP 클라이언트 라이브러리들이 제공하는 인터셉터(interceptor)는 모든 요청·응답이 통과하는 관문을 한 곳에 만들어 이 산재를 막는 장치다. Axios(SPA 진영에서 널리 쓰이는 HTTP 클라이언트)의 전형적 구성은 이렇다: 

const api = axios.create({ baseURL: "/api" });

// 요청 관문: 모든 요청에 공통 헤더 부착
api.interceptors.request.use(cfg => {
  cfg.headers["X-Requested-With"] = "XMLHttpRequest";  // "나는 데이터 요청" 식별
  return cfg;
});

// 응답 관문: 인증·에러 규약을 한 곳에서 처리
api.interceptors.response.use(
  res => res,
  err => {
    const status = err.response?.status;
    if (status === 401) {
      // 세션 만료 — 현재 위치를 기억시켜 로그인으로 (문서 세계로의 전환은 JS가 명시적으로)
      location.assign("/login?next=" + encodeURIComponent(location.pathname));
      return new Promise(() => {});   // 이동 중 — 후속 체인 실행 방지
    }
    if (status === 403) return Promise.reject(new PermissionError(err));
    return Promise.reject(normalizeError(err));  // 그 외는 정규화해 호출부로
  }
);

포인트가 셋 있다. 첫째, 데이터 요청의 "로그인 페이지로 이동"은 서버 리다이렉트가 아니라 클라이언트 JS의 명시적 이동 (location.assign)으로 한다 — 2절에서 본 대로, 두 세계를 건너는 화면 전환은 JS만이 일으킬 수 있다. 둘째, 요청 인터셉터의 식별 헤더는 3절 서버 판별의 짝이다 — 규약은 언제나 양끝이 함께 구현해야 성립한다. 셋째, 401 처리·에러 정규화가 관문 한 곳에 있으므로 호출부는 도메인 로직만 남는다.

인터셉터의 고전적 함정 — 재귀 401: 만료 시 조용히 세션·토큰을 갱신하고 원 요청을 재시도하는 로직을 인터셉터에 넣을 때, 갱신 요청 자체가 401을 받으면 같은 인터셉터가 다시 갱신을 부르는 무한 루프가 된다. 갱신 요청은 인터셉터가 없는 별도 인스턴스로 보내거나 재시도 플래그로 1회 제한하는 것이 정석이다. 여러 요청이 동시에 401을 맞고 각자 로그인 이동·갱신을 중복 발화하는 경합도 흔한 변종이니, 이동·갱신은 1회만 실행되게 잠근다.

흔히 헷갈리는 지점

  • "쿠키가 자동으로 실리니 인증 문제는 없다?" — 로그인 상태의 공유와 실패의 처리는 별개다. 상태는 쿠키가 공유해 주지만, 만료·무권한이라는 실패 사건의 전달 규약은 두 세계가 다르다(3절). "잘 되다가 30분 뒤부터 이상하다"류의 증상은 대부분 후자다.
  • "fetch가 302를 받으면 JS에서 감지해 처리하면 된다?" — 감지 자체가 안 된다. fetch의 기본 동작은 리다이렉트를 따라간 최종 응답만 주며, 중간의 302는 보이지 않는다(응답의 redirected 플래그로 "따라갔었다"는 사실 정도만 안다). 그래서 해법이 "클라이언트에서 302 처리"가 아니라 "서버가 302를 보내지 않기"(401 JSON 규약)인 것이다.
  • "401과 403은 비슷하니 같이 처리해도 된다?" — 사용자에게 시키는 행동이 다르다. 401(미인증)의 처방은 "로그인하라"이고 403(권한 없음)의 처방은 "이 자원은 당신 것이 아니다"다 — 403에서 로그인 페이지로 보내면 이미 로그인한 사용자가 로그인을 반복하는 루프를 돈다. 인터셉터에서 반드시 갈라 처리한다.
  • "SPA 구획만 보면 되니 서버 템플릿 쪽은 몰라도 된다?" — 임베드형 통합에서 SPA의 생존 조건(마운트 지점, 초기 데이터, 쿠키·CSRF 토큰)은 전부 서버 템플릿이 마련한다. 특히 폼 위조 방지 토큰(CSRF 토큰)을 서버가 페이지에 심고 SPA가 데이터 요청 헤더로 되돌려 보내는 연결은, 양쪽을 다 아는 사람이 없으면 끊어진 채 방치되기 쉽다.
  • "이 문제들은 세션 방식이라서 생긴다 — 토큰으로 바꾸면 사라진다?" — 저장 위치가 바뀔 뿐 구조는 남는다. 토큰 방식도 만료는 있고, 만료 시 "데이터 요청에 무엇을 응답하고 클라이언트가 어디서 받는가"라는 두-세계 규약 문제는 동일하다(방식 간 비교는 S2).

★ 언어별 대조 — 두 세계의 분기점은 각 스택 어디에 있는가

이 통합 문제의 클라이언트 절반은 언어가 JS로 고정돼 있다. 따라서 언어별 대조의 관전점은 서버 스택마다 "요청 종류 판별과 응답 이원화"가 어디서, 어떤 관용구로 구현되는가다.

Java — 프레임워크가 분기점을 제공한다: 인증 진입점의 이원화

Java·Spring 스택의 강점은 3절의 "요청 종류별 응답 이원화"가 보안 프레임워크의 공식 확장 지점으로 존재한다는 것이다. Spring Security에서 미인증 요청의 처리는 인증 진입점(AuthenticationEntryPoint)이 담당하는데, 기본 구성은 로그인 페이지 리다이렉트 — 즉 문서 세계만 아는 기본값이다. 통합 시스템에서는 이것을 요청 매처로 갈라 등록한다: 

// 경로·헤더 기준으로 두 세계를 갈라, 미인증 응답을 이원화
http.exceptionHandling(ex -> ex
    .defaultAuthenticationEntryPointFor(
        (req, res, e) -> {                       // 데이터 요청: 401 + JSON
            res.setStatus(401);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"UNAUTHENTICATED\"}");
        },
        new AntPathRequestMatcher("/api/**"))
    .defaultAuthenticationEntryPointFor(
        new LoginUrlAuthenticationEntryPoint("/login"),  // 문서 요청: 리다이렉트
        AnyRequestMatcher.INSTANCE));

세션 식별자는 서블릿 표준의 JSESSIONID 쿠키로 오가며(JVM 관점에서 세션 객체는 힙에 살므로 다중 인스턴스 확장 시 외부 저장소 문제가 생긴다 — C4 소관), CSRF 보호가 기본 활성이라는 점이 통합의 단골 걸림돌이다: 서버 템플릿 폼에는 토큰이 자동 주입되지만, 임베드된 SPA의 데이터 요청에는 토큰을 쿠키·메타 태그로 내려 헤더로 되돌려 받는 배선을 직접 연결해야 한다 — "폼은 되는데 SPA의 POST만 403"이라는 증상의 표준 원인이다.

JS·TS — 인터셉터는 프라미스 체인이다: 클라이언트 절반의 내부 기제

클라이언트 절반의 구현은 4절에서 봤으므로, 여기서는 그 내부 기제를 본다. Axios 인터셉터의 실체는 프라미스 체인의 미들웨어다 — 요청 인터셉터들, 실제 전송, 응답 인터셉터들이 then 연쇄로 이어지며, 인터셉터에서 던진 거부(reject)는 체인을 타고 호출부의 catch까지 흐른다. 이 구조를 알면 4절의 미묘한 코드가 설명된다: 401 처리에서 new Promise(() => {})(영원히 대기하는 프라미스)를 반환한 것은 페이지 이동이 시작된 뒤 후속 체인(호출부의 에러 토스트 등)이 실행되는 깜빡임을 막는 관용구다. 이벤트 루프 관점의 함정도 하나: 페이지 이동은 즉시가 아니라 현재 태스크 이후에 일어나므로, 이동 "후"에도 큐에 남은 콜백은 실행된다 — 이동 직전의 상태 갱신 코드가 사라질 화면에 헛손질하는 경고류 버그의 원인이다. 

// TS: 인터셉터가 정규화한 에러를 타입으로 고정 — 호출부 규약의 문서화
class PermissionError extends Error { readonly kind = "permission" as const; }
class ApiError extends Error {
  constructor(readonly status: number, readonly body: unknown) { super("api"); }
}
// 호출부: 좁히기(narrowing)로 분기 — "어떤 에러가 올 수 있는가"가 코드에 남는다
try { await api.get("/orders"); }
catch (e) {
  if (e instanceof PermissionError) showNoAccess();
  else if (e instanceof ApiError && e.status >= 500) showRetry();
}

TS의 기여는 이 에러 규약의 타입화다. 구조적 타이핑 덕에 서버 JSON 응답의 형태를 인터페이스로 선언해 파싱 지점에서 검증·좁히기를 걸 수 있고 — 3절의 "JSON 기대 자리에 HTML" 사고도 "파싱 결과가 스키마 불일치"라는 이해 가능한 에러로 바뀐다. 단 타입은 소거되므로 런타임 검증 코드는 별도로 있어야 한다는 원칙은 여기서도 같다.

Python — 데코레이터의 기본값이 문서 세계를 향해 있다

Python 웹 프레임워크의 인증 관용구는 데코레이터다 — Django의 login_required, Flask-Login의 동명 데코레이터가 뷰 함수를 감싸 미인증 시의 동작을 주입한다. 함정은 그 기본 동작이 로그인 페이지 리다이렉트 — 문서 세계 전용이라는 점이다. API 뷰에 같은 데코레이터를 무심코 쓰면 3절의 "HTML 200" 사고가 그대로 재현된다. 통합 시스템의 관용구는 API용 변형을 만드는 것이다: 

from functools import wraps
from flask import request, jsonify, redirect, url_for
from flask_login import current_user

def auth_required(view):                # 두 세계를 아는 데코레이터
    @wraps(view)
    def wrapped(*args, **kwargs):
        if current_user.is_authenticated:
            return view(*args, **kwargs)
        wants_json = (request.path.startswith("/api/")
                      or request.accept_mimetypes.best == "application/json")
        if wants_json:
            return jsonify(error="UNAUTHENTICATED"), 401   # 데이터 세계
        return redirect(url_for("login", next=request.path)) # 문서 세계
    return wrapped

객체 모델 관점에서 데코레이터는 뷰 함수를 감싼 클로저일 뿐이므로, 이렇게 판별 로직을 한 겹 끼워 넣는 재정의가 자연스럽다 — 프레임워크 확장 지점을 찾아야 하는 Java와의 결 차이다. 역사적 주의 하나: 과거 Django에 있던 request.is_ajax()는 X-Requested-With 헤더를 보는 헬퍼였는데 제거된 지 오래다(fetch 시대에 이 헤더는 자동으로 붙지 않으므로). 그 관습을 기억하는 코드가 헤더를 안 붙이는 fetch와 만나면 판별이 조용히 어긋난다 — 판별 기준을 경로 접두나 Accept처럼 클라이언트 협조에 덜 기대는 쪽으로 두거나, 붙일 헤더를 인터셉터에서 명시적으로 관리해야 한다(4절의 요청 인터셉터가 그 답이다).

C++ — 프레임워크 없이 같은 문제를 만나는 자리: 내장 웹 콘솔

C++에서 이 통합 문제가 성립하는 대표적 자리는 일반 웹 서비스가 아니라 기기에 내장된 관리 콘솔이다 — 공유기·프린터·계측 장비처럼 C++ 펌웨어가 작은 HTTP 서버를 품고, 관리 화면(정적 SPA 번들)과 JSON API를 함께 서빙하는 구조. 규모는 작아도 두-세계 구조는 동일한데, 차이는 프레임워크가 정해 주는 규약이 없어 전부 스스로 정해야 한다는 것이다: 

// 내장 HTTP 서버의 핸들러 — 판별·이원화를 수동으로
void handle(const Request& req, Response& res) {
    bool is_api = req.path.rfind("/api/", 0) == 0;      // 경로 접두 판별
    if (!session_valid(req.cookie("SID"))) {
        if (is_api) { res.status = 401; res.json("{\"error\":\"UNAUTHENTICATED\"}"); }
        else        { res.status = 302; res.header("Location", "/login.html"); }
        return;
    }
    /* …정상 처리… */
}

메모리·수명 관점의 특이점이 이 자리의 본질이다. 세션 테이블은 고정 크기 배열·풀로 관리되는 경우가 많고(임베디드의 힙 단편화 회피), 세션 만료가 "메모리 회수"와 동의어가 되므로 만료 응답 규약이 곧 자원 관리 규약이다. 컴파일 타임 관점에서는 관리 화면의 정적 자원(SPA 번들·HTML)을 바이너리에 상수로 구워 넣는 관행이 흔한데 — O8에서 본 "구워지는 값"의 극단으로, 화면 하나 고치는 일이 펌웨어 재빌드가 된다는 뜻이다. 큰 시스템 쪽에서 C++이 이 문제와 만나는 또 다른 자리는 게이트웨이·리버스 프록시 계층(고성능 C++ 구현이 표준인 영역)으로, 서버 템플릿 앱과 SPA API를 같은 오리진 아래 경로로 묶어 쿠키·CORS 문제를 구조적으로 줄이는 배치가 이 계층의 기여다.

함께 알면 좋은 것

  • BFF(backend for frontend) — SPA 전용 백엔드를 한 겹 두어, 인증·세션은 BFF가 문서 세계 방식으로 처리하고 SPA에는 일관된 JSON 규약만 노출하는 패턴. 이 문서의 이원화를 "별도 계층으로 승격"한 형태다.
  • CSRF 방어와 SameSite 쿠키 — 쿠키 기반 데이터 요청은 위조 요청(CSRF) 고려가 필수다. 최근 브라우저의 SameSite 기본값 강화(Lax)가 방어의 기본선을 올렸지만, 토큰 헤더 방식과의 병행이 여전히 표준 권고다.
  • 조용한 갱신(silent refresh) 흐름 — 만료를 사용자에게 보이지 않게 처리하는 설계(만료 임박 감지·백그라운드 갱신· 실패 시에만 로그인 유도). 4절 인터셉터의 재귀 함정과 세트로 학습해야 안전하게 쓸 수 있다.
  • 마이크로 프론트엔드 — 한 페이지에 여러 팀의 SPA 구획이 공존하는 확장형. 이 문서의 두-세계 문제가 "N개 구획 + 공통 셸"로 일반화되며, 인증 규약·전역 상태의 소유권 문제가 곱해진다.
  • same-origin 배치와 프록시 라우팅 — SPA 자원과 API를 다른 도메인에 두면 CORS·서드파티 쿠키 문제가 두-세계 문제 위에 얹힌다. 게이트웨이의 경로 라우팅으로 같은 오리진에 묶는 배치가 통합 난도를 한 단계 낮추는 첫 수다.

한 장 요약

  • 서버 렌더 페이지 + 임베드 SPA 통합의 본질: 한 페이지가 문서 요청과 데이터 요청이라는 두 규약으로 서버와 대화하게 된다.
  • 리다이렉트는 문서 세계 전용 수단 — 데이터 요청(fetch·XHR)은 302를 조용히 따라가 화면 전환 없이 최종 응답만 받는다.
  • 그래서 세션 만료가 SPA에서는 "JSON 자리에 로그인 HTML 200"이라는 엉뚱한 에러로 나타난다 — 표면 증상과 원인의 계층이 다른 대표 사례.
  • 해법: 서버는 요청 종류를 판별해 문서엔 리다이렉트, API엔 401/403 JSON으로 이원화하고, 클라이언트는 인터셉터 관문에서 401/403을 갈라 처리한다(재귀 갱신·중복 이동 잠금 필수).
  • 스택별 분기점: Spring은 인증 진입점 이원화, Python은 데코레이터 재정의, 클라이언트는 Axios 프라미스 체인, C++ 내장 콘솔은 수동 판별 — 장치는 달라도 규약은 하나다.
  • 세션 자체의 저장·수명은 C4, 세션 vs 토큰 선택은 S2와 이어서 볼 것.

C18 Node.js 서버 기초

0. 한눈에 보는 결론

  • Node HTTP 서버의 원형은 "요청이 올 때마다 호출되는 콜백 함수 하나"다. 프레임워크(Express 등)는 그 콜백 안에서 라우팅·파싱·에러 처리를 정리해 주는 층이다.
  • 미들웨어(middleware)는 요청이 핸들러에 닿기 전후로 거치는 함수들의 파이프라인이다. 등록한 순서대로 실행되고, 각 미들웨어는 next()를 불러 다음으로 넘기거나, 응답을 보내 파이프라인을 끝내거나, 둘 중 하나를 반드시 해야 한다 — 둘 다 안 하면 요청은 영원히 매달린다.
  • 핸들러는 사실상 전부 비동기다(DB·외부 API 호출). 비동기 핸들러의 에러 처리에는 함정이 있다: async 함수 안에서 던져진 에러는 동기 세계의 try/catch와 프레임워크의 기본 에러 처리망에 잡히지 않을 수 있다.
  • 그 결과가 unhandled rejection(처리되지 않은 Promise 거부) — 에러가 어떤 catch에도 닿지 못한 채 떠도는 상태다. 최신 Node의 기본 동작은 프로세스 종료이므로, 핸들러 하나의 누락이 서버 전체를 내린다.
  • 방어의 원칙: 모든 비동기 핸들러의 에러가 반드시 중앙 에러 처리기로 흘러들게 배관한다(래퍼 함수 또는 자동 전달을 지원하는 프레임워크 버전 사용). 전역 unhandledRejection 핸들러는 최후의 관측 지점이지 처리 수단이 아니다.

1. 원형 — http 모듈의 서버는 콜백 하나다

const http = require('http');

const server = http.createServer((req, res) => {   // 모든 요청이 이 함수로 들어온다
  res.statusCode = 200;
  res.setHeader('Content-Type', 'application/json');
  res.end(JSON.stringify({ ok: true }));
});

server.listen(3000);

이것이 전부다. req(요청)는 읽는 스트림, res(응답)는 쓰는 스트림이며, URL이 무엇이든 메서드가 무엇이든 이 콜백 하나가 받는다. 런타임 구조(C17 Node.js 런타임 구조.html)와 연결하면: 이 콜백은 이벤트 루프의 poll 단계에서, 소켓에 요청이 도착했다는 OS 통지를 받아 호출된다. 요청 1만 개가 동시에 와도 스레드는 하나 — 콜백이 빨리 반환하고 I/O는 양보한다는 전제 하에서다.

원형만으로 실무 서버를 짜면 URL 분기(라우팅), 본문 파싱, 에러 처리를 전부 손으로 해야 한다. 이 반복 작업을 정돈한 것이 프레임워크이고, 이 문서는 사실상 표준인 Express를 대표 예시로 쓴다(개념은 Koa·Fastify 등에도 그대로 통한다).

2. 미들웨어 — 순서가 곧 설계다

1절의 "콜백 하나"에 모든 일을 밀어 넣는 대신, Express는 그 일을 여러 함수로 쪼개 사슬로 잇는다. 즉 Express 서버는 미들웨어의 사슬이다. 요청은 등록된 순서대로 미들웨어를 통과하며, 각 미들웨어는 세 가지 중 하나를 한다: 가공 후 next()로 통과 / 응답을 보내고 종료 / next(err)로 에러 경로 진입.

요청 ─> [로깅] ─> [본문 파싱] ─> [인증] ─> [라우트 핸들러] ─> 응답 │ │ │ └── 어느 단계든 next(err)를 부르면 ──> [에러 미들웨어] ─> 에러 응답
const express = require('express');
const app = express();

app.use(logger);                 // ① 모든 요청 로깅
app.use(express.json());         // ② JSON 본문 파싱 → req.body
app.use('/admin', requireAuth);  // ③ 경로 한정 미들웨어

app.get('/users/:id', async (req, res) => {   // ④ 라우트 핸들러 (미들웨어의 일종)
  const user = await db.findUser(req.params.id);
  if (!user) return res.status(404).json({ error: 'not found' });
  res.json(user);
});

app.use((err, req, res, next) => {            // ⑤ 에러 미들웨어: 인자 4개가 식별자
  console.error(err);
  res.status(500).json({ error: 'internal error' });
});
  • 순서가 의미다. 본문 파싱(②)보다 앞에 놓인 미들웨어에서는 req.body가 없다. 인증(③)을 라우트보다 뒤에 놓으면 인증이 안 된다. "위에서 아래로 흐른다"를 항상 의식해야 한다.
  • 에러 미들웨어는 인자 4개(err, req, res, next)로 선언해야 Express가 에러 처리기로 인식한다. 보통 사슬의 맨 끝에 둔다.
  • next()도, 응답도 없이 반환하면 요청은 매달린 채 클라이언트 타임아웃까지 기다린다 — 에러조차 없는 최악의 실패 형태다.

Java 개발자를 위한 대응 관계: 미들웨어 사슬은 서블릿 필터 체인(chain.doFilter() ≒ next())·Spring 인터셉터와 같은 발상이다. 차이는 Express에서는 라우트 핸들러 자체도 미들웨어의 하나라서, 횡단 관심사와 본 처리 로직이 단일한 파이프라인 모델로 통일된다는 점이다.

3. 비동기 핸들러 — await 지점마다 루프에 양보한다

파이프라인의 종착지가 라우트 핸들러인데, 실무의 핸들러는 거의 항상 async다. DB 조회, 외부 API 호출, 파일 접근이 모두 비동기이기 때문이다. 

app.get('/orders/:id', async (req, res) => {
  const order = await db.findOrder(req.params.id);     // ← 여기서 이벤트 루프에 양보
  const items = await db.findItems(order.id);          // ← 여기서도
  res.json({ order, items });
});

await 지점에서 이 핸들러는 멈추고 다른 요청의 콜백이 실행된다 — 동시성의 원천이자, 주의점의 원천이다. 독립적인 두 조회를 순서대로 await하면 대기 시간이 합산되므로, 의존성이 없다면 Promise.all([a, b])로 대기를 겹치는 것이 기본기다.

4. 에러 처리의 두 세계 — 동기의 throw와 비동기의 rejection

그런데 async는 동시성만 가져오는 것이 아니라, 에러가 전파되는 경로를 통째로 바꿔 놓는다. 에러 처리 규칙이 동기와 비동기에서 다르다는 것 — 이것이 이 주제의 전부다.

동기 핸들러비동기(async) 핸들러
에러의 형태throw — 호출 스택을 따라 전파거부된(rejected) Promise — 스택이 아니라 Promise 사슬을 따라 전파
Express 4의 기본 처리프레임워크가 try/catch로 감싸 두어 자동으로 에러 미들웨어로 전달잡지 못한다. 핸들러가 반환한 Promise를 아무도 지켜보지 않음
잡는 방법그대로 두면 됨try/catch + next(err), 래퍼 함수, 또는 자동 전달되는 프레임워크(Express 5·Fastify 등)

왜 이런 차이가 생기는가? async 함수 안의 throw는 사실 throw가 아니라 반환값(Promise)의 거부다. 호출자(프레임워크)가 그 Promise에 .catch()를 붙여 두지 않았다면, 에러는 어디에도 도달하지 못한다. Express 4는 async/await 이전에 설계되어 핸들러의 반환값을 보지 않는다 — 그래서 다음 절의 사고가 난다.

5. 에러가 조용히 사라지는 경로 — unhandled rejection 해부

4절의 "잡지 못한다"가 실제 사고로 번지는 과정을 처음부터 끝까지 따라가 보자. 아래 코드는 정상 경로에서는 완벽히 동작한다. 문제는 DB가 에러를 던지는 날 드러난다. 

// Express 4 기준 — 함정이 있는 코드
app.get('/orders/:id', async (req, res) => {
  const order = await db.findOrder(req.params.id);  // 어느 날 여기서 reject
  res.json(order);
});

에러의 여정을 단계별로 따라가 보자.

① db.findOrder()가 reject ↓ ② await가 이를 다시 throw → async 핸들러 함수가 "거부된 Promise"를 반환 ↓ ③ Express 4는 핸들러의 반환 Promise를 받지도, .catch()를 붙이지도 않음 ↓ ④ 그 Promise를 지켜보는 catch가 프로세스 어디에도 없음 = unhandled rejection 확정 ↓ ⑤ Node 런타임이 'unhandledRejection' 이벤트 발생 기본 동작(Node 15+): 에러 출력 후 프로세스 종료(exit code 1) ↓ ⑥ 부수 피해: 응답을 못 받은 해당 클라이언트는 타임아웃까지 대기, 프로세스가 죽으므로 그 서버가 처리 중이던 다른 모든 요청도 함께 끊김

이 함정이 악질인 이유: ① 정상 경로 테스트로는 절대 안 잡힌다 — 에러가 나야 드러난다. ② 에러 미들웨어를 잘 만들어 두었어도 소용없다 — 에러가 거기까지 도달하지 못하는 문제라서다. ③ 구버전 Node(14 이하)는 경고만 찍고 살아 있었기 때문에, "로그에 경고는 있는데 서버는 도는" 상태로 방치되다가 Node 업그레이드 날 갑자기 서버가 죽기 시작하는 형태로 터진다. 동작은 하는데 에러가 안 보이는 문제의 일반론은 K5 조용한 실패(silent failure)와 오타.html 참조.

5.1 방어 1 — 핸들러 안에서 잡아 next(err)로 넘긴다

app.get('/orders/:id', async (req, res, next) => {
  try {
    const order = await db.findOrder(req.params.id);
    res.json(order);
  } catch (err) {
    next(err);          // 에러 미들웨어로 명시적 전달 — 배관을 손으로 잇는다
  }
});

확실하지만 모든 핸들러에 반복해야 하고, 한 곳이라도 빠뜨리면 그 핸들러가 지뢰가 된다.

5.2 방어 2 — 래퍼로 배관을 자동화한다 (권장)

// 반환된 Promise에 catch를 붙여 next로 배관하는 고차 함수
const wrap = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

app.get('/orders/:id', wrap(async (req, res) => {
  const order = await db.findOrder(req.params.id);
  if (!order) { const e = new Error('not found'); e.status = 404; throw e; }
  res.json(order);      // 핸들러는 던지기만, 잡는 것은 배관의 일
}));

핸들러는 "실패하면 throw"라는 자연스러운 스타일로 돌아가고, 누락 가능성이 라우트 등록 지점 한 곳으로 모인다. Express 5부터는 이 배관이 내장되어(async 핸들러의 rejection을 자동으로 에러 미들웨어로 전달) 래퍼가 불필요하다 — 사용 중인 프레임워크·버전이 async 에러를 자동 전달하는지가 가장 먼저 확인할 계약이다.

5.3 방어 3 — 전역 핸들러는 관측용 최후 방어선

process.on('unhandledRejection', (reason) => {
  logger.fatal({ reason }, 'unhandled rejection — 배관 누락 존재');
  process.exit(1);   // 기록 후 종료·재기동에 맡기는 것이 정석
});

여기서 "에러를 무시하고 계속 돈다"를 선택하면 안 된다 — 어떤 요청이 어떤 상태로 중단됐는지 알 수 없는 채 프로세스가 오염된 상태로 도는 것이므로, 기록하고 죽고, 프로세스 매니저가 다시 띄우는 것이 정석이다. 이 핸들러에 기록이 남는다는 것 자체가 "어딘가 배관이 빠졌다"는 수리 신호다.

6. 흔히 헷갈리는 지점

5절의 배관 문제가 가장 큰 함정이지만, 파이프라인 모델(2절)과 비동기 실행(3절) 자체에서 오는 함정들도 있다 — 대부분 "next()·응답·await 중 무엇을 했고 무엇을 안 했는가"로 환원된다.

① "응답을 이미 보냈는데 또 보냄" — Cannot set headers after they are sent 에러의 정체. 분기에서 return res.status(404)...의 return을 빠뜨려 아래의 정상 응답 코드까지 흘러내린 경우가 대부분이다. 응답을 보내는 문장은 return과 한 몸으로 쓰는 습관이 방어책.

② "forEach 안의 await" — arr.forEach(async ...)는 기다려 주지 않는다(forEach는 반환된 Promise들을 버린다). 전부 끝난 뒤 응답해야 한다면 for...of(순차) 또는 Promise.all(arr.map(...))(병렬)이어야 하고, 버려진 Promise 중 하나가 reject하면 그대로 unhandled rejection이 된다 — 5절 함정의 변종.

③ "미들웨어에서 next()를 부르고 응답도 보냄" — 파이프라인이 계속 진행되어 뒤쪽 핸들러가 또 응답을 시도한다(①과 합병증). next()와 응답 전송은 배타적으로.

④ "에러 미들웨어가 있는데 왜 안 잡히지" — 두 가지를 순서대로 확인: 에러 미들웨어가 라우트들보다 뒤에 등록됐는가, 그리고 async 핸들러의 에러가 거기까지 배관돼 있는가(5절). 전자는 순서 문제, 후자는 세계관 문제다.

★ 7. 언어별 대조

"요청 전후를 감싸는 파이프라인"과 "핸들러의 에러를 누가 잡아 주는가"는 모든 서버 생태계의 공통 설계 문제다. 특히 에러 자동 포획의 범위는 프레임워크마다 달라서, "내 프레임워크는 어디까지 잡아 주는가"를 계약으로 확인하는 습관이 언어를 불문한 교훈이다.

언어파이프라인 개념핸들러 에러의 기본 처리비고
Java 서블릿 필터 체인·Spring 인터셉터 @ControllerAdvice/@ExceptionHandler가 동기·비동기 모두 중앙 포획 아래 심화 참조
JS·TS Express/Koa 미들웨어 Express 4: async 미포획(본문 주제) / Express 5·Fastify: 자동 전달 같은 언어 안에서도 계약이 갈리는 사례
Python WSGI/ASGI 미들웨어 (FastAPI·Django) FastAPI는 async 핸들러의 예외를 자동으로 예외 핸들러에 전달 아래 심화 참조
C++ 프레임워크 의존(Crow·Drogon 등) — 표준 없음 비동기 콜백 밖으로 새는 예외는 대개 std::terminate — 가장 가혹 "경계 안에서 전부 잡는다"가 생존 규칙

7.1 Java — 중앙 예외 처리가 기본 제공되는 세계

@RestControllerAdvice   // 모든 컨트롤러의 예외가 여기로 모인다
public class GlobalExceptionHandler {
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ErrorBody> notFound(OrderNotFoundException e) {
        return ResponseEntity.status(404).body(new ErrorBody(e.getMessage()));
    }
}

Java 관점의 통찰: Spring에서는 핸들러가 던지기만 하면 프레임워크가 잡아 준다 — Express의 wrap() 래퍼가 하던 배관이 프레임워크 계약에 내장된 형태다. 반대로 Java에서도 @Async 메서드나 별도 스레드 풀에 던진 작업의 예외는 이 그물 밖이라 CompletableFuture의 예외 처리를 따로 배관해야 한다 — "비동기 경계를 넘는 에러는 기본 그물에 안 걸린다"는 원리는 언어가 달라도 같다. 예외 전략의 일반론은 C16 예외 처리 전략.html 참조.

7.2 Python — Node와 같은 모델, 다른 기본 계약

from fastapi import FastAPI, HTTPException
app = FastAPI()

@app.get("/orders/{oid}")
async def get_order(oid: int):
    order = await db.find_order(oid)
    if order is None:
        raise HTTPException(status_code=404)   # async 안의 raise가 그대로 에러 응답으로
    return order

Python 관점의 통찰: FastAPI(ASGI)도 이벤트 루프 기반이지만, 프레임워크가 핸들러 코루틴을 자신이 await하므로 예외가 자연히 프레임워크 손에 떨어진다. Express 4의 함정은 "이벤트 루프라서"가 아니라 "핸들러의 반환 Promise를 프레임워크가 지켜보지 않아서"임이 이 대조로 분명해진다 — 같은 비동기 모델에서도 계약 설계에 따라 함정의 유무가 갈린다.

7.3 C++ / JS·TS — 한 줄 요약

C++ 비동기 서버에서 콜백 밖으로 새는 예외는 프로세스 즉사로 이어지는 것이 보통이라, "비동기 경계 안에서 모두 잡는다"는 규율이 선택이 아닌 생존 조건이다. JS·TS 안에서도 Express 4 → 5로 계약이 바뀌었다는 사실은, 프레임워크 버전 업그레이드 노트가 에러 처리 배관의 명세 변경일 수 있음을 보여 준다.

8. 함께 알면 좋은 것

  • graceful shutdown — 종료 신호를 받으면 새 요청 수락을 멈추고 진행 중인 요청을 마친 뒤 내려가는 절차. 5.3절의 "기록하고 죽는다"와 짝을 이루며, O4 헬스체크와 프로세스 관리.html에서 다룬다.
  • 요청 본문 크기 제한·타임아웃 — express.json({ limit }), 서버/소켓 타임아웃. 기본값 방치는 손쉬운 서비스 거부 표면이 된다.
  • uncaughtException — unhandled rejection의 동기 세계 짝. 처리 원칙(기록 후 종료)도 같다.
  • 구조적 로깅과 요청 상관관계 ID — 비동기 서버에서는 여러 요청의 로그가 뒤섞이므로 요청별 ID가 필수다. P1 로깅과 관측성 기초.html 참조.
  • Fastify·Koa — 같은 미들웨어 개념의 다른 구현. 특히 에러 자동 포획·성능·스키마 검증에서 Express와의 계약 차이를 비교해 볼 것.

9. 한 장 요약

  • Node 서버의 원형은 요청마다 불리는 콜백 하나. 프레임워크는 그 위의 라우팅·파싱·에러 처리 정돈층.
  • 미들웨어는 등록 순서대로 흐르는 파이프라인 — 각 단계는 next() 또는 응답 중 하나를 반드시. 에러 미들웨어는 인자 4개, 맨 끝에.
  • async 핸들러의 throw는 실은 Promise 거부다. 프레임워크가 그 Promise를 지켜보지 않으면(Express 4) 에러 미들웨어가 있어도 도달하지 못한다.
  • 도달하지 못한 거부 = unhandled rejection → 최신 Node 기본 동작은 프로세스 종료. 정상 경로 테스트로는 안 잡히는 지뢰다.
  • 방어는 배관의 자동화: 래퍼(wrap) 또는 자동 전달 프레임워크(Express 5 등)로 모든 async 에러를 중앙 에러 처리기로. 전역 핸들러는 기록·종료용 최후 방어선.

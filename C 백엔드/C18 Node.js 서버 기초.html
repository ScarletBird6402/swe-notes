C18 Node.js 서버 기초

0. 한눈에 보는 결론

  • Node HTTP 서버의 원형은 "요청이 올 때마다 호출되는 콜백 함수 하나"다. 프레임워크(Express 등)는 그 콜백 안에서 라우팅·파싱·에러 처리를 정리해 주는 층이다.
  • 미들웨어(middleware)는 요청이 핸들러에 닿기 전후로 거치는 함수들의 파이프라인이다. 등록한 순서대로 실행되고, 각 미들웨어는 next()를 불러 다음으로 넘기거나, 응답을 보내 파이프라인을 끝내거나, 둘 중 하나를 반드시 해야 한다 — 둘 다 안 하면 요청은 영원히 매달린다.
  • 핸들러는 사실상 전부 비동기다(DB·외부 API 호출). 비동기 핸들러의 에러 처리에는 함정이 있다: async 함수 안에서 던져진 에러는 동기 세계의 try/catch와 프레임워크의 기본 에러 처리망에 잡히지 않을 수 있다.
  • 그 결과가 unhandled rejection(처리되지 않은 Promise 거부) — 에러가 어떤 catch에도 닿지 못한 채 떠도는 상태다. 최신 Node의 기본 동작은 프로세스 종료이므로, 핸들러 하나의 누락이 서버 전체를 내린다.
  • 방어의 원칙: 모든 비동기 핸들러의 에러가 반드시 중앙 에러 처리기로 흘러들게 배관한다(래퍼 함수 또는 자동 전달을 지원하는 프레임워크 버전 사용). 전역 unhandledRejection 핸들러는 최후의 관측 지점이지 처리 수단이 아니다.

1. 원형 — http 모듈의 서버는 콜백 하나다

const http = require('http');

const server = http.createServer((req, res) => {   // 모든 요청이 이 함수로 들어온다
  res.statusCode = 200;
  res.setHeader('Content-Type', 'application/json');
  res.end(JSON.stringify({ ok: true }));
});

server.listen(3000);

이것이 전부다. req(요청)는 읽는 스트림, res(응답)는 쓰는 스트림이며, URL이 무엇이든 메서드가 무엇이든 이 콜백 하나가 받는다. 런타임 구조(C17 Node.js 런타임 구조.html)와 연결하면: 이 콜백은 이벤트 루프의 poll 단계에서, 소켓에 요청이 도착했다는 OS 통지를 받아 호출된다. 요청 1만 개가 동시에 와도 스레드는 하나 — 콜백이 빨리 반환하고 I/O는 양보한다는 전제 하에서다.

원형만으로 실무 서버를 짜면 URL 분기(라우팅), 본문 파싱, 에러 처리를 전부 손으로 해야 한다. 이 반복 작업을 정돈한 것이 프레임워크이고, 이 문서는 사실상 표준인 Express를 대표 예시로 쓴다(개념은 Koa·Fastify 등에도 그대로 통한다).

2. 미들웨어 — 순서가 곧 설계다

1절의 "콜백 하나"에 모든 일을 밀어 넣는 대신, Express는 그 일을 여러 함수로 쪼개 사슬로 잇는다. 즉 Express 서버는 미들웨어의 사슬이다. 요청은 등록된 순서대로 미들웨어를 통과하며, 각 미들웨어는 세 가지 중 하나를 한다: 가공 후 next()로 통과 / 응답을 보내고 종료 / next(err)로 에러 경로 진입.

요청 ─> [로깅] ─> [본문 파싱] ─> [인증] ─> [라우트 핸들러] ─> 응답 │ │ │ └── 어느 단계든 next(err)를 부르면 ──> [에러 미들웨어] ─> 에러 응답
const express = require('express');
const app = express();

app.use(logger);                 // ① 모든 요청 로깅
app.use(express.json());         // ② JSON 본문 파싱 → req.body
app.use('/admin', requireAuth);  // ③ 경로 한정 미들웨어

app.get('/users/:id', async (req, res) => {   // ④ 라우트 핸들러 (미들웨어의 일종)
  const user = await db.findUser(req.params.id);
  if (!user) return res.status(404).json({ error: 'not found' });
  res.json(user);
});

app.use((err, req, res, next) => {            // ⑤ 에러 미들웨어: 인자 4개가 식별자
  console.error(err);
  res.status(500).json({ error: 'internal error' });
});
  • 순서가 의미다. 본문 파싱(②)보다 앞에 놓인 미들웨어에서는 req.body가 없다. 인증(③)을 라우트보다 뒤에 놓으면 인증이 안 된다. "위에서 아래로 흐른다"를 항상 의식해야 한다.
  • 에러 미들웨어는 인자 4개(err, req, res, next)로 선언해야 Express가 에러 처리기로 인식한다. 보통 사슬의 맨 끝에 둔다.
  • next()도, 응답도 없이 반환하면 요청은 매달린 채 클라이언트 타임아웃까지 기다린다 — 에러조차 없는 최악의 실패 형태다.

Java 개발자를 위한 대응 관계: 미들웨어 사슬은 서블릿 필터 체인(chain.doFilter() ≒ next())·Spring 인터셉터와 같은 발상이다. 차이는 Express에서는 라우트 핸들러 자체도 미들웨어의 하나라서, 횡단 관심사와 본 처리 로직이 단일한 파이프라인 모델로 통일된다는 점이다.

3. 비동기 핸들러 — await 지점마다 루프에 양보한다

파이프라인의 종착지가 라우트 핸들러인데, 실무의 핸들러는 거의 항상 async다. DB 조회, 외부 API 호출, 파일 접근이 모두 비동기이기 때문이다. 

app.get('/orders/:id', async (req, res) => {
  const order = await db.findOrder(req.params.id);     // ← 여기서 이벤트 루프에 양보
  const items = await db.findItems(order.id);          // ← 여기서도
  res.json({ order, items });
});

await 지점에서 이 핸들러는 멈추고 다른 요청의 콜백이 실행된다 — 동시성의 원천이자, 주의점의 원천이다. 독립적인 두 조회를 순서대로 await하면 대기 시간이 합산되므로, 의존성이 없다면 Promise.all([a, b])로 대기를 겹치는 것이 기본기다.

4. 에러 처리의 두 세계 — 동기의 throw와 비동기의 rejection

그런데 async는 동시성만 가져오는 것이 아니라, 에러가 전파되는 경로를 통째로 바꿔 놓는다. 에러 처리 규칙이 동기와 비동기에서 다르다는 것 — 이것이 이 주제의 전부다.

동기 핸들러비동기(async) 핸들러
에러의 형태throw — 호출 스택을 따라 전파거부된(rejected) Promise — 스택이 아니라 Promise 사슬을 따라 전파
Express 4의 기본 처리프레임워크가 try/catch로 감싸 두어 자동으로 에러 미들웨어로 전달잡지 못한다. 핸들러가 반환한 Promise를 아무도 지켜보지 않음
잡는 방법그대로 두면 됨try/catch + next(err), 래퍼 함수, 또는 자동 전달되는 프레임워크(Express 5·Fastify 등)

왜 이런 차이가 생기는가? async 함수 안의 throw는 사실 throw가 아니라 반환값(Promise)의 거부다. 호출자(프레임워크)가 그 Promise에 .catch()를 붙여 두지 않았다면, 에러는 어디에도 도달하지 못한다. Express 4는 async/await 이전에 설계되어 핸들러의 반환값을 보지 않는다 — 그래서 다음 절의 사고가 난다.

5. 에러가 조용히 사라지는 경로 — unhandled rejection 해부

4절의 "잡지 못한다"가 실제 사고로 번지는 과정을 처음부터 끝까지 따라가 보자. 아래 코드는 정상 경로에서는 완벽히 동작한다. 문제는 DB가 에러를 던지는 날 드러난다. 

// Express 4 기준 — 함정이 있는 코드
app.get('/orders/:id', async (req, res) => {
  const order = await db.findOrder(req.params.id);  // 어느 날 여기서 reject
  res.json(order);
});

에러의 여정을 단계별로 따라가 보자.

① db.findOrder()가 reject ↓ ② await가 이를 다시 throw → async 핸들러 함수가 "거부된 Promise"를 반환 ↓ ③ Express 4는 핸들러의 반환 Promise를 받지도, .catch()를 붙이지도 않음 ↓ ④ 그 Promise를 지켜보는 catch가 프로세스 어디에도 없음 = unhandled rejection 확정 ↓ ⑤ Node 런타임이 'unhandledRejection' 이벤트 발생 기본 동작(Node 15+): 에러 출력 후 프로세스 종료(exit code 1) ↓ ⑥ 부수 피해: 응답을 못 받은 해당 클라이언트는 타임아웃까지 대기, 프로세스가 죽으므로 그 서버가 처리 중이던 다른 모든 요청도 함께 끊김

이 함정이 악질인 이유: ① 정상 경로 테스트로는 절대 안 잡힌다 — 에러가 나야 드러난다. ② 에러 미들웨어를 잘 만들어 두었어도 소용없다 — 에러가 거기까지 도달하지 못하는 문제라서다. ③ 아주 오래된 Node(14 이하)는 경고만 찍고 살아 있었기 때문에, "로그에 경고는 있는데 서버는 도는" 상태로 방치되다가 런타임 업그레이드 날 갑자기 서버가 죽기 시작하는 형태로 터진다(현재 유지되는 LTS 계열은 모두 종료가 기본 동작이다). 동작은 하는데 에러가 안 보이는 문제의 일반론은 K5 조용한 실패(silent failure)와 오타.html 참조.

5.1 방어 1 — 핸들러 안에서 잡아 next(err)로 넘긴다

app.get('/orders/:id', async (req, res, next) => {
  try {
    const order = await db.findOrder(req.params.id);
    res.json(order);
  } catch (err) {
    next(err);          // 에러 미들웨어로 명시적 전달 — 배관을 손으로 잇는다
  }
});

확실하지만 모든 핸들러에 반복해야 하고, 한 곳이라도 빠뜨리면 그 핸들러가 지뢰가 된다.

5.2 방어 2 — 래퍼로 배관을 자동화한다 (권장)

// 반환된 Promise에 catch를 붙여 next로 배관하는 고차 함수
const wrap = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

app.get('/orders/:id', wrap(async (req, res) => {
  const order = await db.findOrder(req.params.id);
  if (!order) { const e = new Error('not found'); e.status = 404; throw e; }
  res.json(order);      // 핸들러는 던지기만, 잡는 것은 배관의 일
}));

핸들러는 "실패하면 throw"라는 자연스러운 스타일로 돌아가고, 누락 가능성이 라우트 등록 지점 한 곳으로 모인다. Express 5부터는 이 배관이 내장되어(async 핸들러의 rejection을 자동으로 에러 미들웨어로 전달) 래퍼가 불필요하다 — 사용 중인 프레임워크·버전이 async 에러를 자동 전달하는지가 가장 먼저 확인할 계약이다.

최근에는: Express 5가 안정판으로 자리 잡아(2020년대 중반 기준) 신규 프로젝트에서는 이 배관이 기본 제공된다. 따라서 본문의 함정은 사라진 문제가 아니라 적용 범위가 좁아진 문제로 이해하는 편이 정확하다 — 4 계열을 유지보수하는 코드베이스, 그리고 프레임워크가 지켜보지 않는 자리(setTimeout 콜백 안의 async, 이벤트 리스너, 던져 놓고 안 기다리는 작업)에서는 버전과 무관하게 그대로 발생한다. 원리(비동기 경계를 넘는 에러는 기본 그물에 안 걸린다)가 본체이고, 프레임워크의 자동 전달은 그중 가장 흔한 경로 하나를 막아 준 것이다.

5.3 방어 3 — 전역 핸들러는 관측용 최후 방어선

process.on('unhandledRejection', (reason) => {
  logger.fatal({ reason }, 'unhandled rejection — 배관 누락 존재');
  process.exit(1);   // 기록 후 종료·재기동에 맡기는 것이 정석
});

여기서 "에러를 무시하고 계속 돈다"를 선택하면 안 된다 — 어떤 요청이 어떤 상태로 중단됐는지 알 수 없는 채 프로세스가 오염된 상태로 도는 것이므로, 기록하고 죽고, 프로세스 매니저가 다시 띄우는 것이 정석이다. 이 핸들러에 기록이 남는다는 것 자체가 "어딘가 배관이 빠졌다"는 수리 신호다.

6. 흔히 헷갈리는 지점

5절의 배관 문제가 가장 큰 함정이지만, 파이프라인 모델(2절)과 비동기 실행(3절) 자체에서 오는 함정들도 있다 — 대부분 "next()·응답·await 중 무엇을 했고 무엇을 안 했는가"로 환원된다.

① "응답을 이미 보냈는데 또 보냄" — Cannot set headers after they are sent 에러의 정체. 분기에서 return res.status(404)...의 return을 빠뜨려 아래의 정상 응답 코드까지 흘러내린 경우가 대부분이다. 응답을 보내는 문장은 return과 한 몸으로 쓰는 습관이 방어책.

② "forEach 안의 await" — arr.forEach(async ...)는 기다려 주지 않는다(forEach는 반환된 Promise들을 버린다). 전부 끝난 뒤 응답해야 한다면 for...of(순차) 또는 Promise.all(arr.map(...))(병렬)이어야 하고, 버려진 Promise 중 하나가 reject하면 그대로 unhandled rejection이 된다 — 5절 함정의 변종.

③ "미들웨어에서 next()를 부르고 응답도 보냄" — 파이프라인이 계속 진행되어 뒤쪽 핸들러가 또 응답을 시도한다(①과 합병증). next()와 응답 전송은 배타적으로.

④ "에러 미들웨어가 있는데 왜 안 잡히지" — 두 가지를 순서대로 확인: 에러 미들웨어가 라우트들보다 뒤에 등록됐는가, 그리고 async 핸들러의 에러가 거기까지 배관돼 있는가(5절). 전자는 순서 문제, 후자는 세계관 문제다.

★ 7. 언어별 대조

"요청 전후를 감싸는 파이프라인"과 "핸들러의 에러를 누가 잡아 주는가"는 모든 서버 생태계의 공통 설계 문제다. 그런데 두 번째 질문의 답은 언어마다 예외가 어떤 길로 돌아오는가에 따라 갈린다 — 호출 스택을 타고 되돌아오는 언어(Java·C++)와, 스택이 끊긴 자리를 "값으로 실어 나르는 배관"(Promise·코루틴·future)이 대신하는 언어(JS·Python·C++의 비동기)는 기본 그물의 모양이 다르다. 아래 표는 그 차이를 한눈에 놓고, 이어지는 절에서 언어마다 "어디까지 잡아 주고 어디서 새는가"를 내부 기제로 따라간다. "내 프레임워크는 어디까지 잡아 주는가"를 계약으로 확인하는 습관이 언어를 불문한 교훈이다.

언어파이프라인 개념핸들러 에러의 기본 처리그물 밖으로 새는 지점
Java 서블릿 필터 체인·Spring 인터셉터 요청당 스레드 — 예외가 호출 스택을 타고 @ControllerAdvice까지 되돌아온다 필터 안에서 던진 예외, @Async void로 던져 놓은 작업
JS·TS Express/Koa 미들웨어 Express 4: 반환 Promise 무시(본문 주제) / Express 5·Fastify: 자동 전달 프레임워크가 지켜보지 않는 Promise 전부. TS 타입은 체인 순서를 보증하지 못한다
Python WSGI/ASGI 미들웨어 (FastAPI·Django) 코루틴은 await해야만 실행되므로 프레임워크가 반드시 기다린다 → 예외 핸들러로 전달 create_task로 던져 놓은 작업 — 경고만 남고 계속 돈다
C++ 프레임워크 의존(Crow·Drogon 등) — 표준 없음 콜백 밖으로 새는 예외는 대개 std::terminate — 가장 가혹 std::future에 실린 예외를 아무도 get()하지 않으면 경고조차 없이 소멸

7.1 Java — 요청당 스레드가 예외의 귀갓길을 지켜 준다

Java 서버(서블릿 컨테이너 + Spring MVC)의 기본 모델은 요청 하나에 스레드 하나다. 그 스레드가 필터 체인 → 디스패처 서블릿 → 인터셉터 → 컨트롤러를 하나의 호출 스택 위에서 차례로 부른다. 그래서 컨트롤러가 던진 예외는 어디로도 사라지지 않고 스택을 거슬러 디스패처 서블릿까지 돌아오며, 거기서 @ControllerAdvice·@ExceptionHandler가 받아 응답으로 바꾼다. 5.2절의 래퍼가 필요 없는 이유는 Spring이 특별히 친절해서가 아니라, 스택이 끊기지 않는 실행 모델이라 예외의 기본 귀갓길이 살아 있기 때문이다. 

// ① 필터 — 서블릿 필터 체인: chain.doFilter()가 Express의 next()에 해당
@Component
public class LoggingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        log.info("{} {}", req.getMethod(), req.getRequestURI());
        chain.doFilter(req, res);   // 안 부르면 요청이 여기서 멈춘다 — 2절의 함정과 동일
    }
}

// ② 컨트롤러 — 그냥 던진다. 잡는 것은 프레임워크 계약
@GetMapping("/orders/{id}")
Order find(@PathVariable long id) {
    return repo.findById(id).orElseThrow(() -> new NotFoundException(id));
}

// ③ 중앙 포획 — 컨트롤러·인터셉터에서 난 예외는 전부 여기로 온다
@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(NotFoundException.class)
    ResponseEntity<Map<String, String>> notFound(NotFoundException e) {
        return ResponseEntity.status(404).body(Map.of("error", "not found"));
    }
}

// ④ 그물 밖 — 호출자는 이미 응답을 보냈고, 이 코드는 다른 스레드에서 돈다
@Async
public void sendReceipt(long orderId) {
    mailer.send(orderId);   // 여기서 throw → AsyncUncaughtExceptionHandler에 로그만 남는다
}

그물의 경계가 두 곳에서 드러난다. 첫째, 필터는 디스패처 서블릿 바깥에 있다. 필터 체인은 서블릿 컨테이너가 돌리는 층이고 @ControllerAdvice는 디스패처 서블릿 안쪽의 장치라서, 필터에서 던진 예외(인증 토큰 파싱 실패 등)는 그 그물에 걸리지 않고 컨테이너의 기본 에러 페이지로 떨어진다. 같은 "요청 전후 처리"라도 인터셉터(디스패처 안쪽)에서 던지면 잡히고 필터에서 던지면 안 잡히는 것은, Express에서 미들웨어와 라우트 핸들러가 단일 파이프라인인 것과 대비되는 Java 특유의 계층 구조다. 둘째, 스택을 벗어나는 순간 Java도 똑같이 샌다. @Async는 메서드를 별도 스레드 풀에 넘기는 프록시라서, 반환형이 void면 호출자는 결과를 받을 길이 없고 예외는 AsyncUncaughtExceptionHandler(기본 동작: 로그)에서 끝난다 — 프로세스는 살아 있으니 Node의 unhandled rejection보다 조용하지만 "누구도 회수하지 않은 실패"라는 본질은 같다. 반면 CompletableFuture를 반환하면 Spring MVC가 그 future를 지켜보다가 완료 시 요청을 다시 디스패치해 예외를 @ControllerAdvice로 보낸다 — Express 5가 반환 Promise를 지켜보는 것과 같은 계약이다.

Java 관점의 통찰(JVM과 실행 모델): 요청당 스레드 모델의 비용은 OS 스레드 자체다 — 스레드마다 수백 KB의 스택을 쥐고, 블로킹 I/O 동안 그 스레드는 놀면서도 메모리를 점유한다. Node가 "스레드 하나 + await마다 양보"로 이 비용을 피한 것이라면, Java의 답은 반대 방향이었다: 가상 스레드(virtual thread — JVM이 스케줄링하는 매우 가벼운 스레드로, 블로킹 시 OS 스레드를 반납한다)로 스레드를 싸게 만들어 블로킹 스타일 코드와 스택 기반 예외 전파를 그대로 유지한다. 2020년대 중반 기준 Java 21 이상과 Spring Boot 3.2 이상에서는 설정 한 줄(spring.threads.virtual.enabled=true)로 요청 처리 스레드가 가상 스레드로 바뀌며, 이때 예외 처리 코드는 한 글자도 바꿀 필요가 없다. 같은 동시성 문제를 "스택을 끊고 배관을 새로 깐다"(JS)와 "스택을 유지하고 스레드를 싸게 만든다"(Java)로 각기 푼 셈이다.

7.2 JS·TS — 배관은 런타임 계약이고, 타입은 그 계약을 보증하지 못한다

본문이 이미 본진이므로 여기서는 두 가지만 보탠다. 하나는 Express가 미들웨어를 식별하는 방식이 타입이 아니라 런타임 반영(reflection)이라는 점이고, 다른 하나는 TS의 타입이 미들웨어 체인 어디에서 끊기는가다.

Express는 등록된 함수의 fn.length(선언된 매개변수 개수)를 보고 4개면 에러 미들웨어, 아니면 일반 미들웨어로 분류한다. 이것이 2절의 "인자 4개가 식별자"의 정체다. 그래서 (err, req, res)처럼 next를 생략하면 TS는 아무 불평이 없지만 런타임은 이를 일반 미들웨어로 보고, 에러 경로에서 절대 부르지 않는다. Express 5의 자동 전달도 같은 층의 계약이다 — 핸들러의 반환값이 Promise면 .catch(next)를 붙이는 것(2020년대 중반 기준 npm의 latest가 5 계열), 4는 반환값을 버리는 것. 타입 정의 파일은 두 버전에서 거의 같으므로, 이 차이는 컴파일러가 아니라 문서와 버전 번호로만 알 수 있다. 

// ① 미들웨어가 req에 붙인 값은 타입 시스템이 모른다 — 선언 병합으로 '알려 준다'
declare global {
  namespace Express {
    interface Request { user?: { id: string; role: 'admin' | 'member' } }
  }
}

const requireAuth: RequestHandler = (req, res, next) => {
  const user = verify(req.headers.authorization);   // 실패 시 undefined
  if (!user) { res.status(401).end(); return; }
  req.user = user;
  next();
};

app.get('/me', (req, res) => {
  res.json(req.user!.id);   // '!'는 타입만 잠재운다 — requireAuth가 앞에 없으면 런타임 TypeError
});

// ② 에러 미들웨어의 식별은 인자 개수(fn.length) — 타입이 아니라 런타임 반영
const onError: ErrorRequestHandler = (err, req, res, _next) => {   // 4번째 인자를 지우면 일반 미들웨어가 된다
  res.status(err.status ?? 500).json({ error: err.message });
};

①이 TS 타입이 끊기는 지점이다. req.user는 인증 미들웨어를 통과한 뒤에만 존재하지만, 타입 시스템에는 "이 라우트 앞에 어떤 미들웨어가 있는가"라는 정보가 없다. 선언 병합(declaration merging — 같은 이름의 interface를 여러 곳에서 선언하면 하나로 합쳐지는 TS 규칙)으로 Request에 필드를 덧붙이는 것이 관행이지만, 이 필드는 모든 라우트에서 전역으로 보이므로 ?로 선언할 수밖에 없고, 그러면 라우트마다 !나 분기가 따라붙는다. 제네릭 Request<Params, ResBody, ReqBody>로 경로 변수·본문 타입을 지정하는 방법도 마찬가지로 "파싱 미들웨어가 앞에 있었다"는 약속을 타입으로 적는 것이지 검증하는 것이 아니다. TS 타입은 컴파일 후 지워지므로(타입 소거), 이 약속이 깨져도 런타임에는 아무 검사도 남지 않는다 — 체인 순서라는 2절의 핵심 계약은 타입 밖에 있다.

JS·TS 관점의 통찰(이벤트 루프와 unhandled rejection의 판정 시점): Node가 "처리되지 않은 거부"를 확정하는 시점은 거부 즉시가 아니라 현재 매크로태스크가 끝나고 마이크로태스크 큐가 비워진 직후다. 그 시점까지 .catch나 await가 붙지 않은 거부된 Promise가 있으면 unhandledRejection이 발생한다. 이것이 5.2절 래퍼가 동작하는 원리다 — Promise.resolve(fn(...)).catch(next)는 핸들러 호출과 같은 동기 구간에서 catch를 붙이므로 판정 시점 이전에 배관이 완성된다. 반대로 Promise를 변수에 담아 두고 "나중에" catch를 붙이는 설계는 한 틱만 늦어도 거부 판정을 받는다(그 뒤 catch가 붙으면 rejectionHandled가 따로 발생한다). 배관은 즉시 이어야 한다는 것이 이 런타임의 규칙이다.

7.3 Python — 코루틴은 게으르므로 프레임워크가 반드시 기다린다

Python에도 같은 파이프라인 모델이 있고(ASGI 미들웨어의 call_next가 next()에 해당), 예외 핸들러를 중앙에 등록하는 방식도 같다. 그런데 Express 4의 함정만은 성립하지 않는다 — 그 이유가 언어 차이의 핵심이다. JS의 async 함수는 호출 즉시 첫 await까지 실행되고 Promise를 돌려주므로, 호출자가 반환값을 버려도 함수는 이미 달리고 있다. Python의 async def 함수는 호출해도 코루틴 객체를 만들 뿐 한 줄도 실행하지 않는다 — 누군가 await하거나 태스크로 감싸야 비로소 돈다. 따라서 ASGI 프레임워크는 핸들러의 반환 코루틴을 무시할 수가 없다. 무시하면 핸들러가 아예 실행되지 않고 "coroutine was never awaited" 경고만 남으니, 반드시 await하게 되고, 그 await가 곧 예외의 귀갓길이 된다. 

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

@app.middleware("http")                          # ASGI 미들웨어 — call_next가 next()에 해당
async def timing(request: Request, call_next):
    response = await call_next(request)          # 다음 단계를 '기다린다' — 예외도 이 await로 되돌아온다
    return response

@app.exception_handler(LookupError)              # 중앙 포획: async·sync 핸들러 모두
async def not_found(request: Request, exc: LookupError):
    return JSONResponse(status_code=404, content={"error": "not found"})

@app.get("/orders/{id}")
async def find(id: int):
    return await db.find_order(id)               # 프레임워크가 이 코루틴을 await하므로 예외가 되돌아온다

@app.get("/report")
def report():                                    # 동기 핸들러 → 스레드 풀에서 실행, 이벤트 루프를 막지 않음
    return heavy_sync()

마지막 핸들러가 Python 특유의 지점이다. FastAPI는 def로 선언한 동기 핸들러를 스레드 풀에서 돌려 이벤트 루프를 보호한다 — Node에는 없는 선택지인데, GIL(global interpreter lock — 한 프로세스에서 Python 바이트코드를 한 번에 한 스레드만 실행하게 하는 잠금) 때문에 CPU 작업은 여전히 병렬이 아니지만 블로킹 I/O 동안에는 GIL이 풀리므로 루프가 계속 돈다. 반대로 async def 안에서 동기 블로킹 호출을 하면 Node에서 콜백이 루프를 붙드는 것과 정확히 같은 사고가 난다 — "핸들러 선언 방식이 실행 스레드를 정한다"는 계약을 알아야 하는 이유다. 그리고 프레임워크가 기다려 주지 않는 자리, 즉 루프에 던져 놓고 아무도 결과를 기다리지 않는 작업의 예외는 Node와 같은 방식으로 사라진다. 

import asyncio

async def failing():
    raise ValueError("boom")

async def main():
    # ① 기다리는 경우: 예외가 정상적으로 전파된다
    try:
        await failing()
    except ValueError:
        print("잡힘")

    # ② 던져 놓고 안 기다리는 경우: 여기서 예외는 어디로도 가지 않는다
    asyncio.create_task(failing())        # Node의 "await 없이 호출한 async 함수"와 동형
    await asyncio.sleep(0.1)
    # 태스크가 수거될 때에야 경고: "Task exception was never retrieved"
    #  → 즉시 실패하지 않고 '나중에 로그로만' 알려지는 조용한 실패

asyncio.run(main())

Python 관점의 통찰: Task exception was never retrieved는 Node의 unhandled rejection과 같은 사건의 다른 이름이다 — 결과를 아무도 회수하지 않은 비동기 작업의 실패. 다만 기본 처리가 다르다: Node는 프로세스를 종료시키고, Python은 경고만 남기고 계속 돈다(그것도 태스크 객체가 가비지 컬렉션될 때라서 시점조차 늦다). 어느 쪽이 나은가는 C16 예외 처리 전략.html의 오랜 논쟁(빨리 죽기 vs 계속 돌기)이지만, 대응은 동일하다 — 던져 놓는 작업에는 반드시 예외 처리를 붙이거나(task.add_done_callback으로 결과 회수), 애초에 기다릴 수 있게 설계한다. 여기서 JS의 forEach 안 await 함정(6절 ②)이 왜 생기는지도 함께 풀린다 — 반환된 코루틴/Promise를 버리는 구조가 곧 이 함정의 일반형이기 때문이다. 게으른 코루틴이라는 언어 설계가 프레임워크 층의 함정 하나를 없앴지만, 사용자 층의 함정은 그대로 남았다.

7.4 C++ — 비동기 경계를 넘는 예외는 프로그램을 죽이고, 실어 나른 예외는 소리 없이 버려진다

5절의 함정("에러가 어떤 catch에도 닿지 못한다")은 Node만의 사정이 아니라 비동기 일반의 구조적 문제다. C++에서는 그 결과가 가장 가혹한 형태로 나타난다 — 콜백이나 스레드 밖으로 예외가 새어 나가면 프로그램이 즉시 종료된다. 

// 비동기 콜백에서 예외가 새면: 이 예외를 받아 줄 호출 스택이 이미 사라졌다
server.on_request([](Request req, Response res) {
    auto data = db.query(req.id);   // 여기서 throw 하면?
    res.send(data);                 // → 콜백 밖으로 전파 → std::terminate() → 프로세스 종료
});

// 그래서 규율은 "경계 안에서 전부 잡는다"가 된다
server.on_request([](Request req, Response res) {
    try {
        res.send(db.query(req.id));
    } catch (const std::exception& e) {
        res.status(500).send("internal error");   // 경계를 넘기 전에 반드시 흡수
    }
});

그런데 C++에도 Promise에 해당하는 배관이 있다. std::future는 결과 또는 예외를 값으로 실어 나르는 객체로, 작업 스레드에서 던진 예외는 future 안에 저장됐다가 get()을 부르는 쪽에서 다시 throw된다 — "거부된 상태를 값으로 들고 다닌다"는 Promise의 발상과 같다. 차이는 회수하지 않았을 때의 처리다. 

// std::future — 예외를 '값으로' 실어 나른다 (Promise의 거부 상태와 같은 배관)
std::future<Data> f = std::async(std::launch::async, [id] { return db.query(id); });
try {
    Data d = f.get();                 // 작업 스레드에서 던진 예외가 여기서 다시 throw
} catch (const std::exception& e) { /* 처리 */ }

// get()을 아무도 부르지 않으면? 저장된 예외는 future의 소멸자에서 경고 한 줄 없이 사라진다
//  → Node는 프로세스 종료, Python은 경고, C++은 완전한 무음 — 같은 사건의 세 가지 기본값

// 수명 함정 — 콜백은 등록한 함수가 반환한 '뒤에' 불린다
void handle(Request& req, Response& res) {
    db.query_async(req.id, [&res](Data d) {   // res를 참조로 캡처
        res.send(d);                          // handle()은 이미 반환 → res는 댕글링 참조
    });
}

마지막 예제가 C++만의 두 번째 함정이다. Node에서는 콜백이 req·res를 클로저로 붙들면 가비지 컬렉터가 그 객체들을 콜백이 끝날 때까지 살려 둔다. C++에는 그런 보호가 없다 — 콜백이 참조나 원시 포인터로 붙든 객체는 등록 함수가 반환하는 순간 사라질 수 있고, 나중에 불린 콜백은 이미 죽은 메모리를 건드린다. 비동기 콜백은 필요한 것을 값으로 캡처하거나 std::shared_ptr로 수명을 연장해야 하며, 이 규율을 잊은 코드는 예외가 아니라 정의되지 않은 동작으로 실패한다.

C++ 관점의 통찰(수명·예외 안전성): 예외가 스택을 거슬러 올라가는 과정에서 C++은 지역 객체들의 소멸자를 차례로 호출한다(스택 되감기, stack unwinding). 그런데 비동기 콜백은 자신을 등록한 함수의 스택 위에 있지 않다 — 등록 함수는 이미 반환했고, 콜백은 나중에 이벤트 루프의 스택에서 불린다. 그래서 "호출한 쪽에서 잡는다"는 예외의 기본 모델 자체가 성립하지 않으며, 되감기가 이벤트 루프의 바닥까지 닿으면 std::terminate다.
이것이 Node의 unhandled rejection과 정확히 같은 사건임을 보라: 비동기는 호출 스택을 끊고, 예외는 호출 스택을 타고 전파되므로, 비동기 경계를 넘는 순간 예외의 귀갓길이 사라진다. Promise가 "거부된 상태"를 값으로 들고 다니는 것은 이 끊긴 길을 대신할 새 배관을 만든 것이고, 5.2절의 래퍼는 그 배관을 프레임워크에 연결하는 작업이었다. C++20 코루틴의 co_await도 같은 원리로 예외를 다시 throw해 주지만, 누구도 기다리지 않는 분리(detached) 코루틴에서 새는 예외는 다시 std::terminate로 돌아간다 — 배관을 어디까지 이었는가를 프로그래머가 전적으로 책임지는 언어다.

8. 함께 알면 좋은 것

  • graceful shutdown — 종료 신호를 받으면 새 요청 수락을 멈추고 진행 중인 요청을 마친 뒤 내려가는 절차. 5.3절의 "기록하고 죽는다"와 짝을 이루며, O4 헬스체크와 프로세스 관리.html에서 다룬다.
  • 요청 본문 크기 제한·타임아웃 — express.json({ limit }), 서버/소켓 타임아웃. 기본값 방치는 손쉬운 서비스 거부 표면이 된다.
  • uncaughtException — unhandled rejection의 동기 세계 짝. 처리 원칙(기록 후 종료)도 같다.
  • 구조적 로깅과 요청 상관관계 ID — 비동기 서버에서는 여러 요청의 로그가 뒤섞이므로 요청별 ID가 필수다. P1 로깅과 관측성 기초.html 참조.
  • Fastify·Koa — 같은 미들웨어 개념의 다른 구현. 특히 에러 자동 포획·성능·스키마 검증에서 Express와의 계약 차이를 비교해 볼 것.

9. 한 장 요약

  • Node 서버의 원형은 요청마다 불리는 콜백 하나. 프레임워크는 그 위의 라우팅·파싱·에러 처리 정돈층.
  • 미들웨어는 등록 순서대로 흐르는 파이프라인 — 각 단계는 next() 또는 응답 중 하나를 반드시. 에러 미들웨어는 인자 4개, 맨 끝에.
  • async 핸들러의 throw는 실은 Promise 거부다. 프레임워크가 그 Promise를 지켜보지 않으면(Express 4) 에러 미들웨어가 있어도 도달하지 못한다.
  • 도달하지 못한 거부 = unhandled rejection → 최신 Node 기본 동작은 프로세스 종료. 정상 경로 테스트로는 안 잡히는 지뢰다.
  • 방어는 배관의 자동화: 래퍼(wrap) 또는 자동 전달 프레임워크(Express 5 등)로 모든 async 에러를 중앙 에러 처리기로. 전역 핸들러는 기록·종료용 최후 방어선.

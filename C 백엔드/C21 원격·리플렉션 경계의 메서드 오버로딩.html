C21 원격·리플렉션 경계의 메서드 오버로딩

0. 한눈에 보는 결론

  • 오버로딩(overloading)은 컴파일 타임의 선택이다 — 어느 메서드가 불릴지는 컴파일러가 인자의 정적 타입을 보고 미리 결정하고, 그 결정은 타입 시스템이 보증한다.
  • 원격 호출·리플렉션(reflection) 경계를 건너는 순간 그 보증이 사라진다. 메서드 선택이 "문자열 이름 + 인자 수" 런타임 매칭으로 퇴화하기 때문이다.
  • 퇴화의 원인은 시그니처 소실이다: 직렬화된 요청에는 타입이 깎인 값과 이름만 남고, 컴파일러가 쓰던 정적 타입 정보는 경계를 통과하지 못한다.
  • 같은 이름의 오버로드가 경계 너머에 여러 개 있으면 어느 것이 불릴지는 매칭 규칙(구현체마다 다름)에 달려 있고, 최악의 경우 조용히 엉뚱한 쪽이 불린다.
  • 경계에 노출할 메서드를 별도 등록 목록(화이트리스트)으로 관리하면, 그 목록은 인터페이스 계약이 아니라 병행 관리 대상이 된다 — 코드 삭제와 등록 삭제가 따로 놀면 죽은 등록·유령 API가 남는다.
  • 실천 규칙: 경계에 노출하는 이름은 오버로드 없이 1이름 1시그니처로, 등록 목록은 코드에서 자동 유도되게 만들어 대칭 문제를 원천 제거한다.

1. 오버로딩은 컴파일 타임의 선택이다

오버로딩은 "같은 이름, 다른 매개변수 목록"의 메서드를 여러 개 두는 기능이다. 알림 발송 서비스를 예로 잡자. 이 문서 전체에서 이 예제 하나를 계속 변형해 가며 쓸 것이다. 

// Java — 같은 이름 send, 시그니처 3개
void send(String message)                 // ① 기본 발송
void send(String message, int retryCount) // ② 재시도 지정
void send(Notification notification)      // ③ 구조화된 알림 객체

호출부에 send("hi")라고 쓰면 ①이, send(notif)라고 쓰면 ③이 불린다. 여기서 중요한 것은 누가, 언제 이 선택을 하는가다. 선택의 주체는 런타임이 아니라 컴파일러이고, 시점은 실행 전이다. 컴파일러는 호출 인자의 정적 타입을 보고 가장 구체적으로 들어맞는 시그니처를 골라, 그 선택을 바이트코드·기계어에 새겨 넣는다. 실행 시점에는 "어느 send를 부를까"라는 질문 자체가 이미 존재하지 않는다.

이 설계의 대가로 우리는 두 가지 보증을 얻는다. 첫째, 모호하면 컴파일이 안 된다 — 어느 오버로드인지 판정 불가능한 호출은 에러로 잡힌다. 둘째, 존재하지 않는 조합은 호출할 수 없다 — 이름과 인자 타입이 어긋난 호출은 실행에 도달하지 못한다. 즉 "올바른 메서드가 선택된다"는 사실을 타입 시스템이 실행 전에 증명해 주는 것이다.

관점: 오버로딩을 "편의 문법"이 아니라 컴파일러에게 선택을 위임하는 계약으로 보면, 이 문서의 나머지 절반이 자연스러워진다. 위임받은 선택자(컴파일러)가 사라지는 곳에서 무슨 일이 벌어지는가 — 그것이 경계의 문제다.

2. 경계를 건너면 시그니처가 사라진다

앞 절의 보증은 전부 "컴파일러가 호출부와 선언부를 동시에 본다"는 전제 위에 서 있다. 그런데 이 전제가 깨지는 지점이 있다. 호출하는 쪽과 실행되는 쪽이 다른 프로세스·다른 언어·다른 시점에 있는 경우 — 원격 호출(HTTP API, RPC), 그리고 같은 프로세스 안이라도 메서드를 문자열 이름으로 찾아 부르는 리플렉션이 그렇다.

알림 서비스를 원격 API로 노출했다고 하자. 클라이언트가 보내는 것은 컴파일된 호출이 아니라 직렬화된 요청이다: 

{ "method": "send", "params": ["서버 점검 안내", 3] }

이 요청 어디에도 "②번 send(String, int)를 불러 달라"는 정보는 없다. 있는 것은 메서드 이름 문자열과, 타입이 깎여 나간 값들뿐이다. JSON을 거치면서 int였는지 long이었는지, Notification 객체였는지 그냥 맵이었는지가 뭉개진다 — 값이 언어·표현 경계를 건널 때 타입 정보가 어떻게 깎이는지는 C11 마샬링과 타입 시그니처 매핑.html이 자세히 다룬다. 수신 쪽 프레임워크가 할 수 있는 일은 결국 하나다: 이름이 "send"이고 인자 수가 2개인 메서드를 런타임에 찾아서 부른다.

컴파일 타임 오버로딩: 인자 정적 타입 → 컴파일러가 시그니처 선택 → 실행 전 확정 경계 너머 디스패치: 이름 문자열 + 인자 수 → 런타임 매칭 → 실행 중에야 판명

컴파일러가 하던 "가장 구체적인 시그니처 선택"이 "이름 + 인자 수(arity) 매칭"으로 퇴화한 것이다. 이름과 인자 수가 모두 같은 오버로드 ①·③(send(String) vs send(Notification)은 둘 다 인자 1개)이 공존하면 매칭은 모호해진다. 이때 무슨 일이 벌어지는가는 표준이 아니라 구현체의 재량이다 — 첫 번째로 발견된 것을 부르거나, 인자를 대상 타입으로 변환해 보다가 성공하는 쪽을 부르거나, 에러를 던지거나. 셋 중 무엇이든 컴파일 타임 보증과는 거리가 멀고, 앞의 둘은 엉뚱한 메서드가 조용히 성공하는 최악의 경로를 연다.

개념 함정: "오버로드를 원격에 노출해도 어차피 프레임워크가 알아서 맞는 걸 골라 주겠지"라는 기대는 컴파일 타임 해석의 기억이 만든 착시다. 경계 너머에는 그 해석기가 없다. 있는 것은 문자열 비교와 인자 개수 세기, 그리고 구현체마다 다른 임기응변 규칙뿐이다.

그래서 원격 경계의 실천 규칙은 단순하다: 노출하는 이름에는 오버로드를 두지 않는다. send 하나에 세 시그니처를 겹치는 대신 sendText·sendWithRetry·sendNotification처럼 1이름 1시그니처로 편다. 언어 안에서는 오버로딩이 주던 이름의 경제성을 포기하는 대신, 경계에서의 모호성을 구조적으로 제거하는 교환이다.

3. 이름이 계약이 되면, 등록 목록이 생긴다

경계 디스패치가 "이름 문자열 매칭"이라는 사실은 또 하나의 구조를 강제한다. 아무 메서드나 이름으로 찾아 부를 수 있게 두면 내부 구현·위험한 관리 기능까지 원격에서 호출 가능해지므로, 실무의 프레임워크들은 노출할 메서드 목록을 따로 관리한다. 어노테이션·데코레이터로 표시하든, 설정 파일에 나열하든, 라우팅 테이블에 등록하든 — 형태는 달라도 본질은 같다. "경계에서 부를 수 있는 이름들의 화이트리스트"다.

여기서 미묘한 전환이 일어난다. 언어 안에서 "호출 가능한 메서드의 집합"은 인터페이스·클래스 정의 그 자체였고, 컴파일러가 정의와 호출의 일치를 강제했다. 그런데 화이트리스트는 인터페이스 계약이 아니라 별도의 데이터다. 코드와 목록이 서로를 참조하지 않는 두 개의 진실이 되고, 둘의 일치는 이제 사람의 규율에 달린다.

이 구조가 낳는 문제가 삭제의 대칭성이다. 메서드를 추가할 때는 대칭이 저절로 지켜진다 — 등록을 안 하면 호출이 안 되니, 동작하게 만드는 과정에서 반드시 등록까지 하게 된다. 그러나 삭제는 반대 방향으로 실패한다:

어긋남남는 것증상
코드는 지웠는데 등록이 남음죽은 등록(dangling registration)호출 시점에야 "메서드 없음" 런타임 에러. 목록만 보고 "이 API는 살아 있다"고 믿은 클라이언트가 깨진다.
등록은 지웠는데 코드가 남음유령 구현(dead code)에러는 없지만 아무도 못 부르는 코드가 유지보수 비용으로 남고, "왜 안 불리지?"라는 디버깅 미궁을 만든다.

어느 쪽이든 컴파일러는 침묵한다. 코드와 목록은 서로 다른 세계의 산물이라, 한쪽만 지워도 빌드는 성공하기 때문이다. 이것이 API 발견성(discoverability) 문제와도 이어진다: 경계 너머의 클라이언트가 "지금 부를 수 있는 메서드가 무엇인가"를 알 수 있는 길은 목록뿐인데, 그 목록이 코드와 어긋날 수 있다면 발견성 자체가 신뢰를 잃는다.

구조적 해법: 목록을 손으로 쓰지 말고 코드에서 유도하게 만든다. 어노테이션·데코레이터 스캔으로 등록을 자동 생성하면 "코드 삭제 = 등록 삭제"가 한 동작이 되어 대칭 문제가 사라진다. 목록을 손으로 관리해야 하는 환경이라면, 기동 시점에 목록의 모든 항목이 실제 메서드와 연결되는지 검증하는 단계를 넣어 어긋남을 배포 직후로 앞당긴다. 호출 이름으로 분기하는 디스패처 쪽 설계는 C8 디스패처 패턴과 method 분기.html에서 이어진다.

정리하면, 경계의 메서드 노출은 두 겹의 취약점을 갖는다. 선택의 퇴화(2절 — 시그니처 대신 이름+인자 수)와 계약의 분리(이 절 — 인터페이스 대신 병행 목록). 다음 절의 헷갈리는 지점들은 대부분 이 두 겹을 혼동하는 데서 나온다.

4. 흔히 헷갈리는 지점

  • "오버로딩은 다형성이니까 런타임에 골라진다?" — 반대다. 오버로딩은 컴파일 타임(정적 타입 기준), 오버라이딩(overriding)이 런타임(실제 객체 기준)이다. 이 둘을 섞어 기억하면 "경계에서도 알아서 골라지겠지"라는 2절의 착시가 강화된다. 경계 디스패치는 그 어느 쪽도 아닌 제3의 것 — 문자열 매칭이다.
  • "인자 수가 다르면 안전하다?" — 절반만 맞다. 이름+인자 수 디스패치에서 send(String)과 send(String, int)는 구분되지만, send(String)과 send(Notification)은 구분되지 않는다. 그리고 옵션 인자·가변 인자가 끼는 순간 인자 수조차 유일하지 않게 된다.
  • "타입 정보를 요청에 실어 보내면 되지 않나?" — 직렬화 포맷에 타입 힌트를 넣는 방식은 존재하지만, 이는 호출자와 수신자가 타입 이름 체계를 공유해야 성립한다. 언어가 다르면 그 공유 자체가 새 계약이 되고, 계약이 하나 늘어난 만큼 어긋날 지점도 늘어난다. 경계에서는 계약을 늘리는 쪽보다 모호성을 없애는 쪽(1이름 1시그니처)이 싸다.
  • "화이트리스트는 보안 장치니까 있으면 좋은 것?" — 보안 장치로서는 맞다. 함정은 그 목록을 계약 문서로 착각하는 데 있다. 목록은 "지금 이 순간 부를 수 있는 것"의 스냅샷일 뿐, 코드와의 일치를 아무도 보증하지 않는다면 문서로서의 효력은 없다.
  • "리플렉션은 어차피 같은 프로세스 안이니 원격보다 안전하다?" — 프로세스는 같아도 컴파일러의 부재라는 본질은 동일하다. 문자열로 메서드를 찾는 순간 오타·리네이밍 누락이 컴파일 에러에서 런타임 예외(또는 침묵)로 강등된다. 리팩터링 도구가 문자열 안의 이름까지는 바꿔 주지 못한다는 점에서, 오히려 원격보다 어긋나기 쉽다.

5. ★ 언어별 대조 — 경계에서 오버로딩은 어떻게 무너지는가

앞 절까지의 이야기는 언어 중립이지만, "경계에서 무엇이 사라지는가"는 언어마다 다르게 나타난다. 애초에 오버로딩이 없는 언어는 이 문제를 언어 안에서부터 겪고 있고, 오버로딩이 강한 언어는 경계에서 낙차가 크다.

JavaJS·TSPythonC++
언어 내 오버로딩있음 — 컴파일러가 정적 타입으로 해석없음 — TS의 오버로드 선언은 타입 검사용일 뿐없음 — 같은 이름 재정의는 덮어쓰기있음 — 이름 장식(name mangling)으로 심벌 수준 구분
경계에서의 모습리플렉션·RMI에서 이름+파라미터 타입 배열로 탐색런타임엔 함수 1개 — 언어 자체가 이미 "경계식" 디스패치getattr 문자열 탐색이 관용구 — 항상 이름 1개C ABI로 나가려면 오버로드를 펴서 이름을 갈라야 함
대표 함정오토박싱·가변 인자로 탐색 결과가 직관과 어긋남오버로드 선언과 런타임 분기 로직의 불일치재정의 덮어쓰기가 조용히 일어남extern "C"는 같은 이름 2개를 허용하지 않음

5.1 Java — 컴파일러의 선택 vs 리플렉션의 탐색

Java는 오버로딩 해석이 가장 정교한 축에 든다. 컴파일러는 오토박싱·가변 인자까지 고려한 단계적 규칙으로 "가장 구체적인" 메서드를 고른다. 그런데 리플렉션으로 넘어가면 그 규칙이 통째로 사라지고, 개발자가 파라미터 타입 배열을 직접 정확히 제시해야 한다: 

// 컴파일 타임: 컴파일러가 골라 줌
service.send("hi", 3);                     // send(String, int)로 확정

// 리플렉션: 탐색 키를 사람이 조립
Method m = service.getClass()
    .getMethod("send", String.class, int.class); // 정확히 일치해야 발견
m.invoke(service, "hi", 3);

함정은 getMethod가 컴파일러식 "가장 근접한" 해석을 해 주지 않는다는 것이다. int.class와 Integer.class는 다른 키다 — 컴파일 타임엔 오토박싱이 이어 주던 간극이 리플렉션에서는 NoSuchMethodException으로 나타난다. Spring 같은 프레임워크가 요청을 컨트롤러 메서드에 물어 줄 때 오버로드된 핸들러 이름을 피하도록 안내하는 것도 같은 이유다: HTTP 요청에는 Java의 정적 타입이 실려 오지 않으므로, 프레임워크의 매칭은 결국 이름·어노테이션·인자 개수 수준에서 이루어진다. 또 하나, 제네릭은 타입 소거(type erasure — 컴파일 후 제네릭 타입 인자가 지워지는 것) 때문에 send(List<String>)과 send(List<Integer>)가 언어 안에서조차 같은 시그니처로 취급된다 — 경계 이전에 이미 시그니처 소실이 일어나는 지점이다.

5.2 JS·TS — 오버로딩이 없는 언어는 이미 경계 위에 산다

JavaScript에는 오버로딩이 없다. 함수는 이름당 하나이고, 같은 이름으로 두 번 선언하면 나중 것이 이긴다. "인자에 따라 다르게 동작"은 함수 안에서 런타임 검사로 구현한다 — 즉 JS 함수는 언어 안에서부터 "이름 하나 + 런타임 인자 판별"이라는, 이 문서가 말한 경계식 디스패치로 살아간다. TypeScript는 그 위에 오버로드 선언을 얹지만, 이는 타입 검사 전용이며 컴파일 시 지워진다(타입 소거): 

// TS: 선언은 2개, 구현은 1개
function send(message: string): void;
function send(notification: Notification): void;
function send(arg: string | Notification): void {
  if (typeof arg === "string") { /* 텍스트 발송 */ }
  else { /* 알림 객체 발송 */ }   // ← 실제 분기는 여기, 런타임 검사
}

함정은 선언과 구현 분기의 불일치다. 오버로드 선언을 3개로 늘리고 구현의 if를 안 고치면, 타입 검사는 통과하는데 런타임 동작이 어긋난다 — TS의 오버로드 검사는 각 선언이 구현 시그니처와 "호환되는지"만 보지, 구현 본문이 모든 선언을 실제로 구별해 처리하는지는 증명하지 않기 때문이다. 구조적 타이핑(structural typing — 이름이 아니라 모양으로 타입을 판정)도 한몫한다: typeof로는 객체끼리 구분이 안 되므로 Notification인지 판별하려면 속성 존재 검사 같은 런타임 휴리스틱이 필요하고, 모양이 겹치는 두 타입은 런타임에서 구분 불가능하다. JSON 직렬화 경계에서 타입이 깎이는 문제를, JS는 언어 경계 없이도 상시 겪고 있는 셈이다.

5.3 Python — 덮어쓰기와 문자열 디스패치의 세계

Python도 오버로딩이 없지만, JS와 결이 다른 함정이 하나 있다. 클래스 본문에서 같은 이름을 두 번 정의하면 에러 없이 나중 정의가 앞 정의를 덮어쓴다 — 클래스 본문은 그저 이름공간(namespace)에 순서대로 대입되는 코드이기 때문이다: 

class NotificationService:
    def send(self, message: str): ...          # ① 조용히 사라짐
    def send(self, message: str, retry: int): ...  # ②만 남는다

svc = NotificationService()
svc.send("hi")        # TypeError: retry 인자 누락 — ①은 이미 없다
m = getattr(svc, "send")   # 문자열 이름 → 메서드 객체 (항상 1개)

Java 개발자가 오버로딩 습관대로 쓴 코드가 정의 시점엔 조용히 통과하고 호출 시점에야 깨지는 전형적 경로다. 한편 getattr이 보여 주듯 Python의 메서드 접근은 원래부터 문자열 키 탐색이다 — 객체는 사실상 딕셔너리이고(덕 타이핑: 타입 선언이 아니라 "그 이름에 응답하는가"로 판정), 이름당 값은 하나뿐이므로 모호성 문제 자체가 성립하지 않는다. 그 대신 오타·리네이밍 누락이 AttributeError로, 혹은 getattr(obj, name, None) 폴백을 쓰면 침묵으로 나타난다. 타입 기반 분기가 정말 필요하면 표준 라이브러리의 functools.singledispatch가 첫 인자 타입 기준 디스패치를 제공하는데, 이는 "런타임 값 검사로 오버로딩을 흉내 내는" 것 — 즉 경계식 디스패치를 언어가 공식화한 도구다.

5.4 C++ — 시그니처가 심벌에 새겨지는 언어, 그래서 경계가 가장 급격한 언어

C++ 오버로딩의 내부 기제는 이름 장식이다: 컴파일러가 함수 이름에 파라미터 타입 정보를 인코딩해 send(std::string)과 send(std::string, int)를 서로 다른 링크 심벌로 만든다. 시그니처가 바이너리 수준까지 보존되는 셈이라 언어 안에서는 가장 견고하다. 문제는 이 장식 규칙이 컴파일러·버전마다 달라 ABI(Application Binary Interface — 바이너리 간 호출 규약) 경계를 안전히 건너지 못한다는 것이다. 그래서 동적 로딩·타 언어 연동은 장식을 끄는 extern "C"를 쓰는데, 그 순간 오버로딩이 언어 규칙상 불가능해진다: 

// C ABI로 노출: 장식이 꺼지므로 이름은 문자 그대로 심벌이 된다
extern "C" void send_text(const char* msg);
extern "C" void send_with_retry(const char* msg, int retry);
// extern "C" void send(const char*); 와 extern "C" void send(const char*, int); 는
// 같은 심벌 "send"를 요구하므로 컴파일 에러 — 오버로드를 손으로 펴야 한다

void* f = dlsym(handle, "send_text");   // 런타임: 문자열로 심벌 탐색

즉 C++은 이 문서의 실천 규칙(경계에서는 1이름 1시그니처)을 컴파일러가 강제하는 언어다. dlsym은 문자열 이름으로 심벌을 찾을 뿐 시그니처를 전혀 검증하지 않으므로, 찾은 포인터를 잘못된 함수 타입으로 캐스팅해 부르면 미정의 동작(undefined behavior)이 된다 — 다른 언어라면 예외로 끝날 어긋남이, C++ 경계에서는 메모리 오염으로 확대될 수 있다는 점이 특이점이다. 수명 관점의 덤: 경계를 건너는 인자는 누가 소유하고 언제 해제하는지(소유권)까지 문자열 계약 밖에서 별도로 합의해야 한다.

6. 함께 알면 좋은 것

  • 스키마 우선 인터페이스 정의(IDL) — gRPC의 Protocol Buffers, OpenAPI 명세처럼 경계 계약을 별도 스키마로 선언하고 양쪽 코드를 생성하는 접근. 이름 목록과 코드가 한 원천에서 나오므로 3절의 대칭 문제가 구조적으로 사라진다. 이들 IDL이 대부분 오버로딩을 아예 지원하지 않는 것은 우연이 아니다.
  • 기동 시점 검증(fail-fast) — 등록 목록의 각 항목이 실제 호출 가능 대상과 연결되는지 서버 시작 시 전수 확인. 죽은 등록을 "첫 호출이 실패할 때"가 아니라 "배포 직후"에 드러낸다.
  • 계약 테스트(contract test) — 경계 양쪽이 같은 계약을 보고 있는지를 테스트로 고정. 시그니처 변경이 경계 너머로 어떻게 번지는지는 I11 계층을 관통하는 계약 변경·시그니처 파급.html과 짝으로 보면 좋다.
  • 디프리케이션(deprecation) 절차 — 경계에 노출된 이름은 클라이언트를 모르는 채로 지울 수 없다. "표시 → 유예 → 제거"의 단계적 폐기가 등록 목록 관리의 짝 규율이 된다.
  • 가변 인자·옵션 인자와 arity — 언어 안에서는 편의지만, 이름+인자 수 매칭 세계에서는 "인자 수가 유일하지 않은 메서드"를 만들어 모호성을 키운다. 경계 노출 대상에서는 피하는 것이 안전하다.

7. 한 장 요약

  • 오버로딩의 본질은 컴파일러에게 메서드 선택을 위임하는 것 — 선택은 실행 전에 확정되고 타입 시스템이 보증한다.
  • 원격·리플렉션 경계에는 컴파일러가 없다. 선택은 이름 문자열 + 인자 수 매칭으로 퇴화하고, 모호할 때의 동작은 구현체 재량이다.
  • 따라서 경계에 노출하는 이름은 오버로드 금지, 1이름 1시그니처 — 이름의 경제성보다 모호성 제거가 우선이다.
  • 노출 목록(화이트리스트)은 인터페이스 계약이 아니라 코드와 병행 관리되는 별도 데이터 — 추가는 저절로 대칭이 지켜지지만 삭제는 어긋나기 쉽다.
  • 해법은 목록을 코드에서 자동 유도(어노테이션 스캔·IDL 코드 생성)하거나, 기동 시점에 목록↔코드 일치를 전수 검증하는 것.
  • 언어별 낙차: Java는 리플렉션에서 해석 규칙 소실, JS·Python은 애초에 이름당 1개(대신 덮어쓰기·불일치 함정), C++은 extern "C"가 1이름 1시그니처를 강제.

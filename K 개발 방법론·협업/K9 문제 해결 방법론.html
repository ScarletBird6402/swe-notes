K9 문제 해결 방법론

0. 한눈에 보는 결론

  • 문제 해결 방법론은 디버깅의 상위 방법론이다. 디버깅이 "증상의 원인을 찾아 제거"하는 활동이라면, 문제 해결은 그 원인을 구조 속에서 보고, 제약을 확인하고, 복수의 방안을 트레이드오프로 비교해 구현까지 이르는 전 과정이다.
  • 표준 파이프라인은 7단계다: 증상 → 근본원인 → 구조 추적 → 제약 → 방안 → 트레이드오프 → 구현. 앞 세 단계가 "문제를 정확히 아는 일", 뒤 네 단계가 "답을 고르는 일"이다.
  • 원인 규명의 핵심 기술은 관문(gate)을 순서대로 끊어 가설 공간을 좁히고, 가설을 "한 줄로, 참/거짓 판정 가능하게" 만드는 것이다 — 판정 불가능한 가설은 가설이 아니라 인상이다.
  • 빠른 판정의 대표 기법이 카디널리티 비교다: 두 집합의 개수만 세어 "1:1 대응일 것"이라는 가설을 몇 초 만에 참/거짓으로 가른다.
  • 해법 공간을 넓히는 대표 기법이 표면 요청의 이면 재질문이다: 제안된 수정을 그대로 받지 않고 "그 요청이 지키려는 불변식이 무엇인가"를 물으면, 더 좋은 해법이 후보에 들어온다.
  • 증상 제거는 문제 해결이 아니다 — 증상만 가린 수정은 원인을 구조 속에 남겨 두고, 다음 발현을 조용한 실패로 바꿔 놓기 쉽다.

1. 층위 구분 — 디버깅·문제 해결·장애 대응은 다른 활동이다

"문제를 푼다"는 말 아래에 실은 세 개의 다른 활동이 겹쳐 있다. 이 문서의 위치를 정확히 잡기 위해 먼저 셋을 가른다.

층위목표지배 조건소관
장애 대응 서비스 복구 — 일단 살린다 시간 압박 — 근본원인 규명은 사후로 미룰 수 있다(롤백 우선) O5
디버깅 증상의 원인 규명·제거 재현과 검증 — 가설·이분 탐색의 기술 K6
문제 해결 원인을 구조에서 보고 올바른 변경을 고름 제약과 트레이드오프 — 복수 방안의 비교 이 문서

관계를 한 줄로 하면: 장애 대응은 "지금 당장"의 절차이고, 디버깅은 "왜 그런가"의 기술이며, 문제 해결은 그 둘을 부분 절차로 포함하는 상위 방법론이다 — 디버깅이 원인을 찾아 주면, 문제 해결은 "그래서 무엇을 어떻게 고치는 것이 옳은가"까지 책임진다. 왜 그 "이후"가 별도의 방법론을 필요로 하는가? 원인을 아는 것과 올바른 수정을 고르는 것 사이에 구조·제약·트레이드오프라는 세 개의 관문이 더 있기 때문이다. 이제 전체 지도를 펴자.

2. 7단계 파이프라인 — 그리고 하나의 러닝 예제

① 증상 ──> ② 근본원인 ──> ③ 구조 추적 ──> ④ 제약 ──> ⑤ 방안 ──> ⑥ 트레이드오프 ──> ⑦ 구현 └──── 문제를 정확히 아는 일 ────┘ └────────── 답을 고르는 일 ──────────┘ (디버깅이 담당하는 구간 포함) (문제 해결 고유의 구간)

이 문서 전체를 하나의 예제로 관통한다: "주문 목록 화면에 같은 주문이 두 번씩 보인다". 흔하고 사소해 보이는 이 증상이, 각 단계를 지나며 어떻게 다른 질문으로 바뀌는지를 따라가면 방법론의 뼈대가 잡힌다. 출발점은 당연히 ①이다 — 그런데 증상을 "적는 법"부터 이미 기술이다.

3. ①증상 → ②근본원인 — 관문을 끊어 가설을 한 줄로

증상 서술의 규율은 기대와 실제의 쌍이다: "이상해요"가 아니라 "주문 3건을 기대했는데 목록에 6행이 보인다". 기대-실제 쌍이 있어야 다음 작업 — 어디서부터 어긋났는지의 추적 — 이 시작될 수 있다.

추적의 기본기는 관문 끊기다. 데이터가 흐르는 경로(DB → 쿼리 → 응답 → 화면)를 관문으로 나누고, 중간 관문 하나를 골라 "여기까지는 정상인가?"를 확인한다 — 정상이면 문제는 하류, 비정상이면 상류로, 확인 한 번에 수색 범위가 절반이 된다. 예제라면: 응답 JSON을 열어 본다 → 이미 6건이다 → 화면(렌더링)은 무죄, 문제는 서버 쪽 상류다.

관문을 좁힌 끝에서 가설을 세운다. 규율은 하나다: 한 줄로, 참/거짓 판정 가능하게. "쿼리가 뭔가 이상하다"는 인상이고, "주문-배송 조인이 1:N이라 주문 행이 배송 수만큼 복제된다"는 가설이다 — 후자만이 검증 절차를 가진다. 그리고 이런 가설에는 놀랍도록 싼 판정법이 있다.

기법 ① 카디널리티 비교 — 개수만 세어 가설을 가른다. "결과 행과 주문이 1:1로 대응할 것"이라는 가설은, 두 집합의 개수만 세면 즉시 판정된다: 전체 행 수와 고유 주문 ID 수를 비교해 다르면 1:1 가설은 거짓 — 복제가 존재한다. 내용물을 들여다보기 전에 개수라는 가장 싼 속성부터 비교하는 것이 요령이다.

-- 전체 행 수 vs 고유 주문 수: 두 숫자가 다르면 "1:1" 가설은 그 자리에서 거짓
SELECT COUNT(*), COUNT(DISTINCT o.order_id)
FROM   orders o JOIN shipments s ON s.order_id = o.order_id;
-- 6, 3  → 복제 확정. 배송이 2건인 주문이 있다: 1:N 조인 가설 참

가설이 참으로 판정됐다 — 근본원인은 "1:N 관계를 조인해 행이 복제됨". 디버깅이라면 여기서 수정으로 직행할 것이다. 문제 해결 방법론이 갈라지는 지점이 바로 다음 단계다: 이 원인은 이 쿼리만의 문제인가?

4. ③구조 추적 — 원인의 "주소"를 구조에서 찾는다

구조 추적은 "이 원인이 재발할 구조인가"를 묻는 단계다. 같은 조인 패턴을 쓰는 화면이 또 있는가? 주문-배송이 1:N이 된 것은 최근의 모델 변경 때문인가? 그렇다면 그 변경을 소비하는 다른 코드들도 같은 폭탄을 안고 있는가?

  • 탐색이 한 지점에서 끝나면 — 이 쿼리 하나의 실수 — 국소 수정으로 충분하다.
  • 탐색이 패턴을 드러내면 — 여러 화면이 같은 조인을 복사해 씀 — 수정의 단위가 "쿼리 한 줄"에서 "조회 계층의 공통화"로 승격된다.

즉 구조 추적의 산출물은 수정의 올바른 크기다. 이 단계를 건너뛰면 두 실패 중 하나로 기운다: 패턴 문제를 한 지점만 고쳐 두더지 잡기가 되거나, 한 지점 문제에 전면 개편을 들이대 과잉 수술이 된다. 수정의 크기가 잡혔으면, 이제 무엇이 가능한지의 울타리를 확인할 차례다.

5. ④제약 — 해법 공간의 울타리를 먼저 그린다

제약은 "바꿀 수 없는 것"의 목록이다: 스키마는 이번 배포에서 동결인가, 응답 포맷은 하위 호환이어야 하는가(프론트가 이미 소비 중), 허용 가능한 성능 예산은 얼마인가. 제약을 방안 이전에 명시하는 이유는 경제적이다 — 울타리 밖의 방안을 정교하게 설계하는 것만큼 비싼 낭비가 없다.

단, 제약 목록에는 위조품이 섞인다. 대표가 "요청된 수정" 그 자체를 제약으로 착각하는 것이다.

기법 ② 표면 요청의 이면 재질문 — 요청이 지키려는 불변식을 묻는다. "화면에서 중복을 제거해 주세요"라는 요청을 그대로 받으면 해법은 렌더링 수정 하나로 고정된다. 여기서 되묻는다: 이 요청이 지키려는 불변식(invariant — 언제나 참이어야 하는 조건)이 무엇인가? 답이 "한 주문은 목록에 한 번만 나타난다"라면, 그 불변식을 지키는 방법은 렌더링 말고도 쿼리 수정·조회 모델 분리 등 여럿이다 — 요청은 해법 하나의 제안이었을 뿐, 제약이 아니었던 것이다. 같은 원리로 "삭제 후 재삽입으로 바꿔 달라"는 요청의 이면 불변식이 "두 작업이 하나처럼 완결되어야 한다(원자성)"라면, 진짜 후보에는 트랜잭션 묶음 같은 더 곧은 해법이 들어온다. 표면 요청은 접수하되, 불변식으로 번역한 뒤에 해법을 찾는 것 — 이것이 해법 공간을 넓히는 가장 싼 질문이다.

울타리가 그려지고(진짜 제약), 지켜야 할 것이 명확해졌다(불변식). 이제야 비로소 방안을 나열할 자격이 생긴다.

6. ⑤방안 → ⑥트레이드오프 → ⑦구현 — 답을 "고르는" 일

방안은 복수로 나열한다 — 하나뿐인 방안은 비교가 불가능하고, 비교 없는 선택은 검토가 아니라 통보다. 예제의 불변식("주문당 1행")을 지키는 후보:

방안얻는 것감수하는 것판단 근거(③·④에서)
A. 쿼리에서 집약(주문 기준 그룹) 원천에서 해결 — 모든 소비자가 동시에 교정 쿼리 복잡도 상승, 배송 상세가 필요한 화면은 별도 조회 ③에서 같은 패턴 다수 발견 시 최선
B. 응답 조립 단계에서 주문 기준 재구성 쿼리 단순 유지, 배송 목록을 중첩 구조로 제공 가능 조립 코드 추가, 대량 결과에서 메모리 비용 응답 포맷 변경이 허용될 때(④ 확인 필요)
C. 화면에서 중복 제거(원 요청) 변경 최소·가장 빠름 원인이 구조에 잔존 — 집계·내보내기 등 다른 소비자는 여전히 6행을 본다 ③에서 소비자가 이 화면뿐임이 확인될 때만 정당

넷째 열이 보여주듯 트레이드오프의 심판은 앞 단계들이다 — 구조 추적(③)이 A와 C를 가르고, 제약(④)이 B의 가부를 정한다. 근거 열이 비면 선택은 취향으로 퇴행한다. 선택이 끝난 ⑦구현 단계의 규율은 두 가지다: 최소 변경(고르지 않은 방안의 흔적을 함께 들이지 않기)과 검증 계획 — 3절의 카디널리티 비교를 재실행해 "6 → 3"을 확인하고, 같은 판정을 회귀 테스트로 남겨 재발 시 즉시 발각되게 한다. 판정 도구가 검증 도구로 재사용되는 것이다.

7. 흔히 헷갈리는 지점

네 오해는 각각 앞 단계의 그림자다 — ①은 6절 C안의, ②는 3~4절 가설·원인의, ③은 파이프라인 전체의, ④는 5절 제약의 함정이다.

① "증상이 사라졌으니 해결됐다"? — 증상 제거와 문제 해결의 혼동이 이 주제 최대의 함정이다. 화면 중복 제거(C안)로 증상은 사라지지만 원인은 구조에 남고, 다음 발현은 더 조용한 곳(집계 수치, 내보내기 파일)에서 일어난다 — 가려진 원인은 조용한 실패의 공급원이 된다(K5). C안이 틀렸다는 것이 아니라, C안을 "③에서 소비자가 하나뿐임을 확인한 뒤" 고르는 것과 확인 없이 고르는 것이 다르다는 뜻이다.

② "근본원인은 항상 하나다"? — 복합 원인은 흔하다(1:N 조인 + 그것을 전제한 화면 코드). "하나의 진짜 원인"을 강박적으로 찾기보다, 관문 끊기가 드러낸 어긋남의 지점들을 모두 기록하고 구조 추적에서 관계를 정리하는 편이 정확하다.

③ "모든 문제에 7단계를 다 돌려야 하나"? — 아니다. 오타 수정에 트레이드오프 표는 과잉이다. 스케일 판단 기준은 ③과 ⑥이다: 구조에 손대는가? 방안이 둘 이상인가? 둘 다 아니오면 파이프라인은 자연히 ①②⑦로 축약된다 — 방법론은 의식이 아니라, 필요할 때 꺼내 쓰는 관문들의 목록이다.

④ "제약이라서 안 됩니다"의 상당수는 가정이다 — 진짜 제약(계약된 하위 호환)과 물어보면 풀리는 가정("스키마는 못 건드리는 줄 알았다")을 구분하는 유일한 방법은 제약의 출처를 적는 것이다. 출처를 쓸 수 없는 제약은 제약 목록이 아니라 확인 목록으로 보낸다 — 5절의 이면 재질문이 요청에 하는 일을, 제약에도 똑같이 하는 셈이다.

★ 8. 언어별 대조

방법론 자체는 언어 중립이다 — 언어가 바꾸는 것은 관문을 끊고 가설을 판정하는 도구의 생김새다(3절의 기술이 언어별로 어떤 손잡이를 갖는가).

언어관문 끊기의 주 도구가설 판정(카디널리티류)의 관용 수단고유의 유의점
Java 디버거·조건부 중단점, 상관 ID 로그 스트림 count/distinct 즉석 비교 프레임워크 계층이 두꺼워 관문 수가 많음 — 경로 정의가 선행
JS·TS 브라우저 개발자 도구(네트워크·콘솔) console.table·Set 크기 비교 비동기 타이밍이 재현성을 흔듦 — 재현 조건 기록이 관건
Python 대화형 실행(REPL)으로 중간 상태 즉시 조회 Counter·set 한 줄 판정 판정 스크립트가 가장 싸다 — 대신 제품 코드와 분리 규율 필요
C++ 단계별 실패 지점(컴파일/링크/런타임) 분기, 디버거 assert로 가설을 코드에 박아 판정 빌드가 느려 재현 1회가 비쌈 — 최소 재현 예제의 가치 최대

8.1 C++ — 가설을 assert로 박되, 부작용을 넣으면 안 되는 언어

C++의 관문 끊기는 시작 전에 분기 하나가 더 있다: 실패가 컴파일/링크/런타임 중 어느 단에서 났는가 — 단이 다르면 수색 대상(코드/빌드 설정/실행 환경)이 완전히 다르다. 런타임 단에 들어오면, 가설을 assert(조건이 거짓이면 즉시 프로그램을 중단시키는 검사 매크로)로 코드에 박아 실행 자체를 판정기로 쓸 수 있다. 

// 가설 "결과 행의 orderId는 유일하다"를 실행 중에 판정
std::set<long> seen;
for (const auto& row : rows) {
    bool first = seen.insert(row.orderId).second;   // 판정용 계산은 assert 밖에서
    assert(first && "orderId 중복 — 1:N 조인 가설이 참");
}

// 함정: assert(seen.insert(id).second) 처럼 부작용을 assert 안에 넣으면,
// 릴리스 빌드(NDEBUG — assert를 통째로 제거하는 빌드 설정)에서 insert 자체가 사라진다

C++ 관점의 통찰: 마지막 줄의 함정은 이 문서와 K5가 만나는 지점이다 — 가설 판정 코드가 빌드 설정에 따라 조용히 소멸하면, 진단 도구가 조용한 실패의 생산자가 된다. 그래서 C++의 규율은 "판정용 계산은 assert 밖, assert 안에는 순수 조건만"이고, 재현이 비싼 언어 특성(느린 빌드)상 증상을 수십 줄짜리 최소 재현 예제로 압축하는 투자가 관문 끊기 전체보다 먼저 이득을 낸다.

8.2 Python — 가설 판정이 가장 싼 대신, 진단 코드의 격리가 필요한 언어

Python의 강점은 실행이 곧 판정이라는 데 있다 — 대화형 실행(REPL)에서 중간 관문의 데이터를 즉시 조회하고, 카디널리티 비교를 표준 라이브러리 한 줄로 끝낸다. 

from collections import Counter

print(len(rows), len({r.order_id for r in rows}))       # 6 3 → 1:1 가설 즉시 거짓
dup = [k for k, n in Counter(r.order_id for r in rows).items() if n > 1]
print(dup)                                              # 어떤 주문이 복제됐는지까지 한 줄

Python 관점의 통찰: 판정 비용이 낮다는 것은 3절의 "가장 싼 속성부터 비교"를 극한까지 밀 수 있다는 뜻이다 — 개수, 그다음 키 집합의 차집합, 그다음에야 내용물. 대가로 따라오는 규율이 진단 코드의 격리다: 판정용 print·임시 필터가 제품 코드에 눌러앉으면 그 자체가 다음 문제의 씨앗이 되므로, 판정 스크립트는 별도 파일이나 테스트로 옮겨 "판정 도구 → 회귀 검증 도구"(6절)로 승격시키는 것이 건강한 종착지다.

8.3 Java / JS·TS — 한 줄 요약

Java의 관문 끊기는 디버거의 조건부 중단점("orderId가 중복일 때만 멈춤")과 상관 ID를 심은 로그가 양대 도구이고, 카디널리티 판정은 스트림의 count와 distinct().count() 비교로 즉석에서 끝난다 — 두꺼운 프레임워크 계층 때문에 관문 자체가 많으므로, 3절의 경로 정의(어떤 관문들이 있는가)를 먼저 그리는 것이 이 언어에서 특히 값지다. JS·TS의 관문은 브라우저 개발자 도구가 절반을 대신한다 — 네트워크 탭이 "응답까지는 정상인가"를, 콘솔의 console.table과 Set 크기 비교가 카디널리티 판정을 담당한다. 고유의 어려움은 비동기 타이밍이 만드는 재현 불안정으로, "언제·어떤 순서로"까지 포함해 증상을 기록해야 기대-실제 쌍(3절)이 완성된다.

9. 함께 알면 좋은 것

본문 각 단계를 실무 제도·기법으로 확장한 어휘들이다 — 첫째는 ②의 심화, 둘째는 관문 끊기의 자동화, 셋째는 ①의 재현 규율, 넷째는 ③⑦의 조직화, 다섯째는 가설 언어화의 보조 기법이다.

  • 5 Whys — "왜?"를 연쇄로 물어 표면 원인에서 근본원인으로 내려가는 고전 기법. 기계적으로 다섯 번이 아니라, "이 층을 고치면 재발이 멎는가"가 멈춤 기준이라는 점이 요체다.
  • 이분 탐색 디버깅 — 관문 끊기의 "절반씩"을 변경 이력에 적용해, 문제를 유발한 커밋을 로그 이분 탐색으로 자동 특정하는 기법(디버깅 기술의 본진은 K6). 버전 관리 도구의 bisect류 명령이 이를 제도화했다.
  • 최소 재현 예제(minimal reproducible example) — 증상을 재현하는 가장 작은 코드로 압축하는 규율. 압축 과정 자체가 관문 끊기여서, 만들다가 원인이 드러나는 일이 잦다 — 질문하기 전의 예의이자 진단 기법.
  • 사후 분석(postmortem)과 재발 방지 — 해결된 문제의 ②③(원인과 구조)을 기록으로 남기고, ⑦의 검증을 회귀 테스트·경보로 제도화하는 절차. "같은 문제를 두 번 풀지 않는다"의 조직판.
  • 러버덕 디버깅 — 문제를 소리 내어 설명하는 것만으로 가설이 정리되는 현상을 이용한 기법. "한 줄 가설"(3절)을 강제로 언어화하는 가장 저렴한 장치다.

10. 한 장 요약

  • 층위: 장애 대응(복구 우선·O5) ⊂ 디버깅(원인 규명·K6) ⊂ 문제 해결(구조·제약·트레이드오프까지) — 이 문서는 최상위 층위다.
  • 파이프라인: 증상 → 근본원인 → 구조 추적 → 제약 → 방안 → 트레이드오프 → 구현. 앞 셋은 문제를 아는 일, 뒤 넷은 답을 고르는 일.
  • 원인 규명: 기대-실제 쌍으로 증상을 적고, 관문을 끊어 절반씩 좁히며, 가설은 한 줄·판정 가능으로. 판정은 가장 싼 속성부터 — 카디널리티 비교(개수 두 개)가 대표.
  • 구조 추적이 수정의 크기를, 제약이 해법의 울타리를 정한다. 요청은 불변식으로 번역한 뒤 해법을 찾는다(이면 재질문) — 제약의 출처를 못 적으면 그것은 가정이다.
  • 방안은 복수로, 트레이드오프의 근거는 ③④에서, 구현은 최소 변경 + 판정 도구의 회귀 테스트 승격.
  • 증상 제거 ≠ 문제 해결 — 가려진 원인은 다음번에 더 조용하게 돌아온다.

P3 메트릭과 대시보드

0. 한눈에 보는 결론

  • 메트릭(metric)은 수집 시점에 미리 집계해 두는 수치의 시계열이다 — "몇 건인가·얼마나 빠른가"를 매번 원본 전체를 뒤져 세는 대신, 세어진 결과만 저장한다.
  • 로그로 세는 비용과 메트릭으로 세는 비용은 구조가 다르다: 로그는 사건 수에 비례해 저장하고 질의 때 계산하지만, 메트릭의 비용은 사건 수와 무관하게 시계열 개수에 비례한다.
  • 그 시계열 개수를 결정하는 것이 카디널리티(cardinality) — 라벨 값 조합의 수 — 이며, 메트릭 시스템의 붕괴는 거의 항상 여기서 온다: 무한히 늘어나는 값(사용자 ID·요청 경로 원문)을 라벨에 넣는 순간이다.
  • 기본 도구는 세 가지다: 카운터(counter, 단조 증가 누적치 → 변화율로 읽음) · 게이지(gauge, 현재값) · 히스토그램(histogram, 분포를 버킷으로).
  • 대시보드는 그래프 진열장이 아니라 질문에 답하는 화면이다 — "지금 정상인가"에 답하는 표준 질문 틀(RED/USE)로 시작하고, 지연은 평균이 아니라 백분위로 본다.
  • 개별 사건의 맥락은 로그, 수치의 추이는 메트릭 — 역할 분담이 원칙이다(분담의 로그 쪽 절반은 P1 참고).

1. 숫자가 필요한 순간 — 로그로 세는 것의 비용

"지난 1시간 오류율은 몇 %인가", "결제 API의 응답 시간 추이는 어떤가" — 운영의 핵심 질문들은 개별 사건이 아니라 수치의 추이를 묻는다. 로그만 있는 시스템에서 이 질문에 답하려면, 매번 해당 구간의 로그 전체를 저장해 두고, 질의 시점에 전부 훑어 세어야 한다. 사건이 초당 수천 건이면 저장량도 질의 비용도 사건 수에 정비례로 자란다 — "몇 건인가" 하나를 알기 위해 모든 건을 다시 만지는 셈이다.

메트릭은 계산의 시점을 뒤집는다. 수집하는 순간에 미리 집계해 — 카운터를 1 올리고, 관측값을 버킷에 더해 — 결과 수치만 시계열로 저장한다. 질의는 이미 세어진 숫자를 읽는 것이므로, 초당 사건이 10건이든 10만 건이든 저장·질의 비용은 거의 같다. 대가도 명확하다: 집계 과정에서 개별 사건의 얼굴이 사라진다 — "오류 137건"은 남지만 "그중 사용자 X의 요청이 왜 실패했나"는 메트릭에 없다. 그 질문의 답은 사건을 기록하는 로그의 몫이며, 이 역할 분담의 로그 쪽 절반 — 어떤 사건을 어떻게 남길 것인가 — 은 P1이 다룬다(관련 문서).

질문: "오류가 몇 건인가?" [로그 방식] 사건마다 기록 ─▶ 전량 저장 ─▶ 질의 때 전체 스캔·집계 비용 ∝ 사건 수 (사후 계산) [메트릭] 사건마다 카운터 +1 ─▶ 집계 결과만 저장 ─▶ 질의는 숫자 읽기 비용 ∝ 시계열 수 (사전 계산)

"비용이 시계열 수에 비례한다"고 했다 — 그렇다면 시계열이란 정확히 무엇이고, 그 개수는 무엇이 결정하는가? 이것이 메트릭의 데이터 모델이다.

2. 메트릭의 데이터 모델 — 이름 + 라벨 = 시계열

메트릭 하나는 이름(무엇을 재는가: http_requests_total)과 라벨(어떤 조각인가: method="GET", status="500")의 조합으로 식별되고, 그 조합마다 시간에 따른 값의 나열 — 시계열(time series) — 이 하나씩 만들어진다. 라벨은 집계의 차원이다: status 라벨이 있어야 "상태코드별 오류율"로 쪼개 볼 수 있고, sum by (status) 같은 질의가 가능해진다.

값을 기록하는 도구는 재려는 것의 성질에 따라 세 가지로 나뉜다.

도구성질예읽는 법
카운터단조 증가하는 누적 합계 (내려가지 않음)총 요청 수·총 오류 수누적값 자체가 아니라 구간 변화율(초당 요청 수)로 변환해 읽는다
게이지오르내리는 현재값메모리 사용량·큐 길이·동시 접속값 그대로 — 순간의 상태
히스토그램관측값들의 분포를 버킷별 개수로응답 시간·페이로드 크기버킷 누적 개수에서 백분위를 추정

카운터가 "누적"인 이유는 신뢰성이다 — 수집이 한 번 실패해도 다음 수집에서 누적값을 읽으면 놓친 구간의 증가분이 자연히 포함된다. 순간 증가량을 보내는 방식이었다면 실패한 구간은 영영 유실됐을 것이다. "카운터는 rate로 읽는다"는 관용구는 이 누적 설계의 이면이다.

모델을 갖췄으니 다음 질문은 운반이다 — 이 수치들은 어떻게 애플리케이션에서 저장소까지 이동하는가.

3. 수집 방식 — pull과 push, 그리고 집계가 일어나는 곳

두 가지 흐름이 표준이다. pull(스크레이프)은 애플리케이션이 현재 수치를 노출하는 끝점(/metrics)을 열어 두면, 수집 서버가 일정 주기(예: 15초)로 긁어 가는 방식이다 — Prometheus로 대표되는 모델로, 무엇을 수집하는지가 수집 서버 설정에 중앙화되고, 긁기 실패 자체가 "대상 죽음"의 신호가 된다. push는 애플리케이션이 수집기로 수치를 밀어 넣는 방식으로, 수명이 짧은 작업(배치·서버리스)처럼 "긁힐 때까지 살아 있지 않은" 대상에 적합하다.

어느 쪽이든 공통의 요점은 집계가 애플리케이션 프로세스 안에서 먼저 일어난다는 것이다. 카운터 증가는 메모리 위 정수 연산일 뿐이고, 네트워크를 타는 것은 주기당 한 번의 스냅샷이다 — 사건마다 무언가를 전송하는 로그와 비용 구조가 갈라지는 지점이 바로 여기다. 그리고 이 "프로세스 안 집계"는 시계열 조합마다 메모리 칸을 하나씩 차지한다. 조합의 수가 폭발하면 무슨 일이 벌어지는가 — 메트릭 운영의 최대 함정, 카디널리티다.

4. 카디널리티 — 시계열 수가 폭발하는 방식

한 메트릭의 시계열 수는 라벨 값 개수의 곱이다:

http_requests_total{method, status, endpoint} method 5종 × status 8종 × endpoint 40종 = 시계열 1,600개 (감당 가능) 여기에 user_id 라벨(사용자 10만 명)을 추가하면: 1,600 × 100,000 = 1억 6천만 시계열 (붕괴)

시계열 하나마다 수집기의 메모리 칸·저장소의 인덱스 항목·질의 시 스캔 대상이 하나씩 늘므로, 카디널리티 폭발은 곧 메모리 폭발 + 질의 시간 폭발 + (과금형 백엔드라면) 비용 폭발이다. 치명적인 것은 값의 집합이 무계(unbounded)인 라벨이다 — 사용자 ID, 세션 ID, 요청 경로 원문(경로 매개변수 포함), 오류 메시지 원문처럼 새 값이 계속 태어나는 것들. 이런 라벨 하나가 시계열을 무한 증식시킨다.

라벨 추가 전 3문(問) — ① 값의 집합이 유한하고 안정적인가(전부 나열할 수 있는가)? ② 이 라벨로 sum by 집계를 실제로 할 것인가? ③ 값 종류가 대략 수백~천 이하인가? 하나라도 "아니오"면 라벨이 아니라 로그(또는 추적)의 필드가 될 자리다. 경로는 원문 대신 매개변수를 지운 틀(/users/{id})로 정규화해 넣는 것이 표준 처방이다.

최근에는(2020년대 중반 기준) 이 함정이 보편화되면서 방어 장치도 표준화되는 추세다 — 계측 SDK·수집기 수준의 카디널리티 상한(한도 초과 조합을 overflow로 뭉침), 수집 단계의 라벨 삭제·재라벨링, 스크레이프당 샘플 상한 같은 장치들이다. 다만 이는 안전벨트일 뿐, 설계 원칙은 여전히 "무계 값은 라벨에 넣지 않는다"이다.

여기까지가 수치를 모으는 쪽의 전부다. 남은 절반은 모인 수치를 읽는 쪽 — 대시보드다.

5. 대시보드 — 그래프 진열장이 아니라 질문의 답안지

나쁜 대시보드는 잴 수 있는 것을 전부 그린 진열장이고, 좋은 대시보드는 정해진 질문에 위에서 아래로 답하는 화면이다. 질문의 표준 틀이 두 가지 있다.

틀대상보는 것
RED요청을 처리하는 서비스Rate(초당 요청 수) · Errors(오류율) · Duration(지연 분포)
USE자원(CPU·메모리·디스크·풀)Utilization(사용률) · Saturation(포화 — 대기열) · Errors(오류)

서비스마다 RED 세 줄을 최상단에 두면 "지금 정상인가"가 한눈에 판정되고, 이상이 보일 때만 자원(USE)·하위 구성요소로 파고드는 층위 구조가 만들어진다.

Duration에서 결정적인 규율 하나 — 지연은 평균으로 보지 않는다. 지연 분포는 한쪽 꼬리가 긴 형태가 보통이라, 대부분이 50ms인데 일부가 5초여도 평균은 "괜찮은 숫자"로 뭉개진다. 백분위(percentile)로 본다: p50(중앙값)은 보통의 경험, p99는 최악에 가까운 1%의 경험. "p99가 나쁘다"는 것은 100번에 1번꼴로 누군가 심각하게 느린 응답을 받고 있다는 뜻이며, 요청이 많은 시스템일수록 그 "1%"는 절대 수로 거대하다. 히스토그램(§2)이 존재하는 이유가 바로 이 백분위 추정이다.

대시보드 설계의 리트머스 — 각 그래프에 "이 그래프가 답하는 질문"을 한 문장으로 적을 수 있는가? 적을 수 없는 그래프는 장식이고, 장애 상황에서는 소음이다. 질문이 같은 그래프끼리 묶고, 질문의 긴급도 순으로 위에서 아래로 배치한다.

6. 흔히 헷갈리는 지점

  • "평균 응답 시간이 정상이니 괜찮다" — 꼬리를 못 본 것이다. 평균은 긴 꼬리를 숨긴다. 보고·경보의 기준은 백분위(p95·p99)로 두는 것이 기본기다.
  • 카운터 그래프가 "우상향 직선"이라 놀람. 카운터는 누적치라 원래 계속 오른다 — 정보는 기울기(rate)에 있다. 재시작 시 0으로 떨어지는 리셋도 정상이며, rate 계산이 이를 보정한다.
  • 히스토그램 백분위는 정확값이 아니라 추정값. 버킷 경계 안에서 보간하므로, 버킷 구획이 관심 구간과 어긋나면 추정이 거칠어진다. "p99 = 2.0초"가 버킷 경계의 산물일 수 있음을 알고 읽는다.
  • 메트릭으로 개별 사건을 추적하려는 시도. "그 요청이 왜 실패했나"를 메트릭에서 찾으면 §4의 함정(ID를 라벨로)으로 직행한다. 개별 사건은 로그·추적의 영토다 — 도구를 바꿀 신호이지, 라벨을 늘릴 신호가 아니다.
  • 수집 주기보다 짧은 스파이크는 안 보인다. 15초 주기 수집 사이에 일어난 1초짜리 폭증은 스냅샷 사이로 빠져나간다. 메트릭은 연속 기록이 아니라 표본이라는 한계를 전제로 읽는다.

★ 7. 언어별 대조

"프로세스 안에서 집계하고 스냅샷만 내보낸다"(§3)는 모델은 공통이지만, 그 집계를 담는 자리 — 스레드가 나눠 갖는가, 프로세스가 나뉘는가, 증가 연산의 원가는 얼마인가 — 는 언어 런타임의 성격을 그대로 탄다.

7.1 Python — 카운터는 프로세스에 산다: 포크 워커의 함정

계측 클라이언트의 카운터는 결국 프로세스 메모리 위의 변수다. Python 웹 서비스는 성능을 위해 워커 프로세스를 여러 개 띄우는 구성이 일반적인데, 그 순간 같은 이름의 카운터가 프로세스 수만큼 따로 존재하게 된다 — 스크레이프 요청은 그중 한 워커에게만 도착하므로, 매번 다른 워커의 부분 수치가 읽히는 조각난 그림이 나온다. 

from prometheus_client import Counter, Histogram

REQUESTS = Counter("app_requests_total", "총 요청 수",
                   ["method", "status"])          # 라벨: 유계 값만 (§4)
LATENCY  = Histogram("app_request_seconds", "응답 시간")

def handle(request):
    with LATENCY.time():                          # 관측값을 버킷에 집계
        resp = process(request)
    REQUESTS.labels(request.method, resp.status).inc()
    return resp

# 함정: 워커 4개 구동 시 위 카운터는 "4벌" 존재한다.
# 표준 처방: 멀티프로세스 모드 — 워커들이 공유 저장 공간에 수치를 쓰고,
# 노출 시점에 합산한다 (클라이언트가 공식 지원하는 구성)

Python 관점의 통찰: 이 함정은 라이브러리 결함이 아니라 §3의 모델("집계는 프로세스 안에서")과 Python의 스케일 방식("프로세스를 늘려서")이 정면 충돌한 결과다. 그래서 처방도 모델 수준이다 — 집계 저장소를 프로세스 밖(공유 파일·공유 메모리)으로 빼거나, 프로세스마다 식별 라벨을 붙여 질의 시점에 합산하거나. 어느 쪽이든 "내 수치가 어느 프로세스의 것인가"를 물을 줄 아는 것이 Python 계측의 첫 감각이다.

7.2 C++ — 증가 연산의 원가: 핫패스 위의 계측

초당 수십만 번 실행되는 경로에 카운터를 놓는 순간, 그 증가 연산 자체가 성능 인자가 된다. 여러 스레드가 같은 카운터를 올리려면 원자적 연산(atomic operation) — 중간에 끼어들 수 없게 보장된 갱신 — 이 필요한데, 이는 일반 덧셈보다 비싸고, 모든 스레드가 같은 메모리 주소를 두드리므로 코어 간 경합이 생긴다. 

#include <atomic>
#include <cstdint>

std::atomic<uint64_t> g_requests{0};

void handle_request() {
    // 원자적 증가 — 락 없이 스레드 안전.
    // 순서 보장이 필요 없는 단순 카운트는 relaxed로 원가 최소화
    g_requests.fetch_add(1, std::memory_order_relaxed);
    // ... 처리 ...
}
// 스크레이프 시점: g_requests.load() 스냅샷을 노출 (§3의 모델 그대로)

C++ 관점의 통찰: 원자 카운터의 진짜 비용은 연산 자체보다 캐시에서 온다 — 여러 코어가 한 주소를 갱신하면 그 값을 담은 캐시 라인(캐시가 데이터를 주고받는 최소 단위)이 코어 사이를 계속 오가며 대역을 태운다. 극단적 핫패스의 표준 처방은 "스레드/코어별 카운터에 각자 쌓고, 읽을 때 합산" — 흥미롭게도 이것은 7.1의 Python 멀티프로세스 처방과 같은 모양이다. 스케일 단위(스레드든 프로세스든)마다 지역 집계 + 읽기 시점 합산이라는 패턴이 계측의 범언어 정답인 셈이다.

7.3 Java / JS·TS — 한 줄 요약

Java의 Micrometer는 로깅의 SLF4J처럼 "계측 API와 백엔드의 분리"를 표준화한 창구로, 프레임워크가 HTTP·풀·JVM 지표를 자동 계측해 주는 대신 어떤 라벨이 기본 부착되는지 파악하는 것이 카디널리티 관리(§4)의 출발점이 된다 — JVM 내부 상태를 노출하는 더 오래된 통로인 JMX와의 관계는 P2의 주제다. JS·TS(Node)는 단일 이벤트 루프 덕에 프로세스 안 동시성 걱정은 적지만, 클러스터로 다중 프로세스를 띄우는 순간 Python과 동일한 합산 문제를 만난다.

8. 함께 알면 좋은 것

  • OpenTelemetry — 메트릭·로그·추적 세 신호의 계측 API와 전송 형식을 벤더 중립으로 표준화한 프로젝트. 최근에는(2020년대 중반 기준) 신규 계측의 기본 선택지로 자리 잡아, "계측은 표준으로, 백엔드는 교체 가능하게"라는 방향이 굳어지는 추세다.
  • 수집·시각화 생태계 — 수집·저장·질의(대표 예: Prometheus)와 대시보드(대표 예: Grafana)의 조합이 사실상의 공통어다. 개념(§2~5)은 도구가 바뀌어도 그대로 이식된다.
  • exemplar — 집계된 메트릭 지점에 "이 버킷에 들어간 실제 요청 하나"의 추적 ID를 매달아 두는 기법. §1에서 잃어버린 개별 사건의 얼굴을, 그래프의 이상 지점에서 곧장 추적으로 건너가는 다리로 복원한다.
  • 고카디널리티 대응의 두 갈래 — 상한·재라벨링으로 막는 접근(§4)과, 고카디널리티를 감당하도록 저장·질의 구조를 바꾼 백엔드로 수용하는 접근이 공존하며 발전 중이다. 어느 쪽이든 "라벨 3문"의 설계 규율이 먼저다.
  • 경보와 SLO로 가는 길 — 대시보드는 사람이 보는 화면이고, 같은 메트릭에 임계와 목표(SLO)를 걸면 기계가 깨우는 경보가 된다. 어떤 지표에 어떤 임계를 거는가는 P5의 주제다.

9. 한 장 요약

  • 메트릭 = 수집 시점 사전 집계 + 시계열 저장. 로그(사건 수 비례)와 비용 구조가 다르며, 추이는 메트릭·개별 사건은 로그로 분담한다.
  • 시계열은 이름+라벨 조합마다 하나 — 카운터는 rate로, 게이지는 그대로, 히스토그램은 백분위 추정용.
  • 집계는 프로세스 안에서 먼저 일어나고, pull(스크레이프)·push는 그 스냅샷의 운반 방식이다.
  • 카디널리티 = 라벨 값의 곱. 무계 값(ID·경로 원문)을 라벨에 넣는 순간 붕괴 — 라벨 3문(유계인가·집계하는가·~천 이하인가)으로 방어한다.
  • 대시보드는 질문의 답안지: 서비스는 RED, 자원은 USE, 지연은 평균 아닌 백분위(p50/p99).
  • 다중 프로세스(Python·Node 클러스터)는 지역 집계+합산 구성이 필요하고, C++ 핫패스는 증가 연산의 원가까지 설계 대상이다 — 지역 집계+읽기 시 합산은 범언어 공통 패턴.

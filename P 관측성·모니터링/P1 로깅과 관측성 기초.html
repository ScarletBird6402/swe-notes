P1 로깅과 관측성 기초

0. 한눈에 보는 결론

  • 로그의 목적은 "지금 보는 것"이 아니라 "나중에, 없던 자리에서 재구성하는 것"이다 — 장애는 디버거를 붙일 수 없는 시간과 장소에서 터진다.
  • 관측성(observability)은 시스템 바깥으로 나온 출력만으로 내부 상태를 추론할 수 있는 성질이며, 로그는 그 세 기둥(로그·메트릭·추적) 중 첫 번째다.
  • 로그 레벨은 심각도에 대한 계약이다: 레벨을 일관되게 매기면 "운영에서는 INFO 이상만, 조사할 때만 DEBUG"처럼 코드를 바꾸지 않고 출력량을 조절할 수 있다.
  • 구조적 로깅(structured logging)은 로그를 문장이 아니라 검색·집계 가능한 데이터(키-값)로 남기는 것이다 — 사람이 읽는 한 줄이 아니라 기계가 질의하는 레코드.
  • 상관관계 ID(correlation ID)는 요청 하나에 부여한 식별자를 모든 로그 라인에 전파해, 수만 줄 로그 더미에서 한 요청의 이야기만 실처럼 뽑아내게 한다.
  • 흔한 실패는 기술이 아니라 규율에서 온다: 레벨 남발, 문자열 이어붙이기, 예외를 삼키고 로그 한 줄로 끝내기, 민감정보 출력.

1. 왜 로그인가 — 디버거가 없는 곳에서 일어나는 일

개발 중에는 중단점을 걸고 변수를 들여다볼 수 있다. 그러나 운영 서버의 문제는 어젯밤 3시에, 특정 사용자에게만, 재현 불가능한 조합으로 발생한다. 그 순간으로 돌아갈 수 없으므로, 시스템이 스스로 남긴 기록이 유일한 증거가 된다. 로깅은 이 증거를 미리, 체계적으로 남기는 행위다.

관측성이라는 더 큰 그림에서 보면, 로그는 "무슨 일이 있었는가"(이산적 사건), 메트릭은 "얼마나 자주·많이"(수치의 시계열), 추적(tracing)은 "요청이 어디를 거쳐 어디서 느려졌는가"(경로)를 담당한다. 이 문서는 첫 기둥인 로그를 다루며, 나머지 둘은 관련 문서에서 이어진다.

[사건 발생] → 로그(무엇이 있었나) + 메트릭(얼마나) + 추적(어디서) └─ 세 출력을 합쳐 내부 상태를 "밖에서" 추론 = 관측성

print와 로깅의 차이는 출력 대상이 아니라 제어권이다. print는 항상 찍히고 항상 같은 곳으로 가지만, 로거는 레벨로 걸러지고, 포맷이 통일되고, 목적지(콘솔·파일·수집기)를 코드 밖 설정으로 바꿀 수 있다.

2. 로그 레벨 — 심각도의 계약

로그 레벨은 대부분의 생태계에서 대체로 다음 사다리를 공유한다. 중요한 것은 이름이 아니라 각 레벨이 요구하는 행동이다.

레벨의미요구되는 행동
TRACE/DEBUG개발자용 상세 흐름·변수 값평시에는 꺼 둔다. 조사 시에만 켠다
INFO정상 동작의 이정표(시작·완료·주요 상태 전이)운영 기본 출력. 읽어서 "잘 돌고 있음"을 확인
WARN지금은 견뎠지만 방치하면 문제가 될 조짐(재시도 발생, 임계 근접)추이를 지켜본다. 반복되면 조사
ERROR해당 작업이 실패했고 개입이 필요알림·조사 대상. 실패한 작업 단위가 명확해야 함
FATAL프로세스가 더 진행할 수 없음즉시 대응. 대개 프로세스 종료를 동반

이 사다리가 계약인 이유: 레벨이 일관되면 필터가 의미를 갖는다. 운영 환경은 INFO 이상만 출력하도록 설정하고, 장애 조사 때만 특정 모듈의 레벨을 DEBUG로 내리는 식으로 — 코드 수정·재배포 없이 — 관찰의 해상도를 조절한다. 반대로 사소한 것을 ERROR로, 실패를 INFO로 찍는 코드가 섞이면 필터는 무의미해지고, 진짜 오류가 소음에 묻힌다.

흔히 헷갈리는 지점 — "ERROR인데 아무도 안 봐도 되는 로그"는 레벨 오용의 신호다. 어떤 로그를 ERROR로 찍을지 망설여지면 "이 라인이 찍혔을 때 사람이 개입해야 하는가"를 물으면 된다. 아니라면 WARN 이하다. 이 질문 하나가 알림 소음의 대부분을 예방한다.

3. 구조적 로깅 — 문장이 아니라 데이터

전통적 로그는 사람이 읽을 문장이다: "user 42 checkout failed after 3 retries". 사람 한 명이 읽기엔 좋지만, "지난 1시간 동안 재시도 후 실패한 결제가 몇 건인가?"라고 질의하려는 순간 문제가 된다 — 문장마다 표현이 달라 정규식 곡예가 시작된다.

구조적 로깅은 같은 사건을 필드가 분리된 레코드로 남긴다: 

{"level":"ERROR", "event":"checkout_failed", "user_id":42,
 "retries":3, "correlation_id":"a1b2c3", "ts":"2026-07-06T14:02:11Z"}

이제 수집기에서 event = checkout_failed AND retries >= 3처럼 필드로 거르고, 세고, 그래프로 만들 수 있다. 핵심 전환은 포맷(JSON이냐 아니냐)이 아니라 관점이다: 로그의 1차 독자는 사람이 아니라 검색·집계 시스템이고, 사람은 그 시스템을 통해 로그를 만난다.

실무 규율 한 가지 — 메시지는 고정 문자열로, 변하는 값은 필드로. "user 42 failed"처럼 값을 문장에 녹이면 같은 사건이 42가지 메시지로 흩어진다. event="checkout_failed" + user_id=42로 분리하면 같은 사건은 항상 같은 키로 모인다.

4. 상관관계 ID — 로그 더미에서 한 요청의 실을 뽑기

운영 로그는 수많은 요청의 라인이 시간순으로 뒤섞여 쌓인다. 어떤 사용자의 요청 하나가 실패했을 때 필요한 것은 "그 요청이 남긴 라인들만" 순서대로 보는 것이다. 상관관계 ID는 요청이 시스템에 들어올 때 고유 식별자를 하나 발급하고, 그 요청을 처리하는 모든 코드 경로의 모든 로그 라인에 같은 ID를 자동으로 붙이는 기법이다.

[요청 진입] → ID 발급(a1b2c3) → 컨텍스트에 저장 ├─ 컨트롤러 로그 {correlation_id: a1b2c3, ...} ├─ 서비스 로그 {correlation_id: a1b2c3, ...} ├─ 외부 호출 헤더에 ID 전파 → 상대 서비스 로그에도 a1b2c3 └─ 오류 발생 로그 {correlation_id: a1b2c3, ...} 검색: correlation_id = a1b2c3 → 이 요청의 전체 이야기만 시간순 정렬

구현의 요점은 두 가지다. 첫째, ID를 함수 인자로 일일이 넘기지 않도록 요청 범위의 컨텍스트(스레드·비동기 작업에 붙는 보관소)에 넣어 로거가 자동으로 꺼내 쓰게 한다. 둘째, 프로세스 경계를 넘을 때(HTTP 호출, 메시지 발행) ID를 헤더·메타데이터로 전파한다 — 이 전파를 표준화·자동화한 것이 분산 추적이며, 상관관계 ID는 그 수동 원형이다.

5. 흔히 헷갈리는 지점

  • "로그를 많이 남기면 관측성이 좋아진다" — 아니다. 로그는 저장·전송·검색 비용이 있고, 소음은 신호를 가린다. 좋은 관측성은 양이 아니라 질의 가능성(구조화)과 연결성(상관관계 ID)에서 온다.
  • 예외를 삼키고 로그 한 줄로 끝내기 — 조용한 실패의 제조법. catch 블록에서 로그만 찍고 정상 흐름으로 복귀하면, 시스템은 겉으로 멀쩡한데 데이터는 조용히 어긋난다. 로그는 실패 처리가 아니라 실패의 기록일 뿐이다 — 처리(전파·재시도·보상)는 별도로 설계해야 한다.
  • 로그에 민감정보 — 로그는 대개 DB보다 보호가 약한 곳에 오래 남는다. 비밀번호·토큰·개인정보는 애초에 찍지 않거나 마스킹한다. "디버깅에 필요해서 잠깐"이 사고의 표준 경로다.
  • 로깅 호출 자체의 비용. 걸러질 DEBUG 로그라도, 메시지를 만드는 연산(문자열 조립·직렬화)이 호출부에서 먼저 실행되면 비용은 이미 지불된 것이다. 지연 평가(람다·포맷 인자 분리)를 지원하는 로거 관용구를 쓰는 이유다.

★ 6. 언어별 대조

지금까지 본 원칙 — 레벨의 일관성, 컨텍스트의 자동 전파, 걸러지는 로그의 비용 제거 — 은 언어 중립적이다. 그런데 이 원칙을 실제로 강제하는 기제는 언어마다 표준 라이브러리의 유무, 동시성 모델, 타입 시스템에 따라 확연히 갈린다. 특히 "컨텍스트를 어떻게 자동으로 전파하는가"는 그 언어가 요청을 어떻게 처리하는가(스레드 하나당 요청 하나인가, 이벤트 루프에서 콜백이 뒤섞이는가)에 직접 좌우된다.

언어대표 도구레벨 제어 기제컨텍스트 전파(상관관계 ID)비용 제어의 특이점
JavaSLF4J(파사드) + Logback·Log4j2 등 구현체설정 파일 기반, 운영 중 재조정 가능MDC — 스레드에 붙는 키-값 저장소지연 평가 오버로드로 문자열 조립 비용 회피
JS·TSconsole(원시적) → pino·winston 등 구조적 로거로거 인스턴스 설정AsyncLocalStorage — 비동기 체인을 따라가는 저장소동기 I/O로 인한 이벤트 루프 블로킹 회피
Python표준 logging 모듈(내장)로거 이름의 점(.) 구분 계층 트리contextvars + 필터·어댑터포맷 인자 분리를 통한 지연 평가
C++표준 로깅 없음 — spdlog 등 라이브러리 선택런타임 설정 + 컴파일 타임 매크로 제거수동 전달 또는 스레드 로컬 직접 구성로그 호출 자체를 바이너리에서 제거 + 전역 로거의 초기화 순서

6.1 Java — SLF4J라는 파사드, 그리고 스레드에 묶인 컨텍스트

Java 생태계는 이 문서의 원칙 대부분을 표준 관행으로 제도화했다. SLF4J는 파사드(facade — 여러 구현을 하나의 단순한 창구 뒤로 감추는 설계)로, 라이브러리·애플리케이션 코드는 SLF4J의 인터페이스에만 대고 로그를 남기고, 실제로 그 로그를 어디에 어떤 형식으로 쓸지는 배포 시점에 클래스패스에 올라온 구현체(Logback, Log4j2 등)가 결정한다. 그래서 코드는 로깅 구현체를 몰라도 되고, 운영 환경은 설정 파일 하나로 어느 패키지를 어느 레벨로 찍을지 재조정할 수 있다 — 이 재조정은 코드 재배포 없이 설정만 다시 읽어들이는 방식으로 이뤄지는 경우가 많다.

컨텍스트 전파는 MDC(Mapped Diagnostic Context — 현재 스레드에 매달리는 키-값 저장소)가 담당한다. Java의 전통적 요청 처리 모델은 "요청 하나당 스레드 하나"이므로, 요청이 들어올 때 MDC에 넣은 상관관계 ID는 그 요청을 처리하는 호출 스택 전체에서 별도로 전달할 필요 없이 자동으로 따라온다. 

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

class CheckoutService {
    private static final Logger log = LoggerFactory.getLogger(CheckoutService.class);

    void process(String requestId, int userId) {
        MDC.put("correlationId", requestId);   // 이 스레드의 이후 모든 로그에 자동 포함
        try {
            log.info("checkout_started userId={}", userId);
            // ... 비즈니스 로직 ...
        } finally {
            MDC.clear();   // 스레드 풀 환경에서 다음 요청으로의 오염을 막는 필수 정리
        }
    }
}

Java 관점의 통찰: MDC가 "스레드에 붙는다"는 성질은 축복이자 함정이다. 스레드 풀에서는 스레드가 재사용되므로, finally에서 clear()를 빠뜨리면 다음 요청이 이전 요청의 상관관계 ID를 그대로 물려받는 조용한 오염이 생긴다. 그리고 비동기·리액티브 코드로 넘어가 콜백이 다른 스레드에서 실행되면 MDC는 그 경계를 넘지 못하므로, 스레드를 넘길 때 컨텍스트를 명시적으로 복사해야 한다.

6.2 JS·TS — console의 한계와 이벤트 루프에서 컨텍스트를 잃지 않는 법

console.log는 레벨도, 필드 구조도, 목적지 전환도 없는 원시적 출력이다. 값을 문자열로 즉시 조립해 표준 출력에 동기적으로 쓰기 때문에, 트래픽이 몰리면 이 출력 자체가 이벤트 루프(자바스크립트가 콜백을 순서대로 꺼내 실행하는 단일 스레드의 처리 루프)를 잠깐씩 막을 수 있다. pino 같은 구조적 로거는 로그를 JSON 레코드로 남기고, 무거운 직렬화·쓰기를 별도 흐름으로 넘겨 이 병목을 줄인다.

더 근본적인 문제는 컨텍스트 전파다. Node의 동시성 모델에는 요청마다 배정되는 전용 스레드가 없다 — 하나의 스레드가 여러 요청의 콜백을 번갈아 실행한다. 그래서 Java의 MDC처럼 "현재 스레드"에 상관관계 ID를 걸어 둘 자리가 없고, 과거에는 모든 함수 인자에 ID를 꿰어 넘기거나 요청 객체에 얹어 전달하는 수밖에 없었다. AsyncLocalStorage는 이 공백을 메운 해법으로, 저장소에 넣은 값을 콜백·프라미스·await 경계를 넘어서도 그 실행 체인을 따라 자동으로 유지한다. 

const { AsyncLocalStorage } = require('node:async_hooks');
const pino = require('pino');

const logger = pino();
const als = new AsyncLocalStorage();

function withRequest(correlationId, fn) {
  als.run({ correlationId }, fn);   // 이 콜백 체인 전체에 컨텍스트가 따라붙는다
}

async function checkout(userId) {
  const { correlationId } = als.getStore();     // 인자로 넘기지 않아도 꺼낼 수 있다
  logger.info({ correlationId, userId }, 'checkout_started');
  await chargeCard(userId);                     // await 너머에서도 store는 유지된다
}

JS·TS 관점의 통찰: AsyncLocalStorage가 자동으로 따라가는 것은 프라미스 체인·await처럼 언어가 추적하는 비동기 흐름이다. 반면 setTimeout이나 별도 이벤트 리스너처럼 완전히 새 매크로태스크로 갈라지는 지점에서는 체인이 끊길 수 있어, 그런 진입점마다 컨텍스트를 다시 run으로 감싸야 한다는 점을 유의해야 한다.

6.3 Python — 로거 "계층 트리"라는 설계

Python의 logging은 로거를 이름의 점(.) 구분 계층으로 조직한다: app.db.pool 로거는 app.db의 자식이고, 레벨·핸들러 설정은 부모에서 자식으로 흘러내린다. 그래서 "앱 전체는 INFO, 단 app.db 계열만 DEBUG"라는 정밀 제어가 코드 수정 없이 가능하다 — "레벨은 계약이고 필터로 해상도를 조절한다"는 원칙이 언어 표준 라이브러리의 객체 모델(로거 인스턴스 사이의 부모-자식 관계)에 그대로 내장된 형태다. 

import logging, contextvars

correlation_id = contextvars.ContextVar("correlation_id", default="-")

class CorrelationFilter(logging.Filter):
    def filter(self, record):
        record.correlation_id = correlation_id.get()  # 모든 레코드에 자동 주입
        return True

logger = logging.getLogger("app.checkout")   # "app"의 자식 — 설정을 상속
logger.addFilter(CorrelationFilter())

# 요청 진입 지점에서:
correlation_id.set("a1b2c3")
logger.info("checkout_started", extra={"user_id": 42})

Python 관점의 통찰: logger.debug("value=%s", big_obj)처럼 포맷 인자를 분리해 넘기면, 레벨이 걸러질 때 문자열 조립 자체가 생략된다 — f-string으로 미리 조립해서 넘기는 순간 이 지연 평가의 이점을 스스로 버리는 셈이다. "걸러질 로그는 비용도 걸러져야 한다"는 원칙이 표준 라이브러리의 관용구로 굳어진 예다.

6.4 C++ — 표준이 없다는 것, 그리고 비용과 수명을 컴파일 타임에 다루는 것

C++에는 표준 로깅이 없어 라이브러리(예: spdlog)를 선택하게 되는데, 이 생태계가 성능에 민감한 만큼 로깅 비용 제어가 언어 특성과 깊게 얽힌다. 핵심 기제는 두 가지다. 첫째, 포맷팅을 호출 시점이 아니라 필터 통과 후로 미루는 API 설계. 둘째, 매크로와 컴파일 타임 상수를 이용해 일정 레벨 이하의 로그 호출을 바이너리에서 아예 제거하는 것 — 걸러지는 수준이 아니라, 기계어에 존재하지 않게 만든다.

비용뿐 아니라 수명도 문제가 된다. 로거 객체를 평범한 전역 변수로 선언하면, 서로 다른 번역 단위(translation unit — 소스 파일 하나가 컴파일되는 단위)에 걸친 전역 객체들의 초기화 순서는 표준이 보장하지 않는다(정적 초기화 순서 문제, static initialization order fiasco). 다른 전역 객체의 생성자가 아직 만들어지지 않은 로거를 먼저 사용하면 정의되지 않은 동작으로 이어진다. 이를 피하는 관용 기법이 함수 지역 static(Meyer's singleton — 함수가 처음 호출될 때 한 번만 초기화되는 지역 정적 변수를 이용한 지연 생성 패턴)이다. 

#include <spdlog/spdlog.h>
#include <memory>

// 전역 로거를 "함수 지역 static"으로 감싸 초기화 순서 문제를 피한다
// — 다른 전역 객체의 생성자에서 먼저 호출돼도 이 시점에야 비로소 생성된다
std::shared_ptr<spdlog::logger>& app_logger() {
    static std::shared_ptr<spdlog::logger> logger = spdlog::stdout_color_mt("app");
    return logger;
}

// 컴파일 타임 레벨: 이보다 낮은 로그는 코드 자체가 사라짐
// (빌드 옵션) -DSPDLOG_ACTIVE_LEVEL=SPDLOG_LEVEL_INFO
void process(int user_id) {
    SPDLOG_LOGGER_DEBUG(app_logger(), "cache state user={}", user_id);   // 릴리스 빌드에서 소멸
    SPDLOG_LOGGER_INFO(app_logger(), "checkout_started user={}", user_id);
}

C++ 관점의 통찰: "런타임에 거른다"와 "컴파일 타임에 지운다"는 결과가 같아 보여도 다르다 — 전자는 분기 비용과 코드 크기가 남고, 후자는 흔적이 없는 대신 배포 후 레벨을 내려도 그 로그를 되살릴 수 없다. 그리고 로거를 일반 전역 변수로 두면 이 비용 최적화 이전에 "초기화되지 않은 로거에 접근"이라는 더 근본적인 수명 문제가 먼저 터질 수 있다는 점에서, C++의 로깅은 성능 설계이자 동시에 객체 수명 설계다.

7. 함께 알면 좋은 것

  • 중앙 수집 파이프라인 — 각 서버의 로그를 한곳으로 모아 검색하는 구조(수집기→저장소→검색 UI). 구조적 로깅의 효용은 중앙화와 만날 때 완성된다.
  • 메트릭과의 역할 분담 — "몇 건인가"를 로그 집계로 세는 것은 비싸다. 수치 추이는 메트릭으로, 개별 사건의 맥락은 로그로.
  • 분산 추적 — 상관관계 ID의 전파를 표준화하고 구간별 소요 시간까지 기록하는 확장. 마이크로서비스에서 "어디가 느린가"의 답.
  • 샘플링과 보존 정책 — 전량 저장은 비용 폭탄이다. 정상 요청은 일부만, 오류는 전량 남기는 식의 차등과, 보존 기간 설계.
  • 로그와 민감정보 규제 — 개인정보가 로그에 남으면 삭제 요구·유출 사고의 사각지대가 된다. 마스킹·필드 차단을 로거 계층에서 강제하는 접근.

8. 한 장 요약

  • 로그는 재현 불가능한 순간을 위해 시스템이 미리 남기는 증거이며, 관측성 세 기둥(로그·메트릭·추적)의 첫 번째다.
  • 로그 레벨은 심각도의 계약 — 일관돼야 필터가 의미를 갖고, 코드 수정 없이 관찰 해상도를 조절할 수 있다.
  • 구조적 로깅: 고정 메시지 + 가변 필드. 로그의 1차 독자는 사람이 아니라 검색·집계 시스템이다.
  • 상관관계 ID는 요청마다 발급해 컨텍스트로 자동 주입하고 경계 너머로 전파한다 — 뒤섞인 로그에서 한 요청의 이야기를 복원하는 실.
  • 함정은 규율 문제다: ERROR 남발, 예외 삼킴 후 로그 한 줄, 민감정보, 걸러질 로그의 조립 비용.
  • Python은 로거 계층·contextvars, C++은 컴파일 타임 제거라는 언어다운 방식으로 같은 원칙을 구현한다.

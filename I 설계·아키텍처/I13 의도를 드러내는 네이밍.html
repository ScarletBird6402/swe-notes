I13 의도를 드러내는 네이밍

0. 한눈에 보는 결론

  • 이름은 장식이 아니라 축약된 계약이다 — 읽는 사람은 본문을 열지 않고 이름만 믿고 호출한다.
  • 나쁜 이름의 진짜 비용은 "읽기 어려움"이 아니라 조용한 오독이다: 이름과 동작이 어긋나도 컴파일러·테스트는 잡아주지 않는다.
  • 계약을 정확히 쓰는 핵심 규약: 조회와 명령을 이름으로 구분하고, boolean 이름은 긍정형 질문으로 짓고, 단위·시점 같은 숨은 전제를 이름에 싣는다.
  • 코드는 진화하고 이름은 낡는다. 이름이 거짓말하기 시작하는 순간이 리네이밍 시점이며, IDE의 시맨틱 리네임 덕에 그 비용은 이미 충분히 싸다.
  • 좋은 이름의 기준은 길이가 아니라 스코프 대비 정보량이다 — 세 줄짜리 루프의 i는 좋은 이름이고, 전역에 노출된 data는 나쁜 이름이다.

1. 이름은 축약된 계약이다

코드는 한 번 쓰이고 수십 번 읽힌다. 그리고 대부분의 "읽기"는 정독이 아니라 호출부에서 이름만 보고 동작을 추정하는 훑어 읽기다. calculateShippingFee(order)라는 호출을 본 독자는 함수 본문을 열지 않는다. "주문을 받아 배송비를 계산해 돌려주겠구나, 그 과정에서 주문을 바꾸지는 않겠구나"라고 믿고 지나간다. 이 믿음이 바로 이름이 맺는 계약이다.

그래서 이름은 인터페이스의 일부다. 시그니처가 "무엇을 받아 무엇을 돌려주는가"라는 형식을 계약한다면, 이름은 "그 과정에서 무슨 일이 일어나는가"라는 의미를 계약한다. 타입 시스템이 아무리 강해도 이 의미 계약은 이름이 진다 — int를 돌려준다는 사실은 타입이 보장하지만, 그것이 "할인 적용 후 금액"인지 "할인액 자체"인지는 오직 이름만이 말해준다.

관점 전환: "좋은 이름 짓기"를 문체의 문제가 아니라 계약서 작성으로 보면 판단이 쉬워진다. 계약서의 미덕은 유려함이 아니라 정확함이다 — 읽는 사람이 본문을 열어 확인하지 않아도 되게 만드는 것.

2. 계약이 어긋나면 — 오도성 이름의 비용

계약이라는 관점에 서면, 나쁜 이름의 비용이 어디서 발생하는지도 분명해진다. 모호한 이름(process, handle, data)은 독자를 본문으로 내려보내 시간을 뺏는 정도로 끝난다. 정말 위험한 것은 오도성 이름 — 구체적이어서 믿게 만들지만 실제 동작과 어긋나는 이름이다.

이름이 모호함 → 독자가 본문을 확인 → 시간 손실 (비싸지만 안전) 이름이 거짓말 → 독자가 믿고 지나감 → 잘못된 코드가 리뷰를 통과 → 조용한 오독 (싸 보이지만 치명적)

예를 들어 getUser(id)가 "없으면 새로 만들어 저장까지" 한다면, 호출자는 읽기 전용인 줄 알고 검증 로직 안에서 호출했다가 의도치 않은 데이터 생성을 겪는다. 이 버그는 에러를 던지지 않는다. 코드도, 이름도 각자 나름대로 "정상 동작"하기 때문이다. 이름과 동작의 불일치가 만드는 동작은 하는데 에러가 없는 상태는 조용한 실패의 전형적인 입구다 — 오타로 인한 이름 불일치가 조용한 실패로 이어지는 경로는 K5 조용한 실패와 오타.html에서 다루는 것과 정확히 같은 구조다.

오도성 이름이 더 해로운 이유는 전염되기 때문이다. 어긋난 이름 하나를 믿고 작성된 호출부는 그 오해를 전제로 또 다른 이름을 낳고, 몇 단계 지나면 "코드를 다 읽기 전엔 아무 이름도 못 믿는" 상태가 된다. 이 시점부터 이름은 정보가 아니라 소음이며, 코드베이스 전체의 읽기 비용이 구조적으로 올라간다.

3. 계약을 정확히 쓰는 규약들

그렇다면 계약을 어떻게 써야 어긋나지 않을까. 오랜 시행착오 끝에 살아남은 규약들은 공통적으로 "독자가 가장 자주 오해하는 지점"을 이름에 명시한다.

3.1 조회와 명령을 이름으로 구분한다

독자가 가장 크게 오해하는 지점은 "이 함수가 상태를 바꾸는가"다. 그래서 명령-조회 분리(command-query separation, CQS) 원칙은 함수를 두 부류로 나눈다: 조회는 값을 돌려주되 상태를 바꾸지 않고(getTotal, findUser, isEmpty), 명령은 상태를 바꾸되 그 사실이 이름에 드러난다(save, register, markAsRead). 앞 절의 getUser 사례가 위험했던 이유가 바로 이 경계를 몰래 넘었기 때문이며, 정직한 이름은 findOrCreateUser처럼 부수효과(side effect)를 이름 표면에 올린다.

3.2 boolean 이름 — 긍정형 질문으로, 부정 조건 명명은 피한다

조건 분기에 쓰이는 boolean은 이름이 곧 논리식의 일부가 되므로 함정이 하나 더 있다. 부정형으로 지은 이름은 사용처마다 이중 부정을 만든다. isNotExpired가 있으면 어딘가에는 반드시 !isNotExpired가 생기고, "만료되지 않은 것이 아니면"을 매번 머릿속에서 뒤집어 읽어야 한다. 그 뒤집기 한 번이 틀리는 순간이 곧 버그다. disableAutoSave = false 같은 부정형 플래그도 같은 이유로 "이중 부정을 읽게 만드는" 이름이다. 규약은 단순하다: 긍정형 질문(isExpired, hasPermission, canRetry)으로 짓고, 부정은 사용처에서 !로 표현한다.

3.3 숨은 전제를 이름에 싣는다 — 단위·시점·범위

타입이 잡아주지 못하는 마지막 오해 지점은 값에 붙은 암묵적 전제다. delay: number는 밀리초인지 초인지 말해주지 않고, endDate는 그 날짜가 포함인지 제외인지 말해주지 않는다. 이런 전제는 delayMillis, timeoutSeconds, endDateExclusive처럼 이름에 실어야 호출부에서 계약이 보인다. 단위 오해는 값이 1000배 어긋나도 타입 검사·테스트를 통과하는, 전형적인 "조용한" 버그의 원천이기 때문이다.

공통 원리: 세 규약 모두 "독자가 확인하러 본문에 들어가지 않아도 되게 하라"는 같은 목표의 다른 단면이다. 상태 변경 여부(3.1), 논리 방향(3.2), 값의 전제(3.3) — 오해가 잦은 순서대로 이름에 명시하는 것이다.

4. 이름이 거짓말하기 시작하는 순간 — 리네이밍 시점

규약대로 정확하게 지은 이름도 영원하지 않다. 코드는 진화하기 때문이다. 처음엔 검증만 하던 validateOrder에 할인 적용이 추가되고 재고 예약이 추가되면, 이름은 그대로인데 계약 내용이 바뀐 상태 — 즉 이름이 낡아서 거짓말이 된 상태가 된다. 2절의 오도성 이름은 대부분 이렇게 태어난다. 처음부터 거짓말로 지어지는 이름은 드물고, 동작이 바뀔 때 이름을 함께 고치지 않아서 거짓말이 되는 경우가 압도적이다.

그래서 리네이밍 시점의 판단 기준은 명확하다: "이름이 거짓말하기 시작하는 순간"이 곧 리네이밍 시점이다. 동작을 바꾸는 수정을 할 때마다 "이 이름은 아직 참인가?"를 함께 묻고, 거짓이 됐다면 그 커밋 안에서 이름도 고친다. "나중에 정리하자"가 위험한 이유는 앞서 본 전염성 때문이다 — 거짓말하는 이름은 방치되는 동안 그 이름을 믿는 호출부를 계속 늘린다.

이 판단을 미루게 만들던 고전적 핑계는 "고칠 곳이 너무 많다"였지만, 현대 IDE의 리네임 리팩터링은 텍스트 치환이 아니라 구문 트리 기반으로 참조를 추적하므로 정적 언어에서는 사실상 무위험이다. 동적 언어에서는 문자열 참조(설정 키, 직렬화 필드명, 리플렉션)가 추적을 벗어날 수 있으므로, 리네임 후 전역 검색으로 옛 이름의 잔재를 확인하는 습관이 필요하다 — 특히 API 응답 필드처럼 외부와 공유된 이름은 나 혼자 리네임할 수 없는 계약이므로 별도의 호환 계획이 필요하다.

5. 흔히 헷갈리는 지점

① "이름은 길수록 좋다"? — 아니다. 기준은 길이가 아니라 스코프 대비 정보량이다. 세 줄짜리 루프의 인덱스 i는 관례로 굳은 좋은 이름이고, 모듈 전역의 userAccountInformationDataObject는 길지만 정보가 없는 나쁜 이름이다. 스코프가 넓어질수록(오래 살수록, 멀리서 보일수록) 이름에 실어야 할 문맥이 늘어날 뿐이다.

② "이름이 부족하면 주석으로 보완하면 된다"? — 주석은 호출부에서 보이지 않는다. 계약은 이름·시그니처처럼 사용하는 자리에서 보이는 것에 실어야 한다. "이 함수는 사실 저장도 함"이라는 주석은 본문을 연 사람만 구제할 뿐이고, 본문을 열지 않는 것이 이름의 존재 이유였다.

③ "타입이 강하면 이름은 대충 지어도 된다"? — 타입은 형식(무엇을 받고 돌려주나)을 검사할 뿐, 의미(부수효과 유무, 단위, 논리 방향)는 검사하지 못한다. 3절의 세 규약이 전부 "타입이 못 잡는 지점"을 겨냥하는 이유다.

④ 일관성과 정확성이 충돌하면? — 코드베이스 전체가 get 접두를 느슨하게 쓰고 있는데 혼자 엄격한 이름을 쓰면 오히려 혼란이라는 딜레마가 있다. 원칙은 "같은 단어는 코드베이스 안에서 같은 의미"라는 어휘의 일관성을 지키되, 일관성을 이유로 거짓말을 복제하지는 않는 것이다. 관례가 잘못됐다면 새 이름 하나를 몰래 다르게 짓는 것이 아니라 관례 자체를 고치는 결정이 필요하다.

★ 6. 언어별 대조

"이름이 계약"이라는 원리는 언어 중립이지만, 그 계약을 언어가 얼마나 검사해 주는가는 언어마다 크게 다르다. 검사 장치가 약한 언어일수록 이름이 짊어지는 책임이 커진다.

언어이름 계약을 뒷받침하는 장치이름만 남는 지점(특유 함정)
Java 강타입 + 관례(JavaBeans)가 프레임워크 동작과 연결 get 접두 뒤에 숨은 부수효과 — 관례가 강할수록 배신이 치명적
JS·TS TS의 구조적 타입 검사(형식만), 린터의 이름 규칙 검사 async 함수의 반환값 오독 — truthy 검사와 결합해 조용히 어긋남
Python 관례가 사실상 전부 — _ 접두, PEP 8, 타입 힌트(선택적) 접근 제어가 없어 이름이 캡슐화 계약 그 자체
C++ const로 조회 계약을 컴파일러 검사로 승격 가능 이름이 성능 계약까지 짊어짐(복사 vs 참조), 연산자 오버로딩은 이름 없는 계약

6.1 Java — 관례가 프레임워크 계약으로 승격된 언어

Java의 get/set/is 접두는 단순한 문체가 아니라 JavaBeans 관례라는 준표준이며, 수많은 라이브러리가 리플렉션(reflection — 런타임에 클래스 구조를 조회·호출하는 기능)으로 이 이름 패턴을 파싱해서 동작을 결정한다. 직렬화 라이브러리는 getXxx를 찾아 JSON 필드를 만들고, Spring Data 계열은 findByEmailAndStatus 같은 메서드 이름 자체를 해석해 쿼리를 생성한다. 즉 Java 생태계에서 이름은 사람과의 계약을 넘어 기계가 문자 그대로 실행하는 계약이 되곤 한다 — 이름을 잘못 지으면 오독이 아니라 오동작이 된다. 

// 이름이 거짓말하는 조회 — "get"인데 상태를 바꾼다
public User getUser(String id) {
    User u = repository.find(id);
    if (u == null) {
        u = new User(id);
        repository.save(u);   // 호출자는 읽기 전용인 줄 알았는데 행이 생긴다
    }
    return u;
}

// 정직한 이름 — 부수효과가 이름 표면에 드러난다
public User findOrCreateUser(String id) { ... }

Java 관점의 통찰: 직렬화·프록시가 getter 이름을 훑는 생태계에서는 "get인데 무겁고 부수효과 있는 메서드"가 도구에 의해 예상 밖 시점에 호출되는 사고로 이어진다. 관례를 지키는 것이 곧 도구와의 호환성이다.

6.2 JS·TS — 타입이 형식을 맡고, 이름이 의미를 맡는 언어

JavaScript는 시그니처에 타입이 없으므로 이름이 유일한 사전 정보다. TypeScript가 형식 검사를 더해주지만 구조적 타이핑(structural typing — 이름이 아니라 "필요한 속성을 갖췄는가"로 타입 호환을 판정하는 방식)은 값의 모양만 볼 뿐, 단위·부수효과·논리 방향 같은 의미는 여전히 이름의 몫이다. 게다가 타입은 컴파일 시 소거되므로 런타임에는 다시 이름만 남는다. JS 특유의 함정은 async와 truthy 검사의 결합이다: 

// isValid라는 이름 + async라는 사실이 결합하면
async function isValid(input) { ... }        // 반환 타입: Promise<boolean>

if (isValid(userInput)) {                    // await 누락 — Promise는 항상 truthy
    submit(userInput);                       // 검증 결과와 무관하게 언제나 통과
}

isXxx라는 이름은 "boolean이 온다"는 강한 기대를 만들기 때문에, 실제로는 Promise가 오는 순간 이름이 절반의 거짓말이 된다. 에러 없이 항상 참이 되는 전형적 조용한 실패이며, 그래서 async 조회에는 checkValidity처럼 기대를 다르게 만드는 이름을 쓰거나 린터의 미스유즈 검사(부동 Promise 검출)를 켜는 것이 관행이다. 2020년대 중반 기준으로 typescript-eslint의 naming-convention 규칙처럼 "boolean 변수는 is/has 접두 강제" 같은 이름 규약을 기계 검사로 강제하는 설정도 널리 쓰인다.

6.3 Python — 이름이 접근 제어를 대신하는 언어

Python에는 private 키워드가 없다. 무엇이 공개 API이고 무엇이 내부 구현인지는 오직 이름 관례(_ 접두)가 계약한다. 인터프리터는 obj._cache에 접근해도 막지 않으므로, 이 계약은 컴파일러가 아니라 독자의 존중으로 유지된다 — 이름이 캡슐화 장치 그 자체인 셈이다. 덕 타이핑(duck typing — 타입 이름이 아니라 "필요한 메서드를 갖고 있는가"로 객체를 다루는 방식) 문화에서는 시그니처 선언조차 없는 경우가 많아, 함수 이름과 매개변수 이름이 사실상 문서의 전부가 된다. 여기에 @property는 메서드를 속성처럼 보이게 하는 기능이라, 잘못 쓰면 "조회처럼 보이는 명령"을 문법 차원에서 위장하게 된다: 

class Order:
    @property
    def total(self):          # 속성 접근처럼 보인다: order.total
        self._recalculate()   # 그런데 내부 상태를 바꾼다 — 위장된 명령
        return self._total

# 계약이 정직한 형태: 속성은 순수 조회로, 갱신은 동사 메서드로
#   order.total            → 저장된 값만 반환
#   order.recalculate()    → 상태 변경이 이름에 드러남

Python 관점의 통찰: PEP 8이 스타일(snake_case 등)을 통일해 주는 덕분에, Python에서 이름의 진짜 승부처는 표기법이 아니라 의미다. 타입 힌트를 붙이는 코드가 늘면서 "이름이 형식까지 설명하던 부담"은 줄었지만, is_로 시작하는 함수가 bool을 돌려주는지조차 힌트가 없으면 이름만 믿어야 하는 언어라는 본질은 그대로다.

6.4 C++ — 이름의 약속을 타입 시스템에 새길 수 있는 언어

C++는 3.1의 조회/명령 구분을 관례에만 맡기지 않고 const 멤버 함수로 컴파일러 검사에 새길 수 있다. "이 함수는 객체를 바꾸지 않는다"는 이름의 약속을 시그니처에 함께 쓰면, 약속을 어기는 구현은 컴파일 에러가 된다 — 이름 계약의 기계 검증판이다. 

class Cache {
public:
    // "조회"라는 이름의 약속이 const로 컴파일러 검사까지 받는다
    const Entry& lookup(const Key& k) const;

    // 변경 가능성이 이름과 시그니처 양쪽에 드러난다
    Entry& fetch_or_insert(const Key& k);
};

한편 C++에서 이름은 성능 계약까지 짊어진다. 값 의미론(value semantics — 대입·반환이 기본적으로 복사인 성질) 때문에 getItems()가 컨테이너를 복사해 돌려주는지 참조를 돌려주는지는 호출 비용을 수십 배 가르는데, 시그니처를 못 본 독자에게는 이름이 유일한 힌트다. 그래서 무거운 계산을 동반하면 get 대신 compute·build 같은 동사로 비용을 암시하는 관행이 있다. 반대 극단으로 연산자 오버로딩은 이름이 아예 없는 계약이다 — a + b가 무슨 일을 하는지는 순전히 구현자의 절제에 달려 있으므로, "수학적 직관과 일치할 때만 연산자를 쓴다"는 규율이 네이밍 원칙의 연장선에 있다.

C++ 관점의 통찰: const 정확성은 전파된다 — const 함수 안에서는 non-const 함수를 부를 수 없으므로, 조회/명령 구분을 한 번 타입에 새기면 컴파일러가 코드베이스 전체에 그 구분을 강제해 준다. 이름 관례가 언어 기능으로 승격되면 얻는 것이 무엇인지 보여주는 사례다.

7. 함께 알면 좋은 것

  • 명령-조회 분리 원칙의 심화 — 3.1의 구분을 아키텍처 수준으로 확장하면 읽기 모델과 쓰기 모델을 분리하는 설계(CQRS)로 이어진다. 이름 규약이 설계 원칙의 씨앗인 사례.
  • 유비쿼터스 언어(ubiquitous language) — 도메인 주도 설계의 핵심 실천. 기획·화면·코드가 같은 대상을 같은 단어로 부르도록 용어집을 유지하면, "코드에서만 쓰는 번역어"가 만드는 오독을 줄일 수 있다.
  • 린터의 이름 규칙 검사 — typescript-eslint naming-convention, Java 진영의 Checkstyle, Python의 pylint 이름 검사, C++의 clang-tidy readability-identifier-naming 등. 표기법·접두 규약은 기계에 맡기고 사람은 의미에 집중하는 분업이 현행 관행이다.
  • IDE 리네임 리팩터링 — 구문 트리 기반 리네임은 주석·문자열 내 참조까지 옵션으로 함께 갱신해 준다. "리네이밍은 비싸다"는 전제를 무너뜨린 도구이므로, 단축키 수준으로 익혀둘 가치가 있다.
  • 리팩터링 카탈로그의 Rename 계열 — 함수 이름 변경을 "옛 이름을 새 이름으로 위임 후 점진 제거"로 안전하게 수행하는 절차. 공개 API처럼 한 번에 못 바꾸는 이름의 이행 전략으로 유용하다.

8. 한 장 요약

  • 이름 = 축약된 계약. 독자는 본문 대신 이름을 읽으므로, 이름의 정확성이 곧 코드베이스의 읽기 비용을 결정한다.
  • 모호한 이름은 시간을 뺏지만, 오도성 이름은 조용한 오독을 만든다 — 에러 없이 잘못 동작하는 코드의 입구.
  • 계약 작성 3규약: 조회/명령을 이름으로 구분, boolean은 긍정형 질문으로, 단위·시점 같은 숨은 전제는 이름에 싣는다.
  • 동작이 바뀌면 이름도 같은 커밋에서 — 이름이 거짓말하기 시작하는 순간이 리네이밍 시점이다.
  • 언어가 검사해 주지 않는 부분일수록 이름의 책임이 크다: Python은 이름이 접근 제어를 대신하고, C++는 const로 이름의 약속을 컴파일러에 새긴다.
  • 표기법 규약은 린터에, 참조 갱신은 IDE에 맡기고 — 사람이 집중할 것은 "이 이름이 아직 참인가"라는 질문이다.

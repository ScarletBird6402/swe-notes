I4 의존성 주입(DI)과 테스트 용이성

0. 한눈에 보는 결론

  • 의존성 주입(DI, Dependency Injection)은 "필요한 것을 직접 만들지(new) 않고, 밖에서 받아서 쓴다"는 한 문장으로 요약된다.
  • 클래스 내부의 new는 그 구현체와의 영구 결합 선언이다 — 교체 불가, 대체 불가. DI는 이 결합을 "인터페이스로 받는 자리"로 바꿔 갈아 끼울 수 있는 틈(seam)을 만든다.
  • 그 틈의 최대 수혜자가 테스트다: 진짜 DB·메일 서버 대신 가짜(mock) 객체를 주입하면, 외부 세계 없이 내 로직만 빠르고 결정적으로 검증할 수 있다.
  • 주입 방식은 생성자 주입을 기본으로 한다 — 필수 의존성이 시그니처에 드러나고, 주입 없이는 객체가 만들어질 수조차 없기 때문이다. setter 주입은 "선택적·교체 가능" 의존성에 한정한 보조 수단이다.
  • DI는 프레임워크가 아니라 설계 기법이다. Spring 없이 new OrderService(new EmailSender())라고 손으로 조립해도 DI다. DI 컨테이너는 그 조립을 자동화해 줄 뿐이다.
  • 실무 감각: "이 클래스, 테스트하기 어렵네"라는 느낌은 대개 숨은 의존성(내부 new, 전역 접근)의 냄새다. 테스트 용이성은 설계 품질의 리트머스지다.

1. 문제 — 클래스 안의 new가 만드는 강한 결합

주문이 완료되면 확인 메일을 보내는 서비스를 보자. 가장 자연스러워 보이는 코드는 이렇다. 

public class OrderService {
    private final EmailSender emailSender = new EmailSender();  // 내부에서 직접 생성

    public void completeOrder(Order order) {
        // ... 주문 처리 로직 ...
        emailSender.send(order.getEmail(), "주문이 완료되었습니다");
    }
}

동작에는 문제가 없다. 문제는 변화와 검증에서 드러난다.

  • 교체 불가 — 알림을 메일에서 문자로 바꾸려면? OrderService의 내부 코드를 열어 고쳐야 한다. 알림 수단이라는 "남의 사정"이 주문 로직의 수정 이유가 된다.
  • 테스트 불가 — completeOrder의 주문 처리 로직을 테스트하고 싶을 뿐인데, 이 코드를 실행하면 진짜 메일이 발송된다. 메일 서버가 없는 환경에서는 테스트가 실패하고, 있는 환경에서는 테스트 돌릴 때마다 메일이 날아간다.
  • 숨은 의존성 — 이 클래스가 메일 발송 능력을 요구한다는 사실이 시그니처 어디에도 없다. 사용자는 코드를 열어 보고서야 "아, 이게 메일을 보내는구나"를 알게 된다.

원인은 하나다: new EmailSender()라는 한 줄이 "나는 반드시, 진짜 EmailSender와만 일한다"는 선언이기 때문이다. 생성을 내부에서 해버리면 그 무엇도 끼어들 수 없다.

2. 전환 — 만들지 말고, 받아라

의존성 주입의 발상은 생성의 방향을 뒤집는 것이다: 필요한 것을 안에서 만들지 않고, 밖에서 넣어 준다. 

public class OrderService {
    private final NotificationSender sender;   // ① 인터페이스로 받는 "자리"

    public OrderService(NotificationSender sender) {  // ② 생성자로 주입받음
        this.sender = sender;
    }

    public void completeOrder(Order order) {
        // ... 주문 처리 로직 ...
        sender.send(order.getEmail(), "주문이 완료되었습니다");
    }
}

// 조립하는 쪽(외부)이 무엇을 꽂을지 결정한다
OrderService service = new OrderService(new EmailSender());   // 운영: 진짜 메일
OrderService service = new OrderService(new SmsSender());     // 교체: 문자로
Before: OrderService ──(내부 new)──> EmailSender 결합이 코드에 박제 After : OrderService ──(자리만 선언)──> NotificationSender(인터페이스) ↑ 외부 조립자가 구현체를 "주입" ← 무엇을 꽂을지는 바깥의 결정

바뀐 것을 정리하면:

  • OrderService는 이제 "알림을 보낼 수 있는 무언가"만 알 뿐, 그것이 메일인지 문자인지 모른다. 구체와의 결합이 추상과의 결합으로 완화됐다.
  • 의존성이 생성자 시그니처에 공개됐다 — 이 클래스를 쓰려면 무엇이 필요한지가 계약으로 드러난다.
  • "생성과 조립"이라는 관심사가 클래스 밖으로 분리됐다. 이렇게 제어(무엇을 쓸지의 결정권)가 사용자 쪽에서 조립자 쪽으로 넘어가는 것을 제어의 역전(IoC, Inversion of Control)이라 부르고, DI는 그 대표적인 구현 수단이다.

3. 주입 방식 — 생성자 주입 vs setter 주입

"밖에서 받는다"(2절)로 방향이 정해졌다면, 다음 질문은 어느 문으로 받을 것인가다. 문의 위치에 따라 객체의 불변성과 "불완전한 상태로 존재할 수 있는가"가 갈리고, 그 차이는 4절의 테스트 장면에서 그대로 되돌아온다.

방식형태장점약점·용도
생성자 주입
(기본 권장)		 public OrderService(NotificationSender s) · 주입 없이는 객체 생성 자체가 불가 → 불완전한 상태가 존재하지 않음
· 필드를 final(불변)로 선언 가능
· 필수 의존성이 시그니처에 전부 노출		 의존성이 아주 많아지면 생성자가 비대해짐 — 단, 이는 감춰야 할 불편이 아니라 클래스가 과로 중이라는 경고등이다
setter 주입 public void setSender(NotificationSender s) · 생성 후 교체 가능
· 없어도 동작하는 선택적 의존성 표현에 적합		 · 주입을 빼먹어도 객체가 만들어짐 → 실행 중 null 폭발 위험
· 언제든 바뀔 수 있어 불변성 상실
필드 직접 주입
(프레임워크 전용)		 필드에 어노테이션만 붙여 컨테이너가 몰래 채움 코드가 짧아 보임 · 생성자도 setter도 없어 컨테이너 없이는(=순수 테스트에서는) 채울 방법이 없음
· 의존성이 시그니처에서 사라져 은폐됨 → 지양

선택 기준 한 줄: "이것 없이 이 객체가 성립하는가?" — 성립하지 않으면(필수) 생성자 주입, 없어도 기본 동작이 가능하면(선택) setter 주입. 필드 주입은 테스트에서 주입할 공식 통로가 없다는 이유 하나만으로도 피할 가치가 있다.

4. 테스트 용이성 — mock 대체가 열리는 순간

1절의 두 번째 고통 — 테스트를 돌리면 진짜 메일이 발송되는 문제 — 로 돌아가자. 2절이 만든 "갈아 끼울 수 있는 자리"와 3절이 권한 "생성자라는 문"이 갖춰졌으니, 이제 그 문으로 가짜를 들여보낼 수 있다. 이 자리의 최대 수혜자가 테스트다. 운영에서는 진짜 구현체를 꽂지만, 테스트에서는 가짜를 꽂는다. 

// 테스트용 가짜 — 메일을 보내는 척만 하고, 호출 사실을 기록한다
class FakeSender implements NotificationSender {
    List<String> sentTo = new ArrayList<>();
    public void send(String to, String message) {
        sentTo.add(to);                    // 실제 발송 없음, 기록만
    }
}

@Test
void 주문_완료시_구매자에게_알림이_발송된다() {
    FakeSender fake = new FakeSender();
    OrderService service = new OrderService(fake);   // 가짜를 주입

    service.completeOrder(order("buyer@example.com"));

    assertEquals(List.of("buyer@example.com"), fake.sentTo);  // 상호작용을 검증
}

이 테스트는 메일 서버 없이, 네트워크 없이, 밀리초 안에, 몇 번을 돌려도 같은 결과로 끝난다. 검증 대상이 "메일이 진짜 가는가"(그건 EmailSender 자신의 테스트 몫)가 아니라 "주문 완료 로직이 알림을 요청하는가"로 정확히 좁혀졌기 때문이다. 이런 대역을 통칭 테스트 더블(test double)이라 하며, 위처럼 손으로 만들 수도 있고 mock 라이브러리로 자동 생성할 수도 있다(★6.1).

4.1 왜 "테스트하기 어렵다"가 설계 냄새인가

DI 없는 1절의 코드로 같은 테스트를 시도해 보면, 가짜를 끼워 넣을 자리 자체가 없다는 벽에 부딪힌다. 테스트가 어렵다는 것은 대개 다음 중 하나가 숨어 있다는 뜻이다:

  • 내부 new — 협력자를 교체할 틈이 없음
  • 전역/정적 접근 — 어디서 무엇을 읽는지 시그니처에 없음(숨은 의존성)
  • 한 클래스가 너무 많은 협력자를 필요로 함 — 테스트 준비 코드가 산더미

그래서 테스트 용이성은 결합도의 실측기다. "테스트를 위해 설계를 굽히는" 것이 아니라, 테스트가 어렵다는 신호를 통해 결합 문제를 조기에 발견하는 것이다 — I1에서 본 "낮은 결합"이 지켜졌는지를 테스트가 매 순간 검사해 주는 셈이다.

5. DI 컨테이너 — 수동 조립의 자동화, 그 이상도 이하도 아니다

2절에서 "생성과 조립"을 클래스 밖으로 밀어냈지만, 그 노동이 사라진 것은 아니다 — 조립자의 손으로 이동했을 뿐이다. 객체가 수십 개로 늘면 new A(new B(new C(...)))식 수동 조립이 번거로워진다. DI 컨테이너는 이 조립을 대신해 주는 도구다: 클래스들을 등록해 두면, 컨테이너가 생성자 시그니처를 보고 필요한 의존성을 찾아 자동으로 꽂아서 객체를 만들어 준다. Java 진영의 Spring이 대표적이다.

순서를 바로잡자: "Spring을 쓰니까 DI를 한다"가 아니라, DI라는 설계 기법이 먼저 있고, 컨테이너는 그 조립 노동을 자동화하는 도구다. 컨테이너 없이 main에서 손으로 조립해도 완전한 DI이며, 반대로 Spring을 쓰면서도 클래스 내부에서 new를 남발하면 DI의 이점은 사라진다. 프레임워크는 기법을 대신 이해해 주지 않는다.

프론트엔드에도 같은 구도가 있다. Vue3의 provide/inject는 조상 컴포넌트가 제공한 것을 후손이 주입받는 메커니즘이고, 더 근본적으로는 컴포넌트 props 자체가 "밖에서 받는" 구조 — 즉 주입의 한 형태다. 컴포넌트가 데이터를 스스로 fetch하지 않고 props로 받도록 설계하면, 스토리북·테스트에서 가짜 데이터를 꽂기 쉬워지는 것 역시 정확히 같은 원리다.

6. 흔히 헷갈리는 지점

여기까지의 층위 — 기법(2절)·문(3절)·효용(4절)·도구(5절) — 마다 단골 오해가 하나씩 있다. ①은 5절의, ②는 2절의, ③은 4절의, ④는 3절의 그림자다.

① "DI = Spring(프레임워크)"? — 아니다. DI는 언어 불문의 설계 기법이고, 컨테이너는 편의 도구다. 이 구분이 무너지면 "프레임워크 없는 코드에서는 DI를 못 한다"는 이상한 결론에 도달한다. 함수 인자로 협력자를 받는 것조차 이미 DI다.

② "전부 인터페이스로 만들고 전부 주입해야 한다"? — 과잉이다. 갈아 끼울 이유(구현 교체 가능성, 테스트 대역 필요)가 있는 경계의 협력자(외부 통신, 저장소, 시간·난수 같은 비결정 요소)가 주 대상이다. 값 객체나 순수 계산 유틸까지 주입하면 조립 복잡도만 늘어난다 — 추상화는 공짜가 아니다.

③ "mock을 많이 쓸수록 좋은 테스트다"? — 역효과 구간이 있다. 내부 구현의 호출 순서·횟수까지 mock으로 촘촘히 검증하면, 테스트가 동작이 아니라 구현 방식에 결합된다 — 리팩토링만 해도 우수수 깨지는 취약한 테스트가 된다. mock은 경계(외부 세계)를 끊는 데 쓰고, 검증의 중심은 결과와 상태에 두는 것이 균형점이다.

④ "생성자 파라미터가 7개가 됐다. DI가 문제다"? — 반대다. DI는 문제를 만든 게 아니라 보이게 했다. 내부 new 7개는 조용히 숨지만, 생성자 파라미터 7개는 시끄럽게 드러난다 — 이 클래스의 책임이 너무 많다는(I1의 낮은 응집) 신호다. 처방은 주입을 숨기는 것이 아니라 클래스를 쪼개는 것이다.

★ 7. 언어별 대조

6절의 네 가지 오해는 언어를 가리지 않는 원리 차원의 경고였다. 그런데 그 오해가 실제로 코드에 파고드는 지점 — "의존성이 어디에 하드와이어링되기 쉬운가"와 "무엇이 대체를 가능하게 하는 관용 수단인가" — 은 언어마다 다르다. 아래 표로 개요를 잡고, 각 언어의 내부 기제 안에서 이 원리가 어떻게 나타나는지 살펴본다.

언어결합이 박제되는 단골 지점주입의 관용 형태테스트 대체 수단
Java 클래스 내부 new, static 유틸 호출 인터페이스 + 생성자 주입, DI 컨테이너(Spring) mock 라이브러리(Mockito 등), 손수 만든 fake
JS·TS 모듈 최상단 import한 구현을 직접 호출 함수 인자/팩토리로 전달, Vue provide/inject, props 테스트 러너의 모듈 mock, 주입 지점에 가짜 전달
Python 모듈 전역에서 생성한 클라이언트 객체 기본값 있는 인자 주입(def f(sender=real)) — 덕 타이핑이라 인터페이스 선언 불필요 monkeypatch(런타임 치환), 인자로 가짜 전달
C++ 멤버로 구체 타입을 값 소유, 전역 싱글턴 추상 클래스 포인터/참조 주입, 템플릿 파라미터(정적 주입) 가상 함수 기반 mock, 템플릿에 가짜 타입 대입

7.1 Java — 컨테이너가 규율을 강제하는 지점, 순환 의존

Java 생태계의 관례는 생성자 주입을 표준으로 못 박는다. 이유는 3절의 원칙(불완전한 상태를 원천 봉쇄) 그대로지만, Spring 같은 DI 컨테이너에서는 그 원칙이 실행 가능한 규칙으로 바뀐다 — 생성자 주입만 쓰면 순환 의존이 컨테이너 기동 시점에 예외로 드러난다. 

@Service
class OrderService {
    private final PaymentService paymentService;
    OrderService(PaymentService paymentService) {   // 생성자 주입
        this.paymentService = paymentService;
    }
}

@Service
class PaymentService {
    private final OrderService orderService;
    PaymentService(OrderService orderService) {      // 서로가 서로의 생성자에서 필요
        this.orderService = orderService;
    }
}
// 컨테이너 기동 시:
// BeanCurrentlyInCreationException: ...OrderService...PaymentService...
// → 완전히 조립되기 전에는 존재할 수 없는 생성자 주입 특성상, 순환은 원천적으로 조립 불가

같은 순환을 필드 주입(@Autowired 필드)으로 바꾸면 예외 없이 "성공"한다 — 컨테이너가 빈(bean, 컨테이너가 생성·관리하는 객체)을 일단 속이 빈 껍데기 상태로 먼저 등록해 두고, 두 빈이 모두 만들어진 뒤에 필드를 나중에 채워 넣기 때문이다. 조립이 통과했다는 사실이 설계가 건강하다는 뜻은 아니다 — 두 클래스가 서로 없이는 존재할 수 없다는 결합 문제는 그대로 남아 있고, 필드 주입은 그 증상을 감췄을 뿐이다.

Java 관점의 통찰: Spring이 생성자 주입에서 순환을 예외로 막는 것은 프레임워크가 베푸는 친절이 아니라, DI라는 기법 자체가 요구하는 규율 — "완전히 조립된 뒤에만 객체가 존재해야 한다" — 을 컨테이너가 코드 대신 강제하는 것뿐이다. 필드 주입으로 우회해 순환을 통과시키면 컨테이너의 경고는 사라지지만 설계 결함은 사라지지 않는다. "DI는 기법, 컨테이너는 도구"라는 5절의 원칙이 여기서 다시 확인된다 — 도구가 강제하지 않는 순간, 규율을 지키는 몫은 사람에게 돌아간다.

7.2 JS·TS — 모듈 시스템 자체가 주입 통로인 언어

JS·TS에서는 클래스의 생성자 없이도 "갈아 끼울 자리"가 이미 하나 더 있다 — import 문 자체다. 모듈은 런타임의 모듈 레지스트리(불러온 모듈을 경로별로 캐싱해 두는 내부 표)에 한 번 로드되어 캐싱되는데, 테스트 러너는 이 레지스트리를 코드 실행 전에 가로채 특정 경로의 모듈을 통째로 가짜로 바꿔치기할 수 있다. OrderService의 시그니처를 전혀 바꾸지 않고도 대역을 끼워 넣을 수 있는 이유다. 

// emailSender.js
export function sendEmail(to, msg) { /* 실제 발송 */ }

// orderService.js — 여전히 import를 직접 호출한다
import { sendEmail } from './emailSender.js';
export function completeOrder(order) {
    sendEmail(order.email, '주문이 완료되었습니다');
}

// orderService.test.js (Vitest 예시)
import { vi, test, expect } from 'vitest';
vi.mock('./emailSender.js', () => ({ sendEmail: vi.fn() }));  // 모듈 레지스트리 자체를 치환

import { sendEmail } from './emailSender.js';
import { completeOrder } from './orderService.js';

test('주문 완료 시 이메일 발송을 요청한다', () => {
    completeOrder({ email: 'buyer@example.com' });
    expect(sendEmail).toHaveBeenCalledWith('buyer@example.com', expect.any(String));
});

그러나 이 통로는 공짜가 아니다. 모듈 모킹은 파일 하나의 import 경로 전체를 치환하는 것이라 같은 프로세스 안에서 인스턴스마다 다른 구현을 동시에 꽂을 수 없고, completeOrder(order)라는 함수 시그니처만 읽어서는 이 함수가 이메일 발송에 의존한다는 사실을 알 방법이 없다 — 1절에서 본 "숨은 의존성"이 클래스 대신 모듈 그래프 수준에서 재현된 것이다. 그래서 여러 알림 채널을 한 서비스에 동시에 주입해야 하거나, 다른 실행 환경(서버·엣지·테스트)마다 다른 구현을 갈아 끼워야 하는 경계에는 함수 인자·팩토리로 넘기는 명시적 주입이 여전히 필요하다.

JS·TS 관점의 통찰: 모듈 임포트 자체가 갈아 끼울 수 있는 자리라는 점에서 JS·TS는 클래스 기반 언어 없이도 이미 구조적으로 DI에 우호적이다. 하지만 이 자리는 시그니처가 아니라 파일 시스템 경로에 뚫려 있는 자리다 — 편리함의 대가로 의존성이 코드의 계약이 아니라 import 목록에만 적혀 있게 된다. 테스트 편의를 위한 대체는 모듈 모킹으로, 여러 구현이 공존해야 하는 설계상의 경계는 명시적 인자 주입으로 — 목적에 따라 통로를 가려 쓰는 것이 이 언어의 균형점이다.

7.3 Python — 형식 비용이 가장 낮은 대신, 함정도 내장된 언어

Python은 덕 타이핑(duck typing — 선언된 타입이 아니라 "필요한 메서드를 실제로 가졌는가"로 호환을 판정하는 방식) 덕에 인터페이스 선언 없이도 아무 객체나 주입할 수 있다 — DI의 형식 비용이 가장 낮은 언어다. 관용 형태는 기본값 있는 인자 주입이다. 

class FakeSender:                          # 인터페이스 선언 없이 메서드만 맞추면 호환
    def __init__(self): self.sent = []
    def send(self, to, msg): self.sent.append(to)

def complete_order(order, sender=None):
    sender = sender or EmailSender()       # 호출 시점 생성 — 아래 함정의 회피 관용구
    ...
    sender.send(order.email, "주문이 완료되었습니다")

complete_order(order, sender=FakeSender())   # 테스트: 키워드로 가짜 주입

그런데 파이썬에는 파라미터 자리를 거치지 않고도 대역을 끼우는 두 번째 길이 있다 — monkeypatch(테스트 중 클래스·모듈·인스턴스의 속성을 런타임에 임시로 다시 바인딩하는 기법)다. 이것이 가능한 이유는 파이썬의 객체 모델에 있다: 클래스·모듈·인스턴스는 모두 이름과 값을 매핑하는 네임스페이스(속성 사전)를 갖고, 속성 조회는 그때그때 이 사전을 찾아보는 런타임 동작이다. 그래서 실행 도중 EmailSender.send = fake_send처럼 이름을 다시 연결하면, 그 이름을 참조하는 모든 코드가 다음 호출부터 즉시 영향을 받는다 — 코드에 주입받을 자리(파라미터)가 전혀 없어도 이런 치환이 성립한다는 뜻이다.

Python 관점의 통찰: 덕 타이핑은 "타입을 선언하지 않아도 되는 주입"이고 monkeypatch는 "자리가 없어도 되는 주입"이다 — 둘 다 형식 비용을 없애 주지만 성격은 다르다. 명시적 인자 주입은 코드에 새겨진 계약이라 읽는 사람이 알 수 있지만, monkeypatch는 이름 재바인딩이 실행 시점에만 일어나므로 변경 범위가 그 함수가 아니라 프로세스 전역이고, 테스트가 끝난 뒤 되돌리지 못하면 다른 테스트가 오염된다. sender=EmailSender()처럼 기본값 자리에서 직접 생성하면 안 되는 이유도 같은 뿌리다 — 기본값은 함수 정의(모듈 로드) 시점에 단 한 번 평가되므로 진짜 구현이 import만으로 실체화되고 모든 호출이 그 한 객체를 공유하게 된다. 주입받을 자리를 낼 수 있는 곳에는 명시적 인자를, monkeypatch는 그 자리조차 낼 수 없는 외부 라이브러리·전역 상태를 다룰 때의 최후 수단으로 남겨 두는 편이 안전하다.

7.4 C++ — 주입이 수명·소유권 설계와 결부되는 언어

C++에서 협력자를 구체 타입의 값 멤버로 소유하는 것은 Java의 내부 new와 같은 박제다. 주입의 관용 형태는 두 갈래다: 가상 함수 기반 주입(추상 클래스 참조/포인터로 받아 런타임에 갈아 끼움)과 템플릿 파라미터 주입(갈아 끼울 타입 자체를 컴파일 타임에 끼워 넣는 정적 DI). 

// ① 런타임 주입 — 추상 클래스 참조로 받는다. 소유하지 않고 "빌려" 쓴다
struct NotificationSender {
    virtual void send(const std::string& to, const std::string& msg) = 0;
    virtual ~NotificationSender() = default;
};

class OrderService {
    NotificationSender& sender_;              // 참조 = 빌림. 서비스보다 먼저 죽으면 안 됨
public:
    explicit OrderService(NotificationSender& s) : sender_(s) {}
};

// ② 컴파일 타임 주입 — 테스트에서는 OrderServiceT<FakeSender>로 대체
template <typename Sender>
class OrderServiceT {
    Sender sender_;
public:
    void complete_order(const Order& o) { sender_.send(o.email(), "완료"); }
};

①에서 참조로 받는다는 선택 자체가 소유권 결정이다 — OrderService는 NotificationSender의 수명을 책임지지 않으므로, 주입한 쪽이 그 객체를 서비스보다 오래 살려 둬야 한다는 계약이 코드 밖에 암묵적으로 생긴다. 그 계약을 코드 안으로 끌어오고 싶다면 참조 대신 std::unique_ptr<NotificationSender>를 생성자로 받아 소유권 자체를 서비스로 옮길 수도 있다 — 다만 이번엔 서비스가 그 대역의 수명까지 떠안는다는 새로운 책임이 생긴다. "누가 무엇을 얼마나 오래 갖고 있는가"가 주입 방식 선택에서 빠질 수 없는 이유다.

C++ 관점의 통찰: ①은 가상 호출(어느 구현의 함수를 부를지 런타임에 결정하는 메커니즘) 비용을 치르는 대신 mock 프레임워크와 호환되고, ②는 그 비용이 0인 대신 조합이 컴파일 타임에 굳는다 — 성능 민감 코드가 ②를 선호하는 이유다. 그리고 다른 세 언어와 달리 C++의 DI는 "무엇을 주입할지"뿐 아니라 "누가 그것을 소유하고 언제 해제할지"까지 매번 함께 결정해야 하는 설계다. 참조·포인터로 빌려 쓸지, 스마트 포인터로 소유권을 넘길지는 취향이 아니라 수명 계약의 문제이며, 이 결정을 생략하면 댕글링 참조(가리키는 대상이 이미 소멸한 참조)라는 런타임 함정으로 되돌아온다.

8. 함께 알면 좋은 것

본문 각 절을 한 걸음씩 확장하는 어휘들이다 — 첫째는 2절의 원리 층위, 둘째는 4절의 대역 어휘, 셋째는 5절의 조립 위치, 넷째는 6-②에서 스친 비결정 요소, 다섯째는 1절의 "숨은 의존성"을 반대편에서 비추는 상대역이다.

  • 의존성 역전 원칙(DIP, Dependency Inversion Principle) — "구체가 아니라 추상에 의존하라"는 설계 원칙. DI는 그 원칙을 실현하는 기법이다 — 이름이 비슷해 자주 혼동되는 짝.
  • 테스트 더블의 분류 — 이 문서의 fake·mock 외에도 stub, spy 등 목적별 대역의 어휘가 있다. 대역을 "무엇을 검증하려고 쓰는가"로 구분하는 눈이 mock 남용(6-③)의 예방주사가 된다.
  • 합성 루트(composition root) — 조립 코드를 애플리케이션 진입점 한 곳에 모으는 패턴. "생성과 조립은 한 곳에, 사용은 어디서나"라는 DI 구조의 완성형.
  • 시간·난수의 주입 — now()·랜덤을 직접 호출하는 코드는 비결정적이라 테스트가 흔들린다. 시계(clock)와 난수원을 주입 대상으로 삼는 것은 DI의 대표적 응용.
  • 서비스 로케이터(service locator)와의 대비 — 필요한 것을 "전역 등록소에서 꺼내 쓰는" 방식은 DI와 비슷해 보이지만 의존성이 시그니처에서 사라진다(숨은 의존성). DI가 선호되는 이유를 대조로 이해하기 좋은 상대역.

9. 한 장 요약

  • DI = 만들지 말고 받아라. 내부 new는 구현체와의 영구 결합 선언이고, 주입은 갈아 끼울 수 있는 틈을 만든다.
  • 그 틈으로 테스트가 들어온다: 진짜 대신 가짜(mock/fake)를 주입 → 외부 세계 없이, 빠르고 결정적으로, 내 로직만 검증.
  • 방식은 필수 의존성 = 생성자 주입(불변·시그니처 공개·불완전 상태 원천 봉쇄), 선택적 의존성 = setter 주입. 필드 주입은 테스트 통로가 없어 지양.
  • DI는 기법, 컨테이너(Spring 등)는 조립 자동화 도구 — 순서를 뒤집지 말 것. 프론트의 props·provide/inject도 같은 원리의 다른 표현.
  • 주입 대상은 경계의 협력자(외부 통신·저장소·시간·난수)부터. 전부 주입은 과잉, mock 과다는 구현 결합 테스트.
  • 테스트하기 어렵다 = 결합이 높다는 실측 신호. 생성자가 비대해지면 DI 탓이 아니라 책임 과다의 경고등으로 읽는다.

I11 계층을 관통하는 계약 변경·시그니처 파급

0. 한눈에 보는 결론

  • "필드 하나 추가했을 뿐인데 파일 10개를 고쳤다" — 이 현상의 원인은 각 계층의 인터페이스(시그니처·타입)가 서로의 계약(contract)이고, 그 계약이 사슬처럼 이어져 있기 때문이다.
  • 파급은 두 갈래로 온다: 데이터 형태의 파급(DTO·타입 정의가 바뀜)과 시그니처의 파급(메서드 파라미터 목록이 바뀜). 후자가 훨씬 아프다 — 호출부 전체가 깨지기 때문이다.
  • 파급을 0으로 만들 수는 없다. 새 데이터가 화면까지 흘러야 한다면 각 계층이 그 데이터를 운반은 해야 한다. 목표는 "운반 경로는 유지하되, 깨지는 지점을 줄이는 것"이다.
  • 대표 처방 두 가지: ① 값을 낱개로 나열하지 말고 파라미터 객체(parameter object)로 묶어 시그니처를 안정화한다. ② 계층 경계마다 경계 DTO(Data Transfer Object)를 두어, 변경이 경계에서 흡수·변환되게 한다.
  • 단, DTO 분리는 공짜가 아니다 — 매핑 코드라는 비용을 지불한다. 변경 이유가 다른 경계에만 분리를 적용하는 것이 실무 감각이다.
  • 계약 변경에도 안전한 방향이 있다: 선택(optional) 필드 추가는 하위 호환, 필드 삭제·이름 변경·타입 변경은 파괴적 변경이다.

1. 시나리오 — 주문에 "배송 메모" 필드 하나를 추가한다면

쇼핑몰 주문 기능에 deliveryMemo(배송 메모) 필드 하나를 추가하는 요구가 들어왔다고 하자. 전형적인 웹 애플리케이션(Vue 프론트엔드 + Java 백엔드 + RDB)에서 이 값이 화면 입력부터 DB 저장까지 흘러가려면, 다음 지점들이 모두 그 값을 알아야 한다.

[Vue 컴포넌트 폼] → [프론트 API 함수·타입 정의] → (HTTP) → [Controller 요청 DTO] → [Service 메서드] → [Repository/DAO] → [Entity·SQL 컬럼] ··· 그리고 응답 방향으로 같은 사슬을 역순으로 한 번 더

필드 "하나"의 추가가 모든 계층의 인터페이스를 한 번씩 관통한다. 이것이 이 문서의 주제인 계약 변경의 파급(ripple)이다. 문제는 파급의 존재 자체가 아니라 — 데이터가 흘러야 하니 어느 정도는 불가피하다 — 설계에 따라 "고쳐야 하는 파일 수"와 "컴파일이 깨지는 지점 수"가 몇 배씩 달라진다는 점이다.

2. 왜 파급되는가 — 시그니처는 계층 간 "계약"이다

1절의 flow에서 계층을 잇는 화살표(→) 하나하나는 단순한 호출선이 아니라 약속의 연결선이다. 메서드 시그니처, DTO의 필드 목록, API의 요청/응답 스키마는 모두 계약(contract)이다. 호출하는 쪽은 "이 이름으로, 이 타입의 값들을, 이 순서로 주면 된다"는 약속을 믿고 코드를 작성한다. 계약이 바뀌면 그 계약을 믿던 모든 코드가 영향을 받는다 — 이것이 I1에서 다룬 결합(coupling)의 한 형태인 계약 결합이다.

2.1 파급의 두 갈래 — 형태의 파급 vs 시그니처의 파급

구분무엇이 바뀌나깨지는 범위체감
데이터 형태의 파급 DTO·타입 정의에 필드가 추가/삭제됨 그 필드를 실제로 읽고 쓰는 코드만 비교적 온화 — 필드를 안 쓰는 코드는 무사하다
시그니처의 파급 메서드의 파라미터 목록 자체가 바뀜
create(a, b) → create(a, b, c)		 그 메서드의 모든 호출부 + 모든 구현체 + 모든 테스트 고통 — 값에 관심 없는 호출부까지 전부 수정

같은 "필드 하나 추가"라도 어느 갈래로 흐르게 설계했는지에 따라 비용이 갈린다. 핵심 통찰: 객체(형태)에 필드를 더하는 것은 국소적이지만, 시그니처에 파라미터를 더하는 것은 전역적이다. 따라서 전략의 큰 방향은 "변경을 시그니처의 파급에서 형태의 파급으로 옮기는 것"이 된다.

한 줄 정리: 파라미터 목록은 "깨지기 쉬운 계약", 객체의 필드 목록은 "늘어나도 덜 깨지는 계약"이다. 파급을 관리한다는 것은 변경이 후자를 타고 흐르도록 물길을 파는 일이다.

3. 파급을 키우는 대표 안티패턴

2절의 결론이 "변경이 형태의 파급을 타도록 물길을 파는 것"이었다면, 이 절의 셋은 그 반대로 파는 물길들이다 — 앞의 둘(3.1·3.2)은 변경을 시그니처 파급·전 계층 파급으로 흘려보내고, 마지막 하나(3.3)는 파급의 예측 자체를 불가능하게 만든다. 각각 4절의 처방과 짝을 이루므로, 어떤 처방이 어떤 병을 겨냥하는지 대응시키며 읽자.

3.1 파라미터 나열형 시그니처

// 값이 늘 때마다 시그니처가 깨진다 — 모든 계층에서, 모든 호출부가
OrderResult createOrder(Long userId, List<Long> itemIds,
                        String address, String paymentType);
// 배송 메모 추가 → createOrder(..., String deliveryMemo)
// → Controller·Service·인터페이스·구현체·테스트의 호출/정의 전부 수정

파라미터가 낱개로 나열되어 있으면 필드 추가 = 시그니처 파괴가 된다. 게다가 같은 타입의 파라미터가 늘어날수록(String, String, String…) 순서 실수로 인한 버그 위험도 함께 커진다.

3.2 하나의 타입을 전 계층이 공유 — "Entity 직행"

반대 극단은 DB 엔티티(entity) 하나를 Repository부터 API 응답, 심지어 프론트 타입까지 그대로 공유하는 구조다. 당장은 매핑 코드가 없어 편하지만, 모든 계층이 하나의 계약에 결합된 상태가 된다.

  • DB 컬럼 하나를 바꾸면 → API 응답 포맷이 바뀌고 → 프론트가 깨진다. 내부 사정이 외부 계약을 흔드는 역전이 일어난다.
  • 화면에 보여선 안 되는 내부 필드(원가, 관리용 플래그 등)가 응답에 그대로 노출될 위험이 생긴다.
  • 화면 요구("이 두 값을 합쳐서 보여줘")가 역으로 DB 모델을 오염시키기 시작한다.

3.3 계층 건너뛰기

Controller가 Repository를 직접 호출하는 식으로 계층을 건너뛰면, 당장은 코드가 줄지만 계약의 소비자가 예상 밖의 위치에 숨는다. 나중에 Repository 시그니처를 바꿀 때 "Service만 보면 되겠지"라는 가정이 무너지며, 파급 범위를 예측할 수 없게 된다. 파급은 크기보다 예측 불가능성이 더 위험하다 — 놓친 한 곳이 런타임 장애가 된다.

4. 파급 최소화 전략

이제 처방이다. 4.1은 3.1(파라미터 나열)의, 4.2는 3.2(한 타입의 전 계층 공유)의 해독제이고, 4.3은 두 처방으로도 피할 수 없는 순간 — 계약 자체를 바꿔야 할 때 — 를 위한 마지막 층위다. 3.3(계층 건너뛰기)의 처방은 별도 기법이 아니라 "경계를 우회하지 않는 규율" 그 자체이므로, 4.2의 경계 논의에 녹아 있다.

4.1 파라미터 객체 — 시그니처를 안정화한다

// 요청을 하나의 객체로 묶는다
public class CreateOrderRequest {
    private Long userId;
    private List<Long> itemIds;
    private String address;
    private String paymentType;
    private String deliveryMemo;   // ← 추가는 여기 한 줄
}

OrderResult createOrder(CreateOrderRequest request);  // 시그니처 불변

필드 추가가 객체 내부의 변경으로 국소화되고, 시그니처는 그대로다. 값을 실제로 사용하는 지점(폼 바인딩, INSERT 구문)만 고치면 되고, 단순히 값을 운반만 하던 중간 계층은 손대지 않아도 된다. 변경이 3.1의 "시그니처 파급"에서 2.1의 "형태 파급"으로 옮겨진 것이다.

4.2 경계 DTO — 변경을 경계에서 흡수한다

파라미터 객체가 시그니처를 지킨다면, 경계 DTO는 계층 간 계약을 분리한다. "바뀌는 이유가 다른" 경계 — 대표적으로 외부 공개 API ↔ 내부 구현, 도메인 모델 ↔ 영속성 모델 — 마다 그 경계 전용의 데이터 타입을 두고, 경계에서 변환한다.

[API 요청/응답 DTO] ←변환→ [도메인 객체] ←변환→ [Entity/테이블] (외부 계약) (비즈니스 규칙) (저장 구조) 각 구간은 자기 이유로만 변한다. 변환 지점이 "충격 흡수대" 역할.
  • DB 컬럼명이 바뀌어도 API 응답은 그대로 — 변환 코드 한 곳만 고친다.
  • 화면 전용 가공(두 필드 합치기, 포맷팅)은 응답 DTO에서 끝낸다. 도메인·DB가 화면 사정에 오염되지 않는다.
  • 노출하면 안 되는 필드는 응답 DTO에 아예 존재하지 않으므로, 실수로 새어 나갈 경로가 없다.

실전 감각 — 어디에 경계를 둘 것인가: 모든 계층 사이에 DTO를 두는 것이 아니라, "변경 이유가 다른 곳"과 "내가 통제할 수 없는 소비자가 있는 곳"에 둔다. 외부에 공개된 API는 프론트(또는 타 팀)가 소비하므로 반드시 전용 DTO를 둘 가치가 있다. 반면 같은 모듈 안에서 항상 함께 배포·수정되는 두 클래스 사이라면, DTO 분리는 비용만 낳는 과잉일 수 있다 — 함께 변하는 것은 경계 안에 둔다는 I1의 원칙 그대로다.

4.3 하위 호환 변경 — 계약을 "깨지 않고" 바꾸는 법

경계를 나눠도 계약 자체를 바꿔야 할 때는 온다. 이때 변경에는 안전한 방향과 파괴적인 방향이 있다.

변경 유형하위 호환(backward compatibility)이유
선택(optional) 필드 추가 대체로 안전 기존 소비자는 모르는 필드를 무시하면 된다
필수(required) 필드 추가 파괴적 기존 요청이 전부 유효성 검사에서 탈락
필드 삭제·이름 변경 파괴적 그 필드를 읽던 소비자가 즉시 깨짐
필드 타입·의미 변경 가장 위험 구조는 그대로라 컴파일·파싱은 통과하는데 동작이 조용히 틀어진다

그래서 실무의 계약 진화는 "추가는 optional로, 삭제는 단계적으로(새 필드 추가 → 소비자 이전 → 구 필드 제거)"라는 리듬을 탄다. 프론트와 백엔드가 동시에 배포되지 않는다는 사실을 기억하면 이 규칙의 이유가 자명해진다 — 배포 사이의 시간 동안 구버전 소비자와 신버전 제공자가 공존한다.

5. 흔히 헷갈리는 지점

4절의 처방들은 각각 남용하면 새로운 병이 된다 — ①은 4.2의, ③은 4.1의 과용이 만드는 그림자이고, ②·④는 4.3의 "추가는 안전" 규칙이 성립하는 조건을 짚는다.

① "계층마다 DTO를 두면 무조건 좋다"? — 아니다. DTO 하나당 변환 코드와 "필드 추가 시 고칠 파일 +1"이 따라온다. 변경 이유가 같은 두 계층 사이의 DTO 분리는 파급을 줄이는 게 아니라 복제하는 것이다. 분리는 변경 이유가 갈라지는 경계에만.

② "필드 추가는 항상 안전하다"? — 조건부다. 역직렬화가 미지의 필드를 거부하도록 설정된 소비자(strict 모드), 필드를 필수로 선언한 프론트 타입, "모든 필드를 검증"하는 계약 테스트가 있으면 추가만으로도 깨진다. "추가는 안전"은 소비자가 관대(tolerant)할 때만 성립하는 약속이다.

③ 파라미터 객체의 부작용 — 만능 가방 — 시그니처를 지키려고 모든 값을 하나의 거대 객체에 계속 욱여넣으면, "무엇이 실제로 필요한지"가 시그니처에서 사라진다. 어떤 필드가 채워져 오는지 아무도 모르는 객체는 계약이 아니라 안개다. 요청 객체는 유스케이스 단위로 두는 것이 균형점이다.

④ "컴파일 에러가 안 나면 파급이 없다"? — 위험한 착각. 동적 바인딩 구간(JSON 키, 폼 필드명, SQL 컬럼명, JS의 비타입 코드)에서는 계약 위반이 컴파일 타임에 안 잡히고 런타임의 undefined·null·누락 데이터로 나타난다. 정적 타입이 끊기는 지점이 곧 파급 추적이 끊기는 지점이므로, 그 경계에 검증(스키마 검사·계약 테스트)을 세워야 한다.

★ 6. 언어별 대조

5절 ④에서 본 것처럼, 정적 타입이 끊기는 경계에서 계약 위반은 컴파일 에러가 아니라 런타임의 undefined·예외로 나타난다. 이 "발각 시점의 차이"를 4언어 각각에서 따라가 보면, 2절에서 나눈 형태의 파급과 시그니처의 파급이라는 두 갈래는 그대로지만 그 파급을 누가, 언제 잡아내는가는 언어의 타입 시스템과 실행 모델에 따라 전혀 다른 그림이 된다.

언어계약 위반이 드러나는 시점시그니처 파급이 아픈 지점파급을 줄이는 대표 도구
Java 컴파일 타임(강함) — 단, 재컴파일 안 된 옛 바이트코드가 섞이면 실행 시점 인터페이스 변경 → 모든 구현체·호출부·mock 동시 파손 요청/응답 객체, 빌더(builder), 리팩토링 도구의 시그니처 변경 기능
JS·TS TS는 컴파일 타임(단, 타입 검사가 못 보는 경계에서는 소실), JS는 런타임(undefined) API 응답 타입 변경 → 컴포넌트 props 사슬로 전파 interface+선택 필드 ?, 객체 인자 패턴, 런타임 스키마 검증
Python 인터프리터 자체는 검사하지 않음 — 실행되는 순간에야, 그것도 정적 검사기를 돌려야 부분적으로 앞당겨짐 위치 인자 순서 변경이 개수는 맞아 조용히 값을 뒤바꿈 키워드 전용 인자(*), dataclass, 타입 힌트+정적 검사기
C++ 소스 컴파일 타임 + 바이너리 경계는 링크/런타임 헤더의 시그니처·구조체 변경 → 광범위 재컴파일, ABI(바이너리 호환) 파손 구조체 인자, Pimpl, 바이너리 경계에서는 버전 필드·불투명 포인터

6.1 Java — 파급이 컴파일 에러 목록으로 즉시 드러나는 언어

Java의 정적 타입 검사와 분리 컴파일 모델이 만나면, 시그니처 변경의 파급은 눈에 안 보이는 위험이 아니라 컴파일러가 나열해 주는 목록이 된다. 인터페이스의 메서드 하나에 파라미터를 추가하면, 그 인터페이스를 구현하는 모든 클래스와 호출하는 모든 지점, 심지어 테스트의 mock 설정까지 한 번에 컴파일이 깨진다. 

// 인터페이스는 계약 — 파라미터 하나만 늘려도 사슬 전체가 컴파일 에러로 드러난다
public interface OrderRepository {
    OrderResult save(Order order, String deliveryMemo);   // 추가된 파라미터
}

// → 이 인터페이스를 구현하는 모든 클래스가 컴파일 실패
class JpaOrderRepository implements OrderRepository {
    // save(Order, String)를 구현하지 않음 → "메서드를 오버라이드하지 않았습니다" 에러
}

// → 이 인터페이스를 호출하는 모든 지점, 모든 mock이 함께 실패
repository.save(order);          // 컴파일 에러: 인자 개수 불일치
Mockito.when(repository.save(order)).thenReturn(result);  // 동일하게 실패

이 즉시성에는 예외가 하나 있다. 여러 모듈이 독립적으로 빌드·배포되는 구조에서 한 모듈만 새 인터페이스로 재컴파일하고, 다른 모듈이 옛 바이트코드(.class·.jar)를 그대로 참조하면, 파급을 잡아내는 주체가 컴파일러에서 클래스 로더로 넘어간다. 이때는 컴파일 에러가 아니라 실행 중 NoSuchMethodError·AbstractMethodError로 터진다 — 컴파일 타임 안전은 "모두 함께 재컴파일한다"는 전제 위에서만 성립하는 약속이다.

Java 관점의 통찰: 컴파일러가 파급 지점을 하나도 빠짐없이 나열해 준다는 것은, 그 목록을 사람이 손으로 따라가지 않고 도구에 맡길 수 있다는 뜻이기도 하다. IDE의 "메서드 시그니처 변경(Change Signature)"·"사용처 찾기(Find Usages)" 리팩토링이 자바 생태계에서 표준 관행으로 자리 잡은 이유가 여기 있다 — 컴파일러가 이미 알고 있는 파급 목록을 도구가 대신 순회하며 고쳐 주는 것뿐이므로, 사람이 놓칠 여지가 구조적으로 작다.

6.2 JS·TS — 컴파일 타임을 되찾지만 경계에서 다시 놓치는 언어

TS는 구조적 타이핑(structural typing — 타입 이름이 아니라 멤버 구성이 같으면 호환으로 판정하는 방식)으로 interface의 필드·시그니처 변경을 컴파일 타임에 추적한다는 점에서, 1절 시나리오의 프론트 쪽에 Java에 가까운 즉시성을 되돌려준다. 문제는 이 추적이 타입 검사기가 실제로 보는 범위 안에서만 유효하다는 것이다. 

interface CreateOrderRequest {
  userId: number;
  itemIds: number[];
  address: string;
  deliveryMemo?: string;   // 선택 필드 추가 — 기존 호출부는 무파괴
}

function createOrder(req: CreateOrderRequest) { /* ... */ }
createOrder({ userId: 1, itemIds: [1, 2], address: "..." });  // 컴파일 통과

// 하지만 서버 응답은 "타입"이 아니라 값이다 — 컴파일러는 이 경계를 보지 못한다
const res = await fetch("/api/orders").then(r => r.json()) as CreateOrderRequest;
console.log(res.deliveryMemo.length);  // 타입은 string이라 믿지만 실제론 undefined일 수 있다
                                        // → 컴파일은 통과, 런타임에 TypeError

네트워크로 값이 오가는 순간 타입 정보는 소거되고, as CreateOrderRequest는 검증이 아니라 선언일 뿐이다. 이런 "타입 정보가 소거된 채로 값이 오가는 경계"는 원격 호출·리플렉션 상황에서 더 근본적인 형태로 나타나는데, 그 지점은 C21 원격·리플렉션 경계의 메서드 오버로딩에서 다룬다.

JS·TS 관점의 통찰: TS가 되찾아 준 컴파일 타임 안전은 "이 값이 어디서 왔는지도 타입 검사기가 지켜봤는가"라는 조건이 붙은 안전이다. 자체 코드 안에서 만들어지고 소비되는 값에는 Java에 준하는 즉시성이 작동하지만, 직렬화·역직렬화나 리플렉션처럼 값이 타입 검사기의 시야 밖에서 재구성되는 경계를 넘는 순간 그 보장은 다시 "믿음"으로 되돌아간다.

6.3 Python — 파급이 인터프리터가 아니라 실행 그 자체로 드러나는 언어

Python 인터프리터는 함수를 호출할 때 인자의 개수와 이름만 맞춰 볼 뿐, 그 값이 의미상 올바른 자리에 있는지는 관심이 없다. 그래서 위치 인자 순서를 바꾸는 시그니처 변경은 에러 없이 조용히 값을 뒤바꿔 전달하는 사고로 이어지기 쉽다 — 파급이 존재하지 않는 게 아니라, 그 호출 경로가 실제로 실행될 때까지 숨어 있을 뿐이다. 

# 위치 인자 계약: 인터프리터는 개수만 확인할 뿐 순서의 의미는 신경 쓰지 않는다
def create_order(user_id, item_ids, address):
    ...

create_order(1001, address, item_ids)   # 인자 개수는 맞으니 인터프리터는 통과시킨다
                                         # address와 item_ids가 뒤바뀐 채로 실행된다

# 타입 힌트는 인터프리터가 아니라 별도의 정적 검사기가 읽는 "주석"이다
def create_order(user_id: int, item_ids: list[int], address: str) -> None:
    ...
# mypy·pyright 같은 검사기를 CI에 연결해야만 위와 같은 순서 실수가 실행 전에 잡힌다
# 검사기 없이 그냥 실행하면 힌트는 아무것도 막지 않는다

이 취약함을 시그니처 문법 자체로 막는 것이 키워드 전용 인자(함수 정의에서 * 뒤에 오는 인자 — 호출 시 반드시 이름을 붙여야 함)와 기본값이다. dataclass(필드 선언만으로 생성자·비교 메서드 등을 만들어 주는 표준 데코레이터)로 인자를 객체 하나로 묶으면 4.1의 파라미터 객체가 그대로 파이썬 관용형이 되고, 새 필드에 기본값을 주는 것은 4.3의 하위 호환 변경과 정확히 같은 문법이 된다.

Python 관점의 통찰: 인터프리터·객체 모델 수준에서 보면 Python의 함수 호출은 "이름과 개수가 맞는 인자 뭉치를 넘긴다"는 것 이상을 검사하지 않는다. 타입 힌트는 이 간극을 메우려는 장치이지만 어디까지나 선택적 주석이라, 정적 검사기를 파이프라인에 실제로 연결해야만 컴파일 타임에 가까운 발각이 회복된다 — 힌트를 적는 것과 그것을 강제하는 도구를 돌리는 것은 별개의 결정이라는 점이 Java의 "컴파일러가 곧 강제자"인 구조와 가장 다른 지점이다.

6.4 C++ — 계약이 소스와 바이너리, 두 겹인 언어

C++의 시그니처 변경은 다른 언어보다 한 겹 더 깊이 파급된다. 첫 겹은 소스 계약이다: 헤더에 선언된 시그니처·구조체가 바뀌면 그 헤더를 포함하는 모든 번역 단위가 재컴파일 대상이 된다 — 파급이 "고칠 파일 수"만이 아니라 빌드 시간으로도 청구되는 언어다. 둘째 겹이 ABI(Application Binary Interface — 컴파일이 끝난 바이너리끼리 함수를 찾고 인자를 주고받는 방식의 약속)다. 소스 수준에서는 하위 호환인 변경(구조체 끝에 필드 추가)조차 구조체의 크기와 메모리 배치를 바꾸므로, 재컴파일되지 않은 바이너리(공유 라이브러리·플러그인)와의 경계에서는 계약 위반이 된다. 

// 경계 헤더 — 이 구조체가 곧 계약이다
struct CreateOrderRequest {
    long userId;
    int  itemCount;
    // char deliveryMemo[128];   // ← 필드 추가: "형태의 파급"이라 소스는 호환이지만
};                               //    sizeof와 배치가 바뀌어 ABI 계약은 깨진다

OrderResult createOrder(const CreateOrderRequest& req);
// 재컴파일된 쪽은 새 배치로, 안 된 쪽은 옛 배치로 메모리를 해석
// → 컴파일·링크는 통과하고 런타임에 조용히 어긋난다: 가장 위험한 파급 형태

이 문제는 시그니처가 재컴파일 없이 배포될 때만 성립한다는 점이 핵심이다. 모든 소비자가 항상 같이 재컴파일된다면 ABI는 신경 쓸 필요가 없는 개념이지만, 공유 라이브러리나 플러그인처럼 제공자와 소비자가 서로 다른 일정으로 배포되는 순간 소스 수준의 하위 호환은 바이너리 수준의 하위 호환을 보장하지 않는다.

C++ 관점의 통찰: 그래서 C++의 파급 방어는 "경계 뒤로 숨기기"로 수렴한다 — Pimpl(pointer to implementation, 구현 멤버들을 불투명 포인터 하나 뒤로 옮겨 헤더의 구조체 배치를 고정하는 기법)은 경계 DTO(4.2)의 "충격 흡수대"를 바이너리 수준에서 구현한 것이고, 배포 경계를 넘는 구조체에 버전·크기 필드를 두는 관례는 4.3의 하위 호환 진화를 메모리 배치의 세계로 옮긴 것이다.

7. 함께 알면 좋은 것

본문 처방들의 "제도화된 이름"들이다 — 앞의 셋은 4.3(하위 호환 진화)을, 넷째는 4.1(파라미터 객체)을, 다섯째는 4.2(경계를 어디에 둘 것인가)를 실무 어휘로 확장한다.

  • 관대한 소비자(Tolerant Reader) — "모르는 필드는 무시하고, 필요한 것만 읽는다"는 소비자 측 원칙. 제공자의 추가 변경을 무파급으로 만드는 짝꿍 규율.
  • 소비자 주도 계약 테스트(consumer-driven contract testing) — 프론트(소비자)가 기대하는 계약을 테스트로 명문화해, 백엔드 변경이 그 계약을 깨면 배포 전에 잡아내는 기법.
  • API 버저닝 — 파괴적 변경이 불가피할 때 구/신 계약을 병존시키는 공식 수단. "단계적 삭제" 리듬의 제도화.
  • 파라미터 객체 도입(Introduce Parameter Object) — 나열형 시그니처를 객체로 묶는 정식 리팩토링 카탈로그 항목. 테스트 보호망 아래 작은 단계로 수행한다.
  • 공개(published) 인터페이스 vs 내부 인터페이스 — 같은 "인터페이스"라도 통제 불가능한 외부 소비자가 있으면 변경 규율이 완전히 달라진다는 구분. 경계 DTO를 "어디에" 둘지의 판단 기준이 된다.

8. 한 장 요약

  • 시그니처·DTO·API 스키마는 모두 계층 간 계약이며, 계약의 사슬을 따라 변경이 파급된다.
  • 파급에는 두 갈래가 있다 — 형태의 파급(온화)과 시그니처의 파급(전 호출부 파손). 설계란 변경이 전자를 타게 만드는 일이다.
  • 처방 ①: 낱개 파라미터 대신 파라미터 객체 — 필드 추가를 객체 내부 변경으로 국소화.
  • 처방 ②: 변경 이유가 다른 경계에 경계 DTO — 변환 지점이 충격 흡수대가 된다. 단, 모든 계층에 남발하면 매핑 비용만 복제된다.
  • 계약 진화의 안전 문법: 추가는 optional로, 삭제·의미 변경은 단계적으로. 프론트와 백엔드는 동시에 배포되지 않는다.
  • 정적 타입이 끊기는 경계(JSON·폼·SQL)가 파급 추적이 끊기는 지점 — 그곳에 검증을 세운다.

I1 응집도와 결합도

0. 한눈에 보는 결론

  • 응집도(cohesion)는 모듈 내부 요소들이 하나의 목적을 위해 얼마나 뭉쳐 있는가, 결합도(coupling)는 모듈 사이가 서로 얼마나 얽혀 있는가를 나타낸다.
  • 목표는 언제나 높은 응집 · 낮은 결합. 이유는 단 하나 — 변경 파급(ripple effect)을 줄이기 위해서다.
  • 응집도가 높으면 "하나를 고칠 때 한 곳만" 고치면 되고, 결합도가 낮으면 "한 곳을 고쳐도 다른 곳이 안 깨진다".
  • 결합을 0으로 만들 수는 없다. 모듈은 협력해야 하므로, 결합의 개수가 아니라 결합의 성격(무엇에 의존하는가)을 관리하는 것이 핵심이다.
  • 모듈 경계는 "함께 변하는 것은 안으로, 따로 변하는 것은 밖으로"라는 기준으로 그린다.
  • 두 지표는 테스트 용이성과 직결된다: 응집도 높고 결합도 낮은 코드는 작은 단위로 떼어 검증하기 쉽다.

1. 두 개념은 "변경"에 대한 이야기다

응집도와 결합도는 코드의 미적 기준이 아니라, 소프트웨어가 계속 바뀐다는 전제에서 나온 실용적 지표다. 요구사항이 하나 바뀌었을 때 코드 몇 곳을 열어야 하는지, 그리고 한 곳을 고쳤을 때 몇 곳이 덩달아 깨지는지를 결정하는 것이 바로 이 두 성질이다.

[요구사항 변경 1건] │ ▼ 응집도 낮음 → 관련 로직이 여러 모듈에 흩어짐 → 여러 파일을 동시에 수정 결합도 높음 → 수정한 모듈에 얽힌 모듈들이 연쇄로 깨짐 → 파급 확산 │ ▼ 수정 비용 ↑, 버그 위험 ↑, 테스트 범위 ↑

1.1 응집도 — 모듈 안쪽을 보는 렌즈

응집도는 한 모듈(클래스, 파일, 패키지, 컴포넌트 등 경계가 있는 단위) 안의 요소들이 같은 이유로 존재하고 같은 이유로 변하는가를 묻는다. "주문 금액 계산"이라는 목적을 가진 모듈 안에 금액 계산 규칙만 들어 있다면 응집도가 높다. 그 안에 이메일 발송, 로그 포맷팅, 화면 문자열 조립까지 섞여 있다면, 서로 다른 이유로 변하는 코드가 한 몸이 된 것이므로 응집도가 낮다.

1.2 결합도 — 모듈 바깥쪽을 보는 렌즈

결합도는 모듈 A가 모듈 B에 대해 얼마나 많이, 얼마나 깊이 알고 있는가를 묻는다. A가 B의 공개 함수 시그니처만 알고 있다면 얕은 결합이다. A가 B의 내부 필드 구조, 호출 순서 규칙, 전역 상태까지 알아야 동작한다면 깊은 결합이며, B의 내부를 조금만 바꿔도 A가 깨진다.

한 줄 정리: 응집도는 "이 모듈이 하나의 변경 이유를 갖는가", 결합도는 "이 모듈의 변경이 다른 모듈로 새어 나가는가"다. 둘 다 변경을 기준으로 읽으면 헷갈리지 않는다.

2. 응집도의 스펙트럼

전통적 분류(구조적 설계 시대의 7단계)를 전부 외울 필요는 없다. 입문 단계에서는 아래 세 층위로 이해하면 충분하다.

수준특징예시
기능적 응집 (가장 좋음) 모든 요소가 하나의 잘 정의된 작업에 기여 "할인율 계산"만 담당하는 모듈 — 할인 정책이 바뀔 때만 수정된다
논리적/시간적 응집 (애매함) "비슷해 보여서" 또는 "같은 시점에 실행돼서" 묶임 utils 파일에 문자열·날짜·파일 처리 함수가 잡다하게 모임, "초기화 때 하는 일" 전부를 담은 모듈
우연적 응집 (가장 나쁨) 아무 관련 없는 것들이 한 모듈에 동거 파일이 커지자 임의로 반 잘라 만든 misc2 — 어떤 변경에도 열어봐야 하는 파일이 된다

판별 질문은 간단하다: "이 모듈을 한 문장으로, '그리고' 없이 설명할 수 있는가?" "주문 금액을 계산하고, 그리고 영수증 메일도 보내고, 그리고…"가 되면 응집도가 무너지고 있다는 신호다.

3. 결합도의 스펙트럼

결합도 역시 "무엇을 통해 의존하는가"에 따라 위험도가 달라진다. 아래로 갈수록 안전하다.

수준의존 대상위험
내용 결합 (최악) 상대 모듈의 내부 구현·비공개 데이터를 직접 조작 상대 내부가 바뀌면 즉시 파손. 캡슐화가 사실상 없음
공통(전역) 결합 여러 모듈이 공유 전역 상태를 읽고 씀 누가 언제 바꿨는지 추적 불가 → 조용한 실패의 온상
제어 결합 플래그 인자를 넘겨 상대의 내부 분기를 조종 호출자가 피호출자의 내부 로직을 알아야 함
데이터/메시지 결합 (양호) 필요한 값만 인자로 전달, 또는 공개 인터페이스로만 소통 계약(시그니처)만 유지되면 내부는 자유롭게 변경 가능

실전 감각: "낮은 결합"의 실체는 안정적인 것에 의존하기다. 자주 바뀌는 구현 세부가 아니라, 잘 바뀌지 않는 인터페이스·계약에 의존하도록 방향을 잡으면 결합의 해로움이 크게 줄어든다.

4. 모듈 경계 — 두 지표를 실제 설계로 옮기기

응집도와 결합도는 결국 경계를 어디에 긋는가의 문제다. 좋은 경계의 기준은 하나다:

함께 변하는 것은 경계 안에 모으고(응집↑), 따로 변하는 것은 경계 밖으로 분리한다(결합↓).

예를 들어 "결제 수수료 정책"과 "결제 화면 문구"는 바뀌는 이유와 시점이 다르다. 같은 파일에 있으면 문구 수정 커밋이 수수료 로직을 건드릴 위험을 만든다. 반대로 "수수료율 표"와 "수수료 계산식"은 항상 함께 바뀌므로 한 경계 안에 있어야 한다 — 이 둘을 갈라놓으면 오히려 수정 한 번에 두 모듈을 여는 낮은 응집이 된다.

즉 분리 자체가 미덕이 아니다. 잘못 그은 경계는 응집을 깨뜨리면서 결합만 늘린다. 관심사의 분리(separation of concerns)는 "관심사" 단위로 자를 때만 효과가 있다.

5. 흔히 헷갈리는 지점

① "파일이 작으면 응집도가 높다"? — 아니다. 응집도는 크기가 아니라 변경 이유의 개수다. 큰 모듈이라도 하나의 목적에 집중하면 응집도가 높고, 10줄짜리라도 무관한 두 책임이 섞이면 낮다.

② "결합도는 0이 이상적이다"? — 결합이 전혀 없는 모듈은 아무와도 협력하지 않는, 쓸모없는 모듈이다. 목표는 결합의 제거가 아니라 결합 지점을 좁고 명시적인 인터페이스로 한정하는 것이다.

③ 추상화 남발의 함정 — 결합을 낮추겠다고 모든 클래스에 인터페이스를 씌우면, 계층만 늘어 코드 추적이 어려워진다. 추상화는 변할 것으로 예상되는 지점에만 대가를 지불하고 사는 도구다.

④ 잘못된 중복 제거가 결합을 만든다 — 우연히 코드가 닮았다고 하나로 합치면, 다른 이유로 변하는 두 사용처가 한 함수에 묶인다. 한쪽 요구가 바뀌는 순간 분기 플래그가 생기며 제어 결합으로 악화된다. 중복 제거는 "지식의 중복"일 때만 유효하다.

★ 6. 언어별 대조

같은 원리지만, 각 언어에서 "결합이 드러나는 지점"과 "경계를 만드는 도구"가 다르다.

언어모듈 경계의 단위결합이 드러나는 방식결합을 낮추는 대표 도구
Java 클래스·패키지·모듈 구체 클래스 직접 new, 패키지 간 순환 참조 인터페이스에 의존 + 의존성 주입(dependency injection), 접근 제어자
JS·TS ES 모듈(파일), 컴포넌트 import 그래프, 컴포넌트 간 과도한 props 전달·전역 스토어 남용 명시적 export로 공개 면 최소화, TS 타입을 계약으로 사용
Python 모듈(파일)·패키지 import 시점 부작용, 순환 import, 내부 속성 직접 접근 _ 관례로 비공개 표시, 덕 타이핑·추상 기반 클래스
C++ 헤더/소스 분리, 클래스, 네임스페이스 #include로 인한 컴파일 시간 결합 — 헤더 하나 수정에 광범위 재컴파일 전방 선언, Pimpl, 헤더에서 구현 숨기기

6.1 C++ — 결합이 "컴파일 시간"으로 눈에 보이는 언어

C++에서는 결합도가 추상적 개념이 아니라 빌드 시간으로 체감된다. #include는 헤더 내용을 소스에 통째로 붙여 넣는 방식이라, 어떤 헤더를 포함한 모든 번역 단위(translation unit — 소스 파일 하나가 컴파일되는 단위)는 그 헤더가 바뀔 때마다 다시 컴파일된다. 즉 헤더에 노출된 내용이 곧 결합의 표면적이다.

이를 줄이는 관용 기법이 Pimpl(pointer to implementation — 구현부를 별도 클래스로 빼고 포인터로만 참조하는 기법)이다. 헤더에는 포인터 선언만 남기 때문에, 구현이 바뀌어도 이 헤더를 포함한 파일들은 재컴파일되지 않는다. 

// widget.h — 공개 경계: 구현 세부가 전혀 노출되지 않는다
class Widget {
public:
    Widget();
    ~Widget();
    void draw();
private:
    class Impl;                  // 전방 선언만 — 내부 필드를 숨김
    std::unique_ptr<Impl> pImpl; // 구현으로 가는 포인터 하나
};

// widget.cpp — 내부 필드·헬퍼가 아무리 바뀌어도
// widget.h 사용자들은 재컴파일되지 않는다 (파급 차단)
class Widget::Impl {
    int cache_;
    void recompute() { /* ... */ }
};

객체 수명과 메모리 관점의 통찰: C++에서 두 모듈이 원시 포인터로 서로의 객체를 참조하면, 코드 결합에 더해 "수명 결합"이 생긴다 — 한쪽이 먼저 소멸하면 다른 쪽이 댕글링 포인터를 쥔다. 소유권을 한쪽에 명확히 두는 설계는 결합도 원칙이 메모리 안전으로 직결되는 C++ 특유의 사례다.

6.2 Python — 유연함이 결합을 숨기는 언어

Python은 접근 제어자가 없고 무엇이든 런타임에 접근·수정할 수 있어, 결합이 생기기 쉽고 눈에 잘 안 띈다. 다른 모듈의 _로 시작하는 내부 속성을 가져다 쓰는 순간 내용 결합이 되지만, 인터프리터는 아무 경고도 하지 않는다.

반면 덕 타이핑(duck typing — 타입 이름이 아니라 "필요한 메서드를 갖고 있는가"로 객체를 다루는 방식)은 결합을 낮추는 강력한 도구가 된다. 호출자가 구체 클래스가 아니라 행동에만 의존하기 때문이다. 

# 나쁨: 구체 클래스에 결합 — SmtpMailer 내부가 바뀌면 파급
def notify(order):
    mailer = SmtpMailer(host="...", port=587)   # 생성 지식까지 떠안음
    mailer.connect()
    mailer.send(order.email, "주문 완료")

# 좋음: "send를 가진 무언가"라는 행동에만 의존 (덕 타이핑)
def notify(order, sender):
    sender.send(order.email, "주문 완료")        # 테스트에선 가짜 sender 주입

Python 관점의 통찰: 순환 import 오류는 대개 "결합도 문제의 증상"이다. A와 B가 서로를 import해야 한다면 두 모듈이 사실상 한 덩어리(함께 변하는 코드)라는 뜻이므로, import 위치를 함수 안으로 옮기는 임시방편보다 공통 부분을 제3의 모듈로 추출해 경계를 다시 긋는 것이 근본 해법이다.

6.3 Java / JS·TS — 한 줄 요약

Java는 인터페이스와 의존성 주입 컨테이너로 "계약에 의존"을 언어·생태계 차원에서 제도화한 경우다. JS·TS(Vue 포함)에서는 컴포넌트가 모듈이며, props/이벤트라는 좁은 계약으로만 소통하는 컴포넌트가 응집·결합 원칙의 프론트엔드 버전이다 — 부모 상태를 직접 변경하거나 전역 스토어를 남용하면 공통 결합이 재현된다.

7. 함께 알면 좋은 것

  • 단일 책임 원칙 — "변경 이유는 하나"라는 응집도 개념을 클래스 수준 원칙으로 정식화한 것. SOLID의 S.
  • 의존성 주입과 테스트 용이성 — 결합을 "주입 지점"으로 좁혀, 테스트에서 가짜 구현으로 갈아끼울 수 있게 하는 실천 기법.
  • 디미터 법칙(Law of Demeter) — "직접 아는 친구에게만 말하라". a.getB().getC().doX() 같은 체이닝이 만드는 은닉 결합을 막는 경험 법칙.
  • 커네이선스(connascence) — 결합을 "이름·타입·순서·타이밍 중 무엇을 공유해서 함께 변해야 하는가"로 세분한 현대적 분류 체계. 결합도 논의의 심화판.
  • 정적 분석 도구 — import/의존 그래프 시각화 도구(언어별 dependency graph 도구, 순환 의존 탐지기)로 결합 구조를 눈으로 점검할 수 있다.

8. 한 장 요약

  • 응집도 = 모듈 안이 한 목적으로 뭉친 정도, 결합도 = 모듈 사이가 얽힌 정도. 판단 기준은 언제나 "변경".
  • 높은 응집: 한 변경 → 한 곳 수정. 낮은 결합: 한 곳 수정 → 파급 없음.
  • 결합의 개수보다 성격이 중요하다 — 내부 구현·전역 상태·제어 플래그 의존은 피하고, 좁은 인터페이스 계약에 의존한다.
  • 경계 기준: 함께 변하는 것은 안으로, 따로 변하는 것은 밖으로. 잘못 자르면 분리가 오히려 결합을 늘린다.
  • C++에서는 헤더 노출이 곧 결합(컴파일 파급), Python에서는 유연함이 결합을 숨긴다(순환 import는 경계 이상 신호).
  • 두 지표가 좋은 코드는 곧 테스트하기 쉬운 코드다.

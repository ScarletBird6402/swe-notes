J2 테스트 피라미드

0. 한눈에 보는 결론

  • 테스트 피라미드(test pyramid)는 "단위는 많이, 통합은 적당히, E2E는 조금"이라는 비중의 그림으로 알려져 있지만, 비중은 결과일 뿐이다. 모형의 실제 내용은 층마다 잡는 결함의 종류가 다르다는 것이다.
  • 단위 테스트는 한 조각의 로직 결함(계산·분기·변환의 오류)을, 통합 테스트는 조각 사이의 연결 결함(계약 불일치·설정·매핑·쿼리)을, E2E는 경로 전체와 환경의 결함(배선·배포 구성·사용자 흐름)을 잡는다. 어느 층도 다른 층을 완전히 대신하지 못한다.
  • 위 층은 아래 층의 결함을 "잡을 수는" 있지만 세 가지 비용이 붙는다: 느림(실행·준비 시간), 비결정성(같은 코드가 어떤 날은 실패), 진단 거리(실패 지점에서 원인까지 멀다). 이 비용이 위로 갈수록 급격히 커지는 것이 삼각형 모양의 이유다.
  • 역피라미드·아이스크림콘은 "E2E가 많다"가 문제가 아니라, 하위 층에서 싸게 잡을 결함을 상위 층에서 비싸게 잡는 배치가 문제다 — 비용은 복리로 불어나 결국 테스트가 신호를 잃는다.
  • 배분 원리는 하나다: 각 결함을 그것을 잡을 수 있는 가장 낮은 층에 둔다. 비중은 그 결과로 따라온다.
  • 상위 층의 통과가 하위 층의 작동을 보증하지 않는다 — 여러 방어 계층이 겹친 코드에서는 각 층이 실제로 발동하는지를 층별로 검증해야 한다(J18의 주제).

1. 피라미드가 그리는 세 층 — 모형의 주장과 그 한계

테스트 피라미드는 자동 테스트를 세 층으로 나누고, 아래가 넓고 위가 좁은 삼각형으로 그린 모형이다. 맨 아래 단위 테스트(unit test)는 함수·클래스 한 조각을 외부 의존 없이(필요하면 J1에서 다룬 테스트 더블로 대체해) 검증한다. 중간 통합 테스트(integration test)는 여러 조각을 실제로 붙여서 — 데이터베이스, 프레임워크의 요청 처리 계층, 외부 API 클라이언트 등 — 검증한다. 맨 위 종단 간 테스트(end-to-end test, E2E)는 사용자의 시각에서 시스템 전체를 실제 경로로 통과시킨다.

▲ 비용·느림·비결정성·진단 거리 │ ┌───────────┐ │ E2E │ 브라우저·실제 배포 구성·전체 경로 ┌─┴───────────┴─┐ │ 통합 테스트 │ 조각을 실제로 연결: DB·프레임워크 계층·외부 클라이언트 ┌─┴───────────────┴─┐ │ 단위 테스트 │ 한 조각의 로직: 계산·분기·변환 └───────────────────┘ │ ▼ 개수·속도·정밀한 실패 위치

이 그림에서 대부분 눈에 들어오는 것은 넓이, 즉 개수의 비중이다. 그래서 논쟁도 비중을 둘러싸고 벌어진다 — "단위 70%가 맞나", "프론트엔드는 통합이 더 많아야 하지 않나". 그러나 삼각형은 처방이 아니라 결과의 그림이다. 세 층을 나눈 이유를 모르면 비중 숫자는 근거 없는 관습이 되고, 팀은 숫자를 지키면서도 결함을 놓친다. 그러니 질문을 바꿔야 한다: 왜 굳이 세 층으로 나누는가 — 각 층은 무엇을 잡는가?

2. 층마다 잡는 결함이 다르다

앞 절의 질문에 답하려면 "결함"을 하나의 덩어리로 보지 말고 어디에서 생기는 결함인지로 갈라야 한다. 같은 "주문에 할인이 잘못 적용됐다"는 증상도 원인은 세 곳 중 어디에든 있을 수 있다. 

// (1) 로직 결함 — 조각 내부: 경계값 처리가 틀렸다
int discounted(int amount, int rate) {
    return amount - amount * rate / 100;        // rate가 100을 넘을 때 음수 허용 — 분기 누락
}

// (2) 연결 결함 — 조각 사이: 계산은 맞지만 저장소 매핑이 다른 컬럼을 읽는다
//     @Column(name = "discount_rate")  ← 실제 스키마의 컬럼명은 "rate_percent"
//     단위 테스트에서는 저장소가 대역이므로 절대 드러나지 않는다

// (3) 경로·환경 결함 — 시스템 전체: 코드는 전부 맞지만 배포 구성에서
//     할인 서비스로 가는 라우팅 규칙이 빠져 있어 요청이 다른 핸들러로 간다

세 결함은 존재하는 장소가 다르므로, 그것을 볼 수 있는 시야도 다르다. 이것이 층을 나누는 근거다.

층시야(무엇을 실제로 실행하는가)이 층이 잡는 결함이 층이 원리상 못 보는 것
단위 조각 하나 — 의존은 대역 계산·분기·변환의 오류, 경계값, 예외 처리 규칙 조각 사이의 계약 불일치 — 대역이 실제 이웃이 아니므로 연결 결함은 구조적으로 보이지 않는다
통합 조각 여러 개를 실제로 연결 — 실제 DB·프레임워크 계층·직렬화 매핑·쿼리·설정·직렬화 규칙·계약 불일치 배포 구성, 브라우저 동작, 여러 시스템을 넘나드는 사용자 흐름
E2E 실제 배포 형태의 시스템 전체 배선·라우팅·인프라 구성·사용자 흐름의 단절 "어느 조각이 왜 틀렸는가" — 볼 수는 있어도 가리키지 못한다(3절)

핵심 문장: 단위 테스트가 1000개 있어도 (2)와 (3)은 잡히지 않는다 — 개수 부족이 아니라 시야의 종류가 다르기 때문이다. 반대로 E2E는 (1)·(2)·(3)을 모두 "볼 수" 있다. 그렇다면 E2E만 촘촘히 두면 되지 않는가? 이 질문에 답하는 것이 다음 절이다.

3. 위로 갈수록 청구되는 세 비용 — 느림·비결정성·진단 거리

앞 절의 표에서 E2E는 세 결함을 모두 볼 수 있었다. 그런데도 E2E로 로직 결함을 잡는 것이 나쁜 선택인 이유는, 상위 층이 같은 결함을 잡는 데 훨씬 큰 비용을 청구하기 때문이다. 비용은 세 종류로 갈린다.

① 느림. 단위 테스트는 밀리초 단위로 수천 개가 돈다. 통합은 DB·컨테이너·프레임워크 초기화가 붙어 초 단위, E2E는 브라우저 구동과 시스템 전체 준비로 분 단위가 된다. 느림 자체보다 무서운 것은 느리면 덜 실행된다는 것이다 — 저장할 때마다 돌던 테스트가 하루 한 번으로 밀리면, 결함은 발생 직후가 아니라 하루 뒤에 발견되고 그사이 쌓인 변경 전부가 용의자가 된다.

② 비결정성(non-determinism). 상위 층은 실행할 때마다 달라질 수 있는 요소 — 네트워크 지연, 스레드 스케줄링, 시각, 외부 서비스 상태, 브라우저 렌더링 타이밍 — 를 실제로 포함한다. 그래서 코드 변화 없이도 어떤 날은 실패하는 플레이키 테스트(flaky test)가 생긴다. 플레이키 테스트의 진짜 비용은 재실행 시간이 아니라 신호의 상실이다: "저건 원래 가끔 빨개져"가 되는 순간, 진짜 실패도 같은 눈으로 넘겨진다.

③ 진단 거리. 이 문서에서 진단 거리란 테스트가 실패한 지점에서 결함이 있는 코드까지의 거리를 말한다. 단위 테스트의 실패는 "이 함수의 이 분기"를 가리킨다 — 거리 0이다. E2E의 실패는 "주문 완료 화면이 뜨지 않음"이다 — 원인은 프론트의 상태 관리일 수도, API 계약일 수도, DB 매핑일 수도, 라우팅일 수도 있다. 같은 결함이라도 상위 층에서 발견되면 찾는 일이 통째로 추가된다.

결함 하나 = "rate가 100을 넘을 때 음수 허용" 단위 테스트로 잡을 때 실행 1ms · 결정적 · 실패 메시지: discounted(1000, 150) expected 0 but was -500 → 원인까지의 거리 0 E2E로 잡을 때 실행 3분 · 가끔 타임아웃 · 실패 메시지: "결제 확인 화면에 합계가 표시되지 않음" → 원인 후보: 프론트 표시 로직 / API 응답 형식 / 서비스 계산 / DB 매핑 / 라우팅 → 거리: 계층 다섯 개

세 비용은 독립적이지 않다 — 느리면 덜 돌리고, 덜 돌리면 원인 후보가 늘어 진단 거리가 커지며, 비결정성은 그 위에 "진짜 실패인가"라는 물음표를 얹는다. 그렇다면 이 비용을 무시하고 상위 층에 테스트를 몰아넣으면 실제로 무슨 일이 벌어지는가.

4. 역피라미드와 아이스크림콘 — 비용이 복리로 커지는 이유

앞 절의 세 비용이 한꺼번에 청구되는 배치가 있다. 역피라미드는 E2E·통합이 많고 단위가 적은 형태, 아이스크림콘은 그 위에 자동화되지 않은 수동 테스트라는 커다란 덩어리가 얹힌 형태다.

아이스크림콘 피라미드 ┌───────────────────┐ │ 수동 테스트 (대량) │ ┌───────┐ └─┬───────────────┬─┘ │ E2E │ │ E2E (많음) │ ┌───┴───────┴───┐ └─┬───────────┬─┘ │ 통합 │ │ 통합 (약간) │ ┌───┴───────────────┴───┐ └─┬───────┬─┘ │ 단위 │ │ 단위 │ └───────────────────────┘ └─────┘

이 형태는 나태의 산물이 아니라 합리적으로 보이는 선택의 누적이다. 단위 테스트를 쓰기 어려운 설계(의존이 생성자 안에서 직접 만들어져 대역을 끼울 틈이 없는 코드 — I4의 주제)에서는 "차라리 실제로 띄워서 확인하자"가 가장 빠른 길이다. 게다가 E2E는 "실제와 똑같이" 돌아가므로 안심의 착시가 크다 — 초록불 하나가 모든 층을 덮어 준 것처럼 느껴진다.

문제는 비용이 복리로 붙는다는 것이다:

  • E2E가 많아 스위트가 느려진다 → 저장할 때마다가 아니라 하루 한 번 돈다 → 결함 발견이 늦어지고 원인 후보(그사이의 변경)가 늘어난다.
  • 느린 스위트 안에 플레이키 테스트가 몇 개 섞인다 → 재실행이 습관이 된다 → 진짜 실패가 재실행으로 "사라지는" 경험이 쌓인다 → 빨간불이 정보를 잃는다.
  • 로직 결함이 E2E에서 발견된다 → 진단 거리가 계층 수만큼 길다 → 고치는 데 오래 걸린다 → 테스트 작성 시간이 더 줄어든다 → 단위 층은 더 얇아진다.

역피라미드의 진짜 문제는 "E2E가 많다"가 아니다. E2E가 잡아야 할 결함(배선·구성·흐름)을 E2E가 잡는 것은 정상이다. 문제는 단위 층에서 밀리초에 잡힐 로직 결함이 E2E에서 분 단위·비결정적·진단 거리 다섯 계층으로 잡히는 배치다 — 같은 결함에 가장 비싼 영수증을 끊는 것이다.

이렇게 보면 처방도 "E2E를 줄여라"가 아니다. 각 결함을 어느 층에 두어야 가장 싸게 잡히는가가 기준이 되어야 한다.

5. 배분 원리 — 결함을 가장 싸게 잡는 층으로 내린다

앞 절의 결론을 규칙 하나로 압축하면 이렇다: 각 결함은 그것을 잡을 수 있는 가장 낮은 층에 둔다. 2절의 표가 "어느 층이 무엇을 볼 수 있는가"였다면, 이 규칙은 "볼 수 있는 층 중 가장 싼 곳을 고르라"다. 비중은 이 배분의 결과로 나온다 — 로직 결함이 가장 많고 가장 아래에서 잡히므로 단위가 넓어지고, 배선 결함은 종류가 적고 위에서만 잡히므로 E2E가 좁아진다.

결함 후보(무엇이 틀릴 수 있는가)를 하나 고른다 │ ├─ 조각 하나만 실행해도 드러나는가? (계산·분기·변환) │ 예 ──> 단위 층. 로직을 대역 없이 시험할 수 있게 조각을 분리한다 │ ├─ 조각 둘 이상을 실제로 붙여야 드러나는가? (매핑·쿼리·계약·설정) │ 예 ──> 통합 층. 붙이는 범위는 결함을 드러내는 최소로 — 전체가 아니라 슬라이스 │ └─ 배포된 시스템 전체를 지나야만 드러나는가? (라우팅·인프라·사용자 흐름) 예 ──> E2E 층. 핵심 흐름 소수만 — "주문이 끝까지 되는가" 수준

이 절차에는 두 가지 부수 효과가 있다. 첫째, 내릴 수 없는 결함이 설계의 신호가 된다: "이 계산은 DB를 띄워야만 시험할 수 있다"면 계산이 저장소 코드와 엉켜 있다는 뜻이고, 분리하면 단위 층으로 내려온다. 둘째, 상위 층에 남는 테스트는 그 층에서만 잡히는 결함으로 정당화된다 — "실제처럼 돌아가니까"가 아니라 "이 배선은 여기서만 보이니까"가 E2E 하나하나의 존재 이유가 된다.

그런데 이 배분에는 암묵적 전제가 하나 숨어 있다. "위 층이 통과했으니 아래 층도 괜찮다"는 믿음이다. 이 전제는 성립하지 않는다 — 다음 절이 그 이유다.

6. 층은 서로를 대신하지 못한다 — 통과는 발동을 보증하지 않는다

앞 절에서 결함을 층별로 배분했으니 "E2E가 초록이면 그 아래는 전부 작동 중"이라 믿기 쉽다. 그러나 상위 층의 통과가 말해 주는 것은 최종 결과가 맞았다는 것뿐, 중간의 각 조각이 자기 몫을 했다는 것이 아니다. 

// 같은 입력을 세 층이 방어한다 — 프론트 검증, API 검증, 도메인 규칙
// 도메인 규칙의 조건이 잘못 고쳐져 항상 참을 반환하게 됐다고 하자
boolean isValidRate(int rate) {
    return rate >= 0 || rate <= 100;      // && 이어야 했다 — 이제 어떤 값도 통과
}
// E2E: 프론트 검증이 150을 먼저 막으므로 화면 결과는 정상 → 초록불
// 통합: API 검증이 같은 값을 또 막으므로 응답도 정상 → 초록불
// 도메인 규칙은 죽어 있지만 아무 증상이 없다 — 앞 층이 가려 주는 동안만

이것이 무증상 퇴화다: 여러 방어 계층이 겹친 코드에서는 하나가 죽어도 다른 층이 가려 주므로 상위 테스트는 계속 통과하고, 죽은 층은 앞 층이 우회되는 날(다른 진입 경로, 배치 작업, 내부 호출) 비로소 드러난다. 그래서 다층 방어의 각 층은 그 층만 실행하는 테스트로 따로 검증해야 한다 — 이것이 피라미드가 J18(층별 검증)로 이어지는 지점이다. 피라미드의 "단위 층이 넓다"는 결국 "각 조각의 발동을 개별로 확인하는 테스트가 많다"는 뜻이기도 하다.

반대 방향도 같다. 단위 테스트가 전부 초록이어도 연결은 검증되지 않았다 — 대역은 이웃의 실제 행동이 아니라 내가 가정한 행동을 돌려주기 때문이다(J1에서 본 대역의 본질). 층은 위에서 아래로도, 아래에서 위로도 서로를 대신하지 못한다. 이 대칭을 받아들이면, 남는 것은 모형을 둘러싼 오해들이다.

7. 흔히 헷갈리는 지점

① "비중 숫자가 정답이다" — 70/20/10 같은 숫자는 특정 형태의 시스템에서 5절의 배분을 했을 때 나온 결과이지 목표가 아니다. 로직이 얇고 연결이 두꺼운 시스템(화면 조립 중심의 프론트, 데이터를 옮기기만 하는 파이프라인)은 배분을 정직하게 해도 통합 층이 넓어진다. 숫자를 맞추려 로직 없는 코드에 단위 테스트를 채우면 J10에서 본 동어반복 테스트가 양산된다.

② "통합 테스트 = 느린 단위 테스트" — 두 층의 차이는 속도가 아니라 시야다(2절). 실제 DB 대신 인메모리 대체물을 쓰면 빨라지지만, 그 순간 실제 DB의 방언·제약·매핑 결함은 시야 밖으로 나간다. 빨라진 통합 테스트가 잡을 수 있는 결함 목록이 줄었는지 확인해야 한다.

③ "대역을 쓰면 단위 테스트, 안 쓰면 통합 테스트" — 층의 정의는 도구가 아니라 실제로 실행되는 범위다. 대역을 하나도 안 썼어도 순수 함수 하나만 실행하면 단위이고, 대역을 썼어도 실제 DB와 프레임워크 계층을 함께 띄우면 통합이다. 도구로 층을 정의하면 "mock을 썼으니 빠르겠지"라는 착각이 생긴다.

④ "플레이키 테스트는 재시도로 해결된다" — 재시도는 비결정성의 증상을 가릴 뿐이다. 비결정성의 원인(시각·순서·외부 상태 의존)이 코드에 있다면 그것은 테스트 결함이 아니라 코드 결함의 신호이고, 원인이 테스트 환경에 있다면 그 테스트는 한 층 아래로 내릴 수 있는지(5절) 먼저 물어야 한다. 재시도를 기본값으로 켜는 순간 3절의 "신호 상실"이 제도화된다.

★ 8. 언어별 대조

같은 세 층이지만, 언어마다 층을 나누는 도구와 그 경계를 지키는 방식이 다르다 — 어떤 생태계는 빌드 도구가 층을 물리적으로 분리해 주고, 어떤 생태계는 관례(마커·파일명)에만 의존한다. 그 차이가 곧 "단위 층이 조용히 통합 층으로 새는" 함정의 모양을 결정한다.

언어단위 층 도구통합·E2E 층과의 경계그 언어만의 함정
Java JUnit 5 + Mockito 빌드 도구의 단계 분리(단위/통합 실행기 분리)·태그·프레임워크 슬라이스 테스트 무엇이든 mock할 수 있게 되면서 "전부 대역인 단위 테스트"가 연결 결함을 영원히 못 보게 된다
JS·TS Jest / Vitest 모듈 모킹·시뮬레이션 DOM(jsdom) vs 실제 브라우저 실행 jsdom 위의 테스트를 E2E로 착각 — 브라우저 결함은 시야 밖이다
Python pytest + unittest.mock 마커(-m)와 픽스처 스코프로 층을 관례적으로 분리 patch 대상 경로가 틀리면 대역이 걸리지 않고 실제 의존이 조용히 실행된다 — 층 경계의 누수
C++ GoogleTest + GoogleMock 테스트 실행 파일 자체를 층별로 분리(링크 단위)·CTest 라벨 대역을 끼우려면 가상 인터페이스라는 설계 비용이 먼저 든다 — 단위 층의 넓이가 설계에 의해 상한을 받는다

8.1 Java — JUnit 5 + Mockito: 빌드가 층을 나눠 주지만, mock이 층을 무너뜨릴 수 있다

Java 생태계의 특징은 층 분리가 빌드 도구 수준에서 제도화돼 있다는 점이다. 단위 테스트와 통합 테스트를 서로 다른 실행 단계에서 돌리는 관례(파일명 규칙이나 JUnit 5의 @Tag로 분류)가 표준 빌드 도구에 내장돼 있어, "빠른 층만 먼저"가 설정 몇 줄로 된다. 통합 층에서는 프레임워크의 특정 계층만 띄우는 슬라이스 테스트가 "결함을 드러내는 최소 범위"(5절)를 구현한 형태이고, 그 세부는 J8의 주제다. 

@ExtendWith(MockitoExtension.class)          // JUnit 5 확장 모델로 Mockito를 붙인다
@Tag("unit")                                  // 빌드 단계에서 층을 고르는 열쇠
class DiscountServiceTest {
    @Mock  RateRepository rateRepository;      // 이웃은 대역 — 연결 결함은 이 테스트의 시야 밖
    @InjectMocks DiscountService service;

    @Test
    void 할인율_상한을_넘으면_0원까지만_깎는다() {
        when(rateRepository.findRate("VIP")).thenReturn(150);
        assertEquals(0, service.discounted(1000, "VIP"));   // 로직 결함만 잡는다
    }
}

함정은 Mockito의 힘에서 온다. Mockito 5(2023년 이후)부터는 final 클래스·정적 메서드까지 기본으로 mock할 수 있어(인라인 mock maker 기본화), 설계를 바꾸지 않고도 무엇이든 대역으로 바꿀 수 있다. 편리함의 대가는 단위 층이 무한히 넓어질 수 있다는 것 — 저장소·직렬화·프레임워크 계층까지 전부 대역으로 바꾼 "단위 테스트"는 초록불을 내지만 2절의 연결 결함은 영원히 시야 밖이다. 또 하나, MockitoExtension은 기본이 엄격 스텁(strict stubs)이라 쓰이지 않은 스텁이 있으면 테스트를 실패시킨다: 이는 "대역 설정이 실제 코드 경로와 어긋났다"는 신호이므로, 끄기보다 왜 그 스텁이 남았는지를 묻는 편이 층 경계를 지키는 데 유리하다.

8.2 JS·TS — Jest / Vitest: 시뮬레이션 DOM과 실제 브라우저 사이에 층이 하나 더 있다

JS·TS의 단위·컴포넌트 층은 Jest와 Vitest가 담당한다. 둘은 describe/it/expect와 모듈 모킹 API가 거의 같아 옮겨 다니기 쉽지만 실행 기반이 다르다 — Jest는 CommonJS 중심으로 변환 계층을 거치고, Vitest는 Vite의 변환 파이프라인 위에서 ESM·TypeScript를 그대로 실행한다. 2020년대 중반 기준 Vite 기반 프로젝트(Vue 3 포함)에서는 Vitest가 일반적인 선택이고, Jest는 기존 CommonJS 코드베이스와 그 생태계에서 여전히 널리 쓰인다. 

// Vitest — 모듈 모킹으로 API 계층을 대역으로: 이 테스트는 "단위·컴포넌트 층"이다
import { describe, it, expect, vi } from 'vitest'
import { fetchRate } from './rateApi'
import { discounted } from './discount'

vi.mock('./rateApi')                               // 파일 상단으로 끌어올려져 적용된다(hoisting)

describe('discounted', () => {
  it('할인율이 100을 넘으면 0원까지만 깎는다', async () => {
    vi.mocked(fetchRate).mockResolvedValue(150)      // 이웃의 "가정된" 행동
    expect(await discounted(1000, 'VIP')).toBe(0)    // 잡는 것: 로직 결함
  })
})

이 언어만의 층 구조는 DOM이 두 종류라는 데서 생긴다. Jest·Vitest의 기본 환경은 jsdom 같은 시뮬레이션 DOM — 브라우저를 흉내 내는 자바스크립트 구현 — 이라 컴포넌트를 렌더링해 볼 수는 있지만, 레이아웃·실제 이벤트 타이밍·브라우저별 차이는 시야 밖이다. 그러니 jsdom 위의 컴포넌트 테스트는 아무리 화면과 비슷해 보여도 E2E가 아니라 통합 층의 한 형태이고, 브라우저 결함은 실제 브라우저를 구동하는 E2E 도구(또는 Vitest의 브라우저 모드처럼 실제 브라우저에서 돌리는 방식)에서만 보인다. 두 번째 함정은 모듈 모킹의 편의다 — vi.mock/jest.mock으로 API 모듈을 통째로 대역화하면 응답 형식이 바뀐 계약 불일치를 프론트 테스트가 전부 통과시킨다. 그 결함은 실제 응답을 받는 층(계약 테스트 또는 E2E)에 명시적으로 배정돼 있어야 한다.

8.3 Python — pytest + unittest.mock: 층 경계가 관례뿐이라 누수가 조용하다

pytest에는 층을 강제하는 장치가 없다. 대신 마커로 테스트에 층 이름을 붙이고 -m "not integration"처럼 골라 돌리며, 실제 DB 같은 비싼 자원은 픽스처 스코프(함수·모듈·세션 단위로 수명을 정하는 방식)로 통합 층에서만 한 번 띄운다. 즉 층은 이름표로 존재한다. 

import pytest
from unittest.mock import patch

@pytest.mark.unit
def test_rate_over_100_floors_at_zero():
    # 함정: patch 대상은 "정의된 곳"이 아니라 "찾아보는 곳"의 이름이어야 한다
    with patch("orders.discount.fetch_rate", return_value=150):   # orders.discount가 import한 이름
        from orders.discount import discounted
        assert discounted(1000, "VIP") == 0

@pytest.mark.integration          # -m "not integration" 으로 단위 층만 돌릴 수 있다
def test_rate_mapping_reads_correct_column(db_session):          # 세션 스코프 픽스처: 실제 DB
    ...

이 언어의 고유한 함정은 대역이 걸리지 않아도 아무 오류가 없다는 것이다. patch("rates.api.fetch_rate")처럼 함수가 정의된 모듈을 패치하면, 이미 from rates.api import fetch_rate로 이름을 가져간 orders.discount 모듈은 원본을 계속 부른다 — 테스트는 "단위"라는 마커를 달고 실제 네트워크나 DB를 조용히 때린다. 층 경계가 관례뿐이므로, 새는 순간을 알려 주는 것은 느려진 실행 시간과 어느 날의 비결정적 실패뿐이다(J12에서 이름 패치와 객체 교체를 대조한다).

Python 관점의 통찰: 층의 경계를 흐리는 것은 pytest가 아니라 Python의 이름 결정 방식이다 — 모듈은 실행 시점에 이름을 찾아보는 네임스페이스이므로, 대역을 "타입"이 아니라 "이름"에 끼우게 되고 어느 이름을 바꿔야 하는지가 호출자마다 다르다. 정적 언어에서 타입 시스템이 강제하는 "이 자리에 무엇이 들어오는가"를 Python에서는 patch 경로 문자열이 대신하며, 그 문자열은 컴파일러가 검사해 주지 않는다. 그래서 autospec(원본의 시그니처를 대역에 강제하는 옵션)을 켜고, 대역이 정말 호출됐는지를 단언에 포함시키는 것이 이 언어에서 층 경계를 지키는 최소 비용이다.

8.4 C++ — GoogleTest + GoogleMock: 층이 링크 단위로 갈리고, 단위 층의 넓이는 설계가 정한다

C++에서 테스트는 실행 파일이다. 단위 테스트 실행 파일은 대상 객체 파일과 GoogleTest만 링크하고, 통합 테스트 실행 파일은 실제 DB 클라이언트·네트워크 라이브러리까지 링크한다 — 층이 빌드 산출물 수준에서 갈리며, CTest의 라벨로 골라 돌린다. 다른 언어에서 관례였던 것이 여기서는 링크 의존성이라는 물리적 사실이다. 

#include <gmock/gmock.h>
#include <gtest/gtest.h>

// 대역을 끼우려면 먼저 "자리"가 있어야 한다 — 가상 인터페이스라는 설계 비용
class RateSource {
public:
    virtual ~RateSource() = default;
    virtual int fetchRate(const std::string& grade) = 0;
};

class MockRateSource : public RateSource {
public:
    MOCK_METHOD(int, fetchRate, (const std::string& grade), (override));
};

TEST(DiscountTest, RateOver100FloorsAtZero) {
    MockRateSource source;
    EXPECT_CALL(source, fetchRate("VIP")).WillOnce(testing::Return(150));
    DiscountService service(source);              // 참조로 주입 — 수명은 테스트 스코프가 보장
    EXPECT_EQ(0, service.discounted(1000, "VIP"));
}

이 언어의 함정은 단위 층의 넓이가 설계에 의해 상한을 받는다는 것이다. gMock은 가상 함수(virtual function — 실행 시점에 실제 객체의 타입을 보고 호출을 고르는 메서드)가 있는 인터페이스나 템플릿 매개변수로 주입된 타입만 대체할 수 있다. 구체 클래스를 직접 생성해 쓰는 코드에는 대역을 끼울 자리가 없고, 그런 코드는 실제 의존을 링크해야만 시험할 수 있어 구조적으로 통합 층으로 밀려난다. Java에서 Mockito가 "무엇이든 mock"으로 단위 층을 과잉 확장시켰다면, C++은 반대로 설계가 단위 층을 과소 확장시킨다 — 역피라미드가 나태가 아니라 설계의 결과일 수 있다는 4절의 관찰이 가장 선명한 언어다.

C++ 관점의 통찰: 3절의 "느림"에 C++은 컴파일·링크 시간을 추가한다 — 통합 테스트 실행 파일이 무거운 라이브러리를 링크하면 실행보다 빌드가 병목이 되므로, 층 분리는 곧 빌드 그래프 분리다. 대역 주입의 수명도 다른 언어에 없는 축이다: 참조나 포인터로 주입한 mock은 테스트 스코프가 대상 객체보다 오래 살아야 하고, 이를 어기면 테스트가 미정의 동작 위에서 "통과"할 수 있다. 그리고 미정의 동작이 있는 코드는 어느 층의 초록불도 정확성을 보증하지 않으므로, C++에서는 새니타이저 빌드(주소·미정의 동작 검출기를 켠 별도 빌드)가 사실상 피라미드의 네 번째 층 노릇을 한다.

9. 함께 알면 좋은 것

본문의 축 — "층마다 잡는 결함이 다르다" — 을 인접 어휘로 넓힌 것들이다. 첫째·둘째는 1절의 모형 논쟁을, 셋째는 2절의 연결 결함을, 넷째는 3절의 비결정성을, 다섯째는 5절의 배분 절차를 잇는다.

  • 테스팅 트로피(testing trophy) — 정적 검사(타입·린트)를 맨 아래 층으로 추가하고 통합 층을 가장 넓게 그린 변형 모형. 프론트엔드처럼 로직이 얇고 조립이 두꺼운 코드에서 5절의 배분을 하면 자연히 나오는 모양이며, 피라미드와 대립이 아니라 "결함의 분포가 다르면 비중도 다르다"는 같은 원리의 다른 결과다.
  • 벌집·다이아몬드 모형 — 마이크로서비스처럼 서비스 하나의 내부 로직은 작고 서비스 간 경계가 두꺼운 구조에서 통합 층을 넓게 그린 모형. 마찬가지로 1절의 비중 논쟁이 아니라 결함 분포의 차이로 읽어야 한다.
  • 계약 테스트(contract test) — 호출자와 제공자가 경계의 기대(요청·응답 형식)를 명문화해 각자 검증하는 방식. 2절의 "연결 결함"을 E2E까지 올리지 않고 통합 층 아래로 내리는 도구이며, 8.2의 모듈 모킹이 가리는 계약 불일치를 되찾는다.
  • 비결정성 격리 — 시각·난수·순서·외부 상태 같은 비결정 요소를 주입 가능한 의존으로 빼내는 설계(시계 주입, 시드 고정, 테스트 컨테이너로 격리된 DB). 3절의 플레이키 테스트를 재시도가 아니라 원인 제거로 다루는 접근이며, C20에서 다루는 시각 처리와 맞닿는다.
  • 테스트 대상 선정과 커버리지 — 5절의 배분 절차는 "어느 층에"를 정하지만 "테스트할 가치가 있는가"는 별개의 판별이다(J10). 층별 커버리지 수치를 비중 목표로 쓰면 7-①의 함정으로 돌아간다(J9).

10. 한 장 요약

  • 피라미드의 삼각형은 처방이 아니라 결과다 — 모형의 내용은 층마다 잡는 결함의 종류가 다르다는 것이다: 단위 = 로직, 통합 = 연결, E2E = 경로·환경.
  • 상위 층은 하위 결함을 볼 수 있지만 느림·비결정성·진단 거리라는 세 비용을 청구하며, 셋은 서로를 키운다.
  • 역피라미드·아이스크림콘의 문제는 E2E의 개수가 아니라 싸게 잡힐 결함에 가장 비싼 영수증을 끊는 배치이고, 비용은 복리로 불어 결국 빨간불이 정보를 잃는다.
  • 배분 원리: 각 결함을 잡을 수 있는 가장 낮은 층에 둔다. 내릴 수 없는 결함은 설계의 신호이고, 상위 층에 남는 테스트는 그 층에서만 보이는 결함으로 정당화된다.
  • 층은 서로를 대신하지 못한다 — 상위 통과는 하위 작동을 보증하지 않으므로(무증상 퇴화), 겹친 방어는 층별로 검증한다.
  • 언어마다 층 경계를 지키는 장치가 다르다: Java는 빌드가 나누되 mock이 무너뜨릴 수 있고, JS·TS는 시뮬레이션 DOM이라는 중간층을 가지며, Python은 관례뿐이라 누수가 조용하고, C++은 설계가 단위 층의 상한을 정한다.

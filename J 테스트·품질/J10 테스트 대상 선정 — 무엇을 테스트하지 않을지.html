J10 테스트 대상 선정 — 무엇을 테스트하지 않을지

0. 한눈에 보는 결론

  • 테스트는 공짜가 아니다 — 작성·유지·실행 비용을 계속 청구하는 코드 자산이다. 그래서 "무엇을 테스트할까"만큼 "무엇을 테스트하지 않을까"가 성숙한 판단의 영역이다.
  • 안 쓸 후보 1순위는 트리비얼 테스트(trivial test): 구현을 그대로 복사해 되읽는 동어반복 테스트다. 실패하려면 구현과 테스트를 같은 방식으로 동시에 잘못 써야 하므로, 검증력이 0이면서 유지비만 청구한다.
  • 2순위는 위임/패스스루(pass-through) 계층: 받은 것을 다음 계층에 넘기기만 하는, 로직(분기·계산·변환) 없는 통로다. 통로를 단위 테스트하면 결국 대역 설정을 되읽는 동어반복이 된다.
  • "안 쓴다"는 "안 지킨다"가 아니다 — 통로의 검증 가치는 인접 계층으로 이동한다: 로직이 있는 이웃 계층의 단위 테스트와, 경로 전체를 실제로 통과하는 상위(통합) 테스트가 그 몫을 담당한다.
  • 언어·프레임워크·표준 라이브러리가 이미 보증하는 것을 재검증하지 않는다(컨벤션 존중). 남의 보증을 되풀이하는 대신, 내가 작성한 조합·설정·로직에 테스트 예산을 집중한다.
  • 판별 질문은 세 개면 충분하다: ① 내가 쓴 로직이 있는가 → ② 이 테스트는 구현의 복사인가 → ③ 인접 계층/도구가 이미 지키고 있는가.

1. 전제 — 테스트는 자산이면서 부채다

이 문서에서 "테스트"는 코드 조각의 동작을 자동으로 검증하는 코드, 특히 단위 테스트를 가리킨다(단위/통합의 구분과 대역(mock 등)의 종류는 J1의 주제이므로 여기서는 필요한 만큼만 쓴다). 테스트가 자산인 이유는 익숙하다: 회귀를 잡고, 리팩토링의 안전망이 되고, 동작의 문서가 된다. 덜 이야기되는 쪽은 부채의 얼굴이다 — 테스트도 코드이므로 작성 시간이 들고, 대상 코드가 바뀔 때마다 함께 고쳐야 하며, 빌드마다 실행 시간을 소비한다.

가치 있는 테스트는 이 비용을 검증력으로 상환한다. 문제는 검증력 없이 비용만 청구하는 테스트가 존재한다는 것 — 심지어 이런 테스트는 초록불로 "검증되고 있다"는 착시까지 만들어, 없느니만 못한 음수 자산이 된다. 그렇다면 어떤 테스트가 검증력이 없는가. 가장 순수한 형태부터 보자.

2. 트리비얼 테스트 — 구현을 복사해 되읽는 동어반복

트리비얼 테스트(동어반복 테스트)는 구현이 하는 일을 테스트가 그대로 반복하는 테스트다. 

// 대상: 로직이 전혀 없는 접근자
public class Order {
    private int amount;
    public int getAmount() { return amount; }
    public void setAmount(int amount) { this.amount = amount; }
}

// 동어반복 테스트: "넣은 값이 나온다"를 확인 — 언어의 대입 문법을 재검증하는 셈
@Test
void getAmount는_설정한_값을_반환한다() {
    Order order = new Order();
    order.setAmount(1000);
    assertEquals(1000, order.getAmount());
}

이 테스트가 실패하는 경우를 생각해 보면 정체가 드러난다: getAmount가 다른 필드를 반환하도록 구현을 잘못 고치고, 테스트는 안 고쳤을 때뿐이다. 즉 이 테스트의 검증 대상은 내 로직이 아니라 "구현과 테스트를 같은 방식으로 틀리지는 않았겠지"라는 우연이다. 상수 값을 그대로 비교하는 테스트, 대역에게 "X를 반환하라"고 설정한 뒤 X가 반환되는지 확인하는 테스트도 같은 부류다 — 마지막 것은 내 코드가 아니라 mock 라이브러리를 테스트하고 있다.

판별 도구 — "이 테스트는 무엇이 틀렸을 때 실패하는가?": 답이 "구현을 일부러 망가뜨렸을 때뿐"이라면 동어반복이다. 좋은 테스트는 요구사항이 어겨졌을 때 실패한다 — "할인율 10% 적용 시 9,000원이어야 한다"는 요구를 검증하지, "필드에 넣은 값이 나온다"는 문법을 검증하지 않는다.

그런데 트리비얼 테스트는 접근자 같은 한 줄짜리에서만 생기는 게 아니다. 계층 하나가 통째로 트리비얼인 경우가 있다 — 다음 절의 주제다.

3. 위임/패스스루 계층 — 로직 없는 통로

계층화된 웹 애플리케이션에는 받은 것을 다음 계층에 넘기기만 하는 코드가 구조적으로 생긴다. 

// 전형적인 패스스루: 분기도, 계산도, 변환도 없다
@RestController
public class OrderController {
    private final OrderService orderService;
    // ...
    @GetMapping("/orders/{id}")
    public OrderResponse getOrder(@PathVariable Long id) {
        return orderService.getOrder(id);        // 위임이 전부
    }
}

이 메서드를 단위 테스트하려면 OrderService를 대역으로 바꾸고 "대역이 돌려준 값이 그대로 반환되는가"를 확인하게 된다 — 2절의 마지막 사례, 즉 대역 설정을 되읽는 동어반복과 정확히 같은 구조다. 여기서 이 문서의 중심 기준이 나온다:

로직 유무 기준: 테스트 가치의 원천은 계층의 이름이 아니라 로직의 존재다 — 분기(조건에 따라 다른 일), 계산(값의 가공), 변환(형태의 매핑 규칙) 중 하나라도 내가 작성했다면 테스트 후보고, 셋 다 없다면(순수 위임) 단위 테스트 후보가 아니다. 같은 Controller라도 요청 값을 조합·검증하는 분기가 있다면 그 분기는 테스트한다. 기준은 항상 코드의 내용물이지 위치가 아니다.

납득이 되면서도 불안이 남을 것이다 — "그럼 이 통로가 잘못 이어져 있으면(엉뚱한 서비스 호출, 경로 오타) 누가 잡아 주나?" 정당한 질문이고, 답은 "아무도 안 잡는다"가 아니다.

4. 검증 가치는 인접 계층으로 — "안 쓴다"와 "안 지킨다"는 다르다

패스스루의 단위 테스트를 접는 대신, 그 검증 가치는 두 방향의 이웃으로 이동한다.

[상위: 통합·경로 테스트] 요청 → Controller → Service → 저장소 → 응답 ──────── 실제 경로 전체를 한 번에 통과 ──────── 통로가 잘못 이어졌으면 여기서 반드시 발각된다 [인접: 로직 계층의 단위 테스트] Service의 분기·계산 — 검증력이 실제로 사는 곳
  • 아래·옆으로: 통로가 향하는 곳, 즉 로직이 있는 계층(Service의 할인 계산, 도메인 규칙)의 단위 테스트가 검증력의 본진이다. 통로에 쓸 예산을 여기에 쓴다.
  • 위로: 경로 전체를 실제로 관통하는 소수의 통합 테스트("주문 조회 요청 → 200과 주문 응답")가 연결 자체를 검증한다. 통로의 오배선은 개별 대역 테스트로는 오히려 안 잡히고(대역이라 연결이 실제가 아니므로), 실제 경로 통과에서만 잡힌다.

즉 계층별로 같은 밀도의 단위 테스트를 까는 것이 아니라, 로직 계층에 촘촘한 단위 테스트 + 경로에 성긴 통합 테스트라는 분업이 답이다. 그런데 이 분업에는 아직 등장하지 않은 세 번째 참여자가 있다 — 나 대신 이미 검증을 끝내 놓은 쪽, 언어와 프레임워크다.

5. 컨벤션 존중 — 남이 보증하는 것을 재검증하지 않는다

프레임워크의 라우팅이 경로를 핸들러에 연결하는 것, 직렬화 라이브러리가 객체를 JSON으로 바꾸는 것, 컴파일러가 타입을 지키는 것 — 이것들은 그 도구 자신의 테스트 스위트가 이미 보증하는 동작이다. 내 테스트로 "어노테이션을 붙이면 라우팅이 되는가"를 확인하는 것은 프레임워크를 재검증하는 낭비다.

단, 경계선을 정확히 긋자. 보증의 주체가 갈리는 지점이 있다:

구분예테스트?
도구가 보증하는 메커니즘 라우팅 동작 자체·직렬화 엔진·의존성 주입 컨테이너의 주입 동작 안 한다 — 도구의 테스트 소관
내가 작성한 설정·조합 검증 규칙의 조합("금액은 양수 + 필수"), 직렬화 커스텀 규칙, 권한 설정 한다 — 메커니즘은 남의 것이지만 이 조합은 내 로직이다
도구가 생성해 주는 코드 어노테이션·데코레이터가 만들어 주는 접근자·동등성 비교 안 한다 — 2절의 트리비얼로 회귀

이로써 "안 쓸 목록"의 세 축이 모였다: 동어반복(2절), 로직 없는 통로(3절), 남의 보증(5절) — 그리고 각각의 검증 가치가 어디로 가는지(요구사항 검증, 인접 계층, 도구 자신)도 확인했다. 이제 이것을 하나의 판별 절차로 조립한다.

6. 판별 절차 — 세 질문으로 좁힌다

테스트 후보 코드 │ ├─ Q1. 내가 쓴 로직(분기·계산·변환)이 있는가? │ 없음 ──> 단위 테스트 제외 (통로: 4절의 통합 테스트가 커버) │ ├─ Q2. 이 테스트가 실패하는 유일한 경우가 "구현을 일부러 망가뜨림"인가? │ 예 ──> 제외 (동어반복: 요구사항 기준으로 다시 쓰거나 버림) │ └─ Q3. 언어·프레임워크·라이브러리가 이미 보증하는 동작인가? 예 ──> 제외 (컨벤션 존중: 내 "조합"만 남긴다) 세 관문을 통과한 것 = 테스트 예산을 쓸 곳

순서에도 뜻이 있다: Q1이 대상의 성질을, Q2가 테스트의 형태를, Q3가 보증의 주체를 거른다. 셋을 통과한 대상 — 내 분기, 내 계산, 내 조합 — 에 테스트를 집중하면, 같은 테스트 예산으로 훨씬 높은 검증 밀도를 얻는다. 남는 위험은 이 판별 자체를 둘러싼 오해들인데, 자주 만나는 네 가지를 짚는다.

7. 흔히 헷갈리는 지점

① "커버리지를 채우려면 결국 다 테스트해야 하는 것 아닌가"? — 커버리지 수치를 목표로 삼는 순간 트리비얼 테스트가 양산된다: 통로와 접근자를 테스트로 덮으면 수치는 오르지만 검증력은 그대로다(커버리지 지표의 의미와 함정은 J9의 주제). 수치는 테스트 안 된 로직을 찾는 지도로 쓰는 것이지, 채워야 할 할당량이 아니다.

② "테스트를 안 쓰는 건 게으름 아닌가"? — 판별 없이 안 쓰는 것이 게으름이고, 판별 후에 안 쓰는 것은 배분이다. 둘의 차이는 근거의 유무다: "이 계층은 순수 위임이고, 경로는 통합 테스트 X가 커버한다"고 말할 수 있으면 배분이다.

③ "통로였는데 어느새 로직이 스며들었다" — 패스스루 판정은 영구 자격이 아니다. 위임만 하던 메서드에 분기 하나가 추가되는 순간 Q1의 답이 바뀌고, 테스트 의무가 발생한다. 리뷰에서 "이 변경으로 통로가 로직이 되지 않았나"를 묻는 습관이 판정을 최신으로 유지한다.

④ "내부(private) 메서드는 어떻게 테스트하나"? — 질문 자체를 뒤집는 것이 답이다: 내부 메서드는 공개 동작을 통해 간접 검증되는 것이 기본이고, 내부를 직접 테스트하고 싶은 충동이 강하다면 그 내부에 독립된 책임이 자랐다는 신호다 — 꺼내서 공개 단위로 만들면 Q1~Q3를 정상적으로 통과시킬 수 있다.

★ 8. 언어별 대조

같은 원리지만, 언어마다 "언어·도구가 대신 보증해 주는 범위"(Q3의 크기)가 다르다 — 그래서 "테스트하지 않아도 되는 목록"의 길이가 언어마다 다르다.

언어언어·도구가 이미 보증하는 것(Q3 제외 대상)테스트 예산이 실제로 가야 할 곳
Java 타입·null 어노테이션 계약, 코드 생성 라이브러리의 접근자·동등성, 프레임워크 와이어링 도메인 분기·계산, 내가 조합한 검증·설정(슬라이스 테스트 영역)
JS·TS TS 도입 시 타입 오류 검출(컴파일러로 이관), 프레임워크의 렌더링 메커니즘 상태 가공·분기 로직, 조건부 렌더링의 분기
Python 표준 데코레이터·라이브러리가 생성하는 메서드, (정적 검사기 도입 시) 타입 계약 내 로직 + 실행돼야 발각되는 경로의 커버
C++ 컴파일 타임에 판정되는 타입·상수 계약 전부 — 보증 범위가 가장 넓은 축 런타임 로직·경계값, 미정의 동작 주변

8.1 C++ — 컴파일 타임이 테스트의 절반을 대신하는 언어

C++은 Q3의 목록이 가장 긴 언어다. 정적 타입 검사에 더해, static_assert(조건을 컴파일 시점에 검사해 실패하면 컴파일 자체를 중단시키는 선언)로 타입·상수 수준의 계약을 빌드 단계에서 판정할 수 있다 — 이런 계약은 런타임 테스트로 재확인할 대상이 아니다. 

// 타입 계약: 컴파일 타임 검사가 담당 — 런타임 테스트로 되풀이하지 않는다
static_assert(std::is_copy_constructible<Order>::value,
              "Order는 값 복사 가능해야 한다");

constexpr int max_items_per_order = 50;
static_assert(max_items_per_order > 0, "상한은 양수");   // 상수 계약도 빌드가 판정

// 반면 이 함수의 "경계에서의 동작"은 내 로직 — 런타임 테스트 대상이다
int clamp_quantity(int q) { return q < 1 ? 1 : (q > max_items_per_order ? max_items_per_order : q); }

C++ 관점의 통찰: 템플릿 코드는 인스턴스화(구체 타입을 넣어 실제 코드가 생성되는 일) 자체가 컴파일 타임 검사를 한 번 통과하는 것이므로, 테스트에서 대표 타입 몇 개로 인스턴스화해 보는 것만으로도 상당한 검증이 된다. 주의할 반대편도 있다 — 미정의 동작(표준이 결과를 정의하지 않아 무슨 일이든 일어날 수 있는 코드 영역)은 "테스트가 통과했다"가 "올바르다"를 보증하지 않는 예외 지대라서, 이 언어에서는 테스트 통과를 과신하지 않는 감각과 정적 분석·새니타이저의 병행이 테스트 대상 선정만큼 중요하다.

8.2 Python — 보증이 얇은 만큼, "무엇을 안 쓸지"가 더 정교해야 하는 언어

동적 언어인 Python은 기본 상태에서 컴파일러 보증이 얇다 — 타입 오류조차 실행돼야 발각되므로(K5에서 본 지연 발각), 테스트가 "경로를 실행해 보는 것" 자체의 가치를 겸한다. 그래서 순서가 중요하다: 타입 힌트 + 정적 검사기를 먼저 도입해 타입 계약을 도구로 이관하면, 테스트는 로직 검증이라는 본업에 집중할 수 있다. 이관 없이 테스트로 타입까지 커버하려 들면 예산이 남아나지 않는다. 

from dataclasses import dataclass

@dataclass
class Order:
    id: int
    amount: int
# __init__·__eq__·__repr__는 dataclass가 생성 — 표준 라이브러리 보증분, 테스트 제외(Q3)

def apply_discount(order: Order, rate: float) -> Order:      # 타입 계약은 정적 검사기로 이관
    return Order(order.id, int(order.amount * (1 - rate)))   # 이 계산이 내 로직

def test_discount_applied():                  # 테스트는 요구사항만 검증한다
    assert apply_discount(Order(1, 10000), rate=0.1).amount == 9000

Python 관점의 통찰: 덕 타이핑 환경에서는 "인터페이스 구현 여부" 같은 형식 계약을 테스트할 방법 자체가 마땅치 않았는데, 타입 힌트와 정적 검사기의 정착으로 그 몫이 도구로 넘어갔다 — Q3 목록이 언어 진화에 따라 길어진 사례다. 남는 고유 과제는 커버리지의 의미 차이다: 정적 보증이 얇은 언어에서 "실행된 적 없는 경로"는 타입 오탈자까지 품고 있을 수 있으므로, 같은 커버리지 수치라도 로직 경로의 실행 여부가 갖는 무게가 정적 언어보다 무겁다.

8.3 Java / JS·TS — 한 줄 요약

Java에서 "안 쓸 목록"의 고전은 접근자·코드 생성 라이브러리 산출물·프레임워크 와이어링이고, 예산이 갈 곳은 도메인 로직과 내가 조합한 설정이다 — 프레임워크의 특정 층만 띄워 내 검증 규칙·직렬화 규칙의 조합을 확인하는 슬라이스 테스트가 "메커니즘은 남의 것, 조합은 내 것"이라는 5절 경계선의 제도화된 형태다. JS·TS에서는 TS 도입이 타입 오류 검증을 컴파일러로 이관하는 분수령이고, 컴포넌트 테스트의 판별도 로직 유무 기준 그대로다 — prop을 받은 그대로 뿌리는 표시용 컴포넌트는 통로이므로 제외, 조건부 렌더링·이벤트 처리 분기가 생기면 승격. 렌더 결과 전체를 저장해 두고 다음 실행과 비교하는 스냅샷 테스트의 남용은 "구현의 복사"를 자동화한 트리비얼 테스트가 되기 쉬워, 2절의 판별 질문("무엇이 틀렸을 때 실패하는가")을 그대로 들이대 볼 대상이다.

9. 함께 알면 좋은 것

본문의 판별 축들을 실무 어휘로 확장한 것들이다 — 첫째는 4절의 분업 구도를, 둘째는 7-①을, 셋째는 2절의 판별 질문을, 넷째·다섯째는 테스트 자체의 품질 관리를 잇는다.

  • 테스트 피라미드 — "로직 계층에 촘촘한 단위 + 경로에 성긴 통합"(4절)을 일반화한 고전 모형: 아래(단위)가 넓고 위(통합·E2E)가 좁은 배분이 비용 대비 검증력의 균형점이라는 주장. 프론트 중심에서는 변형 모형도 논의된다.
  • 커버리지 지표의 함정 — 라인/분기 커버리지의 의미 차이와 "100% 신화"에 대한 검토(J9의 주제). 수치를 지도로 쓰는 법과 할당량으로 쓸 때의 부작용.
  • 뮤테이션 테스트(mutation testing) — 코드를 일부러 조금씩 변형(변이)시켜 테스트가 그 변이를 잡아내는지로 테스트의 검증력 자체를 측정하는 기법. 동어반복 테스트는 변이를 하나도 못 잡는 것으로 정량 발각된다 — 2절의 판별 질문을 자동화한 도구.
  • 테스트 냄새(test smell) — 취약한 테스트(리팩토링마다 깨짐), 느린 테스트, 서로 의존하는 테스트 등 테스트 코드의 품질 문제 어휘. "테스트도 유지보수 대상 코드"라는 1절 전제의 실무 목록판.
  • 계약 테스트 — 서로 다른 시스템(프론트↔백엔드) 경계의 기대를 명문화해 검증하는 접근. 단위로도 통합으로도 애매한 "경계의 약속"을 담당하는 제3의 층위.

10. 한 장 요약

  • 테스트는 자산이자 부채 — 검증력 없는 테스트는 초록불 착시까지 만드는 음수 자산이다.
  • 안 쓸 목록의 세 축: 동어반복(구현의 복사 — "무엇이 틀렸을 때 실패하는가"로 판별), 로직 없는 통로(분기·계산·변환 부재), 남의 보증(언어·프레임워크·라이브러리 소관).
  • 통로의 검증 가치는 소멸하지 않고 인접 계층으로 이동한다: 로직 계층의 촘촘한 단위 테스트 + 경로를 실제로 관통하는 성긴 통합 테스트의 분업.
  • 컨벤션 존중의 경계선: 메커니즘(남의 것)은 제외, 내가 만든 조합·설정은 포함.
  • 판별 3문: 내 로직이 있는가 → 구현의 복사인가 → 남이 이미 보증하는가. 판정은 영구가 아니다 — 통로에 분기가 스며드는 순간 재판정.
  • 언어가 보증하는 범위(Q3)는 언어마다 다르다: 정적 언어일수록 "안 쓸 목록"이 길고, 동적 언어는 타입 계약을 도구로 이관한 뒤에야 같은 배분이 성립한다.

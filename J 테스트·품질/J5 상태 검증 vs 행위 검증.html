J5 상태 검증 vs 행위 검증

0. 한눈에 보는 결론

  • 테스트가 "맞다"고 판정하는 방법은 둘뿐이다. 상태 검증(state verification)은 실행 후 남은 결과(반환값·객체 상태·저장된 데이터)를 묻고, 행위 검증(behavior verification)은 실행 중 협력자를 어떻게 불렀는지(어떤 메서드를, 어떤 인자로, 몇 번)를 묻는다.
  • 둘은 검증하는 대상의 층위가 다르다. 상태 검증은 요구사항("할인 후 9,000원")에, 행위 검증은 구현 방식("저장소의 findById를 한 번 호출")에 묶인다. 요구사항은 구현보다 오래 산다.
  • 그래서 행위 검증이 과하면 구현 결합이 생긴다 — 요구사항은 그대로인데 내부 호출 순서·횟수·협력자 구성을 바꾸는 리팩토링만으로 테스트가 깨진다. 이런 테스트는 안전망이 아니라 리팩토링을 막는 족쇄가 된다.
  • 선택 기준은 하나로 압축된다: 관측 가능한 결과가 있으면 상태 검증을 우선한다. 행위 검증은 결과가 협력자 밖으로 새어 나가 관측할 수 없는 경우(알림 발송·외부 시스템 호출 같은 부수효과)에만 쓴다.
  • 행위 검증을 쓸 때도 "무엇을 요청했는가"만 고정하고 "어떻게 도달했는가"(호출 순서·부수 호출 유무)는 열어 둔다. 호출 세부를 전부 못 박는 과잉 명세(over-specification)가 결합의 주범이다.
  • 정리하면 질문은 이것이다 — "이 테스트는 요구사항이 바뀌었을 때 깨지는가, 구현이 바뀌었을 때 깨지는가?" 후자라면 검증 방식을 다시 고른다.

1. 전제 — 테스트가 "맞다"고 말하는 두 가지 방법

단위 테스트는 대상 코드를 실행한 뒤 "기대와 같다"고 판정하는 코드다. 여기서 무엇을 기대와 비교하느냐가 이 문서의 전부다. 비교할 수 있는 것은 두 종류뿐이다 — 실행이 남긴 것과 실행이 한 일.

문서 전체에서 하나의 예제를 쓴다. 주문 서비스가 (a) 할인 규칙을 적용해 최종 금액을 계산하고, (b) 주문이 확정되면 고객에게 알림을 보낸다고 하자. (a)는 결과가 값으로 남는다. (b)는 값을 남기지 않는다 — 알림 발송기(협력자)를 호출한 사실만 있고, 그 사실은 서비스 밖에서 관측되지 않는다.

[상태 검증] [행위 검증] 실행 → 결과가 남는다 실행 → 협력자가 호출된다 │ │ "최종 금액이 9,000원인가?" "알림 발송기가 '주문 확정'으로 "주문 상태가 CONFIRMED인가?" 정확히 한 번 호출됐는가?" │ │ 묻는 대상 = 결과(what) 묻는 대상 = 과정(how)

두 방식은 대체재가 아니라 서로 다른 것을 묻는 도구다. 상태 검증이 무엇을 보장하고 무엇을 못 보는지부터 확인하자.

2. 상태 검증 — 관측 가능한 결과를 묻는다

상태 검증은 대상 코드를 실행한 뒤 관측 가능한 결과를 기대값과 비교한다. 반환값, 대상 객체의 필드, 협력자 대신 놓아 둔 가짜 저장소(fake)에 남은 데이터가 모두 "결과"다. J1에서 본 대역 중 스텁(정해진 값을 돌려주기만 하는 대역)과 페이크(단순화된 실제 구현)가 이 방식의 동반자다 — 둘 다 "무엇이 불렸는지"를 기록하지 않고, 결과가 나오게만 돕는다. 

// 대상: 할인 적용 — 결과가 값으로 남는다
@Test
void 회원_등급이_GOLD면_10퍼센트_할인된다() {
    OrderRepository repo = new InMemoryOrderRepository();          // 페이크
    repo.save(new Order(1L, 10_000, Grade.GOLD));
    OrderService service = new OrderService(repo);

    int total = service.finalPrice(1L);

    assertEquals(9_000, total);                                     // 결과만 묻는다
}

이 테스트가 모르는 것에 주목하자. finalPrice가 저장소를 한 번 조회했는지 두 번 조회했는지, 내부에서 할인 계산기를 별도 객체로 분리했는지, 캐시를 거쳤는지 — 전혀 모른다. 모른다는 것이 장점이다. 테스트가 아는 것은 "GOLD 회원의 만 원 주문은 9,000원"이라는 요구사항뿐이고, 그 요구사항이 유지되는 한 내부를 아무리 재구성해도 테스트는 초록이다.

상태 검증이 구현에 둔감한 이유: 테스트가 결합하는 상대가 공개 계약(입력 → 관측 가능한 출력)이지 내부 협력 구조가 아니기 때문이다. 계약은 리팩토링에서 보존되는 것이고, 협력 구조는 리팩토링이 바꾸는 것이다. 테스트를 전자에 묶으면 리팩토링의 안전망이 되고, 후자에 묶으면 리팩토링의 장애물이 된다.

그런데 1절의 (b), 알림 발송은 이 방식으로 검증할 수 없다. 반환값도 없고, 서비스의 필드도 변하지 않으며, 알림은 프로세스 밖으로 나가 버린다. 관측할 결과가 없을 때 테스트는 무엇을 물어야 하는가.

3. 행위 검증 — 협력자 호출을 묻는다

행위 검증은 실행 중 대상 코드가 협력자에게 무엇을 요청했는지를 기대와 비교한다. 이를 위해 협력자 자리에 호출을 기록하는 대역 — J1의 목(mock) 또는 스파이 — 을 놓고, 실행 후 기록을 조회한다. 

// 대상: 주문 확정 시 알림 — 결과가 서비스 밖으로 나가 버린다
@Test
void 주문을_확정하면_고객에게_확정_알림을_보낸다() {
    Notifier notifier = mock(Notifier.class);                     // 호출을 기록하는 대역
    OrderService service = new OrderService(repo, notifier);

    service.confirm(1L);

    verify(notifier).send(1L, "주문 확정");                       // "무엇을 요청했는가"만 고정
}

여기서는 행위 검증이 유일한 선택지다. "알림이 갔다"는 사실이 서비스의 상태 어디에도 남지 않으므로, 협력자를 올바르게 불렀는가가 곧 요구사항이다. 즉 행위 검증의 정당한 영역은 "협력자 호출 자체가 요구사항의 일부인 경우"다 — 알림 발송, 외부 결제 요청, 감사 로그 기록처럼 호출이 곧 효과인 상호작용.

문제는 같은 도구가 요구사항이 아닌 것까지 얼마든지 고정할 수 있다는 점이다. verify는 알림 발송기에도, 저장소에도, 할인 계산기에도 똑같이 붙는다. 2절의 할인 테스트를 행위 검증으로 다시 쓰면 무슨 일이 생기는지가 다음 절, 이 문서의 중심이다.

4. 함정 — 행위 검증 과잉과 구현 결합

2절의 할인 테스트를 목으로 다시 쓰면 이렇게 된다. 

// 같은 요구사항("GOLD 만 원 → 9,000원")을 행위 검증으로 — 흔한 안티패턴
@Test
void 할인_행위검증_버전() {
    OrderRepository repo = mock(OrderRepository.class);
    DiscountPolicy policy = mock(DiscountPolicy.class);
    when(repo.findById(1L)).thenReturn(new Order(1L, 10_000, Grade.GOLD));
    when(policy.rateFor(Grade.GOLD)).thenReturn(0.10);
    OrderService service = new OrderService(repo, policy);

    service.finalPrice(1L);

    verify(repo, times(1)).findById(1L);            // 저장소를 정확히 한 번 조회했는가
    verify(policy).rateFor(Grade.GOLD);             // 정책 객체에 등급을 넘겼는가
    verifyNoMoreInteractions(repo, policy);         // 그 외에는 아무것도 하지 않았는가
}

이 테스트는 통과한다. 그리고 다음 변경들 각각에서 요구사항이 그대로인데도 깨진다:

리팩토링(요구사항 불변)깨지는 검증왜
조회 결과를 메서드 안에서 두 번 쓰느라 findById를 두 번 호출 times(1) 호출 횟수는 요구사항이 아니라 구현 세부다
할인율 계산을 정책 객체 대신 Order의 메서드로 이동 verify(policy) 어느 객체가 계산하는지는 설계 선택이지 계약이 아니다
로깅·지표 수집을 위해 저장소의 다른 메서드를 추가 호출 verifyNoMoreInteractions "그 외에는 하지 말 것"은 미래의 모든 변경을 금지한다

더 나쁜 것은 이 테스트가 정작 요구사항은 검증하지 않는다는 점이다. 9,000원이라는 숫자가 어디에도 없다. finalPrice가 할인율을 곱하는 대신 더해서 11,000원을 돌려줘도 세 verify는 모두 통과한다. 협력자를 어떻게 불렀는지는 완벽히 고정했는데, 그 호출로 무엇을 만들어 냈는지는 묻지 않은 것이다.

구현 결합의 정체: 행위 검증 과잉 테스트는 구현의 호출 그래프를 테스트 코드에 복사한 것이다. 구현이 "A를 부르고 B를 부른다"이면 테스트도 "A가 불렸고 B가 불렸다"를 확인한다 — J10의 동어반복 테스트가 협력자 차원으로 확장된 형태다. 이런 테스트는 두 가지를 동시에 잃는다: 요구사항 위반을 잡지 못하고(검증력 상실), 요구사항을 보존하는 변경을 막는다(리팩토링 취약). 관통 질문 — "구현을 바꿨을 때 깨지는가, 요구사항을 바꿨을 때 깨지는가?" — 에 "구현"이라고 답하는 테스트가 여기에 해당한다.

그렇다면 3절의 알림 테스트도 같은 함정인가? 아니다 — 그 테스트에서 "알림 발송기를 이 인자로 불렀다"는 구현 세부가 아니라 요구사항 자체였다. 두 테스트의 차이는 도구(verify)가 아니라 고정한 것이 계약인가 구현인가다. 이 차이를 사전에 판정하는 기준이 필요하다.

5. 선택 기준 — 관측 가능한 결과가 있으면 상태 우선

4절의 결론을 뒤집으면 기준이 나온다. 테스트가 결합해야 할 상대는 계약이고, 계약은 "입력 → 관측 가능한 결과"로 표현되므로, 관측 가능한 결과가 존재하는 한 그것을 물어야 한다. 행위 검증은 결과가 존재하지 않을 때의 대체 수단이다.

검증하려는 요구사항 │ ├─ Q1. 실행 후 관측 가능한 결과가 있는가? │ (반환값 · 대상 객체 상태 · 페이크 저장소에 남은 데이터) │ 예 ──> 상태 검증. 협력자는 스텁·페이크로 대체하고 verify는 쓰지 않는다 │ └─ Q2. 없다 — 효과가 협력자 밖으로 나가 버리는가? (알림 발송 · 외부 시스템 호출 · 이벤트 발행 · 감사 기록) 예 ──> 행위 검증. 단, "무엇을 요청했는가"(대상·핵심 인자)만 고정하고 횟수·순서·부수 호출은 요구사항일 때만 추가한다

이 기준은 협력자의 성격 분류와도 겹친다. 값을 돌려주는 협력자(조회, 계산, 정책 판단)는 그 값이 대상 코드의 결과에 반영되므로 결과를 검증하면 호출은 자동으로 검증된다 — 저장소가 조회되지 않았다면 9,000원이 나올 수 없다. 반면 값을 돌려주지 않고 일을 시키는 협력자(발송, 기록, 전송)는 결과에 흔적을 남기지 않으므로 호출 자체를 봐야 한다.

상태 우선의 실질적 의미: "목을 쓰지 말라"가 아니다. 반환값이 있는 협력자에는 verify를 붙이지 말라다. 스텁으로 값을 주입한 협력자를 다시 verify하는 것은 이미 결과로 검증된 사실을 구현 세부로 한 번 더 못 박는 중복이며, 그 중복이 4절의 결합을 만든다. Mockito 문서조차 "스텁한 호출의 verify는 보통 중복"이라고 명시한다 — 결과가 그 값에 의존한다면 호출이 없었을 때 이미 다른 곳에서 깨진다.

Q2에 해당하는 행위 검증에서도 결합을 줄이는 방향은 같다. 인자 전체를 정확히 맞추는 대신 요구사항에 해당하는 인자만 고정하고 나머지는 "아무 값"으로 열어 두거나, 협력자에 넘어간 객체를 붙잡아 그 상태를 검증하는 식으로 행위 검증을 상태 검증으로 되돌린다 — 이 기법(인자 매처와 캡터)은 J4의 주제다. 또 하나의 선택지는 목 대신 페이크다: 알림 발송기를 "보낸 알림 목록을 쌓아 두는 가짜"로 만들면 verify 없이 목록의 내용을 상태로 검증할 수 있다.

기준이 단순한 만큼 경계에서 오해가 잦다. 자주 부딪히는 네 가지를 짚는다.

6. 흔히 헷갈리는 지점

① "목을 썼으니 행위 검증이다"? — 도구와 검증 방식은 별개다. 목 라이브러리로 만든 객체를 스텁으로만 쓰고(when…thenReturn) verify를 붙이지 않았다면 그 테스트는 상태 검증이다. 반대로 직접 만든 페이크라도 "호출 기록 목록"만 검사한다면 행위 검증이다. 구분 기준은 단언문이 결과를 보는가, 호출을 보는가다.

② "행위 검증은 나쁘다"? — 과잉이 나쁜 것이지 행위 검증이 나쁜 것이 아니다. 알림·외부 호출처럼 호출이 곧 요구사항인 곳에서는 행위 검증이 유일하고 정당한 수단이고, 이를 억지로 상태 검증으로 바꾸려다 협력자 내부를 노출시키면 오히려 설계가 나빠진다.

③ "호출되지 않았음도 검증해야 안전하지 않은가"? — "호출되지 않음"이 요구사항일 때만이다. "취소된 주문에는 알림을 보내지 않는다"는 요구사항이므로 never()가 정당하다. 그러나 "이 협력자 외에는 아무것도 부르지 않는다"(verifyNoMoreInteractions 전면 사용)는 요구사항이 아니라 현재 구현의 스냅샷이며, 4절의 결합을 가장 강하게 만든다.

④ "상태 검증인데도 리팩토링에 깨진다"? — 그렇다면 검증한 "상태"가 공개 계약이 아니라 내부 상태였을 가능성이 크다. 비공개 필드를 리플렉션으로 읽거나, 중간 계산값을 노출하는 접근자를 테스트 때문에 추가했다면, 형식은 상태 검증이어도 실질은 구현 결합이다. 관측 가능성은 "읽을 수 있는가"가 아니라 "계약의 일부인가"로 판단한다.

★ 7. 언어별 대조

원리는 언어 중립이지만, 각 생태계의 테스트 도구는 기본 모드가 상태 쪽인지 행위 쪽인지, 그리고 과잉 명세로 미끄러지기 얼마나 쉬운지가 다르다. 도구의 기본값이 곧 그 언어 테스트의 습관을 만든다.

언어 / 도구상태 검증행위 검증그 도구만의 함정
Java / JUnit 5 + Mockito assertEquals·assertThat, 스텁은 when().thenReturn() verify(mock, times(n))·never()·verifyNoMoreInteractions 스텁과 verify가 같은 객체에 공존해 "스텁한 것을 다시 verify"하는 중복이 관성적으로 생긴다
JS·TS / Jest · Vitest expect(x).toBe/toEqual jest.fn()/vi.fn() + toHaveBeenCalledWith·toHaveBeenCalledTimes 모듈 단위 목킹이 쉬워 "어느 모듈의 어느 함수를 불렀는가"라는 모듈 구조 자체에 결합된다
Python / pytest + unittest.mock assert 문 하나로 충분 Mock의 assert_called_once_with·call_args·patch 무엇이든 받아 주는 Mock이 검증 메서드의 오타·부재를 조용히 삼킨다
C++ / GoogleTest + gMock EXPECT_EQ, 스텁은 ON_CALL EXPECT_CALL(...).Times(n), StrictMock EXPECT_CALL이 스텁 겸용으로 쓰이면서 모든 스텁이 행위 검증으로 승격되고, 검증 시점이 소멸자에 묶인다

7.1 Java — JUnit 5 + Mockito: 스텁과 verify의 공존이 만드는 중복

Mockito는 하나의 목 객체에 스텁(when)과 행위 검증(verify)을 함께 붙일 수 있는 구조라, 4절의 "스텁한 것을 다시 verify"하는 패턴이 자연스럽게 나온다. 원리적으로 필요한 것은 반환값 있는 협력자에는 스텁만, 부수효과 협력자에는 verify만이라는 분리다. 

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repo;      // 반환값 있는 협력자 → 스텁만
    @Mock Notifier notifier;         // 부수효과 협력자 → verify만
    @InjectMocks OrderService service;

    @Test
    void 확정하면_금액이_계산되고_알림이_간다() {
        when(repo.findById(1L)).thenReturn(new Order(1L, 10_000, Grade.GOLD));

        int total = service.confirm(1L);

        assertEquals(9_000, total);                          // 상태: 요구사항
        verify(notifier).send(eq(1L), anyString());          // 행위: 대상·핵심 인자만 고정
        // verify(repo).findById(1L) — 쓰지 않는다: total이 맞다면 조회는 이미 증명됐다
    }
}

Mockito 고유의 특이점은 엄격 스텁(strict stubs)이다. JUnit 5용 MockitoExtension은 기본으로 엄격 모드를 적용해, 설정했지만 실행 중 한 번도 쓰이지 않은 스텁을 테스트 실패로 보고한다. 이는 행위 검증이 아니라 테스트 위생 장치지만 효과는 이 문서의 원리와 같은 방향이다 — 결과에 기여하지 않는 스텁은 구현 세부를 테스트에 복사한 흔적이므로 지우라는 신호다. 2020년대 중반 기준 Mockito 5는 인라인 목 메이커(바이트코드를 직접 바꿔 final 클래스·정적 메서드까지 대체하는 방식)를 기본으로 채택했는데, 이는 "목으로 만들 수 있는 것"의 범위를 넓힐 뿐 "verify해야 하는 것"의 범위를 넓히는 것은 아니다 — 정적 메서드를 목으로 만들 수 있게 됐다고 그 호출을 verify하기 시작하면 결합은 더 깊어진다.

7.2 JS·TS — Jest / Vitest: 모듈 목킹이 모듈 구조에 결합시킨다

Vitest는 Jest 호환 API를 목표로 설계돼 jest.fn↔vi.fn, jest.spyOn↔vi.spyOn, 단언 매처(toHaveBeenCalledWith 등)가 거의 그대로 대응한다. 2020년대 중반 기준 신규 프로젝트에서는 Vitest 채택이 늘고 있지만 이 문서의 원리 차원에서 둘의 차이는 없다. JS·TS 생태계만의 함정은 모듈 목킹(jest.mock/vi.mock)이다. 클래스나 인터페이스 없이 모듈 경로 단위로 의존성을 통째로 바꿔치기할 수 있어서, 행위 검증이 "어느 파일에서 가져온 어느 함수를 불렀는가"라는 모듈 구조 자체에 결합된다. 

import { vi, it, expect } from 'vitest';
import { confirmOrder } from './orderService';
import * as notifier from './notifier';

it('주문을 확정하면 확정 알림을 보낸다', () => {
  const send = vi.spyOn(notifier, 'send').mockResolvedValue(undefined);

  const total = confirmOrder({ id: 1, amount: 10000, grade: 'GOLD' });

  expect(total).toBe(9000);                                   // 상태
  expect(send).toHaveBeenCalledWith(1, expect.any(String));  // 행위: 핵심 인자만 고정
});
// send를 './notifier'에서 './messaging/notifier'로 옮기면 요구사항 불변인데 테스트가 깨진다

TS의 구조적 타이핑(이름이 아니라 모양이 같으면 같은 타입으로 취급하는 규칙)은 반대 방향의 도움을 준다 — 협력자와 같은 모양의 페이크 객체를 선언 없이 리터럴로 만들 수 있어서, 5절의 "목 대신 페이크"가 어느 언어보다 싸다. 발송 함수를 인자로 받도록 설계하면 모듈 목킹 없이 { send: (id, msg) => sent.push([id, msg]) }를 넘기고 sent의 내용을 상태로 검증할 수 있다. 한 가지 도구 세부: Vitest의 목은 호출 인자를 참조로 보관하므로, 호출 뒤에 그 객체를 변경하면 toHaveBeenCalledWith가 변경된 값과 비교된다 — 인자 객체를 재사용하는 테스트에서 원인 모를 실패의 흔한 출처다.

7.3 Python — pytest + unittest.mock: 무엇이든 받아 주는 목의 조용한 통과

pytest에서 상태 검증은 assert 한 줄이다 — 단언 재작성으로 실패 시 양변의 값을 풀어 보여주므로 별도 단언 API가 필요 없다. 행위 검증은 표준 라이브러리 unittest.mock의 Mock·patch가 담당하는데, 여기서 이 언어만의 함정이 나온다: Mock은 존재하지 않는 속성 접근을 새 Mock을 만들어 응답한다. 

from unittest.mock import Mock, create_autospec

def test_confirm_sends_notification():
    repo = Mock()
    repo.find_by_id.return_value = Order(1, 10_000, "GOLD")   # 스텁
    notifier = create_autospec(Notifier, spec_set=True)      # 시그니처까지 검사하는 목
    service = OrderService(repo, notifier)

    total = service.confirm(1)

    assert total == 9_000                                     # 상태
    notifier.send.assert_called_once_with(1, "주문 확정")      # 행위

    # 함정: 아래 줄은 오타인데도 조용히 통과한다 —
    # notifier.send.called_once_with(1, "주문 확정")
    # 'assert_' 접두어가 없는 이름은 검증이 아니라 그냥 Mock 속성 접근(항상 참)이다

Python 3.5부터 assert로 시작하는 오타(예: assert_called_wiht)는 AttributeError로 막지만, 접두어 자체를 빠뜨린 이름은 여전히 조용히 통과한다 — 행위 검증이 있는 것처럼 보이는데 실제로는 아무것도 검증하지 않는 조용한 실패(K5의 주제)다. create_autospec·spec_set=True는 실제 클래스의 속성·시그니처 밖의 접근을 막아 이 부류를 잡는다. 또 patch는 이름이 조회되는 모듈 경로를 문자열로 지정하므로, 7.2의 모듈 목킹과 같은 이유로 리팩토링(함수를 다른 모듈로 이동)에 취약하다. 값이 돌아오는 협력자라면 patch 대신 생성자 주입 + 페이크가 상태 검증을 가능하게 하는 첫 단계다.

Python 관점의 통찰: 덕 타이핑(타입 선언이 아니라 "필요한 메서드가 있는가"로 객체를 받아들이는 규칙) 덕분에 페이크는 클래스 한 개로 즉시 만들어지고, 목은 어떤 속성 요청에도 응답하는 만능 객체가 된다 — 언어가 행위 검증을 극단적으로 쉽게 만든 만큼, "쉽다"가 "옳다"로 미끄러지는 것을 막는 규율은 도구가 아니라 작성자 몫이다. 특히 Mock 객체는 진리값 판정에서 항상 참이므로, 검증문이 아닌 표현식이 assert 없이 남아 있어도 인터프리터는 아무 말도 하지 않는다.

7.4 C++ — GoogleTest + gMock: 기대(EXPECT_CALL)가 스텁을 겸하는 구조

gMock의 핵심 특이점은 EXPECT_CALL이 실행 전에 선언하는 "기대"라는 점이다. 반환값을 정하는 WillOnce/WillRepeatedly가 EXPECT_CALL에 붙기 때문에, 스텁을 만들려다 행위 검증까지 함께 선언하게 된다 — WillOnce를 n개 붙이면 Times(n)이 암묵적으로 따라온다. gMock은 이를 위해 ON_CALL(기본 동작만 지정, 호출 여부는 묻지 않음)을 별도로 두며, 공식 지침도 "검증이 목적이 아니면 ON_CALL을 쓰라"고 권한다. 이 문서의 5절 기준이 API 두 개로 구현돼 있는 셈이다. 

class MockRepo : public OrderRepository {
 public:
  MOCK_METHOD(Order, findById, (long id), (override));
};
class MockNotifier : public Notifier {
 public:
  MOCK_METHOD(void, send, (long id, const std::string& msg), (override));
};

TEST(OrderService, ConfirmComputesPriceAndNotifies) {
  testing::NiceMock<MockRepo> repo;            // 관심 없는 호출은 조용히 허용
  MockNotifier notifier;
  ON_CALL(repo, findById(1L))                  // 스텁: 호출 여부를 검증하지 않는다
      .WillByDefault(testing::Return(Order{1L, 10000, Grade::GOLD}));
  EXPECT_CALL(notifier, send(1L, testing::_)); // 행위: 대상·핵심 인자만 고정
  OrderService service(repo, notifier);

  int total = service.confirm(1L);

  EXPECT_EQ(total, 9000);                      // 상태
}   // notifier 소멸 시점에 EXPECT_CALL이 판정된다

두 번째 특이점은 엄격도의 세 단계다. 기본 목(NaggyMock)은 기대에 없는 호출을 경고만 하고, NiceMock은 무시하며, StrictMock은 실패로 처리한다. StrictMock은 verifyNoMoreInteractions를 모든 메서드에 자동 적용한 것과 같으므로 4절의 결합을 기본값으로 켜는 셈이다 — "호출되지 않음"이 요구사항인 협력자에만 한정해서 쓴다.

C++ 관점의 통찰: gMock의 행위 검증은 목 객체의 소멸자에서 실행된다 — 즉 검증 시점이 객체 수명에 묶여 있다. 목을 힙에 만들고 해제하지 않으면 기대가 영원히 판정되지 않아 조용히 통과하고, 반대로 대상 코드가 협력자를 값으로 복사해 가지면 호출이 기록되는 쪽은 복사본이라 원본의 기대는 충족되지 않는다. 대상 코드에 참조·포인터로 넘겨야 하는 이유이자, 필요하면 testing::Mock::VerifyAndClearExpectations로 판정 시점을 명시하는 이유다. 또 MOCK_METHOD는 가상 함수(호출할 구현을 실행 시점의 실제 타입으로 고르는 함수)를 재정의하는 방식이라 협력자는 인터페이스여야 한다 — 값 타입 협력자에는 목을 씌울 수 없고, 그때는 자연스럽게 페이크 + 상태 검증 쪽으로 밀린다.

8. 함께 알면 좋은 것

본문의 축을 확장하는 개념들이다 — 첫째·둘째는 5절의 협력자 분류를, 셋째는 3절의 대역 선택을, 넷째는 4절의 결합 문제를, 다섯째는 5절 끝에 언급한 기법을 잇는다.

  • 명령-조회 분리(command–query separation) — 메서드를 "상태를 바꾸되 값을 돌려주지 않는 명령"과 "값을 돌려주되 상태를 바꾸지 않는 조회"로 나누는 설계 원칙. 5절의 "조회 협력자는 상태 검증, 명령 협력자는 행위 검증"이 이 분류 위에 서 있다 — 둘을 섞은 메서드가 검증 방식 선택을 어렵게 만든다.
  • 고전파와 목 중심파(classical vs mockist) — 단위 테스트에서 협력자를 실제(또는 페이크)로 두고 결과를 보는 흐름과, 협력자를 모두 목으로 바꾸고 상호작용을 보는 흐름의 대비. 이 문서의 "상태 우선"은 고전파 쪽에 가깝지만, 부수효과 경계에서는 두 흐름이 수렴한다.
  • 페이크(fake)의 설계 — 인메모리 저장소·목록에 쌓는 발송기처럼 "행위를 상태로 바꿔 주는" 단순 구현. 3절의 목 대신 쓸 수 있는 대안이며, 여러 테스트가 공유하면 목 설정 코드의 반복도 사라진다(J1의 대역 분류와 이어진다).
  • 취약한 테스트(fragile test)와 테스트 냄새 — 요구사항이 아닌 변경에 깨지는 테스트를 가리키는 테스트 품질 어휘. 4절의 구현 결합이 대표 원인이며, 리팩토링 때마다 테스트를 "고치는" 빈도가 이 냄새의 측정치다.
  • 인자 매처와 캡터 — 행위 검증에서 인자 전체가 아니라 요구사항에 해당하는 부분만 고정하거나, 협력자에 넘어간 객체를 붙잡아 상태로 검증하는 기법. 5절 끝의 "행위 검증을 상태 검증으로 되돌리기"의 구체적 도구(J4의 주제).

9. 한 장 요약

  • 상태 검증은 결과(반환값·상태·페이크에 남은 데이터)를, 행위 검증은 협력자 호출(대상·인자·횟수)을 묻는다. 전자는 요구사항에, 후자는 구현 방식에 결합된다.
  • 행위 검증 과잉은 구현의 호출 그래프를 테스트에 복사한 것 — 요구사항 위반은 못 잡고, 요구사항을 보존하는 리팩토링은 깨뜨린다.
  • 선택 기준: 관측 가능한 결과가 있으면 상태 검증. 반환값 있는 협력자는 스텁·페이크로만 대체하고 verify를 붙이지 않는다 — 결과가 맞으면 호출은 이미 증명됐다.
  • 행위 검증은 효과가 협력자 밖으로 나가는 부수효과(알림·외부 호출·이벤트)에만. 그때도 "무엇을 요청했는가"만 고정하고 횟수·순서·"그 외 없음"은 요구사항일 때만 추가한다.
  • 판별 질문 하나: "이 테스트는 구현이 바뀔 때 깨지는가, 요구사항이 바뀔 때 깨지는가?"
  • 도구의 기본값이 습관을 만든다: Mockito는 스텁과 verify의 공존, JS·Python은 모듈 경로 목킹, gMock은 EXPECT_CALL의 스텁 겸용 — 각각 과잉 명세로 미끄러지는 고유한 경사가 있다.

J14 테스트 케이스 설계 관점

0. 한눈에 보는 결론

  • 테스트 케이스 설계는 "케이스를 몇 개 쓸까"가 아니라 "이 함수는 어떤 축으로 실패할 수 있나"라는 한 질문에 답하는 일이다. 이 문서의 8관점(정상·경계·동등분할·오류·멱등·순서의존·상태전이·부분실패)은 체크리스트가 아니라 그 한 질문의 여덟 가지 답이다.
  • 여덟 답은 다섯 축으로 묶인다: 입력 공간(정상·동등분할·경계), 입력 밖(오류), 반복과 순서(멱등·순서의존), 시간(상태전이), 부분(부분실패). 함수마다 성립하는 축이 다르므로, 여덟을 다 쓰는 게 아니라 성립하는 축만 고른다.
  • 동등 분할(equivalence partitioning)은 입력 영역을 "같은 방식으로 처리된다고 가정할 수 있는" 등가 클래스로 나눠 클래스당 대표값 하나를 고르는 기법이고, 경계값 분석(boundary value analysis)은 그 클래스 경계의 양쪽 값을 짝으로 고르는 기법이다. 둘은 별개가 아니라 전자가 후자의 전제다.
  • 라인·분기 커버리지는 입력 공간 축만 간접적으로 잰다. 멱등·순서의존·상태전이·부분실패는 같은 코드 줄을 통과하면서도 실패하므로, 케이스 설계 없이 커버리지만 올리면 이 네 축이 통째로 비어 있어도 100%가 나온다.
  • 이 문서는 3부작의 가운데다: 무엇을 테스트하지 않을지(J10, 대상 선정) → 무엇을 테스트할지(이 문서, 케이스 설계) → 얼마나 됐는지(J9, 커버리지 측정). 관점끼리 교차할 때 생기는 조합 폭발은 J16의 소관이다.

1. 전제 — 대상은 골랐다, 이제 케이스다

J10의 판별 3문(내 로직이 있는가 → 구현의 복사인가 → 남이 보증하는가)을 통과한 대상이 손에 있다고 하자 — 이를테면 주문의 수량과 쿠폰으로 할인율을 계산하는 함수, 주문 상태를 바꾸는 메서드, 주문을 확정하며 재고를 잡고 알림을 보내는 절차. "테스트한다"고 결정한 뒤에 곧바로 부딪히는 질문은 "그래서 케이스를 무엇으로 쓰나"다. 정상 입력 하나로 초록불을 보고 끝내는 테스트가 흔한데, 이런 테스트는 J10의 판별 질문("무엇이 틀렸을 때 실패하는가")에 "정상 경로가 통째로 망가졌을 때"라고밖에 답하지 못한다.

J10 무엇을 테스트하지 않을지 → 대상 선정 (어디에 예산을 쓰나) J14 무엇을 테스트할지 → 케이스 설계 (그 대상이 어떤 축으로 실패하나) ← 이 문서 J9 얼마나 됐는지 → 커버리지 측정 (설계한 케이스가 코드를 얼마나 밟았나)

세 문서의 순서에는 뜻이 있다. 대상을 고르지 않고 케이스를 설계하면 통로와 접근자에 정성 들인 케이스를 쓰게 되고, 케이스를 설계하지 않고 커버리지를 재면 "밟은 줄"만 세게 된다. 그래서 이 문서의 관통 질문은 하나다 — "이 함수는 어떤 축으로 실패할 수 있나?" 여덟 관점은 이 질문에 대한 여덟 답이고, 각 답은 함수의 서로 다른 단면에서 결함을 찾는다. 가장 먼저 떠오르는 답은 "입력이 이상하면"이다 — 그 축부터 정확히 세운다.

2. 입력 공간의 축 — 정상·동등 분할·경계값

수량이 1~50인 주문에서 10개 이상이면 10% 할인이라는 규칙을 계산하는 함수 rateFor(quantity)를 생각하자. 입력은 정수 전체이므로 값을 다 넣어볼 수는 없다. 그렇다면 어떤 값을 넣어봐야 "전부 넣어본 것과 비슷한" 확신을 얻는가 — 이것이 고전적 두 기법의 출발점이다.

동등 분할은 입력 영역을 등가 클래스(equivalence class)로 나눈다. 등가 클래스란 프로그램이 그 안의 모든 값을 같은 방식으로 처리한다고 합리적으로 가정할 수 있는 값의 집합이다 — 그러므로 한 값에서 결함이 드러나면 같은 클래스의 다른 값에서도 드러날 것이고, 한 값이 통과하면 나머지도 통과할 것이라고 가정한다. 이 가정 덕에 클래스당 대표값 하나로 클래스 전체를 대신할 수 있다. 클래스는 유효 등가 클래스(규칙이 받아들이는 값)와 무효 등가 클래스(규칙이 거부해야 하는 값)로 갈린다. 고전 규칙 하나가 더 있다: 유효 클래스 여러 개는 한 케이스로 묶어 덮을 수 있지만, 무효 클래스는 케이스 하나에 하나씩 — 두 무효 입력을 한 케이스에 넣으면 먼저 거부된 쪽이 나머지를 가려(마스킹) 두 번째 무효 처리가 검증되지 않기 때문이다. 

// rateFor(quantity)의 입력 영역을 등가 클래스로 나누면
//   무효 1 : quantity < 1          → 거부
//   유효 A : 1 ≤ quantity ≤ 9      → 할인 없음 (0.0)
//   유효 B : 10 ≤ quantity ≤ 50    → 10% 할인 (0.1)
//   무효 2 : quantity > 50         → 거부
// 동등 분할만 쓰면 대표값 4개: 0 / 5 / 20 / 100
// 경계값 분석을 더하면 클래스 경계 양쪽: 0|1 · 9|10 · 50|51  (+ 대표값)

경계값 분석은 동등 분할 위에 얹힌다. 결함은 클래스의 한가운데보다 클래스가 갈리는 경계에 몰린다는 경험 법칙(<를 <=로 잘못 쓰는 하나 차이 오류가 대표)에서, 각 경계에 대해 경계 바로 안쪽 값과 바로 바깥쪽 값을 짝으로 고른다. 수량 규칙이라면 0과 1, 9와 10, 50과 51이다 — 51이 "무효 클래스의 대표"라서가 아니라 50의 짝이라서 고르는 것이다. 경계가 여러 차원(수량·금액·날짜)에 걸치면 차원마다 따로 짝을 세우고, 출력에도 경계가 있다면(할인액 상한 등) 출력 경계에서도 같은 짝을 세운다.

그러면 정상(happy path) 관점은 어디에 있는가 — 유효 등가 클래스의 대표값이 곧 정상 케이스다. 즉 정상 케이스는 8관점 중 하나이되 독립된 기법이 아니라 동등 분할의 유효 쪽 절반이며, 정상 케이스 하나만 쓴 테스트는 클래스 하나만 덮은 동등 분할이다.

입력 공간 축의 정리: 등가 클래스를 먼저 그린다(동등 분할) → 클래스마다 대표값 하나(정상 = 유효 클래스의 대표) → 클래스 경계마다 안쪽·바깥쪽 짝(경계값). 이 순서를 지키면 "케이스를 몇 개 쓸지"가 감이 아니라 클래스와 경계의 개수로 결정된다.

그런데 무효 클래스의 "거부"는 입력값이 규칙 밖일 때의 이야기다. 입력은 멀쩡한데 함수가 기대는 바깥이 무너지면 — 가격 조회 저장소가 예외를 던지거나 응답이 없으면 — 이 함수는 어떻게 실패하는가. 입력 공간 밖의 축이다.

3. 입력 밖의 축 — 오류

앞 절의 무효 클래스는 값이 규칙을 어긴 경우이고, 오류 관점은 값은 규칙 안인데 실행 환경이 약속을 어긴 경우다 — 의존 대상이 예외를 던지거나, 없는 것을 돌려주거나(null·빈 값), 시간을 넘긴다. 둘을 구분하는 이유는 케이스를 만드는 방법이 다르기 때문이다: 무효 클래스는 인자만 바꾸면 되지만, 오류 조건은 의존 대상을 대역으로 바꿔 실패를 주입해야 만들어진다(대역의 종류와 주입 방법은 J1의 주제).

오류 관점의 케이스는 "예외가 던져지는가" 하나로 끝나지 않는다. 함수가 오류를 어떻게 보고하는가에 따라 검증할 것이 세 갈래로 갈린다:

함수의 오류 보고 방식케이스가 확인해야 할 것놓치면 생기는 일
예외로 전파기대한 종류의 예외인가, 원인 정보가 보존되는가아무 예외나 통과시키면 다른 결함이 같은 케이스에 숨는다
결과값으로 보고(실패 객체·오류 코드)호출자가 실패를 구분할 수 있는 값인가성공값과 구분되지 않는 기본값(0·빈 목록)이 돌아오는 조용한 실패
삼키고 계속삼키는 것이 명세인가, 삼킨 뒤 상태가 일관적인가로그만 남기고 진행하는 코드가 "정상 통과"로 보인다

세 번째 줄이 오류 축의 함정이다. 오류를 잡아서 기본값을 돌려주는 코드는 오류 케이스에서도 초록불을 낸다 — 케이스가 "예외가 안 났다"만 확인하면 조용한 실패(K5의 주제)를 테스트가 승인하는 셈이 된다. 그래서 오류 케이스의 단언은 "실패가 호출자에게 보이는 형태로 보고되는가"까지 가야 한다.

여기까지의 세 관점(정상·경계·동등분할)과 오류는 모두 한 번 호출의 결과를 본다. 그러나 함수는 한 번만 호출되지 않는다 — 같은 요청이 두 번 오거나, 두 함수가 순서를 바꿔 호출되면 무슨 일이 생기는가.

4. 반복과 순서의 축 — 멱등·순서 의존

멱등(idempotence)은 같은 연산을 여러 번 적용한 결과가 한 번 적용한 결과와 같다는 성질이다. 값 함수라면 f(f(x)) = f(x)이고, 부작용이 있는 연산이라면 "같은 요청을 두 번 처리해도 상태와 부작용이 한 번 처리한 것과 같다"는 뜻이다. 결제 확인 통지가 네트워크 재전송으로 두 번 도착하거나, 사용자가 취소 버튼을 두 번 누르는 상황이 이 축을 요구한다 — 재시도가 있는 곳에는 반드시 멱등이 요구된다.

멱등 케이스의 형태는 단순하다: 두 번 호출하고, 상태는 한 번 호출과 같은지, 부작용 횟수는 1인지 확인한다. 두 번째 확인이 핵심이다 — 상태는 같아 보여도(두 번 취소해도 상태는 "취소됨") 환불이 두 번 나갔다면 멱등이 아니다. 부작용 횟수는 반환값에 드러나지 않으므로 이 케이스에는 호출을 기록하는 대역이 필요하다. 

// 멱등 케이스의 뼈대 (언어 중립 의사코드)
order = paidOrder(id = 1)
refunds = recordingDouble()          // 호출 횟수를 기록하는 대역

order.cancel(refunds)
order.cancel(refunds)                // 두 번째 호출: 예외도, 추가 환불도 없어야 한다

assert order.status == CANCELLED
assert refunds.callCount(refund, id = 1) == 1   // 상태만 보면 놓치는 부분

순서 의존은 반대 방향의 질문이다 — 두 연산의 적용 순서가 결과를 바꾸는가. 정액 쿠폰 1,000원과 비율 할인 10%는 순서에 따라 총액이 달라진다(10,000원에서 쿠폰 후 할인은 8,100원, 할인 후 쿠폰은 8,000원). 순서가 결과를 바꾸는 연산이라면 명세가 순서를 정해야 하고, 케이스는 정해진 순서의 결과와 뒤집힌 순서의 결과가 다름을 함께 보여야 한다 — 한쪽만 확인하면 구현이 순서를 뒤집어도 잡히지 않는다. 반대로 순서가 결과를 바꾸지 않아야 하는 연산(가환성)이라면 뒤집어도 같음을 확인하는 케이스가 그 성질을 지킨다.

멱등과 순서 의존은 "같은 연산의 반복"과 "다른 연산의 순서"라는 두 방향에서 호출의 이력을 본다. 이력을 더 밀고 가면 함수가 아니라 객체의 이력이 된다 — 지금 상태가 무엇이냐에 따라 같은 호출의 결과가 달라지는 대상이다.

5. 시간의 축 — 상태 전이

주문 상태를 바꾸는 cancel()은 앞 절의 멱등 케이스에서 이미 상태에 의존하고 있었다 — "결제됨" 상태에서의 취소와 "배송됨" 상태에서의 취소는 다른 결과여야 한다. 이런 대상은 상태 기계(state machine), 즉 유한한 상태와 상태 사이의 허용된 전이로 명세된다.

생성됨 ──결제──> 결제됨 ──출고──> 배송중 ──도착──> 배송완료 │ │ └──취소──> 취소됨 <──취소──┘ (배송중 이후의 취소는 금지 전이)

상태 전이 관점의 케이스는 전이표에서 나온다: 행은 현재 상태, 열은 이벤트, 칸은 "다음 상태" 또는 "금지". 허용 전이는 앞 절까지의 방식으로 검증되지만(전이 후 상태 확인), 이 축이 새로 추가하는 것은 금지 전이 케이스다 — 배송중에 취소하면 상태가 바뀌지 않고 거부되는가. 흔히 허용 전이만 테스트하고 금지 칸은 비워 두는데, 상태 기계의 결함은 대부분 금지 칸에서 나온다(허용되지 않아야 할 전이가 조용히 허용됨).

현재 \ 이벤트결제출고취소
생성됨결제됨금지취소됨
결제됨금지(멱등 후보: 재통지)배송중취소됨(+환불)
배송중금지금지금지
취소됨금지금지취소됨(멱등)

표에 앞 절이 되돌아온 것이 보인다 — 같은 이벤트가 같은 상태에 다시 오는 대각선 칸이 멱등 케이스다. 두 축은 겹치는 것이 아니라 하나의 표에서 서로 다른 칸을 담당한다. 전이 하나가 원자적이라면 여기서 끝이지만, 전이 하나가 여러 단계(재고 차감·결제·알림)로 이루어진다면 "전이의 중간"이라는 새로운 실패 지점이 생긴다.

6. 부분의 축 — 부분 실패

주문 확정이 "재고를 잡고 → 결제하고 → 알림을 보내는" 절차라면, 앞 절의 오류 관점은 각 단계가 실패할 수 있다고 말해 준다. 부분 실패 관점은 한 걸음 더 간다: 앞 단계는 성공했는데 뒤 단계가 실패하면 이미 성공한 단계는 어떻게 되는가. 재고는 잡혔는데 결제가 실패하면 재고가 묶인 채 남는가, 결제까지 됐는데 알림만 실패하면 주문은 확정인가.

이 질문에 대한 답은 구현이 아니라 명세의 결정이고, 케이스는 그 결정을 고정한다. 결정은 대체로 세 가지 중 하나다:

  • 전부 아니면 전무(원자성): 뒤 단계가 실패하면 앞 단계를 되돌린다(보상). 케이스 — k번째 단계에 실패를 주입하고, 1~k-1단계의 효과가 취소되었는지 확인.
  • 부분 성공 허용 + 보고: 실패한 부분을 결과에 담아 돌려준다. 케이스 — 여러 수신자 중 하나의 알림만 실패시키고, 나머지는 발송되었으며 실패 목록에 그 하나가 담기는지 확인.
  • 지연 완결: 실패한 단계를 재시도 대기열에 넣고 진행한다. 케이스 — 실패가 대기열에 기록되었는지, 이후 재시도가 4절의 멱등을 만족하는지 확인.

케이스를 만드는 방법은 오류 축과 같지만(대역으로 실패 주입) "몇 번째 호출에서"가 추가된다 — 세 번째 수신자만 실패하도록 대역을 설정하는 식이다. 그리고 단언은 실패한 단계가 아니라 실패하지 않은 나머지의 상태를 향한다. 부분 실패 축의 결함은 예외가 나는 곳이 아니라, 예외 뒤에 남겨진 절반의 상태에 있다.

이제 여덟 답이 다 모였다. 한 함수에 이것을 실제로 적용하면 어떤 모양이 되는지, 그리고 이 케이스들이 J9의 자로 재면 어떻게 보이는지를 종합한다.

7. 종합 — 한 함수에 여덟 답을 대면

주문 확정 함수 confirm(order)에 관통 질문을 던져 보자. 여덟 관점을 전부 억지로 채우는 게 아니라 이 함수에 성립하는 축만 답이 된다는 점이 중요하다 — 상태가 없는 순수 계산 함수에는 상태 전이·멱등 축이 성립하지 않고(항상 참이므로 케이스가 무의미), 단일 단계 함수에는 부분 실패 축이 없다.

이 표를 J9의 자로 재면 3부작의 관계가 드러난다. 라인·분기 커버리지는 입력 공간 축이 밟은 분기를 세는 데는 유용하다 — 무효 클래스 케이스가 없으면 거부 분기가 비어 있다고 알려 준다. 그러나 멱등 케이스는 이미 밟은 줄을 한 번 더 밟는 케이스이고, 순서 의존·상태 전이·부분 실패 케이스도 새 줄을 밟지 않는 경우가 많다. 즉 표의 아래 다섯 줄은 커버리지에 거의 나타나지 않는다. 커버리지가 "얼마나 됐는지"를 재는 자로서 부족한 이유가 바로 이것이고, 그래서 케이스 설계가 측정에 앞선다.

케이스 수의 셈법: 관점을 각각 세우면 케이스 수는 관점별 케이스의 합이다. 그런데 관점끼리 교차시키면 — 할인 클래스 × 쿠폰 유무 × 현재 상태 × 실패 단계 — 케이스 수는 곱이 되어 폭발한다. 어떤 교차가 결함을 낳고 어떤 교차는 생략해도 되는지, 곱을 어떻게 줄이는지는 이 문서의 범위를 넘는 J16의 주제다. 이 문서의 답은 "먼저 축을 각각 세우라"까지다.

여덟 답을 세우는 과정에서 자주 뒤섞이는 개념들이 있다. 네 가지를 짚는다.

8. 흔히 헷갈리는 지점

① 멱등과 결정성은 다르다. 결정성(같은 입력 → 항상 같은 출력)은 한 번 호출의 성질이고, 멱등(반복 적용 = 한 번 적용)은 반복의 성질이다. 난수도 시각도 안 쓰는 charge(order)는 결정적이지만 두 번 부르면 두 번 청구된다 — 결정적이되 멱등이 아니다. "같은 입력을 넣으면 같은 값이 나온다"는 케이스는 멱등 케이스가 아니다.

② 경계값은 "무효 대표"가 아니라 "짝"이다. 51을 무효 클래스의 대표로 하나 넣고 끝내면 quantity <= 50을 quantity < 50으로 잘못 쓴 구현이 통과한다 — 이 결함을 잡는 것은 바깥쪽 51이 아니라 안쪽 50이다. 경계값 분석의 검증력은 안쪽·바깥쪽을 함께 둘 때만 나온다.

③ "순서 의존"은 두 가지를 가리킨다. 4절의 순서 의존은 함수의 성질(설계 관점, 케이스로 고정할 것)이고, 테스트 A가 먼저 돌아야 테스트 B가 통과하는 테스트 간 순서 의존은 공유 상태가 새는 테스트 냄새(없애야 할 것)다. 후자는 실행 순서를 무작위로 섞어 보면 발각된다 — 순서를 고정하는 기능으로 통과시키는 것은 결함을 봉인하는 일이다.

④ 오류 케이스는 "예외가 나는가"로 끝나지 않는다. 오류 축의 절반은 "삼키지 않았는가"(3절), 부분 실패 축의 전부는 "남은 상태가 일관적인가"(6절)다. 예외 종류 하나를 단언하고 오류 처리가 검증됐다고 여기면, 예외 뒤에 남는 절반의 상태와 기본값으로 위장한 실패가 그대로 남는다.

★ 9. 언어별 대조

여덟 관점은 언어 중립이지만, 케이스를 표현하는 도구는 언어마다 다르다 — 특히 입력 공간 축(등가 클래스와 경계를 표 하나로 나열하는 매개변수화 테스트), 오류 축(예외 단언), 반복·순서 축(부작용 횟수와 호출 순서를 기록하는 대역)에서 도구의 차이가 드러난다.

9.1 Java — JUnit 5 + Mockito: 매개변수화 표와 엄격 스텁의 충돌

JUnit 5의 @ParameterizedTest는 2절의 등가 클래스·경계 짝을 표 하나로 적게 해 준다 — 케이스가 "입력 공간의 지도"로 읽힌다. 멱등 축의 부작용 횟수는 Mockito의 verify(times(1))가, 순서 축은 InOrder가 담당한다. 

@ExtendWith(MockitoExtension.class)
class OrderConfirmTest {
    @Mock RefundGateway refunds;

    // 동등 분할 + 경계값: 클래스 경계 양쪽을 한 표에 (안쪽·바깥쪽 짝)
    @ParameterizedTest(name = "수량 {0} → 할인율 {1}")
    @CsvSource({ "1, 0.0", "9, 0.0", "10, 0.1", "50, 0.1" })
    void 수량_구간별_할인율(int quantity, double expected) {
        assertEquals(expected, DiscountPolicy.rateFor(quantity));
    }

    @ParameterizedTest
    @ValueSource(ints = { 0, 51 })                    // 무효 클래스는 케이스 하나에 하나씩
    void 범위_밖_수량은_거부한다(int quantity) {
        assertThrows(IllegalArgumentException.class, () -> DiscountPolicy.rateFor(quantity));
    }

    @Test
    void 취소는_멱등이다() {
        Order order = Order.paid(1L, refunds);
        order.cancel();
        order.cancel();                                // 두 번째 호출
        assertEquals(OrderStatus.CANCELLED, order.status());
        verify(refunds, times(1)).refund(1L);         // 상태만 보면 놓치는 부작용 횟수
    }
}

이 도구 조합의 함정은 엄격 스텁(strict stubs)이다. MockitoExtension은 기본적으로 엄격 모드로 동작해, 설정했지만 한 번도 호출되지 않은 스텁을 UnnecessaryStubbingException으로 실패시킨다(2020년대 중반 기준 기본값). 취지는 좋다 — 안 쓰는 스텁은 3절의 "구현의 복사"로 가는 길목이다. 그러나 매개변수화 테스트에서 일부 케이스만 스텁을 쓰면(무효 클래스 케이스는 거부되어 저장소를 호출하지 않으므로) 나머지 케이스가 실패로 판정된다. 해법은 lenient()로 넘어가는 것이 아니라, 스텁이 필요한 케이스와 필요 없는 케이스(유효 클래스 vs 무효 클래스)를 다른 테스트 메서드로 나누는 것이다 — 도구의 판정이 등가 클래스의 경계를 그대로 드러낸 셈이다. JUnit 5의 메서드 실행 순서는 결정적이되 의도적으로 예측하기 어렵게 되어 있고, @TestMethodOrder로 고정할 수 있다 — 8-③에서 말한 대로 이 기능으로 테스트 간 순서 의존을 통과시키는 것은 결함의 봉인이다.

9.2 JS·TS — Jest / Vitest: 표 문법과 비동기 오류의 조용한 통과

Jest와 Vitest는 API가 거의 같아서(Vitest는 명시적 import, Jest는 전역) 케이스 표현도 같다 — test.each가 매개변수화, vi.fn()/jest.fn()이 호출을 기록하는 대역이다. 6절의 부분 실패 케이스는 mockResolvedValueOnce·mockRejectedValueOnce를 순서대로 쌓아 "n번째 호출만 실패"를 만드는 것이 관용구다. 

import { describe, it, expect, vi } from 'vitest';   // Jest: import 없이 전역, vi → jest

describe('rateFor — 입력 공간 축', () => {
  it.each([
    [1, 0],   [9, 0],        // 무할인 클래스의 양 끝
    [10, 0.1], [50, 0.1],    // 할인 클래스의 양 끝
  ])('수량 %i → 할인율 %f', (qty, rate) => {
    expect(rateFor(qty)).toBe(rate);
  });

  it.each([0, 51])('범위 밖 %i 는 거부', (qty) => {
    expect(() => rateFor(qty)).toThrow(RangeError);
  });
});

it('알림의 부분 실패 — 한 수신자의 실패가 나머지를 막지 않는다', async () => {
  const send = vi.fn()
    .mockResolvedValueOnce(undefined)
    .mockRejectedValueOnce(new Error('unreachable'))   // 2번째 수신자만 실패
    .mockResolvedValueOnce(undefined);
  const result = await notifyAll(['a', 'b', 'c'], send);
  expect(send).toHaveBeenCalledTimes(3);              // 나머지는 계속 발송됐는가
  expect(result.failed).toEqual(['b']);               // 실패가 보고되는가
});

// 함정: 비동기 오류 단언은 반드시 await — 아래는 거부를 기다리지 않아 항상 통과한다
//   expect(confirm(badOrder)).rejects.toThrow();      // await 누락 → 조용한 통과

이 생태계의 함정은 오류 축에 몰려 있다. 비동기 함수의 오류는 거부된 프로미스로 오는데, expect(...).rejects.toThrow() 앞에 await를 빠뜨리면 단언 자체가 프로미스가 되어 테스트가 끝나도 평가되지 않는다 — 오류 케이스가 통과하는 것이 아니라 검사되지 않은 채 초록불이 된다(3절의 "삼키는" 실패가 테스트 코드 쪽에서 재현되는 셈). 두 도구 모두 반환되지 않은 단언을 경고하는 규칙(린트)을 붙이는 것이 관례다. 2020년대 중반 기준으로 Vitest는 test.each를 Jest 호환용으로 유지하고, 인자를 펼치지 않고 하나의 값으로 넘기며 테스트 컨텍스트에 접근할 수 있는 test.for를 새 코드에 권한다 — 케이스 표의 의미는 같고 넘기는 형태만 다르다. 테스트 간 순서 의존(8-③)은 두 도구 모두 파일 단위 격리가 기본이라 파일 안에서만 생기고, 실행 순서를 섞는 옵션으로 발각시킬 수 있다.

9.3 Python — pytest + unittest.mock: 케이스에 이름을 붙이는 표, 무엇이든 받아 주는 대역

pytest의 @pytest.mark.parametrize는 매개변수화의 표준이고, pytest.param(..., id=)로 케이스마다 이름을 붙일 수 있다 — "min", "no-discount-max"처럼 등가 클래스와 경계의 이름을 케이스 id로 쓰면 실패 보고가 곧 2절의 지도가 된다. 오류 축은 pytest.raises에 match=로 메시지까지 좁힐 수 있고, 반복·순서 축은 Mock의 assert_called_once_with·mock_calls가 담당한다. 

import pytest
from unittest.mock import Mock, create_autospec

@pytest.mark.parametrize("qty, rate", [
    pytest.param(1, 0.0,  id="valid-min"),          # 경계 안쪽
    pytest.param(9, 0.0,  id="no-discount-max"),
    pytest.param(10, 0.1, id="discount-min"),
    pytest.param(50, 0.1, id="valid-max"),
])
def test_rate_for_partitions(qty, rate):
    assert rate_for(qty) == rate

@pytest.mark.parametrize("qty", [0, 51], ids=["below-min", "above-max"])   # 경계 바깥쪽
def test_rate_for_rejects_out_of_range(qty):
    with pytest.raises(ValueError, match="quantity"):
        rate_for(qty)

def test_cancel_is_idempotent():
    refunds = create_autospec(RefundGateway)        # 실제 인터페이스로 봉인한 대역
    order = Order.paid(1, refunds)
    order.cancel()
    order.cancel()
    assert order.status == "CANCELLED"
    refunds.refund.assert_called_once_with(1)       # 부작용은 한 번만

def test_cancel_after_shipping_is_rejected():       # 상태 전이 축: 금지 칸
    order = Order.shipped(1)
    with pytest.raises(InvalidTransition):
        order.cancel()

함정은 대역의 개방성이다. 맨 Mock()은 존재하지 않는 속성과 메서드도 즉석에서 만들어 돌려주기 때문에, 오류 축 케이스에서 저장소 대역에 find_price.side_effect = TimeoutError를 설정했는데 구현이 find_prices(다른 이름)를 호출하면 예외 대신 또 다른 Mock이 조용히 돌아온다 — 오류 케이스가 오류를 주입하지 못한 채 통과한다. create_autospec·spec=으로 실제 인터페이스에 봉인하면 없는 이름은 즉시 실패한다. 단, assert_called_once류의 단언 메서드 이름 오타는 표준 라이브러리가 별도로 막아 준다(assert로 시작하는 미지의 속성은 예외). 테스트 간 순서 의존은 모듈 수준의 가변 상태와 scope="module" 픽스처에서 생기기 쉽고, 실행 순서를 무작위화하는 플러그인이 8-③의 발각 도구다.

Python 관점의 통찰: 이 언어의 객체 모델은 속성 접근을 런타임에 해석하고(__getattr__ 훅으로 무엇이든 만들어 낼 수 있음) 상태를 언제든 바꿀 수 있는 개방형이라, 5절의 "금지 전이"를 언어가 막아 주지 않는다 — 배송중 주문의 status 필드에 무엇이든 대입할 수 있다. 상태 기계의 불변식은 오직 메서드와 테스트가 지키므로, 정적 언어에서 타입으로 표현되곤 하는 상태 제약(상태별 타입)이 Python에서는 상태 전이 케이스의 몫으로 넘어온다. 같은 이유로 대역도 개방형이고, 그래서 spec으로 닫아 주는 한 줄이 오류 축 케이스의 검증력을 좌우한다.

9.4 C++ — GoogleTest + GoogleMock: 값 매개변수화와 순서 검증, 그리고 경계 바깥의 미정의 동작

GoogleTest의 값 매개변수화 테스트는 TEST_P로 케이스 본문을, INSTANTIATE_TEST_SUITE_P로 값 목록을 따로 선언한다 — 표와 본문이 분리되는 형태다. 순서 축은 gMock의 InSequence가 가장 직접적으로 표현한다: 블록 안의 EXPECT_CALL이 선언 순서대로 일어나야 통과한다. 

#include <gtest/gtest.h>
#include <gmock/gmock.h>
using ::testing::Values;

// 동등 분할·경계값: 값 매개변수화
class RateFor : public ::testing::TestWithParam<std::pair<int, double>> {};
TEST_P(RateFor, ReturnsRateOfPartition) {
    auto [qty, rate] = GetParam();
    EXPECT_DOUBLE_EQ(rate_for(qty), rate);
}
INSTANTIATE_TEST_SUITE_P(Boundaries, RateFor,
    Values(std::pair{1, 0.0}, std::pair{9, 0.0}, std::pair{10, 0.1}, std::pair{50, 0.1}));

TEST(RateFor, RejectsOutOfRange) {                  // 오류 축 (예외를 쓰는 프로젝트)
    EXPECT_THROW(rate_for(0),  std::out_of_range);
    EXPECT_THROW(rate_for(51), std::out_of_range);
}

// 순서 의존 축: 재고 확보 → 알림. 순서가 뒤집힌 구현은 여기서 실패해야 한다
class MockStock    : public Stock    { public: MOCK_METHOD(void, reserve, (int), (override)); };
class MockNotifier : public Notifier { public: MOCK_METHOD(void, send,    (int), (override)); };
TEST(Confirm, ReservesBeforeNotifying) {
    MockStock stock; MockNotifier notifier;
    ::testing::InSequence seq;                       // 아래 기대는 선언 순서대로
    EXPECT_CALL(stock,    reserve(1)).Times(1);
    EXPECT_CALL(notifier, send(1)).Times(1);
    confirm_order(1, stock, notifier);
}

이 언어의 함정은 경계값 축에서 근본적이다. 부호 있는 정수의 오버플로는 미정의 동작(표준이 결과를 정하지 않아 무슨 일이든 일어날 수 있음)이므로, 수량 상한이 자료형의 최댓값과 겹치는 설계에서는 "경계 바깥쪽 값"을 넣는 케이스 자체가 정의된 동작을 관찰하지 못한다 — 통과해도 보장이 아니고, 실패해도 재현이 안 된다. 경계값 분석이 성립하려면 경계가 자료형 한계 안쪽에 있어야 하고(std::numeric_limits로 한계를 명시), 한계 근처의 계산은 검사식을 먼저 두어야 한다. 예외를 끄고 빌드하는 프로젝트에서는 EXPECT_THROW가 쓸모없고 오류는 반환값(오류 코드·기대값 타입)으로 보고되는데, 반환값은 무시가 조용히 가능하므로 3절의 "삼키는" 실패가 언어 차원에서 열려 있다 — [[nodiscard]]가 그 문을 닫는 최소 장치다. 테스트 간 순서 의존은 --gtest_shuffle로 실행 순서를 섞어 발각시킨다.

C++ 관점의 통찰: gMock의 대역은 가상 함수 표(vtable — 가상 함수 호출을 런타임에 실제 구현으로 연결하는 함수 포인터 표)를 통해 끼어들므로, 순서·횟수를 기록하려면 대상이 virtual이어야 한다 — 템플릿 기반 정적 다형성으로 짠 코드는 순서 축 케이스를 위해 인터페이스를 뽑아내거나 템플릿 인자로 대역을 넣어야 한다. 부분 실패 축은 이 언어에서 자원 수명과 겹친다: RAII(객체 수명에 자원 획득·해제를 묶는 관용구)로 잡은 재고 예약이 뒤 단계의 예외에서 소멸자로 되돌려지는지가 곧 6절의 "전부 아니면 전무" 케이스이고, 예외 경로에서 소멸자가 실행되는지는 테스트만이 아니라 새니타이저(런타임 메모리·수명 오류 검출기)로 함께 확인해야 한다.

10. 함께 알면 좋은 것

여덟 답을 도구와 이론으로 확장한 것들이다 — 첫째·둘째는 2절과 7절의 표를, 셋째는 4절의 성질을, 넷째는 5절의 표를, 다섯째는 7절의 마지막 질문을 잇는다.

  • 결정 테이블 테스트(decision table testing) — 조건 여러 개의 참·거짓 조합을 행으로 늘어놓고 각 행의 기대 결과를 적는 기법. 2절의 등가 클래스가 한 입력의 분할이라면 결정 테이블은 여러 조건의 교차이고, 7절의 "합에서 곱으로" 넘어가는 첫 걸음이다.
  • 뮤테이션 테스트(mutation testing) — 코드를 조금씩 변형(<를 <=로)해 테스트가 잡아내는지 보는 기법. 경계 변이를 잡지 못하면 경계값 케이스가 짝이 아니었다는 뜻(8-②)이므로, J9의 커버리지가 재지 못하는 "케이스의 검증력"을 재는 자다.
  • 속성 기반 테스트(property-based testing) — 개별 값 대신 "모든 입력에 대해 성립해야 할 성질"을 적고 도구가 값을 생성하는 방식. 멱등(f(f(x)) == f(x))과 가환성(g(f(x)) == f(g(x)))은 이 형식으로 가장 자연스럽게 표현되며, 등가 클래스의 대표값 선택을 도구에 맡기는 셈이다.
  • 모델 기반 테스트(model-based testing) — 5절의 상태 전이표를 모델로 두고, 허용·금지 전이의 케이스를 모델에서 생성하는 접근. 전이표의 빈 칸(금지)을 사람이 빠뜨리지 않게 해 준다.
  • 사전·사후 조건(design by contract) — 함수가 요구하는 것(사전)과 보장하는 것(사후)을 명세로 적는 방식. 3절의 무효 클래스는 사전 조건 위반, 6절의 "남은 상태의 일관성"은 사후 조건이므로, 계약이 명문화된 함수는 오류·부분 실패 축의 케이스가 계약에서 직접 나온다.

11. 한 장 요약

  • 관통 질문은 하나 — "이 함수는 어떤 축으로 실패할 수 있나". 8관점은 그 답이며, 함수에 성립하는 축만 고른다.
  • 입력 공간: 등가 클래스를 그리고(동등 분할, 유효·무효, 무효는 하나씩) → 클래스당 대표값(정상 = 유효 클래스의 대표) → 경계마다 안쪽·바깥쪽 짝(경계값).
  • 입력 밖(오류): 대역으로 실패를 주입하고, 실패가 호출자에게 보이는 형태로 보고되는지까지 단언한다 — 삼킨 오류를 테스트가 승인하지 않게.
  • 반복·순서: 멱등은 두 번 호출 후 상태 + 부작용 횟수 1, 순서 의존은 정해진 순서와 뒤집힌 순서의 결과 차이. 멱등 ≠ 결정성.
  • 시간·부분: 상태 전이는 전이표의 금지 칸이 핵심, 부분 실패는 n번째 단계에 실패를 주입하고 나머지의 상태를 단언한다.
  • 3부작: J10이 대상을 고르고 → 이 문서가 케이스를 세우고 → J9가 잰다. 커버리지는 입력 공간 축만 비추므로 케이스 설계가 측정에 앞선다. 축의 교차(조합 폭발)는 J16으로.

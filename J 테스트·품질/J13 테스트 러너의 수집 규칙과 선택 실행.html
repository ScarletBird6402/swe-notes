J13 테스트 러너의 수집 규칙과 선택 실행

0. 한눈에 보는 결론

  • 테스트 러너(test runner)는 테스트를 실행하기 전에 먼저 찾는다. 이 수집(collection) 단계의 결과 목록에 없는 테스트는 통과도 실패도 아닌 제3의 상태 — "안 돌았음" — 에 놓이며, 초록불은 이 상태에 대해 아무것도 말해 주지 않는다.
  • 수집은 대부분 관례(convention)에 의한 암묵 등록이다: 파일명 패턴·클래스명·함수 접두사·어노테이션/데코레이터·마커가 여러 층으로 겹쳐 "무엇이 테스트인가"를 정의한다. 관례에서 벗어난 코드는 잘못된 테스트가 아니라 그냥 테스트가 아닌 코드로 해석된다 — 그래서 오류가 나지 않는다.
  • 핵심 함정은 조용한 제외(silent exclusion): 이름 오타, 어노테이션 누락, 마커 오타, 비동기 마커 누락, 링크 누락으로 신규 테스트가 목록에서 빠져도 스위트는 초록불이다. K5가 다룬 조용한 실패의 테스트판이다.
  • 발각 수단은 세 가지 — 수집 목록을 직접 본다(--collect-only·--listTests·--gtest_list_tests), 테스트 수의 변화를 감시한다, 일부러 실패시켜 빨간불을 한 번 확인한다.
  • 선택 실행(selective execution) — 노드 ID·이름 표현식·태그·only — 은 수집된 집합에 대한 필터로 피드백 루프를 초 단위로 줄인다. 단, 코드 안에 남는 only/skip은 커밋에 섞이는 순간 임시 필터가 영구 제외로 변한다.
  • 수집 규칙은 팀의 "테스트 정의 계약"이다 — 설정 파일에 명시하고, 미등록 마커·미실행 비동기·0개 매치를 오류로 승격시키는 도구 옵션을 켜 두는 것이 조용함을 시끄러움으로 바꾸는 방법이다.

1. 전제 — 실행 결과에는 세 번째 상태가 있다

테스트 러너의 일을 "테스트를 실행하고 결과를 보고한다"로만 이해하면 이 문서의 함정이 보이지 않는다. 러너의 일은 네 단계다: 수집 → 선택 → 실행 → 보고. 러너가 실행하는 것은 "내가 작성한 테스트"가 아니라 "러너가 찾아낸 테스트"이고, 이 둘이 같다는 보장은 어디에도 없다.

내가 쓴 테스트 코드 │ ▼ [수집] 관례에 맞는 것만 목록에 올린다 ← 이 문서의 1축 │ (파일명 · 클래스명 · 함수명 · 어노테이션 · 마커) ▼ [선택] 목록 중 실행할 부분집합을 고른다 ← 이 문서의 2축 │ (노드 ID · -k 표현식 · 태그 · only/skip) ▼ [실행] ──▶ [보고] 통과 N · 실패 M · 건너뜀 S ───────────────────────── 목록에 없던 테스트는 여기 어디에도 없다

보고서의 세 숫자(통과·실패·건너뜀)는 모두 수집된 것에 대한 집계다. 수집되지 않은 테스트는 건너뜀에조차 세어지지 않는다 — 러너 입장에서 그것은 애초에 존재하지 않았기 때문이다. 그러므로 초록불의 정확한 의미는 "모든 테스트가 통과했다"가 아니라 "수집된 테스트 중 실패한 것이 없다"다. 이 차이가 이 문서 전체의 출발점이다.

그렇다면 러너는 무엇을 근거로 "이 코드는 테스트다"라고 판정하는가 — 다음 절의 주제인 수집 관례다.

2. 수집 관례 — 여러 층의 필터가 AND로 겹친다

러너가 테스트를 찾는 방식은 크게 두 가지다. 하나는 명시 등록 — 스위트 파일에 실행할 테스트를 손으로 나열하는 방식이고, 다른 하나는 관례 기반 자동 수집 — "이런 모양이면 테스트로 간주한다"는 규칙으로 코드베이스를 훑는 방식이다. 명시 등록은 누락이 생기지 않을 것 같지만, 실제로는 "등록을 잊는" 실패로 형태만 바뀐다. 그래서 현대의 러너는 거의 모두 관례 기반이고, 관례는 보통 아래처럼 여러 층으로 겹쳐 있다.

층무엇을 보는가대표 관례이 층의 소유자
① 파일·경로 어떤 파일을 열어 볼 것인가 test_*.py / *.test.ts / *Test.java / __tests__/ 디렉터리 러너 설정 또는 빌드 도구(러너와 별개일 수 있음)
② 컨테이너 파일 안에서 어떤 클래스·블록을 볼 것인가 Test* 클래스, describe() 블록, 테스트 스위트 이름 테스트 프레임워크
③ 케이스 무엇이 하나의 테스트인가 test_ 접두 함수, @Test 어노테이션, TEST() 매크로, it() 호출 테스트 프레임워크
④ 속성 그 테스트를 어떤 조건·방식으로 다룰 것인가 마커·태그(@Tag, @pytest.mark.*), 비동기 마커, DISABLED_ 접두, skip 프레임워크 + 플러그인

층들은 AND로 결합된다 — 파일명이 맞아도 함수 접두사가 틀리면 제외되고, 어노테이션이 있어도 파일이 빌드 도구의 패턴 밖이면 제외된다. 그리고 각 층의 소유자가 다르다는 점이 중요하다: 파일 패턴은 빌드 도구가, 어노테이션은 프레임워크가, 비동기 마커는 플러그인이 결정한다. 한 도구의 문서만 읽고는 전체 규칙을 알 수 없다는 뜻이다.

등록의 기제도 둘로 갈린다. 스캔형은 파일을 불러들인(import) 뒤 이름·어노테이션을 검사해 목록을 만든다(pytest·JUnit). 정적 등록형은 코드가 로드되는 순간 매크로나 함수 호출이 스스로 전역 레지스트리에 자신을 넣는다(GoogleTest의 TEST, Jest의 it()). 이 차이는 뒤에서 실패 양상의 차이로 돌아온다 — 스캔형은 "이름이 안 맞아서", 정적 등록형은 "코드가 로드되지 않아서" 빠진다.

관례 기반 수집의 대가는 분명하다: 관례를 지키지 않은 코드는 존재하지 않는 것이 된다. 그것이 왜 오류가 아니라 침묵으로 나타나는지가 다음 절이다.

3. 조용한 제외 — 관례 불일치는 오류가 아니다

2절의 관례를 어긴 코드가 있다고 하자. test_discount_applied를 쓰려다 tset_discount_applied로 오타를 냈다. 러너의 관점에서 이 함수는 잘못 작성된 테스트가 아니다 — 테스트 파일 안에 흔히 있는 헬퍼 함수와 구별할 방법이 없다. 러너는 의도를 모르므로 "테스트일 뻔한 것"을 판정할 수 없고, 따라서 진단 없이 지나간다. 

# test_discount.py — 세 테스트를 추가했다고 믿지만, 러너가 수집하는 것은 0개다
import pytest

class TestDiscount:
    def __init__(self):            # ① 생성자가 있는 클래스는 수집 제외 (경고 한 줄)
        self.rate = 0.1

    def tset_rate_applied(self):   # ② 접두사 오타 — 헬퍼 함수로 취급
        assert apply_discount(10000, self.rate) == 9000

async def test_notify_sent():      # ③ 비동기 마커 없음 — 코루틴만 만들어지고 실행되지 않음
    assert await notifier.send("order-1") is True

# 실행 결과: "no tests ran" 또는 다른 파일의 초록불 사이에 묻힌다

같은 구조의 사례는 층마다 하나씩 있다:

층조용한 제외의 사례러너에게 보이는 모습
파일파일명이 패턴 밖(discount_tests.py, DiscountCalcSpec.java)열어 보지도 않는 파일
컨테이너Test 접두 누락, 생성자가 있는 테스트 클래스평범한 클래스
케이스접두사 오타, 헬퍼를 복사해 만들었는데 @Test를 안 붙임헬퍼 함수
속성마커 오타(slwo), 비동기 마커 누락마커 없는 테스트 / 실행되지 않는 코루틴
로드·링크정적 등록형에서 파일이 링크·import되지 않음등록 자체가 일어나지 않음

K5가 다룬 조용한 실패는 "오류가 있는데 신호가 없다"였다. 여기서는 "검증이 있는데 실행이 없다" — 코드는 존재하고, 컴파일되고, 아무 경고 없이(또는 아무도 읽지 않는 경고 한 줄과 함께) 초록불이 켜진다. 특히 위험한 것은 신규 테스트다. 원래 있던 테스트가 사라지면 개수가 줄어 눈에 띌 수 있지만, 처음부터 안 돌던 테스트는 기준선(baseline)에 존재한 적이 없어 "사라짐"조차 감지되지 않는다.

그리고 비동기 마커 누락은 그중에서도 가장 교묘하다. 함수가 호출되기는 하지만 본문이 한 줄도 실행되지 않는 채 "통과"로 보이거나(코루틴 객체만 생성), 본문이 시작은 하되 단언에 도달하기 전에 테스트가 끝난다(대기하지 않은 프라미스). 어느 쪽이든 단언이 한 번도 평가되지 않은 초록불이다.

왜 러너는 경고조차 약하게 내는가: 테스트 파일에는 헬퍼·픽스처·상수가 정당하게 공존한다. "관례에 안 맞는 함수마다 경고"를 내면 소음이 되어 곧 무시된다. 그래서 러너는 명백한 이상 징후(생성자 있는 Test 클래스, 실행되지 않은 코루틴)에만 경고를 붙이고, 나머지는 판정을 보류한다. 침묵은 러너의 결함이 아니라 관례 기반 수집의 구조적 대가다.

구조적 대가라면 러너가 대신 잡아 주기를 기대할 수 없다 — 그렇다면 무엇으로 발각하는가?

4. 발각 — 수집 결과를 눈으로 확인하는 세 가지 방법

3절의 결론은 "러너는 없는 것을 보고할 수 없다"였다. 따라서 발각의 원리는 하나다: 러너가 무엇을 찾았는지를 내가 직접 확인한다. 방법은 정밀도 순으로 세 가지다.

③ 빨간불 확인 ─ 이 테스트가 실제로 실행되어 판정을 내리는가 (가장 확실, 테스트 1개) ② 수집 목록 확인 ─ 이 테스트가 목록에 있는가 (정확, 새 테스트 추가 직후) ① 테스트 수 감시 ─ 개수가 기대만큼 늘었는가·줄지 않았는가 (넓지만 성김, 커밋·CI 단위)
  • 수집 목록 확인 — 실행 없이 목록만 출력하는 옵션은 거의 모든 러너에 있다: pytest --collect-only, Jest --listTests, Vitest list, GoogleTest --gtest_list_tests, JUnit Platform 콘솔 런처의 discover. 새 테스트를 쓴 직후 목록에서 그 이름을 찾는 습관이 3절의 함정 대부분을 즉시 잡는다.
  • 테스트 수 변화 감시 — 보고서의 "N tests"를 변경 전후로 비교한다. CI에서 총 개수가 줄면 경고를 내는 규칙은 기존 테스트의 소실을 잡는다. 단 3절에서 봤듯 신규 테스트는 "줄어듦"이 아니라 "안 늘어남"으로 나타나므로, 리뷰에서 "이 변경이 테스트 수를 얼마나 늘렸는가"를 묻는 것이 보완이 된다.
  • 빨간불 확인 — 테스트를 처음 쓸 때 단언을 일부러 뒤집거나 assert False를 한 줄 넣어 실패를 한 번 본다. 실패하지 않으면 그 테스트는 수집되지 않았거나 본문이 실행되지 않은 것이다. TDD의 "먼저 빨간불" 단계는 설계 규율로만 이야기되지만, 실제로는 수집 검증을 겸하는 가장 값싼 절차다. J10이 던진 "이 테스트는 무엇이 틀렸을 때 실패하는가"의 실행판이기도 하다.

사람의 습관 위에 도구의 승격을 얹을 수 있다. 미등록 마커를 경고가 아니라 오류로 취급하는 옵션(pytest --strict-markers), 실행되지 않은 비동기 테스트를 실패로 판정하는 러너 동작, 필터에 걸린 테스트가 0개면 실행 자체를 실패로 처리하는 빌드 도구 옵션 등이 그것이다. 원리는 같다 — 조용함을 시끄러움으로 바꾼다.

수집 목록을 보는 습관이 생기면 자연스러운 다음 욕구가 생긴다: 목록 전체가 아니라 지금 고치는 부분만 돌리고 싶다. 그것이 두 번째 축, 선택 실행이다.

5. 선택 실행 — 수집된 집합에서 고르기

선택(selection)은 수집된 집합에 대한 필터다. 이 정의에서 두 가지가 따라 나온다. 첫째, 수집에서 빠진 테스트는 어떤 선택 표현식으로도 실행할 수 없다 — 선택은 수집을 대체하지 못한다. 둘째, 선택 표현식이 0개를 매치했을 때 그것이 표현식 오타인지 미수집인지 구분해야 한다 — 둘 다 "0개 실행"이라는 같은 결과로 보이기 때문이다.

선택 수단형태장점대가
노드 ID(정확한 주소) tests/test_discount.py::TestDiscount::test_rate, Suite.Name, 클래스#메서드 정확히 하나를 지목 이름 변경에 취약, 주소 형식이 도구마다 다름
이름 표현식 -k "discount and not slow", -t "discount", --gtest_filter=*Discount* 여러 테스트를 한 번에 의도치 않은 매치(discount가 no_discount도 잡음)
태그·마커·그룹 -m slow, @Tag("integration") + 포함/제외 설정 이름과 독립된 분류, CI 단계 분리에 적합 태그 오타는 조용한 제외(3절)로 직결
코드 내 포커스 it.only, describe.only, @Disabled, DISABLED_ 편집기에서 바로, 옵션 기억 불필요 코드에 남는다 — 6절의 함정
관련성·이력 기반 변경 파일과 연관된 테스트만, 직전 실패만 재실행(--lf), 감시(watch) 모드 선택 자체를 자동화 연관 추적이 놓치는 간접 의존

선택 실행의 존재 이유는 피드백 루프의 길이다. 전체 스위트가 몇 분이면 개발자는 실행 횟수를 줄이게 되고, 실행 횟수가 줄면 한 번의 실행에 여러 변경이 섞여 실패의 원인 추적이 어려워진다. 지금 고치는 함수의 테스트 몇 개를 초 단위로 돌릴 수 있으면 "고치고 → 확인"의 주기가 짧아져 변경 하나와 결과 하나가 일대일로 대응한다.

역할 분담: 선택 실행은 개발 시간의 도구이고, 전체 실행은 커밋·CI의 게이트다. 좁게 돌리며 고치고, 넓게 돌리고 나서 커밋한다. 이 분담이 무너지는 지점 — 좁힌 상태가 커밋에 딸려 들어가는 경우 — 가 다음 절이다.

6. only·skip 잔존 — 임시 필터가 영구 제외로

5절의 선택 수단 중 코드 안에 쓰는 것(only·skip·비활성 접두)은 편리한 만큼 커밋에 따라 들어간다. describe.only가 남은 채 커밋되면 CI는 그 파일의 나머지 테스트를 모두 건너뛴다 — 정확히 3절의 조용한 제외를 손으로 만든 셈이다. 실행 보고서엔 여전히 초록불이고, 개수는 줄었지만 이유가 표시되지 않는다.

skip은 성격이 다르다. 명시적 제외이므로 보고서의 "건너뜀 N"에 잡히고, 그래서 조용하지 않다. 문제는 이 숫자가 상수가 될 때 시작된다 — 늘 "skipped 3"인 보고서에서 4가 되어도 아무도 알아채지 못한다. 아무도 읽지 않는 로그가 로그가 아니듯, 아무도 세지 않는 건너뜀 수는 신호가 아니다.

방지책은 세 층이다:

  • 린트 규칙 — 포커스 테스트(only)와 비활성 테스트(skip)를 검출하는 규칙을 켜 두면 커밋 전에 잡힌다.
  • CI 플래그 — CI 환경에서 only가 있으면 실행을 실패시키는 러너 옵션. 로컬에선 허용하고 CI에선 금지하는 비대칭이 핵심이다.
  • 사유와 조건이 있는 skip — @Disabled("사유")처럼 사유를 강제하고, 가능하면 조건부 skip(특정 OS·환경변수·버전에서만)으로 바꿔 제외가 스스로 풀리게 한다. 사유·기한 없는 skip은 K4의 죽은 코드와 같은 경로를 밟는다.

여기까지가 두 축 — 수집과 선택 — 의 원리와 함정이다. 실제 도구로 내려가기 전에, 원리 수준에서 자주 뒤섞이는 지점을 정리한다.

7. 흔히 헷갈리는 지점

① "테스트가 안 돌면 어떻게든 실패하지 않나?" — 아니다. 러너는 수집된 것만 판정한다. 수집이 전체 0개일 때는 대부분의 러너가 "no tests ran"과 함께 비정상 종료 코드를 내지만, 100개 중 1개가 빠진 경우는 99개의 초록불로 덮인다. 발각 수단(4절)이 필요한 이유는 정확히 이 부분 누락이다.

② "skip과 조용한 제외는 같은 것" — 다르다. skip은 의도가 있고 보고서에 세어지는 제외이고, 조용한 제외는 의도 없이 존재 자체가 지워진 제외다. 그러나 skip 수가 상수가 되어 아무도 보지 않으면 실질적으로 같아진다(6절). 구분의 기준은 형식이 아니라 누군가 그 숫자를 읽는가다.

③ "-k로 0개가 매치되면 오류가 나겠지" — 도구마다 다르다. 어떤 러너는 "0 selected"를 정상 종료로, 어떤 빌드 도구는 실패로 처리한다. 더 중요한 것은 0개 매치의 원인이 표현식 오타인지 미수집인지 러너가 구분해 주지 않는다는 점이다 — 0개가 나오면 수집 목록부터 본다.

④ "비동기 테스트가 통과했으니 됐다" — 비동기 마커나 await가 빠진 테스트는 단언이 평가되기 전에 끝나며 통과로 보인다. 코루틴은 호출만으로 실행되지 않고, 대기하지 않은 프라미스는 테스트 함수가 반환된 뒤에야 처리된다. 비동기 테스트는 특히 빨간불 확인(4절)을 한 번 거쳐야 "본문이 실제로 돌았다"를 믿을 수 있다.

원리는 같지만, 2절의 "층의 소유자"와 "등록 기제"가 언어마다 달라 어느 층에서 조용히 빠지는가가 달라진다. Java는 빌드 도구 층이, JS·TS는 파일 글롭과 이벤트 루프가, Python은 이름 관례와 코루틴이, C++은 링커가 각각 그 언어만의 제외 지점이다.

8.1 Java — JUnit 5 + Mockito: 어노테이션 층과 빌드 도구 층이 따로 논다

JUnit 5는 JUnit Platform(테스트를 발견·실행하는 기반) 위에 Jupiter 엔진(JUnit 5 문법을 해석하는 엔진)이 얹힌 구조다. Jupiter의 수집 규칙은 단순하다 — @Test(또는 @ParameterizedTest 같은 파생 어노테이션)가 붙은 메서드가 테스트이며, 클래스명·메서드명은 보지 않고, JUnit 4와 달리 public도 필요 없다(단 private·static은 안 된다). 그래서 Java의 조용한 제외는 어노테이션 층보다 그 위아래 층에서 일어난다.

위층은 빌드 도구의 파일 패턴이다. Maven의 테스트 플러그인은 기본적으로 **/Test*.java·**/*Test.java·**/*Tests.java·**/*TestCase.java만 포함하므로, DiscountCalculatorSpec.java는 안에 @Test가 아무리 많아도 열리지 않는다. Gradle은 컴파일된 클래스를 스캔하는 방식이라 이름 의존이 덜하지만, 필터 설정이 있으면 마찬가지다. 아래층은 엔진이다 — JUnit 4의 @Test(org.junit.Test)를 import한 클래스는 JUnit 5 전용 프로젝트에서 Vintage 엔진 없이는 조용히 0개로 집계되고, 플랫폼을 모르는 오래된 빌드 플러그인도 같은 결과("Tests run: 0")를 낸다. import 문 한 줄, 플러그인 버전 하나가 수집 결과를 바꾼다. 

// DiscountCalculatorTest.java — 파일명이 빌드 도구 패턴(*Test.java)에 맞아야 열린다
import org.junit.jupiter.api.*;           // org.junit.Test(JUnit 4)를 import하면 엔진이 달라진다
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class DiscountCalculatorTest {             // public 불필요 (JUnit 5)

    @Test                                  // 수집 기준은 이 어노테이션뿐
    @Tag("fast")                           // 선택 실행: includeTags("fast") / excludeTags("slow")
    void appliesTenPercent() {
        Assertions.assertEquals(9000, new DiscountCalculator().apply(10000, 0.1));
    }

    @Test
    @Disabled("할인율 반올림 정책 확정 전 — 정책 이슈 해결 시 해제")   // 사유가 있는 skip
    void roundsHalfUp() { /* ... */ }

    void rejectsNegativeRate() {           // 헬퍼를 복사해 만들다 @Test를 빠뜨림 → 조용한 제외
        Assertions.assertThrows(IllegalArgumentException.class,
            () -> new DiscountCalculator().apply(10000, -0.1));
    }
}

Mockito는 수집과는 무관하지만 대조점이 하나 있다. @ExtendWith(MockitoExtension.class)를 빠뜨리면 @Mock 필드가 null로 남아 테스트가 시끄럽게 실패한다 — 조용한 제외와 정반대의, 오히려 다행스러운 실패다. 반대로 Mockito의 안전장치(엄격 스텁 모드가 쓰이지 않은 스텁을 잡아 주는 것)는 테스트가 실행되어야 작동한다. 수집에서 빠진 테스트는 검증뿐 아니라 이런 부수적 안전망도 함께 잃는다. 선택 실행은 Gradle --tests "*.DiscountCalculatorTest.appliesTenPercent", Maven -Dtest=DiscountCalculatorTest#appliesTenPercent 형태이고, 수집 목록은 JUnit Platform 콘솔 런처의 discover 서브커맨드(5.10부터 제공)나 빌드 도구의 테스트 보고서로 확인한다.

8.2 JS·TS — Jest / Vitest: 글롭이 파일을 고르고, 이벤트 루프가 단언을 놓친다

Jest와 Vitest의 수집은 파일 글롭이 지배한다. Jest의 testMatch 기본값은 __tests__/ 아래의 파일과 *.test.*·*.spec.*이고, Vitest의 include 기본값은 **/*.{test,spec}.?(c|m)[jt]s?(x)다. discount.tests.ts(복수형)는 어느 쪽에서도 열리지 않는다. 파일 안에서는 정적 등록형이다 — 파일을 로드하는 동안 describe()·it() 호출이 스스로 등록한다. 그래서 파일 최상위에서 예외가 나면 파일 전체가 시끄럽게 실패하지만(좋은 성질), if 문 안에 넣은 it()은 조건이 거짓이면 호출조차 되지 않아 조용히 사라진다.

이 생태계만의 함정은 비동기 테스트에서 await(또는 프라미스 반환) 누락이다. 이벤트 루프 관점에서 보면 이유가 분명하다: 테스트 함수의 동기 부분이 반환되는 순간 러너는 테스트를 완료로 간주하고, .then() 안의 단언은 그 뒤 마이크로태스크에서 실행된다. 단언이 실패해도 이미 통과 판정이 난 뒤라, 처리되지 않은 거부(unhandled rejection)로 다른 테스트의 출력에 섞여 나오거나 아예 묻힌다. 

// notifier.test.ts — 파일명이 include 글롭(*.test.ts)에 맞아야 수집된다
import { describe, it, expect } from "vitest";   // Jest면 전역 describe/it/expect

describe("Notifier", () => {
  it("sends order notification", () => {           // ✗ 함정: await도 return도 없다
    notifier.send("order-1").then((ok) => expect(ok).toBe(true));
    // 동기 부분이 여기서 끝난다 → 단언이 평가되기 전에 "통과"
  });

  it("sends order notification (fixed)", async () => {
    expect.assertions(1);                            // 단언이 정확히 1번 평가되지 않으면 실패
    await expect(notifier.send("order-1")).resolves.toBe(true);
  });

  it.only("applies discount", () => { /* ... */ }); // ✗ 잔존 시 이 파일의 다른 테스트 전부 제외
});

선택 실행은 파일 경로 인자와 -t(이름 패턴), 그리고 코드 내 .only/.skip/.todo다. 수집 목록은 Jest --listTests(파일 목록), Vitest list(개별 테스트까지, .only와 이름 패턴이 적용된 결과)로 본다. .only 잔존 대책은 도구가 갈린다 — 2020년대 중반 기준 Vitest는 allowOnly 옵션이 CI 환경변수가 있으면 기본적으로 꺼져 .only 잔존이 CI에서 실패하고, Jest는 린트 규칙(포커스 테스트 금지)에 맡기는 것이 일반적이다. TS는 이 문제에 도움을 주지 못한다 — 파일 글롭과 await 누락은 타입 오류가 아니기 때문이다(반환된 프라미스를 버리는 것을 잡는 린트 규칙이 별도로 있다).

8.3 Python — pytest + unittest.mock: 이름 관례와 코루틴의 침묵

pytest의 기본 관례는 세 층이 모두 이름이다: test_*.py 또는 *_test.py 파일, Test로 시작하고 생성자(__init__)가 없는 클래스, test로 시작하는 함수·메서드. 이름 규칙은 설정(python_files·python_classes·python_functions)으로 바꿀 수 있다. 예외가 하나 있다 — unittest.TestCase의 하위 클래스는 클래스명 관례와 무관하게 수집된다(상속이 곧 등록이므로). 반대로 표준 라이브러리의 python -m unittest discover는 test*.py 패턴에 더해 디렉터리가 패키지로 import 가능해야(__init__.py) 하위 폴더를 내려가므로, 같은 트리에서 두 러너의 수집 결과가 다를 수 있다.

속성 층의 함정 둘이 이 언어의 핵심이다. 첫째, 마커 오타: @pytest.mark.slwo는 기본 설정에서 "알 수 없는 마커" 경고일 뿐이고, -m slow 선택에서 그 테스트는 조용히 빠진다. --strict-markers(또는 설정의 addopts)를 켜면 미등록 마커가 오류로 승격된다. 둘째, 비동기 마커 누락: async def 테스트에 @pytest.mark.asyncio(pytest-asyncio의 기본인 엄격 모드 기준)가 없으면, pytest 8.4 이전에는 "async def functions are not natively supported and have been skipped"라는 경고와 함께 건너뛰었다 — 코루틴이 만들어지기만 하고 실행되지 않는 것이다. 2025년의 pytest 8.4부터는 이 경우를 실패로 판정하도록 바뀌었다. 조용한 제외가 도구 차원에서 시끄러운 실패로 승격된 대표적 사례이니, 사용하는 버전이 어느 쪽인지 확인해 둘 가치가 있다. 

# tests/test_discount.py
import pytest
from unittest.mock import patch

class TestDiscount:                       # __init__이 없어야 수집된다
    @pytest.mark.slow                     # pytest.ini에 markers = slow ... 로 등록 + --strict-markers
    def test_rate_applied(self):
        assert apply_discount(10000, 0.1) == 9000

@patch("shop.notifier.send")              # patch 데코레이터는 함수 이름을 보존 → 수집에 영향 없음
def test_notify_called(mock_send):
    place_order("order-1")
    mock_send.assert_called_once()

@pytest.mark.asyncio                      # 이 한 줄이 없으면: 8.4 이전 skip+경고, 8.4부터 실패
async def test_async_notify():
    assert await notifier.send("order-1") is True

# 확인: pytest --co -q            → 노드 ID 목록  tests/test_discount.py::TestDiscount::test_rate_applied ...
# 선택: pytest "tests/test_discount.py::TestDiscount::test_rate_applied"
#       pytest -k "discount and not slow"      pytest -m slow       pytest --lf

unittest.mock은 수집에 개입하지 않지만 관례가 한 번 더 등장한다. @patch를 클래스에 붙이면 patch.TEST_PREFIX(기본 "test")로 시작하는 메서드에만 적용된다 — 이름 관례를 어긴 메서드는 수집에서 빠지는 동시에, 수집되더라도 패치를 받지 못한다. 선택 실행은 노드 ID(파일::클래스::함수[파라미터]), -k 표현식, -m 마커, 직전 실패 재실행 --lf가 기본 도구다.

Python 관점의 통찰: pytest의 수집은 곧 import다 — 테스트 모듈의 최상위 코드가 실제로 실행되므로 그 시점의 import 오류·부작용은 "collection error"로 시끄럽게 드러나지만, 데코레이터는 정의 시점에 실행되는 평범한 함수 호출이라 오타 마커도 그저 함수 객체의 속성(pytestmark)으로 얌전히 붙을 뿐 오류가 아니다 — 그래서 --strict-markers가 필요하다. 비동기의 침묵도 객체 모델의 귀결이다: async def 함수를 호출하면 본문은 한 줄도 실행되지 않고 코루틴 객체만 반환되며, 그 객체는 이벤트 루프에 넘겨지지 않으면 가비지 컬렉션 때 "never awaited" 경고를 남기고 사라진다. 러너가 이 객체를 실행하려면 플러그인이 루프를 제공해야 하고, 마커는 그 플러그인에게 "이 테스트는 네 것"이라고 알리는 유일한 수단이다.

8.4 C++ — GoogleTest + GoogleMock: 등록은 링커가 결정한다

GoogleTest의 TEST(Suite, Name) 매크로는 테스트 클래스를 정의하고, 그 옆에 전역 객체를 하나 만들어 정적 초기화 시점에 레지스트리에 등록한다. 즉 2절의 정적 등록형이며, 등록은 main()이 시작되기도 전에 끝난다. 이 구조의 귀결이 C++만의 조용한 제외다: 등록 객체가 최종 실행 파일 안에 존재해야 등록이 일어난다. 테스트 소스를 정적 라이브러리(.a·.lib)로 묶어 링크하면, 링커는 실행 파일에서 참조되지 않는 목적 파일을 통째로 버린다 — 테스트 등록 객체는 아무도 참조하지 않으므로 함께 버려지고, 컴파일도 링크도 성공한 채 테스트만 사라진다.

대책은 링크 단위를 바꾸는 것이다: 테스트 소스를 실행 파일 타깃에 직접 넣거나, 아카이브 전체를 강제로 포함하는 링커 옵션(--whole-archive 계열)을 쓴다. CMake의 gtest_discover_tests는 빌드 후 실행 파일에 --gtest_list_tests를 돌려 그 결과를 CTest에 등록한다 — 4절의 "수집 목록 확인"을 빌드 시스템이 자동으로 수행하는 셈이며, 소스를 정규식으로 훑는 구형 gtest_add_tests보다 매크로 변형에 강하다. 

// discount_test.cpp — 이 목적 파일이 실행 파일에 링크되어야만 아래 등록이 존재한다
#include <gtest/gtest.h>
#include <gmock/gmock.h>

TEST(DiscountTest, AppliesTenPercent) {            // 정적 초기화 시 레지스트리에 등록
    EXPECT_EQ(apply_discount(10000, 0.1), 9000);
}

TEST(DiscountTest, DISABLED_RoundsHalfUp) {        // 접두사로 비활성 — 보고서에 "YOU HAVE 1 DISABLED TEST"
    EXPECT_EQ(apply_discount(10001, 0.1), 9001);
}

class MockNotifier : public Notifier {
public:
    MOCK_METHOD(bool, send, (const std::string&), (override));
};

TEST(OrderTest, NotifiesOnPlace) {
    MockNotifier n;
    EXPECT_CALL(n, send("order-1")).WillOnce(testing::Return(true));  // 검증은 n의 소멸 시점
    place_order(n, "order-1");
}
// 확인: ./discount_test --gtest_list_tests
// 선택: ./discount_test --gtest_filter='DiscountTest.*:-*Slow*'   --gtest_also_run_disabled_tests

선택 실행은 --gtest_filter의 포함패턴:-제외패턴 문법이고, DISABLED_ 접두는 skip에 해당하되 보고서 끝에 비활성 테스트 수를 눈에 띄게 출력한다(6절의 "세어지는 제외"). 파라미터화 테스트(TEST_P)는 INSTANTIATE_TEST_SUITE_P로 인스턴스화해야 케이스가 생기는데, 최근 안정판은 인스턴스화되지 않은 스위트를 기본적으로 오류로 보고한다 — 이것도 조용한 제외의 도구 차원 승격이다. gMock의 EXPECT_CALL은 mock 객체가 소멸할 때 검증되므로, 테스트 본문이 등록되지 않으면 기대도 검증도 함께 사라진다.

C++ 관점의 통찰: 다른 언어의 수집이 "런타임에 이름을 훑는 일"이라면 C++의 수집은 "이진 파일에 코드가 존재하는가"라는 링크 타임의 문제다 — 링커의 미참조 제거는 K4의 죽은 코드 제거와 같은 기제이며, 테스트 등록 객체는 정의상 아무도 참조하지 않으므로 링커에게는 죽은 코드로 보인다. 정적 초기화에 기대는 설계의 또 다른 주의점은 초기화 순서다: 서로 다른 번역 단위의 정적 객체는 초기화 순서가 정의되지 않으므로, 등록 시점에 다른 파일의 전역 객체를 참조하는 픽스처는 미정의 동작에 빠질 수 있다. 등록이 main() 전에 끝난다는 사실은 편리함이자, 디버거를 붙이기 전에 이미 수집이 결정되어 있다는 뜻이기도 하다.

9. 함께 알면 좋은 것

본문의 두 축을 도구·기법 어휘로 확장한 것들이다 — 첫째·둘째는 5절의 선택 실행을, 셋째는 4절의 빨간불 확인을, 넷째는 4절의 테스트 수 감시를, 다섯째는 2절의 관례 등록을 잇는다.

  • 변경 기반 테스트 선택(test impact analysis) — 변경된 파일과 의존 관계로 연결된 테스트만 골라 실행하는 기법(감시 모드의 관련 테스트 실행, 변경 파일 기준 필터). 5절의 선택 실행을 자동화한 형태이며, 간접 의존을 놓치는 한계 때문에 커밋 게이트는 여전히 전체 실행이다.
  • 실패 우선·직전 실패 재실행 — 마지막 실행의 실패만 다시 돌리거나(--lf) 실패한 것을 먼저 돌리는 옵션. 선택 표현식을 손으로 쓰지 않고도 피드백 루프를 줄이는 이력 기반 선택.
  • 뮤테이션 테스트 — 코드를 일부러 변형해 테스트가 잡아내는지로 검증력을 측정하는 기법. 수집되지 않았거나 본문이 실행되지 않는 테스트는 변이를 하나도 잡지 못하므로, 4절의 빨간불 확인을 스위트 전체에 자동으로 적용한 것과 같다.
  • 테스트 보고서 표준과 개수 추이 — 러너들이 공통으로 내는 XML 보고서 형식을 CI가 읽어 총 개수·건너뜀 수의 추이를 그리면, 4절의 테스트 수 감시와 6절의 "상수가 된 skip 수"를 사람이 아니라 대시보드가 읽게 된다.
  • 관례 등록의 다른 얼굴 — 픽스처·확장의 자동 로드 — pytest의 conftest.py, JUnit의 확장 자동 등록처럼 테스트가 아닌 구성 요소도 관례로 등록된다. 파일명·위치가 틀리면 픽스처가 조용히 로드되지 않는 것도 같은 원리의 함정이다.

10. 한 장 요약

  • 러너의 일은 수집 → 선택 → 실행 → 보고이고, 초록불은 "수집된 것 중 실패 없음"만 뜻한다. 수집되지 않은 테스트는 통과·실패·건너뜀 어디에도 세어지지 않는 "안 돌았음" 상태다.
  • 수집은 파일·컨테이너·케이스·속성 네 층의 관례가 AND로 겹친 암묵 등록이며, 층마다 소유자(빌드 도구·프레임워크·플러그인)가 다르다.
  • 관례 불일치는 오류가 아니라 "테스트가 아님"으로 해석된다 — 이름 오타·어노테이션 누락·마커 오타·비동기 마커 누락·링크 누락이 조용한 제외를 만들고, 신규 테스트는 기준선에 없어 소실조차 감지되지 않는다.
  • 발각은 수집 목록 확인 → 테스트 수 감시 → 빨간불 확인의 세 층, 그 위에 미등록 마커·미실행 비동기·0개 매치를 오류로 승격시키는 도구 옵션.
  • 선택 실행(노드 ID·표현식·태그·only)은 개발 시간의 도구, 전체 실행은 커밋의 게이트. 코드 안의 only/skip은 린트·CI 플래그·사유 있는 조건부 skip으로 잔존을 막는다.
  • 언어별 제외 지점: Java는 빌드 도구 패턴·엔진, JS·TS는 글롭과 await 누락, Python은 이름 관례·마커·코루틴, C++은 링커의 미참조 제거.

관련 문서

  • J12 목킹 주입 2패러다임 — 객체 교체 vs 이름 패치.html — 이 문서와의 접점: 이름 패치(@patch)와 객체 교체(@Mock 주입)는 테스트가 실행되어야 작동하는 장치다. 수집에서 빠진 테스트는 대역 설정도, 엄격 스텁 검증도 함께 잃으며, Python의 클래스 단위 @patch는 수집 관례(test 접두)를 그대로 재사용한다
  • K5 조용한 실패와 오타.html — 이 문서와의 접점: 관례 불일치·마커 오타로 테스트가 목록에서 빠지는 것은 "오류가 있는데 신호가 없다"는 조용한 실패의 테스트판이다. K5의 발각 원리(신호를 강제로 만든다)가 여기서는 수집 목록 확인·빨간불 확인·오류 승격 옵션으로 나타난다

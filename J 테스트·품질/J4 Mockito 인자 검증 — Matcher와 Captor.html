J4 Mockito 인자 검증 — Matcher와 Captor

0. 한눈에 보는 결론

  • 행위 검증의 질문은 "호출됐는가"에서 끝나지 않는다 — "무엇을 들고 호출됐는가"까지 물어야 요구사항 검증이 된다. 그 인자를 다루는 도구가 매처(matcher)와 캡터(captor) 둘이다.
  • 매처(any()·anyString()·eq()·argThat())는 인자에 조건을 건다. 요구사항에 해당하는 부분만 고정하고 나머지는 열어 두어, 검증이 구현 세부에 결합되는 것을 막는다.
  • 매처는 값이 아니라 내부 스택에 남는 기록이다. 메서드가 호출되는 순간 기록 개수가 파라미터 개수와 일치해야 하므로 "모두 매처거나 모두 실값"이라는 혼용 규칙이 생기고, 어기면 InvalidUseOfMatchersException이다. 실값은 eq()로 감싸 매처로 승격시킨다.
  • 캡터(ArgumentCaptor)는 넘어간 인자를 값으로 꺼내 일반 단언에 넘긴다 — 행위 검증을 상태 검증으로 되돌리는 기법이고, 반환값이 없는 void 메서드를 검증하는 정석이다.
  • 캡터도 매처의 일종이라 혼용 규칙을 그대로 따르고, 타입 소거 때문에 제네릭 캡터는 @Captor(또는 최근의 ArgumentCaptor.captor())로 선언해야 경고 없이 안전하다.
  • 고전적 함정: Mockito 2 이후 any()는 null을 매칭하지 않는다. 매처 규칙을 지켜도 "통과해야 할 테스트가 실패"하는 대표 원인이다.

1. 전제 — 행위 검증은 "무엇이 넘어갔나"까지 물어야 완성된다

J3에서 본 Mockito의 3단계(대역 준비 → 스텁 → verify)의 마지막 단계는 행위 검증(behavior verification), 즉 "협력자의 메서드가 호출되었는가"를 묻는 일이다. 그런데 호출 사실만으로는 요구사항이 검증되지 않는 경우가 대부분이다. "주문이 확정되면 그 고객에게 확정 알림을 보낸다"는 요구사항에서 send가 한 번 불렸다는 사실은 절반이고, 어떤 알림이 넘어갔는가가 나머지 절반이다. 

// 대상: 주문 확정 시 알림 발송 — 반환값이 없다(void)
public class OrderService {
    private final NotificationSender sender;
    public OrderService(NotificationSender sender) { this.sender = sender; }

    public void confirm(Order order) {
        sender.send(new Notification(order.customerId(), "주문 " + order.id() + " 확정"));
    }
}

이 메서드는 void다 — 반환값을 단언할 수 없으니 협력자에게 넘긴 인자가 유일한 관측 지점이다. verify(sender).send(...)의 괄호 안에 무엇을 쓰느냐가 곧 인자 검증의 전부인데, Mockito는 기본적으로 인자를 equals로 비교한다. 즉 verify(sender).send(new Notification("c-1", "주문 o-1 확정"))처럼 기대 인자를 통째로 실값으로 써야 하고, 그러려면 Notification이 equals를 올바르게 구현했어야 하며, 메시지 문구 한 글자만 바뀌어도 테스트가 깨진다. J5가 경고한 구현 세부에의 과잉 결합이 바로 이 지점에서 시작된다. 그렇다면 인자의 "어디까지"를 고정할지 고를 수는 없을까 — 그것이 매처의 역할이다.

2. 매처 — 인자에 값 대신 조건을 건다

인자 매처(argument matcher)는 "이 값이어야 한다" 대신 "이 조건을 만족하면 된다"를 인자 자리에 놓는 도구다. Mockito의 ArgumentMatchers가 제공하는 것을 넓이 순으로 놓으면 이렇다.

매처조건쓰임
any()아무 값(단, null 제외 — 4절)"호출됐다"만 확인할 때
any(Notification.class)·anyString()·anyInt()해당 타입의 아무 값타입만 고정하고 내용은 열어 둘 때
eq(값)equals로 같은 값실값을 매처로 승격시킬 때(3절)
argThat(조건식)람다·ArgumentMatcher가 참요구사항에 해당하는 속성만 고정할 때
isNull()·nullable(타입)null / null 또는 해당 타입null이 정당한 인자일 때
// 요구사항: "그 고객에게" 보낸다 — 수신자만 고정, 문구는 열어 둔다
verify(sender).send(argThat(n -> n.recipient().equals("c-1")));

// 요구사항이 "보낸다"뿐이라면 타입까지만
verify(sender).send(any(Notification.class));

매처의 가치는 고정의 범위를 요구사항의 범위에 맞추는 것이다. 문구가 요구사항이 아니라면 문구를 고정하지 않고, 수신자가 요구사항이라면 수신자만 고정한다 — 그래야 문구를 손보는 리팩토링이 테스트를 깨뜨리지 않는다. 매처는 verify뿐 아니라 스텁(when(repo.find(anyString())))에도 같은 문법으로 쓰이며, 스텁에서는 "어떤 인자가 오든 이 값을 돌려준다"는 뜻이 된다.

그런데 여기서 입문자가 거의 반드시 부딪히는 예외가 있다. 두 파라미터 중 하나만 열어 두려고 when(repo.find(anyString(), "KR"))이라고 쓰는 순간 Mockito는 InvalidUseOfMatchersException을 던진다. 왜 하나만 매처로 쓰는 것이 금지되는가 — 이 규칙은 관례가 아니라 매처의 구현 원리에서 나온다.

3. 혼용 규칙의 원리 — 매처는 값이 아니라 스택에 남는 기록이다

anyString()은 Java 관점에서 그저 String을 반환하는 정적 메서드다. 그런데 "아무 문자열"이라는 조건을 String 타입의 값 하나에 담을 방법은 없다 — anyInt()라면 더 분명해서, int에는 "아무 정수"를 표시할 특별한 값이 존재하지 않는다. 그래서 Mockito는 매처를 반환값이 아니라 곁길(side channel)로 전달한다: 매처 메서드는 호출되는 순간 자신을 스레드 로컬 저장소(스레드마다 하나씩 따로 두는 변수 — 여기서는 ArgumentMatcherStorage)에 밀어 넣고, 반환값으로는 타입만 맞춘 더미(anyString()은 빈 문자열, anyInt()는 0, any()는 null)를 돌려준다. 그다음 대역의 메서드가 실제로 호출되면, 대역은 인자로 받은 더미 값들을 무시하고 저장소에 쌓인 매처들을 꺼내 파라미터에 순서대로 대응시킨다.

when(repo.find(anyString(), "KR")) // 파라미터 2개 1. anyString() 실행 → 저장소: [Any<String>] 반환값 ""(더미) 2. "KR"은 그냥 값 → 저장소에 아무것도 남지 않음 3. repo.find("", "KR") 호출 → 대역이 가로채 저장소를 확인 매처 1개 ≠ 파라미터 2개 → 대응 불가 → InvalidUseOfMatchersException ("2 matchers expected, 1 recorded") when(repo.find(anyString(), eq("KR"))) // 저장소: [Any<String>, Eq("KR")] → 2 = 2 ✓ when(repo.find("o-1", "KR")) // 저장소: [] → 0개면 전부 equals 비교 ✓

이제 규칙의 정체가 보인다. 대역이 호출 시점에 볼 수 있는 것은 저장소의 매처 개수와 파라미터 개수뿐이고, 둘이 다르면 어느 파라미터가 매처이고 어느 것이 실값인지 복원할 방법이 없다(저장소는 순서만 알지 "몇 번째 파라미터용"인지는 모른다). 그래서 허용되는 상태는 두 가지뿐이다 — 저장소가 비어 있어 전부 equals로 비교하거나, 저장소 개수가 파라미터 개수와 같아 전부 매처로 비교하거나. "모두 매처거나 모두 실값"은 이 두 상태를 문장으로 옮긴 것이고, eq()는 실값을 저장소에 기록되는 매처로 감싸 두 번째 상태를 만드는 승격 도구다.

부작용 — 예외가 엉뚱한 줄에서 난다: 매처가 저장소에 남았는데 소비되지 않으면(예: if (any() != null)처럼 대역 호출 밖에서 매처를 부르거나, 대역이 아닌 실제 객체의 메서드에 매처를 넘긴 경우) 저장소에 매처가 잔류한 채 테스트가 진행되고, 다음 대역 상호작용이나 테스트 종료 시점의 사용 검사에서 "Misplaced or misused argument matcher"가 터진다. 예외가 가리키는 줄이 아니라 그 앞에서 매처를 호출한 줄을 의심해야 한다.

규칙과 원리는 이해했다. 그러나 규칙을 완벽히 지켜도 "통과해야 할 테스트가 실패"하거나, 더 나쁘게 "실패해야 할 테스트가 통과"하는 함정이 매처에는 따로 있다.

4. 매처의 함정 — any()는 null을 매칭하지 않고, 넓은 매처는 검증을 비운다

첫째 함정은 null이다. Mockito 1에서 any()는 문자 그대로 아무 값(null 포함)이었지만, Mockito 2부터 any()·any(타입)·anyString()은 null을 매칭하지 않는다. 그래서 대상 코드가 어떤 파라미터에 null을 넘기는 경로가 있으면, verify(repo).save(any(), anyString())은 "호출된 적 없다"로 실패한다 — 호출은 분명히 됐는데 인자 하나가 null이라 매처가 거부한 것이다. null이 정당한 인자라면 isNull()로 명시하고, null일 수도 아닐 수도 있다면 nullable(String.class)를 쓴다. 이 변경은 의도된 것이다 — "아무 값"에 null까지 포함하면 null이 잘못 흘러드는 결함을 매처가 덮어 버리기 때문이다.

둘째 함정은 반대 방향, 즉 매처가 너무 넓어 검증이 비어 버리는 것이다. verify(sender).send(any())는 알림을 엉뚱한 고객에게 보내도, 빈 메시지를 보내도 통과한다. 이것은 "호출됐다"만 검증하는 테스트이며, 그 자체로 잘못은 아니지만 인자를 검증했다고 착각하는 것이 문제다. 스텁 쪽에서도 같은 일이 생긴다: when(repo.find(any(), any()))는 대상 코드가 인자를 뒤바꿔 넘겨도 정상 응답을 돌려주므로 결함이 조용히 통과한다. 

// 함정 ①: 대상 코드가 두 번째 인자로 null을 넘기는 경로
service.register(order);                       // 내부에서 repo.save(order, null) 호출
verify(repo).save(any(), anyString());         // 실패 — anyString()은 null 거부
verify(repo).save(any(), isNull());            // 통과 — null을 명시

// 함정 ②: 넓은 매처는 "호출됐다"만 남긴다
verify(sender).send(any());                    // 수신자가 틀려도 통과
verify(sender).send(argThat(n -> n.recipient().equals("c-1")));   // 요구사항만큼만 좁힌다

argThat으로 좁히면 두 번째 함정은 해소된다. 그러나 argThat에는 한계가 있다 — 조건식은 참·거짓만 답하므로 실패했을 때 메시지가 "매칭되는 호출이 없다"에 그치고, 확인할 속성이 서너 개면 람다가 길어지며, 조건식 안에서 던진 예외는 매칭 실패로만 보인다. "무엇이 넘어갔는지를 값으로 꺼내, 익숙한 단언으로 하나씩 비교할 수는 없을까"가 다음 질문이고, 그 답이 캡터다.

5. 캡터 — 넘어간 값을 꺼내 상태 검증으로 되돌린다

인자 캡터(argument captor)는 매칭 대신 기록을 하는 매처다. captor.capture()를 인자 자리에 놓으면 모든 값을 매칭하되(넓이는 any()급), 그 값을 캡터 안에 저장해 두었다가 getValue()로 꺼내 준다. 꺼낸 순간부터는 일반 객체이므로 assertEquals·assertTrue 같은 보통의 상태 단언을 쓸 수 있다. 

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock NotificationSender sender;
    @Captor ArgumentCaptor<Notification> captor;
    @InjectMocks OrderService service;

    @Test
    void 확정_시_해당_고객에게_확정_알림을_보낸다() {
        service.confirm(new Order("o-1", "c-1"));

        verify(sender).send(captor.capture());        // 행위: send가 한 번 호출됐다
        Notification sent = captor.getValue();        // → 넘어간 값을 꺼낸다
        assertEquals("c-1", sent.recipient());        // 상태: 익숙한 단언으로 검증
        assertTrue(sent.message().contains("o-1"));
    }
}

이것이 J5가 말한 "행위 검증을 상태 검증으로 되돌리기"의 실행형이다. 검증의 형식은 여전히 verify(행위)이지만, 실제 판단은 꺼낸 객체의 상태에 대해 이루어진다. 얻는 것은 세 가지다: 실패 메시지가 "기대 c-1, 실제 c-2"처럼 값 수준으로 나오고, 여러 속성을 단언 여러 줄로 자연스럽게 나눌 수 있으며, 무엇을 검증하는지가 조건식 안에 숨지 않고 테스트 본문에 드러난다. 그리고 1절의 문제 — void 메서드는 반환값이 없어 관측할 것이 인자뿐이라는 문제 — 에 대한 정석 답이 된다. 반환값 대신 인자를 관측 결과로 승격시키는 것이다.

여러 번 호출된 메서드라면 verify(sender, times(2)).send(captor.capture()) 뒤에 getAllValues()로 리스트를 받는다. 이때 getValue()는 마지막 값 하나만 돌려준다는 점을 기억해야 한다.

편리하지만, 캡터도 결국 매처다. 즉 3절의 저장소에 기록되고 혼용 규칙의 지배를 받으며, 여기에 제네릭이라는 Java 고유의 문제가 얹힌다.

6. 캡터의 규율 — 혼용 규칙, 제네릭 안전성, 그리고 매처와의 선택

capture()는 저장소에 기록되는 매처이므로 verify(repo).save(captor.capture(), "KR")은 3절과 똑같이 InvalidUseOfMatchersException이다 — 나머지 인자도 eq("KR")로 승격시켜야 한다. 같은 이유로 캡터는 verify 안에서 쓰는 것이 원칙이며, 스텁(when) 안에서의 사용은 Mockito 문서가 권장하지 않는다 — 값을 꺼내는 시점과 호출 시점의 관계가 흐려져 가독성만 나빠진다. 또 verify가 실패하면 getValue()까지 도달하지 않고, verify 없이 getValue()를 부르면 "캡처된 값이 없다"는 예외가 난다.

제네릭 문제는 타입 소거(type erasure) — Java 제네릭의 타입 인자가 컴파일 후 바이트코드에서 지워져, 런타임에는 List<String>과 List<Integer>를 구분할 수 없다는 성질 — 에서 온다. ArgumentCaptor.forClass(List.class)는 Class 객체를 받는데 List<String>.class라는 것은 존재하지 않으므로, 결과는 원시 타입(raw type) ArgumentCaptor<List>이고 이를 ArgumentCaptor<List<String>>에 대입하려면 비검사 경고(unchecked warning)를 감수한 캐스팅이 필요하다. 

// 경고를 부르는 형태 — 런타임에 List<String>임을 검사할 방법이 없다
ArgumentCaptor<List<String>> c1 = (ArgumentCaptor<List<String>>) (Object) ArgumentCaptor.forClass(List.class);

// 안전한 형태 ①: 필드 선언의 타입 인자를 확장이 읽어 준다
@Captor ArgumentCaptor<List<String>> c2;

// 안전한 형태 ②(Mockito 5.9, 2023년 이후): 대입 대상 타입으로 추론
ArgumentCaptor<List<String>> c3 = ArgumentCaptor.captor();

@Captor가 안전한 이유는 검사를 하기 때문이 아니라 검사가 필요 없기 때문이다 — 캡터는 어차피 넘어온 객체를 그대로 저장할 뿐이고, 필드 선언의 타입 인자는 컴파일러가 꺼낼 때의 타입을 정하는 데만 쓰인다. 원시 타입을 거치지 않으니 경고가 날 자리가 없다.

매처인가 캡터인가 — 선택 기준: 확인할 것이 조건 하나("이 고객에게")이고 실패 메시지가 단순해도 되면 argThat, 확인할 속성이 둘 이상이거나 값 수준의 실패 메시지가 필요하거나 void 메서드의 인자가 유일한 관측 지점이면 캡터. 어느 쪽이든 고정 범위는 요구사항만큼만 — 캡터로 꺼낸 뒤 객체 전체를 equals로 비교하면 1절의 과잉 결합으로 되돌아간다.

도구 두 개의 원리·규칙·선택 기준을 모두 봤다. 남는 것은 이 둘을 둘러싼 오해들이다.

7. 흔히 헷갈리는 지점

① "verify(sender).send(any())가 통과했으니 인자도 검증됐다"? — 아니다. any()는 호출 사실만 남기고 인자는 아무것도 묻지 않는다. 인자에 대한 요구사항이 있다면 argThat으로 좁히거나 캡터로 꺼내야 한다(4절). 반대로 요구사항이 정말 "호출된다"뿐이라면 any()가 정직한 표현이다.

② "예외가 가리키는 줄에는 매처가 없는데 InvalidUseOfMatchersException이 난다" — 매처는 저장소에 기록되었다가 대역 호출에서 소비된다. 앞 줄에서 소비되지 못한 매처(대역이 아닌 실제 객체에 넘겼거나, 대역 호출 밖에서 부른 경우)가 잔류하면 다음 대역 상호작용에서 터진다(3절). 예외 위치가 아니라 직전 매처 호출을 찾는다.

③ "verify가 없어도 captor.getValue()는 마지막 호출 값을 돌려준다"? — 캡터는 capture()가 매처로 소비될 때만 값을 기록한다. verify(또는 스텁) 안에서 capture()가 실행되지 않았다면 기록은 비어 있고 getValue()는 예외다. 캡터는 도청 장치가 아니라 verify의 인자 자리다(6절).

④ "times(2)로 검증했으니 getValue()에 두 값이 다 있다"? — getValue()는 마지막 값 하나다. 여러 호출의 인자는 getAllValues()로 리스트를 받아야 하고, 순서는 호출 순서다(5절). 첫 호출을 검증하려고 getValue()를 쓰면 조용히 마지막 호출을 검증하게 된다.

★ 8. 언어별 대조

매처와 캡터라는 두 역할은 어느 언어의 대역 라이브러리에도 있다. 다만 혼용 규칙은 Mockito 특유의 것이다 — 그 규칙은 "매처를 값으로 표현할 수 없다"는 Java 정적 타입 시스템의 제약에서 나왔고(3절), 매처를 일급 객체로 넘길 수 있는 언어에서는 성립하지 않는다. 각 도구에서 두 역할이 어떤 API로 나타나고 그 언어만의 함정이 무엇인지 대조한다.

언어 / 도구매처(조건)캡터(값 꺼내기)혼용 규칙그 언어만의 함정
Java / JUnit 5 + Mockito any()·eq()·argThat() ArgumentCaptor·@Captor 있음(스레드 로컬 저장소) any()의 null 거부, 제네릭 캡터의 비검사 경고
JS·TS / Jest·Vitest expect.any()·expect.objectContaining() fn.mock.calls[i][j] 없음(매처가 값 객체) toHaveBeenCalledWith는 깊은 동등성 — 참조가 아니라 구조를 비교
Python / pytest + unittest.mock ANY·__eq__ 재정의 객체 call_args·call_args_list 없음(== 프로토콜) ANY는 None도 매칭, 위치·키워드 인자 구분
C++ / GoogleTest + gMock _·Eq()·Field()·Truly() SaveArg<N>() 액션 없음(실값은 Eq로 암묵 변환) 기대를 호출 전에 선언, 저장은 복사 — 수명·복사 가능성

8.1 Java — JUnit 5 + Mockito: 정적 타입이 만든 규칙과 타입 소거가 만든 경고

본문이 이미 Java로 쓰였으므로 여기서는 왜 하필 Java에서 이런 모양이 되었는가를 JVM·타입 시스템 관점에서 정리한다. 매처가 곁길(스레드 로컬 저장소)을 쓰는 근본 이유는 정적 타입이다: anyInt()의 반환 타입은 int여야 대역 메서드의 시그니처에 맞고, int에는 "조건"을 실어 보낼 자리가 없다. 저장소가 스레드 로컬인 것도 같은 설계의 귀결이라, 다른 스레드에서 호출한 매처는 이 스레드의 대역이 볼 수 없다 — 비동기 코드 검증에서 매처가 "없다"고 나오는 원인 중 하나다.

제네릭 캡터의 경고는 타입 소거의 귀결이고(6절), 반대로 any(Notification.class)가 any()와 달리 런타임 타입 검사를 하는 것은 소거되지 않는 원시 Class 객체를 받기 때문이다 — send(Object) 같은 넓은 시그니처에서 두 매처의 차이가 드러난다. 

@ExtendWith(MockitoExtension.class)
class OrderRepositoryTest {
    @Mock OrderRepository repo;
    @Captor ArgumentCaptor<List<String>> idsCaptor;     // 타입 소거를 우회하는 선언

    @Test
    void 일괄_보관_시_주문_id_목록을_지역_코드와_함께_넘긴다() {
        new OrderBatch(repo).archive(List.of("o-1", "o-2"), "KR");

        // 캡터도 매처 — 나머지 인자는 eq()로 승격해야 혼용 규칙을 만족한다
        verify(repo).archiveAll(idsCaptor.capture(), eq("KR"));
        assertEquals(List.of("o-1", "o-2"), idsCaptor.getValue());

        // 스텁 쪽 매처: 기본 strict stubs에서는 스텁 인자와 실제 호출 인자가
        // 어긋나면 PotentialStubbingProblem — 넓은 any()는 이 검출을 무디게 한다
    }
}

생태계 관행 하나를 덧붙이면, JUnit 5 확장(MockitoExtension)은 2020년대 중반 기준 기본 엄격도가 strict stubs여서 스텁의 인자와 실제 호출의 인자가 어긋나면 실패로 알려 준다. 스텁에 any()를 남발하면 이 안전장치가 무력해지므로, 스텁에서도 "요구사항만큼만 넓게"라는 2절의 원칙이 그대로 적용된다. Mockito 5(2023년 이후)는 인라인 mock maker가 기본이 되어 final 클래스도 대역으로 만들 수 있게 됐지만, 매처·캡터의 동작 원리는 그대로다.

8.2 JS·TS — Jest / Vitest: 매처가 값 객체라 혼용 규칙이 없다

Jest와 Vitest(문법이 거의 같고, Vitest는 vi.fn()·모듈 처리 방식이 다르다)의 비대칭 매처(expect.any(Number)·expect.objectContaining({...}))는 그냥 객체다. 동적 타입 언어라 인자 자리에 어떤 객체든 놓을 수 있고, 비교 시점에 그 객체가 "나는 매처"라고 답하면 동등성 비교기가 조건 매칭으로 전환한다. 곁길이 필요 없으니 실값과 매처를 자유롭게 섞을 수 있다. 캡터에 해당하는 것은 별도 도구가 아니라 대역 함수가 항상 기록해 두는 mock.calls다 — 모든 호출의 인자 배열이 남아 있으므로 "꺼내는 절차" 자체가 없다. 

const sender = { send: vi.fn() };                // Jest라면 jest.fn()
new OrderService(sender).confirm({ id: "o-1", customerId: "c-1" });

// 매처: 부분 구조만 고정 — 실값("c-1")과 매처(expect.any)를 섞어도 된다
expect(sender.send).toHaveBeenCalledWith(
  expect.objectContaining({ recipient: "c-1", message: expect.any(String) })
);

// 캡터: 기록된 호출에서 그대로 꺼낸다 — 첫 호출의 첫 인자
const [sent] = sender.send.mock.calls[0];
expect(sent.message).toContain("o-1");

이 언어의 함정은 다른 곳에 있다. toHaveBeenCalledWith는 깊은 동등성(toEqual과 같은 재귀 구조 비교)이라 참조가 달라도 내용이 같으면 통과하고, 반대로 undefined 속성의 유무 같은 미세 차이에서 예상 밖으로 갈린다. 또 expect.any(Object)는 Java의 any()처럼 null·undefined를 거부하지만 expect.anything()도 마찬가지이므로, null이 정당한 인자면 실값 null을 그대로 쓴다. TS에서는 mock.calls[0]의 원소 타입이 대역 함수의 시그니처에서 추론되어 꺼낸 값에 타입이 붙는다 — 단 이 타입은 컴파일 시 소거되므로 런타임 검사가 아니라 편집기 안내일 뿐이다.

8.3 Python — pytest + unittest.mock: 매칭은 ==이고, 캡처는 이미 되어 있다

unittest.mock의 매처는 ANY 하나가 사실상 전부이고, 그 정체는 __eq__가 항상 True를 돌려주는 객체다. assert_called_once_with(...)는 기록된 호출의 인자 튜플과 기대 튜플을 ==로 비교할 뿐이므로, __eq__를 재정의한 어떤 객체든 매처가 된다 — argThat에 해당하는 것을 클래스 하나로 직접 만든다. 혼용 규칙이 없는 이유도 같다: 매처가 값이니 곁길이 없다. 

from unittest.mock import Mock, ANY

def test_confirm_sends_notification_to_customer():
    sender = Mock()
    OrderService(sender).confirm(Order(id="o-1", customer_id="c-1"))

    sender.send.assert_called_once_with(ANY)          # 매처: 호출 사실 + 인자 1개
    (sent,), kwargs = sender.send.call_args           # 캡터: 마지막 호출의 (args, kwargs)
    assert sent.recipient == "c-1"                    # 상태 단언으로 전환
    assert "o-1" in sent.message

함정은 두 가지다. 첫째, ANY는 None도 매칭한다 — Java와 정반대라, None이 잘못 흘러든 결함을 ANY가 덮는다. None이 오면 안 된다면 값을 꺼내 직접 단언해야 한다. 둘째, call_args는 위치 인자와 키워드 인자를 구분해 저장하므로, 대상 코드가 send(notification=n)처럼 키워드로 호출하면 call_args.args는 비어 있고 call_args.kwargs["notification"]에 있다. create_autospec(실제 시그니처를 본뜬 대역)을 쓰면 호출이 시그니처에 결속되어 위치·키워드 어느 쪽으로 호출했든 같은 기대식으로 검증된다.

Python 관점의 통찰: Mock이 캡처를 별도 도구 없이 제공하는 것은 객체 모델 덕분이다 — 속성 접근이 자식 Mock을 지연 생성하고, 호출은 call 객체(인자 튜플과 딕셔너리)로 남으므로 "기록"이 곧 기본 동작이다. 매칭이 == 프로토콜 하나로 통일된 대가로, 검증의 정밀도는 인자 객체의 __eq__ 구현에 좌우된다: dataclass(eq=True)라면 값 비교, 그렇지 않은 일반 클래스라면 정체성(identity) 비교여서 같은 내용의 다른 인스턴스를 넘겨도 검증이 실패한다.

8.4 C++ — GoogleTest + gMock: 매처는 템플릿, 캡처는 복사

gMock의 매처(_·Eq()·Field(&T::member, m)·Truly(람다))는 Matcher<T>로 변환되는 템플릿 객체이고, EXPECT_CALL의 인자 자리에 실값을 쓰면 컴파일러가 암묵적으로 Eq()로 감싼다. 매처와 값이 같은 타입 체계 안에서 처리되므로 혼용 규칙이 없고, 타입 불일치는 런타임 예외가 아니라 컴파일 오류다. 캡터에 해당하는 것은 매처가 아니라 액션이다: SaveArg<N>(&변수)는 N번째 인자를 지정한 변수에 복사해 둔다. 

class MockSender : public NotificationSender {
 public:
  MOCK_METHOD(void, Send, (const Notification&), (override));
};

TEST(OrderServiceTest, ConfirmSendsNotificationToCustomer) {
  MockSender sender;
  Notification sent;                                    // 캡처 대상 — 호출보다 오래 산다
  EXPECT_CALL(sender, Send(Field(&Notification::recipient, Eq("c-1"))))  // 매처
      .WillOnce(SaveArg<0>(&sent));                                          // 캡처(복사)

  OrderService service(sender);
  service.Confirm(Order{"o-1", "c-1"});                 // 기대는 호출 '전'에 선언되어 있다

  EXPECT_THAT(sent.message, HasSubstr("o-1"));          // 상태 단언
}

Mockito와 순서가 뒤집혀 있다는 점이 첫 특이점이다 — EXPECT_CALL은 호출 전에 선언하고, 매칭 여부는 호출 시점에, 기대 충족 여부는 대역이 소멸될 때 판정된다. 그래서 캡처된 값에 대한 단언은 호출 뒤에 놓을 수 있지만, "호출됐는가" 자체는 스코프 끝에서 보고된다.

C++ 관점의 통찰: SaveArg가 "복사"라는 사실이 이 언어의 함정을 결정한다. 인자 타입이 복사 불가(이동 전용)이면 SaveArg는 컴파일되지 않고, 인자가 참조라면 복사본을 저장하므로 원본이 호출 직후 소멸해도 안전하지만 — 포인터 인자를 저장했다면 그 포인터가 가리키는 객체의 수명은 테스트가 책임져야 한다. 매처 쪽에서는 Eq("c-1")의 비교 대상이 std::string 멤버라면 문자열 리터럴과의 비교가 템플릿 인스턴스화 시점에 결정되어, 잘못된 타입 조합은 실행 전에 컴파일 오류로 발각된다. 대역 검증의 상당 부분을 컴파일러가 대신하는 대신, 저장한 값의 수명과 소유권은 온전히 테스트 작성자의 몫이다.

9. 함께 알면 좋은 것

첫째·둘째는 6절의 선택 기준을, 셋째는 4절의 null 함정을, 넷째는 8.1의 strict stubs를, 다섯째는 5절의 "인자를 관측 결과로 승격"을 잇는다.

  • 사용자 정의 ArgumentMatcher — argThat의 람다를 이름 있는 클래스로 추출하고 toString을 구현하면 실패 메시지에 조건의 이름이 찍힌다. 캡터로 갈아타지 않고도 4절의 "메시지가 빈약하다"는 한계를 일부 메우는 방법.
  • verifyNoMoreInteractions·never()·InOrder — "무엇이 넘어갔나"의 옆 질문들: 그 밖의 호출은 없었는가, 특정 호출이 없었는가, 순서는 맞는가. 매처·캡터와 조합되며, 남용하면 J5의 행위 검증 과잉으로 직행한다.
  • Optional·널 안전성 어노테이션 — any()가 null을 거부하게 된 배경과 같은 문제의식. 대상 코드가 null을 넘길 여지를 설계에서 줄이면 isNull()·nullable()이 필요한 테스트 자체가 줄어든다.
  • strict stubs와 lenient() — 스텁 인자와 실제 호출 인자의 불일치를 실패로 보고하는 엄격 모드와, 특정 스텁만 예외로 두는 완화 장치. 매처의 넓이가 이 안전장치의 감도를 결정한다.
  • 이벤트·메시지 발행 검증 — void 메서드로 이벤트를 발행하는 코드에서 캡터로 발행된 이벤트 객체를 꺼내 검증하는 것은 5절의 기법이 가장 자주 쓰이는 형태다. 발행된 객체가 곧 "관측 가능한 결과"가 된다.

10. 한 장 요약

  • 행위 검증은 "호출됐는가"에 "무엇을 들고"를 더해야 요구사항 검증이 된다 — 특히 void 메서드는 인자가 유일한 관측 지점이다.
  • 매처는 인자에 조건을 걸어 고정 범위를 요구사항만큼으로 줄인다. any()는 호출 사실만, argThat은 조건, eq()는 실값의 매처 승격.
  • 매처는 값이 아니라 스레드 로컬 저장소의 기록이고, 호출 시 기록 개수 = 파라미터 개수여야 한다 → "모두 매처거나 모두 실값", 위반은 InvalidUseOfMatchersException(때로 다음 줄에서).
  • Mockito 2 이후 any()는 null을 거부한다 — isNull()·nullable()로 명시. 너무 넓은 매처는 검증을 비운다.
  • 캡터는 넘어간 값을 꺼내 보통의 단언에 넘기는 행위→상태 전환 도구. verify 안에서만, 나머지 인자는 eq()로, 여러 호출은 getAllValues()로.
  • 제네릭 캡터는 타입 소거 때문에 forClass가 경고를 부른다 — @Captor 또는 ArgumentCaptor.captor()로 선언. 혼용 규칙은 Java 정적 타입의 산물이라 매처가 값인 언어(JS·Python·C++)에는 없다.

J18 다층 방어의 층별 검증 — 무증상 퇴화

0. 한눈에 보는 결론

  • 웹 애플리케이션의 입력 검증은 보통 여러 층이 같은 규칙을 겹쳐 지킨다 — 프론트 폼 검증 → API 요청 검증 → 도메인 규칙 → 데이터베이스 제약. 이 겹침이 정당한지는 I32의 판정 문제이고, 이 문서는 정당하다고 판정한 겹침이 지금도 살아 있는가를 묻는다.
  • 상위 층이 조용히 죽어도 하위 층이 같은 입력을 거부하므로 최종 결과는 그대로다. 그래서 결과만 보는 테스트(E2E·통합)는 초록을 유지한다 — 이것이 무증상 퇴화(asymptomatic decay)다.
  • 무증상이지 무해가 아니다. 잃는 것은 즉시 피드백(사용자가 제출한 뒤에야 오류를 봄), 진단 거리(오류가 더 깊은 층에서 더 모호한 형태로 나옴), 하위 층의 부하, 그리고 방어의 여유 — 다음 층까지 죽는 날 한 번에 붕괴한다.
  • 사각지대의 정체는 질문의 모양이다: 결과 기준 테스트는 "거부됐는가"만 묻고 "어느 층이 거부했는가"를 묻지 않는다.
  • 검출 원리는 층별 발동 단언이다 — 각 층을 단독으로 실행해 그 층이 막았음을 오류 출처·응답 코드·하위 호출의 부재로 단언하고, 하위 층은 "무엇이든 통과시키는" 스텁으로 두어 거부의 유일한 후보가 검증 대상 층이 되게 만든다.
  • 호출 부재 단언은 반드시 짝(유효 입력이면 호출된다)과 함께 써야 한다 — 대역이 끼워지지 않았을 때 "호출되지 않았다"는 공허하게 참이 되기 때문이다.

1. 전제 — 다층 방어는 "같은 규칙을 여러 층이 지킨다"는 뜻이다

J2의 마지막 절은 "상위 층의 통과가 하위 층의 작동을 보증하지 않는다"는 문장으로 끝났다. 그 문장이 가장 날카롭게 성립하는 곳이 이 문서의 대상, 즉 다층 방어(defense in depth) 구조다. 웹 애플리케이션에서 "주문 수량은 1 이상 100 이하"라는 규칙 하나는 흔히 네 곳에 존재한다.

사용자 입력 "수량 0" │ ▼ [1층] 프론트 폼 검증 — 제출 전에 빨간 글씨, 서버로 보내지 않는다 │ ▼ [2층] API 요청 검증 — 요청 DTO의 범위 검사, 400으로 되돌린다 │ ▼ [3층] 도메인 규칙 — Order 생성 시 불변식 검사, 예외를 던진다 │ ▼ [4층] 데이터베이스 제약 — CHECK (quantity BETWEEN 1 AND 100), 저장을 거부한다

각 층은 같은 규칙을 지키지만 하는 일이 다르다. 1층은 사용자 경험(타이핑 중 즉시 피드백)을, 2층은 API의 계약(다른 클라이언트·스크립트가 보내는 요청도 막는다)을, 3층은 어떤 진입 경로로 오든 지켜야 할 불변식을, 4층은 애플리케이션을 우회한 직접 쓰기까지 막는 최후의 선을 담당한다. 이 겹침이 정당한 방어인지 단순한 복사인지 — 즉 어떤 층을 두고 어떤 층을 뺄지 — 는 I32가 판정한다. 이 문서는 그 판정 이후를 다룬다: 정당하다고 두기로 한 층들이, 지금 이 순간에도 전부 살아 있는가?

질문이 이상하게 들릴 수 있다. 층이 죽었으면 테스트가 빨개질 텐데, 굳이 물을 필요가 있나. 바로 그 직관이 틀리는 지점이 다음 절이다.

2. 무증상 퇴화 — 상위 가드가 죽어도 결과는 같다

앞 절의 네 층에서 2층(API 요청 검증)이 사라졌다고 하자. 리팩토링 중 어노테이션이 떨어졌거나, DTO 클래스를 교체하면서 범위 검사가 옮겨지지 않았거나, 검증을 켜는 설정이 빠진 경우다. 이제 "수량 0" 요청은 어떻게 되는가. 

// 2층이 살아 있을 때:  요청 → [2층] 400 Bad Request           (서비스는 호출되지 않음)
// 2층이 죽었을 때:     요청 → 2층 통과 → [3층] 도메인 예외
//                            → 예외 처리기가 400으로 변환        (서비스는 호출됨)
//
// 결과 기준 E2E 테스트:  "수량 0을 제출하면 거부된다"  →  두 경우 모두 초록

최종 결과는 두 경우 모두 "거부"다. 응답 코드까지 같을 수 있다 — 도메인 예외를 400으로 매핑하는 전역 예외 처리기가 있다면 상태 코드조차 구분되지 않는다. 결과만 보는 테스트는 이 차이를 볼 수 없다. 이것이 무증상 퇴화다: 방어 층 하나가 기능을 잃었는데, 하위 층이 같은 입력을 거부해 최종 결과를 보정하므로 어떤 테스트도 빨개지지 않는 상태.

왜 "퇴화"인가: 층이 "고장"났다면 증상이 있다. 퇴화는 증상 없이 기능만 빠지는 것이다 — 겉모습(응답)은 유지되고 내부(어느 층이 일했는가)만 바뀐다. 다층 방어의 본질적 성질이 이 퇴화를 낳는다: 층이 겹쳐 있기 때문에 하나가 빠져도 티가 안 난다. 즉 다층 방어의 장점(한 층이 뚫려도 다음 층이 막는다)과 무증상 퇴화는 같은 성질의 두 얼굴이다.

그렇다면 이렇게 되물을 수 있다 — 어차피 막히는데, 어느 층이 막든 무슨 상관인가. 상관이 있다. 잃는 것이 네 가지나 되기 때문이다.

3. 무증상이지 무해가 아니다 — 잃는 네 가지

앞 절에서 "결과는 같다"고 했지만, 정확히는 거부라는 사실만 같다. 거부의 시점·형태·비용·여유는 전부 달라진다.

잃는 것살아 있을 때죽은 뒤(하위 층이 보정)
① 즉시 피드백 프론트 층: 입력하는 순간 필드 옆에 오류 표시, 제출 자체가 막힌다 제출 → 서버 왕복 → 응답 해석 → 오류 표시. 사용자는 "제출했는데 튕겼다"를 경험한다. 필드 단위 메시지는 응답을 파싱해 다시 매핑해야 하고, 그 매핑이 없으면 "요청이 잘못되었습니다"라는 뭉뚱그린 문구가 된다
② 진단 거리 2층 거부는 "요청 필드 quantity가 범위를 벗어남"으로 정확히 말한다 4층까지 내려가면 "제약 조건 위반(constraint violation)"이라는 저장소 언어의 오류가 되고, 스택은 저장 계층을 가리킨다. 원인은 입력인데 증상은 저장에서 난다 — J2에서 본 진단 거리가 층 수만큼 늘어난다
③ 하위 층의 부하·비용 잘못된 입력은 가장 싼 층에서 소비된다 — 브라우저에서 끝나거나 요청 파싱 직후 끝난다 잘못된 입력이 서비스 로직·트랜잭션·데이터베이스 왕복까지 소비한다. 대량의 잘못된 요청(오작동 클라이언트·스크립트)이 오면 데이터베이스가 검증기 노릇을 한다
④ 방어의 여유 네 층 중 하나가 뚫려도 셋이 남는다 여유가 하나 줄었는데 아무도 모른다. 다음 층이 같은 방식으로 죽으면 그때는 여유가 0이 되어 있고, 잘못된 데이터가 저장되는 순간에야 발각된다 — 조용히 줄어든 여유가 한 번에 무너지는 것이 무증상 퇴화의 최종 형태다

네 가지 중 ④가 가장 위험하다. 다층 방어의 가치는 "여유"인데, 무증상 퇴화는 정확히 그 여유를 보이지 않게 깎는다. 여유가 셋에서 둘로, 둘에서 하나로 줄어드는 동안 모든 테스트는 초록이고, 하나에서 0이 되는 순간 사고가 된다. 방어가 두꺼울수록 퇴화가 더 오래 숨는다는 역설이다.

그렇다면 왜 기존 테스트는 이것을 못 보는가. 테스트가 부족해서가 아니라, 테스트가 던지는 질문의 모양 때문이다.

4. 결과 기준 테스트의 사각지대 — "거부됐다"는 묻지만 "누가"는 묻지 않는다

앞 절의 손실은 전부 "어느 층이 막았는가"에 관한 것이다. 그런데 E2E·통합 테스트의 단언은 대개 이런 모양이다. 

// 결과 기준 단언 — 전형적인 E2E
제출(수량 = 0)
expect(응답.status).toBe(400)                // 거부됐는가?  → 예
expect(화면).toContain("수량은 1 이상")     // 오류가 보이는가? → 예 (서버 응답을 표시해도 참)

이 단언이 참이 되는 경로는 하나가 아니다. 1층이 막아도, 2층이 막아도, 3층이 막고 예외 처리기가 400으로 바꿔도 참이다. 즉 이 테스트는 네 층의 논리합(OR)을 검증한다. 논리합은 하나만 참이면 참이므로, 세 층이 죽고 하나만 남아도 초록이다.

사각지대의 정확한 위치: 결과 기준 테스트는 시스템이 규칙을 지키는가를 검증하고, 실제로 그것을 잘 검증한다. 못 보는 것은 규칙을 지키는 구조가 설계대로인가다. 두 질문은 다르다 — 앞의 것은 "무엇을"이고 뒤의 것은 "어떻게·어디서"다. 다층 방어는 "어디서"가 곧 가치(3절의 네 가지)인 구조이므로, "무엇을"만 묻는 테스트로는 가치의 소실을 볼 수 없다.

그렇다고 E2E를 "어느 층이 막았는가"까지 묻게 고치는 것은 답이 아니다. E2E는 전체 경로를 실제로 통과하는 층이라 특정 층을 떼어 낼 수 없고(J2의 배분 원리: 결함은 그것을 볼 수 있는 가장 낮은 층에서), 층을 하나씩 죽여 보며 E2E를 돌리는 것은 뮤테이션 테스트에 가까운 비용이 든다. 필요한 것은 질문의 모양을 바꾼 다른 종류의 단언이다.

5. 층별 발동 단언 — 세 가지 기법

앞 절에서 결과 기준 단언이 논리합이라는 점을 확인했다. 층별 검증의 원리는 그 반대다: 한 번에 한 층만 실행되게 만들고, 그 층이 막았음을 그 층에서만 나올 수 있는 증거로 단언한다. 증거는 세 종류다.

5.1 단독 실행 + 출처 단언

검증 대상 층만 띄우고, 잘못된 입력을 넣고, 그 층 고유의 거부 형태를 단언한다. 2층이면 "400이고 오류 본문의 출처가 요청 검증이며 필드명이 quantity"이고, 3층이면 "도메인 예외의 타입"이고, 4층이면 "제약 위반 예외"다. 핵심은 출처를 구분할 수 있는 거부 형태를 층마다 갖는 것이다. 2층 거부와 3층 거부가 둘 다 "400 + 빈 본문"이면, 단독 실행을 해도 어느 층이 막았는지 알 수 없다. 오류 응답에 출처(예: source: "request-validation" vs source: "domain-rule")나 층별로 다른 오류 코드를 두는 설계가 층별 검증의 전제 조건이다.

5.2 하위 호출의 부재 — "통과시키는 스텁"

단독 실행이 어려운 층(프레임워크 위에서만 도는 검증, 다음 층을 호출하는 컨트롤러)에는 다른 증거가 있다: 상위 층이 막았다면 하위 층은 호출되지 않았어야 한다. 하위 층을 대역으로 바꾸되, 이 대역은 무엇이든 통과시킨다. 아무 검사도 하지 않고 성공을 돌려주는 스텁이다. 이렇게 하면 시스템 안에서 거부할 수 있는 층은 검증 대상 층 하나뿐이 되고, 거부가 관찰되면 그 층이 살아 있다는 뜻이 된다. 더 강하게는, 대역이 호출조차 되지 않았음을 단언한다. 

// 2층(API 검증)의 발동 단언 — 하위 층(서비스)은 통과시키는 대역
service = 대역(무엇을 받든 성공을 돌려줌)
응답 = 컨트롤러.요청(수량 = 0)

expect(응답.status).toBe(400)
expect(service.create).not.toHaveBeenCalled()   // 거부가 2층에서 났다는 증거:
                                                 // 3층에 닿기 전에 멈췄다

부재 단언의 짝 규칙: "호출되지 않았다"는 단언은 같은 대역이 유효 입력에서는 호출된다는 짝 테스트와 함께 있어야 의미를 가진다. 대역이 실제로 끼워지지 않았거나(잘못된 주입·패치 경로 — J12의 주제), 컨트롤러가 애초에 서비스를 부르지 않는 경로라면, "호출되지 않았다"는 공허하게 참이다. 짝 테스트(수량 = 5 → service.create가 1회 호출됨)가 대역의 배선을 증명해 준 뒤에야 부재 단언이 증거가 된다.

5.3 층별 발동 로그·지표

테스트가 닿지 못하는 곳 — 운영 중의 실제 트래픽 — 에는 세 번째 증거가 있다. 각 층이 거부할 때 자기 이름을 남기게 하면(로그의 출처 필드, 층별 거부 횟수 지표), 정상 상태의 분포가 곧 기준선이 된다: 대부분의 잘못된 입력은 1·2층에서 소비되고 3·4층 거부는 드물다. 어느 날 2층 거부가 0으로 떨어지고 3층 거부가 그만큼 늘었다면, 테스트 없이도 2층의 퇴화가 드러난다. 이것은 5.1·5.2가 개발 시점에 잡는 것을 운영 시점에 잡는 안전망이며, 3절의 ③(하위 층 부하)을 직접 측정하는 지표이기도 하다.

기법 실행 범위 증거 잡는 시점 ───────────────────────────────────────────────────────────────────────── 5.1 단독 실행 그 층만 층 고유의 거부 형태(출처·코드) 개발·CI 5.2 부재 단언 그 층 + 통과 대역 하위 대역이 호출되지 않음 개발·CI 5.3 발동 지표 실제 전체 경로 층별 거부 횟수의 분포 변화 운영

세 기법을 알았으니 남는 질문은 비용이다. 모든 층에, 모든 규칙에 이것을 다 할 것인가.

6. 어느 층을 층별로 검증할 것인가 — I32 판정과의 짝

앞 절의 기법은 층당 테스트 하나 이상을 요구한다. 네 층 × 규칙 수만큼 테스트가 늘어나면 J10에서 경고한 부채가 된다. 그래서 층별 검증에도 배분이 필요하고, 그 배분의 근거는 I32의 판정 결과에서 그대로 온다.

I32는 겹친 검증 각각에 대해 "이 층은 무엇을 위해 존재하는가"를 묻고, 답이 없는 층(다른 층의 단순 복사)은 제거를, 답이 있는 층(고유한 역할)은 유지를 판정한다. 층별 검증은 유지 판정을 받은 층에만 붙인다. 판정의 근거가 곧 단언의 내용이 된다:

층I32의 존재 이유(유지 근거)J18의 발동 단언(그 이유가 살아 있는가)
프론트 폼즉시 피드백 UX제출 전에 오류가 표시되고 제출 핸들러가 호출되지 않는다
API 요청 검증계약 — 모든 클라이언트에 대한 경계400 + 요청 검증 출처, 서비스가 호출되지 않는다
도메인 규칙진입 경로 무관한 불변식도메인 예외 타입, 저장소가 호출되지 않는다
데이터베이스 제약애플리케이션 우회에 대한 최후선도메인을 우회해 직접 쓰기 → 제약 위반(실제 데이터베이스로)

두 문서의 관계를 한 문장으로 하면: I32가 "이 중복은 정당한가"를 판정하면, J18은 "정당한 중복이 살아 있는가"를 검증한다. 판정 없이 검증하면 복사에 불과한 층까지 테스트로 고정해 제거를 방해하고, 검증 없이 판정만 하면 정당한 층이 조용히 퇴화해도 판정 문서만 남는다.

비용을 더 줄이는 방법은 규칙 단위가 아니라 층 단위로 검증하는 것이다. 층의 발동은 대개 층 전체가 켜져 있는가의 문제(어노테이션·설정·미들웨어 등록)이므로, 규칙 하나를 대표로 골라 층의 발동을 단언하면 층이 통째로 빠지는 퇴화는 잡힌다. 규칙 개별의 정확성은 그 층의 단위 테스트가 이미 맡고 있다. 이 배분까지 마치면 원리는 끝났다. 남는 것은 이 원리를 적용할 때 자주 빠지는 오해다.

7. 흔히 헷갈리는 지점

① "E2E가 있으니 방어는 검증됐다" — E2E는 네 층의 논리합(4절)을 검증한다. 세 층이 죽고 하나만 남아도 초록이므로, E2E의 초록은 "규칙이 지켜진다"의 증거이지 "네 층이 살아 있다"의 증거가 아니다. 두 질문을 분리하지 않는 것이 무증상 퇴화가 숨는 첫 번째 이유다.

② "호출되지 않았다를 단언했으니 상위 층이 막은 것이다" — 대역이 끼워지지 않았거나 애초에 그 경로에서 호출이 없다면 부재 단언은 공허하게 참이다(5.2). 유효 입력에서 호출된다는 짝 테스트 없이 부재 단언만 있는 테스트는, 검증 대상 층이 사라져도 계속 초록일 수 있다 — 층별 검증 자체가 무증상 퇴화하는 재귀적 함정이다.

③ "테스트 환경의 하위 대역이 거부를 흉내 내면 더 실제 같다" — 반대다. 서버 대역(요청 가로채기 도구)이 "수량 0이면 400"을 흉내 내면, 프론트 층이 죽어도 컴포넌트 테스트는 서버 대역의 400을 표시하며 초록이 된다. 층별 검증에서 하위 대역은 통과시켜야 한다 — 거부의 유일한 후보가 검증 대상 층이어야 하기 때문이다. 대역의 충실도가 높을수록 상위 층의 퇴화를 가리는 역설이다.

④ "층별 검증은 중복 검증을 옹호하는 것이다" — 아니다. 층별 검증은 I32가 "정당하다"고 판정한 층에만 붙는다(6절). 정당성 판정 없이 모든 겹침을 테스트로 고정하면 복사에 불과한 층까지 제거할 수 없게 되어, 오히려 I32의 판정을 방해한다. 검증은 판정의 결과를 지키는 것이지 판정을 대신하는 것이 아니다.

★ 8. 언어별 대조

원리는 하나 — "그 층만 실행하고, 그 층 고유의 증거로 단언한다" — 지만, 층을 단독으로 띄우는 방법과 하위 호출의 부재를 단언하는 API는 언어별 테스트 도구마다 다르다. 그리고 각 언어에는 무증상 퇴화가 그 언어 특유의 모양으로 나타나는 지점이 있다.

언어 / 도구층 단독 실행하위 호출 부재 단언그 언어만의 함정
Java / JUnit 5 + Mockito 컨트롤러 슬라이스 테스트(요청 검증 층만 띄움), 도메인은 순수 단위, 데이터베이스 제약은 실제 데이터베이스 통합 verifyNoInteractions(mock) 전역 예외 처리기가 도메인 예외를 400으로 바꾸면 상태 코드로는 층을 구분 못 함 — 출처 필드가 필요
JS·TS / Jest · Vitest 컴포넌트 렌더 + 사용자 이벤트(Testing Library 관점) expect(fn).not.toHaveBeenCalled() 서버 대역(msw류)이 거부를 흉내 내면 프론트 층 소실이 안 보임; 시뮬레이션 DOM의 내장 검증 동작 차이
Python / pytest + unittest.mock 스키마·시리얼라이저 검증 층을 단독 호출 mock.assert_not_called() MagicMock은 기본이 "무엇이든 통과"; 패치 경로가 틀리면 부재 단언이 공허하게 참
C++ / GoogleTest + gMock 입력 경계 함수 단독 호출, 계약 검사 EXPECT_CALL(mock, Save).Times(0) assert 층은 NDEBUG 빌드에서 통째로 사라진다 — 언어 내장 무증상 퇴화

8.1 Java — JUnit 5 + Mockito: 슬라이스 테스트가 층을 물리적으로 떼어 준다

Java 웹 프레임워크의 슬라이스 테스트는 층별 검증에 가장 잘 맞는 도구다. 컨트롤러 슬라이스는 요청 처리 계층과 검증 층만 띄우고 서비스 이하를 컨테이너에 등록된 mock으로 바꾼다 — 5.2의 "통과시키는 스텁"이 프레임워크 수준에서 준비되는 셈이다. Bean Validation의 @Valid가 요청 DTO에서 발동하면 컨트롤러 메서드 본문에 들어가기 전에 400이 되고, 서비스 mock은 건드려지지 않는다. Mockito의 verifyNoInteractions가 그 부재를 단언한다. 

@WebMvcTest(OrderController.class)          // 요청 처리·검증 층만 띄운다
class OrderRequestValidationTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService orderService;   // 하위 층은 통과시키는 대역

    @Test
    void 수량_0은_요청_검증_층에서_거부된다() throws Exception {
        mvc.perform(post("/orders").contentType(APPLICATION_JSON)
                .content("{\"productId\": 7, \"quantity\": 0}"))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.source").value("request-validation"))  // 출처 단언
           .andExpect(jsonPath("$.field").value("quantity"));
        verifyNoInteractions(orderService);   // 3층에 닿기 전에 멈췄다는 증거
    }

    @Test
    void 유효한_수량은_서비스에_도달한다() throws Exception {   // 부재 단언의 짝
        mvc.perform(post("/orders").contentType(APPLICATION_JSON)
                .content("{\"productId\": 7, \"quantity\": 5}"))
           .andExpect(status().isCreated());
        verify(orderService).create(any());
    }
}

이 언어의 함정은 전역 예외 처리기다. 도메인 층의 예외를 400으로 매핑하는 처리기가 있으면, @Valid가 떨어져도 E2E에서 상태 코드는 그대로 400이다 — 2절의 무증상 퇴화가 정확히 이 형태로 생긴다. 슬라이스 테스트의 verifyNoInteractions가 이를 잡지만, 출처 단언까지 하려면 요청 검증 오류와 도메인 오류의 응답 본문이 구분되게 설계돼 있어야 한다. verifyNoInteractions(어떤 호출도 없었음)와 verifyNoMoreInteractions(검증한 호출 외에 없었음)는 다르다 — 부재 단언에는 전자가 맞다. 데이터베이스 제약 층은 슬라이스 밖이다: 도메인 객체를 거치지 않고 직접 행을 쓰는 통합 테스트로, 실제 데이터베이스(또는 같은 제품의 컨테이너)에서 제약 위반 예외를 단언한다. 인메모리 대체물은 제약 문법이 달라 제약 자체가 생성되지 않을 수 있고, 그러면 4층 테스트는 "거부되지 않음"으로 빨개지는 것이 아니라 아예 4층이 없는 환경을 검증한 것이 된다. 2020년대 중반 기준, 컨테이너 등록 mock 어노테이션은 @MockBean에서 프레임워크 자체가 제공하는 @MockitoBean으로 옮겨 가는 중이다(구 어노테이션은 폐기 예정) — 역할은 같다.

8.2 JS·TS — Jest / Vitest: 서버 대역이 너무 충실하면 프론트 층이 안 보인다

프론트 층(1층)의 존재 이유는 즉시 피드백과 제출 자체를 막는 것이다. 따라서 발동 단언도 그 둘이다: 오류가 화면에 보이고, 제출 핸들러(또는 네트워크 호출)가 일어나지 않는다. Testing Library 관점 — 구현이 아니라 사용자가 보고 하는 것으로 테스트한다 — 에서는 입력·클릭을 사용자 이벤트로 넣고, 결과를 접근 가능한 텍스트로 찾는다. Jest와 Vitest는 이 수준의 API(jest.fn()/vi.fn(), .not.toHaveBeenCalled())가 사실상 같다; 차이는 실행 기반(변환 계층 vs Vite 파이프라인)이지 단언 방식이 아니다. 

// Vitest + Testing Library — 1층(폼 검증)의 발동 단언
import { render, screen } from '@testing-library/vue'
import userEvent from '@testing-library/user-event'
import OrderForm from './OrderForm.vue'

test('수량 0은 제출 전에 막히고, 제출 핸들러는 호출되지 않는다', async () => {
  const onSubmit = vi.fn()                                // 하위 층: 통과시키는 대역
  render(OrderForm, { props: { onSubmit } })
  const user = userEvent.setup()

  await user.clear(screen.getByLabelText('수량'))
  await user.type(screen.getByLabelText('수량'), '0')
  await user.click(screen.getByRole('button', { name: '주문' }))

  expect(screen.getByText('수량은 1 이상이어야 합니다')).toBeInTheDocument()
  expect(onSubmit).not.toHaveBeenCalled()                 // 1층이 막았다는 증거
})

test('유효한 수량은 제출된다', async () => {              // 부재 단언의 짝
  const onSubmit = vi.fn()
  render(OrderForm, { props: { onSubmit } })
  const user = userEvent.setup()
  await user.type(screen.getByLabelText('수량'), '5')
  await user.click(screen.getByRole('button', { name: '주문' }))
  expect(onSubmit).toHaveBeenCalledWith(expect.objectContaining({ quantity: 5 }))
})

이 언어의 고유한 함정은 7-③의 실체다. 컴포넌트가 직접 API를 호출하는 구조에서, 요청 가로채기 도구(msw류)의 핸들러에 "수량 0이면 400을 돌려준다"를 써 두면 테스트는 더 실제 같아 보인다. 그러나 그 순간 프론트 검증이 통째로 사라져도 테스트는 초록이다 — 서버 대역의 400을 화면에 표시했을 뿐인데 "오류가 보인다"는 단언은 참이기 때문이다. 1층을 검증하는 테스트에서 서버 대역은 무엇이든 성공을 돌려주거나, 아예 요청이 나가지 않았음(fetch 스파이의 부재 단언, 또는 처리되지 않은 요청을 오류로 취급하는 설정)을 단언해야 한다. 두 번째 함정은 실행 환경이다. HTML 속성(required·min)에 기대는 브라우저 내장 검증은 시뮬레이션 DOM에서 실제 브라우저와 다르게 동작할 수 있다. 그 층의 발동을 믿으려면 실제 브라우저 층(E2E)에서 확인하거나, 검증을 스크립트 층으로 끌어와 시뮬레이션 DOM에서도 단언 가능하게 만드는 편이 안전하다.

8.3 Python — pytest + unittest.mock: 기본 대역이 "무엇이든 통과"라는 양날

Python 웹 스택에서 2층은 스키마·시리얼라이저 라이브러리(pydantic류, 프레임워크의 시리얼라이저)가 맡는다. 이 층은 프레임워크 없이도 단독 호출이 가능해 5.1이 가장 싸다 — 스키마 클래스에 잘못된 값을 넣고 검증 예외를 단언하면 된다. 하위 호출의 부재는 unittest.mock의 assert_not_called()가 담당한다. 

import pytest
from pydantic import BaseModel, Field, ValidationError
from unittest.mock import MagicMock

class OrderRequest(BaseModel):                 # 2층: 요청 스키마
    product_id: int
    quantity: int = Field(ge=1, le=100)

def test_schema_layer_rejects_zero_quantity():   # 5.1 단독 실행 + 출처 단언
    with pytest.raises(ValidationError) as info:
        OrderRequest(product_id=7, quantity=0)
    assert info.value.errors()[0]["loc"] == ("quantity",)

def test_handler_stops_before_service():         # 5.2 부재 단언
    service = MagicMock()                        # 무엇이든 통과시키는 대역 — 기본 동작이 그렇다
    response = create_order_handler({"product_id": 7, "quantity": 0}, service=service)
    assert response.status == 400
    service.create.assert_not_called()

def test_valid_request_reaches_service():        # 부재 단언의 짝
    service = MagicMock()
    create_order_handler({"product_id": 7, "quantity": 5}, service=service)
    service.create.assert_called_once()

이 언어의 특이점은 MagicMock의 기본 동작이다. 어떤 속성·메서드를 부르든 또 다른 MagicMock을 돌려주므로, 설정 없이도 "무엇이든 통과시키는 스텁"이 된다 — 5.2에 이상적이다. 양날은 같은 성질에서 온다: 하위 층이 거부하기를 기대한 테스트에서 MagicMock을 쓰면 거부가 절대 일어나지 않고, 반환값이 참으로 평가되므로 "저장 성공" 분기를 조용히 탄다. 어느 층을 검증하는지에 따라 대역의 기본 관대함이 자산이 되기도 함정이 되기도 한다. 두 번째 특이점은 J12·J2에서 본 패치 경로 문제가 부재 단언과 만나는 지점이다. patch("app.service.create")의 경로가 틀려 대역이 끼워지지 않으면, 대역은 호출된 적이 없으니 assert_not_called()는 항상 참이다 — 7-②의 공허한 단언이 이 언어에서는 오타 하나로 생긴다. 짝 테스트가 필수인 이유다. 데이터베이스 제약 층은 다른 언어와 같이 실제 데이터베이스로 검증한다. 가벼운 파일 데이터베이스의 제약 문법·강제 여부가 운영 제품과 다를 수 있어, 4층의 발동을 믿으려면 같은 제품이어야 한다.

Python 관점의 통찰: 이 언어의 대역은 객체 모델의 동적 속성 접근(존재하지 않는 속성을 부르면 __getattr__가 만들어 준다)으로 구현되므로, "통과시키는 스텁"이 언어의 기본 상태이고 "거부하는 스텁"은 명시적으로 만들어야 한다. 정적 언어에서 대역의 관대함이 설정의 결과라면 Python에서는 부재의 결과다 — 층별 검증에서 대역의 기본 관대함을 의식하지 않으면 어느 층이 막았는지가 아니라 어느 층도 막지 않았음을 초록으로 보게 된다.

8.4 C++ — GoogleTest + GoogleMock: 빌드 설정 하나가 층을 통째로 지운다

C++에서 입력 경계의 검증 층은 보통 두 종류로 갈린다. 외부 입력(파일·네트워크·사용자)에 대한 검사는 예외나 오류 반환으로 표현되어 릴리스에도 남고, 내부 호출자와의 계약(전제 조건)은 단언(assert)으로 표현되어 디버그 빌드에서만 검사된다. 두 층은 잡는 결함이 다르므로(외부 입력의 오류 vs 내 코드의 버그) 이 구분 자체는 정당하다. gMock에서 하위 호출의 부재는 .Times(0)가 단언한다. 

#include <gtest/gtest.h>
#include <gmock/gmock.h>
#include <cassert>

class MockRepository : public OrderRepository {
public:
    MOCK_METHOD(void, Save, (const Order&), (override));
};

// 입력 경계의 검증 층: 예외로 표현 — 릴리스에도 남는다
Order CreateOrder(int product_id, int quantity, OrderRepository& repo) {
    if (quantity < 1 || quantity > 100)
        throw std::invalid_argument("quantity out of range");
    Order order{product_id, quantity};
    repo.Save(order);
    return order;
}

// 내부 계약 층: 단언으로 표현 — NDEBUG 빌드에서 통째로 사라진다
int ApplyDiscount(int amount, int rate_percent) {
    assert(rate_percent >= 0 && rate_percent <= 100);   // 릴리스에서는 이 줄이 없다
    return amount * (100 - rate_percent) / 100;
}

TEST(OrderBoundary, RejectsZeroQuantityBeforeRepository) {
    MockRepository repo;
    EXPECT_CALL(repo, Save).Times(0);                     // 하위 호출의 부재
    EXPECT_THROW(CreateOrder(7, 0, repo), std::invalid_argument);   // 층 고유의 거부 형태
}

TEST(OrderBoundary, ValidQuantityReachesRepository) {   // 부재 단언의 짝
    MockRepository repo;
    EXPECT_CALL(repo, Save).Times(1);
    CreateOrder(7, 5, repo);
}

이 언어에는 무증상 퇴화의 언어 내장판이 있다. assert로 만든 계약 층은 NDEBUG가 정의된 빌드(대부분의 릴리스 빌드)에서 전처리 단계에 통째로 제거된다. 디버그 빌드의 테스트는 그 층이 발동하는 것을 보고 초록이 되고, 릴리스 바이너리에는 그 층이 없다 — 하위 층(예외·데이터베이스)이 있다면 거부는 여전히 일어나므로 3절의 손실이 그대로 발생하고, 없다면 잘못된 값이 계산에 들어간다. 이는 코드가 바뀌어서가 아니라 빌드 설정 하나로 층이 사라지는 퇴화이며, "이 검사는 릴리스에도 있어야 하는가"라는 질문에 따라 assert가 아닌 예외·오류 반환으로 층을 옮겨야 한다. gMock 쪽 함정은 대역의 기본 관대함이다. 기대를 설정하지 않은 호출은 경고만 내고 통과하며(NiceMock이면 경고도 없다), 그래서 .Times(0)를 명시하지 않으면 하위 호출의 부재는 검증되지 않는다. StrictMock은 예상 밖 호출을 실패로 만들어 부재 단언을 기본값으로 바꿔 주지만, 검증 대상과 무관한 호출까지 실패시켜 테스트를 취약하게 만들 수 있으므로 검증하려는 호출에만 .Times(0)를 두는 편이 의도가 분명하다.

C++ 관점의 통찰: 이 언어에서 "층"은 런타임 구조만이 아니라 컴파일 타임 산출물이다 — 어떤 검사는 전처리기가 지우고, 어떤 검사는 최적화기가 결과가 쓰이지 않는다며 제거하고, 어떤 검사(static_assert)는 빌드 자체를 층으로 삼는다. 따라서 층별 검증에는 "어느 빌드 구성에서 이 층이 존재하는가"라는 질문이 하나 더 붙고, 릴리스 구성으로도 테스트를 한 번 돌리는 것이 C++에서의 층별 발동 단언에 해당한다. 또한 대역을 끼우려면 가상 함수라는 설계 비용이 먼저 들기 때문에, 부재 단언이 가능한 경계는 설계 시점에 정해진다 — 경계에 인터페이스가 없으면 5.2는 성립하지 않고 5.1(단독 실행)과 5.3(로그)만 남는다.

9. 함께 알면 좋은 것

본문의 축을 인접 어휘로 넓힌 것들이다 — 첫째는 5.3을, 둘째는 4절의 논리합 문제를, 셋째는 5.1의 전제를, 넷째는 3절의 ④를, 다섯째는 6절의 배분을 잇는다.

  • 관측 가능성(observability)과 층별 지표 — 5.3의 발동 로그를 일반화한 것. 시스템이 "무엇을 했는가"뿐 아니라 "어느 구성 요소가 했는가"를 외부에서 알 수 있게 하는 설계 원칙이며, 무증상 퇴화는 관측 가능성이 낮은 시스템에서 가장 오래 숨는다.
  • 뮤테이션 테스트 — 코드를 일부러 변형해 테스트가 잡는지를 보는 기법. 층 하나를 통째로 제거하는 변이에 E2E가 반응하지 않는다는 사실이 4절의 논리합 문제를 정량으로 드러낸다 — 층별 단언이 없는 스위트의 변이 점수가 낮게 나오는 이유다.
  • 문제 상세(problem details) 응답 형식 — 오류 응답에 유형·출처·필드를 구조적으로 담는 표준화된 형식. 5.1의 출처 단언이 성립하려면 층마다 구분되는 오류 표현이 필요한데, 이런 형식이 그 표현의 틀이 된다.
  • 정상화된 일탈(normalization of deviance) — 안전 여유가 조금씩 깎여도 사고가 나지 않으면 그 상태가 정상으로 받아들여지는 현상. 3절의 ④(방어 여유가 조용히 0이 됨)를 설명하는 안전공학의 어휘로, 무증상 퇴화의 조직적 얼굴이다.
  • 계약 테스트 — 프론트↔백엔드 경계의 기대를 명문화해 양쪽에서 검증하는 접근. 2층(API 검증)이 "계약"이라는 존재 이유를 가진다면(6절), 그 계약이 지금도 지켜지는가를 검증하는 도구가 곧 2층의 층별 검증이 된다.

10. 한 장 요약

  • 다층 방어는 같은 규칙을 여러 층이 지키는 구조다. 어느 층이 막는가가 곧 가치(즉시 피드백·진단 거리·부하·여유)이므로, 거부라는 결과만 같아서는 부족하다.
  • 무증상 퇴화: 상위 층이 죽어도 하위 층이 결과를 보정해 어떤 테스트도 빨개지지 않는 상태. 방어가 두꺼울수록 더 오래 숨고, 여유가 0이 되는 순간 한 번에 무너진다.
  • 결과 기준 테스트는 층들의 논리합을 검증한다 — "거부됐는가"는 묻지만 "누가 거부했는가"는 묻지 않는다. 이것이 사각지대의 정확한 위치다.
  • 층별 발동 단언 세 기법: 단독 실행 + 출처 단언 / 하위 층을 통과시키는 대역 + 호출 부재 단언 / 층별 발동 지표. 출처를 구분할 수 있는 거부 형태가 전제 조건이다.
  • 부재 단언은 짝(유효 입력이면 호출된다)이 있어야 증거다 — 대역이 끼워지지 않으면 공허하게 참이 된다. 하위 대역이 거부를 흉내 내면 상위 층의 퇴화를 가린다.
  • I32가 "이 중복은 정당한가"를 판정하면, J18은 "정당한 중복이 살아 있는가"를 검증한다. 유지 판정을 받은 층에만, 규칙 단위가 아니라 층 단위로 붙인다.

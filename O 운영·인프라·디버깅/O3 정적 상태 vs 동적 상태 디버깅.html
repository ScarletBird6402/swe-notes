O3 정적 상태 vs 동적 상태 디버깅

0. 한눈에 보는 결론

  • "고쳤는데 반영이 안 된다"는 코드 버그가 아니라 대부분 상태 불일치다: 디스크에 있는 값(정적 상태)과 지금 실행·표시 중인 값(동적 상태)이 서로 다른 것.
  • 불일치가 생기는 이유는 값이 최종 화면까지 가는 길에 복사·고정되는 관문이 여러 개이기 때문이다: 소스→빌드→서빙→포트(프로세스)→브라우저.
  • 각 관문은 자기만의 스냅샷을 갖는다 — 번들은 빌드 시점의 소스를, 프로세스는 시작 시점의 설정을, 브라우저 캐시는 다운로드 시점의 파일을 기억한다.
  • 진단의 정석은 감이 아니라 관문을 하나씩 끊어 확인하는 것이다: 각 관문에서 "여기까지는 새 값인가?"를 직접 관측해, 새 값→옛 값으로 바뀌는 경계를 찾는다.
  • 확인은 반드시 그 계층의 실제 산출물을 본다 — 소스는 편집기로, 번들은 산출물 검색으로, 서빙은 원본 응답으로, 프로세스는 포트 점유로, 브라우저는 캐시 우회로.
  • 이 방법은 이분 탐색이다: 관문 하나를 확인할 때마다 용의 구간이 절반으로 줄어든다. 다섯 관문이면 다섯 번의 확인으로 끝난다.

1. 두 세계 — 디스크의 상태와 실행 중의 상태

시스템의 어떤 값이든 두 곳에 존재한다. 하나는 정적 상태: 디스크에 저장된 것 — 소스 코드, 설정 파일, 빌드 산출물. 편집기로 열어 볼 수 있고, 고치면 즉시 바뀐다. 다른 하나는 동적 상태: 실행 중인 시스템이 실제로 들고 있는 것 — 프로세스 메모리에 로드된 설정, 브라우저가 실행 중인 JS, 화면에 그려진 값.

개발자가 고치는 것은 언제나 정적 상태이고, 확인하는 것은 언제나 동적 상태다. 그리고 이 둘은 자동으로 동기화되지 않는다 — 정적 상태가 동적 상태가 되려면 로드·빌드·전송이라는 명시적 복사 행위가 일어나야 하며, 복사가 일어나기 전까지 동적 상태는 과거의 정적 상태를 계속 들고 있다. "파일값≠메모리값"이라는 이 원리는 이미 두 곳에서 각론으로 만났다: 환경변수는 프로세스 시작 시점의 스냅샷이었고(O1), 브라우저가 받는 것은 소스가 아니라 빌드 시점의 산출물이었다(O2). 이 문서는 그 각론들을 하나의 파이프라인으로 이어, "어디서 옛 값이 살아남았는가"를 찾는 일반 진단법으로 종합한다.

2. 파이프라인 — 값이 복사·고정되는 다섯 관문

소스의 한 줄이 브라우저 화면에 도달하기까지의 경로를 관문 단위로 펼치면 다음과 같다. 각 관문의 오른쪽에 적은 것이 그 관문이 붙잡고 있는 스냅샷 — 즉 옛 값이 살아남을 수 있는 은신처다.

┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ ① 소스 │ → │ ② 빌드 │ → │ ③ 서빙 │ → │ ④ 포트 │ → │ ⑤ 브라우저│ └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘ 저장 안 된 빌드 시점의 서빙 루트의 시작 시점 다운로드 편집 내용, 소스 스냅샷 (옛) 산출물, 스냅샷을 든 시점의 캐시, 다른 브랜치 = 번들 루트 불일치 (다른) 프로세스 메모리의 옛 JS 각 화살표(→)가 복사 행위: 저장 / 빌드 / 배치·복사 / 로드·기동 / 전송 복사가 빠지면 → 그 지점 이후는 전부 옛 값으로 흐른다

관문이라는 표현을 쓰는 이유는, 값이 각 단계를 통과한 시점에 고정되기 때문이다. 번들은 빌드 버튼을 누른 순간의 소스를 얼려 담고, 프로세스는 기동한 순간의 설정을 얼려 담고, 브라우저 캐시는 다운로드한 순간의 파일을 얼려 담는다. 따라서 "반영 안 됨"은 신비로운 현상이 아니라, 다섯 개의 얼음 중 어느 하나가 안 녹은 것이다. 문제는 겉보기 증상(화면이 옛날 그대로)만으로는 어느 얼음인지 알 수 없다는 것 — 그래서 확인 절차가 필요하다.

3. 진단 — 관문을 하나씩 끊는 순서

원칙은 하나다: 각 관문에서 그 계층의 실제 산출물을 직접 관측해, "여기까지는 새 값"인 마지막 지점을 찾는다. 새 값이 옛 값으로 바뀌는 경계 — 거기가 안 녹은 얼음이다. 상류(소스)부터 순서대로:

관문확인 질문확인 방법 (그 계층의 산출물을 직접)
① 소스디스크의 파일이 정말 새 값인가편집기 버퍼 말고 저장된 파일을 다시 열기·grep. 브랜치·작업 디렉터리가 맞는지도 — "다른 체크아웃을 고치고 있었다"는 실화가 흔하다
② 빌드산출물에 새 값이 들어갔는가산출 디렉터리에서 새 값 문자열을 grep. 산출물의 수정 시각이 방금인지 확인 — 빌드가 실패했는데 옛 산출물이 남아 "성공처럼" 보이는 경우를 걸러낸다
③ 서빙서버가 그 산출물을 내보내는가브라우저 말고 curl로 원본 응답을 받아 새 값 확인 — 브라우저 캐시(⑤)를 건너뛰고 서버만 순수하게 관측하는 방법. 서빙 루트가 산출 디렉터리와 일치하는지(O2의 좌표 문제)
④ 포트내가 보는 주소의 프로세스가 내가 방금 띄운 그 프로세스인가포트 점유 프로세스 확인(lsof -i :포트 류). 어제 띄워둔 옛 프로세스가 포트를 잡고 있고 새 프로세스는 다른 포트로 떴다면 — 지금 보는 화면의 출처 자체가 다르다
⑤ 브라우저브라우저가 새 응답을 받아 실행 중인가캐시 우회 새로고침·개발자 도구의 네트워크 탭에서 응답이 캐시인지(304/디스크 캐시 표기) 서버발인지 구분. 탭이 옛 JS를 메모리에 물고 있을 수도 — 탭 자체를 새로

이 절차가 이분 탐색인 이유. 아무 관문이나 하나 확인하면, 결과가 "새 값"이면 문제는 그 하류에, "옛 값"이면 그 상류(또는 그 관문 자체)에 있다 — 용의 구간이 절반으로 준다. 경험상 빠른 출발점은 가운데인 ③ 서빙이다: curl 한 방이 "서버까지는 정상 / 서버부터 문제"를 갈라, 앞 셋과 뒤 둘 중 어느 쪽을 팔지 즉시 정해 준다.

그리고 각 관문의 "왜 안 녹았는가"에는 각자의 세부 이론이 있다: ④ 프로세스가 옛 설정을 무는 기제는 O1(시작 시점 로드)이, ③ 서빙 루트·base 불일치는 O2(경로 좌표)가, ⑤ 브라우저가 옛 파일을 무는 기제와 그 구조적 해법(콘텐츠 해시)은 M4가 다룬다. 이 문서의 역할은 어느 각론으로 들어갈지를 결정하는 상위 절차다.

4. 왜 감으로 하면 실패하는가 — 무작위 재시도의 함정

절차 없이 이 문제를 만나면 보통 "일단 다 다시" 전략이 나온다: 재빌드하고, 재시작하고, 캐시 지우고, 새로고침. 자주 통하지만 두 가지 대가가 있다. 첫째, 고쳐져도 무엇이 문제였는지 모른다 — 같은 문제가 다음 주에 또 오고, 또 전부 다시 한다. 둘째, 더 나쁜 경우로, 여러 조치를 한꺼번에 하면 진짜 원인이 아닌 조치를 원인으로 오학습한다("이건 캐시 문제야"라는 미신의 탄생). 관문 절차는 확인 한 번에 하나의 사실만 확정하므로, 끝났을 때 "③과 ④ 사이가 문제였고, 원인은 서빙 루트가 옛 디렉터리였다"는 재사용 가능한 지식이 남는다.

흔히 헷갈리는 지점 — "일단 전부 리셋"이 위험해지는 순간. 전부 리셋은 증거도 함께 지운다. 옛 산출물의 타임스탬프, 포트를 잡고 있던 프로세스, 캐시된 응답 — 이들이 "왜 이렇게 됐는가"의 증거인데, 리셋 후에는 재발해도 조사할 단서가 없다. 급하지 않다면 관측 먼저, 리셋은 원인 확정 후.

5. 흔히 헷갈리는 지점 (종합)

  • "방금 빌드했으니 산출물은 새것"이라는 가정. 빌드는 실패할 수 있고, 실패해도 옛 산출물은 디스크에 남아 있다. 터미널의 성공 메시지가 아니라 산출물의 내용·시각이 증거다.
  • "화면이 떴으니 서버는 정상"이라는 가정. 뜬 화면이 캐시일 수 있고(⑤), 다른 프로세스의 응답일 수 있다(④). 화면은 다섯 관문 전체의 합성 결과라서, 그 자체로는 어느 관문의 상태도 증언하지 못한다.
  • 확인 수단이 관문을 건너뛰는 경우. "브라우저로 확인"은 ③을 보는 것 같지만 실제로는 ③+④+⑤의 합성을 보는 것이다. 관문 하나만 순수하게 관측하는 수단(curl, grep, 포트 조회)을 골라야 이분 탐색이 성립한다.
  • 정적/동적의 경계는 상대적이다. 번들은 서빙 관점에선 정적(디스크의 파일)이지만 소스 관점에선 동적(빌드 시점의 스냅샷)이다. "이 값은 어느 시점에 고정된 것인가"를 관문 기준으로 묻는 습관이 혼란을 없앤다.

★ 6. 언어별 대조

"고쳤는데 옛것이 돈다"는 웹 파이프라인만의 문제가 아니다. 어떤 언어든 소스와 실행 표현 사이에 캐시나 변환 산출물이 끼는 지점에서 같은 구조가 재현된다 — 언어별로 그 은신처가 어디인지가 다를 뿐이다.

언어옛 값의 은신처녹이는 방법
Java로드된 클래스(클래스로더가 시작 시 고정)·빌드 도구의 증분 캐시재기동이 원칙. 핫스왑은 메서드 본문 수준의 제한적 교체
JS·TS번들(빌드 스냅샷)·개발 서버의 모듈 캐시·Node의 require 캐시재빌드 / HMR(변경 모듈만 런타임 교체 — 단 상태는 남을 수 있음)
Pythonsys.modules의 import 캐시·.pyc 바이트코드 캐시인터프리터 재시작이 원칙. importlib.reload는 부분 해법
C++스테일 오브젝트 파일·빌드 시스템의 의존성 누락·컴파일러 캐시의존성 그래프 수선 또는 클린 빌드

6.1 Python — import 캐시: "파일을 고쳤는데 모듈은 옛날 것"

Python은 모듈을 처음 import할 때 실행 결과 객체를 sys.modules에 캐시하고, 이후의 import는 파일을 다시 읽지 않고 캐시를 돌려준다. 장시간 도는 프로세스(서버, 노트북 세션, 대화형 셸)에서 모듈 파일을 고치는 순간, 디스크(정적)와 sys.modules(동적)가 갈라진다 — 이 문서의 파이프라인에서 ②빌드+④프로세스 관문이 합쳐진 형태다. 

import helper                 # 디스크에서 읽어 실행 → sys.modules['helper']에 캐시
helper.greet()                # "hello v1"

# --- 이 사이에 helper.py를 고쳐 "hello v2"로 저장 ---

import helper                 # 파일을 다시 읽지 않는다! 캐시 반환
helper.greet()                # 여전히 "hello v1"   ← 파일값 ≠ 메모리값

import importlib
importlib.reload(helper)      # 강제 재로드 — 그러나 부분 해법:
helper.greet()                # "hello v2". 단, 다른 모듈이
                              # from helper import greet 으로 가져간 참조나
                              # 이미 만들어진 인스턴스의 클래스는 여전히 v1을 가리킴

Python 관점의 통찰: reload가 부분 해법인 이유는 "복사가 이미 퍼졌기 때문"이다 — from-import는 이름을, 인스턴스는 클래스 참조를 각자 복사해 갔고, reload는 sys.modules의 원본만 바꾼다. 관문 모델로 말하면 상류 관문 하나를 녹여도 하류에 이미 흘러간 스냅샷들은 그대로라는 것 — 그래서 웹 프레임워크 개발 서버들이 reload 대신 프로세스 통째 재시작을 택한다: 모든 관문을 한 번에 확실히 녹이는 유일한 방법이다.

6.2 C++ — 스테일 산출물: 빌드 시스템이 의존을 놓칠 때

C++의 빌드는 번역 단위별 오브젝트 파일을 만들고 바뀐 것만 다시 컴파일하는 증분 빌드가 기본이다. "무엇이 바뀌었는가"의 판정은 빌드 시스템의 의존성 그래프가 맡는데, 이 그래프가 현실과 어긋나면 — 헤더 의존이 누락됐거나, 파일 시각이 꼬였거나, 생성 코드가 추적 밖이거나 — 일부만 새로 컴파일된 혼혈 바이너리가 나온다. 특히 헤더의 구조체 정의를 고쳤는데 일부 오브젝트 파일만 재컴파일되면, 같은 타입을 서로 다른 메모리 배치로 아는 코드가 한 바이너리에 공존한다 — 단일 정의 규칙(ODR: 프로그램 전체에서 하나의 타입·함수는 하나의 정의만 가져야 한다는 규칙) 위반이며, 컴파일도 링크도 통과한 채 런타임에 영문 모를 오동작으로 나타난다. 

# 진단: "소스를 고쳤는데 동작이 안 바뀐다 / 괴상하게 바뀐다"
$ grep -rn "NEW_FIELD" build/       # ② 산출물에 새 심볼이 들어갔는가
$ ls -lt build/*.o | head           # 재컴파일된 파일과 안 된 파일의 시각 대조
                                    #  → 헤더를 고쳤는데 일부 .o가 옛 시각이면
                                    #    의존성 그래프가 그 파일의 헤더 의존을 모르는 것

# 처방: 의존성 자동 추적(-MMD 류) 확인 / 최후엔 클린 빌드
$ rm -rf build && cmake --build .   # 모든 관문을 확실히 녹이는 리셋

C++ 관점의 통찰: 증분 빌드는 "정적→동적 복사를 전부 다시 하지 않고 바뀐 부분만"이라는 최적화이고, 그 대가는 '무엇이 바뀌었는지'의 장부(의존성 그래프)를 정확히 유지해야 한다는 부채다. 장부가 틀리면 최적화는 스테일 상태 제조기가 된다 — 캐시가 있는 곳에 무효화 문제가 있다는 일반 법칙의 컴파일 타임 버전이며, 브라우저 캐시(⑤ 관문)와 정확히 같은 구조다.

6.3 Java / JS·TS — 한 줄 요약

Java는 클래스가 로드 시점에 고정되는 모델이라 "고치면 재기동"이 문화적 기본값이고, 디버거의 핫스왑이 메서드 본문 교체라는 좁은 예외를 제공한다 — 그 좁음이 오히려 관문 원리의 방증이다. JS·TS의 HMR은 바뀐 모듈만 런타임에 갈아끼우는 정교한 관문 우회지만, 교체된 모듈 바깥에 살아남은 상태(전역, 클로저에 잡힌 옛 참조)까지는 책임지지 않는다 — "HMR 후 이상하면 일단 전체 새로고침"이라는 관행이 존재하는 이유다.

7. 함께 알면 좋은 것

  • 재현 가능한 빌드(reproducible build) — 같은 소스에서 항상 같은 산출물이 나오게 하는 규율. "산출물이 소스의 어느 시점인가"라는 질문 자체를 검증 가능하게 만든다.
  • 빌드 정보 심기 — 산출물·응답 헤더에 버전/커밋 해시를 넣어 두면 ③·⑤ 관문 확인이 "문자열 grep"에서 "버전 대조"로 단순해진다. 배포 검증의 표준 기법.
  • 콘텐츠 해시 파일명 — ⑤ 관문(브라우저 캐시)의 구조적 해법: 내용이 바뀌면 URL이 바뀌므로 옛 캐시가 참조될 수 없다. 상세는 M4.
  • 프로세스 관리자의 재시작 의미론 — reload/restart/재기동의 차이(무엇을 다시 읽는가)는 도구마다 계약이 다르다. ④ 관문을 녹였다고 믿었는데 안 녹은 사고의 흔한 출처.
  • 불변 배포(immutable deployment) — 실행 중인 것을 고치지 않고 새 산출물·새 프로세스로 통째 교체하는 배포 철학. 관문들의 부분 갱신이 만드는 혼혈 상태 자체를 설계로 제거한다.

8. 한 장 요약

  • 고치는 것은 정적 상태(디스크), 확인하는 것은 동적 상태(실행 중) — 둘 사이의 동기화는 명시적 복사 행위로만 일어난다.
  • 파이프라인 다섯 관문: 소스→빌드→서빙→포트→브라우저. 각 관문은 통과 시점의 스냅샷을 문다.
  • 진단 = 각 관문의 실제 산출물을 직접 관측해 새 값→옛 값 경계를 찾는 이분 탐색. 가운데(curl로 서빙)부터 끊으면 빠르다.
  • 화면은 다섯 관문의 합성이라 아무 관문도 증언하지 못한다 — 관문 하나만 보는 순수한 관측 수단을 골라라.
  • "일단 전부 리셋"은 증거를 지우고 미신을 만든다. 관측으로 원인을 확정한 뒤 리셋하라.
  • 언어 세계의 같은 구조: Python의 import 캐시, C++의 스테일 오브젝트, Java의 로드된 클래스, JS의 HMR 잔존 상태 — 캐시가 있는 곳에 무효화 문제가 있다.

O7 에러 재래핑과 진단 경로

0. 한눈에 보는 결론

  • 예외는 계층을 건널 때마다 재래핑(rewrapping)된다 — 각 계층이 자기 추상화 수준의 예외로 감싸 올리는 것은 정상 설계이지, 사고가 아니다.
  • 문제는 재래핑이 대부분 손실적이라는 데 있다: 원인 정보는 계층을 오를수록 깎이고, 특히 원격 호출·언어 경계·UI 경계에서 크게 뭉개진다.
  • 그 결과 근본 원인은 원천 계층의 로그에만 남고, 사용자가 보는 표면에는 일반화된 문구("일시적인 오류가 발생했습니다")만 도달한다.
  • 따라서 표면 문구를 읽고 원인을 추정하는 것은 진단이 아니다 — 서로 다른 수십 가지 원인이 같은 표면 문구 하나로 수렴하기 때문이다.
  • 올바른 진단 경로는 표면에서 원인을 "생각해 내는" 것이 아니라, 계층 지도를 따라 원천 로그로 직행하는 것 — 이를 가능하게 하는 장치가 원인 체인 보존과 상관관계 ID다.
  • 설계 규율 한 줄: 재래핑할 때 원인을 버리지 말 것(cause 연결·원천 식별자 전파). 진단 규율 한 줄: 표면은 출발점일 뿐, 판단은 원천에서.

1. 예외는 계층을 건널 때마다 다시 포장된다

주문 저장 버튼을 눌렀더니 화면에 "일시적인 오류가 발생했습니다"가 떴다고 하자. 이 문구가 만들어지기까지의 경로를 거꾸로 추적해 보면, 이 문서가 다루는 구조 전체가 드러난다. 실제로 벌어진 일은 데이터베이스의 고유 제약 위반(unique constraint violation) 하나였다:

DB: "duplicate key value violates unique constraint orders_number_key" ↓ 드라이버/ORM 계층 — DB 방언 예외를 프레임워크 표준 예외로 변환 DataIntegrityViolationException (원본은 cause로 첨부) ↓ 서비스 계층 — 도메인 언어로 재래핑 OrderConflictException("주문번호 중복") ↓ API 계층 — HTTP 응답으로 직렬화 (여기서 스택·cause 소멸) HTTP 409 { "error": "CONFLICT" } ↓ 프론트엔드 — 사용자 언어로 최종 포장 "일시적인 오류가 발생했습니다"

각 화살표가 하나의 재래핑이다. 그리고 짚어야 할 것은, 이 재래핑들 하나하나는 전부 정당하다는 점이다. ORM이 DB 방언을 감추는 것은 이식성을 위한 추상화 계약이고, 서비스가 도메인 예외로 바꾸는 것은 호출자가 인프라를 몰라도 되게 하기 위함이며, API가 내부 예외를 그대로 내보내지 않는 것은 정보 노출을 막는 보안 원칙이고, 프론트가 기술 용어를 감추는 것은 사용자 배려다. 계층화 아키텍처를 택한 순간 재래핑은 필연이다 — 각 계층은 자기 추상화 수준의 언어로 말해야 하고, 예외도 그 언어의 일부이기 때문이다.

문제는 재래핑 자체가 아니라 재래핑의 손실률이다. 위 경로에서 정보량이 어떻게 변하는지 보라. DB 메시지에는 어느 제약이 어떤 값으로 깨졌는지까지 있었다. 서비스 예외에는 "주문번호 중복"이라는 요지만 남았다. HTTP 응답에는 분류 코드 하나만 남았다. 화면에는 원인과의 연결 고리가 하나도 없는 문구만 남았다. 특히 세 종류의 경계에서 손실이 급격하다: 원격 호출 경계(스택 트레이스와 예외 객체는 프로세스를 건너지 못한다 — 직렬화된 요약만 건넌다), 언어 경계(한쪽의 예외 체계가 다른 쪽에 존재하지 않는다), UI 경계(기술 정보를 의도적으로 전부 감춘다).

핵심 프레임: 예외 전파를 손실 압축의 연쇄로 보라. 각 계층은 아래층의 풍부한 정보를 자기 어휘로 압축해 올린다. 압축은 필요한 일이지만, 압축된 결과물(표면 문구)에서 원본(근본 원인)을 복원할 수는 없다. 복원이 안 되면 어떻게 하는가 — 원본이 있는 곳으로 가야 한다. 그것이 3절의 진단 경로다.

2. 표면 문구로 판단하면 안 되는 이유 — 다대일 수렴

앞 절의 압축 연쇄가 진단에 무엇을 의미하는지부터 정확히 하자. 손실 압축의 수학적 귀결은 다대일 사상이다: 서로 다른 많은 원인이 같은 표면 문구 하나로 수렴한다. "일시적인 오류가 발생했습니다"의 자리에 올 수 있었던 원인을 나열해 보면 — 주문번호 중복, DB 커넥션 풀 고갈, 원격 결제 서비스 타임아웃, 역직렬화 실패, 배포 직후 스키마 불일치, 메모리 부족… 전부 같은 문구다. 표면 문구가 주는 정보는 "무언가 실패했다"에서 크게 나아가지 않는다.

그런데도 표면 문구로 원인을 추정하고 싶은 유혹은 강하다. 이유는 그 문구가 지금 눈앞에 있는 유일한 단서이기 때문이다. 이 유혹이 위험한 것은 두 가지 방향으로 오판을 만들기 때문이다. 첫째, 과잉 해석: "타임아웃이라고 떴으니 네트워크 문제겠지" — 하지만 그 문구는 상위 계층이 여러 실패를 뭉뚱그려 타임아웃으로 번역한 결과일 수 있다. 실제 원인은 아래층의 느린 쿼리였는데 표면에서는 타임아웃으로 보이는 식이다. 둘째, 익숙한 문구와의 성급한 대조: "저번에도 이 문구였고 그때는 캐시 문제였으니 이번에도" — 다대일 수렴 구조에서 같은 표면 문구는 같은 원인을 전혀 보증하지 않는다.

개념 함정: 표면 문구는 원인의 요약이 아니라 원인의 "분류 결과"다. 그것도 각 계층의 번역 규칙이 몇 단계 누적된 분류다. 분류 결과를 보고 개별 사례를 단정하는 것은, 우편번호만 보고 그 집의 내부 구조를 단정하는 것과 같다 — 방향은 맞을 수 있어도 판단 근거는 되지 못한다.

그렇다면 표면 문구의 올바른 용도는 무엇인가. 검색 키이자 출발점이다. 문구·에러 코드·발생 시각은 "어느 계층의 로그부터 뒤질 것인가"를 정하는 좌표로는 유용하다. 판단을 표면에서 내리지 않고 좌표로만 쓴다는 것 — 이 태도 전환이 다음 절의 진단 경로로 이어진다.

3. 진단 경로 — 원천 로그로 직행하기

표면에서 판단할 수 없다면 어디서 판단하는가. 1절의 압축 연쇄를 다시 보면 답이 나온다. 정보는 위로 갈수록 깎였으므로, 가장 풍부한 기록은 실패가 처음 발생한 원천 계층에 있다. 진단이란 압축의 연쇄를 거슬러 내려가 그 기록에 도달하는 일이고, 잘 설계된 시스템은 이 하강을 몇 번의 조회로 끝나게 만든다. 하강을 빠르게 만드는 장치가 두 가지 있다.

첫째, 원인 체인 보존. 재래핑이 손실적이 되는 이유의 절반은 습관 문제다 — 감쌀 때 원본 예외를 버리는 것. 대부분의 언어는 예외에 원인(cause)을 연결하는 표준 수단을 제공하며(5절에서 언어별로 본다), 원인을 연결해 두면 한 계층의 로그 안에서 표면 예외부터 근본 원인까지의 전체 체인이 한 번에 남는다. "감쌀 때는 반드시 원인을 첨부한다"는 한 줄 규율이, 진단 시 계층을 하나하나 파 내려가는 수고를 로그 한 화면으로 줄여 준다. 

// 나쁜 재래핑 — 원인을 버린다 (진단 경로 절단)
catch (DataIntegrityViolationException e) {
    throw new OrderConflictException("주문번호 중복");
}
// 좋은 재래핑 — 원인을 연결한다 (체인이 로그에 함께 남는다)
catch (DataIntegrityViolationException e) {
    throw new OrderConflictException("주문번호 중복", e);   // cause 첨부
}

둘째, 상관관계 ID(correlation ID) 전파. 원인 체인은 한 프로세스 안에서만 유효하다 — 예외 객체는 원격 경계를 건너지 못하기 때문이다. 경계 너머까지 진단 경로를 잇는 표준 장치가, 요청 진입 시점에 고유 ID를 발급해 모든 계층·모든 서비스의 로그에 함께 찍는 상관관계 ID다. 이제 표면에서 출발하는 하강은 "각 계층에서 시각과 정황으로 짐작해 뒤지기"가 아니라 ID 하나로 전 계층 로그를 꿰어 보기가 된다:

표면 문구 + 발생 시각 + (응답에 실린) 상관관계 ID → 로그 시스템에서 ID로 검색 → 전 계층의 기록이 시간순으로 정렬됨 → 체인의 가장 아래(원천 계층 기록)에서 판단

로그를 어떻게 남기고 모아 검색 가능하게 만드는가 — 구조화 로깅과 수집 파이프라인 — 는 P1 로깅과 관측성 기초.html의 소관이다. 이 문서의 요지는 그 인프라를 전제로 한 경로의 방향이다: 표면 → ID → 원천, 그리고 판단은 원천에서. 장애 상황에서 이 경로를 어떤 절차와 우선순위로 밟는가(영향 파악·전파·복구 우선 판단)는 O5 장애 대응 기초.html이 다루며, O5가 "원인 조사는 원천 로그에서"라고 위임한 그 구조적 근거가 바로 이 문서다.

설계·진단 규율 요약: ① 재래핑할 때 원인을 버리지 않는다(cause 연결). ② 경계를 건널 때는 상관관계 ID를 전파한다. ③ 원천 계층에서는 판단에 필요한 문맥(어느 제약·어느 값·어느 자원)을 로그에 남긴다. ④ 진단은 표면 문구 해석이 아니라 원천 로그 직행으로 한다. 앞의 셋이 설계 시점의 투자, 마지막이 그 투자를 회수하는 순간이다.

4. 흔히 헷갈리는 지점

  • "재래핑이 나쁜 것이니 원본 예외를 그대로 위로 던지면 된다?" — 반대편 함정이다. 원본을 그대로 관통시키면 상위 계층이 하위 구현에 결합되고(ORM 예외가 컨트롤러까지 올라오면 ORM 교체가 전 계층 수정이 된다), API 경계에서는 내부 구조 노출이라는 보안 문제가 된다. 정답은 "래핑하지 않기"가 아니라 "손실 없이 래핑하기"다.
  • "cause를 연결했으니 어디서든 원인을 볼 수 있다?" — cause 체인은 프로세스 안에서만 산다. HTTP 응답·메시지 큐로 직렬화되는 순간 체인은 끊긴다. 경계 밖으로는 체인이 아니라 식별자(상관관계 ID)가 건너가야 한다.
  • "에러 메시지를 상세하게 쓰면 표면에서도 판단할 수 있게 되지 않나?" — 표면 문구를 상세화하는 데는 천장이 있다. 사용자에게 스택을 보여 줄 수 없고, 공개 API 응답에 내부 구조를 실을 수 없다. 상세함은 로그에, 표면에는 분류와 추적 식별자에 — 정보의 목적지를 나누는 것이 정답이지, 한쪽을 다른 쪽 용도로 확장하는 것이 아니다.
  • "로그에 스택 트레이스가 있으면 근본 원인이 있는 것이다?" — 스택 트레이스는 "그 예외가 던져진 지점까지의 호출 경로"이지 근본 원인의 서술이 아니다. cause 없는 래핑 예외의 스택은 래핑한 지점을 가리킬 뿐이며, 근본 원인은 몇 계층 아래의 다른 기록에 있을 수 있다. 스택의 최상단이 아니라 체인의 최하단을 봐야 한다.
  • "같은 문구가 여러 건 쌓이면 같은 장애다?" — 다대일 수렴의 재판이다. 표면 문구 기준의 집계는 서로 다른 원인들을 한 버킷에 섞는다. 집계·알림의 기준 키는 표면 문구가 아니라 원천 계층의 에러 분류여야 한다.

5.1 Java — 체인은 표준이 갖췄고, 함정은 변환 계층의 습관에 있다

Java는 원인 체인이 언어 표준에 가장 깊이 들어간 언어다. 모든 예외 생성자가 cause를 받을 수 있고, 로그에 찍히는 스택 트레이스는 Caused by: 연쇄로 체인 전체를 자동 출력한다. 검사 예외(checked exception)의 존재는 재래핑을 문법적으로 강제하는 효과가 있다 — 하위 계층의 검사 예외를 처리하거나 감싸지 않으면 컴파일이 안 되므로, Java 코드에는 래핑 지점이 유난히 많고, 그만큼 "cause 누락" 실수가 발생할 표면적도 넓다. 

try {
    repository.save(order);
} catch (SQLException e) {
    // 검사 예외라 반드시 처리해야 함 — 이 강제된 래핑 지점이 cause 누락의 최다 발생지
    throw new OrderPersistenceException("주문 저장 실패", e);  // e를 빼먹는 순간 경로 절단
}

생태계 차원의 특기 사항은 예외 변환 계층이다. Spring의 데이터 접근 예외 변환이 대표적인데, DB 드라이버·ORM마다 다른 DB 예외를 공통 계층(DataAccessException 하위 분류)으로 번역하면서 원본을 cause로 보존한다 — 1절에서 본 "손실 없는 재래핑"을 프레임워크가 규약화한 사례다. JVM 내부 기제로는, JIT 컴파일러가 같은 지점에서 반복 발생하는 예외의 스택 트레이스 생성을 생략하는 최적화가 있어(핫 루프에서 스택이 빈 예외가 관찰되는 원인), "로그에 스택이 없다"가 코드 문제가 아니라 런타임 최적화일 수 있다는 점도 진단 시 알아 둘 가치가 있다.

5.2 JS·TS — 체인보다 먼저, 비동기 틈으로 새는 예외를 막아야 한다

JavaScript의 Error에 표준 원인 연결(cause 옵션)이 들어온 것은 ES2022로 비교적 최근이다(2020년대 초반 표준화). 그 전까지는 커스텀 속성으로 흉내 냈기 때문에 로거·에러 수집기가 체인을 따라가 주는지가 제각각이었고, 지금도 console.log가 아닌 로거를 쓴다면 cause를 재귀 출력하는지 확인이 필요하다. 

try {
  await saveOrder(order);
} catch (e) {
  throw new Error("주문 저장 실패", { cause: e });   // ES2022 표준 체인
}

// 함정: await를 빼먹으면 catch가 잡지 못한다
try {
  saveOrder(order);        // Promise가 떠 있는 채로 try를 벗어남
} catch (e) { /* 도달 불가 */ }
// → 거부는 unhandledrejection으로 새어나감 — 진단 경로 바깥의 실패

JS 특유의 함정은 이벤트 루프가 만드는 비동기 틈이다. 예외 전파는 호출 스택을 따라가는데, 비동기 콜백·미대기 Promise의 실패 시점에는 원래의 호출 스택이 이미 사라져 있다. await로 이어진 경로는 엔진이 비동기 스택 트레이스를 이어 붙여 주지만, await 누락·콜백 API 혼용 지점에서는 "어디서 시작된 요청인지"가 스택에서 사라진다 — 프로세스 안인데도 원격 경계처럼 손실이 일어나는 셈이라, 상관관계 ID를 요청 문맥에 실어 두는 장치가 서버 JS에서 특히 값지다. 마지막으로 브라우저 배포 환경에서는 압축(minification)이 스택의 함수명·행 번호를 뭉개므로, 소스 맵을 에러 수집기에 연결해야 프론트 표면의 스택이 진단 가능한 형태로 복원된다.

5.3 Python — 체인이 자동이라 편하지만, 자동이라서 생기는 오독이 있다

Python은 원인 체인을 자동으로 남기는 유일한 축이다. except 블록 안에서 새 예외를 던지면 언어가 앞 예외를 __context__로 붙여 traceback에 "During handling of the above exception, another exception occurred"로 출력한다. 의도적 재래핑은 raise ... from e로 __cause__를 명시한다: 

try:
    repository.save(order)
except IntegrityError as e:
    raise OrderConflictError("주문번호 중복") from e   # 명시적 체인(__cause__)
    # from을 빼도 __context__로 자동 연결은 되지만, 의미가 달라진다:
    # "이것 때문에 던졌다"(cause)가 아니라 "처리 중에 우연히 겹쳤다"(context)로 읽힌다

함정은 그 자동성의 이면이다. __context__ 자동 연결은 의도한 재래핑과 에러 처리 중의 2차 사고를 같은 모양으로 출력하므로, from을 생략하는 습관은 로그 독자에게 "원인인가, 우연인가"라는 불필요한 해석 부담을 넘긴다. 반대로 raise ... from None은 체인을 의도적으로 절단하는 문법인데, "로그를 깔끔하게"라는 이유로 남용하면 1절의 손실적 재래핑을 언어 차원에서 실행하는 것이 된다. 객체 모델 관점의 통찰 하나: Python의 traceback은 예외 객체에 붙은 일급 데이터라 (e.__traceback__), 로깅 프레임워크가 체인 전체를 구조화해 남기기 쉽다 — logging.exception() 한 줄이 체인 포함 전체 기록을 남기는 표준 관용구다.

5.4 C++ — 체인도 수동, 경계는 예외가 아예 못 건너는 벽

C++에는 자동 원인 체인이 없다. 표준이 주는 도구는 std::throw_with_nested·std::rethrow_if_nested로, 현재 예외를 안에 품은 예외를 던지고 잡는 쪽에서 재귀적으로 풀어내는 수동 체인이다. 스택 트레이스조차 표준 예외에는 실리지 않아(문자열 what()이 전부), 발생 지점 기록부터가 라이브러리·수동 구현의 몫이다: 

void save_order(const Order& o) {
    try {
        repo.save(o);
    } catch (...) {
        std::throw_with_nested(OrderError("주문 저장 실패"));  // 수동 체인
    }
}
void log_chain(const std::exception& e, int depth = 0) {
    log(depth, e.what());
    try { std::rethrow_if_nested(e); }              // 안쪽 예외를 다시 던져서
    catch (const std::exception& inner) { log_chain(inner, depth + 1); }  // 재귀로 풀기
}

C++의 진짜 특이점은 경계의 경도다. 예외는 C ABI(바이너리 호출 규약)를 건널 수 없다 — C 콜백이나 extern "C" 함수 밖으로 예외가 전파되면 미정의 동작 또는 즉시 종료(std::terminate)다. 스레드 경계도 마찬가지여서, 다른 스레드로 예외를 넘기려면 std::exception_ptr로 캡처해 명시적으로 운반해야 한다. 그래서 C++ 시스템의 경계 계층은 예외를 에러 코드·결과 타입으로 번역하는 층을 반드시 갖게 되는데, 이 번역이 1절에서 본 손실 압축의 가장 급격한 형태다 — 풍부한 예외 객체가 정수 코드 하나로 깎인다. 번역 지점에서 원천 정보를 로그로 남기는 규율이 다른 언어보다 한층 절실한 이유다. 수명 관점의 주의 하나: 예외 객체가 소멸된 뒤의 what() 포인터를 로그 큐에 넘기는 식의 실수는 진단 기록 자체를 오염시키므로, 경계에서는 문자열을 값으로 복사해 남긴다.

6. 함께 알면 좋은 것

  • 분산 트레이싱(distributed tracing) — 상관관계 ID를 표준화·자동화한 생태계. W3C Trace Context 헤더와 OpenTelemetry가 2020년대의 사실상 표준으로, 요청이 거친 전 서비스·전 구간을 하나의 트레이스로 이어 준다. 이 문서의 "ID로 꿰기"를 수작업에서 플랫폼 기능으로 올려 주는 도구.
  • 구조화된 에러 응답 표준 — HTTP API의 에러 본문을 기계 판독 가능하게 규격화한 RFC 9457(Problem Details, 구 RFC 7807). "표면에는 분류와 추적 식별자"라는 3절의 원칙을 응답 포맷 차원에서 실현한다.
  • 에러 분류 체계(taxonomy) — 재시도 가능/불가, 클라이언트 잘못/서버 잘못 같은 분류 축을 예외 계층에 새기는 설계. 재래핑이 "정보를 깎는 일"에서 "판단에 필요한 분류를 부여하는 일"로 바뀐다. 예외 계층 설계 전반은 C16 예외 처리 전략.html 소관.
  • 에러 수집기(error tracker) — 표면까지 올라온 에러를 스택·문맥과 함께 자동 수집·집계하는 서비스류. 집계 키가 표면 문구가 아니라 스택 지문(fingerprint)이라는 점이 4절의 "표면 문구 집계 금지"와 정확히 같은 통찰이다.
  • 로그 레벨과 이중 기록 문제 — 같은 실패를 모든 계층이 ERROR로 찍으면 한 장애가 수십 건으로 부풀어 노이즈가 된다. 관례는 "처리(래핑)하는 곳은 낮은 레벨로, 최종 미처리 지점 한 곳만 ERROR로" — 체인 보존과 짝을 이루는 로깅 규율이다.

7. 한 장 요약

  • 재래핑은 계층화의 필연 — 각 계층은 자기 추상화 수준의 예외로 말한다. 문제는 래핑이 아니라 원인을 버리는 래핑이다.
  • 정보는 위로 갈수록 깎여, 근본 원인은 원천 계층 로그에만, 표면에는 일반 문구만 남는다 — 특히 원격·언어·UI 경계에서 급락한다.
  • 표면 문구는 다대일 수렴의 결과라 판단 근거가 못 된다 — 검색 좌표(출발점)로만 쓴다.
  • 진단 경로: 표면 → 상관관계 ID → 원천 로그 직행, 판단은 체인의 최하단에서.
  • 설계 투자 세 가지: cause 연결(프로세스 안), 상관관계 ID 전파(경계 너머), 원천 계층의 문맥 로깅.
  • 언어별: Java는 체인 표준·변환 계층 관례가 성숙, JS는 비동기 틈이 추가 손실원, Python은 자동 체인(대신 from 규율 필요), C++은 체인 수동·경계는 예외 불통과라 번역층 로깅이 사활적.
